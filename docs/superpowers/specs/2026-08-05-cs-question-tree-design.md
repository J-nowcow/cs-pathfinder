# CS 질문 트리 — 설계 문서

작성일: 2026-08-05
작업명: `cs-question-tree` (최종 서비스명 미정)

---

## 1. 문제

CS 면접 질문을 매일 하나씩 공유하는 카톡방이 있다. 질문 하나와 좋은 답변의 흐름, 그리고 꼬리질문 5~6개가 함께 올라온다.

문제는 형식이다. 카톡은 선형 텍스트라 꼬리질문이 나열만 되고 관계가 보이지 않는다. 어느 질문에서 어느 질문으로 뻗는지, 내가 어디까지 이해했는지가 드러나지 않는다. 꼬리질문의 꼬리를 파고들면 맥락이 끊긴다.

## 2. 해결 방향

질문을 **그래프**로 저장하고 사용자에게는 자기가 파고든 **경로를 트리로** 보여준다. 꼬리질문은 미리 다 만들어두지 않는다. 사용자가 누를 때 그 자리에서 생성하고, 만들어진 노드는 전역 자산으로 남겨 다음 사람이 재사용한다.

핵심 성질 세 가지가 설계 전체를 지탱한다.

- **CS 질문은 수렴한다.** 수백 명이 똑같이 "TCP 3-way handshake란?"을 판다. 이걸 캐시로 바꾸면 비용이 내려가고 콘텐츠가 쌓인다.
- **같은 질문은 여러 맥락에서 나온다.** DB 커넥션에서도, 네트워크에서도 나온다. 노드를 부모와 무관하게 하나만 두면 중복이 사라지고 교차 연결 자체가 학습 콘텐츠가 된다.
- **파고든 경로에는 서사가 있다.** 그래서 경로 묶음이 곧 공유 가능한 콘텐츠 단위가 된다.

### 기존 서비스와의 차이

가장 가까운 것은 **꼬꼬면**(kokomen.kr)이다. 이름부터 꼬리질문이고 CS·인프라 등 분야도 겹친다.

다만 성격이 반대에 가깝다. 꼬꼬면은 AI가 `Q1 → Q2 → Q3` 순서를 정하고 사용자는 답을 하며, 끝나면 총점과 종합 평가가 나온다. **시험**이다. 트리나 그래프 시각화는 없다.

이 서비스는 사용자가 어디로 팔지 고른다. 답변은 선택이고 적지 않아도 계속 판다. **탐험**이 먼저고 회상이 얹힌다.

정리하면 축이 셋 다르다.

| | 꼬꼬면 | 이 서비스 |
|---|---|---|
| 구조 | 선형 (AI가 순서 결정) | 분기 그래프 (사용자가 방향 선택) |
| 목적 | 답변 연습과 채점 | 지식 지도 탐험 |
| 축적 | 개인 면접 기록 | 전역 지식 그래프 (모두의 자산) |

한편 꼬꼬면의 결과 페이지에서 가져올 것도 있다. 노드별 답변·AI 피드백·등급 배지, 그리고 공유 페이지 상단의 AI 요약이다.

## 3. 범위

### 1차 범위

- 매일 자동 발행되는 오늘의 질문
- 추천 꼬리질문 클릭 + 자유 질문 입력으로 무한 확장
- 비로그인 체험 / 로그인 시 학습 기록 저장
- 노드별 답변 기록과 AI 피드백 (선택 입력)
- 트리 공유와 포크
- 트리 게시판 (인기·최신·카테고리)
- 모바일 포커스 읽기 + 지도 모드
- 생성 결과의 GitHub 레포 자동 커밋

### 범위 밖 (로드맵)

- 대분류 지도와 진척도 시각화 — 2차
- 교차 경로 배지 — 2차
- 노드 단위 집단지성 기여 (좋은 꼬리질문을 공식 트리에 병합) — 3차
- `curated` 트리 종류와 자동 승격 — 3차

라이선스가 없으면 권리 전부 보유다. 본문 복제는 불가하다. 다만 주제어 나열은 사실에 가까워 보호 강도가 낮고, 해설을 전부 새로 쓰므로 원문을 복제할 일이 없다. 이 방식이면 모든 레포를 소스로 쓸 수 있다.

목표는 주제어 400개다.

3. 데이터베이스
4. 자료구조 · 알고리즘

중분류 이하는 **설계하지 않는다.** 시드가 매일 소비되며 가지가 자라고 사용자가 파는 꼬리질문이 잔가지를 채운다. 미리 짜두면 생성 결과와 충돌한다.

### 초기 부트스트랩

카테고리가 10개라 하루 1개 발행으로는 모든 탭이 차기까지 오래 걸린다. 첫날부터 빈 탭이 보이면 서비스가 비어 보인다.

그래서 오픈 시점에 **카테고리당 3~5개를 미리 발행한다.** 배치 1회로 30~50개다. 이후에는 하루 1개 정상 발행으로 돌아간다.

## 5. 데이터 모델

### 저장은 그래프, 화면은 트리

바닥에 지식 그래프가 하나 깔린다. 사용자에게 보이는 트리는 전부 그 그래프에서 잘라낸 뷰다.

```
qnode ──< qedge >── qnode        지식 그래프 (DAG)
   ↑                    ↑
   │                    │
user_path            tree.node_ids
(개인 발자국)         (콘텐츠 단위)
```

### qnode — 질문 노드

| 필드 | 설명 |
|---|---|
| `id` | PK |
| `normalized_hash` | **유일키.** 정규화된 질문 텍스트의 해시. 부모와 무관 |
| `normalized_question` | 정규화 게이트가 만든 표준 질문 문장 |
| `question` | 질문 원문 (사용자가 입력한 그대로) |
| `body` | 해설 본문 |
| `suggestions` | 추천 꼬리질문 5개 (텍스트 배열) |
| `primary_category` | 최초 생성된 맥락의 대분류 |
| `origin` | `batch` \| `on_demand` |
| `created_at` | |

유일키가 부모를 포함하지 않는 것이 핵심이다. "TCP 3-way handshake란?"은 세상에 하나만 존재하고 DB 경로와 Network 경로 양쪽에서 도달한다.

카테고리가 단일 필드인 점에 주의한다. 노드는 여러 부모를 가질 수 있으므로 카테고리도 원래 여럿이다. `primary_category`는 최초 생성 맥락을 기록할 뿐이고, 실제로 어느 대분류에서 닿는지는 `qedge`를 거슬러 올라가 판정한다. 게시판 카테고리 필터도 노드가 아니라 `tree` 기준으로 건다.

해시는 `normalized_question`에 대해 계산한다. 텍스트 정규화는 공백 정리와 문장부호 통일 정도로 최소화한다. 표현 차이를 흡수하는 일은 정규화 게이트(LLM)가 맡고 해시는 그 결과를 그대로 받는다.

### qedge — 부모-자식 연결

| 필드 | 설명 |
|---|---|
| `parent_id` | qnode |
| `child_id` | qnode |
| `created_at` | |

다대다다. 그래서 구조는 트리가 아니라 DAG다. 삽입 시 순환 검사를 한다.

**화면은 여전히 트리다.** 사용자는 자기가 온 경로만 따라가므로 트리로 보인다. 다른 경로에서도 닿는다는 사실은 배지 한 줄로만 노출한다(2차).

### tree — 콘텐츠 단위

| 필드 | 설명 |
|---|---|
| `id`, `slug` | |
| `title` | |
| `kind` | `daily` \| `shared` |
| `root_node_id` | |
| `node_ids` | 포함 노드 배열 |
| `author_id` | `daily`는 null |
| `upvotes`, `views`, `forks` | |
| `published_at` | |

오늘의 질문과 사용자 공유 트리를 **한 테이블로 통합한다.** 게시판 정렬·상세 보기·포크가 종류에 상관없이 같은 코드로 돌아간다.

- `kind = daily` — 매일 배치가 발행. 루트 + 추천 꼬리 5개라 깊이 1로 시작
- `kind = shared` — 사용자가 판 경로 묶음. 깊이가 깊고 서사가 있다

`upvotes`는 정렬용으로만 쓴다. 자동 승격은 없다.

### user_path — 개인 발자국

| 필드 | 설명 |
|---|---|
| `user_id`, `qnode_id` | |
| `visited_at` | |

사용자가 소유하는 것은 노드가 아니라 발자국이다. "내 트리"는 내 발자국이 만든 부분그래프다.

그래서 공유는 복사가 아니라 발자국 묶음의 스냅샷이고, 포크는 그 발자국을 내 것으로 복제하는 것뿐이다. 노드 데이터는 한 벌만 유지된다.

### user_answer — 답변 기록

| 필드 | 설명 |
|---|---|
| `user_id`, `qnode_id` | |
| `answer` | 사용자가 적은 답 |
| `feedback` | AI 피드백 |
| `grade` | A~D |
| `created_at` | |

노드마다 답변란이 접힌 채로 있다. 적으면 AI 피드백과 등급이 붙고 해설이 자동으로 열린다.

**답변은 강제하지 않는다.** 이 서비스는 탐험이 먼저다. 답변을 필수로 만들면 시험이 되고 매일 오고 싶은 곳이 아니게 된다. 해설만 보고 넘어가도 되고 적고 싶을 때만 적는다.

답변은 사람마다 다르므로 **캐시가 먹지 않는다.** 그래서 피드백은 로그인 사용자 전용이고 확장 할당량과 별도로 잡는다.

### topic_seed / usage_quota

`topic_seed`는 주제어·카테고리·사용 여부를 갖는다. `usage_quota`는 키(비로그인은 IP+쿠키, 로그인은 user_id)·날짜·확장 횟수·답변 피드백 횟수를 갖는다.

## 6. 확장 흐름

"더 파기"를 눌렀을 때의 처리다.

```
① 입력          추천 꼬리 클릭 또는 자유 질문 입력
       ↓
② 정규화 게이트  Flash-Lite — 부모 질문과 연관 있는지 판정 + 표준 문장으로 정규화
       ↓         무관한 입력(번역·코드 대필 등)은 여기서 거절
③ 캐시 조회      normalized_hash로 qnode 검색
       ↓
   ┌───┴────────────────────────┐
 히트                          미스
 LLM 0회. 즉시 표시            Flash가 해설 + 꼬리 5개 생성 → qnode + qedge 저장
 할당량 미차감                 이 순간부터 모든 사용자의 자산
   └───┬────────────────────────┘
       ↓
④ 발자국 기록   로그인 상태면 user_path에 기록. 비로그인은 화면에만
```

정규화가 이 설계의 급소다. "코어 수로 정하는 이유가 뭔가요?"와 "왜 코어 수 기반?"이 같은 해시로 수렴해야 캐시가 작동한다. 여기가 깨지면 캐시가 통째로 무너진다.

부수 효과가 있다. 자유 질문이 정규화되어 쌓이면 많이 물어본 질문을 추천 꼬리로 승격시킬 수 있다. 3차 집단지성 기능의 토대가 여기서 공짜로 생긴다.

## 7. 화면

### 홈

오늘의 질문이 주인공이다. 히어로 카드로 크게 놓고 아래에 트리 게시판을 둔다. 매일 방문할 이유가 선명해야 습관이 붙는다. 게시판은 다 판 뒤에 둘러보는 곳이다.

게시판 탭은 인기 / 최신 / 카테고리 10개다. 탭이 많아 모바일에서는 가로 스크롤로 처리한다.

### 읽기 뷰

모바일이 기준이다. 카톡 링크를 타고 들어오니 첫 방문은 대부분 폰이다.

들여쓰기 트리는 쓰지 않는다. 무한 확장과 정면으로 충돌한다. 깊이 5단이면 질문 한 줄이 세로로 접힌다.

대신 **한 번에 질문 하나**를 전체 폭으로 보여준다. 깊이는 상단 경로 칩(breadcrumb)이 표현하고 칩을 누르면 그 지점으로 점프한다. 깊이가 아무리 깊어져도 화면은 그대로다. 뒤로 스와이프로 부모에 돌아간다.

화면 구성은 위에서부터 경로 칩, 질문, 해설, 추천 꼬리 5개, 자유 입력란이다.

### 지도 모드

읽기 뷰 상단의 지도 버튼을 누르면 전체화면 캔버스가 열린다. 내가 어디까지 팠는지 조망하고 원하는 노드로 점프한 뒤 읽기로 돌아온다.

별도 페이지가 아니라 모달이다. 읽던 자리를 잃지 않아야 한다.

데스크톱은 같은 두 모드를 나란히 놓는다. **렌더러를 두 벌 만들지 않는다.**

### 라우팅

| 경로 | 설명 |
|---|---|
| `/` | 오늘의 질문 + 게시판 |
| `/q/[nodeId]` | 읽기 뷰 |
| `/t/[slug]` | 트리 상세 (공유·오늘의 질문 공통) |
| `/me` | 내 학습 기록 |

경로는 URL에 담지 않는다. 그래프라 경로가 길어지면 URL이 감당하지 못한다. 클라이언트 상태로 들고 있다가 로그인 상태면 `user_path`에 기록하고 공유할 때만 명시적으로 스냅샷한다.

## 8. 인증과 비용 방어

| | 확장 횟수 | 답변 피드백 | 저장 |
|---|---|---|---|
| 비로그인 | 하루 5회 | 불가 | 안 됨 |
| 로그인 | 하루 50회 | 하루 20회 | user_path · user_answer에 기록 |

캐시 히트는 확장 횟수를 차감하지 않는다. 비용이 들지 않는 조회를 체험분에서 깎을 이유가 없다. 인기 경로일수록 무료로 파고들 수 있어서 체험 만족도가 오히려 올라간다.

답변 피드백은 캐시가 먹지 않으므로 별도 할당량으로 분리한다.

로그인은 Supabase Auth Google OAuth를 쓴다. 비로그인도 열람과 체험이 되므로 진입 마찰이 없고, 막힐 때 로그인할 이유가 자연히 생긴다.

### 모델 티어링

Gemini 무료 티어를 쓴다. Google AI Studio 무료 티어는 상업적 이용을 허용하되 입출력이 모델 학습에 사용된다. 다루는 것이 공개 CS 지식이라 민감정보가 없어 문제되지 않는다.

| 용도 | 모델 | 근거 |
|---|---|---|
| 정규화 게이트 | Gemini Flash-Lite | 짧은 판정과 문장 다듬기. 호출 빈도가 가장 높은 자리 |
| 해설 + 꼬리 생성 | Gemini Flash | 품질과 한도의 균형 |
| 답변 피드백 | Gemini Flash | |
| 매일 루트 질문 | Gemini Pro | 하루 한 번뿐이라 한도에 여유. 서비스 얼굴이라 품질 우선 |

### 무료 한도 안에서 버티는가

Flash 무료 티어가 15 RPM / 1,500 RPD, Pro가 5 RPM / 50 RPD다.

일 사용자 100명이 각 5회씩 판다고 가정하면 정규화 500회에, 캐시 미스를 30%로 잡으면 생성 150회, 답변 50회로 **약 700회**다. 하루 한도의 절반 이하다.

관건은 RPD보다 **분당 한도(15 RPM)**다. 저녁 시간대에 동시 사용자가 몰리면 걸린다. 요청 큐와 지수 백오프를 넣고, 한도에 걸리면 "잠시 뒤 다시" 대신 **캐시된 인접 노드를 먼저 보여주는** 식으로 완화한다.

일 사용자가 300명을 넘으면 무료 한도를 벗어난다. 그 시점이면 유료 전환을 판단할 근거도 함께 생긴다.

## 9. API

| 엔드포인트 | 설명 |
|---|---|
| `POST /api/expand` | 정규화 게이트 → 캐시 조회 → 미스면 생성 → 발자국 기록 |
| `GET /api/node/[id]` | 노드 조회 |
| `GET /api/daily` | 오늘의 질문 |
| `GET /api/trees` | 게시판 목록 (정렬·카테고리 필터) |
| `POST /api/answer` | 답변 저장 → AI 피드백·등급 생성 |
| `POST /api/share` | 경로 스냅샷 → tree 생성 (답변 포함 여부 선택) |
| `POST /api/fork` | tree의 node_ids를 내 user_path로 복제 |
| `POST /api/publish-daily` | GitHub Actions가 호출. 시드 1개 소비 → 루트 발행. `CRON_SECRET` 헤더로 보호 |

`/api/expand`가 사실상 서비스의 심장이다. 나머지는 얇다.

## 10. 기술 스택과 배포

Next.js 16 App Router + React 19 + Tailwind v4 + Supabase(Postgres/Auth) + **Vercel Hobby**. 기존 프로젝트 관례를 그대로 따른다. 개인 비상업 프로젝트라 Hobby 무료 범위 안이다.

지도 모드 캔버스는 React Flow를 쓴다.

### 매일 발행은 GitHub Actions

Vercel Cron이 아니라 GitHub Actions로 뺀다. Hobby의 Cron 제약을 피하고, 발행과 동시에 콘텐츠 레포 커밋까지 한 워크플로에서 처리할 수 있다.

```
GitHub Actions (매일)
  → POST /api/publish-daily   시드 1개 소비, 루트 발행
  → 응답을 마크다운으로 변환
  → 레포에 커밋
```

### 콘텐츠 레포

발행 결과를 마크다운으로 레포에 함께 쌓는다. 서비스와 별개로 "매일 자라는 CS 지식 그래프" 저장소가 된다.

이 판단에는 근거가 있다. CS 면접 **콘텐츠** 레포는 스타가 몰리는 영역이다 — gyoogle 17.5k, awesome-interview-questions 83.9k. 반면 서비스 **코드** 오픈소스는 self-host 유인이 있어야 스타가 붙는데, 이 서비스는 LLM 키가 필요하고 가치가 콘텐츠에 있어 유인이 약하다. 콘텐츠를 자산으로 쌓는 쪽이 승산이 크다.

디렉터리는 카테고리별로 나누고 파일명에 발행일을 넣는다. 사용자가 판 노드도 주기적으로 함께 반영한다.

### Streamlit을 쓰지 않는 이유

검토했고 배제했다. 지도 모드 자체는 `streamlit-flow`(React Flow 래퍼)로 가능하지만 두 가지가 막힌다.

첫째, **OG 메타태그를 넣을 수 없다.** 카톡에 링크를 붙여도 제목·설명·썸네일이 뜨지 않는다. 카톡방에서 출발한 서비스이고 공유가 핵심 기능이라 치명적이다.

둘째, **아이템별 동적 페이지가 불가능하다.** `/t/[slug]` 트리 공유 링크가 설계의 축인데 성립하지 않는다.

여기에 rerun 모델이 얹힌다. 인터랙션마다 스크립트 전체가 다시 돌아 무한 확장 UX에서 지연이 체감된다.

## 11. 테스트

**정규화 게이트가 최우선이다.** 표현이 다른 같은 질문이 같은 해시로 수렴하는지, 무관한 입력이 걸러지는지를 골든 케이스로 고정한다. 캐시 효율 전체가 여기에 달려 있다.

그 외에 다음을 잡는다.

- 캐시 히트/미스 분기와 할당량 차감 규칙 (히트는 확장 횟수 미차감)
- qedge 삽입 시 순환 방지
- 할당량 초과 시 로그인 유도 처리
- Gemini RPM 한도 도달 시 큐·백오프 동작
- E2E — 오늘의 질문 진입 → 파기 → 답변 작성 → 공유 → 다른 계정으로 포크
