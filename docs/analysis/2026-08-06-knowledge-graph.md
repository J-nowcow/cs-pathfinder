# CS 지식을 하나의 그래프로 엮기 — 문제 분석

작성 2026-08-06 · 상태: 분석, 결정 전

## 무엇을 하려는 것인가

이 서비스의 목표는 **전체 CS 지식을 하나의 그래프로 구조화**하는 것이다. 꼬리질문은 새 질문을 무한히 만드는 장치가 아니라 지식과 지식을 잇는 선이다. 트리는 그 그래프를 사람이 공부할 수 있게 보여주는 방식일 뿐이고, 반드시 트리일 필요도 없다.

지금은 그 반대로 돌고 있다.

## 실측

### 그래프가 사실상 비어 있다

운영 DB(`npm run check:graph`, 2026-08-06):

| 지표 | 값 |
|---|---|
| ready 노드 | 51 |
| 간선 | 9 |
| 고립 노드 | 38 (75%) |
| 연결 요소 | 42개 |
| 가장 큰 덩어리 | 12% |
| 차수 중앙값 | 0 |

레포에 있는 249개(예시 30 + 생성 219)는 **간선이 하나도 없다.** 시드로 심을 때 `qnode`와 `qnode_suggestion`만 넣고 `qedge`는 안 만든다.

### 꼬리질문은 1245개가 떠 있다

249개 × 5개 = 1245개의 꼬리질문이 있는데, 전부 `target_node_id = null`이다. 누르면 그때 새 노드를 만든다. 즉 **잠재적 간선 1245개가 전부 끊겨 있다.**

### 낱말 비교로는 못 잇는다

꼬리질문 1245개를 기존 질문 249개와 낱말 자카드 유사도로 맞춰봤다.

| | |
|---|---|
| 0.4 이상 겹침 | 61개 (5%) |
| 그중 다른 카테고리 | 38개 |

**5%도 문제지만 매칭 내용이 더 문제다.** 실제로 잡힌 것들:

```
"샤딩 키는 무엇을 기준으로 고르는가?"     ≈  "배포 방식은 무엇을 기준으로 고르는가?"
"파티션 키는 무엇을 기준으로 정하는가?"   ≈  "호출 시간 제한은 무엇을 기준으로 정하는가?"
"HSTS는 무엇을 막는가?"                  ≈  "CORS는 무엇을 막는가?"
```

주제가 아니라 **문장 틀**이 잡혔다. 우리가 질문 형식을 `~는 무엇을 기준으로 고르는가?`로 통일한 것이 원인이다. 형식을 통일한 것은 읽기에는 좋지만 텍스트 유사도를 무의미하게 만든다.

## 왜 안 이어지나 — 근본 원인

`collectCandidates(parentNodeId)`는 후보를 이렇게 모은다.

```sql
siblings : 같은 부모의 다른 자식
uncles   : 조부모의 다른 자식
```

**후보 집합이 그래프 이웃에서 나온다.** 그런데 그래프가 비어 있으면 이웃이 없고, 이웃이 없으면 후보가 0이고, 후보가 0이면 게이트가 매칭할 대상이 없어서 항상 새 노드를 만든다. 새 노드를 만들면 간선은 부모-자식 하나만 생긴다.

즉 **후보 발견이 구조적(structural)인데 필요한 것은 의미적(semantic)이다.** 빈 그래프에서 시작하면 영원히 사슬만 자라고 그물이 안 된다.

이것이 고립률 75%의 원인이다. 사람이 판 9개의 간선은 전부 부모→자식 사슬이다.

## 무엇을 고를 수 있나

### A. 생성 시점에 잇는다

꼬리질문을 만들 때 **기존 질문 목록을 후보로 주고** "이미 답하는 것이 있으면 그것을 가리켜라"고 시킨다.

- 장점: 새로 만들어지는 것부터 그물이 된다. 지금 게이트 구조(선택, 생성 아님)를 그대로 쓴다
- 단점: 이미 만든 1245개는 안 고쳐진다. 후보를 249개 다 주면 프롬프트가 커진다
- 위험: 잘못 이으면 되돌릴 수 없다 (기존 원칙)

### B. 사후에 잇는다

이미 있는 1245개 꼬리질문을 기존 질문과 대조해 `target_node_id`를 채우고 `qedge`를 만든다.

- 장점: 지금 있는 것이 즉시 그물이 된다. 한 번 돌리면 끝
- 단점: 1245번 판정이 필요하다. 낱말 비교만으로는 위에서 봤듯 틀린다
- 위험: 대량 오연결. 한 번에 1245개를 잘못 이으면 손으로 못 되돌린다

### C. 개념 계층을 먼저 세운다

질문 위에 **개념 노드**(TCP, 인덱스, GC …)를 두고 질문을 개념에 매단다. 질문끼리 직접 잇지 않고 개념을 통해 이어진다.

- 장점: 카테고리 간 연결이 자연스럽다(네트워크의 TCP와 모바일의 네트워크 재시도가 같은 개념에 붙는다). 오연결 위험이 낮다 — 개념 매핑이 질문 매핑보다 쉽다
- 단점: 스키마와 화면이 모두 바뀐다. 가장 크다
- 위험: 개념 목록을 누가 정하나. 잘못 나누면 전부 다시

### D. 후보 발견만 의미 기반으로 바꾼다

`collectCandidates`가 그래프 이웃 대신 **같은 카테고리 + 인접 카테고리의 질문**을 후보로 준다. 나머지(게이트가 고르는 방식)는 그대로.

- 장점: 변경이 가장 작다. 빈 그래프에서도 후보가 나온다. A와 B 양쪽의 전제 조건이기도 하다
- 단점: 이것만으로는 이미 있는 1245개가 안 이어진다
- 위험: 후보가 늘면 게이트의 오선택 확률이 올라간다 (precision 100% 원칙과 충돌)

## 결정해야 할 것

1. **A·B·C·D 중 무엇을, 어떤 순서로**
2. **오연결을 어디까지 허용하나.** 기존 원칙은 "잘못 합친 것은 복구 불가"라 precision 100%였다. 그물을 만들려면 이 기준을 유지할 수 있나
3. **카테고리 간 인접 관계를 누가 정하나.** 손으로 적을 것인가, 데이터에서 뽑을 것인가
4. **꼬리질문을 미리 노드로 만들 것인가.** 만들면 그물이 즉시 생기지만 "사람이 판 경로가 지도"라는 전제가 흔들린다

## 재보지 않은 것

- 게이트에 후보를 20개·50개 줬을 때 정확도가 어떻게 변하는지 (기존 측정은 3·10·25·50개에서 했으나 같은 카테고리 후보가 아니었다)
- 개념 노드를 도입했을 때 질문→개념 매핑의 정확도
- 사람이 실제로 파는 비율. 지금 조회 대비 확장 비율이 얼마인지
