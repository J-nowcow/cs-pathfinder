## 결론

CS Pathfinder의 본체는 공통 CS 지식 그래프다. 면접 준비와 자격증은 그래프를 공부하는 **목적형 트랙**이다. 별도 문제은행이나 읽기용 백과사전으로 분리하지 않는다.

첫 학습 루프는 작게 만든다.

1. 홈에서 기한이 된 복습을 우선해 오늘의 세 문제를 고른다.
2. 해설을 보기 전에 직접 설명한다.
3. 모범답안과 비교해 `다시 볼래요` 또는 `설명할 수 있어요`를 고른다.
4. 자기 점검 결과에 따라 다음 복습일을 정한다.
5. 꼬리질문 5개와 질문 지도에서 다음 개념으로 이동한다.

초기 트랙은 기존 질문을 가장 많이 재사용할 수 있는 `백엔드 CS 면접 30`으로 한다. 정보처리기사는 두 번째 **개념 보강 파일럿** 후보다. 2026 공식 출제기준의 세부 항목에 기존 CS 질문을 표본 매핑하고 자체 문항만 만든다. 필기·실기 모의시험을 대신한다고 주장하지 않는다.

## 풀려는 문제

현재 정적 원본에는 제목이 정확히 겹치지 않는 질문 337편이 있다. 의미가 비슷한 질문은 별도로 남아 있으므로 이를 `중복 없음`으로 해석하지 않는다. 질문 지도, 키워드 역탐색, 답변 초안, 자기 점검, 학습 기록도 이미 있다. 재료는 충분하다. 그러나 사용자가 다시 왔을 때 무엇을 해야 하는지가 한 화면에 연결되지 않는다.

- 해설을 읽는 일과 질문에 답할 수 있는 일은 다르다.
- `다시 볼 답`은 모이지만 언제 다시 볼지는 정하지 않는다.
- 추천은 관심 분야를 반영하지만 준비 목표와 진도를 반영하지 않는다.
- 질문 지도는 연결을 보여 주지만 하루 학습량을 잘라 주지 않는다.
- 정보처리기사처럼 목적이 선명한 유입 경로가 없다.

따라서 콘텐츠 추가보다 **회상 → 비교 → 자기 점검 → 복습**을 먼저 완성한다.

- [Exercism](https://github.com/exercism/python): 개념 연습과 열린 실전 연습을 나누고 선수 개념에 따라 다음 연습을 연다. 문항 UUID, 작성자, 출처와 트랙 검증 도구를 둔다.
- [freeCodeCamp](https://github.com/freeCodeCamp/freeCodeCamp): 인증 과정을 워밍업, 학습, 연습, 복습, 퀴즈로 나눈다. 읽기와 평가 사이에 반복 연습 단계를 둔다.

공통 패턴은 자료량이 아니다. 범위, 순서, 안정적인 콘텐츠 식별자, 진도, 기여 계약이 있다. CS Pathfinder는 여기에 질문 그래프와 한국어 답변 연습을 더한다.

위 저장소에서 제품 패턴만 배운다. 문항과 해설은 각 프로젝트의 라이선스를 별도로 확인하지 않고 가져오거나 번역하지 않는다.

Anki에서 빌리는 것은 `오늘 복습할 큐`와 `답 공개 뒤 자기평가`다. CS 설명을 원자적인 암기 카드로 잘게 쪼개지는 않는다. 한 질문 안에서 정의, 원리, 트레이드오프, 실제 예시를 연결하는 현재 해설의 장점을 보존한다.

### 정보처리기사 개념 보강 파일럿

[Q-Net 종목별 검정현황](https://www.q-net.or.kr/crf005.do?gId=&gSite=Q&id=crf00503s01&jmCd=1320&jmInfoDivCcd=A0)에 따르면 2025년 필기 응시는 66,308건이다. 실기 응시는 73,858건이다. 실기 합격률은 22.1%다. 고유 사용자 수가 아닌 **응시 건수**다.

수요와 시험 일정은 재방문 동기가 될 수 있다. 그러나 본체를 정보처리기사 문제집으로 바꾸면 다음 문제가 생긴다.

- 시험 개편 때마다 별도 문제은행을 갱신해야 한다.
- 기존 면접 질문과 중복된 설명을 두 벌로 유지하게 된다.
- 시험 직전 사용 후 이탈하는 계절형 제품이 된다.
- 공식 공개 대상이 아닌 문항의 권리와 시험 보안 규정을 문항별로 확인해야 한다.

첫 파일럿에서는 정보처리기사를 공통 CS 개념을 다시 배열하는 **개념 보강 트랙**으로만 검증한다. [Q-Net 종목 상세정보](https://www.q-net.or.kr/crf005.do?gId=&gSite=Q&id=crf00503s02&jmCd=1320&jmInfoDivCcd=B0)에 따르면 필기는 5과목, 과목당 20문항의 객관식 4지 택일형이다. 실기는 2시간 30분 필답형이다. 현재 제품의 설명형 질문 20~30개만으로 이 형식과 범위를 대체할 수 없다. 필기 객관식, 실기 필답형, 시간·점수 모의훈련은 파일럿 범위에서 제외한다.

[Q-Net 출제기준 자료실](https://www.q-net.or.kr/cst006.do?code=1202&gSite=Q&id=cst00601)의 2026 출제기준을 범위의 기준선으로 삼는다. 2026-08-14 확인 기준 유효기간은 `2026.1.1~2026.12.31`이다. 필기 5과목과 실기 정보처리 실무를 구분하고 세부 항목별 `전체·부분·미매핑` 상태를 공개한다.

[Q-Net 가답안·확정답안 안내](https://www.q-net.or.kr/anc002.do?gId=99&gSite=Q&id=anc00203)는 CBT 필기와 필답형 실기를 인터넷 답안 공개 대상에서 제외한다. 문항별 권리와 시험 보안 규정도 달라질 수 있다. 따라서 응시자의 기억에 의존한 복원 문항, 무단 반출 문항, 제3자 문제집 문항과 그 근접 개작을 수집·전재하지 않는다. 공식 출제기준을 바탕으로 독립 작성한 문항만 사용한다. 기여자는 작성자·독립 작성 여부·원문 출처·라이선스·검토일을 남긴다. 사람 리뷰를 필수로 하고 유사도 검사는 보조 수단으로만 쓴다.

## 제품 구조

```text
공통 CS 지식 그래프
├── 질문과 해설
├── 한/영 키워드와 관계
├── 꼬리질문 5개
└── 난이도와 분야
        │
        ├── 백엔드 CS 면접 30
        ├── 컴공 기초 다시 잡기
        ├── 정보처리기사 개념 보강 파일럿
        └── 향후 공개 GitHub·레쥬메 맞춤 경로
                │
                └── 오늘의 3문제
                    ├── 기한이 된 복습 최대 3개
                    └── 남는 자리에 새 질문
```

트랙은 본문을 복제하지 않는다. 정적 원본의 질문 키와 순서만 참조한다. 질문이 고쳐지면 모든 트랙이 같은 최신 해설을 본다.

## 핵심 개념 모델

### `LearningTrack`

정적 TypeScript 데이터로 시작한다. 운영 DB는 바꾸지 않는다.

```ts
type LearningTrack = {
  id: string
  title: string
  description: string
  audience: string
  estimatedMinutesPerQuestion: number
  questionKeys: string[]
  contentReviewedOn: string
  sources?: Array<{ title: string; url: string }>
}
```

규칙:

- `id`는 불변 식별자로 유지한다.
- 존재하지 않거나 중복된 질문 키는 테스트에서 실패한다.
- 초기에 동적 LLM 분류를 쓰지 않는다.
- 자격증 확장 트랙에는 공식 출제기준 버전, 검토일, 세부 항목별 매핑 상태를 둔다.
- 트랙 하나는 20~40문제로 시작한다. 긴 트랙은 구간으로 나눈다.
- 전체 예상 시간은 문제당 예상 시간과 질문 수로 계산한다. 하나의 모호한 숫자를 직접 저장하지 않는다.

현재 DB의 `qnode.id`는 모든 환경에서 재계산할 수 있는 콘텐츠 ID가 아니다. 사용자 요청으로 먼저 만들어진 일부 질문은 임의 UUID를 유지한다. 따라서 P0에서 DB ID를 정적 트랙 파일에 박지 않는다. 정적 원본의 정확한 질문 문장을 `questionKey`로 쓰고 `listRoots()` 결과의 실제 ID로 해석한다. 이 키는 P0의 검증 가능한 호환 키이지 불변 식별자가 아니다. 제목을 바꾸면 검증 테스트가 깨져 트랙도 함께 고치게 한다. 별도 영구 `contentKey` 도입은 전체 스키마 영향을 검토한 뒤 진행한다.

### `AnswerReview`

복습 기록을 답변 초안과 분리한다. 답변 원문은 계속 브라우저에만 둔다.

```ts
type AnswerReview = {
  status: 'needs-review' | 'understood'
  reviewedAt: string
  nextReviewOn: string
  reviewCount: number
  successStreak: number
}
```

현재 저장소는 자기 점검을 `drafts[nodeId]` 안에 넣고 최근 초안 100개만 남긴다. 이 구조를 그대로 확장하면 101번째 답변부터 오래된 복습 일정도 함께 사라진다. 전체 질문 337편을 공부하는 제품에는 맞지 않는다.

P1에서 `reviews: Record<nodeId, AnswerReview>`를 별도 필드로 둔다. v1의 `draft.reviewStatus`와 `reviewedAt`은 읽을 때 `reviews`로 옮긴다. 초안 100개 상한은 유지한다. 복습 기록은 원문이 없어 작지만 손상된 localStorage 방어를 위해 별도 상한을 둔다. 초기 상한은 500개다. 상한을 넘으면 기한이 지난 복습을 버리지 않고, 완료 상태 중 가장 오래된 기록부터 정리한다.

v1 마이그레이션 규칙도 결정론적으로 고정한다. 유효한 `reviewedAt`이 있는 `needs-review`는 해당 시각의 KST 날짜 다음 날과 `successStreak: 0`으로 옮긴다. `understood`는 KST 날짜 7일 뒤와 `successStreak: 1`로 옮긴다. 상태나 날짜가 손상된 항목은 복습 기록만 버리고 답변 초안은 보존한다. 마이그레이션은 같은 원본을 여러 번 읽어도 같은 v2 결과를 내야 한다.

초기 간격은 다음 휴리스틱으로 완결한다. 학습 연구가 이 날짜를 정답으로 보장하는 것은 아니다.

- `다시 볼래요`: 성공 연속 횟수를 0으로 되돌리고 다음 날
- 첫 `설명할 수 있어요`: 성공 연속 1회, 7일 뒤
- 두 번째 연속 `설명할 수 있어요`: 성공 연속 2회, 30일 뒤
- 세 번째 이후 연속 `설명할 수 있어요`: 성공 연속 3회 이상, 90일 뒤
- 기한을 넘긴 답: 가장 먼저 복습

`nextReviewOn`은 KST 기준 `YYYY-MM-DD` 날짜다. 시각을 저장하지 않는다. 오늘의 질문과 잔디가 이미 쓰는 KST 날짜 기준과 맞춘다. 세션 선택 함수에는 오늘 날짜를 인자로 넘긴다. 함수 안에서 현재 시각을 읽지 않는다. 사용자가 초안을 고쳐 써도 기존 복습 일정은 지우지 않는다. 답을 보완한 뒤 다음 회상에서 다시 자기 점검한다.

복잡한 숙련도 점수와 FSRS는 도입하지 않는다. 현재는 복습 이력도 부족하다. 먼저 기한 도래 수와 완료율을 측정할 수 있는 구조를 만든다. 추후 `어려움 / 애매함 / 설명 가능` 같은 3단계 자기평가가 필요하면 저장 버전 마이그레이션과 함께 바꾼다.

질문을 연 기록과 답변 연습 기록도 분리한다. 현재 잔디는 질문을 연 `(날짜, 노드)`를 기록한다. 이를 학습 완료로 바꾸거나 덮어쓰지 않는다. answer practice v2에 로컬 전용 `practiceDays: Record<YYYY-MM-DD, nodeId[]>`를 추가한다. 오늘 세션에서 자기 점검까지 마친 노드만 해당 KST 날짜에 한 번 기록한다. 최근 400일만 보존하고 날짜별 ID는 중복 제거한다. 과거 v1의 유효한 `reviewedAt`은 실제 자기 점검이 있었으므로 해당 KST 날짜에 한해 이관할 수 있다. 답변 원문처럼 로그인 동기화는 하지 않는다.

### `DailyLearningSession`

순수 함수가 같은 입력에서 같은 3문제를 고른다.

```ts
type SessionKind = 'review' | 'new'
type DailyLearningItem = {
  kind: SessionKind
  questionId: string
  reason: string
  completedAt?: string
}
```

선택 규칙:

1. `복습`: `nextReviewOn <= 오늘`인 답을 오래 밀린 순서로 최대 세 개 선택
2. 복습일이 같으면 `needs-review`를 `understood`보다 먼저 선택
3. 남은 자리에 선택한 트랙에서 답변하지 않은 질문을 순서대로 선택
4. 중복을 제거한 후보 자체가 3개보다 적으면 있는 것만 표시

처음 온 사용자에게는 복습이 없으므로 새 질문 세 개가 보인다. 이를 복습이나 약점이라고 부르지 않는다. 초기 버전은 사용자의 약점을 추론한다고 말하지 않는다. 사용자가 `다시 볼래요`로 표시한 질문은 복습 큐 안에서 우선할 뿐 별도 고정 슬롯을 차지하지 않는다. 관련 개념 추론과 AI 평가는 별도 검증 뒤에 추가한다.

고정된 `복습 1 + 약점 1 + 새 질문 1`은 쓰지 않는다. 매일 새 질문 세 개를 완료하면 7일 뒤부터 하루 세 개씩 복습 기한이 돌아온다. 복습 슬롯이 하나뿐이면 적체가 매일 두 개씩 늘어난다. 복습을 최대 세 자리까지 먼저 채워야 새 질문 유입을 자동으로 멈추고 밀린 큐를 줄일 수 있다.

선택 결과는 그날의 로컬 스냅샷으로 저장한다.

```ts
type DailySessionSnapshot = {
  date: string
  trackId: string
  createdAt: string
  items: DailyLearningItem[]
}
```

같은 날 자기 점검 상태가 바뀌어도 스냅샷의 세 질문을 새 질문으로 갈아 끼우지 않는다. 그렇지 않으면 한 문제를 끝낼 때마다 다음 후보가 들어와 `오늘의 3문제`가 끝나지 않는다. 날짜나 선택 트랙이 바뀌었을 때만 새 세션을 계산한다.

과거 `reviewedAt`만 보고 오늘 항목을 완료 처리하지 않는다. 오늘 세션에서 모범답안과 비교하고 자기 점검을 남긴 시각을 해당 항목의 `completedAt`에 기록해야 완료다. 연습 상태는 `미시도 → 답변 시도 또는 모르겠어요 → 모범답안 공개 → 자기 점검 → 복습 예약`으로 이동한다. 한 글자 입력, 질문 열기, 모범답안 공개만으로 완료 처리하지 않는다.

## 사용자 흐름

### 첫 방문

1. `백엔드 CS 면접 30`을 기본 추천한다.
2. 예상 시간과 학습 방식을 짧게 보여 준다.
3. 첫 질문에서 해설보다 답변 작성칸을 먼저 연다.
4. 답변 후 모범답안과 자기 점검을 보여 준다.
5. 다음 질문 또는 질문 지도로 이어진다.

### 재방문

1. 홈 첫 화면에 `오늘의 3문제`를 둔다.
2. 각 카드에 `복습`, `다시 볼 답`, `새 질문` 이유를 표시한다.
3. 한 문제를 완료할 때마다 정확한 다음 복습일과 다음 날 준비된 복습 수를 알려 준다.
4. 세 문제를 끝내면 트랙 진도와 다음 방문 때 할 일을 보여 준다.
5. 세 문제를 모두 끝내지 않아도 한 문제의 자기 점검을 마치면 학습일로 인정한다.

푸시 알림이나 이메일 없이도 사용자가 스스로 돌아오는지를 먼저 검증한다. 초기 파일럿은 `알림 없는 자발적 재방문` 실험이다. 외부 알림 부재를 일정 알고리즘의 성과와 혼동하지 않는다.

### 초보자 scaffold

- 첫 방문이나 이력이 없는 질문: `정의 → 동작 원리 → 트레이드오프 → 예시` 답변 뼈대를 선택적으로 제공한다.
- `다시 볼래요`로 표시한 질문: 다음 복습에서 답변 뼈대 또는 키워드 힌트를 먼저 고를 수 있다.
- 반복해서 `설명할 수 있어요`로 표시한 질문: 빈 답변칸을 기본으로 두고 도움은 요청할 때만 보인다.
- 답을 시작하지 못하면 `예제로 시작하기`를 직접 선택할 수 있다. 이때 모범답안을 본 것은 답변 완료로 세지 않는다.
- 모범답안과 비교한 뒤 `내 답에서 빠진 전제나 조건 1개`를 직접 적게 한다.
- worked example을 본 다음에는 같은 개념의 꼬리질문에서 일부 힌트만 주고 다음 지연 복습에서는 독립 설명을 요구한다.

질문의 `기초·심화·깊이` 표시는 콘텐츠 난이도다. 사용자의 숙련도와 같지 않다. scaffold는 정답을 새로 생성하지 않는다. 기존 해설, 답변 뼈대, 통제된 키워드 힌트를 조합한다. 모든 사용자의 모범답안을 자동으로 먼저 펼치지는 않는다. 힌트 없는 지연 복습을 두 번 연속 성공한 뒤에 기본 도움을 줄인다.

worked example 연구는 프로그래밍 문제 해결 과제에서 얻은 결과다. CS 면접식 설명 과제로의 적용은 검증되지 않은 탐색적 전이다. 답변 뼈대도 그 자체로 완성된 worked example은 아니다. 따라서 힌트 사용 여부와 지연 복습 결과를 따로 기록해 효과를 확인한다.

## 가설과 성공 지표

분석 도구를 새로 붙이지 않는다. 우선 로컬 이벤트 모델과 계산 가능한 지표 이름을 정한다. 운영 수집은 개인정보 정책을 정한 뒤 별도 결정한다.

| 가설 | 제품 행동 | 1차 지표 | 초기 성공 기준 |
| --- | --- | --- | --- |
| 할 일을 세 문제로 줄이면 첫 행동이 빨라진다. | 홈에 오늘의 3문제 | 세션 노출 대비 첫 답변 시작률 | 기준선 대비 증가 |
| 해설 전 답변이 읽기보다 기억에 남는다. | 답변 후 모범답안 공개 | 모범답안 공개 전 답변 작성 비율 | 기준선 확보 뒤 목표 설정 |
| 날짜가 있는 복습은 `다시 볼 답` 적체를 줄인다. | 자기 점검 뒤 다음 복습일 | 기한 도래 복습 완료율과 적체 수 | 기준선 확보 뒤 목표 설정 |
| 목적형 트랙은 다시 올 이유를 만든다. | 트랙 진도와 다음 항목 | D1·D7 재방문율 | 기준선 대비 증가 |
| 한 그래프를 여러 목표에서 재사용하면 본문 유지비가 낮다. | 트랙은 질문 키만 참조 | 트랙별 중복 본문 수 | 0건 |

장기 학습 대리지표는 `7일 이상 지난 복습에서 힌트 없이 답한 뒤 핵심 기준과 비교해 설명 가능으로 자기 점검한 비율`로 잡는다. 힌트 사용과 `모르겠어요` 선택도 함께 본다. 자기평가만으로 정답률을 단정하지 않는다. 방문일이나 읽은 질문 수를 숙련도로 부르지 않는다.

D1·D7과 기존 홈 대비 증가는 운영 이벤트 수집 없이는 계산할 수 없다. 개인정보 정책을 정하기 전에는 추적기를 붙이지 않는다. 먼저 10~20명의 명시적 테스트 참여자에게 같은 과업을 맡겨 기준선을 확보한다. 그 전까지 표의 기준은 탐색적 목표이며 학습 효과로 홍보하지 않는다.

- 최신 공식 출제기준의 대표 세부 항목 20~30개만 표본으로 고르고 기존 질문에 사람이 매핑

- 필기 5과목과 실기 정보처리 실무를 구분하고 `시험 / 면접 / 현업`의 연결 이유 표시
- 파일럿에서 확인된 작은 공백만 독립 작성 문항으로 보강
- 기여 가이드에 복원·반출·제3자 문항 금지와 독립 작성 확인 절차를 명시
- 사람 리뷰를 필수화하고 유사도 검사는 근접 개작을 찾는 보조 수단으로만 사용
- 출제기준 유효기간 만료 전, 변경 공고 시, 각 시험 시즌 노출 전에 검토
- 매핑 검토 항목 수, 부분·미매핑 비율, 기준 변경 후 갱신 시간을 유지비로 기록

자격증 전용 메타데이터는 범용 `LearningTrack`에 억지로 넣지 않는다. P2에서 다음 확장 타입으로 분리한다.

```ts
type CertificationTrackMetadata = {
  authority: string
  qualificationCode: string
  validFrom: string
  validTo: string
  checkedOn: string
  sourceUrl: string
  syllabusMappings: Array<{
    syllabusCode: string
    questionKeys: string[]
    coverage: 'full' | 'partial' | 'unmapped'
  }>
}

type CertificationLearningTrack = LearningTrack & {
  certification: CertificationTrackMetadata
}
```

독립 작성한 질문은 `author`, `origin`, `license`, `reviewedOn`을 콘텐츠 메타데이터로 남긴다. `unmapped` 항목은 빈 `questionKeys`를 허용한다. 필기 객관식의 오답지와 실기 답안·채점 기준이 필요하다는 사용 수요가 확인되면 별도 문제 모델 또는 제품 분리를 다시 결정한다.

## 첫 트랙 질문 초안

`백엔드 CS 면접 30`은 기초 개념에서 운영 판단으로 이동한다. 현재 정적 원본에 정확히 존재하는 질문만 골랐다. 유사 질문이 여러 개면 문장이 짧고 판단 기준이 드러나는 한 편만 사용한다.

11. `HTTPS는 무엇을 보장하고 무엇을 못 하는가?`

### 3구간 — 데이터를 안전하고 빠르게 다루기

### 5구간 — 배포와 보안

27. `컨테이너는 가상 머신과 무엇이 다른가?`
28. `SQL 인젝션은 무엇으로 막는가?`
29. `JWT를 세션 대신 쓸 때 무엇을 잃는가?`
30. `요청이 한꺼번에 몰릴 때 어떻게 막는가?`

이 목록은 난이도 순서의 첫 기준선이다. 관계 그래프의 선수 개념과 사용자 완료 데이터를 함께 쓸 수 있게 된 뒤 순서를 다시 평가한다.

선정한 30편의 원본 구성은 `generated` 17편, 손글 기준선 9편, `authored` 4편이다. 현재 공개 중이라는 사실만으로 트랙 품질 검수를 대신하지 않는다. UI에 트랙을 노출하기 전 30편을 다음 기준으로 한 번씩 읽는다.

- 질문과 첫 문단이 바로 맞물리는가
- 정의만 나열하지 않고 판단 기준과 트레이드오프가 있는가
- `위 도식은`, `핵심은`, `면접에서는 이렇게` 같은 메타 해설이 없는가
- 현재 추천 꼬리질문이 정확히 5개이며 본문을 반복하지 않는가
- 최신성이 필요한 주장에 범위와 1차 출처가 있는가

검수를 통과하지 못한 질문은 트랙 출시 때문에 급히 자동 재생성하지 않는다. 기존 `authored` 방식으로 한 편씩 고친 뒤 넣는다.

- 첫 정보처리기사 개념 보강 파일럿은 본체 전환이 아닌 목적형 트랙으로 검증한다. 모의시험·채점·실기 연습 수요가 확인되면 구조를 다시 결정한다.
- 첫 트랙은 기존 콘텐츠 재사용률이 높은 백엔드 면접 트랙이다.
- SRS 라이브러리를 바로 붙이지 않는다. 단순한 복습 날짜와 행동 데이터를 먼저 만든다.
- AI가 약점을 추측하지 않는다. 사용자의 자기 점검을 우선한다.
- 답변 원문은 로컬에만 보관한다.
