# 도식 어휘를 넓힌다 — 설계

작성 2026-08-07 · 상태: 설계, 구현 전

표본은 레포에 실린 249개다(`data/example-nodes.ts` 30 + `data/generated-nodes.ts` 219). 운영 DB에는 매일 올라온 것이 몇 개 더 있지만 여기서는 세지 않았다. 도식은 `parseBlocks`를 그대로 돌려 셌다.

---

## 요약

세 가지가 실측에서 나왔다.

**첫째, 노드 249개가 전부 도식을 정확히 하나씩 가진다.** 0개도 2개도 없다. 프롬프트는 "1~2개가 적당하다"(`src/lib/llm/generate.ts:52`)고 하지만 실제 분포는 1에 못박혀 있다. 그래서 이 논의는 "도식을 더 넣을까"가 아니라 **"그 하나를 무엇으로 그릴까"**다.

**둘째, 도피처는 표가 아니라 stack이다.** 표 127개 중 형태가 틀린 것은 30개(24%)인데, stack 56개 중 틀린 것은 23개(41%)다. 느슨한 기준까지 세면 표 44개(35%) 대 stack 49개(88%)다. 파서가 이유를 설명한다 — `parseStack`은 **절대 실패하지 않는다**(`src/lib/markdown/blocks.ts:104-112`). `STACK_LINE`이 비어 있지 않은 모든 줄에 매치하기 때문이다. flow는 화살표가 없으면 `null`, 표는 구분줄이 없으면 `null`인데 stack만 무엇이든 받는다.

**셋째, 표는 형태가 아니라 관성이다.** 생성분 표 113개 중 107개(94.7%)가 첫 칸 머리글이 `기준`이다. 손으로 쓴 14개는 3개(21.4%)뿐이고 머리글이 11가지로 갈린다. 모델은 표를 고르는 것이 아니라 `기준 | A | B` 틀을 채운다.

결론: 어휘를 넓히되 순서는 **stack의 뜻을 좁히는 것 → 상태 전이 → 트리 → 메모리 배치 → 타임라인**이다. 막대그래프는 만들지 않는다. 토폴로지도 만들지 않는다. 근거는 아래에 있다.

## 1. 실제로 무엇이 표로 그려지고 있나

### 분포

| | 노드 | flow | stack | 표 |
|---|---|---|---|---|
| 손으로 쓴 것 | 30 | 12 | 4 | 14 (47%) |
| 생성된 것 | 219 | 54 | 52 | 113 (52%) |
| 합계 | 249 | 66 | 56 | 127 (51%) |

카테고리별로 갈린다. 자료구조·알고리즘은 25개 중 20개(80%)가 표고 flow는 1개뿐이다. 데이터베이스는 19개 중 17개(89%)가 표고 stack은 0개다. 반대로 모바일은 30개 중 표가 5개(17%)뿐이다. 표가 몰리는 곳은 "둘 중 무엇을 고르는가" 꼴의 질문이 많은 영역이다.

### 표 127개를 갈랐다

판정 기준을 둘로 나눴다.

- **A등급** — 지금 형태가 **정보를 잃거나 화면이 깨진다**. 사이클이 직선이 되거나, 공간 관계가 사라지거나, 렌더가 망가진다.
- **B등급** — 지금도 읽히지만 다른 형태가 더 낫다.

| | 진짜 비교표 | A등급 오형 | A+B 오형 |
|---|---|---|---|
| 표 127개 | 97 (76%) → 83 (65%) | 30 (23.6%) | 44 (34.6%) |

**표의 4분의 3은 정당하다.** `낙관적 락 대 비관적 락`, `TCP 대 UDP`, `체크 예외 대 런타임 예외` — 이런 것은 표가 맞다. 문제는 표가 절반이라는 것 자체가 아니라, 표 말고 갈 곳이 없어서 표와 stack이 함께 부푼 것이다.

기계적으로 검증되는 결함도 있다.

- **4열 이상 7개** — 프롬프트가 "열은 세 개까지"(`generate.ts:78`)라고 했는데 지켜지지 않았다. `기준 | GET | POST | PUT | PATCH | DELETE`가 두 번 나왔다(6열). 390px에서 칸당 65px이라 글자가 뭉갠다.
- **1행짜리 4개** — 축이 하나면 표 골격이 낭비다. 한 문장이면 끝난다.
- **같은 비교쌍 중복 6쌍** — `체이닝 | 개방 주소법`이 두 번, `체이닝 | 오픈 어드레싱`이 또 두 번. 해시 충돌 해결만 표 4개다.

### 대표 사례 다섯

**(1) 축이 하나인데 표를 세웠다** — `변경점을 비교하면 언제 비용이 줄어드는가?`

```
| 기준 | 가상 트리 비교 | 직접 DOM 갱신 |
| --- | --- | --- |
| 강점 | 선언적 일괄 반영 | 작은 변경에 단순함 |
```

행이 하나다. "가상 트리는 선언적으로 한꺼번에 반영하고 직접 갱신은 작은 변경에 단순하다"라는 한 문장을 표로 부풀린 것이다. 폰에서는 이것이 카드로 접혀 3줄을 먹는다.

**(2) 상태 전이를 표로 눌렀다** — `프로세스 스케줄링 방식은 무엇으로 결정하는가?`

```
| 기준 | 비선점형 | 선점형 |
| --- | --- | --- |
| CPU 점유 | 프로세스가 반납할 때까지 대기 | OS가 강제로 회수 가능 |
| 응답성 | 낮음. 긴 작업으로 밀림 | 높음. 시분할 처리 |
```

이 질문의 답은 **준비 → 실행 → 대기 → 준비**로 도는 프로세스 상태와, 선점이 그 고리 어디를 끊는가다. 표에는 고리가 없다.

**(3) 메모리 배치를 표로 눌렀다** — `프로세스와 스레드의 핵심 차이는 무엇인가?`

```
| 기준 | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 독립적 할당 | 스택 제외 공유 |
| 컨텍스트 스위칭 | 무겁다 | 가볍다 |
| 영향도 | 독립적 실행 | 장애 전파 가능 |
```

"스택 제외 공유"가 이 답의 전부인데, 그림이면 한눈에 보이는 것을 여섯 글자로 압축했다. 코드·데이터·힙은 한 덩어리이고 스택만 스레드마다 따로 있다는 배치가 답이다.

**(4) 트리를 표로 눌렀다** — `일반 이진트리 대신 이진탐색트리를 사용하는 이유는 무엇인가?`

```
| 구분 | 이진트리 | 이진탐색트리 |
| --- | --- | --- |
| 노드 배치 | 규칙 없음 | 왼쪽 < 부모 < 오른쪽 |
| 평균 탐색 | O(N) | O(log N) |
```

`왼쪽 < 부모 < 오른쪽`은 문장으로 읽으면 규칙이지만 그림으로 보면 자명하다. 트리를 설명하는데 트리를 안 그린다.

**(5) 결정 매핑을 비교표 틀에 욱여넣었다** — `최단 경로 알고리즘의 선택 기준은 무엇인가?`

```
| 기준 | BFS | 다익스트라 | 벨만-포드 |
| --- | --- | --- | --- |
| 가중치 | 없음 | 양수 | 음수 포함 |
```

4열 1행이다. 실제 구조는 `가중치가 없다 → BFS`, `양수다 → 다익스트라`, `음수가 있다 → 벨만-포드`라는 **조건 → 선택** 매핑인데, 그것을 90도 돌려 표로 만들었다. 열이 넷이라 폰에서 카드로 접히면 "가중치 / BFS: 없음 / 다익스트라: 양수 / 벨만-포드: 음수 포함"이 되어 조건과 선택의 방향이 뒤집힌다.

### 표 말고도 깨진 것이 있다 — stack이 표를 통째로 삼켰다

`data/generated-nodes.ts:1673` (`HTTP 상태 코드는 어떤 기준으로 분류하는가?`):

```
:::stack
상태 코드 | 분류
--- | ---
1xx | 정보 제공
2xx는 성공적인 처리
3xx는 리다이렉션
:::
```

본문이 "위 **표**는…"이라고 이어진다. 모델은 표를 쓰려 했는데 stack 울타리에 넣었다. `parseStack`이 무엇이든 받으므로 `--- | ---`이 **이름이 `---`이고 설명이 `---`인 층으로 그대로 화면에 그려진다.** `2xx는 성공적인 처리`는 파이프가 없어 설명 없는 층이 된다.

`data/generated-nodes.ts:2570` (`멀티스레드 환경에서 스레드 세이프한…`)도 같은 모양이다(`--|--`). **56개 중 2개(3.6%)가 지금 화면에 구분줄을 그리고 있다.**

이것이 어휘를 넓힐 때의 가장 큰 경고다. 모델은 형태를 못 고르면 **문법을 섞는다.**

### stack 56개의 실상

층수 분포: 2층 30 · 3층 14 · 4층 9 · 5층 2 · 7층 1.

**절반이 넘는 30개가 2층이다.** 2층 stack은 계층이 아니라 둘을 나란히 놓은 것이다. `웹 서버 | 정적 파일` / `WAS | 동적 콘텐츠`를 위아래로 쌓으면 독자는 "WAS가 웹 서버 아래층인가"로 읽는다. 정보를 잃는 정도가 아니라 **없는 계층을 만들어낸다.**

나머지도 성격이 제각각이다. `데드락은 어떤 조건이 모두 모여야 생기는가?`는 4개 조건의 **집합**이지 층이 아니다. `공유 상태는 어느 컴포넌트에 두는가?`는 `공통 조상 / 자식 A / 자식 B`라 **트리**다. `화면이 닫혔는데 객체가 남는 이유는?`은 `GC Root → 싱글턴 → Activity`라 **참조 사슬**이다. 전부 stack으로 그려져 있다.

### flow 66개

18개(27%)가 상태 머신인데 시퀀스로 그려졌다. 가장 선명한 것이 `서킷 브레이커는 무엇을 막아주는가?`다.

```
:::flow
닫힘 -> 열림: 실패율이 기준을 넘는다. 이제 즉시 거절한다
열림 -> 반열림: 일정 시간 뒤 몇 건만 흘려본다
반열림 -> 닫힘: 성공하면 원래대로
반열림 -> 열림: 또 실패하면 다시 막는다
:::
```

문법은 완벽하다. 그런데 `FlowDiagram`(`src/components/Diagram.tsx:41-71`)이 이것을 **1·2·3·4번이 붙은 세로 목록**으로 그린다. 화면에는 네 걸음이 차례로 일어나는 것처럼 보인다. 실제로는 3번과 4번이 **같은 자리에서 갈라지는 두 갈래**이고 그것이 이 개념의 전부다. 도식이 틀린 것을 말하고 있다.

249개 전부를 훑어 "지금 형태가 틀린 것"만 적었다. 판정은 `docs/plan/`에 남기지 않고 아래 표로 요약한다. 각 질문의 현재 형태는 파서를 돌려 대조 검증했다(불일치 0건).

| 형태 | A등급 | A+B | 만드나 |
|---|---|---|---|
| 상태 전이 (state) | **14** | 16 | 1단계 |
| 트리 (tree) | **13** | 13 | 2단계 |
| 메모리 배치 (memory) | **13** | 17 | 3단계 |
| 타임라인 (timeline) | 8 | 10 | 4단계 |

현재 형태별로 보면 A등급 71건의 출처는 표 30 · stack 23 · flow 18이다.

### 만드는 것

**상태 전이 — 14건.** 서킷 브레이커, TCP 종료, 프로세스 스케줄링, 안드로이드 Activity 수명주기(3건), JPA 영속성 컨텍스트(3건), 스프링 빈 수명주기, 코루틴 Job 취소, 권한 상태, WorkManager 재시도, 앱 프로세스 우선순위. 공통점이 있다 — **되돌아오거나 갈라진다.** 지금은 전부 직선으로 그려진다.

flow 66개를 그래프로 훑으면 37개가 같은 노드로 두 번 이상 들어온다. 그중 절반쯤은 시퀀스로도 맞다(`앱 -> DB`가 두 번 나오는 것). 상태 머신으로 확실한 것만 14개로 셌다.

**트리 — 13건.** 이진 탐색 트리(3건), 힙, 트라이(2건), 컴포지트 패턴, 프로토타입 사슬, 인증서 체인, React 상태 끌어올리기(2건), 코루틴 부모-자식, Git 브랜치 전략. 여기에 stack으로 그려진 참조 사슬 3건(안드로이드 누수, ARC 순환 참조)을 흡수하면 **16건**이다.

**메모리 배치 — 13건.** 프로세스 주소 공간(2건), JVM 메모리 영역, 값/참조 타입, 재귀 스택 오버플로, 클로저 캡처, volatile 가시성, 프로세스 대 스레드, 힙/스택 분리, 페이징 대 세그멘테이션(2건), 배열 대 연결 리스트(2건).

정직하게 말하면 이 13건은 둘로 갈린다. 11건은 **영역 배치**(선형 공간에 영역이 놓이고 어느 쪽으로 자라는가)이고, 2건(배열 대 연결 리스트)은 **칸 나열**이라 다른 물건이다. 칸 나열은 2건뿐이라 만들지 않는다. 그래서 실수요는 **11건**이다.

**타임라인 — 8건.** 경쟁 상태, ANR, GIL, 동기·비동기 × 블로킹·논블로킹, 블로킹 I/O, 웹소켓 대 폴링, 이벤트 루프(2건), HTTP/2 멀티플렉싱. 여러 주체가 **같은 시간에** 무엇을 하는가가 답인 것들이다.

### 만들지 않는 것과 그 이유

**막대그래프 — A등급 0건.** 짐작대로였다. 코퍼스에 수치 비교는 많지만(`O(1)` 대 `O(n)`, 처리량 대 지연) **전부 두 값의 대소**이지 여러 값의 분포가 아니다. 두 값을 막대로 그리는 것은 표보다 못하다 — `O(1)`과 `O(n)`은 길이로 그릴 수 있는 양이 아니다. B등급 3건도 "굳이 따지면"에 가깝다. 만들지 않는다.

**토폴로지 — A등급 7건이지만 만들지 않는다.** 세 가지 이유다. 첫째, 7건 중 3건(참조 사슬)은 트리로 흡수된다. 둘째, 남은 4건(프록시 위치, 일관된 해싱 링, 인접 행렬/리스트 2건)은 서로 그림이 다 다르다 — 하나의 문법으로 못 덮는다. 셋째, **임의 그래프는 배치 계산이 필요하다.** 다른 형태는 전부 세로로 쌓으면 되는데 이것만 아니다. 레포에 `@xyflow/react`가 이미 있지만(지도 모드용) 읽기 화면에 끌어오면 서버 렌더로 끝나던 페이지에 클라이언트 번들이 붙는다. 비용이 다른 형태의 다섯 배인데 수요는 절반이다.

**2×2 사분면 — 3건.** 그중 2건은 `기준 | GET | POST | PUT | PATCH | DELETE` 6열 표다. 이건 사분면이 아니라 **열 제한 위반**이라 다르게 풀어야 한다(아래 5단계). 나머지 1건(동기·비동기 × 블로킹·논블로킹)만 진짜 사분면이다. 1건에 형태를 만들지 않는다.

**결정 매핑과 2항 대비 — 코드 없이 프롬프트로.** 이 둘은 **이미 표로 표현할 수 있다.** `상황 | 방식 | 이유` 3열 표는 잘 읽히고 폰에서 카드로 접히는 것도 맞게 동작한다. 문제는 모델이 첫 칸을 무조건 `기준`으로 쓴다는 것이다(94.7%). 그리고 2항 대비를 stack으로 쓴다는 것이다(2층 30개).

이 둘은 **새 형태가 아니라 규칙과 검사로 고친다.** 코드 0줄, 대상 질문 37건(pick 13 + vs 24). 새 어휘를 하나도 안 늘리고 A등급 기준으로도 10건을 고친다.

**조건 집합 — 보류.** 데드락 4조건, XSS로 훔칠 수 있는 것, 게이트웨이 이점 — 이건 사실 **목록**이다. 목록은 도식이 아니고, 지금 게이트는 도식이 없으면 `도식없음`을 남긴다(`content-rules.ts:106`). 목록을 도식으로 셀지 말지는 별도 결정이라 여기서 정하지 않는다.

## 3. 문법

### 설계 원칙

기존 파서에서 그대로 가져온다.

1. **울타리 인식은 넉넉하게.** `FENCE_OPEN`은 `::: flow`처럼 띄어 쓴 것을 받고 `FENCE_CLOSE`는 `:::end`를 받는다(`blocks.ts:37-38`). 새 이름도 같은 정규식에 추가만 하면 그 관용이 따라온다.
2. **한 줄에 한 가지.** flow가 성공한 이유다. 한 줄이 한 걸음이라 모델이 틀릴 자리가 없다.
3. **못 알아보면 문단으로.** 새 `parseX`는 전부 `null`을 돌려줄 수 있어야 한다. `parseStack`처럼 무엇이든 받으면 어휘를 늘린 만큼 쓰레기가 화면에 나온다.
4. **문법을 새로 만들지 않는다.** 아래 넷 중 셋은 기존 문법을 그대로 쓰거나 필드 하나를 더한다. 새로 배울 것은 timeline 하나뿐이다.

이 넷째가 핵심이다. 문법이 같으면 **모델이 종류를 잘못 골라도 파싱은 성공한다.** 다른 렌더러로 그려질 뿐 화면이 깨지지 않는다.

### `:::state` — 상태 전이

**문법은 `:::flow`와 완전히 같다.** `parseFlow`를 그대로 쓴다. 바뀌는 것은 울타리 이름과 렌더러뿐이다.

이미 모델이 이 문법으로 상태 머신을 정확히 쓰고 있다(서킷 브레이커 예시). 학습 비용이 0이다.

```
상태 (state) — 같은 것이 상태를 바꾸며 돌아오거나 갈라질 때.
연결 상태, 프로세스 상태, 트랜잭션, 화면 수명주기.
**한 줄에 전이 하나다.** 왼쪽이 지금 상태, 오른쪽이 다음 상태, 콜론 뒤가 무엇이 그렇게 만드는가다.
같은 상태에서 여러 갈래로 나가면 그만큼 줄을 쓴다.
:::state
닫힘 -> 열림: 실패율이 기준을 넘는다. 이제 즉시 거절한다
열림 -> 반열림: 일정 시간이 지나 몇 건만 흘려본다
반열림 -> 닫힘: 흘려본 것이 성공하면 원래대로
반열림 -> 열림: 하나라도 실패하면 다시 막는다
:::
```

다른 주제 예시(프롬프트에 넣지 않고 참고용):

```
:::state
ESTABLISHED -> FIN_WAIT_1: 내가 먼저 FIN을 보냈다
FIN_WAIT_1 -> FIN_WAIT_2: 상대가 ACK만 보냈다
FIN_WAIT_2 -> TIME_WAIT: 상대의 FIN이 왔다. ACK로 답한다
TIME_WAIT -> CLOSED: 2MSL을 기다렸다. 늦게 온 조각을 여기서 흡수한다
:::
```

```
:::state
비영속 -> 영속: persist를 부르면 1차 캐시에 들어간다
영속 -> 준영속: detach하거나 컨텍스트가 닫힌다
준영속 -> 영속: merge로 다시 붙인다
영속 -> 삭제: remove. 커밋할 때 DELETE가 나간다
:::
```

파서: `parseFlow`와 동일. 추가 조건 하나 — 전이가 2개 미만이면 `null`(상태가 하나뿐이면 상태 머신이 아니다).

### `:::tree` — 무엇이 무엇에 속하는가

stack의 `이름 | 설명`에 **들여쓰기**를 더한다.

들여쓰기 관용이 이 문법의 전부다. 모델은 2칸, 4칸, 탭, `-` 불릿을 섞어 쓴다. 그래서 깊이를 절대값으로 읽지 않고 **나온 들여쓰기 폭을 모아 정렬한 뒤 0·1·2로 다시 매긴다.** 2칸이든 4칸이든 탭이든 같은 트리가 나온다.

```
트리 (tree) — 무엇이 무엇에 속하는가가 답일 때.
탐색 트리, 상속, 참조 사슬, 컴포넌트 계층, 인증서 체인.
**들여쓰기가 소속을 뜻한다.** 자식은 부모보다 두 칸 더 들여 쓴다.
`|` 뒤는 보조 설명이고 없어도 된다. 깊이는 세 단계까지만 쓴다.
:::tree
50 | 루트
  30 | 왼쪽 가지는 전부 50보다 작다
    20
    40
  70 | 오른쪽 가지는 전부 50보다 크다
    60
:::
```

참고용:

```
:::tree
루트 CA | 브라우저가 미리 신뢰하는 것
  중간 CA | 루트가 서명했다
    example.com | 중간이 서명했다. 여기서 사슬이 끝난다
:::
```

```
:::tree
공통 조상 | 상태를 여기서 소유한다
  자식 A | 값을 props로 받는다
  자식 B | 바꾸는 함수를 받는다
:::
```

파서 규칙:

- 앞의 공백을 센다. 탭은 2칸으로 친다. 맨 앞의 `-`나 `*` 불릿은 떼고 그 자리도 들여쓰기로 친다.
- 나온 들여쓰기 폭을 중복 없이 모아 오름차순 정렬하고 그 순서를 깊이 0·1·2…로 쓴다.
- 첫 줄이 들여쓰기되어 있으면 `null`. 깊이가 한 번에 2 이상 뛰면 `null`.
- 깊이 3을 넘으면 3으로 눌러 그린다(**`null`이 아니다** — 도식을 잃는 쪽이 더 나쁘다).
- 줄이 2개 미만이면 `null`.

### `:::memory` — 어디에 놓이고 어느 쪽으로 자라는가

stack의 `이름 | 설명`에 **선택 필드 하나**를 더한다. 세 번째 칸은 `위로` 또는 `아래로`만 받는다. 그 외 값이면 `null`이라 stack과 달리 걸러진다.

```
메모리 (memory) — 무엇이 어디에 놓이고 어느 쪽으로 자라는가가 답일 때.
주소 공간, 스택과 힙, 스레드가 나눠 쓰는 것과 따로 가지는 것.
**위가 높은 주소다.** `|` 뒤가 설명, 그 뒤에 `위로`나 `아래로`를 적으면 자라는 방향이 그려진다.
:::memory
스택 | 지역 변수와 복귀 주소. 함수가 끝나면 사라진다 | 아래로
힙 | new로 잡은 것. GC가 거두거나 직접 반납한다 | 위로
데이터 | 전역·정적 변수. 프로그램이 끝날 때까지 산다
코드 | 기계어. 읽기 전용이다
:::
```

참고용:

```
:::memory
JVM 스택 | 스레드마다 하나씩. 프레임이 쌓인다 | 아래로
힙 | 객체와 배열. 모든 스레드가 나눠 쓴다 | 위로
메서드 영역 | 클래스 정보와 상수 풀. 여기도 공유한다
:::
```

파서: `이름 | 설명 | 방향` 세 칸까지. 칸이 넷 이상이면 `null`. 세 번째 칸이 `위로`/`아래로`가 아니면 `null`. 층이 2개 미만이면 `null`.

### `:::timeline` — 누가 같은 시간에 무엇을 하는가

**유일하게 새로 배울 문법이다.** 한 줄이 한 주체, `|`로 나뉜 칸이 시간이다.

```
타임라인 (timeline) — 둘 이상이 같은 시간에 무엇을 하는가가 답일 때.
경쟁 상태, 블로킹과 논블로킹, 한 연결에 요청이 겹치는 것.
**한 줄이 한 주체다.** 첫 칸이 이름이고 그 뒤가 시간 순서대로의 칸이다.
아무것도 안 하는 칸은 비워 둔다 — 비어 있는 것이 기다림이다.
주체는 셋까지, 칸은 다섯까지 쓴다.
:::timeline
스레드 A | 잔액 100을 읽는다 | 100+50을 계산한다 |  | 150을 쓴다
스레드 B |  | 잔액 100을 읽는다 | 100+30을 계산한다 | 130을 쓴다
:::
```

참고용:

```
:::timeline
블로킹 | read를 부른다 | 기다린다 | 기다린다 | 결과를 받는다
논블로킹 | read를 부른다 | 다른 일을 한다 | 다시 물어본다 | 결과를 받는다
:::
```

파서:

- `|`로 자른다. 첫 칸이 주체 이름, 나머지가 시간 칸.
- 줄이 2개 미만이면 `null`. 시간 칸이 2개 미만이면 `null`(한 칸이면 시간이 아니다).
- 줄마다 칸 수가 다르면 **긴 쪽에 맞춰 빈 칸으로 채운다**(`null`이 아니다). 모델이 끝의 빈 칸을 자주 빠뜨린다.
- 주체가 4개를 넘거나 칸이 6개를 넘으면 `null`(폰에서 못 읽는다).

이것이 마크다운 표와 헷갈릴 위험은 없다. `parseTable`은 구분줄이 있어야만 표로 보고(`blocks.ts:138`), 울타리 안은 애초에 `parseTable`을 타지 않는다.

### 파서에 손대는 자리

`blocks.ts`에서 바뀌는 것은 세 곳이다.

- `FENCE_OPEN` / `INLINE_FENCE`의 이름 목록에 새 이름을 더한다(`blocks.ts:37`, `blocks.ts:51`). **`INLINE_FENCE`를 빠뜨리면 못 알아본 울타리 기호가 본문에 샌다.**
- `splitTrailingFence`의 정규식에도 같은 이름을 더한다(`blocks.ts:171`). 여기를 빠뜨리면 "…나뉜다. :::tree"처럼 이어 쓴 것이 안 살아난다.
- `parseBlocks`의 분기(`blocks.ts:235`)를 이름 → 파서 표로 바꾼다.

이름 목록이 세 군데에 흩어져 있으므로 **상수 하나로 뽑아 셋이 같이 쓰게 한다.** 지금은 셋이 손으로 맞춰져 있어서 하나만 고치면 조용히 어긋난다.

## 4. 렌더

전부 React 요소다. SVG를 쓸 자리가 생기면 `<svg>` 태그를 JSX로 조립하고 문자열은 어디에도 넣지 않는다. 아래 넷 중 SVG가 필요한 것은 없다 — 전부 div와 목록으로 그려진다.

### 색

**`--d1`~`--d5`를 쓰지 않는다.** 이 다섯은 깊이 인코딩 전용이다(`src/lib/journey/depth.ts`를 `PathChips.tsx:97`과 `MinimapStrip.tsx:78,87`이 쓴다). 도식에 `--d3`을 칠하면 독자에게 "3단계 깊이"라는 뜻으로 읽힌다. 색이 정보라서 함부로 못 쓴다.

도식이 쓸 수 있는 것은 이미 유틸리티로 나와 있는 것뿐이다 — `bg-raised` · `bg-surface` · `border-line` / `divide-line` · `text-ink` · `text-muted` · `text-faint` · `text-accent`(=`--d0`) · `bg-accent-soft` · `text-on-accent` · `warn` 계열. 기존 세 도식이 정확히 이 안에서 그려진다.

### 접근성 공통

기존 선례를 그대로 따른다. `FlowDiagram`은 화살표에 `aria-hidden`을 걸고 대신 `aria-label="에서"`를 둔다(`Diagram.tsx:47-59`). `TableDiagram`은 카드로 접힌 뒤에도 표로 읽히도록 `role`을 손으로 붙인다(`Diagram.tsx:125-149`).

새 도식도 같다. **그림 기호는 전부 `aria-hidden`, 뜻은 텍스트로.** 화살표·자람 방향·들여쓰기 선은 낭독기에 안 보이게 하고, 대신 의미를 담은 요소를 쓴다.

### `state`

**출발 상태로 묶는다.** 이것이 flow와 다른 전부다.

```
┌──────────────────────────────┐
│ 닫힘                          │
│   → 열림                      │
│     실패율이 기준을 넘는다      │
├──────────────────────────────┤
│ 열림                          │
│   → 반열림                    │
│     일정 시간이 지나 몇 건만    │
├──────────────────────────────┤
│ 반열림                        │
│   → 닫힘                      │
│     흘려본 것이 성공하면        │
│   ↩ 열림                      │
│     하나라도 실패하면          │
└──────────────────────────────┘
```

- 마크업은 중첩 목록이다. 바깥 `<ul>` 항목이 상태, 안쪽 `<ul>`이 그 상태에서 나가는 길. **낭독기는 중첩 목록을 그대로 읽으므로 "반열림 아래에 두 갈래"가 소리로 전달된다.**
- 갈림이 눈에 보인다 — 안쪽 항목이 둘이면 둘로 갈라진다는 뜻이다. 지금 flow가 지우는 정보가 이것이다.
- **되돌아가는 전이**(앞에 이미 나온 상태로 가는 것)는 `↩`를 붙인다. `aria-hidden`이고, 대신 시각적으로 숨긴 텍스트로 "앞의 상태로 돌아간다"를 둔다.
- 상태 이름: `text-ink font-medium`. 대상 상태: `text-accent`. 사건 설명: `text-muted 15px`.
- 껍데기는 `figure > ul.divide-y.divide-line`으로 기존 둘과 같다.
- 390px: 세로로만 쌓이므로 가로 스크롤이 없다. 들여쓰기는 한 단(12px)뿐이라 좁아질 자리가 없다.

### `tree`

- 중첩 `<ul>`. 깊이가 곧 중첩이라 낭독기가 소속을 그대로 읽는다. 여기는 별도 라벨이 필요 없다.
- 들여쓰기는 `padding-left: 14px`, 가이드선은 `border-left: 1px solid var(--line)`. 선은 `aria-hidden`이 아니라 아예 CSS 테두리라 낭독기에 안 잡힌다.
- 이름 `text-ink 15px`, `|` 뒤 설명 `text-muted 13px`. 설명은 이름 **아래 줄**에 둔다 — stack처럼 오른쪽에 붙이면 깊이 2에서 이름 칸이 좁아진다.
- 390px: 깊이 3에서 왼쪽 여백이 42px, 남는 폭이 ~310px이다. 이름 15자쯤 들어간다. 넉넉하지는 않지만 접을 필요는 없다.
- 깊이가 3을 넘으면 3으로 눌러 그린다. 눌린 자리는 형제로 보이는데, 도식을 통째로 잃는 것보다 낫다.

### `memory`

stack과 **붙어 있는 것**으로 구별한다.

```
높은 주소 ┐
 ┌────────────────────────────┐
 │ 스택                    ↓  │
 │ 지역 변수와 복귀 주소       │
 ├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┤   ← 점선: 빈 공간
 │ 힙                      ↑  │
 │ new로 잡은 것              │
 ├────────────────────────────┤
 │ 데이터                     │
 │ 전역·정적 변수             │
 ├────────────────────────────┤
 │ 코드                       │
 └────────────────────────────┘
낮은 주소 ┘
```

- 칸 사이에 여백이 없다. `divide-y divide-line`로 붙여 그린다. stack은 층마다 `py-3`으로 떠 있는데, memory는 **연속한 공간**이라는 것이 뜻이라 붙여야 한다.
- 왼쪽 바깥에 `높은 주소` / `낮은 주소` 라벨(`text-faint 11px`). 세로 축은 그리지 않는다 — 라벨 둘이면 방향이 읽힌다.
- 자람 방향이 있는 칸은 오른쪽에 `↓`/`↑`(`text-accent`, `aria-hidden`). 뜻은 시각적으로 숨긴 텍스트 "아래로 자란다"로 둔다.
- **방향이 서로 반대인 두 칸이 붙어 있으면 그 사이를 점선으로 그린다.** 마주 자란다는 것이 이 도식의 존재 이유다. 점선 한 줄이 그것을 말한다.
- 마크업은 `<ol>`(위에서 아래가 주소 순서라 순서가 있다). 각 칸은 `<li>`.
- 390px: 세로라 문제없다. 왼쪽 라벨은 `absolute`로 빼지 않고 `grid-cols-[auto_1fr]`로 자리를 준다. 라벨 폭 44px + 본체 ~330px.

### `timeline`

**시간을 아래로 흘린다.** 가로 시간축은 폰에서 죽는다 — 5칸이면 칸당 70px이라 한 칸에 두 글자만 들어간다.

```
        스레드 A        스레드 B
  ┌───────────────┬───────────────┐
1 │ 잔액 100 읽기 │               │
  ├───────────────┼───────────────┤
2 │ 100+50 계산   │ 잔액 100 읽기 │
  ├───────────────┼───────────────┤
3 │               │ 100+30 계산   │
  ├───────────────┼───────────────┤
4 │ 150 쓰기      │ 130 쓰기      │
  └───────────────┴───────────────┘
```

- **진짜 `<table>`을 쓴다.** 행이 시간, 열이 주체. `<th scope="col">`이 주체 이름이다. 낭독기가 "2번째: 스레드 A 100+50 계산, 스레드 B 잔액 100 읽기"로 읽는다. 접근성이 마크업에서 공짜로 나온다.
- 격자선은 최소로. 칸 내용은 `bg-accent-soft` 알약, 빈 칸은 **아무것도 안 그린다.** 빈 칸이 비어 보이는 것이 이 도식의 전부다 — 기다림과 겹침이 거기서 읽힌다.
- 왼쪽에 순번(`font-mono text-faint 11px`). `TableDiagram`이 이미 `font-mono`를 측량값에 쓰는 결이다.
- 390px: 주체 2개면 열당 ~165px, 3개면 ~110px. 3개는 빠듯하므로 프롬프트에서 **셋까지**로 못박는다.
- `.rtable` 접기(`globals.css:154-192`)를 **타면 안 된다.** 그 규칙은 첫 칸을 카드 제목으로 삼는데 timeline의 첫 칸은 순번이라 의미가 없다. 클래스를 안 붙이면 그만이다. 대신 `overflow-x: auto`를 figure에 걸어 3열이 넘칠 때 이 안에서만 밀리게 한다(`TableDiagram`의 주석이 말하는 원칙과 같다).

## 5. 순서

각 단계는 따로 배포된다. 뒤 단계가 앞 단계에 기대지 않는다.

### 0단계 — stack의 뜻을 좁히고 게이트로 센다

**코드에서 새 도식은 0개다.** 프롬프트 규칙과 `contentIssues` 검사만 손댄다.

- 프롬프트: `stack`은 **3층 이상**일 때만. 둘을 견주는 것은 표다.
- 프롬프트: 표의 첫 칸이 늘 `기준`일 필요는 없다. 조건이면 조건을, 갈래면 갈래를 적는다. (손으로 쓴 30개의 머리글 11가지를 예시로 붙인다)
- 프롬프트: 표 안에 `---` 구분줄을 넣지 않는다. 표는 울타리 없이 그대로 쓴다.
- `contentIssues`에 추가: stack 2층 → `note` · 표 4열 이상 → `block` · 표 1행 → `note`.

고치는 질문: A등급 10건, 느슨하게 세면 **40건**(vs 24 + pick 13 + 6열 표 3). 화면이 깨지고 있는 2건도 여기서 잡힌다.

이 단계에는 값을 치른다. 2층 stack 30개가 표로 옮겨가면 **표 비율이 51%에서 63%로 오른다.** 그 숫자를 목표로 삼으면 이 단계는 실패로 보인다. 목표는 표 비율이 아니라 각 설명이 맞는 그림을 얻는 것이다. 지표를 바꿔야 한다 — **"A등급 오형 71건"이 지표고 표 비율은 지표가 아니다.**

### 1단계 — `:::state`

- 파서: `parseFlow` 재사용 + 전이 2개 미만이면 `null`. 새 코드 5줄쯤.
- 렌더러: `StateDiagram` 신규 (~60줄).
- 프롬프트: 위 블록 그대로 + flow와의 판별 한 줄.
- 고치는 질문: **14건.**

### 2단계 — `:::tree`

- 파서: 들여쓰기 정규화 (~30줄).
- 렌더러: `TreeDiagram` 재귀 (~40줄).
- 고치는 질문: **16건**(트리 13 + stack으로 그려진 참조 사슬 3).

### 3단계 — `:::memory`

- 파서: stack에 세 번째 칸 (~15줄).
- 렌더러: `MemoryDiagram` (~50줄). 반대 방향 감지 로직이 조금 있다.
- 고치는 질문: **11건.**

### 4단계 — `:::timeline`

- 파서: 칸 채우기 포함 (~25줄).
- 렌더러: `TimelineDiagram` (~50줄).
- 고치는 질문: **8건.**

전부 마치면 A등급 71건 중 **59건**이 맞는 형태를 얻는다. 남는 12건은 토폴로지 4·사분면 1·집합 3·기타다.

### 단계마다 재는 것

`npm run measure:diagrams`가 이미 종류별 개수와 기호 유출을 센다(`scripts/measure-diagrams.ts:140`). 여기에 둘을 더한다.

- **모르는 울타리 이름 집계.** 모델이 `:::table`이나 `:::diagram`을 지어내는지 본다. 지금은 그런 것이 전부 `도식삼킴`으로 뭉뚱그려진다(`content-rules.ts:103`).
- **종류별 오형 표본.** 새 종류가 붙은 해설을 몇 개 눈으로 본다. 자동으로 못 재는 것이 "이 주제에 이 형태가 맞나"라서다.

나빠지면 그 단계를 되돌린다. 되돌리는 단위가 한 종류라 값이 싸다.

## 6. 위험

### 종류가 늘면 고르기가 어려워진다 — 이미 그렇다

이 위험은 가정이 아니라 **관측된 사실**이다. 지금 종류가 셋인데도 모델은 이렇게 실패한다.

- stack 울타리 안에 마크다운 표를 넣는다 (2건, 화면이 깨진다)
- 열이 세 개까지라고 했는데 여섯 개를 쓴다 (2건)
- 축이 하나인데 표 골격을 세운다 (4건)
- 상태 머신을 시퀀스로 그린다 (18건)

종류가 일곱이 되면 이 실패가 늘 것이다. 그것을 부인하지 않는다. 대신 **틀렸을 때의 손해를 줄이는 쪽**으로 설계했다.

### 완화 1 — 문법을 공유해서 "틀려도 안 깨지게"

이것이 이 설계의 중심이다.

| 새 형태 | 문법 | 헷갈릴 상대 | 헷갈리면 |
|---|---|---|---|
| state | flow와 **동일** | flow | 다른 렌더러로 그려진다. 파싱은 성공 |
| memory | stack + 선택 칸 | stack | 방향 화살표만 안 그려진다 |
| tree | stack + 들여쓰기 | stack | 들여쓰기가 무시된 평평한 목록 |
| timeline | 새로 배움 | 표 | 울타리 안이라 표와 안 섞인다 |

**셋은 잘못 골라도 화면이 안 깨진다.** 지금 화면을 깨는 유일한 실패(stack이 표를 삼키는 것)는 문법이 서로 **다르기** 때문에 생겼다. 문법을 같게 두면 그 실패가 안 생긴다.

### 완화 2 — "무엇을 그릴까"가 아니라 "무엇이 답인가"로 가른다

프롬프트에 형태를 나열하면 모델이 목록에서 고른다. 답의 모양으로 물으면 내용에서 형태가 따라 나온다.

```
도식은 답의 모양으로 고른다. 종류를 훑어 고르지 않는다.
- 누가 누구에게 무엇을 보내는 **차례**가 답이면 flow
- 같은 것이 **상태를 바꾸며** 돌아오거나 갈라지면 state
- 무엇이 무엇에 **속하는가**가 답이면 tree
- 무엇이 **어디에 놓이고 어느 쪽으로 자라는가**가 답이면 memory
- 둘 이상이 **같은 시간에** 무엇을 하는가가 답이면 timeline
- **위아래로 쌓인 층 자체**가 답이면 stack (세 층 이상일 때만)
- 같은 잣대로 둘 이상을 **견주는 것**이 답이면 표
어느 것도 아니면 도식을 넣지 않는다. 억지로 만든 도식은 없는 것보다 나쁘다.
```

### 완화 3 — 검사하지 않는 규칙은 규칙이 아니다

`content-rules.ts:8`이 이미 그렇게 적어 놓았다. 새 규칙마다 검사를 붙인다.

| 규칙 | 검사 | 등급 |
|---|---|---|
| stack은 3층 이상 | 층 수 | note |
| 표는 3열까지 | 열 수 | block |
| 표는 2행 이상 | 행 수 | note |
| state는 전이 2개 이상 | 파서가 이미 거른다 | — |
| timeline은 주체 3까지 | 줄 수 | block |
| 모르는 울타리 이름 | `:::` 뒤 낱말 대조 | block |

마지막 것이 새 어휘의 안전장치다. 지금은 `도식삼킴` 하나로 뭉쳐 있어서 **모델이 무엇을 지어내는지 알 수가 없다.** 이름을 세면 다음 종류를 무엇으로 만들지도 데이터로 나온다.

### 완화 4 — 프롬프트가 길어지는 값

도식 규칙은 지금 1419자다(SYSTEM 전체 3163자의 45%). 네 종류를 더하면 도식 규칙이 2800자쯤 되고 SYSTEM은 4500자를 넘는다. 문체 규칙과 꼬리질문 규칙이 상대적으로 묻힌다.

`tests/llm/prompt-integrity.test.ts`가 규칙 표식을 세고 있으니 새 울타리 이름을 `EXPAND_MARKS`에 더한다. 그러면 도식 규칙이 통째로 잘려도 시험이 먼저 깨진다.

묻히는 문제 자체는 단계마다 `measure:diagrams`의 문단 길이·꼬리질문 길이 지표로 본다. 도식 종류를 늘렸더니 문체가 나빠지면 그것이 값이다.

### "종류를 늘리는 것보다 표를 덜 쓰게 만드는 게 먼저인가"

**전제를 바꿔야 한다.** 표는 남용이 아니다 — 127개 중 65~76%가 정당한 비교표다. 도피처는 **stack이다.**

| | 개수 | A등급 오형 | A+B 오형 |
|---|---|---|---|
| 표 | 127 | 30 (24%) | 44 (35%) |
| stack | 56 | 23 (41%) | 49 (88%) |
| flow | 66 | 18 (27%) | 19 (29%) |

`parseStack`이 절대 실패하지 않는다는 것이 구조적 원인이다. 무엇이든 받는 상자가 하나 있으면 애매한 것이 전부 거기로 간다.

그러니 순서는 "표를 덜 쓰게"가 아니라 **"stack의 뜻을 좁히고, 갈 곳을 만든다"**다. 0단계가 앞을 맡고 1~4단계가 뒤를 맡는다. 0단계만 하면 stack에서 밀려난 것이 표로 가서 표 비율이 오르고, 1~4단계만 하면 stack은 그대로 무엇이든 받는다. 둘 다 해야 한다.

---

## 1단계로 무엇을 할 것인가

**`:::state`.** 근거 넷.

**하나 — 수요가 가장 크다.** A등급 14건으로 최대다. 서킷 브레이커, TCP 종료, Activity 수명주기 3건, JPA 영속성 컨텍스트 3건 — 전부 면접에서 실제로 물어보는 것들이다.

**둘 — 지금 도식이 적극적으로 거짓말을 한다.** 다른 후보들은 "표로도 읽히긴 한다" 수준인데 이건 다르다. 서킷 브레이커의 `반열림 -> 닫힘`과 `반열림 -> 열림`이 3번과 4번 걸음으로 그려진다. 독자는 3번 다음에 4번이 일어난다고 읽는다. **틀린 것을 배운다.** 정보를 못 준 것과 틀린 것을 준 것은 다른 등급의 실패다.

**셋 — 문법이 이미 있다.** `parseFlow`를 그대로 쓴다. 모델은 지금도 이 문법으로 상태 머신을 정확히 쓰고 있다 — 울타리 이름만 `flow`라 렌더러가 잘못 그릴 뿐이다. **모델 쪽 학습 비용이 0이고, 잘못 골라도 파싱이 성공한다.** 첫 종류로 이보다 안전한 것이 없다.

**넷 — 되돌리기 쉽다.** 실패하면 `FENCE_OPEN`에서 이름 하나를 빼면 된다. 그러면 `:::state`가 안 알아본 울타리가 되어 내용만 문단으로 살아난다. 파서의 첫째 성질이 그것을 보장한다.

값도 있다. flow와 state의 문법이 같아서 **모델이 둘을 섞을 것이다.** 시퀀스를 `:::state`로 쓰면 "출발 상태별 묶음"이 그냥 목록으로 보이고, 상태 머신을 `:::flow`로 쓰면 지금과 같다. 후자는 지금과 같으니 나빠지지 않고, 전자는 읽히기는 한다. **어느 쪽으로 틀려도 지금보다 나쁘지 않다**는 것이 이 선택의 값이다.

0단계(stack 3층 규칙 + 게이트 검사)는 코드가 30줄 남짓이고 1단계와 겹치는 파일이 없다. 같이 내는 것을 권한다. 굳이 하나만 고른다면 `:::state`다 — A등급 기준으로 14건 대 10건이라 그쪽이 크고, 화면이 깨지는 2건은 0단계 없이도 `stack 3층` 규칙 한 줄로 잡힌다.
