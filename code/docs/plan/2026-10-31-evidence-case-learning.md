# CS Pathfinder 근거 판단 학습 — 첫 실행 계획

작성일: 2026-10-31. 상태: 첫 모듈 구현·검증 완료.

## 목적과 범위

학습자가 공개 사례의 근거를 들어 자신의 판단을 설명하고 조건이 바뀌었을 때 무엇을 다시 확인할지 작성하는 학습 경험을 만든다. [조사와 한계](../research/adult-learning-2026-10-31/README.md)를 출발점으로 삼는다. 인터뷰를 구현의 선행 조건으로 두지 않는다.

첫 대상은 GitHub 2026년 5월 4일 장애 보고서다. 공개 사실 요약, 작성자의 해설·질문, 교육용 변형 조건을 분리한다. 정확한 당시 로그·내부 임계치·의사결정 순서는 제공되지 않았으므로 재현하지 않는다. 개발자는 관측과 가설, 프로젝트 PM은 변경·중단·재개 조건, 제품 PM은 사용자 영향과 서비스 회복 기준을 연습한다. 한 사례로 각 직무 전체를 가르친다고 주장하지 않는다.

## 순서와 완료 기준

| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| 1. 조사 보존 | 분석 HTML·출처 원장·결정 요약 | 문서 수와 읽은 범위·한계가 일치하고 임시 폴더 밖에 보존됨 |
| 2. 콘텐츠 계약 | 버전 있는 한국어·영어 사례 패키지 | 역할별 산출물·필수 근거·미확인 조건·중대 오개념을 정의하고 질문·예시·점검 기준과 대응. 한영의 사실·부정·조건 의미 검토 |
| 3. 학습 흐름 | `/learn/cases`와 사례 화면 | 역할 선택 → 첫 판단/시범 선택 → 근거 비교·수정 → 새 조건 과제 → 재설명 |
| 4. 기록 보호 | 별도 브라우저 기록·내보내기 | 첫 제출 보존, 역할·언어 전환 유지, 저장 실패 알림, 손상·다른 탭 기록 덮어쓰기 거부 |
| 5. 확인과 검토 | 기능 테스트·타입 검사·빌드·화면 확인·debate | 독립 답안 노출 순서·저장 실패·재방문 검증. 결과와 남은 한계를 문서화 |

## 이번 구현의 설계

- 공통 사실은 모두 읽을 수 있고 낯선 용어는 같은 화면에서 확인한다. 첫 판단을 작성하기 어려우면 작성 예시를 먼저 볼 수 있다.
- 첫 제출은 이후 수정안과 별도로 보관한다. 제출 당시 화면의 예시 열람 여부와 외부 도움 자기보고(있음/없음/미응답)를 각각 기록한다. 근거 비교에서 바꾼 결론뿐 아니라 바꾸지 않은 이유도 기록한다.
- 변형 과제와 뒤늦은 재설명은 예시 답안을 바로 노출하지 않는다. 재설명에서도 공통 사실·용어·출처는 읽을 수 있으므로 단서 없는 기억 회상으로 해석하지 않는다. 복귀 후에는 이전 본인 답도 가리고 첫 재설명을 별도 제출한다. 복습 예정 시각·실제 제출 시각·이전 과제 이후 실제 경과 시간을 구분한다. 같은 사례의 변형은 제한된 맥락의 적용 연습이며 직무 전반에 전이됐다는 증거로 부르지 않는다. 외부 도움 사용은 본인이 표시한다. 독립 수행 여부를 기술적으로 판정하지 않는다.
- 1일·3일 뒤 재설명 시점은 복습 선택지다. 알림 전송이나 효과가 입증된 개인별 최적 간격이 아니다. 브라우저에서 다음 날짜를 확인한다.
- 역할마다 저장 공간을 나눈다. 한국어·영어 전환은 같은 과제 ID와 답안을 유지한다. 번역 기여는 두 언어의 사실·조건·점검 항목을 함께 검토한다.
- 기존 로그인·서재·복습 저장 형식은 수정하지 않고 이 모듈의 기록만 로컬 저장한다. 답안을 서버나 AI로 전송하지 않는다.
- 오픈소스 기여자는 원문 사실/가정/작성 예시, 출처 날짜, 역할별 점검 기준, 두 언어 대응을 함께 수정한다. 실제 전문가 검토가 생기면 검토자·범위·날짜를 추가한다.

## 역할별 콘텐츠 검토 기준

| 역할 | 관찰할 산출물과 근거 | 확인되지 않은 조건 | 중대한 오개념 |
|---|---|---|---|
| 개발자 | F2·F3로 가설 구성, 추가 관측과 가설을 반박할 신호 작성 | 특정 쿼리·연결 한도·개별 잠금 상태 | 마이그레이션만으로 교착 상태 확정, 사용자 트래픽만을 전체 부하로 취급 |
| 프로젝트 PM | F2의 변경과 F3의 의존성 연결, 중단·재개 제안과 협의·승인 주체 작성 | 조직별 승인권·허용 지연·재개 임계치 | PM에게 중단 승인권이 있다고 가정, 변경 완료를 회복으로 취급 |
| 제품 PM | F1의 증상을 사용자 과업에 연결, 보호할 경험과 사용자 관점의 회복 근거 작성 | 과업별 중요도·개별 사용자 손실·서비스 약속 | 이용량만으로 중요도 결정, 오류가 없으면 사용자 영향도 없다고 단정 |

키보드만으로 역할 선택→입력→비교→변형 과제→저장·복귀를 확인한다. 라벨·상태 알림·언어 속성·초점 이동을 점검한다. 모션은 사용하지 않는다. 이 범위의 점검을 전면 접근성 인증으로 표현하지 않는다.

## 이번 범위 밖과 다음 작업

무제한 사례 생성, 자동 서술형 채점, 전세계 전체 커리큘럼, 음성 튜터, 사용자 행동 수집은 넣지 않는다. 이번에는 하나의 완결된 학습 흐름과 콘텐츠 수정 방법을 확인한다.

후속 순서: (1) 첫 모듈의 콘텐츠·화면 검토 사항 수정 → (2) 동일 구조로 다른 주제 한 개를 수작업 제작하며 제작·번역·검토 시간 기록 → (3) 출처 변경 시 영향 받는 질문·예시·번역을 확인하는 기여 절차 확장. 여러 모듈을 만들어 본 뒤 공통 플랫폼 범위를 정한다.

학습 효과를 나중에 평가할 때는 같은 사람의 첫 답·수정 답만 비교해 인과효과를 주장하지 않는다. 과제 난이도·사전지식·도움·시간을 분리하고 새로운 과제의 근거 설명 및 지연 수행을 평가한다. 인터뷰를 하지 않더라도 이 한계는 유지한다.

## Debate 결과: Evaluator-Optimizer

대상은 이번 실행 계획과 조사 README다. 이전 D3-lite 2라운드의 접근법 비교를 반복하지 않았다. Critic과 doc-reviewer 모두 계획 수준 PASS이며, 사용자 수요·학습효과의 실증 판정은 아니다. 주요 보완은 도움 상태 분리, 이전 답을 가린 재설명과 실제 경과시간, 역할별 관찰 가능한 산출물, 한영·키보드 확인 기준이며 본 계획과 구현에 반영했다. 중대한 미해결 이슈는 보고되지 않았다. 시간 범위가 다른 장애 지속시간 수치는 첫 모듈에서 생략한다.

## 작업 환경과 검증 기록

- 기준 커밋: `8e0f4dd12f9b4f3820fd64e4ff0cac107b1ddc4a`.
- 브랜치: `feat/evidence-case-learning`.
- 별도 작업 폴더: `cs-evidence-case-learning`. 기존 `cs-pm-integration`의 진행 중 수정은 이 작업에 합치지 않는다.
- 검증 시 운영 DB 환경을 주입하지 않고 별도 로컬 PGlite를 사용한다.
- 기능 테스트: 새 사례·저장 13개와 기존 홈·탐색 4개, 총 17개 통과. 타입 검사 통과. 운영 DB 연결 없이 프로덕션 빌드 통과(새 사례 두 경로 정적 생성).
- 콘텐츠 검토: 세 역할의 목표/질문/예시/점검 정합성과 한영 의미 대응 PASS. 예시 열람 상태의 역할 전환 오류를 수정하고 회귀 테스트 추가. 프로젝트 PM의 변경 영향·승인 표현과 영어 후속 조치의 추진 상태 수정.
- 브라우저: 키보드 역할 선택, 초기 판단 입력·제출, 수정, 변형 과제, 체크, 3일 뒤 날짜 저장, 새로고침 후 이전 답 가림 확인. 테스트 입력은 에이전트가 만든 것으로 사용자 학습 성과 데이터가 아님.
- 수동 저장·내보내기만 지원, 기존 계정 서재/복습 목록 통합과 가져오기 UI는 후속 범위. 실제 학습자에게 쉬운지와 학습효과는 미검증.
- 게시·푸시: 이번 작업에 포함하지 않음. 실행 시 한국어 문구 검토와 공통 pre-push gate 절차 필요.

조사 보존부터 첫 모듈의 콘텐츠·화면·기록 보호·검토까지 이번 1~5단계를 완료했다. [기여와 실행 안내](../case-learning.md), [검증 기록과 화면](../qa/case-learning-2026-10-31/README.md)을 함께 보관한다. 한영 전환·밝은/어두운 화면과 브라우저의 실제 JSON 내보내기도 확인했다.

다음 작업은 두 번째 주제를 같은 구조로 수작업 제작하며 드는 시간과 검토 문제를 기록하는 것이다. 두 번째 모듈에서 제작·번역·검토 비용을 확인한 뒤 공통화할 구조를 정한다.
