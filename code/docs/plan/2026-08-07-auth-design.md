## 0. 먼저 바로잡을 사실 세 가지

설계에 들어가기 전에, 지시받은 전제 중 실제와 다른 것을 적는다.

**Supabase를 쓰지 않는다.** `@supabase/supabase-js`는 `package.json:38`에 있지만 `src/`·`scripts/`·`tests/` 어디에서도 import하지 않는다. `supabase/migrations/`라는 경로 이름만 남았고 그 경로를 참조하는 곳은 `src/lib/db/client.ts:48` 한 줄뿐이다. 실제 DB 접근은 전부 `pg`의 `Pool`이다(`client.ts:91-131`). **이 의존성은 지워도 된다.**

**운영 DB에는 마이그레이션이 자동으로 돌지 않는다.** 지시문은 "`client.ts`가 순서대로 돌린다"고 했지만 절반만 맞다. `client.ts:185`가 `DATABASE_URL`이 있으면 `__csqtMigrated = true`를 즉시 세워 **마이그레이션을 건너뛴다.** 파일을 실제로 적용하는 것은 `scripts/migrate.ts`뿐이고, 여기만 `schema_migrations(name, applied_at)` 추적 테이블을 쓴다(`migrate.ts:26-31`). 파일마다 `begin` → 실행 → 기록 → `commit`이고 실패하면 `rollback` 후 즉시 중단한다(`migrate.ts:46-60`). 이미 적용된 파일은 이름으로 건너뛴다(`migrate.ts:41`). 파일 순서는 두 러너 모두 파일명 문자열 정렬이다(`client.ts:136`). 결번 `0004`는 아무도 검사하지 않는다 — 디렉터리에 있는 파일만 훑으므로 조용히 지나간다.

이것이 배포 순서를 강제한다. **스키마를 먼저 올리고, 그 다음에 코드를 배포한다.** 새 컬럼을 읽는 코드가 마이그레이션보다 먼저 뜨면 그 순간 500이다.

**데이터 규모가 지시문과 다르다.** 운영 Neon 실측(2026-08-07, `npm run db:status` + 읽기 전용 count):

| 테이블 | 행 수 |
|---|---|
| `qnode` | 271 (batch 258 · on_demand 13) |
| `qnode_suggestion` | 1355 (그중 `target_node_id` 연결된 것 **8개**) |
| `semantic_relation` | 330 (active 330 · `votes >= 2`인 것 **305**) |
| `qedge` | **10** |
| `tree` | 10 (daily 9 · shared **1**) |
| `tree_occurrence` | 11 |
| `tree_vote` | **1행 · 투표자 1명** |
| `expansion_event` | 29 (전부 accepted) |

지시문의 "질문 251개·의미 관계 305개·공유 트리 3개" 중 관계 305개는 맞다(`votes >= 2` 기준). 질문은 271개고, **공유 트리는 3개가 아니라 1개다.** 그리고 `tree_vote`가 1행이라는 사실이 §4의 결론을 거의 혼자 결정한다.

덧붙여 `QUOTA_ANON_DAILY`가 운영에서 **9999**로 설정돼 있다. 익명 하루 한도는 지금 사실상 꺼져 있다. `QUOTA_LOGIN_DAILY=50`도 설정돼 있지만 **코드에서 아무도 읽지 않는다** — `src/lib/quota/key.ts`에는 `anonDailyLimit()`만 있다.

## 1. 인증 수단

### 후보 비교

**Auth.js (NextAuth) v5** — 현재 `next-auth@beta`는 `5.0.0-beta.32`다. `latest` 태그는 아직 4.24.15이므로 정식은 아니다.

여기서 흔히 도는 "Next.js 16에서 peer dependency 에러가 난다"는 말은 **지금 버전에는 해당하지 않는다.** `npm view next-auth@beta peerDependencies` 실측:

```
next:  ^14.0.0-0 || ^15.0.0 || ^16.0.0
react: ^18.2.0  || ^19.0.0
```

Next 16과 React 19가 둘 다 선언돼 있다. `--legacy-peer-deps`가 필요 없다.

DB 어댑터는 `@auth/pg-adapter@1.11.3`이고 peerDependency가 `pg: ^8` 하나다. 이 저장소는 이미 `pg@^8.22.0`을 쓴다(`package.json:41`). Drizzle도 Prisma도 필요 없다. 어댑터가 실제로 던지는 SQL을 뜯어보면 테이블은 `users`·`accounts`·`sessions`·`verification_token` 넷이고 컬럼은 `"userId"`·`"providerAccountId"`·`"sessionToken"`·`"emailVerified"` 같은 따옴표 친 camelCase다.

- 무료 한도: 없다. 자체 호스팅이라 $0이다. 사용자 데이터는 Neon에 얹힌다.
- 마찰: beta다. 정식 전 breaking change를 감수한다. 어댑터가 강제하는 복수형·camelCase 테이블 이름이 이 저장소의 단수형·snake_case 관례(`qnode`, `tree_vote`, `parent_id`)와 어긋난다. 기능 문제는 아니고 보기에 거슬리는 정도다.
- 카카오: 기본 제공 provider 목록에는 없지만 임의 OAuth/OIDC provider를 설정 객체로 직접 적을 수 있다. 코드 20줄 수준이다.

출처: <https://www.npmjs.com/package/next-auth?activeTab=versions>, <https://authjs.dev/reference/pg-adapter>, <https://neon.com/docs/guides/auth-authjs>

**Supabase Auth** — **이 스택에서는 배제된다.** 관리형 Supabase는 프로젝트마다 자기 Postgres가 묶여 있고 Auth가 그 DB 위에 선다. "Auth만 쓰고 DB는 Neon에" 하는 관리형 옵션이 없다. 유일한 길은 GoTrue를 직접 self-host하는 것인데 그건 무료 플랜 이야기가 아니라 인증 서버 인프라를 통째로 떠안는 일이다. 무료 한도 자체는 넉넉하다(50,000 MAU, 프로젝트 2개, DB 500MB). 쓸 수 없어서 의미가 없을 뿐이다.

출처: <https://supabase.com/pricing>, <https://supabase.com/docs/reference/self-hosting-auth/introduction>

**Clerk** — 무료 50,000 MRU(Monthly Retained User). Vercel Marketplace 네이티브 통합이 있어 붙이는 마찰은 가장 적다. 그런데 세 가지가 걸린다.

1. **카카오를 기본 제공하지 않는다.** 공식 provider 목록 25개에 Kakao가 없다. 일본 LINE은 있는데 카카오는 없다. 커스텀 OIDC provider로 우회하는 경로를 문서가 안내하지만, **그 커스텀 provider가 무료 플랜의 "소셜 커넥션 최대 3개" 한도에 들어가는지 별도 유료인지는 공식 문서에서 확인하지 못했다.** 대시보드에서 직접 시도해봐야 안다.
2. 무료 플랜은 Clerk 브랜딩을 못 뗀다.
3. 사용자 저장소가 Clerk에 따로 생긴다. 진실의 출처가 둘이 되고 webhook으로 Neon에 id를 동기화해야 한다. **탈퇴·삭제가 두 시스템에 걸친다.** §5의 파기 의무를 지키기가 그만큼 어려워진다.

출처: <https://clerk.com/pricing>, <https://clerk.com/docs/nextjs/guides/configure/auth-strategies/social-connections/overview>

**이메일 매직링크 직접 구현** — Resend 무료는 월 3,000통·**일 100통**이고 초과하면 과금이 아니라 다음 날까지 발송이 멈춘다. 실제 수신자에게 보내려면 도메인 DNS 인증이 선행돼야 한다. AWS SES는 신규 계정 기준 1년 월 3,000통이다.

문제는 한도가 아니라 **직접 떠안는 코드**다. 토큰 테이블, 만료, 1회용 보장, 재전송 rate limit, 열람 프리페치로 인한 링크 소진, 이메일 열거 공격 방어를 전부 직접 짜고 직접 시험해야 한다. Auth.js를 쓰면 이건 provider 하나 추가로 끝난다. **직접 구현할 이유가 없다.**

출처: <https://resend.com/pricing>, <https://aws.amazon.com/ses/pricing>

### 카카오와 구글의 실제 장벽

**카카오** — 앱 등록에 사업자 등록번호가 필요 없다. 개인 개발자도 닉네임·프로필사진 수준의 로그인은 바로 쓴다. 문제는 **이메일이다.** 공식 문서상 `account_email`은 "비즈 앱, 테스트 앱"에서만 설정 가능하다. 이름·성별·연령대·생일·전화번호·CI도 같다.

다행히 비즈 앱 전환 자체는 사업자 등록이 필요 없다. **앱 소유자 본인인증 + 카카오비즈니스 통합 서비스 약관 동의** 둘이면 된다. 다만 사업자 정보가 없으면 카카오톡 채널을 연결할 수 없다는 제약이 붙는다 — 이 서비스는 채널이 필요 없으니 상관없다.

Redirect URI는 HTTP도 정식 지원한다(HTTPS 강제 아님). 최대 10개. 로그인 API는 무료이고 통합 월 쿼터 300만 건이다.

출처: <https://developers.kakao.com/docs/latest/ko/kakaologin/utilize>, <https://developers.kakao.com/docs/latest/ko/app-setting/app>, <https://developers.kakao.com/docs/latest/ko/getting-started/quota>

**구글** — `email`·`profile`·`openid`는 non-sensitive scope다. 공식 도움말이 "non-sensitive scope만 쓰면 검수 절차가 필수가 아니다"라고 명시한다. 즉 **검수 없이 Production 게시가 된다.**

대신 함정이 하나 있다. **동의 화면을 "테스트 중"으로 두면 refresh token이 동의 시점부터 정확히 7일 뒤 만료된다.** 테스트 사용자도 100명 제한이다. 배포하려면 반드시 Production으로 전환해야 하고, 그건 검수 없이 된다. 이 한 가지만 놓치지 않으면 구글이 가장 싸게 붙는다.

출처: <https://support.google.com/cloud/answer/13464321>, <https://support.google.com/cloud/answer/15549945>

**한국 사용자 선호도** — "회원가입 화면에서 어느 버튼을 누르는가"를 잰 신뢰할 만한 조사는 찾지 못했다. **자료 없음으로 둔다.** 카카오톡 이용률 98.9%(한국언론진흥재단 2024 소셜미디어 이용자 조사) 같은 지표는 있지만 이건 앱 이용률이지 로그인 수단 선택률이 아니다. 근거 없이 "카카오가 1위"라고 적지 않는다.

### 결정

**Auth.js v5 (`next-auth@5.0.0-beta.32`) + `@auth/pg-adapter` + Neon. 1단계는 구글만. 카카오는 마지막 단계에서 붙인다.**

근거는 넷이다.

1. Next 16·React 19가 peerDependency에 선언돼 있고 `pg ^8`은 이미 있다. 새로 들어오는 런타임 의존이 사실상 없다.
2. 사용자 데이터가 Neon 한 곳에 남는다. 탈퇴 처리가 트랜잭션 하나로 끝난다. Clerk를 쓰면 두 시스템에 걸친다.
3. 카카오를 커스텀 provider로 직접 적을 수 있다. Clerk는 이게 무료 플랜에서 되는지 확인이 안 된다.
4. $0이다.

**잃는 것**: beta 의존이다. 정식 전에 breaking change가 오면 따라가야 한다. 그리고 Clerk가 공짜로 주는 것 — 로그인 UI, 비밀번호 재설정, MFA, 봇 방어 — 을 안 받는다. 지금은 OAuth만 쓸 것이라 대부분 필요 없지만, 나중에 이메일·비밀번호를 원하면 그때 비용이 청구된다.

**세션은 JWT 전략으로 둔다.** DB 세션을 쓰면 요청마다 Neon을 때린다. Neon 무료는 5분 유휴 후 강제로 정지되고(끌 수 없다) compute가 월 100 CU-hours다. 세션 조회로 이걸 태울 이유가 없다. 어댑터는 로그인 시점의 사용자·계정 저장에만 쓰고, 세션은 쿠키에 든 JWT로 간다. `sessions` 테이블은 만들어 두되 비워 둔다 — 나중에 전략을 바꿀 때 마이그레이션을 다시 짜지 않아도 된다.

출처: <https://neon.com/pricing>, <https://neon.com/docs/introduction/plans>

## 2. 익명 → 계정 이행

여기가 제일 어렵다. 그리고 **이미 한 번 터진 자리와 정확히 같은 모양이다.**

### 지난번 버그의 모양

`src/lib/journey/path.ts:107-123`과 `src/components/ReadingView.tsx:85-95`에 전말이 적혀 있다. 고친 커밋은 `795db50 새 탭으로 질문을 열어도 쌓인 지도가 남게 한다`이다.

무슨 일이 있었나. 저장된 여정에 없는 질문으로 들어오면 복원 훅이 아무것도 안 하고 넘어갔다. 그런데 화면은 이미 `useState(() => startJourney(...))`로 **1개짜리 새 여정**을 들고 있었다(`ReadingView.tsx:48`). 그리고 바로 아래 저장 훅이 `journey`가 바뀔 때마다 무조건 쓴다(`ReadingView.tsx:98-100`). 그래서 그 1개짜리가 저장소를 덮었다. **판 것이 통째로 날아갔다.**

실패의 뼈대를 추상화하면 이렇다.

> 화면이 비어 있는 새 상태를 먼저 들고 있다 → 복원 경로가 아무것도 못 돌려준다 → 저장 훅이 그 빈 상태로 진짜 데이터를 덮는다.

**로그인은 이 뼈대를 그대로 재현한다.** OAuth는 외부로 나갔다 돌아오는 전체 페이지 이동이다. 돌아오면 `ReadingView`가 새로 마운트되고 `useState`가 또 1개짜리 여정을 만든다. 이때 서버 여정을 `fetch`로 가져오면 그건 **비동기**다. 저장 훅은 동기다. 순서가 뒤집히면 지난번과 똑같이 날아간다. 게다가 이번에는 그 1개짜리가 서버로도 올라간다.

### 규칙 세 개

**규칙 1. 로컬을 먼저 지우지 않는다. 병합은 오직 더하기다.**

서버 응답으로 로컬을 replace하는 코드를 만들지 않는다. API도 `PUT /api/journey`(치환)를 두지 않고 `POST /api/journey/merge`(합집합)만 둔다. 엔드포인트 이름으로 실수를 막는다.

**규칙 2. 충돌하면 로컬이 이긴다.**

정확히는 합집합을 취하되 `currentId`는 로컬 것을 우선한다. 이유는 단순하다. 로컬은 사용자가 **방금** 한 것이다. 서버는 다른 기기에서 예전에 한 것이다. 방금 판 자리를 잃는 쪽이 훨씬 아프다.

**규칙 3. 복원이 끝나기 전에는 저장하지 않는다.**

지금 `restored`는 `useRef`이고 훅 안에서 동기적으로 세워진다(`ReadingView.tsx:68,72-73`). 서버 왕복이 끼면 이 보증이 깨진다. `hydrated` 상태를 따로 두고 저장 훅 첫 줄에서 막는다.

```
useEffect(() => {
  if (!hydrated) return      // ← 이 한 줄이 지난번 버그의 재발을 막는다
  saveJourney(journey)
}, [journey, hydrated])
```

### 발자국을 무엇으로 같다고 볼 것인가

occurrence id는 클라이언트가 만든다(`path.ts:10-14`). 브라우저마다 다르다. **id로는 합칠 수 없다.**

`visit()`이 이미 답을 갖고 있다. 같은 부모 아래 같은 노드로 두 번 가면 기존 발자국을 재사용한다(`path.ts:44-49`). 뿌리도 마찬가지다(`path.ts:128-131`). 즉 **발자국의 정체성은 (부모, nodeId)다.** 이걸 뿌리까지 펴면 경로 전체가 된다.

```
pathKey(occ) = pathTo(state, occ.id).map(o => o.nodeId).join('>')
```

`pathTo`는 이미 있고 순환도 끊는다(`path.ts:71-86`). 새로 짤 것이 없다.

병합은 `pathKey` 기준 합집합이다. 같은 키가 양쪽에 있으면 **서버 id를 남긴다** — 다음 동기화가 안정된다. 자식은 양쪽 것을 다 받는다. 삽입은 얕은 것부터(위상 순서) 한다. 그래야 "부모가 자식보다 앞에 온다"는 전제가 유지된다. `graph.ts`와 `storage.ts:111`이 그 전제를 쓴다.

이 정의의 성질을 두 가지 적어 둔다. 같은 경로를 두 기기에서 걸었으면 하나로 합쳐진다 — 맞다. 다른 경로로 같은 노드에 닿았으면 따로 남는다 — 이것도 맞다. 지금 `visit()`의 의미론과 정확히 같다(`path.ts:32-34`: "부모가 다르면 반드시 새 발자국이다").

### 상한 처리

`MAX_OCCURRENCES`는 400이다(`storage.ts:15`). 병합 결과가 넘을 수 있다.

**`pruneJourney`는 localStorage에 쓸 때만 건다. 서버에는 걸지 않는다.** 이유는 `storage.ts:8-13`이 이미 적었다 — 상한은 용량 때문이 아니라 브라우저 저장 실패 때문이다. 서버에는 그 제약이 없다. 서버가 전체를 들고 로컬이 최근 창만 보는 구조가 맞다.

여기서 트레이드오프가 하나 생긴다. **로컬에서 잘린 발자국이 다음 병합 때 서버에서 돌아온다.** 400개를 넘긴 사용자는 로컬이 계속 400 근처에서 출렁인다. 지금 사용자 규모(`expansion_event` 29건)에서는 이론적 이야기다. 넘어가되 알고 넘어간다.

### 흐름

```
로그인 성공 (OAuth 콜백 → 페이지 재마운트)
  │
  ├─ 로컬 여정 읽기          loadJourney()      동기, 즉시
  ├─ 서버 여정 읽기          GET  /api/journey  비동기
  │
  ├─ 둘 다 도착할 때까지 저장 훅 정지          ← 규칙 3
  │
  ├─ merge(local, server)   pathKey 합집합, currentId는 로컬 우선
  │
  ├─ POST /api/journey/merge  (더하기만, 치환 없음)     ← 규칙 1
  ├─ setJourney(merged) → hydrated = true
  └─ 저장 훅 재개
```

로그아웃하면 로컬은 그대로 둔다. 지우면 익명으로 돌아온 사용자가 자기 지도를 잃는다.

### 무엇을 시험해야 하는가

기존 `tests/journey/persistence.test.ts`와 `tests/components/ReadingView.journey.test.tsx` 옆에 붙인다.

- 서버가 비었을 때 로컬이 살아남는가 (**지난번 버그의 직계**)
- 로컬이 비었을 때 서버가 내려오는가
- 양쪽에 겹치는 경로가 있을 때 중복이 안 생기는가
- 서버 fetch가 실패해도 로컬이 안 지워지는가
- 서버 fetch가 저장 훅보다 늦게 도착해도 안 덮이는가 (**타이밍 재현**)
- 병합 결과가 항상 이어진 숲인가 (고아 없음)

마지막 두 개가 핵심이다. 나머지는 이것들이 통과하면 대개 따라온다.

## 3. 스키마 변화

### 이미 준비된 자리부터 쓴다

이 저장소는 인증을 예상하고 자리를 비워 뒀다. 새로 만들기 전에 그것부터 채운다.

| 자리 | 위치 | 현재 |
|---|---|---|
| `expansion_event.user_id uuid` | `0002_ops.sql:32` | 컬럼은 있고 앱이 **한 번도 안 채운다** |
| `tree.author_id uuid` | `0006_tree.sql:18` | "인증이 붙기 전까지 항상 null이다" |
| `tree_vote.voter_key text` | `0007_vote.sql:14` | `anon:<uuid>` |

특히 `0007_vote.sql:10-11`은 이행 방법까지 적어 뒀다.

> 인증이 붙으면 voter_key를 검증된 UID로 바꾼다. 그때 쿠키 키는 그대로 두고 새 키로만 쌓으면 과거 표를 잃지 않는다.

**이 지침을 그대로 따른다.** `anon:<uuid>` 행을 건드리지 않고 `user:<uid>`로 새로 쌓는다. 잃는 것은 명확하다 — 로그인 전에 누른 표는 로그인 후에 "안 누른 것"으로 보인다. `tree_vote`가 지금 1행이라 실제 피해는 0이다. 표를 옮기려면 (트리, 익명키, 사용자) 매핑을 따로 들고 있어야 하는데 그 복잡도를 1행 때문에 지불하지 않는다.

`src/lib/quota/key.ts:10-11`도 같은 예고를 적어 뒀다: "인증이 붙으면 검증된 세션 UID를 우선한다. 요청 body의 사용자 식별자는 절대 신뢰하지 않는다."

여기서 기존 결함을 하나 짚는다. **할당량 키는 IP인데(`key.ts:16-18`, `anon:<ip>`) 투표 키는 쿠키다(`vote/identity.ts:18`).** 그런데 `vote/identity.ts:8-10`은 IP를 안 쓰는 이유를 이렇게 적었다 — "국내 모바일 캐리어는 NAT가 심해서 수백 명이 같은 출구 IP를 쓴다." 그 논리는 할당량에도 그대로 적용된다. 실제로 운영 `usage_quota`에 `anon:183.100.168.180` 같은 키가 그대로 쌓여 있다. 지금은 `QUOTA_ANON_DAILY=9999`라 아무도 안 막히지만, 한도를 정상값으로 되돌리는 순간 NAT 뒤의 여러 사람이 한 사람 몫을 나눠 쓰게 된다.

**이건 이번 작업의 범위가 아니다.** 다만 로그인 사용자는 `user:<uid>`로 키를 잡으므로 그 사람들만 문제에서 벗어난다. 익명 IP 키 문제는 별도 과제로 남긴다.

### 새 마이그레이션

번호는 `0010`부터다. `0004` 결번은 그대로 둔다 — 러너가 파일명 정렬로만 돌기 때문에 채워 넣을 이유가 없고, 지금 와서 채우면 `schema_migrations`에 이미 기록된 순서와 어긋난다.

**`0010_auth.sql`** — Auth.js 어댑터가 요구하는 네 테이블. 이름과 컬럼은 어댑터가 던지는 SQL에 맞춰야 한다(`@auth/pg-adapter@1.11.3/index.js` 실측): `users`, `accounts`, `sessions`, `verification_token`. 컬럼은 `"userId"`·`"providerAccountId"`·`"sessionToken"`·`"emailVerified"`처럼 따옴표 친 camelCase다. 이 저장소의 snake_case 관례와 어긋나지만 어댑터가 강제한다. 손대면 깨진다.

`sessions`는 만들되 JWT 전략이라 비어 있다(§1).

**`0011_journey.sql`** — `journey_occurrence`. 이름은 `src/lib/journey/types.ts:4`가 이미 부르고 있는 것이다.

`tree_occurrence`(`0006_tree.sql:39-45`)와 같은 모양으로 만든다. 그 테이블의 설계 이유가 여기에도 그대로 적용되기 때문이다 — `0006_tree.sql:34-38`이 적었듯 노드 id 배열로 두면 스냅샷이 아니다. 나중에 두 노드 사이에 `qedge`가 생기면 과거 여정의 모양이 저절로 바뀐다. **부모를 명시적으로 들고 있어야 그때 그 경로가 남는다.** `journey/types.ts:7-9`도 같은 말을 한다.

담을 것: `user_id`, `qnode_id`, `parent_occurrence_id`(자기참조), `position`, `created_at`. 그리고 `path_key text`를 **생성된 값이 아니라 저장된 값으로** 둔다. 병합할 때마다 재귀로 계산하면 비싸고, 부모가 안 바뀌므로 삽입 시점에 고정해도 안전하다. `unique (user_id, path_key)`가 §2의 병합 규칙을 DB 차원에서 보증한다. 응답만 유실돼도 재시도가 중복을 넣을 수 있으니 `on conflict do nothing`으로 받는다 — `0006_tree.sql:24-26`의 `tree_daily_one_per_day`와 같은 발상이다.

`current_occurrence_id`는 여기 두지 않는다. 사용자당 하나뿐이므로 별도 작은 테이블이나 `users` 확장이 맞다.

**`0012_progress.sql`** — 열람 기록과 북마크.

- `node_view(user_id, qnode_id, first_seen_at, last_seen_at, view_count)` — PK `(user_id, qnode_id)`. 복습 추천의 유일한 재료다. 지금 서버에 이런 것이 **전혀 없다.**
- `bookmark(user_id, qnode_id, created_at)` — PK `(user_id, qnode_id)`.
- 복습 상태는 **이 단계에서 만들지 않는다.** §4에서 다룬다.

**`0013_identity.sql`** — 인덱스와 연결.

- `expansion_event(user_id)` 인덱스. 지금 이 컬럼은 항상 null이라 인덱스도 없다.
- `tree(author_id)` 인덱스. `0008_tree_root_index.sql`이 `root_node_id`에 대해 짚은 것과 같은 이유다 — 인덱스 없는 참조 열은 부모를 지울 때 자식 테이블을 통째로 훑는다. 탈퇴에서 사용자를 지우는 자리가 실제로 생긴다.

여기서 `author_id`·`user_id`에 `references users(id)`를 **걸지 않는다.** 걸면 `0010`이 `0002`·`0006`보다 뒤인데 앞 테이블이 뒤 테이블을 참조하게 되고, 무엇보다 탈퇴 시 `on delete cascade`가 공유 트리를 같이 지운다. §5에서 그러면 안 된다고 정한다. 애플리케이션에서 관리한다.

### 익명 사용자를 계속 지원할 것인가

**한다. 가입은 순수하게 더하기다.**

근거 셋.

1. `README.md:7`이 "가입 없이 바로 쓰면 돼요"라고, `README.md:87`이 "추천은 로그인 없이 눌러요"라고 약속했다. 이걸 깨는 것은 기능 추가가 아니라 기능 회귀다.
2. 지금 전체 확장 시도가 **29건이다.** 깔때기 맨 위가 이만한데 그 앞에 가입 벽을 세우면 남는 것이 없다.
3. 계정이 주는 값 — 기기 간 동기화, 복습 — 은 **판 적이 있는 사람에게만** 의미가 있다. 판 적 없는 사람에게 먼저 가입을 물으면 값을 설명할 재료조차 없다. 가입 유도는 지도에 발자국이 어느 정도 쌓인 뒤에 띄우는 것이 맞다.

잃는 것: 코드 경로가 둘로 갈린다. 익명 경로와 로그인 경로를 둘 다 유지해야 하고 시험도 둘씩 필요하다. 그래도 값이 크다.

## 4. "추천"이 무엇인가

세 가지가 섞여 있다. 필요한 재료가 전혀 다르다.

### (a) 다음에 팔 질문 추천

**지금 된다. 계정도 필요 없다.**

재료는 `semantic_relation`이다. 운영에 330행이 있고 `votes >= 2`인 것이 305행이다. 종류는 `shares_concept` 283, `prerequisite` 22, `instance_of` 22, `alternative` 3이다. `source`는 전부 `llm`이다.

`0009_semantic_relation.sql:10-14`가 이 관계의 성질을 이미 정리했다 — 동일성과 달리 관계는 틀려도 선 하나가 잘못 그려질 뿐이고 `active`를 내리면 끝난다. **precision 100%를 요구하지 않는다.** 추천에 쓰기 좋은 성질이다. 판정 흔들림에 대한 방어도 이미 있다. `judge.ts:159`가 기본 3회 뽑아 `judge.ts:212`에서 과반만 채택하고(`need = floor(done/2)+1`), `src/lib/db/graph.ts:108`이 표시 시점에 `votes >= 2`로 한 번 더 거른다.

**한계가 하나 있고 이게 크다.** 관계는 배치 노드 258개에만 걸려 있다. `scripts/build-relations.ts:50`이 `EXAMPLE_NODES`(30) + `GENERATED_NODES`(219)만 대상으로 삼았기 때문이다. 사용자가 실제로 판 `on_demand` 노드 13개에는 관계선이 하나도 없다. **깊이 1까지는 추천이 나오고 그 아래로는 끊긴다.**

그리고 `qnode_suggestion` 1355개 중 `target_node_id`가 연결된 것이 **8개뿐이다.** 나머지 1347개는 누르면 그때 새 노드를 만든다. `docs/analysis/2026-08-06-knowledge-graph.md`가 이걸 "잠재적 간선 1245개가 전부 끊겨 있다"고 적었다.

즉 (a)는 **오늘 붙일 수 있지만 그물이 얕다.** 개인화 이전에 `on_demand` 노드까지 관계 판정을 돌리는 것이 먼저다. 그건 인증과 무관한 별도 작업이다.

### (b) 복습 시점 추천

**재료가 0이다. 계정이 생겨야 비로소 만들어진다.**

서버에 열람 이력이 아예 없다. `expansion_event`는 29건 있지만 `user_id`가 전부 null이다. 애초에 `recordEvent`의 insert 컬럼 목록에 그 이름이 없다(`src/lib/expand/nodes.ts:186-190`). 그리고 이건 "판 것"이지 "본 것"도 아니다. **읽기는 기록조차 되지 않는다.**

`§3`의 `node_view`가 생기는 순간부터 데이터가 쌓인다. 그리고 이게 **계정의 가장 정직한 명분이다.** "기기를 옮겨도 지도가 남는다"는 이미 있는 것을 옮기는 값이고, "언제 다시 봐야 하는지 알려준다"는 계정이 없으면 원리적으로 불가능한 값이다.

다만 **1차에서 SM-2나 간격 반복 알고리즘을 넣지 않는다.** 그런 알고리즘은 사용자가 "기억났다/안 났다"를 답해줘야 도는데 그 UI가 없고, 답할 사람도 아직 없다. 처음에는 `last_seen_at` 기준 단순 정렬로 충분하다 — "3일 전에 본 것", "일주일 넘은 것". 데이터가 쌓인 뒤에 알고리즘을 얹는다.

### (c) 남의 트리 추천 (협업 필터링)

**불가능하다. 접는다.**

`tree_vote`가 **1행이고 투표자가 1명이다.** 공유 트리는 1개다. 협업 필터링은 사용자 수백 명 × 아이템 수십 개의 겹침이 있어야 신호가 나온다. 지금은 행렬이 1×1이다.

그리고 이건 계정을 붙인다고 풀리는 문제가 아니다. **트래픽이 붙어야 풀린다.** 낙관적으로 봐도 1년 뒤에 될지 알 수 없다.

대안은 이미 있다. 비개인화 인기순 정렬이 `0006_tree.sql:31`의 `tree_board_popular_idx`로 붙어 있고 화면도 있다. 그걸로 충분하다. **협업 필터링은 로드맵에서 뺀다.** 지금 설계에 자리를 만들어 두는 것조차 하지 않는다 — 쓰지 않을 테이블이 남으면 나중에 읽는 사람이 이게 왜 비어 있는지 묻게 된다.

### 정리

| 추천 | 지금 되는가 | 필요한 것 |
|---|---|---|
| (a) 다음 질문 | **된다** (얕게) | `on_demand` 노드까지 관계 판정 확대 — 인증과 무관 |
| (b) 복습 시점 | 안 된다 | 계정 + `node_view`. **계정의 핵심 명분** |
| (c) 남의 트리 | 안 된다 | 트래픽. 계정으로 안 풀린다. **접는다** |

## 5. 개인정보

계정을 만드는 순간 개인정보처리자가 된다. 사업자 등록 여부와 무관하다. 개인정보 보호법 제2조는 "업무를 목적으로" 개인정보파일을 운용하는 개인도 포함한다.

### 저장할 것과 안 할 것

**저장한다** — provider와 provider의 사용자 식별자(`sub`), 이메일, 표시 이름, 가입 시각.

**저장하지 않는다** — 비밀번호(OAuth만 쓴다), 프로필 이미지, 생년월일, 성별, 연령대, 전화번호, CI. 카카오 동의항목에서 전부 뺀다.

프로필 이미지를 빼는 이유는 두 가지다. 화면에서 쓸 자리가 없고, provider가 주는 URL은 만료되므로 저장해봐야 깨진 이미지가 남는다.

**이메일을 1단계에서 받을 것인가.** 카카오는 이메일을 받으려면 비즈 앱 전환이 필요하다. 그런데 **식별에는 이메일이 필요 없다.** provider + `sub`로 충분하다. 이메일은 계정 복구와 연락 용도다.

그래서 이렇게 가른다. 구글은 어차피 `email` scope가 non-sensitive라 그냥 받는다. **카카오는 이메일 없이 붙인다.** 비즈 앱 전환을 나중으로 미룰 수 있고, 안 받는 개인정보는 지킬 필요도 없다.

### 탈퇴

즉시 하드 삭제를 원칙으로 한다. 유예 기간을 두면 그 기간 동안의 보관 근거를 따로 설명해야 한다.

다만 **공유 트리는 지우지 않는다.** `tree.author_id`를 null로 끊고 콘텐츠는 남긴다. 이유 둘. 공유 트리는 URL로 남에게 퍼진 공개 지식이고, 한 명이 탈퇴했다고 남의 화면에서 사라지면 안 된다. 그리고 트리 내용 자체는 CS 지식이지 개인정보가 아니다.

**이걸 가입 시점에 명시한다.** 나중에 알게 되면 분쟁이 된다.

탈퇴 시 처리를 표로 고정한다.

| 대상 | 처리 |
|---|---|
| `users`·`accounts`·`sessions` | 즉시 삭제 |
| `journey_occurrence` | 즉시 삭제 (전적으로 개인 데이터) |
| `node_view`·`bookmark` | 즉시 삭제 |
| `tree.author_id` | null로 끊기. 트리 본문 보존 |
| `tree_vote` (`user:<uid>`) | 행 삭제. `tree.upvotes` 카운터 동기 차감 |
| `expansion_event.user_id` | null로 끊기 |

마지막 줄에 새 위험이 하나 있다. `expansion_event.raw_input`은 **사용자가 친 원문**이고, `0002_ops.sql:28-29`가 이미 경고했다 — "사용자 원문은 전역 공개 테이블에서 격리한다. 이름·내부 URL·토큰이 섞여 들어올 수 있다." 지금은 `user_id`가 null이라 누가 썼는지 모른다. **`user_id`를 채우는 순간 "누가 무엇을 물었는지"가 연결된다.** 이건 계정이 새로 만드는 리스크다.

그래서 두 겹으로 막는다. 탈퇴 시 `user_id`를 끊고, 그와 별개로 `raw_input`에 **90일 보존 후 파기**를 건다. 원문이 필요한 이유는 판정 품질 디버깅이고 그건 오래된 데이터에 필요 없다. 파기는 Vercel cron으로 돌린다 — Hobby는 하루 1회 초과 실행을 배포 단계에서 거부하므로 일 1회로 잡는다.

### 최소 법적 요건

| 의무 | 근거 | 할 일 |
|---|---|---|
| 개인정보처리방침 수립·공개 | 제30조 | **정적 페이지 하나 만들어 푸터에 건다.** 규모 예외 없음 |
| 파기 | 제21조 | 위 표대로. `raw_input` 90일 |
| 만 14세 미만 | 제22조의2 | 법정대리인 동의를 받을 수단이 없다 → **가입 시 만 14세 이상 확인 체크로 처리** |
| 보호책임자 | 제31조 | 소상공인은 대표자가 자동. 방침에 연락처 기재 |

처리방침은 개인정보보호위원회 자동생성 도구로 초안을 뽑는다: <https://www.privacy.go.kr/front/per/inf/perInfStep01.do>

**1단계 배포 전에 처리방침 페이지가 떠 있어야 한다.** 로그인 버튼이 먼저 나가면 그 시점부터 위반이다.

한 가지 더. Vercel Hobby 플랜은 약관상 비상업적·개인 용도로 제한된다(<https://vercel.com/docs/plans/hobby>). 지금은 문제없다. 나중에 이 서비스로 수익을 내면 플랜부터 올려야 한다.

## 6. 쪼개기

각 단계는 독립적으로 배포 가능하다. 앞 단계가 배포된 채로 멈춰도 서비스가 성립해야 한다.

**모든 단계에서 마이그레이션이 코드보다 먼저다.** `npm run db:migrate`를 돌리고 통과를 확인한 뒤 배포한다(§0).

### 1단계 — 로그인만 붙인다

넣는 것: `next-auth@beta`, `@auth/pg-adapter`, 마이그레이션 `0010_auth.sql`, `/api/auth/[...nextauth]`, 헤더의 로그인·로그아웃 버튼, **개인정보처리방침 페이지**. provider는 구글만.

**로그인해도 달라지는 것이 없다.** 이름이 헤더에 뜨는 것이 전부다.

이게 독립 배포 가능한 이유: 기존 코드를 하나도 읽지 않고 하나도 쓰지 않는다. 회귀 위험이 사실상 0이다.

확인할 것: 구글 OAuth 동의 화면을 **Production으로 게시**했는가. Testing으로 두면 refresh token이 7일에 끊긴다(§1).

값: 인증 인프라가 실제로 도는지, Neon 무료 compute가 견디는지 본다.

### 2단계 — 여정을 서버에 올린다

넣는 것: 마이그레이션 `0011_journey.sql`, `GET /api/journey`, `POST /api/journey/merge`, `ReadingView`의 `hydrated` 게이트와 병합 로직.

**여기가 위험 구간이다.** §2의 버그가 재발한다면 여기다. 그래서 1단계와 분리했다 — 인증이 흔들리는 것과 여정이 날아가는 것을 동시에 디버깅하지 않는다.

통과 조건: §2 마지막의 시험 여섯 개. 특히 "서버 fetch가 저장 훅보다 늦게 도착해도 안 덮이는가".

이 단계까지만 배포해도 값이 선다 — 기기를 옮겨도 지도가 남는다.

### 3단계 — 나의 공부기록

넣는 것: `/me` 화면, 마이그레이션 `0012_progress.sql`의 `node_view`, 읽기 시점 기록.

2단계가 쌓은 데이터를 읽어서 보여준다. 그리고 **여기서 처음으로 "본 시각"이 쌓이기 시작한다.** 4단계의 재료가 여기서 만들어진다.

`node_view`는 요청마다 upsert가 들어가므로 Neon compute를 처음으로 눈에 띄게 쓴다. 100 CU-hours를 확인한다.

### 4단계 — 복습 추천과 북마크

넣는 것: `bookmark` 테이블, `/me`의 복습 목록.

3단계가 데이터를 쌓은 **뒤에야** 의미가 있다. 최소 2~3주는 지나야 목록이 비어 있지 않다. 순서를 바꾸면 빈 화면을 배포하게 된다.

알고리즘은 `last_seen_at` 정렬로 시작한다. 간격 반복은 넣지 않는다(§4).

### 5단계 — 카카오 로그인

마지막인 이유는 리드타임 때문이다. 비즈 앱 전환에 본인인증과 약관 동의가 필요하고 승인이 언제 떨어지는지 예측할 수 없다. 구글로 전체 흐름을 검증한 뒤에 provider 하나를 더하는 것이 안전하다.

이메일은 안 받는다(§5). 그러면 비즈 앱 전환 자체가 필요 없을 수 있다 — 닉네임만 받는 구성이면 일반 앱으로 되는지 먼저 확인한다.

### 이 순서에서 빠진 것

**"나만의 트리 관리"는 어디에도 없다.** 의도한 것이다.

지금 `tree`는 발행된 콘텐츠다(daily 9 + shared 1). 개인 트리를 만들려면 "저장은 됐지만 공개는 안 된 트리"라는 새 상태가 필요하고, 그건 `tree.kind` enum 확장과 게시판 쿼리 전면 재검토를 부른다.

그런데 **2단계의 `journey_occurrence`가 이미 "나만의 트리"다.** 사용자가 판 경로 전체가 부모 링크째로 서버에 남는다. `/me`에서 그걸 보여주면 별도 테이블 없이 요구가 충족된다. 이름이 다를 뿐이다.

정말로 "고르고 편집해서 이름 붙이는 나만의 트리"가 필요하다면 6단계로 붙인다. 그때는 이미 `journey_occurrence`가 있으니 거기서 부분집합을 떠 `tree`로 승격하는 형태가 된다. **지금 미리 만들지 않는다.**

## 결론

**Auth.js v5 + `@auth/pg-adapter` + Neon. JWT 세션. 구글 먼저, 카카오는 마지막. 익명은 그대로 둔다.**

Supabase Auth는 Neon과 구조적으로 못 붙는다. Clerk는 카카오를 기본 제공하지 않고 사용자 저장소가 둘로 갈려 탈퇴 처리가 어려워진다. 매직링크 직접 구현은 Auth.js가 공짜로 주는 것을 다시 짜는 일이다.

**가장 위험한 것은 인증이 아니라 병합이다.** 로그인은 `path.ts:107-123`이 기록한 버그와 정확히 같은 모양의 경주를 만든다 — 화면이 빈 상태를 먼저 들고, 비동기 복원이 늦게 오고, 동기 저장이 먼저 쓴다. 그래서 규칙을 셋으로 못박았다. 로컬을 먼저 지우지 않는다. 충돌하면 로컬이 이긴다. 복원 전에는 저장하지 않는다.

**계정의 진짜 명분은 복습이다.** 기기 간 동기화는 있는 것을 옮기는 값이지만, 복습 시점은 계정 없이는 원리적으로 못 만든다. 반대로 협업 필터링은 계정으로 안 풀린다 — `tree_vote`가 1행이다. 접는다.

**잃는 것을 다시 적는다.** beta 의존을 진다. 코드 경로가 익명·로그인 둘로 갈린다. 로그인 전 익명 투표는 로그인 후 사라진다. 400개를 넘긴 여정은 로컬에서 출렁인다. 개인정보처리자가 되어 처리방침·파기 의무를 진다. `expansion_event.raw_input`에 사용자가 연결되는 새 리스크가 생긴다.

마지막 하나. **이 문서는 익명 할당량이 IP 기반이라 국내 NAT 뒤에서 공유된다는 기존 결함을 고치지 않는다.** 로그인 사용자만 그 문제에서 벗어난다. 별도 과제로 남긴다.
