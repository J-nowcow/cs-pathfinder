# CS 지식을 하나의 그래프로 엮기 — 문제 분석

작성 2026-08-06 · 상태: 분석, 결정 전

## 무엇을 하려는 것인가

이 서비스의 목표는 **전체 CS 지식을 하나의 그래프로 구조화**하는 것이다. 꼬리질문은 새 질문을 무한히 만드는 장치가 아니라 지식과 지식을 잇는 선이다. 트리는 그 그래프를 사람이 공부할 수 있게 보여주는 방식일 뿐이고, 반드시 트리일 필요도 없다.

지금은 그 반대로 돌고 있다.

## 실측

### 그래프가 사실상 비어 있다

운영 DB(`npm run check:graph`, 2026-08-06):

| 지표 | 값 |
|---|---|
| ready 노드 | 51 |
| 간선 | 9 |
| 고립 노드 | 38 (75%) |
| 연결 요소 | 42개 |
| 가장 큰 덩어리 | 12% |
| 차수 중앙값 | 0 |

레포에 있는 249개(예시 30 + 생성 219)는 **간선이 하나도 없다.** 시드로 심을 때 `qnode`와 `qnode_suggestion`만 넣고 `qedge`는 안 만든다.

### 꼬리질문은 1245개가 떠 있다

249개 × 5개 = 1245개의 꼬리질문이 있는데, 전부 `target_node_id = null`이다. 누르면 그때 새 노드를 만든다. 즉 **잠재적 간선 1245개가 전부 끊겨 있다.**

### 낱말 비교로는 못 잇는다

꼬리질문 1245개를 기존 질문 249개와 낱말 자카드 유사도로 맞춰봤다.

| | |
|---|---|
| 0.4 이상 겹침 | 61개 (5%) |
| 그중 다른 카테고리 | 38개 |

**5%도 문제지만 매칭 내용이 더 문제다.** 실제로 잡힌 것들:

```
"샤딩 키는 무엇을 기준으로 고르는가?"     ≈  "배포 방식은 무엇을 기준으로 고르는가?"
"파티션 키는 무엇을 기준으로 정하는가?"   ≈  "호출 시간 제한은 무엇을 기준으로 정하는가?"
"HSTS는 무엇을 막는가?"                  ≈  "CORS는 무엇을 막는가?"
```

주제가 아니라 **문장 틀**이 잡혔다. 우리가 질문 형식을 `~는 무엇을 기준으로 고르는가?`로 통일한 것이 원인이다. 형식을 통일한 것은 읽기에는 좋지만 텍스트 유사도를 무의미하게 만든다.

## 왜 안 이어지나 — 근본 원인

`collectCandidates(parentNodeId)`는 후보를 이렇게 모은다.

```sql
siblings : 같은 부모의 다른 자식
uncles   : 조부모의 다른 자식
```

**후보 집합이 그래프 이웃에서 나온다.** 그런데 그래프가 비어 있으면 이웃이 없고, 이웃이 없으면 후보가 0이고, 후보가 0이면 게이트가 매칭할 대상이 없어서 항상 새 노드를 만든다. 새 노드를 만들면 간선은 부모-자식 하나만 생긴다.

즉 **후보 발견이 구조적(structural)인데 필요한 것은 의미적(semantic)이다.** 빈 그래프에서 시작하면 영원히 사슬만 자라고 그물이 안 된다.

이것이 고립률 75%의 원인이다. 사람이 판 9개의 간선은 전부 부모→자식 사슬이다.

## 무엇을 고를 수 있나

### A. 생성 시점에 잇는다

꼬리질문을 만들 때 **기존 질문 목록을 후보로 주고** "이미 답하는 것이 있으면 그것을 가리켜라"고 시킨다.

- 장점: 새로 만들어지는 것부터 그물이 된다. 지금 게이트 구조(선택, 생성 아님)를 그대로 쓴다
- 단점: 이미 만든 1245개는 안 고쳐진다. 후보를 249개 다 주면 프롬프트가 커진다
- 위험: 잘못 이으면 되돌릴 수 없다 (기존 원칙)

### B. 사후에 잇는다

이미 있는 1245개 꼬리질문을 기존 질문과 대조해 `target_node_id`를 채우고 `qedge`를 만든다.

- 장점: 지금 있는 것이 즉시 그물이 된다. 한 번 돌리면 끝
- 단점: 1245번 판정이 필요하다. 낱말 비교만으로는 위에서 봤듯 틀린다
- 위험: 대량 오연결. 한 번에 1245개를 잘못 이으면 손으로 못 되돌린다

### C. 개념 계층을 먼저 세운다

질문 위에 **개념 노드**(TCP, 인덱스, GC …)를 두고 질문을 개념에 매단다. 질문끼리 직접 잇지 않고 개념을 통해 이어진다.

- 장점: 카테고리 간 연결이 자연스럽다(네트워크의 TCP와 모바일의 네트워크 재시도가 같은 개념에 붙는다). 오연결 위험이 낮다 — 개념 매핑이 질문 매핑보다 쉽다
- 단점: 스키마와 화면이 모두 바뀐다. 가장 크다
- 위험: 개념 목록을 누가 정하나. 잘못 나누면 전부 다시

### D. 후보 발견만 의미 기반으로 바꾼다

`collectCandidates`가 그래프 이웃 대신 **같은 카테고리 + 인접 카테고리의 질문**을 후보로 준다. 나머지(게이트가 고르는 방식)는 그대로.

- 장점: 변경이 가장 작다. 빈 그래프에서도 후보가 나온다. A와 B 양쪽의 전제 조건이기도 하다
- 단점: 이것만으로는 이미 있는 1245개가 안 이어진다
- 위험: 후보가 늘면 게이트의 오선택 확률이 올라간다 (precision 100% 원칙과 충돌)

## 결정해야 할 것

1. **A·B·C·D 중 무엇을, 어떤 순서로**
2. **오연결을 어디까지 허용하나.** 기존 원칙은 "잘못 합친 것은 복구 불가"라 precision 100%였다. 그물을 만들려면 이 기준을 유지할 수 있나
3. **카테고리 간 인접 관계를 누가 정하나.** 손으로 적을 것인가, 데이터에서 뽑을 것인가
4. **꼬리질문을 미리 노드로 만들 것인가.** 만들면 그물이 즉시 생기지만 "사람이 판 경로가 지도"라는 전제가 흔들린다

## 재보지 않은 것

- 게이트에 후보를 20개·50개 줬을 때 정확도가 어떻게 변하는지 (기존 측정은 3·10·25·50개에서 했으나 같은 카테고리 후보가 아니었다)
- 개념 노드를 도입했을 때 질문→개념 매핑의 정확도
- 사람이 실제로 파는 비율. 지금 조회 대비 확장 비율이 얼마인지

### 내 원인 진단이 절반만 맞았다

249개가 고립된 **직접 원인은 시딩이 간선을 아예 안 만드는 것**이다. `bootstrap.ts`에 `qedge` 언급이 0회다. 시딩 중 `collectCandidates`는 실행조차 안 된다.

`51노드 - 9간선 = 42컴포넌트`는 정확히 forest다. **"아무도 안 파봤다"**는 더 단순한 설명과 완전히 양립한다. 확장률을 안 재본 채로 구조 결함이라 단정한 것이 성급했다.

`check:graph`는 모든 `ready` 노드를 세지만 지도는 `origin='batch'`만 보여준다. **모집단이 다르다.**

### 전략 1은 지식 그래프를 만들지 않는다

Advocate A가 스스로 철회했다.

> 게이트는 "표현이 달라도 답이 같아질 질문"을 찾는 **동일 질문 판정 장치**다. `qedge`는 방향성 있는 탐색 경로, `qnode_equivalence`는 동일성 기록이다. **셋 중 어느 것도 "TCP 재전송"과 "모바일 재시도"처럼 다르지만 관련된 개념을 잇는 관계 타입이 아니다.** 라운드 1의 "그물 형성"은 과장이었다.

D가 A·B의 전제 조건이라는 주장도 틀렸다. `generateNodeContent`에는 `candidates` 파라미터가 **아예 없다.**

### 전략 2의 단일 부모 계층도 틀렸다

Advocate B가 스스로 철회했다. 다중 개념 질문을 못 담는다. 별도 `concept` 테이블과 다대다 `question_concept`가 맞다.

오매칭 논거("같은 카테고리 후보를 줘도 문장 틀로 잘못 고른다")도 철회했다. **낱말 유사도를 전제했을 때만 성립한다.**

### precision 100%는 증거가 아니다

184회 매칭 출력에서 오매칭이 없었다는 뜻이고 **고유 케이스는 51개**다. 반복 실행은 독립 표본이 아니다. 게이트는 유효한 후보 id가 오면 confidence 없이 즉시 승인한다.

"오병합은 복구 불가"도 물리적으로는 틀렸다. 행 삭제와 target 초기화는 된다. `qnode_equivalence.active`도 있다. **다만 매칭 경로가 그것을 안 쓴다.** 물리적 복구가 아니라 **안전한 운영 롤백**이 불가능한 상태다.

>

## 결정

### 순서

1. **데이터 정제** — 카테고리 30% 오분류, `identity_scope` 21%(53/249)가 스키마 밖. 이대로는 어떤 매칭도 못 믿는다
2. **관계 타입 분리** — 전이 / 동일성 / 의미를 각각 다른 곳에 저장. `qedge`에 최소한 `source`·`suggestion_id`·`active`를 붙인다
3. **좁혀진 후보 검색** — 동일 질문 판정 전용. 꼬리질문 + 부모 문맥으로 전역 top-k, 카테고리는 약한 prior로만
4. **1245개는 shadow backfill** — 실제 DB를 안 바꾸고 후보만 만든다. 확정은 클릭이나 검수 때
5. **개념 계층은 그다음** — "왜 이어지는가"와 계층 깊이가 필요한 지점에만

### 카테고리는 다중으로

질문의 **49%가 둘 이상에 걸친다.** 13개 카테고리 쌍이 다리가 된다. `qnode_category` 다대다 하나로 개념 테이블 없이 카테고리 간 연결이 생긴다.

다만 카테고리는 **게시판 탭**이고 순서가 UI 사정으로 정해져 있다(`categories.ts` 주석: "모바일에서 가로 스크롤로 밀리는 뒤쪽일수록 덜 눌리는 자리"). 여기에 의미 구조를 얹으면 탭 개편이 의미를 흔든다. 그래서 개념 계층이 나중에 필요해진다.

### 안 하기로 한 것

- **1245개 즉시 hard-link.** `linkSuggestion`은 "먼저 닿은 노드가 임자"라 첫 판정을 되돌릴 경로가 없다
- **꼬리질문 사전 `qedge` 생성.** 생성된 가능성을 사람이 걸은 경로로 위장한다. 249개짜리 별 모양 컴포넌트만 생기고 루트끼리는 여전히 안 이어진다
- **낱말 유사도 기반 매칭.** 질문 형식을 통일해놔서 주제가 아니라 문장 틀이 잡힌다

## 아직 안 잰 것 — 가장 위험한 가정

> **꼬리질문 1245개 중 실제로 기존 249개 안에 답이 있는 비율.**

이 비율이 낮으면 어느 전략도 그물을 못 만든다. 매칭률을 억지로 올릴수록 precision만 무너진다. **검수 표본으로 이것부터 재야 한다.**

# 추가 실측 (2026-08-06) — 가장 위험한 가정이 틀렸다

Codex가 지목한 미측정 변수를 쟀다. `npm run measure:coverage`.

## 방법

후보를 좁히지 않았다. 249개 질문을 통째로 프롬프트에 넣고 꼬리질문 90개를 판정시켰다. 한 줄이 25자 남짓이라 6KB밖에 안 되고, 좁히는 방법 자체가 미검증이라 좁히면 그 방법의 한계를 재게 된다. **여기서 재려던 것은 상한이다.**

프롬프트에 "관련 있다는 이유로 고르지 마라", "애매하면 -1", "문장 틀이 같다고 고르지 마라"를 명시했다.

## 결과

| | |
|---|---|
| LLM이 매칭했다고 한 것 | 25/90 (28%) |
| 그중 실제로 같은 질문 (내가 25개를 하나씩 판정) | 4~5개 (약 20%) |
| **진짜 coverage** | **약 5~6%** |

낱말 유사도로 잰 5%와 거의 같다. **방법을 바꿔도 결과가 같다.**

맞은 것:

```
"낙관적 락과 비관적 락 중 무엇을 쓰는가?"  →  "…은 무엇으로 고르는가?"
"Stop-the-world는 왜 필요한가?"        →  "가비지 컬렉션이 멈춤을 만드는 이유는?"
"마이크로태스크와 매크로태스크 순서는?"    →  "Promise와 타이머 중 무엇이 먼저?"
```

틀린 것:

```
"공개키 암호화의 수학적 원리는?"   →  "대칭키와 공개키 중 무엇을 선택?"
"useMemo와 useCallback의 차이는?"  →  "React Hook을 사용하는 이유는?"
"트라이에서 단어 삭제는 어떻게?"    →  "트라이를 사용하는 이유는?"
"분산 락은 어떤 상황에서?"        →  "낙관적/비관적 락 고르는 기준"
```

"관련 있다는 이유로 고르지 마라"고 못 박았는데도 관련성으로 골랐다. 이건 프롬프트를 더 다듬어 고칠 문제가 아니다. **꼬리질문과 기존 질문은 실제로 "관련 있지만 다른" 관계이기 때문이다.**

## 무엇이 뒤집혔나

> **꼬리질문은 기존 질문의 다른 표현이 아니다. 진짜로 새로운, 한 단계 더 깊은 질문이다.**

그게 "꼬리질문"의 정의다. 그래서 **동일 질문 판정으로는 그물을 만들 수 없다.** 아무리 좋은 매칭기를 만들어도 이을 대상이 5%뿐이다.

Codex가 "이 가정이 틀리면 전략 1은 그물을 만들지 못한다"고 했고, 실제로 틀렸다.

## 방향 수정

그물은 **"같은 질문이다"**가 아니라 **"관련 있다"**로 만든다.

| | 관계 | 빈도 | 필요한 정확도 | 잘못됐을 때 |
|---|---|---|---|---|
| 동일성 | 같은 질문 | 5% | 100% | 두 질문이 하나로 합쳐진다. 복구 어렵다 |
| **의미 관계** | 관련 있다 | 훨씬 많다 | 낮아도 된다 | 관련 없는 선이 하나 그려진다. 지우면 된다 |

의미 관계는 **precision 100%가 필요 없다.** 잘못 이어도 두 질문을 합치는 것이 아니라 선 하나가 잘못 그려질 뿐이고, 지우면 끝난다.

따라서 debate 결론의 순서를 바꾼다.

1. 데이터 정제 (그대로)
2. **관계 타입 분리** — 이게 3번보다 먼저다. 의미 관계를 담을 자리가 없으면 그물을 만들 수 없다
3. 좁혀진 후보 검색 (동일 판정 전용) — **우선순위가 내려간다.** 5%짜리 문제다
4. 의미 관계 만들기 — 여기가 그물의 본체다
5. 개념 계층 (그대로)

# 규모를 키우면 수렴하는가 (2026-08-06)

"질문을 수천 개 만들면 매칭률이 올라가서 그물이 되지 않겠나"를 확인했다.

## 측정은 실패했다

후보 목록 크기를 바꿔가며 같은 표본을 쟀다.

| 후보 수 | 매칭률 |
|---|---|
| 50 | 12% |
| 120 | 28% |
| 249 | 3% |

단조롭지 않다. 곡선이 아니라 잡음이다.

같은 조건(249개 후보, 같은 표본 30개)으로 3회 반복했다.

| 회차 | 매칭 |
|---|---|
| 1 | 5/30 |
| 2 | 2/30 |
| 3 | 4/30 |

**7~17% 사이에서 흔들린다.** 이 변동으로는 규모별 곡선을 그릴 수 없다.

원인은 판정 구조다. 게이트도 이 측정도 **한 번 뽑아서 그대로 승인**한다. 여러 번 뽑아 다수결하거나 판정에 근거를 요구해야 안정된다. 이 지표로는 어떤 개선도 검증할 수 없다는 뜻이기도 하다.

## 구조로 보면 수렴하지 않는다

측정이 안 되더라도 구조로 답할 수 있다.

지금 249개는 전부 **루트(주제 수준)** 질문이다. 꼬리질문은 그보다 **한 층 아래**다. 프롬프트가 "이 질문에서 한 단계 더 깊이 들어가는 질문"을 만들라고 시키기 때문이다.

```
루트:  "인덱스는 언제 안 타는가?"
꼬리:  "복합 인덱스에서 선행 컬럼을 빼면 왜 못 타는가?"   ← 한 층 아래
```

**루트를 아무리 늘려도 꼬리질문 층은 안 채워진다.** 같은 층에 더 쌓는 것이다. 실제로 맞은 5%도 우연히 다른 루트가 그 깊이에 있던 경우였다.

수렴하려면 **파여진 질문이 코퍼스에 흡수돼야** 한다. 사람이 꼬리질문을 눌러 노드가 생기고, 그 노드가 다음 사람의 꼬리질문과 만나야 한다. **쓸수록 촘촘해지는 구조**이지 미리 많이 만들어서 되는 것이 아니다.

## 세 가지 길의 비교

| 방법 | 그물이 되나 | 걸리는 시간 |
|---|---|---|
| 루트를 수천 개 만든다 | **안 된다.** 넓어질 뿐 층이 안 채워진다 | 즉시 |
| 사람이 파게 둔다 | 된다 | 사용자가 쌓여야 한다 |
| **의미 관계를 직접 잇는다** | **된다. 지금 249개로도** | 즉시 |

세 번째가 답이다. 앞 절의 결론과 같은 곳을 가리킨다.

## 다음에 고쳐야 할 것

**판정 안정화가 선행 조건이다.** 회차마다 7~17%로 흔들리는 지표 위에서는 의미 관계의 품질도 못 잰다. 의미 관계를 만들 때는 처음부터 다수결이나 근거 요구를 넣는다.
