## #1 DB 커넥션을 매번 새로 맺는 비용이 큰 이유는?
`데이터베이스`

```
커넥션 생성은 객체 하나를 만드는 일이 아니다. 네트워크 연결부터 세션 준비까지 여러 단계를 매번 다시 밟는다.

한 번 맺을 때 실제로 오가는 것은 이렇다. 단계마다 왕복이 끼어 있어 밀리초가 쌓인다.

:::flow
앱 -> DB: TCP 연결 요청. 3-way handshake가 먼저 돈다
앱 -> DB: 인증 정보 전달. 계정과 권한을 확인한다
DB -> 앱: 세션 준비 완료. 내부 자원을 할당한 뒤 응답한다
:::

요청마다 맺고 닫으면 이 비용이 응답 시간에 그대로 실린다. 동시 요청이 몰리면 문제가 커진다. DB가 질의 처리 대신 커넥션 생성과 해제에 CPU와 메모리를 쓰기 때문이다.

connection pool은 두 가지를 한다. 미리 만들어 둔 커넥션을 재사용해 생성 비용을 없앤다. 동시에 DB로 나가는 커넥션 수에 상한을 둬 DB를 보호한다. 뒤쪽이 더 중요하다.

면접에서는 pool 크기를 어떻게 정하느냐로 한 단계 더 들어온다. 크게 잡으면 DB 자원을 과점유하고 작게 잡으면 애플리케이션 쪽 대기가 늘어난다는 양면을 함께 말할 수 있어야 한다.
```

## #215 DBSCAN은 K-means보다 어떤 상황에서 더 유리한가?
`데이터베이스`

```
데이터의 분포가 원형이 아니거나 노이즈가 섞인 데이터셋에서 유리하다. K-means는 구형의 클러스터만 찾을 수 있지만, DBSCAN은 밀도 기반으로 임의의 모양을 찾아내기 때문이다.

| 기준 | K-means | DBSCAN |
| --- | --- | --- |
| 클러스터 모양 | 구형 (Centroid 기반) | 임의의 모양 (Density 기반) |
| 노이즈 처리 | 모든 점을 할당 | 밀도 미달 점을 노이즈로 분류 |
| 파라미터 | K (클러스터 개수) | eps, minPts (밀도 기준) |

DBSCAN은 설정한 거리(eps) 내에 최소 점 개수(minPts)가 있으면 이를 핵심적으로 연결한다. 이 과정을 반복해 밀도가 높은 영역을 하나의 덩어리로 묶는다.

반면 K-means는 모든 데이터를 강제로 클러스터에 포함시킨다. 밀도가 낮은 외곽의 점들이 중심점과 묶여 클러스터의 모양을 왜곡시킨다.

따라서 데이터의 실제 모양을 모르거나 이상치(Outlier)를 제거해야 하는 전처리 단계에서 DBSCAN이 효과적이다.
```

## #2 분산 트랜잭션에서 Saga 패턴이 필요한 이유는?
`아키텍처 · 분산시스템`

```
서비스마다 DB가 분리되면 하나의 트랜잭션으로 묶을 수 없기 때문이다. 롤백을 DB에 맡길 수 없으니 애플리케이션이 직접 되돌려야 한다. Saga는 긴 트랜잭션을 로컬 트랜잭션의 연쇄로 바꾸고, 뒤가 실패하면 앞을 되돌린다.

:::flow
주문 -> 결제: 주문 생성하고 커밋. 여기서 이미 확정이다
결제 -> 배송: 결제 성공하고 커밋
배송 -> 결제: 배송 생성 실패
결제 -> 주문: 결제 취소. 앞 단계를 되돌리는 보상이다
:::

각 단계는 자기 DB에서 즉시 커밋한다. 잠금을 들고 기다리지 않으니 가용성이 높다.

2PC는 같은 문제를 조정자로 푼다. 모든 참여자가 커밋 준비를 마칠 때까지 자원을 잠그므로 가용성이 떨어진다. 조정자가 죽으면 참여자가 잠긴 채로 남는 위험도 있다.

대가는 격리성 포기다. 중간 상태가 외부에 보인다. 결제는 됐는데 배송 생성이 실패한 순간이 잠깐 존재한다.

그래서 보상은 반드시 성공해야 하고 그 자체로 멱등해야 한다. 실무에서 갈리는 지점은 오케스트레이션이냐 코레오그래피냐다. 중앙 조정자를 둘지 이벤트로 흘릴지는 단계 수와 디버깅 난이도로 판단한다.
```

## #56 메시지 순서는 어디까지 보장되는가?
`아키텍처 · 분산시스템`

```
대개 파티션 안에서만이다. 여러 파티션에 흩어진 메시지 사이에는 전역 순서가 없고, 만들려면 병렬 처리를 포기해야 한다.

| 범위 | 순서 보장 |
| --- | --- |
| 같은 파티션 | 넣은 순서대로 읽힌다 |
| 다른 파티션 | 순서가 없다. 병렬로 흐른다 |
| 전역 순서 | 파티션 하나로 몰아야 한다. 처리량을 잃는다 |

그래서 순서가 중요한 것끼리 같은 파티션으로 보낸다. 주문 이벤트를 주문 번호로 나누면 한 주문의 사건들은 순서가 지켜진다.

소비자 쪽에서도 깨질 수 있다. 여러 스레드가 한 파티션을 나눠 처리하면 넣은 순서와 끝난 순서가 달라진다.

면접에서는 순서가 정말 필요한지로 되묻는다. 상태를 순서 대신 버전으로 판단하면 늦게 온 이벤트를 버릴 수 있어서 순서 요구 자체가 사라진다.
```

## #3 TCP 연결을 끊을 때 TIME_WAIT 상태가 필요한 이유는?
`네트워크`

```
마지막 ACK가 유실될 수 있기 때문이다. 먼저 닫는 쪽이 잠시 남아 있어야 상대의 재전송을 받아줄 수 있다.

:::flow
능동 종료 -> 수동 종료: FIN. 보낼 것은 다 보냈다
수동 종료 -> 능동 종료: ACK. 알겠다
수동 종료 -> 능동 종료: FIN. 나도 다 보냈다
능동 종료 -> 수동 종료: 마지막 ACK. **이게 유실되면 상대는 FIN을 다시 보낸다**
:::

4-way handshake의 마지막에서 능동 종료 측은 상대의 FIN에 ACK를 보낸다. 이 ACK가 유실되면 상대는 FIN을 재전송한다. 이때 소켓이 이미 사라졌다면 응답할 주체가 없어 상대는 연결을 정상 종료하지 못한다.

두 번째 이유는 이전 연결의 지연 패킷이다. 같은 포트 조합으로 새 연결이 곧바로 열리면 뒤늦게 도착한 옛 패킷이 새 연결의 데이터로 섞일 수 있다. TIME_WAIT은 그 시간을 벌어준다.

대기 시간은 통상 2MSL이다. 문제는 트래픽이 많은 서버에서 TIME_WAIT 소켓이 쌓여 포트가 고갈되는 것이다. 다만 이는 대개 능동 종료를 서버가 하고 있다는 신호다.

면접에서는 해결책을 물어온다. `SO_REUSEADDR`나 커널 파라미터를 만지기 전에 keep-alive로 연결을 재사용하는 쪽이 먼저다. 원인이 연결을 너무 자주 맺고 끊는 데 있기 때문이다.
```

## #153 내부 API에 바이너리 RPC가 유리한 때는?
`네트워크`

```
호출 양이 많고 엄격한 계약과 낮은 지연, 스트리밍이 필요할 때 유리하다. 클라이언트와 서버를 함께 통제할 수 있을수록 도입 비용이 낮다.

| 기준 | gRPC | REST JSON |
| --- | --- | --- |
| 계약 | Protobuf 스키마 | 문서 또는 별도 스키마 |
| 전송 | HTTP/2 바이너리 | 주로 텍스트 |
| 스트리밍 | 기본 지원 | 별도 방식 필요 |

Protobuf로 서버와 여러 언어의 클라이언트 코드를 생성한다. 정적 타입 언어에서는 타입 불일치를 컴파일 단계에서 줄일 수 있지만 스키마 호환 규칙을 지켜야 한다.

멀티플렉싱과 작은 메시지는 서비스 간 통신에 효과적이다. 그러나 공개 API에서는 브라우저 지원과 사람이 읽기 어려운 페이로드가 장벽이 된다.

프록시와 관측 도구가 HTTP/2와 gRPC를 제대로 지원하는지도 확인한다. 단순 CRUD나 외부 연동은 REST가 운영과 디버깅에 더 쉬울 수 있다.
```

## #4 컨텍스트 스위칭 비용은 구체적으로 어디서 발생하는가?
`운영체제`

```
레지스터 교체 자체보다 캐시가 무너지는 비용이 크다. 눈에 보이는 저장·복원은 일부일 뿐이다.

| 구분 | 무엇이 일어나나 | 크기 |
| --- | --- | --- |
| 직접 비용 | 레지스터·PC를 PCB에 저장하고 복원, 커널 모드 전환 | 수 마이크로초 |
| 간접 비용 | 캐시와 TLB가 무효화되어 다시 채워야 한다 | **이쪽이 본체** |

직접 비용은 명확하다. 실행 중이던 스레드의 레지스터와 프로그램 카운터를 PCB에 저장하고 다음 스레드의 것을 복원한다. 커널 모드 전환도 함께 일어난다. 이건 수 마이크로초 수준이다.

간접 비용이 본체다. CPU 캐시와 TLB에 쌓아둔 내용이 새 스레드에게는 쓸모없다. 다시 실행될 때 캐시 미스가 연달아 나고 메모리에서 다시 읽어와야 한다. 프로세스 간 전환이면 주소 공간까지 바뀌어 TLB를 통째로 비운다.

그래서 스레드를 늘린다고 처리량이 비례해 늘지 않는다. 코어 수를 넘어서면 실행이 아니라 전환에 시간을 쓰기 시작한다. 커넥션 풀 크기를 코어 수 기준으로 잡는 근거가 여기 있다.

CPU 바운드 작업은 코어 수에 맞추고 I/O 바운드는 더 늘려도 되는 이유도 같다. 대기 중인 스레드는 CPU를 점유하지 않기 때문이다.
```

## #194 소스 코드가 실행 파일로 변하는 과정은 무엇인가?
`운영체제`

```
전처리기, 컴파일러, 어셈블러, 링커가 순차적으로 처리한다.

:::flow
소스 코드 -> 전처리기: 매크로 확장 및 헤더 포함
전처리기 -> 컴파일러: 어셈블리 코드로 변환
컴파일러 -> 어셈블러: 기계어로 변환
어셈블러 -> 링커: 실행 파일 생성
:::

전처리기는 `#include`와 같은 지시문을 처리한다. 불필요한 주석을 제거하고 매크로를 실제 값으로 치환한다.

컴파일러는 전처리된 코드를 어셈블리 언어로 바꾼다. 구문 분석을 통해 논리적 오류를 잡고 최적화를 수행한다.

어셈블러는 이를 CPU가 읽는 이진 기계어로 바꾼다. 하지만 이 단계의 파일은 다른 모듈과의 연결 정보가 없다.

링커는 여러 오브젝트 파일을 하나로 합친다. 외부 함수 호출부의 실제 메모리 주소를 연결해 최종 실행 파일을 만든다.
```

## #6 useEffect 의존성 배열을 잘못 넣으면 어떤 문제가 생기는가?
`프론트엔드`

```
너무 적게 넣으면 오래된 값을 붙잡고, 너무 많이 넣으면 불필요하게 다시 실행된다. 방향이 반대인 두 문제다.

| 넣는 양 | 증상 | 알아채기 |
| --- | --- | --- |
| 너무 적다 | 클로저가 첫 렌더의 값을 계속 본다 | 오류가 안 나서 늦게 발견된다 |
| 너무 많다 | 매 렌더마다 실행되고 무한 루프로 간다 | 바로 티가 난다 |

의존성을 빠뜨리면 클로저가 첫 렌더의 값을 계속 참조한다. 이펙트 안에서 최신 상태를 읽는 줄 알았는데 초기값이 나오는 상황이 여기서 생긴다. 콘솔에는 아무 오류도 없어 발견이 늦다.

반대로 매 렌더마다 새로 만들어지는 객체나 함수를 의존성에 넣으면 참조가 계속 바뀐다. 이펙트가 매번 실행되고, 그 안에서 상태를 갱신하면 무한 루프가 된다.

정리 함수를 빠뜨리는 것도 같은 범주다. 구독이나 타이머를 걸어두고 정리하지 않으면 언마운트된 컴포넌트가 계속 살아 있다. 이펙트가 자주 실행될수록 누수가 빨리 쌓인다.

판단 기준은 단순하다. 이펙트 안에서 쓰는 모든 외부 값을 넣고, 그래서 너무 자주 실행되면 값 자체를 안정화한다. 의존성을 빼서 해결하는 것은 증상만 가리는 것이다.
```

## #118 번들은 어떤 경계로 나눠 불러오는가?
`프론트엔드`

```
초기 경로에 필요한 코드만 먼저 보낸다. 나머지는 경로, 기능, 무거운 라이브러리 경계로 나눠 필요할 때 불러온다.

:::flow
초기 진입 -> 핵심 청크: 즉시 내려받는다
경로 이동 -> 경로 청크: 동적으로 불러온다
기능 실행 -> 기능 청크: 처음 사용할 때 불러온다
:::

동적 import는 별도 청크를 만드는 경계가 된다. React에서는 lazy와 Suspense를 조합해 로딩 상태를 보여주며 컴포넌트를 늦게 읽는다.

너무 잘게 나누면 요청 수와 로딩 화면이 늘고 공통 모듈이 중복될 수 있다. 사용 빈도, 청크 크기, 캐시 적중률을 측정해 경계를 조정한다.
```

## #7 JWT를 세션 대신 쓸 때 무엇을 잃는가?
`인프라 · 보안`

```
즉시 무효화 능력을 잃는다. 서버가 상태를 갖지 않는다는 장점이 그대로 단점이 된다.

세션은 서버가 저장소를 들고 있으므로 지우면 그 순간 끝난다. JWT는 서명만 유효하면 통과하므로 발급된 토큰을 회수할 방법이 없다. 로그아웃, 권한 변경, 탈취 대응이 전부 만료 시각까지 지연된다.

| 기준 | 세션 | JWT |
| --- | --- | --- |
| 상태 보관 | 서버가 들고 있다 | 토큰 안에 들어 있다 |
| 즉시 무효화 | 지우면 끝 | **만료까지 못 막는다** |

## #8 equals를 재정의할 때 hashCode도 함께 재정의해야 하는 이유는?
`언어 · 런타임`

```
해시 기반 컬렉션이 두 메서드를 함께 쓰기 때문이다. 하나만 바꾸면 컬렉션이 같은 객체를 다른 객체로 취급한다.

HashMap은 먼저 hashCode로 버킷을 찾고 그 안에서 equals로 비교한다. equals만 재정의하면 논리적으로 같은 두 객체가 서로 다른 버킷으로 흩어진다. equals 비교까지 가지도 못하므로 조회가 실패한다.

:::flow
get(key) -> hashCode: 어느 버킷인지 먼저 정한다
hashCode -> 버킷: 그 버킷 안의 후보들만 꺼낸다
버킷 -> equals: 후보와 하나씩 견준다. **여기까지 와야 비교가 일어난다**
:::

규약은 단방향이다. equals가 true면 hashCode는 반드시 같아야 한다. 반대는 성립하지 않는다. hashCode가 같아도 equals는 false일 수 있고 이게 해시 충돌이다.

실무에서 자주 터지는 자리는 JPA 엔티티다. 식별자가 영속화 시점에 채워지므로 id 기반 hashCode는 저장 전후로 값이 바뀐다. Set에 넣어둔 엔티티를 저장하면 다시 찾지 못하게 된다.

가변 필드를 hashCode에 쓰는 것도 같은 함정이다. 컬렉션에 넣은 뒤 필드를 바꾸면 그 객체는 사실상 사라진다.
```

## #14 해시 테이블의 평균 O(1)이 무너지는 경우는?
`자료구조 · 알고리즘`

```
키가 한 버킷으로 몰릴 때다. 평균 O(1)은 해시가 고르게 흩어진다는 전제 위의 값이라, 그 전제가 깨지면 최악 O(n)으로 간다. 완화는 충돌한 것을 어떻게 담느냐와 언제 늘리느냐 두 갈래다.

| 갈래 | 하는 일 | 최악을 어디까지 |
| --- | --- | --- |
| 담는 방식 | 한 버킷이 길어지면 연결 리스트를 트리로 | `O(n)` → `O(log n)` |
| 늘리는 시점 | load factor를 넘으면 버킷을 두 배로 | 애초에 안 몰리게 |

자바 HashMap은 둘을 함께 쓴다. 앞쪽은 이미 몰린 뒤의 방어고, 뒤쪽은 몰리기 전의 예방이다.

몰리는 이유는 둘이다. 해시 함수가 나빠서 자연히 겹치거나, 누군가 일부러 겹치게 만들거나. 뒤쪽이 해시 충돌 공격인데, 사용자 입력이 그대로 키가 되는 자리에서는 실제 공격 벡터가 된다.

늘리는 것 자체에도 값이 있다. 리사이즈는 모든 키를 다시 배치하므로 그 한 번이 무겁다. 분할 상환하면 평균은 O(1)이지만 평균이 지연을 보장하지는 않는다 — 응답 시간이 중요한 경로에서는 이 한 번이 튀는 지점으로 나타난다.

면접에서는 왜 버킷 수를 2의 거듭제곱으로 잡는지로 한 단계 더 들어온다. 나머지 연산 대신 비트 마스크를 쓸 수 있어서다. 대신 하위 비트만 보게 되므로 해시를 한 번 더 섞어야 한다.
```

## #16 @Transactional이 걸리지 않는 경우는?
`프레임워크`

```
프록시를 거치지 않고 메서드에 들어갔을 때다. 스프링의 트랜잭션은 코드가 아니라 프록시가 여는 것이라, 프록시를 통과하지 않으면 애초에 열릴 기회가 없다.

가장 흔한 자리가 자기 호출이다. 같은 클래스 안에서 `this.method()`로 부르면 그 호출은 프록시를 지나지 않고 실제 객체로 곧장 들어간다. 애너테이션은 붙어 있는데 아무 일도 일어나지 않는다. 로그도 예외도 없어서 원인을 찾기 어렵다.

:::flow
다른 빈 -> 프록시: 빈 참조로 부른다. **여기서 트랜잭션이 열린다**
프록시 -> 실제 객체: 메서드 실행
실제 객체 -> 실제 객체: this.method(). 프록시를 건너뛴다 — 안 걸린다
:::

private 메서드도 같은 이유로 안 걸린다. CGLIB 프록시는 상속으로 만들어지는데 private은 재정의할 수 없다. final 메서드와 final 클래스도 마찬가지다.

걸렸는데 안 되돌아가는 경우도 있다. 기본 롤백 대상은 unchecked 예외라, 체크 예외를 던지면 트랜잭션은 그대로 커밋된다. 되돌리려면 rollbackFor를 명시해야 한다.

면접에서는 왜 자기 호출이 안 되는지를 프록시 구조로 설명할 수 있는지를 본다. 우회책을 아는 것보다 구조를 아는 쪽이 중요하다. 우회책은 대개 그 메서드를 다른 빈으로 꺼내는 것이고, 꺼내야 한다는 판단 자체가 구조 이해에서 나온다.

## #96 부모 작업이 취소되면 자식은 어떻게 되는가?
`모바일`

```
부모 작업이 취소되면 모든 자식 작업에도 취소가 전파된다. 자식은 같은 수명 경계 안에서 정리되고 부모보다 오래 남지 않는다.

:::flow
부모 -> 자식: 취소를 아래로 전파한다
자식 -> 부모: 실패를 위로 전파한다
부모 -> 형제 자식: 일반 Job이면 함께 취소한다
:::

부모는 모든 자식이 끝나야 완료된다. 이 규칙 덕분에 호출 범위를 벗어난 작업이 남는 것을 막고 예외와 자원을 한곳에서 관리할 수 있다.

자식 하나의 실패를 격리해야 한다면 SupervisorJob이나 supervisorScope를 쓴다. 이때도 부모 취소는 모든 자식에게 전파된다.
```
