# 사실 확인 표본 20편

## 1. [네트워크] HTTPS는 HTTP와 무엇이 다른가?

<!-- id: 10f835f1-f9b4-4bff-90ab-d398907b5bea · origin: batch -->

HTTP에 SSL/TLS 프로토콜을 추가해 데이터를 암호화한 것이다. 이를 통해 도청, 변조, 위조를 막는다.

:::stack
HTTPS | HTTP + SSL/TLS
HTTP | 평문 전송
:::

전송 계층 위에 SSL/TLS라는 보안 계층을 얹은 구조다. 클라이언트와 서버가 서로의 신원을 확인하고 암호화 키를 교환하는 과정이 핵심이다.

대칭키로 데이터를 빠르게 암호화하고, 비대칭키로 그 대칭키를 안전하게 전달한다. 성능 저하를 최소화하면서 보안성을 챙긴 방식이다.

인증서 기관(CA)의 서명을 통해 서버가 가짜가 아님을 보증한다. 인증서가 없으면 암호화는 가능해도 상대가 누구인지 알 수 없어 피싱에 취약하다.

## 2. [네트워크] 웹소켓과 일반 소켓 통신은 무엇으로 구분하는가?

<!-- id: e1bbcc1c-686f-4845-bc0d-485d37ee8898 · origin: batch -->

웹소켓은 HTTP 기반의 전이중 통신 프로토콜이며, 일반 소켓은 전송 계층의 TCP/UDP 연결 자체를 의미한다.

| 기준 | 웹소켓 | 일반 소켓 |
| --- | --- | --- |
| 계층 | 애플리케이션(L7) | 전송(L4) |
| 연결 방식 | HTTP 핸드셰이크 필요 | 직접 연결 |
| 특징 | 상태 유지(Stateful) | 로우 레벨 데이터 전송 |

웹소켓은 웹 브라우저 환경에서 실시간 통신을 하기 위해 설계되었다. HTTP의 요청-응답 모델을 유지하면서도 연결을 계속 열어두어 서버가 클라이언트로 데이터를 보낼 수 있게 한다.

일반 소켓은 운영체제가 제공하는 네트워크 인터페이스다. IP와 포트를 통해 바이트 스트림을 주고받는 가장 기초적인 도구이며, 웹소켓은 내부적으로 이 소켓을 활용해 구현된다.

따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 통신을 위한 하드웨어/소프트웨어적 통로 그 자체라고 볼 수 있다.

## 3. [데이터베이스] SQL에서 뷰나 인라인 뷰를 사용하여 쿼리를 작성할 때 성능 최적화를 위해 주의해야 할 점은 무엇인가?

<!-- id: 659355a6-1670-497f-ae52-55059ff9d6de · origin: on_demand -->

뷰나 인라인 뷰 작성 시 가장 주의할 점은 옵티마이저의 뷰 병합 실패로 인한 성능 저하다.

| 구분 | 뷰 병합 (Merging) | 뷰 미병합 (Materialization) |
| --- | --- | --- |
| 처리 방식 | 메인 쿼리와 통합 실행 | 결과를 임시 테이블로 구체화 |
| 인덱스 활용 | 메인 쿼리 인덱스 사용 | 구체화 집합에 인덱스 없음 |

옵티마이저가 뷰를 병합하지 못하면 메인 쿼리의 조건이 뷰 내부로 전달되지 않는다.

GROUP BY나 DISTINCT가 들어간 뷰는 병합이 어렵다. 뷰 결과를 임시 집합으로 먼저 만든다. 메모리와 I/O 부담이 늘어난다.

뷰 외부 조건이 내부로 전달되는지 확인한다. 조건 절 푸시다운에 실패하면 뷰 전체를 가져온 뒤 필터링한다.

필요 이상으로 많은 테이블을 조인한 뷰를 피한다. 일부 컬럼만 필요해도 뷰 내부의 모든 조인을 처리한다.

## 4. [데이터베이스] 인덱스 범위 스캔과 전체 스캔 중 무엇을 선택하는가?

<!-- id: 552308dc-7dc6-4fb3-b64c-fcd4621f6859 · origin: batch -->

데이터의 선택도와 비용 옵티마이저의 판단에 따라 결정한다. 읽어야 할 데이터가 전체의 일정 비율을 넘으면 인덱스보다 전체 스캔이 빠르다.

| 기준 | 인덱스 범위 스캔 | 전체 스캔 |
| --- | --- | --- |
| 접근 방식 | B-Tree 탐색 후 리프 노드 순회 | 데이터 페이지 순차 읽기 |
| 효율성 | 소량 데이터 추출 시 유리 | 대량 데이터 추출 시 유리 |
| I/O 방식 | 랜덤 I/O 발생 | 순차 I/O 발생 |

인덱스 범위 스캔은 인덱스 페이지를 거쳐 데이터 페이지로 이동하는 랜덤 I/O가 발생한다. 읽을 양이 많아지면 이 오버헤드가 순차적으로 읽는 전체 스캔보다 커진다.

옵티마이저는 통계 정보를 바탕으로 비용을 계산한다. 인덱스를 통해 읽어야 할 페이지 수가 전체 페이지 수의 상당 부분을 차지하면 전체 스캔을 선택한다.

실무에서는 통계 정보가 오래되었을 때 엉뚱한 스캔 방식이 선택되어 성능이 급락한다. 이때는 힌트를 사용해 강제로 실행 계획을 변경해야 한다.

## 5. [모바일] 비동기로 옮겼는데도 왜 응답 없음이 생기는가?

<!-- id: 9a4e70c3-5916-4be0-afd8-5d7820896dfa · origin: batch -->

작업을 다른 스레드로 보냈어도 메인 스레드가 결과나 잠금을 기다리면 막히기 때문이다. 느린 Binder 호출과 과도한 그리기도 입력 처리를 지연시킨다.

:::flow
사용자 -> 메인 Looper: 입력 이벤트를 보낸다
메인 Looper -> 작업: 결과나 잠금을 기다린다
시스템 -> 앱: 기한 내 응답이 없어 ANR을 기록한다
:::

메인 스레드는 입력과 생명주기 콜백과 화면 갱신을 직렬로 처리한다. 입력 이벤트에 약 5초간 응답하지 못하면 입력 디스패치 ANR이 날 수 있다.

스택 덤프에서 main의 대기 지점을 찾고 잠금 보유 스레드도 따라간다. StrictMode와 Perfetto로 I/O와 느린 Binder 호출을 확인한다.

## 6. [모바일] 첫 화면을 빠르게 띄우려면 무엇을 미뤄야 하는가?

<!-- id: 63ec5b1d-ab0a-4062-870e-188b3fe4133c · origin: batch -->

첫 화면에 필요 없는 초기화를 미뤄야 한다. Application과 시작 화면의 동기 작업을 줄이고 분석 도구나 캐시 예열은 지연하거나 백그라운드로 보낸다.

:::flow
프로세스 -> Application: 필수 초기화만 한다
Application -> 첫 화면: 렌더링을 시작한다
첫 화면 -> 백그라운드: 나머지를 지연 실행한다
:::

콜드 시작은 시작 요청부터 첫 프레임까지 재며 프로세스 초기화도 포함한다. 웜 시작과 핫 시작은 재사용 자원이 달라서 같은 수치로 섞으면 병목을 잘못 판단한다.

시작 추적에서 메인 스레드의 디스크 접근과 클래스 로딩을 찾는다. Baseline Profile은 자주 쓰는 코드의 해석과 컴파일 비용을 줄인다.

지연 초기화도 사용 직전에 몰리면 끊김이 생긴다. 기능 우선순위와 의존성을 정하고 실제 기기에서 첫 표시와 완전 표시를 함께 측정한다.

## 7. [아키텍처 · 분산시스템] 메시지 큐를 두면 무엇을 얻고 무엇을 잃는가?

<!-- id: 76123298-3456-4517-a4a6-5455a6626ded · origin: batch -->

보내는 쪽과 받는 쪽의 시간을 떼어내는 대신 순서와 즉시성을 잃는다. 트래픽이 몰려도 받는 쪽이 자기 속도로 처리할 수 있게 되는 것이 가장 큰 이득이다.

직접 호출은 받는 쪽이 죽으면 보내는 쪽도 같이 실패한다. 큐를 끼우면 메시지가 쌓여 있다가 받는 쪽이 살아난 뒤에 처리된다. 배포 중에도 요청이 유실되지 않는다.

| 기준 | 직접 호출 | 큐를 통해 |
| --- | --- | --- |
| 받는 쪽이 죽으면 | 보내는 쪽도 실패 | 쌓였다가 나중에 처리 |
| 결과를 아는 시점 | 즉시 | 나중에. 따로 알려야 한다 |
| 순서 | 호출한 순서 | 파티션 안에서만 보장 |

대가가 분명하다. 결과를 즉시 못 준다. 주문이 접수됐다는 응답과 실제로 처리됐다는 사실 사이에 틈이 생기고, 그 틈을 화면이 설명해야 한다. 실패도 그 자리에서 안 보여서 따로 관측해야 한다.

면접에서는 중복과 순서로 한 단계 더 들어온다. 대부분의 큐는 최소 한 번 전달을 보장하므로 같은 메시지가 두 번 올 수 있다. 받는 쪽이 멱등해야 하고, 순서가 필요하면 같은 키를 같은 파티션으로 보내야 한다.

## 8. [아키텍처 · 분산시스템] 재시도가 있는 시스템에서 멱등성이 필요한 이유는?

<!-- id: 73c2faaf-ae74-41c1-910a-748c98db7caf · origin: batch -->

같은 요청이 두 번 도착하기 때문이다. 응답만 유실돼도 클라이언트는 실패로 보고 다시 보내는데, 서버 입장에서는 새 요청과 구별되지 않는다.

:::flow
클라이언트 -> 서버: 결제 요청
서버 -> 클라이언트: 처리 완료. 응답이 유실된다
클라이언트 -> 서버: 실패인 줄 알고 재요청
서버 -> 클라이언트: 같은 키다. 앞의 결과를 그대로 돌려준다
:::

막는 방법은 요청마다 고유한 키를 받는 것이다. 서버가 그 키로 결과를 기록해 두면 두 번째 요청은 새로 처리하지 않고 앞의 결과를 돌려준다.

키를 언제까지 들고 있을지가 실무의 급소다. 짧으면 늦은 재시도가 중복 처리되고, 길면 저장소가 계속 늘어난다.

면접에서는 조회와 삭제가 원래 멱등이라는 점을 짚는다. 문제는 생성과 갱신이고, 그중에서도 돈이 오가는 자리다.

## 9. [언어 · 런타임] 가비지 컬렉션이 멈춤을 만드는 이유는?

<!-- id: acd8d116-38e7-4e74-82ae-3075e2ff9956 · origin: batch -->

살아 있는 객체를 세는 동안 그 관계가 바뀌면 안 되기 때문이다. 세는 중에 애플리케이션이 참조를 바꾸면 이미 확인한 것이 틀려져서, 그 구간만은 실행을 세운다.

:::stack
Eden | 새 객체가 여기 태어난다. 대부분 금방 죽는다
Survivor | 한두 번 살아남은 것이 잠시 머문다
Old | 오래 산 것이 승격된다. 여기 청소가 비싸다
:::

대부분의 객체는 태어나자마자 죽는다. 그래서 젊은 영역만 자주 짧게 치우고 늙은 영역은 가끔 손댄다. 젊은 쪽 청소는 보통 밀리초 단위라 눈에 안 띈다.

문제는 늙은 영역이다. 대상이 많고 흩어져 있어 오래 걸리고, 그동안 응답이 멈춘다. 힙을 키우면 빈도는 줄지만 한 번의 멈춤은 길어진다 — 총량과 최악값의 맞바꿈이다.

요즘 수집기는 세는 일 대부분을 실행과 겹쳐서 한다. 멈추는 구간을 시작과 끝의 짧은 두 번으로 줄이는 방식이다. 완전히 없애지는 못한다.

## 10. [언어 · 런타임] 이름이 다른 두 타입이 호환되는 기준은?

<!-- id: 3cf01acf-556e-404c-aacb-ae4c2122900d · origin: batch -->

대상 타입이 요구하는 멤버를 소스 타입이 호환되는 형태로 갖추면 이름이나 선언 계보가 달라도 대입할 수 있다. TypeScript는 기본적으로 구조를 비교한다.

| 기준 | 구조적 타이핑 | 명목적 타이핑 |
| --- | --- | --- |
| 호환 조건 | 멤버 구조 | 선언 이름·계보 |
| 재사용 | 암시적 | 명시적 |
| 구분 강도 | 약함 | 강함 |

소스에 속성이 더 많아도 대입은 대체로 허용된다. 다만 새 객체 리터럴을 바로 넣을 때는 초과 속성 검사로 오타 가능성을 잡는다.

구조가 우연히 같은 식별자 타입은 서로 섞일 수 있다. 브랜드 필드를 더하면 명목적 구분을 흉내 내어 UserId와 OrderId 같은 혼용을 막을 수 있다.

타입 검사는 컴파일 시 사라진다. 외부 입력의 실제 구조는 런타임 검증이 필요하다.

## 11. [운영체제] 데드락을 해결하기 위한 회피 전략은 무엇인가?

<!-- id: 65a36957-f003-4389-9f1d-92bdba32cb78 · origin: batch -->

은행원 알고리즘을 사용하여 자원 할당 시 안전 상태를 유지하는 것이다. 자원을 할당한 후에도 모든 프로세스가 완료될 수 있는 경로가 있는지 확인한다.

:::flow
자원 요청 -> 안전 상태 확인: 할당 가능한 자원이 있는지 검사
안전 상태 확인 -> 자원 할당: 모든 프로세스가 완료될 수 있는 경로가 있다면 할당
자원 할당 -> 자원 반납: 프로세스 완료 후 자원을 시스템에 반납
:::

회피는 교착 상태가 발생할 수 있는 상황을 아예 만들지 않는 것이다. 요청한 자원을 즉시 줄 수 없다면, 다른 프로세스가 자원 반납을 통해 안전하게 완료될 수 있을 때까지 대기시킨다.

반면 예방은 교착 상태의 발생 조건 네 가지 중 하나라도 깨뜨리는 것. 회피는 시스템의 자원 상태를 계속 추적하며 동적으로적으로 결정한다.

은행원 알고리즘은 모든 프로세스가 필요로 하는 최대 자원량을 미리로 알고 있어야 한다. 실무적으로는 프로세스의 최대 자원을 예측하기 어려워 적용으로 범위가 좁다.

## 12. [운영체제] 컨텍스트 스위칭 비용은 구체적으로 어디서 발생하는가?

<!-- id: 9822adc5-13cf-4641-80a0-147c82605eee · origin: batch -->

레지스터 교체 자체보다 캐시가 무너지는 비용이 크다. 눈에 보이는 저장·복원은 일부일 뿐이다.

| 구분 | 무엇이 일어나나 | 크기 |
| --- | --- | --- |
| 직접 비용 | 레지스터·PC를 PCB에 저장하고 복원, 커널 모드 전환 | 수 마이크로초 |
| 간접 비용 | 캐시와 TLB가 무효화되어 다시 채워야 한다 | **이쪽이 본체** |

직접 비용은 명확하다. 실행 중이던 스레드의 레지스터와 프로그램 카운터를 PCB에 저장하고 다음 스레드의 것을 복원한다. 커널 모드 전환도 함께 일어난다. 이건 수 마이크로초 수준이다.

간접 비용이 본체다. CPU 캐시와 TLB에 쌓아둔 내용이 새 스레드에게는 쓸모없다. 다시 실행될 때 캐시 미스가 연달아 나고 메모리에서 다시 읽어와야 한다. 프로세스 간 전환이면 주소 공간까지 바뀌어 TLB를 통째로 비운다.

그래서 스레드를 늘린다고 처리량이 비례해 늘지 않는다. 코어 수를 넘어서면 실행이 아니라 전환에 시간을 쓰기 시작한다. 커넥션 풀 크기를 코어 수 기준으로 잡는 근거가 여기 있다.

CPU 바운드 작업은 코어 수에 맞추고 I/O 바운드는 더 늘려도 되는 이유도 같다. 대기 중인 스레드는 CPU를 점유하지 않기 때문이다.

## 13. [인프라 · 보안] TLS 핸드셰이크의 핵심 목적은 무엇인가?

<!-- id: a4ec9e80-ba7e-409b-91c8-68118a65141f · origin: batch -->

클라이언트와 서버가 서로의 신원을 확인하고, 데이터를 암호화할 수 있는 대칭키를 안전하게 공유하는 것이다.

:::flow
클라이언트 -> 서버: Client Hello. 지원 버전과 암호화 방식 제안
서버 -> 클라이언트: Server Hello. 암호화 방식 선택 및 인증서 전달
클라이언트 -> 서버: Key Exchange. 서버 신원 확인 후 프리마스터 시크릿 전달
서버 -> 클라이언트: Finished. 모든 설정 완료 및 대칭키 생성
:::

위 흐름을 통해 신뢰할 수 있는 기관(CA)이 서명한 인증서를 확인하여 중간자 공격을 방지한다. 공개키 기반의 비대칭 암호화로 초기 연결을 횃불처럼 보호한다.

최종적으로 생성된 세션 키는 대칭키 암호화 방식을 사용한다. 비대칭 암호화는 연산량이 많아 실제 데이터 전송 시에는 효율적인 대칭키를 쓰는 것이 핵심이다.

TLS 1.3 버전에서는 이 과정을 1-RTT로 줄여 연결 속도를 성능상 이득을 얻었다. 이전 버전보다 불필요한 왕복 횟수를 처음부터 줄여 지연 시간을 단축했다.

## 14. [인프라 · 보안] 블로킹과 논블로킹 I/O의 결정적 차이는 무엇인가?

<!-- id: 0c72906c-013c-4126-acbe-a8805e04c930 · origin: batch -->

제어권의 반환 시점이다. 블로킹은 작업 완료까지 기다리며, 논블로킹은 호출 즉시 제어권을 돌려준다.

:::flow
호출자 -> 커널: I/O 요청
커널 -> 호출자: **블로킹**: 완료까지 대기 / **논블로킹**: 즉시 반환 (EAGAIN)
::: 

블로킹 방식은 코드가 직관적이다. 하지만 I/O가 끝날 때까지 쓰레드가 멈춰 자원을 낭비한다.

논블로킹은 대기 시간 동안 다른 일을 할 수 있다. 대신 작업 완료 여부를 계속 확인하거나 알림을 받아야 하므로 로직이 복잡해진다.

이 구분은 동기/비동기 개념과 섞이기 쉽다. 핵심은 '제어권'이 누구에게 있는지에 주목해 구분해야 한다.

## 15. [자료구조 · 알고리즘] 메모리보다 큰 데이터를 정렬할 때 무엇을 쓰는가?

<!-- id: cdfbedf8-315c-4276-beb1-89e1d2516937 · origin: batch -->

외부 정렬을 사용한다. 데이터를 작은 조각으로 나누어 정렬한 뒤, 이를 다시 합치는 방식을 취한다.

:::flow
데이터 분할 -> 정렬된 런 생성 -> 병합 과정 진행
:::

가장 흔한 방식은 외부 병합 정렬이다. 메모리에 올릴 수 있는 만큼 데이터를 읽어 정렬하고 임시 파일로 저장한다. 이를 '런(Run)'이라고 부른다.

이후 여러 런을 동시에 읽으며 가장 작은 값을 선택해 결과 파일에 쓴다. 이때 최소 힙(Min Heap)을 사용해 병합 속도를 높인다.

디스크 I/O 횟수를 줄이는 것이 핵심이다. 메모리 버퍼 크기를 키우거나 병합 단계를 줄여 읽고 쓰는 횟수를 최소화해야 한다.

## 16. [자료구조 · 알고리즘] 최단 경로 알고리즘의 선택 기준은 무엇인가?

<!-- id: 8296435a-7e7f-4cf3-8f42-343e167d7983 · origin: batch -->

가중치 유무와 음수 가중치 존재 여부에 따라 결정한다. 가중치가 없다면 BFS, 양수 가중치만 있다면 다익스트라, 음수 가중치가 있다면 벨만-포드 알고리즘을 쓴다.

| 기준 | BFS | 다익스트라 | 벨만-포드 |
| --- | --- | --- | --- |
| 가중치 | 없음 | 양수 | 음수 포함 |

BFS는 모든 노드를 동일한 거리로 계산하므로 가중치가 없을 때 가장 빠르다. 다익스트라는 우선순위 큐를 이용해 최단 거리를 확정하며 탐색 범위를 좁힌다.

벨만-포드는 모든 간선을 반복적으로 확인하여 음수 사이클이 있는지 판단한다. 다익스트라와 달리 음수 가중치가 있어도 정확한 거리값을 찾을 수 있다.

알고리즘마다 시간 복잡도와 정확성의 트레이드오프가 발생한다. 상황에 맞는 알고리즘을 선택해 불필요한 계산량을 줄이는 것이 핵심이다.

## 17. [프레임워크] 단위 시험과 통합 시험은 무엇으로 가르는가?

<!-- id: 2a1ae829-21b3-42da-8593-599384cd6ec3 · origin: batch -->

무엇을 함께 확인하는지로 가른다. 단위 시험은 작은 동작 하나를 따로 보고 통합 시험은 여러 조각이 맞물리는 자리를 본다.

| 기준 | 단위 | 통합 |
| --- | --- | --- |
| 보는 범위 | 동작 하나 | 조각들이 만나는 곳 |
| 둘레 | 자주 가짜로 바꾼다 | 대개 실제 것을 쓴다 |
| 대개의 속도 | 빠르다 | 느리다 |

가짜로 바꾸는 것은 경향이지 정의가 아니다. 단위 시험이 실제 협력 객체를 써도 되고, 통합 시험이 바깥 시스템만 가짜로 둬도 된다.

비율보다 중요한 것은 **되돌렸을 때 빨간불이 뜨는가**다. 고친 자리를 원래대로 돌려도 통과하면 그 시험은 적어도 이 회귀를 못 잡는다.

## 18. [프레임워크] 인증 정보는 어떻게 보안 문맥에 들어가는가?

<!-- id: 46cd1316-9f2a-4c04-861f-d1df114147e6 · origin: batch -->

인증 필터가 요청에서 자격 증명을 꺼내 미인증 토큰을 만든다. AuthenticationManager가 검증을 위임하고 성공 결과를 SecurityContext에 넣는다.

:::flow
필터 -> Manager: 미인증 토큰
Manager -> Provider: 검증 위임
Provider -> Manager: 인증된 주체·권한
Manager -> 필터: 인증 결과
필터 -> 보안 문맥: 결과 저장
:::

AuthenticationProvider는 토큰 종류를 지원하는지 판단한다. 사용자 조회와 비밀번호 해시 비교를 거쳐 주체와 권한을 담은 결과를 만든다.

이후 인가 필터가 보안 문맥의 권한으로 접근을 판정한다. 인증이 없으면 401이다. 인증은 됐지만 권한이 부족하면 403이다.

세션 방식은 보안 문맥을 요청 사이에 복원한다. 무상태 토큰 방식은 매 요청 토큰을 검증한다. 저장 정책과 필터 위치가 흐름을 바꾼다.

## 19. [프론트엔드] 레이아웃 계산과 픽셀 갱신은 언제 생기는가?

<!-- id: 9f87d916-34b6-4ff7-ace2-c74e0dd591f9 · origin: batch -->

요소의 크기나 위치가 바뀌면 레이아웃 계산이 생긴다. 색상처럼 기하에 영향 없는 속성이 바뀌면 픽셀만 다시 그린다.

:::flow
기하 속성 변경 -> 레이아웃: 크기와 위치를 계산한다
레이아웃 -> 페인트: 픽셀을 그린다
페인트 -> 합성: 레이어를 배치한다
:::

DOM 쓰기 뒤 곧바로 크기를 읽으면 브라우저가 미뤄 둔 계산을 즉시 끝내야 한다. 읽기와 쓰기를 섞어 반복하면 레이아웃 스래싱이 된다.

애니메이션은 가능하면 transform과 opacity를 쓴다. 별도 레이어에서 합성할 수 있어 레이아웃과 페인트를 피하지만 레이어 메모리는 늘 수 있다.

## 20. [프론트엔드] 체감 성능은 어떤 세 지표로 판단하는가?

<!-- id: c87653b7-3510-4fea-9cb4-7c63b6726086 · origin: batch -->

LCP로 주요 콘텐츠 표시 속도를 판단한다. INP로 상호작용 반응성을 본다. CLS로 시각적 안정성을 확인한다. 세 지표는 서로 다른 불편을 드러낸다.

| 기준 | 지표 | 판단 대상 |
| --- | --- | --- |
| 표시 | LCP | 주요 콘텐츠 속도 |
| 반응 | INP | 상호작용 지연 |
| 안정 | CLS | 레이아웃 이동 |

좋음 기준은 LCP 2.5초 이하, INP 200밀리초 이하, CLS 0.1 이하다. 페이지 방문의 75번째 백분위에서 모바일과 데스크톱을 나눠 본다.

현장 데이터는 실제 기기와 네트워크의 경험을 보여준다. 실험실 데이터는 재현과 원인 분석에 유리하다. 개선 전후에는 둘을 함께 본다.
