# 묶음 05 — 28편

## 1. [네트워크] HTTP 메서드 선택의 기준은 무엇인가?

<!-- id: 12c96b42-ede3-42d3-9a36-f715f50f30a9 -->

리소스의 상태를 변경하는 성격과 멱등성 여부로 결정한다. 조회를 위해 GET을, 생성은 POST, 수정은 PUT이나 PATCH를, 삭제는 DELETE를 사용한다.

| 기준 | GET | POST | PUT | PATCH | DELETE |
| --- | --- | --- | --- | --- | --- |
| 목적 | 조회 | 생성 | 전체 수정 | 부분 수정 | 삭제 |
| 멱등성 | O | X | O | X | O |
| 안전성 | O | X | X | X | X |

안전한 메서드는 리소스를 변경하지 않는다. GET은 데이터를 읽기만 하므로 안전하다. 반면 POST는 서버 상태를 바꾼다.

멱등성이란 여러 번 호출해도 결과가 같은지 여부다. PUT은 동일한 데이터로 요청을 보내면 몇 번을 보내도 결과가 항상 같다.

PATCH는 리소스의 일부만 바꾸기 때문에 호출 순서나 현재 상태에 따라 결과가 달라질 수 있다. 그래서 멱등성이 보장되지 않는 경우가 많다.

## 2. [네트워크] 리소스 API의 성숙도를 무엇으로 판단하는가?

<!-- id: 671c2c30-bb53-4dd1-b7a4-df8479dd995f -->

리소스를 URI로 나누고 HTTP 메서드와 상태 코드를 의미에 맞게 쓰며 응답이 다음 행동 링크를 제공하는지로 판단한다. 단계가 높을수록 HTTP 의미를 더 활용한다.

:::stack
Level 3 | 하이퍼미디어가 다음 행동을 안내한다
Level 2 | HTTP 메서드와 상태 코드를 활용한다
Level 1 | 리소스별 URI를 분리한다
Level 0 | 하나의 URI로 원격 호출한다
:::

Richardson 모델은 API가 HTTP를 얼마나 충실히 활용하는지 설명한다. Level 2만 되어도 자원과 행위, 오류 의미가 명확해져 일반적인 API에 실용적이다.

Level 3의 HATEOAS는 클라이언트가 링크를 따라 상태를 전이하게 한다. 결합을 줄일 수 있지만 링크 규약과 클라이언트 구현 비용이 커진다.

높은 단계가 모든 API의 품질 순위는 아니다. 조직의 클라이언트 통제 범위와 변경 빈도에 비해 복잡성의 이득이 있는지 판단해야 한다.

## 3. [네트워크] 재검증 없이 응답을 써도 되는 기준은?

<!-- id: 13c66225-df91-4464-95a5-288b44940b36 -->

저장된 응답이 `max-age` 안에 있으면 재검증 없이 쓸 수 있다. 기간이 지났다면 검증자로 서버에 변경 여부를 물어야 한다.

| 지시자 | 저장 | 재사용 조건 |
| --- | --- | --- |
| `max-age` | 가능 | 신선한 동안 즉시 사용 |
| `no-cache` | 가능 | 매번 재검증 |
| `no-store` | 금지 | 재사용 불가 |

`no-cache`는 저장 금지가 아니다. 캐시에 보관해도 되지만 사용할 때마다 `ETag`나 `Last-Modified`로 확인하라는 뜻이다.

변경이 없으면 서버는 본문 없이 `304 Not Modified`를 보낸다. 전송량은 줄지만 네트워크 왕복은 남는다.

해시가 포함된 정적 파일명에는 긴 `max-age`와 `immutable`이 잘 맞는다. 개인화 응답은 `private`과 `Vary`를 함께 검토해야 한다.

## 4. [데이터베이스] RDB와 NoSQL 중 무엇을 기준으로 선택하는가?

<!-- id: bf952154-6ab9-4bb3-bfb8-beb1abbc9f49 -->

데이터의 정형성도와 쓰기/읽기 부하량에 따라 결정한다. 엄격한 스키마가 필요하면 RDB를, 유연한 구조와 대용량 처리가 우선이면 NoSQL을 쓴다.

| 기준 | RDB | NoSQL |
| --- | --- | --- |
| 스키마 | 고정적 | 유연함 |
| 확장성 | 수직 확장(Scale-up) | 수평 확장(Scale-out) |
| 트랜잭션 | ACID 준수 | BASE (최종 일관성) |

정형 데이터는 RDB가 유리하다. 조인(Join)을 통해 중복을 제거하고 무결성을 보장한다. 반면 NoSQL은 중복을 허용하며 데이터 접근 속도를 높인다.

트랜잭션 보장 수준이 중요하다면 RDB를 쓴다. 금융 거래처럼 정확한 데이터 일관성이 필수적인 곳에 적합하다.

분산 환경에서 빠르게 확장해야 한다면 NoSQL이 낫다. 샤딩(Sharding)이나 복제(Replication)를 통해 수평적 확장이 용이해 데이터 양이 늘어나도 대응이 가능하다.

## 5. [데이터베이스] 데이터베이스 스키마를 설계할 때 고려할 점은 무엇인가?

<!-- id: 133f91d9-d485-4431-acf7-6f97c7dff7b9 -->

데이터의 무결성을 유지하면서 중복을 최소화하는 정규화와 확장성을 고려한 비정규화를 조절하는 것이다.

| 기준 | 정규화 | 비정규화 |
| --- | --- | --- |
| 목적 | 중복 제거 및 무결성 | 조회 성능 향상 |
| 영향 | 쓰기 속도 증가 | 읽기 속도 증가 |

정규화는 데이터 중복을 없애 테이블을 쪼개는 과정이다. 삽입, 수정, 삭제 시 발생하는 이상 현상을 방지해 데이터 신뢰도를 높인다.

반면 비정규화는 성능을 위해 의도적으로 중복을 허용하는 것이다. 조인 횟수가 너무 많아 읽기 성능이 급격히 떨어질 때 선택한다.

결국 서비스의 읽기-쓰기 비율과 트래픽 규모를 판단해 두 전략의 균형점을 찾는 것이 핵심이다.

## 6. [데이터베이스] 인덱스 생성 시 읽기 성능과 쓰기 성능의 트레이드오프는 무엇인가?

<!-- id: 08b0bf93-4af9-4fcc-90dd-949fb5133fcc -->

인덱스가 많아지면 읽기 속도는 빨라지지만, 데이터 변경 시 인덱스 구조를 함께 수정해야 하므로 쓰기 성능이 떨어진다.

| 기준 | 읽기 성능 | 쓰기 성능 |
| --- | --- | --- |
| 인덱스 수 | 많을수록 유리 | 많을수록 불리 |
| 작업 내용 | 인덱스 탐색으로 범위 좁힘 | B-Tree 구조 재구성 및 정렬 |

인덱스는 데이터의 위치를 저장한 별도의 저장소다. 데이터를 삽입하거나 수정할 때 실제 데이터 페이지와 인덱스 페이지를 모두 갱신해야 한다.

특히 삽입 시 B-Tree의 노드 분할이 발생하면 여러 페이지를 수정해야 하므로 오버헤드가 크다. 따라서 쓰기 작업이 빈번한 테이블에서는 인덱스 수를 최소화해야 한다.

## 7. [모바일] 백그라운드 전환 때 어디서 자원을 해제하는가?

<!-- id: 712231f1-3a1c-473c-be94-a040d32ce548 -->

화면이 완전히 보이지 않으면 onStop에서 화면 전용 자원을 멈추거나 줄인다. onPause에는 포커스를 잃을 때 꼭 필요한 짧은 처리만 둔다.

:::flow
시스템 -> Activity: onCreate. 화면을 만든다
Activity -> Activity: onStart와 onResume. 보이고 입력받는다
시스템 -> Activity: onPause와 onStop. 포커스와 가시성을 잃는다
:::

onPause 상태에서도 멀티 윈도우나 반투명 화면 뒤로 보일 수 있다. 그래서 무거운 종료 작업을 넣으면 전환이 느려진다.

onStop 뒤에는 프로세스가 종료될 수 있다. onDestroy 호출에 저장을 의존하지 말고 작은 UI 상태는 저장 상태 API로 남긴다.

## 8. [모바일] 안드로이드에서 메모리 누수가 발생하는 주원인은 무엇인가?

<!-- id: 031700b2-742f-49a5-a571-e64f7034fda4 -->

활동(Activity)이 파괴되었음에도 외부 객체에 의해 참조가 유지되어 가비지 컬렉터가 회수하지 못할 때 발생한다.

:::stack
참조 체인 | Activity $\rightarrow$ 익명 클래스 $\rightarrow$ 외부 객체
루트 객체 | GC Root. 메모리 해제제한의 시작점
:::

가장 흔한 사례는 Activity 내부에서 익명 클래스나 내부 클래스를 사용하는 경우다. 이들은 외부 클래스에 대한 숨은 참조를 가지므로, 내부 클래스가 살아있으면 Activity도 메모리에 남는다.

특히 핸들러(Handler)나 비동기 작업이 Activity보다 오래 실행될 때 위험하다. 작업이 끝나기 전까지 Activity 참조를 붙잡고 있어 누수가 발생한다.

이를 방지하려면 Static 클래스로 선언하고 약한 참조(WeakReference)를 사용해야 한다. 또한 Activity 생명주기에 맞춰 등록한 리스너를 명시적으로 해제해야 한다.

## 9. [모바일] 코루틴의 구조적 동시성은 무엇을 해결하는가?

<!-- id: faa53301-ae3e-434d-9f2a-c08d4ec69c78 -->

비정상적으로 종료된 자식 코루틴이 부모 코루틴에 의해 관리되지 않아 메모리 누수나 불필요한 작업이 계속되는 현상을 해결한다.

:::stack
부모 코루틴 | 자식 코루틴의 생명주기를 관리하고 완료를 기다림
자식 코루틴 | 부모의 컨텍스트와 Job로 묶여 제어됨
:::

구조적 동시성은 코루틴 간의 계층 구조를 형성한다. 부모 코루틴은 모든 자식 코루틴이 끝날 때까지 대기한다. 자식에서 예외가 발생하면 부모와 형제 코루틴 모두 취소된다.

이러한 구조 덕분에 Scope를 통해 코루틴을 한 번에 취소할 수 있다. 예를 들어 안드로이드의 ViewModelScope를 쓰면 화면이 닫힐 때 실행 중인 모든 작업이 자동으로 중단된다.

## 10. [아키텍처 · 분산시스템] 메시지 순서는 어디까지 보장되는가?

<!-- id: f5ab8dca-5942-4742-bafc-9483aaa42082 -->

대개 파티션 안에서만이다. 여러 파티션에 흩어진 메시지 사이에는 전역 순서가 없고, 만들려면 병렬 처리를 포기해야 한다.

:::stack
같은 파티션 | 넣은 순서대로 읽힌다
다른 파티션 | 순서가 없다. 병렬로 흐른다
전역 순서 | 파티션 하나로 몰아야 한다. 처리량을 잃는다
:::

그래서 순서가 중요한 것끼리 같은 파티션으로 보낸다. 주문 이벤트를 주문 번호로 나누면 한 주문의 사건들은 순서가 지켜진다.

소비자 쪽에서도 깨질 수 있다. 여러 스레드가 한 파티션을 나눠 처리하면 넣은 순서와 끝난 순서가 달라진다.

면접에서는 순서가 정말 필요한지로 되묻는다. 상태를 순서 대신 버전으로 판단하면 늦게 온 이벤트를 버릴 수 있어서 순서 요구 자체가 사라진다.

## 11. [아키텍처 · 분산시스템] 재시도가 있는 시스템에서 멱등성이 필요한 이유는?

<!-- id: 73c2faaf-ae74-41c1-910a-748c98db7caf -->

같은 요청이 두 번 도착하기 때문이다. 응답만 유실돼도 클라이언트는 실패로 보고 다시 보내는데, 서버 입장에서는 새 요청과 구별되지 않는다.

:::flow
클라이언트 -> 서버: 결제 요청
서버 -> 클라이언트: 처리 완료. 응답이 유실된다
클라이언트 -> 서버: 실패인 줄 알고 재요청
서버 -> 클라이언트: 같은 키다. 앞의 결과를 그대로 돌려준다
:::

막는 방법은 요청마다 고유한 키를 받는 것이다. 서버가 그 키로 결과를 기록해 두면 두 번째 요청은 새로 처리하지 않고 앞의 결과를 돌려준다.

키를 언제까지 들고 있을지가 실무의 급소다. 짧으면 늦은 재시도가 중복 처리되고, 길면 저장소가 계속 늘어난다.

면접에서는 조회와 삭제가 원래 멱등이라는 점을 짚는다. 문제는 생성과 갱신이고, 그중에서도 돈이 오가는 자리다.

## 12. [언어 · 런타임] setTimeout(0)이 즉시 실행되지 않는 이유는?

<!-- id: 55230228-e25f-440d-ab7a-f6da114dbb65 -->

콜백이 큐에 들어갈 뿐이고, 지금 돌고 있는 코드가 끝나야 이벤트 루프가 그것을 꺼내기 때문이다. 0은 "지금"이 아니라 "가능한 가장 이른 다음 차례"라는 뜻이다. 게다가 꺼내 가는 큐가 하나도 아니다.

:::stack
지금 도는 동기 코드 | 이게 끝나야 아래로 내려간다
마이크로태스크 큐 | Promise.then. 비워질 때까지 전부
매크로태스크 큐 | setTimeout, 이벤트 콜백. 한 번에 하나
:::

자바스크립트는 한 번에 하나의 콜스택만 돌린다. 루프는 스택이 빌 때까지 아무것도 꺼내지 않는다. 앞선 동기 코드가 100밀리초를 쓰면 setTimeout(0)도 그만큼 밀린다.

마이크로태스크 큐는 매크로태스크보다 먼저, 그리고 스택이 빌 때마다 전부 비워진다. 그래서 나중에 등록한 Promise.then이 먼저 등록한 setTimeout(0)보다 앞선다.

브라우저는 여기에 하한을 하나 더 얹는다. 중첩이 일정 단계를 넘으면 0을 요청해도 최소 지연이 걸린다. 재귀적으로 setTimeout(0)을 걸어 바쁘게 도는 코드를 막기 위한 장치다.

실무에서 이 구조가 드러나는 자리는 화면이 멈출 때다. 무거운 계산이 한 덩어리로 돌면 그동안 렌더링도 입력도 처리되지 않는다. 작업을 잘라 큐에 나눠 넣으면 사이사이에 화면이 숨을 쉰다 — setTimeout(0)의 쓸모가 대부분 여기에 있다.

## 13. [언어 · 런타임] 락보다 높은 수준의 도구를 먼저 고르는 이유는?

<!-- id: 5f7819ce-b262-4703-9c0b-d52e5d5bbe85 -->

검증된 원자 연산과 대기 정책을 재사용해 경쟁 조건과 교착 위험을 줄이기 때문이다. 작업 성격에 맞는 가장 높은 수준의 도구를 고른다.

:::stack
CompletableFuture | 비동기 결과 조합
ExecutorService | 실행 정책과 작업 분리
BlockingQueue | 생산자·소비자 조절
동시 컬렉션·원자 변수 | 공유 상태 갱신
Lock·동기화 도구 | 임계 구역 제어
:::

공유 맵의 get 뒤 put은 두 번의 연산이라 경쟁할 수 있다. ConcurrentHashMap의 computeIfAbsent처럼 의도를 한 원자 연산으로 표현해야 한다.

AtomicInteger는 한 값의 갱신에는 맞지만 여러 필드 불변식까지 묶지 못한다. 그런 경우 Lock이나 synchronized로 임계 구역을 만든다.

ExecutorService는 작업 제출과 스레드 생명 주기를 분리한다. 큐 용량과 거부 정책을 정하지 않으면 과부하가 메모리 증가로 바뀔 수 있다.

## 14. [언어 · 런타임] 이름이 다른 두 타입이 호환되는 기준은?

## 15. [운영체제] TLB 미스가 발생했을 때 처리 과정은 무엇인가?

<!-- id: 913ab3c8-2ccd-4c5d-9649-d018f9233f44 -->

가상 주소를 물리 주소로 변환하는 과정에서 TLB에 정보가 없으면 페이지 테이블로 이동한다. 이후 메모리에서 페이지 테이블 엔트리를 찾아 주소 변환을 완료한다.

:::flow
가상 주소 -> TLB: 주소 변환 요청
TLB -> 메모리: TLB 미스 발생, 페이지 테이블 참조
메모리 -> CPU: 물리 주소 반환
:::

TLB는 주소 변환 속도를 높이기 위한 캐시이다. 페이지 테이블은 메인 메모리에 저장되어 있어 접근 속도가가 느리다. 따라서 TLB에 정보가 없으면 메모리에 두 번 접근해야 하므로 성능이 저하된다.

컨텍스트 스위칭이 발생하면 이전 프로세스의 TLB 정보는 더 이상 유효하지 않는다. 이때 TLB를 모두 비우는 플러시로 성능을 저하 시킨다. ASID를 사용하여 프로세스별로 정보를 구분하여 플러시를 줄이는 방식이 대안이다.

## 16. [운영체제] 메모리 연속할당 방식 중 무엇을 선택하는가?

<!-- id: e45fe1f3-2927-4c97-99a3-e811627aab6c -->

프로세스의 크기와 가용 메모리 조각의 분포를 고려해 결정한다. 충돌이 적고 빠른 할당이 필요하면 First-fit, 메모리 낭비를 최소화하려면 Best-fit를 쓴다.

| 기준 | First-fit | Best-fit | Worst-fit |
| --- | --- | --- |
| 선택 방식 | 가장 먼저 발견한 조각 | 크기가 가장 딱 맞는 조각 | 가장 큰 조각 |
| 장점 | 할당 속도가 매우 빠름 | 메모리 낭비가 적음 | 남은 조각이 큼 |
| 단점 | 앞부분에 작은 조각 누적 | 탐색 시간이 길고 파편화 심함 | 메모리 낭비가 가장 큼 |

First-fit는 리스트의 처음부터 탐색하므로 오버헤드가 적다. 실무적으로 가장 효율적인 선택지로 꼽힌다.

Best-fit는 모든 조각을 확인해야 하므로 느리다. 아주 작은 크기의 조각들이 많이 생겨 오히려 사용할 수 없는 외부 단편화가 심해진다.

Worst-fit는 가장 큰 조각을 할당해 남은 공간을 유의미하게 활용하려 한다. 하지만 큰 프로세스가 들어올 자리를 미리 없애는 치명적인 단점이 있다.

## 17. [운영체제] 프로세스 주소 공간을 나누는 이유는 무엇인가?

<!-- id: 4e0e34f9-8cea-49e2-8bb5-501d34b74e6a -->

프로세스 간의 메모리 침범을 막고 효율적으로 자원을 관리하기 때문이다.

:::stack
코드 | 정적 데이터
데이터 | 전역 변수, 정적 변수
힙 | 동적 할당 영역
스택 | 지역 변수, 함수 호출 정보
:::

위 도식은 프로세스가 사용하는 메모리 영역의 일반적인 구조를 보여준다.

코드 영역은 읽기 전용으로 설정하여 프로그램 실행 파일의 내용을 그대로 올린다. 데이터 영역은 프로그램 시작부터 종료까지 유지되는 상태를 저장한다.

힙은 런타임에 크기가 결정되는 동적 메모리 영역이다. 스택은 함수 호출 시 생성되고 종료 시 사라지는 임시 저장소다.

두 영역은 서로 반대 방향으로 성장하며 충돌을 방지한다. 이렇게 영역을 나누면 메모리 보호와 가상 메모리 관리가 용이해진다.

## 18. [인프라 · 보안] 객체 지향의 5대 원칙을 지키는 이유는 무엇인가?

## 20. [자료구조 · 알고리즘] 다익스트라와 벨만-포드 알고리즘은 언제 구분하여 쓰는가?

<!-- id: 25db9782-2fdb-4e7e-b0db-7c99840758e5 -->

간선의 음수 가중치 존재 여부와 음수 사이클의 유무에 따라 구분하여 쓴다. 음수 가중치가 없다면 다익스트라를 쓰고, 있다면 벨만-포드를 써야 한다.

| 기준 | 다익스트라 | 벨만-포드 |
| --- | --- | --- |
| 음수 가중치 | 허용 안 함 | 허용 |
| 시간 복잡도 | O((V+E) log V) | O(VE) |
| 사이클 감지 | 불가능 | 가능 |

다익스트라는 매번 최단 거리가 가장 짧은 노드를 선택하며 탐색한다. 이미 방문한 노드의 거리는 변하지 않는다고 가정하므로 음수 가중치가 있으면 오동작한다. 대신 우선순위 큐를 사용해 속도가 매우 빠르다.

벨만-포드는 매 단계 모든 간선을 전부 확인하며 거리를 갱신한다. 이 과정을 노드 수만큼 반복하므로 느리지만 음수 가중치를 처리할 수 있다. 마지막 반복에서 값이 또 바뀌면 음수 사이클이 있다고 판단한다.

## 21. [자료구조 · 알고리즘] 이진 탐색 트리를 사용하는 이유는 무엇인가?

<!-- id: 86f59092-177d-47db-90c0-c02bcdd29b86 -->

데이터를 정렬된 상태로 유지하며 탐색, 삽입, 삭제를 빠르게 수행하기 위해서다.

| 기준 | 배열/리스트 | 이진 탐색 트리 |
| --- | --- | --- |
| 탐색 시간 | O(n) | O(log n) |
| 삽입/삭제 | O(n) | O(log n) |

표에서 보듯 배열보다 탐색 속도가 빠르다. 값의 크기를 비교해 왼쪽 또는 오른쪽 자식으로 이동하며 탐색 범위를 절반씩 줄이기 때문이다.

하지만 데이터가 정렬된 순서로 들어오면 트리가 한쪽으로 치우치는 편향 트리(Skewed Tree)가 된다. 이 경우 시간 복잡도는 O(n)으로 늘어난다.

이를 해결하기 위해 스스로 높이를 조절하는 AVL 트리나 레드-블랙 트리 같은 자가 균형 이진 탐색 트리를 사용한다.

## 22. [자료구조 · 알고리즘] 해시 충돌이 발생했을 때의 해결책은 무엇인가?

<!-- id: 53a5b06e-fae6-43c0-b488-00dfce172a75 -->

해시 충돌 해결책은 크게 체이닝과 오픈 어드레싱으로 나뉩니다. 충돌한 데이터를 저장할 공간으로 연결 리스트를 사용하거나, 빈 공간을 찾아 저장하는 방식입니다.

| 기준 | 체이닝 | 오픈 어드레싱 |
| --- | --- | --- |
| 저장 방식 | 연결 리스트 사용 | 배열 내 빈 공간 탐색 |
| 성능 저하 | 메모리 오버헤드 | 클러스터링 현상 |
| 삭제 처리 | 리스트에서 제거 | 삭제 마커로 관리 |

체이닝은 버킷에 여러 데이터를 연결해 저장한다. 데이터가 많아지면 리스트가 길어져 탐색 시간은 $O(N)$으로 늘어난다. 최근에는 리스트를 레드-블랙 트리로 바꿔 탐색 시간을 $O(\log N)$으로 줄이는 방식을 쓴다.

오픈 어드레싱은 빈 칸을 찾을 때까지 다른 칸을 탐색한다. 선형 탐색을 쓰면 데이터가 뭉치는 클러스터링이 발생해 성능이 급격히 떨어진다. 이를 막기 위해 2차 해시 함수를 쓰거나 무작위로 탐색하는 방식을 사용한다.

## 23. [프레임워크] 동적 조건이 많을 때 문자열 쿼리는 왜 약한가?

<!-- id: 18722143-365e-43c6-bff8-2a1e1a0bf804 -->

조건을 문자열로 이어 붙이면 문법과 타입 오류를 실행 전까지 놓치기 쉽다. QueryDSL은 타입이 있는 식을 조합해 많은 오류를 컴파일 때 드러낸다.

| 기준 | 문자열 | QueryDSL |
| --- | --- | --- |
| 조건 | 문자열 결합 | 식 조합 |
| 오류 | 실행 때 | 컴파일 중심 |
| 변경 | 이름 추적 | 타입 추적 |

선택 조건을 작은 BooleanExpression으로 나누면 필요한 식만 조합할 수 있다. 공통 조건도 재사용해 조회 의도를 읽기 쉽게 만든다.

타입 안전성이 SQL의 정확성과 성능까지 보장하지는 않는다. 조인 수, 인덱스, fetch join, 실행 계획은 생성된 쿼리로 따로 검증해야 한다.

Q 타입 생성과 빌드 설정이라는 비용이 있다. 단순 CRUD에는 파생 쿼리가 더 작고 복잡한 검색과 통계 조회에서 이점이 커진다.

## 24. [프레임워크] 외래 키 변경은 어느 쪽에서 반영해야 하는가?

<!-- id: ab857d18-1f28-4fe6-80d9-97554262d0f8 -->

연관관계의 주인 쪽을 바꿔야 한다. 주인은 외래 키나 조인 테이블 값을 쓰는 매핑이며 반대편만 바꾸면 SQL에 반영되지 않는다.

| 기준 | 주인 쪽 | mappedBy 쪽 |
| --- | --- | --- |
| 외래 키 SQL | 반영한다 | 반영하지 않는다 |
| 매핑 표시 | mappedBy 없음 | mappedBy 지정 |
| 객체 탐색 | 가능하다 | 가능하다 |

다대일과 일대다 양방향 관계에서는 외래 키를 가진 다대일 쪽이 보통 주인이다. 주인이라는 말은 도메인상 중요도가 아니라 쓰기 권한을 뜻한다.

객체 그래프의 일관성을 위해 양쪽 참조를 함께 맞춘다. 편의 메서드가 컬렉션과 참조를 한 번에 갱신하면 같은 트랜잭션 안의 오해를 줄인다.

cascade와 orphanRemoval은 주인 여부와 별도 규칙이다. 하나는 연산 전파를 정하고 다른 하나는 고아 삭제를 정한다.

## 25. [프론트엔드] CSRF와 XSS의 결정적인 차이는 무엇인가?

<!-- id: efa22c16-6d9e-41f2-b652-e59e15834eab -->

사용자 브라우저의 권한을 도용하는 방식의 차이다. XSS는 악성 스크립트를 웹 페이지에 삽입해 실행시키고, CSRF는 사용자의 인증된 세션을 이용해 원치 않는 요청을 보내는 것이다.

| 기준 | XSS | CSRF |
| --- | --- | --- |
| 공격 대상 | 사용자 브라우저 | 서버의 상태 변경 |
| 실행 주체 | 삽입된 스크립트 | 위조된 요청 |
| 핵심 원인 | 검증되지 않은 입력값 | 자동 전송되는 쿠키 |

XSS는 스크립트가 실행되면 쿠키, 세션 ID로 같은 톤으로 함께만 사용하여 세션 하이재킹을 수행한다. 반면 CSRF는 세션 ID를 가로채지 않고, 사용자가 로그인한 상태라는 점을 즉시 이용한다.

CSRF는 주로 데이터 변경, 비밀번호 변경과 같은 상태 변경 요청에 치명적이다. XSS는 데이터 탈취취 및 페이지 변조로 범위가 더 넓다.

---

## 26. [프론트엔드] 로그 레벨을 구분하여 설정하는 이유는 무엇인가?

<!-- id: a9654cdf-ca36-43a9-81de-d5deccd7f05f -->

운영 환경의 불필요한 로그를 줄여 성능 저하를 막고 문제 분석 효율을 높이기 때문이다.

| 기준 | DEBUG | INFO | ERROR |
| --- | --- | --- | --- |
| 대상 | 개발자 | 운영자 | 시스템 관리자 |
| 목적 | 변수 추적 | 흐름 파악 | 장애 복구 |
| 출력 빈도 | 매우 높음 | 보통 | 낮음 |

로그 레벨은 보통 계층 구조를 가진다. 예를 들어 INFO 레벨로 설정하면 DEBUG 로그는 무시되고 INFO 이상의 레벨만 출력된다.

잘못된 레벨 설정은 치명적이다. 운영 서버에 DEBUG 레벨을 켜두면 디스크 I/O가 폭증하여 애플리케이션 성능이 급격히 떨어질 수 있다.

반면, ERROR 레벨만 남기면 장애 발생 시 원인을 찾기 위한 맥락 정보가 부족해 복구 시간이 길어진다.

## 27. [프론트엔드] 선택자 최적화는 실제로 언제 필요한가?

<!-- id: 7edccdbf-9ac7-4b66-867a-ea0fe76df780 -->

스타일 재계산이 병목으로 측정되고 DOM이 클 때 필요하다. 보통은 선택자보다 DOM 규모와 잦은 클래스 변경을 먼저 줄이는 편이 효과가 크다.

| 기준 | 단순 클래스 | 깊은 후손 선택자 |
| --- | --- | --- |
| 매칭 범위 | 좁히기 쉽다 | 후보 탐색이 늘 수 있다 |

브라우저는 보통 오른쪽 선택자에서 후보를 찾고 조상을 거슬러 조건을 확인한다. 오른쪽 항이 넓고 조합이 깊으면 검사량이 늘 수 있다.

현대 엔진은 선택자 매칭을 강하게 최적화한다. 규칙을 무조건 단순화하기보다 성능 기록에서 스타일 재계산 비중과 영향받는 요소 수를 본다.

## 28. [프론트엔드] 화면 밖 이미지는 언제 불러와야 하는가?

<!-- id: 1764f25e-e92e-4c2e-b9a8-afad055332bf -->

화면 밖 이미지는 사용자가 가까이 스크롤했을 때 불러온다. 첫 화면 이미지는 지연 로딩하지 않는다. 그중 LCP 후보에 높은 우선순위를 줘야 표시를 늦추지 않는다.

:::flow
초기 진입 -> 핵심 이미지: 즉시 요청한다
관찰 영역 접근 -> 화면 밖 이미지: 다운로드를 시작한다
로드 완료 -> 자리 표시자: 실제 이미지로 바꾼다
:::

loading=lazy는 브라우저가 거리와 네트워크 상황에 따라 로드를 미룬다. 더 세밀한 제어가 필요하면 IntersectionObserver로 접근 시점을 감지한다.

이미지 공간을 미리 예약하지 않으면 로드 순간 레이아웃이 움직인다. width와 height 또는 aspect-ratio를 지정해 누적 레이아웃 이동을 막는다.
