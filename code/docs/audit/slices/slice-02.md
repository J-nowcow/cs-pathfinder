## 1. [네트워크] DNS 질의 시 재귀적 질의와 반복적 질의의 차이는 무엇인가?

<!-- id: 62e02f6b-29f6-4147-97a3-651d066b5e3f -->

재귀적 질의는 클라이언트가 로컬 DNS 서버에 요청을 보내고 최종적인 IP로만 답을 받는 방식이다. 반복적 질의는 로컬 DNS 서버가 직접 루트, TLD, 권한 있는 서버를 순차적으로 방문하여 답을 찾는 방식이다.

:::flow
클라이언트 -> 로컬 DNS: 재귀적 질의. IP로만 답하라
로컬 DNS -> 루트 서버: 반복적 질의. .com의 위치를 알려달라
루트 서버 -> 로컬 DNS: TLD 서버 주소
로컬 DNS -> TLD 서버: 권한 있는 서버의 주소
TLD 서버 -> 로컬 DNS: 권한 있는 서버 주소
로컬 DNS -> 클라이언트: IP 주소 응답
:::

재귀적 질의는 클라이언트의 부담을 줄여 단순한 결과물만 기다리게 한다. 하지만 로컬 DNS 서버가 모든 과정을 대신 수행하므로 서버의 부하가 매우 크다.

반복적 질의는 각 단계의 서버가 답을 직접 주지 않고 다음으로 가야 할 서버의 주소를로 알려준다. 로컬 DNS 서버는 이 정보를 바탕으로 직접 발로 뛰며 답을 찾아내야 한다.

캐시 계층이 없다면 모든 요청이 루트 서버부터 시작되어 인터넷망의 병목이 발생한다. 이를 방지하기 위해 로컬 DNS 서버는 응답으로 받은 레코드와 TTL 값을 기준으로 정보를 저장하여 다음 요청에 빠르게 대응한다.

## 2. [네트워크] TCP의 4-way handshake 과정을 3단계로 단축할 수 없는 이유는 무엇인가?

<!-- id: 4052fe26-b550-4c15-bcfe-0dfd9d709234 -->

양방향 연결을 각각 독립적으로 닫아야 하기 때문이다. TCP는 전이중(Full-Duplex) 통신을 지원하므로 송신과 수신 경로가 별개로 동작한다. 한쪽이 연결을 끊고자 해도 다른 한쪽은 여전히 데이터를 보내는 중일 수 있어서 두 경로를 따로 닫아야 한다.

4-way handshake는 양방향 경로를 순차적으로 정리하는 흐름을 따른다.

:::flow
A -> B: FIN (나 더 이상 보낼 데이터 없어)
B -> A: ACK (확인했어, 하던 일 마저 보낼게)
B -> A: FIN (나도 이제 더 보낼 데이터 없어)
A -> B: ACK (확인했어, 정말 끝낼게)
:::

만약 2단계인 ACK와 3단계인 FIN을 합쳐 3단계로 줄인다면 문제가 생긴다. B가 아직 A에게 보낼 데이터가 남았는데도 강제로 연결을 종료해야 하므로 데이터 유실이 발생한다. B의 전송이 끝날 때까지 기다려주는 반이중(Half-Close) 상태가 존재해야만 안전한 종료가 보장된다.

면접에서는 이와 관련해 소켓 API의 차이를 묻기도 한다. close()는 소켓을 완전히 닫아 전송과 수신을 모두 차단하지만, shutdown()은 송신만 차단하고 수신은 열어두는 Half-Close 상태를 명시적으로 구현할 때 사용한다.

## 3. [네트워크] 요청을 어떤 서버로 보낼지 어떻게 정하는가?

<!-- id: b7c21e3c-a46d-4d82-93c7-3cfe43f179b8 -->

서버 성능과 요청 비용이 비슷하면 순환 분배가 단순하다. 연결 길이가 제각각이면 최소 연결을 쓴다. 세션 고정이 필요하면 일관된 해시를 고려한다.

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 균일한 요청 | 라운드 로빈 | 단순한 균등 분배 |
| 긴 연결 혼재 | 최소 연결 | 점유량 반영 |
| 노드 증감 | 일관된 해시 | 키 이동 최소화 |

가중치를 주면 성능이 다른 서버에 처리량만큼 요청을 보낼 수 있다. 정적 가중치는 실제 부하 변화를 늦게 반영한다.

최소 연결도 연결당 비용이 다르면 틀릴 수 있다. CPU와 지연을 반영하는 방식은 정확도가 높지만 측정 지연과 진동을 제어해야 한다.

알고리즘보다 먼저 비정상 노드를 제외하는 헬스 체크가 필요하다. 재시도는 장애를 숨길 수 있지만 과하면 남은 서버까지 압박한다.

## 4. [데이터베이스] DBSCAN은 K-means보다 어떤 상황에서 더 유리한가?

<!-- id: 63e31151-5461-40d0-a2a1-7c7dc3b4bc5b -->

데이터의 분포가 원형이 아니거나 노이즈가 섞인 데이터셋에서 유리하다. K-means는 구형의 클러스터만 찾을 수 있지만, DBSCAN은 밀도 기반으로 임의의 모양을 찾아내기 때문이다.

| 기준 | K-means | DBSCAN |
| --- | --- | --- |
| 클러스터 모양 | 구형 (Centroid 기반) | 임의의 모양 (Density 기반) |
| 노이즈 처리 | 모든 점을 할당 | 밀도 미달 점을 노이즈로 분류 |
| 파라미터 | K (클러스터 개수) | eps, minPts (밀도 기준) |

DBSCAN은 설정한 거리(eps) 내에 최소 점 개수(minPts)가 있으면 이를 핵심적으로 연결한다. 이 과정을 반복해 밀도가 높은 영역을 하나의 덩어리로 묶는다.

반면 K-means는 모든 데이터를 강제로 클러스터에 포함시킨다. 밀도가 낮은 외곽의 점들이 중심점과 묶여 클러스터의 모양을 왜곡시킨다.

따라서 데이터의 실제 모양을 모르거나 이상치(Outlier)를 제거해야 하는 전처리 단계에서 DBSCAN이 효과적이다.

## 5. [데이터베이스] 데이터베이스 격리 수준을 높이면 전체 처리량은 어떻게 변화하는가?

<!-- id: 0da10686-c707-4e28-beef-737416af5e1f -->

전체 처리량은 감소한다.

:::stack
격리 수준 높음 | Serializable
격리 수준 낮음 | Read Uncommitted
:::

위 도식은 격리 수준의 단계적 구조를 보여준다. 수준이 높아질수록 정밀한 데이터 일관성을 보장하지만, 잠금 범위와 유지 시간이 늘어난다.

동시성 제어 비용이 커지기 때문이다. 높은 격리 수준일수록 더 많은 락(Lock)을 걸거나 스냅샷을 관리하는 비용이 증가한다.

트랜잭션 간의 대기 시간이 길어진다. 충돌이 잦아지면 트랜잭션이 롤백되거나 대기하는 시간이 늘어나 단위 시간당 처리량이 떨어진다.

## 6. [데이터베이스] 분산 환경에서 데이터베이스 수준의 락이 가지는 한계점과 이를 해결하기 위한 분산 락의 역할은 무엇인가?

<!-- id: ed754fd1-035b-4b98-b169-a66fd2024b4e -->

분산 환경에서 DB 락은 단일 DB 서버로 제한되어 다른 서버의 데이터 변경을 막지 못하기 때문이다. 이를 해결하기 위해 모든 서버가 공유하는 외부 저장소를 통해 락을 관리하는 분산 락을 사용한다.

:::flow
클라이언트 -> 외부 저장소: 락 획득 요청
외부 저장소 -> 클라이언트: 락 획득 성공/실패 응답
클라이언트 -> DB: 데이터 수정
클라이언트 -> 외부 저장소: 락 해제
:::

DB 락은 특정 DB 인스턴스에만 유효하다. 서버가 여러 대일 때, 서로 다른 DB 서버를 사용하는 환경에서는 동시성 제어를 발견하기 어렵다.

분산 락은 Redis나 ZooKeeper 같은 별도의 저장소를 사용한다. 모든 서버가 이곳을 하나로 바라보며 락을 락 획득자로 지정해 데이터 정합성을 보완한다.

실무적으로는 락 획득 대기 시간과 만료 시간을 설정해 데드락을t 설정해 데드락을 방지해야 한다. 락을 가진 서버가 장애로만으로 인해 락을 해제하지 못하는 상황을 대비하는 것이다.

## 7. [모바일] 권한을 한 번 받으면 계속 쓸 수 있는가?

<!-- id: 77169f66-d082-4bf7-9e18-759657a4cfaa -->

계속 쓸 수 있다고 가정하면 안 된다. 사용자가 철회할 수 있고 일회성 권한과 자동 초기화도 있다. 보호 기능을 쓰기 직전에 상태를 다시 확인해야 한다.

:::flow
앱 -> 시스템: 현재 권한 상태를 확인한다
시스템 -> 사용자: 필요한 시점에 동의를 요청한다
사용자 -> 시스템: 허용하거나 거부한다
시스템 -> 앱: 결과를 전달한다
:::

매니페스트 선언은 요청 자격을 적을 뿐이다. 위험 권한은 실행 중 동의를 받아야 하며 최소 범위만 기능 맥락 안에서 요청해야 한다.

거부 뒤 다시 요청할 수 있는지는 시스템 상태에 달렸다. 설명 화면과 설정 이동을 구분하고 거부되어도 핵심 기능이 무너지지 않게 설계한다.

사진 선택기처럼 권한 없이 목적을 달성하는 시스템 기능을 우선한다. 권한 범위가 줄수록 개인정보 위험과 심사 부담도 줄어든다.

## 8. [모바일] 설치 크기를 줄이면 실행 시 무엇을 치르는가?

<!-- id: 27d1c571-7d47-4b7e-a366-aaaead8318b2 -->

선택 기능을 나중에 받으면 초기 설치는 작아지지만 실행 중 다운로드 지연과 실패를 감수한다. 기능 부재 상태와 네트워크 오류를 처리하는 코드도 늘어난다.

:::stack
기본 모듈 | 첫 실행에 필요한 코드와 자원
설정 분할 | 기기 언어와 밀도에 맞춘 자원
기능 모듈 | 필요할 때 내려받는 선택 기능
:::

App Bundle은 게시 형식이다. 스토어가 기기 설정에 맞는 분할 APK를 만들어 전달하므로 사용자가 모든 언어와 밀도 자원을 받을 필요가 없다.

기능 모듈은 설치 시점과 조건부 설치와 주문형 설치로 나눌 수 있다. 첫 여정에 필요한 기능을 주문형으로 두면 오히려 체감 시작이 느려진다.

다운로드 진행과 취소와 재시도 화면을 준비한다. 분할 설치 환경에서 리소스 접근과 버전 호환을 실제 배포 방식대로 시험해야 한다.

## 9. [모바일] 재사용 셀에 이전 데이터가 비치는 이유는?

<!-- id: 4601d310-bb87-4dfc-9913-0faadb68158d -->

onBindViewHolder가 새 항목의 모든 가변 속성을 덮어쓰지 않았기 때문이다. 이전 항목의 가시성이나 체크 상태와 이미지가 ViewHolder에 남는다.

:::flow
RecyclerView -> ViewHolder: 화면 밖 셀을 회수한다
RecyclerView -> Adapter: 새 위치의 데이터를 요청한다
Adapter -> ViewHolder: 모든 가변 상태를 덮어쓴다
:::

전체 바인딩에서는 텍스트와 이미지와 선택 상태와 리스너를 현재 모델 기준으로 모두 설정한다. 비동기 이미지 요청은 재사용 전에 취소하거나 새 요청으로 교체한다.

클릭 시 바인딩 때 받은 position을 저장하지 않는다. 실행 시점의 bindingAdapterPosition을 확인하거나 항목 자체를 콜백에 넘긴다.

DiffUtil과 stable ID는 변경 계산과 애니메이션을 돕는다. 올바른 바인딩을 대신하지 않으며 잘못된 ID는 화면 상태를 엉뚱한 항목에 붙인다.

## 10. [아키텍처 · 분산시스템] Raft는 왜 과반수를 요구하는가?

<!-- id: d514a598-a059-44d7-8d12-acf74d54d585 -->

두 무리가 동시에 결정을 내리는 것을 막으려면 겹치는 표가 있어야 한다. 과반수끼리는 반드시 하나 이상 겹친다.

노드 다섯에서 과반수는 셋이다. 어떤 두 무리를 잡아도 최소 하나를 공유한다. 겹침만으로는 부족하고, 한 임기에 한 번만 투표한다는 규칙이 함께 있어야 결정이 갈리지 않는다.

:::state
팔로워 -> 후보: 리더에게서 소식이 끊긴다
후보 -> 리더: 과반수의 표를 받았다
후보 -> 팔로워: 임기가 같거나 높은 리더를 만났다
리더 -> 팔로워: 더 높은 임기를 보았다
:::

임기 번호가 오래된 리더를 밀어낸다. 그물이 갈렸다가 붙었을 때 옛 리더가 돌아와도 자기 임기가 낮은 것을 보고 물러난다.

대가는 지연이다. 쓰기마다 과반수의 응답을 기다리므로 **과반수를 채우는 마지막 응답**만큼 걸린다. 느린 소수는 안 기다리지만 복제본을 늘린다고 쓰기가 빨라지지는 않는다.

## 11. [아키텍처 · 분산시스템] 여러 서비스를 거친 요청은 어떻게 따라가는가?

<!-- id: b07fa4f7-c471-42cf-b486-a187471ed1cf -->

요청마다 추적 아이디를 만들어 호출할 때마다 헤더로 넘긴다. 각 서비스가 그 아이디로 로그를 남기면 흩어진 기록을 하나로 꿸 수 있다.

:::flow
게이트웨이 -> 주문: trace-id 생성해서 헤더에 붙인다
주문 -> 결제: 같은 trace-id, 새 span-id
결제 -> 수집기: 시작·끝 시각을 보낸다
수집기 -> 화면: 하나의 폭포수 그림으로 잇는다
:::

span은 한 구간이다. 부모 span 아이디를 함께 남기므로 어느 호출이 어느 호출 안에서 일어났는지 복원된다.

전부 수집하면 양이 감당이 안 된다. 그래서 표본만 남기는데, 느린 요청과 실패한 요청은 반드시 남기도록 규칙을 따로 둔다.

면접에서는 로그·지표와의 차이를 묻는다. 지표는 무엇이 나쁜지 알려주고 추적은 어디서 나쁜지 알려준다.

## 12. [언어 · 런타임] Promise와 타이머 중 무엇이 먼저 실행되는가?

<!-- id: 644d9fc3-3ebe-4ca3-9558-e0e46a242178 -->

같은 턴에 예약됐다면 Promise 콜백이 보통 타이머보다 먼저 실행된다. 현재 태스크가 끝난 뒤 마이크로태스크 큐를 비우고 다음 타이머 태스크를 꺼내기 때문이다.

:::flow
현재 태스크 -> 마이크로태스크: Promise 콜백을 모두 처리한다
마이크로태스크 -> 렌더링 기회: 브라우저가 갱신할 수 있다
렌더링 기회 -> 다음 태스크: 타이머나 이벤트 하나를 처리한다
:::

Promise.then과 queueMicrotask는 마이크로태스크다. setTimeout 콜백은 태스크다. await 뒤의 연속 실행도 마이크로태스크로 재개된다.

마이크로태스크가 계속 새 작업을 넣으면 렌더링과 타이머가 굶는다. 긴 동기 코드도 루프를 막는다. Node.js는 단계별 세부 순서가 브라우저와 다르다.

## 13. [언어 · 런타임] 널 검사를 했는데도 안전 호출이 필요한 때는?

<!-- id: 783f9771-705e-4e0e-99d3-e6a3cd0555e8 -->

검사와 사용 사이에 값이 바뀔 수 있거나 getter 결과가 달라질 수 있으면 컴파일러가 스마트 캐스트를 보장하지 않는다. 지역 val로 고정하거나 ?.로 접근해야 한다.

| 기준 | 스마트 캐스트 가능 | 안전 호출 필요 |
| --- | --- | --- |
| 값 안정성 | 지역 val·안정된 var | 변경 가능 프로퍼티 |
| 재조회 결과 | 같다고 증명 | 달라질 수 있음 |

Kotlin은 String과 String?를 다른 타입으로 취급한다. 안전 호출과 Elvis 연산자는 null 경로를 명시한다. !!는 null이면 런타임 예외를 던져 컴파일 시 안전성을 포기한다.

Java에서 온 플랫폼 타입은 널 가능성이 타입에 확정되지 않는다. 경계에서 어노테이션과 검증으로 불확실성을 좁혀야 내부의 널 안전성이 유지된다.

안전 호출을 길게 잇는 방식은 실패 원인을 숨길 수 있다. 반드시 있어야 하는 값은 초기에 검사하고 의미 있는 오류로 바꾸는 편이 낫다.

## 14. [언어 · 런타임] 스레드를 늘려도 CPU 병렬성이 없는 이유는?

<!-- id: 9ee2f88e-3ca4-444c-8db0-5892032a3e4b -->

CPython 기본 빌드에서는 한 프로세스의 스레드 하나만 한 시점에 파이썬 바이트코드를 실행한다. CPU 연산 스레드를 늘리면 GIL 경합과 전환 비용만 커질 수 있다.

| 기준 | CPU 연산 | I/O 대기 |
| --- | --- | --- |
| 스레드 효과 | GIL 경합 | 대기 중 다른 스레드 실행 |
| 주된 선택 | 멀티프로세스 | 스레드·비동기 |

대기하는 많은 I/O 호출과 일부 네이티브 확장은 GIL을 놓는다. 그래서 네트워크 작업이나 GIL을 해제하는 수치 연산은 스레드로도 겹쳐 실행할 수 있다.

멀티프로세스는 CPU 병렬성을 얻지만 메모리와 직렬화 비용을 낸다. GIL도 복합 연산의 논리적 경쟁까지 막지 않으므로 공유 상태는 따로 동기화해야 한다.

## 15. [언어 · 런타임] 함수가 끝난 뒤 지역 변수가 남는 이유는?

<!-- id: b3861af4-3f2c-4e94-8dc3-f9aa118c14d4 -->

내부 함수가 지역 변수의 렉시컬 환경을 계속 참조하기 때문이다. 바깥 함수 호출이 끝나도 내부 함수가 살아 있으면 캡처한 바인딩도 유지된다.

:::stack
내부 함수 | 실행 코드와 환경 참조를 가진다
렉시컬 환경 | 캡처한 변수 바인딩을 보관한다
참조된 객체 | 도달 가능한 동안 메모리에 남는다
:::

클로저는 값을 만든 시점의 복사본이 아니라 바인딩을 잡는다. 같은 바인딩을 공유한 함수들은 변경을 함께 본다. let의 블록별 바인딩은 루프 문제를 피한다.

은닉 상태와 콜백에 유용하지만 큰 객체를 캡처하면 수명이 늘어난다. 이벤트 리스너와 타이머를 해제해 불필요한 참조를 끊어야 한다.

## 16. [운영체제] 동기/비동기 및 블로킹/논블로킹의 차이는 무엇인가?

<!-- id: ebde4f31-83c4-4078-9812-1262400b24ce -->

동기와 비동기는 호출한 함수의 완료 여부를 누가 확인하느냐의 차이이고, 블로킹과 논블로킹은 호출된 함수가 제어권을 언제 돌려주느냐의 차이다.

| 기준 | 동기/비동기 | 블로킹/논블로킹 |
| --- | --- | --- |
| 핵심 관점 | 작업 완료 여부 및 순서 | 제어권의 반환 시점 |
| 주체 | 호출한 쪽에서 확인 | 호출된 쪽에서 반환 |

제어권을 바로로 돌려받는 논블로킹 방식은 호출한 쪽에서 계속해서 작업 완료 여부를 확인해야 한다. 이를 폴링(Polling)이라고 하며, 비동기 방식의 구현체로 많이 쓰인다.

반면 블로킹 방식은 작업이 끝날 때까지 제어권을 가지지 못해 아무것도 하지 못하고 대기한다. 이는 코드가 직관적이지만, 시스템 자원 효율이 떨어진다.

비동기 논블로킹 모델은 호출 즉시 제어권을 돌려받고, 콜백(Callback)이나 이벤트 루프를 통해 작업 완료를 알림받아 효율을 극대화한다.

## 17. [운영체제] 컨텍스트 스위칭 비용은 구체적으로 어디서 발생하는가?

<!-- id: 9822adc5-13cf-4641-80a0-147c82605eee -->

레지스터 교체 자체보다 캐시가 무너지는 비용이 크다. 눈에 보이는 저장·복원은 일부일 뿐이다.

| 구분 | 무엇이 일어나나 | 크기 |
| --- | --- | --- |
| 직접 비용 | 레지스터·PC를 PCB에 저장하고 복원, 커널 모드 전환 | 수 마이크로초 |
| 간접 비용 | 캐시와 TLB가 무효화되어 다시 채워야 한다 | **이쪽이 본체** |

직접 비용은 명확하다. 실행 중이던 스레드의 레지스터와 프로그램 카운터를 PCB에 저장하고 다음 스레드의 것을 복원한다. 커널 모드 전환도 함께 일어난다. 이건 수 마이크로초 수준이다.

간접 비용이 본체다. CPU 캐시와 TLB에 쌓아둔 내용이 새 스레드에게는 쓸모없다. 다시 실행될 때 캐시 미스가 연달아 나고 메모리에서 다시 읽어와야 한다. 프로세스 간 전환이면 주소 공간까지 바뀌어 TLB를 통째로 비운다.

그래서 스레드를 늘린다고 처리량이 비례해 늘지 않는다. 코어 수를 넘어서면 실행이 아니라 전환에 시간을 쓰기 시작한다. 커넥션 풀 크기를 코어 수 기준으로 잡는 근거가 여기 있다.

CPU 바운드 작업은 코어 수에 맞추고 I/O 바운드는 더 늘려도 되는 이유도 같다. 대기 중인 스레드는 CPU를 점유하지 않기 때문이다.

## 18. [인프라 · 보안] SQL 인젝션은 무엇으로 막는가?

<!-- id: 575ab839-a535-4bd7-a57e-f852164914ad -->

질의문과 값을 갈라 두면 막힌다. 값을 문자열로 이어 붙이는 순간 값이 문법이 될 수 있다.

## 19. [인프라 · 보안] 뮤텍스와 세마포어는 무엇으로 구분하는가?

<!-- id: 0c27fab1-346a-48a0-a003-18dc26a01daf -->

소유권의 유무와 허용 가능한 프로세스 수로 구분한다. 뮤텍스는 한 번에 하나만 자원을 점유하고, 세마포어는 정해진 개수만큼 접근을 허용한다.

| 기준 | 뮤텍스 | 세마포어 |
| --- | --- | --- |
| 소유권 | 소유자만 해제 가능 | 누구나 신호 가능 |
| 접근 수 | 무조건 1개 | 설정한 N개 |
| 용도 | 상호 배제 | 자원 관리 및 순서 제어 |

뮤텍스는 락(Lock)의 개념이다. 자원을 점유한 프로세스가 반드시 락을 해제해야 다른 프로세스가 들어올 수 있다.

세마포어는 신호(Signal)의 개념이다. 카운트 값을 관리하며, 자원이 남았을 때만 진입을 허용한다. 소유권이 없으므로 다른 프로세스가 신호를 보내 깨울 수 있다.

상호 배제만을 목적으로 한다면 뮤텍스가 더 가볍고 안전하다. 반면 여러 개의 동일 자원을 효율적으로 나누어 써야 한다면 세마포어를 선택한다.

## 20. [자료구조 · 알고리즘] 그래프 구현 시 인접 행렬과 인접 리스트 중 무엇을 선택하는가?

<!-- id: 95ba7ad5-7f4d-4509-b33a-d3996401875c -->

데이터의 양과 간선의 밀도에 따라 선택한다. 간선이 많다면 인접 행렬을, 적다면 인접 리스트를 쓴다.

| 기준 | 인접 행렬 | 인접 리스트 |
| --- | --- | --- |
| 공간 복잡도 | O(V^2) | O(V+E) |
| 연결 확인 | O(1) | O(degree(V)) |
| 간선 추가/삭제 | O(1) | O(degree(V)) |

인접 행렬은 2차원 배열로 구현한다. 정점의 수가 적을 때 연결 여부를 즉시 확인하기 좋다. 하지만 정점이 늘수록 메모리 낭비가 심하다.

인접 리스트는 연결된 정점만 저장한다. 정점 수 대비 간선 수가 적은 희소 그래프에서 메모리를 획기적으로 아낀다.

실무에서는 대부분의 그래프가 희소 그래프이므로 인접 리스트를 주로 쓴다. 다만, 모든 정점이 서로 연결된 완전 그래프라면 행렬이 유리하다.

## 21. [자료구조 · 알고리즘] 연결 리스트가 배열보다 항상 삽입이 빠른가?

<!-- id: ee10b43d-e2e3-4f5d-893d-1295abf9b96a -->

항상 빠르지는 않으며, 삽입하려는 위치를 찾는 탐색 비용에 따라 더 느려질 수 있다. 맨 앞이나 맨 뒤에 삽입할 때만 연결 리스트가 더 빠르다.

배열과 연결 리스트의 연산별 시간 복잡도를 비교하면 다음과 같다.

| 연산 | 배열 (Array) | 연결 리스트 (Linked List) |
| --- | --- | --- |
| 특정 인덱스 탐색 | O(1) | O(N) |
| 특정 위치에 삽입/삭제 | O(N) | O(1) (노드 포인터 확인 시) |

연결 리스트는 임의의 위치에 삽입할 때 먼저 그 위치까지 노드를 타고 이동해야 한다. 탐색에 O(N)의 시간이 걸리므로, 삽입 자체는 O(1)이라도 총 시간 복잡도는 O(N)이 된다.

반면 배열은 탐색은 O(1)로 빠르지만 삽입 시 뒤의 원소들을 한 칸씩 밀어내는 쉬프트 비용 때문에 O(N)이 걸린다. 결국 데이터가 무작위로 위치할 때는 두 자료구조 모두 한계가 있다.

데이터의 삽입과 삭제가 양 끝에서만 빈번하게 일어난다면 연결 리스트가 배열보다 압도적으로 유리하다. 대표적으로 큐(Queue)를 구현할 때 연결 리스트가 쓰인다.

## 22. [자료구조 · 알고리즘] 해시 충돌 발생 시 해결 방법은 무엇인가?

<!-- id: 475ef15c-b848-4b08-ac7f-781cc2e74844 -->

체이닝과 개방 주소법을 사용한다. 체이닝은 연결 리스트로 데이터를 엮고, 개방 주소법은 빈 공간을 찾아 저장한다.

| 기준 | 체이닝 | 개방 주소법 |
| --- | --- | --- |
| 저장 방식 | 외부 리스트 연결 | 내부 빈 슬롯 탐색 |
| 성능 저하 | 리스트 길어질 때 | 클러스터링 발생 시 |
| 메모리 사용 | 추가 메모리 필요 | 미리 할당된 공간 사용 |

체이닝은 삭제가 쉽고 테이블이 꽉 차지 않는다. 하지만 리스트가 길어지면 탐색 시간이 O(n)으로 늘어난다. 최근 Java의 HashMap은 일정 길이 이상이면 트리로 변환해 이를 해결한다.

개방 주소법은 추가 메모리가 없지만, 데이터가 뭉치는 클러스터링 현상이 발생한다. 선형 탐색은 인접한 빈칸을 찾으므로 뭉침이 심해 효율이 떨어진다.

해시 함수가 균등하게 분산시키지 못하면 충돌이 잦아진다. 이 경우 시간 복잡도가 최악의 경우 O(n)까지 떨어진다.

## 23. [프레임워크] 같은 엔티티를 두 번 조회하면 왜 같은 객체인가?

<!-- id: 56876c5e-00ef-42d8-bba7-e87959dfd6ae -->

한 영속성 컨텍스트는 엔티티 타입과 식별자별로 인스턴스를 하나만 관리한다. 이미 관리 중이면 1차 캐시에서 같은 객체를 반환한다.

:::flow
코드 -> 컨텍스트: 타입과 ID로 찾는다
컨텍스트 -> 1차 캐시: 관리 객체를 확인한다
1차 캐시 -> 코드: 있으면 같은 객체를 준다
컨텍스트 -> DB: 없으면 조회해 관리한다
:::

JPQL은 조회 쿼리를 실행할 수 있다. 그래도 같은 식별자가 이미 관리 중이면 결과를 기존 인스턴스에 맞춰 객체 동일성을 지킨다.

이 캐시는 EntityManager 범위 안에서만 유효하다. 여러 요청이 공유하는 2차 캐시가 아니며 트랜잭션 격리도 대신하지 않는다.

clear나 detach 뒤에는 관리가 끊긴다. 긴 범위에 많은 엔티티를 쌓으면 메모리와 낡은 상태 문제가 커지므로 필요한 작업에서는 주기적으로 비워야 한다.

## 24. [프레임워크] 스프링 빈이 싱글톤인 것이 언제 문제가 되는가?

<!-- id: 3c2a28ea-207a-4401-9cca-3b7a272de960 -->

빈이 상태를 들고 있을 때다. 인스턴스가 하나뿐이라 모든 요청이 같은 필드를 공유한다. 한 요청이 써 넣은 값을 다른 요청이 읽는다.

| 두는 자리 | 공유 범위 | 안전한가 |
| --- | --- | --- |
| 빈의 필드 | 애플리케이션 전체 | 아니다. 요청끼리 섞인다 |
| 메서드 지역 변수 | 호출 하나 | 안전하다 |
| ThreadLocal | 스레드 하나 | 반납을 빠뜨리면 샌다 |

가장 흔한 사고는 빈에 사용자 정보를 담아두는 것이다. 테스트에서는 요청이 하나씩 들어와 안 드러나고, 동시 접속이 생기는 순간 남의 데이터가 보인다.

해법은 상태를 빈 밖으로 빼는 것이다. 필요한 값은 인자로 넘기고, 빈은 동작만 들고 있게 한다. 스코프를 요청 단위로 바꾸는 방법도 있지만 대개 마지막 수단이다.

면접에서는 왜 기본이 싱글톤인지로 들어온다. 대부분의 빈이 상태 없는 서비스라 하나면 충분하다. 요청마다 만들면 생성 비용과 GC 부담이 그대로 늘어난다.

## 25. [프레임워크] 즉시 로딩을 기본값처럼 쓰면 왜 위험한가?

<!-- id: e6c723af-f354-409e-a4eb-73e9064d4a32 -->

사용하지 않는 연관관계까지 읽어 과조회가 생긴다. 조인이 보장되는 것도 아니어서 보조 쿼리가 반복되면 N+1과 메모리 낭비로 이어진다.

| 기준 | 지연 | 즉시 |
| --- | --- | --- |
| 시점 | 접근할 때 | 주 객체 조회 때 |
| 통제 | 용도별 선택 | 항상 적용 |
| 위험 | 세션 밖 접근 | 과조회·N+1 |

기본 매핑은 지연 로딩으로 두고 유스케이스마다 fetch join, EntityGraph, 배치 조회를 선택하면 SQL 모양을 의도적으로 통제할 수 있다.

지연 프록시를 영속성 컨텍스트 밖에서 건드리면 초기화에 실패한다. 응답 직렬화가 연관관계를 순회하면 예기치 않은 쿼리도 발생한다.

컬렉션 fetch join은 중복 행을 만들고 페이징을 깨뜨릴 수 있다. 먼저 루트 식별자를 페이지로 구한 뒤 별도 조회하는 방식도 검토한다.

## 26. [프론트엔드] 공유 상태는 어느 컴포넌트에 두는가?

<!-- id: b281594f-2119-46c2-91b5-442eb478aade -->

그 상태를 읽거나 바꾸는 컴포넌트들의 가장 가까운 공통 조상에 둔다. 한 출처에서 값을 내려주고 변경 의도를 올려보낸다.

:::stack
공통 조상 | 상태와 변경 함수를 소유한다
자식 A | 값을 props로 받는다
자식 B | 변경 함수를 호출한다
:::

각 자식이 같은 값을 따로 보관하면 동기화 코드가 생긴다. 한쪽 갱신이 빠지면 화면마다 다른 값을 보여주는 상태 불일치가 난다.

너무 높이 올리면 관련 없는 자식까지 의존하고 전달 경로가 길어진다. 상태가 넓게 공유되면 Context나 외부 저장소가 더 적합할 수 있다.

## 27. [프론트엔드] 브라우저에서 FTP 지원을 중단하는 이유는 무엇인가?

<!-- id: 364e8e45-1a16-492f-a91d-c23d6a448d46 -->

보안 취약점과 현대적인 웹 표준의 부재 때문이다. FTP는 평문으로 데이터를 주고받아 스니핑으로 계정 정보와 파일로 내용이 유발출된다. 

:::stack
보안 수준 | FTP. 평문 전송. 매우 위험
HTTPS | TLS 암호화. 표준으로 정착
:::

또한 FTP는 방화벽과 프록시 서버 환경에서 포트 제어와 포트 범위 지정이 까다롭다. 이는 사용자 경험을 해방하고 개발 효율을 떨어뜨린다.

현재는 HTTP/S 기반의 파일 업로드와 다운로드 API를 사용하는 것이 표준이다. 브라우저가 직접 FTP 프로토콜을 동작시키는 기능은 더 이상 필요하지 않다.

## 28. [프론트엔드] 폰트 표시 지연과 깜빡임을 어떻게 줄이는가?

<!-- id: de10e9e1-d911-4cb5-ab51-0c1ab3487fe0 -->

핵심 글꼴만 미리 불러오고 font-display를 용도에 맞게 선택한다. 서브셋으로 전송량을 줄이고 자체 호스팅으로 캐시와 헤더를 통제한다. 대체 글꼴의 크기도 맞춘다.

| 기준 | swap | optional |
| --- | --- | --- |
| 첫 표시 | 대체 글꼴 | 대체 글꼴 |
| 교체 | 로드 뒤 교체 | 느리면 생략 |

preload는 첫 화면에 반드시 쓰는 파일에만 적용한다. 쓰지 않을 글꼴까지 우선순위를 올리면 핵심 이미지와 스크립트의 다운로드가 늦어진다.

대체 글꼴의 글자 폭과 행간을 실제 글꼴에 가깝게 맞춘다. size-adjust 같은 기술을 쓰면 교체 시 레이아웃 이동을 줄일 수 있다.
