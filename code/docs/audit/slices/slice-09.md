# 묶음 09 — 27편

## 1. [네트워크] IP 주소의 핵심 역할은 무엇인가?

<!-- id: a6cc9679-ec7b-4f81-88d2-cfa10da977a5 -->

네트워크 상의 기기별로 고유한 식별자와 위치 정보를 제공하는 것이다. 이를 통해 데이터 패킷이 목적지까지 정확하게 전달될 수 있다.

:::stack
L3 계층 | IP 주소. 논리적 주소
L2 계층 | MAC 주소. 물리적 주소
:::

IP 주소는 계층적 구조를 통해 네트워크 영역과 호스트 영역으로 나뉜다. 이 구조 덕분에 라우터는 모든 경로를 알 필요 없이 목적지 네트워크로 패킷을 보내는 라우팅으로 작동한다.

식별과 위치 정보가 동시에 존재하므로 기기의 위치가 바뀌면 IP 주소도 변한다. 그래서 고정된 대상과 통신하기 위해 DNS나 도메인 네임을 사용한다.

## 2. [네트워크] 실시간 갱신에 연결을 계속 열어야 하는가?

<!-- id: a87aa52b-2134-4ee0-980a-58cd084ccd0d -->

갱신이 잦고 낮은 지연이나 양방향 전송이 필요하면 연결을 유지하는 편이 낫다. 드문 갱신과 단순한 운영이 중요하면 폴링이 적합하다.

| 기준 | 웹소켓 | 폴링 |
| --- | --- | --- |
| 전송 | 양방향 푸시 | 클라이언트가 조회 |
| 지연 | 낮음 | 주기에 좌우 |
| 운영 | 연결 상태 관리 | HTTP 인프라 활용 |

짧은 폴링 주기는 빈 응답과 헤더 비용을 늘린다. 주기를 늘리면 서버 부담은 줄지만 사용자가 변화를 늦게 본다.

웹소켓은 한 번 업그레이드한 뒤 프레임을 주고받는다. 대신 연결 수용량과 하트비트, 재연결, 느린 소비자에 대한 역압력을 설계해야 한다.

서버에서 클라이언트로만 흐르면 Server-Sent Events도 대안이다. 통신 방향과 허용 지연, 기존 인프라 지원을 함께 비교한다.

## 3. [네트워크] 쿠키와 세션은 데이터 저장 위치로 구분하는가?

<!-- id: 8d8da053-5beb-4fcd-bbad-f88fcf19cff8 -->

저장 위치가 다르다. 쿠키는 클라이언트의 브라우저에 저장하고, 세션은 서버 측 저장소에 저장한다.

| 기준 | 쿠키 | 세션 |
| --- | --- | --- |
| 저장 위치 | 브라우저 | 서버 |
| 데이터 크기 | 작음 | 제한 없음 |
| 보안성 | 낮음 | 높음 |

쿠키는 네트워크 요청마다 서버로 자동 전송된다. 서버는 이를 읽어 사용자를 식별한다. 클라이언트가 데이터를 직접 수정할 수 있어 보안에 취약하다.

세션은 서버에 데이터를 저장하고 클라이언트에는 세션 ID만 전달한다. 실제 데이터는 서버가 관리하므로 조작이 어렵다. 하지만 서버 메모리를 사용하므로 사용자 수가 늘면 부하가 증가한다.

## 4. [데이터베이스] 격리 수준을 올리면 무엇을 잃는가?

<!-- id: 070512bd-81b4-4603-9c9a-7f0c5b726798 -->

동시성을 잃는다. 위로 올라갈수록 막아주는 현상이 늘지만 그만큼 잠금을 오래 넓게 쥔다. 무엇을 막고 싶은지가 아니라 무엇을 견딜 수 있는지로 고른다.

| 수준 | 막아주는 것 | 대가 |
| --- | --- | --- |
| Read Committed | 커밋 안 된 값 읽기 | 같은 질의가 두 번 다를 수 있다 |
| Repeatable Read | 읽은 행이 중간에 바뀌는 것 | 없던 행이 끼어드는 것은 못 막는다 |
| Serializable | 전부 | 충돌 시 트랜잭션이 취소된다 |

기본값은 대개 Read Committed다. 대부분의 화면은 조금 어긋난 값을 견딘다. 잔액을 읽어 검사하고 쓰는 자리처럼 읽은 값을 근거로 판단할 때만 위로 올린다.

올리는 것 말고 다른 길도 있다. `select ... for update`로 그 한 줄만 잠그거나, 버전을 두고 커밋 때 확인하는 방식이다. 범위를 좁게 잡으면 수준을 올리지 않고도 같은 것을 지킬 수 있다.

면접에서는 Serializable이 어떻게 구현되는지로 들어온다. 전부 줄 세우는 것이 아니라 충돌을 감지해 한쪽을 취소하는 방식이다. 그래서 애플리케이션에 재시도 코드가 있어야 한다.

## 5. [데이터베이스] 데이터베이스 커넥션 풀의 적정 크기를 설정할 때 왜 CPU 코어 수를 기준으로 설정하는지 그 이유가 궁금합니다.

<!-- id: b6ce7342-8bb3-49a8-be05-ff7c3f45d8ff -->

CPU 코어 수가 처리 가능한 동시 요청의 물리적 한계치이기 때문이다. 코어 수가 적은데 풀 크기만 늘리면 컨텍스트 스위칭 비용만 증가한다.

:::stack
처리량 | 코어 수 * (디스크 I/O 대기 시간 + 1)
병목 지점 | CPU 코어 수. 연산 처리의 실제 한계
:::

DB 서버의 CPU는 쿼리 실행 계획을 짜고 데이터를 연산한다. 풀 크기가 너무 크면 수많은 스레드가 CPU 점유를 위해 경쟁하며 오버헤드가 발생한다.

반면 너무 작으면 CPU가 놀고 있어도 요청이 큐에서 대기한다. 따라서 코어 수와 디스크 I/O 성능을 고려한 적정 지점을 찾아야 한다.

면접에서는 CPU 코어 수뿐만 아니라 디스크 타입(SSD/HDD)에 따른 I/O 대기 시간을 함께 언급하는 것이 좋다.

## 6. [데이터베이스] 커넥션 풀을 사용하는 이유는 무엇인가?

<!-- id: e4cbccfc-2e05-4eb2-a1db-fce3f0a1a54c -->

데이터베이스 연결 생성 비용이 매우 크기 때문이다. 매번 연결을 맺고 끊는 과정에서 TCP 핸드셰이크와 인증 과정이 반복되어 응답 시간이 늘어난다.

:::flow
클라이언트 -> 커넥션 풀: 연결 요청
커넥션 풀 -> 클라이언트: 유효한 커넥션 대여
클라이언트 -> 커넥션 풀: 사용 후 반납
:::

풀에 미리 연결을 생성해 두고 대여하는 방식으로 동작한다. 이를 통해 연결 생성 시간을 제거하여 시스템 전체의 처리량(Throughput)을 높일 수 있다.

풀의 크기를 너무 크게 잡으면 DB 서버의 메모리와 CPU 자원을 과하게 사용한다. 반대로 너무 작게 잡으면 요청이 밀려 대기 시간이 길어진다.

적절한 크기를 설정하는 것이 핵심이다. 서비스의 트래픽 패턴과 DB 서버의 사양을 고려하여 벤치마크 테스트를 통해 최적값을 찾아야 한다.

## 7. [모바일] 비동기로 옮겼는데도 왜 응답 없음이 생기는가?

<!-- id: 9a4e70c3-5916-4be0-afd8-5d7820896dfa -->

작업을 다른 스레드로 보냈어도 메인 스레드가 결과나 잠금을 기다리면 막히기 때문이다. 느린 Binder 호출과 과도한 그리기도 입력 처리를 지연시킨다.

:::flow
사용자 -> 메인 Looper: 입력 이벤트를 보낸다
메인 Looper -> 작업: 결과나 잠금을 기다린다
시스템 -> 앱: 기한 내 응답이 없어 ANR을 기록한다
:::

메인 스레드는 입력과 생명주기 콜백과 화면 갱신을 직렬로 처리한다. 입력 이벤트에 약 5초간 응답하지 못하면 입력 디스패치 ANR이 날 수 있다.

스택 덤프에서 main의 대기 지점을 찾고 잠금 보유 스레드도 따라간다. StrictMode와 Perfetto로 I/O와 느린 Binder 호출을 확인한다.

## 8. [모바일] 오프라인 수정이 서버 값과 충돌하면 누가 이기는가?

<!-- id: 4401ae8b-e4d2-4f68-a3dd-601e395baf35 -->

누가 이기는지는 동기화 정책이 정한다. 중요 데이터라면 마지막 쓰기만 택하지 말고 버전으로 충돌을 감지해 병합하거나 사용자에게 선택을 맡긴다.

| 기준 | 마지막 쓰기 승리 | 버전 기반 병합 |
| --- | --- | --- |
| 구현 | 단순하다 | 복잡하다 |
| 데이터 손실 | 숨기기 쉽다 | 충돌을 드러낸다 |

로컬 데이터베이스를 화면의 기준으로 두면 오프라인에서도 일관된 읽기가 가능하다. 변경은 outbox에 기록해 연결이 돌아왔을 때 순서대로 보낸다.

재전송에는 멱등 키와 서버 버전을 함께 쓴다. 성공 응답을 잃어도 중복 반영을 막고 오래된 버전의 덮어쓰기를 거절할 수 있다.

장바구니는 항목 병합이 가능하지만 결제 상태는 서버 권위가 필요하다. 충돌 정책은 데이터 의미와 되돌릴 수 있는지를 기준으로 정한다.

## 9. [모바일] 화면을 돌리면 데이터가 사라지는 이유는?

<!-- id: a984ce89-022d-4d6b-b3aa-42becfca2c17 -->

구성이 바뀌면 액티비티가 파괴되고 새로 만들어지기 때문이다. 기존 인스턴스가 들고 있던 값은 그 인스턴스와 함께 사라진다. 남기려면 무엇까지 견뎌야 하는지에 따라 세 층 중 하나를 고른다.

| 수단 | 어디까지 견디나 | 담기 좋은 것 |
| --- | --- | --- |
| ViewModel | 구성 변경까지. **프로세스 종료엔 사라진다** | 목록, 진행 중인 작업 |
| onSaveInstanceState | 프로세스 종료까지 | 작고 직렬화 가능한 값 |
| 파일·DB | 앱을 지울 때까지 | 오래 남겨야 하는 것 |

일부러 그렇게 설계했다. 가로와 세로는 레이아웃도, 이미지도, 때로는 문자열도 다른 리소스를 쓴다. 리소스를 다시 고르는 가장 확실한 방법이 처음부터 다시 만드는 것이다 — 언어 변경이나 다크 모드 전환도 같은 경로를 탄다.

셋을 가르는 축은 무엇을 견뎌야 하느냐다. 구성 변경만 견디면 되는 값은 ViewModel로 충분하다. 다만 시스템이 메모리를 회수하며 프로세스를 죽이면 ViewModel도 함께 사라진다. 그때까지 살아야 하는 값은 번들이나 저장소로 내려야 한다.

면접에서는 이 둘을 구별하는지를 본다. "ViewModel을 쓰면 된다"까지는 대부분 말한다. 프로세스 종료는 못 견딘다는 것과 그 자리를 SavedStateHandle이 메운다는 데까지 가면 한 단계 위다.

## 10. [아키텍처 · 분산시스템] 분산 트랜잭션에서 Saga 패턴이 필요한 이유는?

<!-- id: d06deb06-5f59-458b-844b-50e9d8800547 -->

서비스마다 DB가 분리되면 하나의 트랜잭션으로 묶을 수 없기 때문이다. 롤백을 DB에 맡길 수 없으니 애플리케이션이 직접 되돌려야 한다. Saga는 긴 트랜잭션을 로컬 트랜잭션의 연쇄로 바꾸고, 뒤가 실패하면 앞을 되돌린다.

:::flow
주문 -> 결제: 주문 생성하고 커밋. 여기서 이미 확정이다
결제 -> 배송: 결제 성공하고 커밋
배송 -> 결제: 배송 생성 실패
결제 -> 주문: 결제 취소. 앞 단계를 되돌리는 보상이다
:::

각 단계는 자기 DB에서 즉시 커밋한다. 잠금을 들고 기다리지 않으니 가용성이 높다.

2PC는 같은 문제를 조정자로 푼다. 모든 참여자가 커밋 준비를 마칠 때까지 자원을 잠그므로 가용성이 떨어진다. 조정자가 죽으면 참여자가 잠긴 채로 남는 위험도 있다.

대가는 격리성 포기다. 중간 상태가 외부에 보인다. 결제는 됐는데 배송 생성이 실패한 순간이 잠깐 존재한다.

그래서 보상은 반드시 성공해야 하고 그 자체로 멱등해야 한다. 실무에서 갈리는 지점은 오케스트레이션이냐 코레오그래피냐다. 중앙 조정자를 둘지 이벤트로 흘릴지는 단계 수와 디버깅 난이도로 판단한다.

## 11. [아키텍처 · 분산시스템] 호출 시간 제한은 무엇을 기준으로 정하는가?

<!-- id: c69036ba-5f3d-4dc6-9626-590a8b9715d6 -->

바깥에서 안으로 좁혀 간다. 사용자가 기다릴 수 있는 시간에서 시작해 그 안에 들어가도록 각 단계를 나눈다.

:::stack
사용자 응답 3초 | 여기서 시작한다
게이트웨이 2.5초 | 남는 시간에 여유를 뺀다
주문 서비스 2초 | 다시 그 안에서
결제 호출 1초 | 재시도까지 넣어도 들어가야 한다
:::

안쪽이 바깥쪽보다 길면 안 된다. 그러면 바깥이 이미 포기한 요청을 안쪽이 계속 붙들고 자원을 쓴다.

제한이 아예 없는 것이 가장 위험하다. 응답 없는 호출 하나가 스레드를 묶고, 그 스레드가 다 떨어지면 멀쩡한 요청까지 못 받는다.

면접에서는 재시도와의 곱을 짚는다. 1초 제한에 3회 재시도면 최악 3초다. 바깥 예산이 2초라면 이미 넘는다.

## 12. [언어 · 런타임] 값 타입과 참조 타입은 무엇으로 구분하는가?

<!-- id: 6f6b9e44-b4f0-4aaf-a5f1-cc8f05ca02b1 -->

데이터가 메모리에 저장되는 방식과 전달되는 방식의 차이로 구분한다. 값 타입은 실제 값을 직접 저장하고, 참조 타입은 값이 저장된 메모리 주소를 저장한다.

:::stack
값 타입 | 스택 메모리. 실제 데이터가 저장됨
참조 타입 | 힙 메모리. 주소값이 저장되며 데이터는 힙에 위치함
:::

값 타입은 변수 간 복사 시 값이 그대로 복사되어 서로 영향을 주지 않는다. 독립적인 상태를 유지하므로 부수 효과가 적어 안전하다.

참조 타입은 주소값을 복사한다. 여러 변수가 동일한 객체를 가리키므로 한 곳에서 수정하면 다른 변수에도 반영된다. 이는 메모리 효율을 높이지만 상태 변경 추적이 어렵다.

## 13. [언어 · 런타임] 속성이 없을 때 엔진은 어디까지 찾는가?

<!-- id: 9634fa27-4cb7-4015-8d18-3b8fbf888de2 -->

객체의 자체 속성을 먼저 보고, 없으면 내부 프로토타입을 따라 같은 키를 찾는다. 일치할 때까지 반복하며 체인의 끝인 null에 닿으면 undefined가 된다.

:::flow
객체 -> 자체 속성: 키가 있는지 확인한다
키 없음 -> 프로토타입: 같은 키를 찾는다
키 계속 없음 -> 상위 프로토타입: null까지 반복한다
:::

하위 객체에 같은 키가 있으면 상속 속성을 가린다. 대입은 보통 자체 속성을 만들지만 상속된 setter나 쓰기 금지 속성이 있으면 결과가 달라진다.

class의 인스턴스 메서드는 prototype에 둔다. static 메서드는 클래스 생성자 자체에 두며 각 위치에서 같은 속성 탐색 규칙을 따른다.

## 14. [언어 · 런타임] 클로저를 사용해 상태를 은닉하는 이유는 무엇인가?

<!-- id: 52a45cde-c872-41e5-bb31-0733d3c660c6 -->

외부 함수의 지역 변수를 외부에서 직접 수정하지 못하게 막아 데이터 무결성을 지키기 때문이다.

| 기준 | 전역 변수 | 클로저 은닉 |
| --- | --- | --- |
| 접근성 | 누구나 가능 | 정의된 함수만 가능 |
| 상태 보호 | 불가능 | 캡슐화 가능 |

함수가 생성될 때 자신의 렉시컬 환경을 기억한다. 따라서 내부 함수를 통해 변수에 접근하는 통로만 열어두면 외부에서는 변수 값을 바꿀 수 없다.

이는 객체 지향의 캡슐화와 유사한 효과를 낸다. 불필요한 전역 변수 사용을 줄여 이름 충돌을 방지하고 상태 변화를 예측 가능하게 만든다.

다만 클로저는 참조하는 변수를 계속 메모리에 유지한다. 과하게 사용하면 가비지 컬렉션 대상에서 제외되어 메모리 누수가 발생할 수 있다.

## 15. [운영체제] 데드락은 어떤 조건이 모두 모여야 생기는가?

<!-- id: 29992d13-ec8a-450e-a643-195dfb8ec48e -->

네 조건이 동시에 성립할 때다. 하나만 깨도 데드락은 생기지 않는다.

:::stack
상호 배제 | 자원을 한 번에 하나만 쓸 수 있다
점유하며 대기 | 하나를 쥔 채로 다른 것을 기다린다
비선점 | 쥔 것을 강제로 뺏을 수 없다
순환 대기 | 기다림이 고리를 이룬다
:::

실무에서 가장 자주 깨는 것은 마지막이다. 자원에 순서를 매기고 항상 그 순서로만 잡게 하면 고리가 생길 수 없다. 계좌 두 개를 잠글 때 언제나 번호가 작은 쪽부터 잡는 식이다.

점유하며 대기를 깨는 방법도 있다. 필요한 자원을 한 번에 전부 잡거나, 못 잡으면 쥔 것을 놓고 처음부터 다시 한다. 다만 이쪽은 굶주림이 생길 수 있다 — 계속 실패하는 쪽이 영영 못 잡는다.

면접에서는 예방과 회피와 탐지를 구별하는지를 본다. 예방은 조건을 아예 못 만들게 한다. 회피는 요청마다 안전한지 따져본다. 탐지는 생기게 두되 발견하면 푼다. 데이터베이스는 대개 마지막을 고른다 — 앞의 둘이 처리량을 너무 깎기 때문이다.

## 16. [운영체제] 스레드 풀을 사용하는 주된 이유는 무엇인가?

<!-- id: 2041ab82-86f9-4745-8521-74b91db6afea -->

스레드 생성과 제거에 드는 오버헤드를 줄이기 위해서다. 요청마다 스레드를 새로 만들면 커널 모드 전환과 메모리 할당 비용이 반복적으로 발생한다.

:::stack
풀링 영역 | 미리 생성해 둔 스레드들의 집합
작업 큐 | 대기 중인 요청들이 쌓이는 곳
:::

작업 큐에 요청이 들어오면 풀에 있는 유휴 스레드가 이를 가져가 처리한다. 처리가 끝나면 스레드는 소멸하지 않고 다시 풀로 돌아가 다음 작업을 기다린다.

적절한 풀 크기를 설정하지 않으면 문제가 생긴다. 너무 작으면 요청이 큐에 쌓여 응답 시간이 느려지고, 너무 크면 컨텍스트 스위칭 비용이 커져 전체 처리량이 떨어진다.

## 17. [인프라 · 보안] CPU와 메모리 중 무엇이 데이터 처리 속도를 결정하는가?

<!-- id: f2d1093f-78ce-451d-a0f6-ba72371f013e -->

CPU의 연산 속도와 메모리 접근으로 인한 대기 시간의 균형이 결정한다.

:::stack
CPU 코어 | 연산 속도. 직접 처리하는 힘
메모리 | 데이터 공급 속도. 대기 시간 발생
:::

CPU는 매우 빠르지만 메모리에서 데이터를 가져오는 속도는 상대적으로 느리다. 이를 메모리 벽(Memory Wall)리라 부른다.

데이터가 없으면 CPU는 아무리 빨라도 놀게 된다. 이를 해결하기 위해 CPU 내부에 캐시 메모리를 두어 데이터 공급 속도를를 높인다.

## 18. [인프라 · 보안] 대칭키와 공개키 중 무엇을 선택하는가?

<!-- id: 61e43b03-57ea-4211-a981-189bd2295061 -->

데이터의 양과 보안 요구 수준에 따라 선택한다. 대량 데이터 전송에는 대칭키를, 초기 키 교환이나 인증에는 공개키를 쓴다.

| 기준 | 대칭키 | 공개키 |
| --- | --- | --- |
| 속도 | 빠름 | 매우 느림 |
| 키 관리 | 공유 키 보안 위험 | 공개키 배포 가능 |
| 용도 | 본문 암호화 | 키 교환, 서명 |

공개키 방식은 복잡한 수학 연산을 수행하므로 대칭키보다 훨씬 느리다. 따라서 전체 데이터를 공개키로 암호화하면 성능 저하가 심하다.

실무에서는 하이브리드 방식을 쓴다. 공개키로 대칭키를 안전하게 전달한 뒤, 실제 데이터는 그 대칭키로 빠르게 암호화하는 구조다.

TLS 핸드셰이크가 대표적인 사례다. 비대칭키로 세션 키를 합의하고, 이후 통신은 대칭키로 수행하여 보안과 효율을 모두 잡는다.

## 19. [인프라 · 보안] 함수형 프로그래밍을 적용하는 이유는 무엇인가?

<!-- id: 248eb887-bf2c-4f81-ae85-54fa864c0ca4 -->

상태 변경을 최소화하여 코드의 예측 가능성을 높이기 때문이다.

| 기준 | 명령형 프로그래밍 | 함수형 프로그래밍 |
| --- | --- | --- |
| 상태 관리 | 가변 상태 사용 | 불변 상태 유지 |
| 실행 결과 | 입력에 따라 달라짐 | 동일 입력 동일 결과 |
| 처리 방식 | 어떻게(How) 수행 | 무엇(What)을 수행 |

순수 함수는 외부 상태를 바꾸지 않고 오직 입력값으로만 결과를 만든다. 따라서 사이드 이펙트가 없어 테스트와 디버깅이 매우 쉽다.

불변성을 유지하면 멀티스레드 환경에서 데이터 경쟁 상태가 발생하지 않는다. 락을 거는 비용 없이도 안전한 동시성 제어가 가능하다.

선언적 스타일로 코드를 작성하면 비즈니스 로직이 명확해진다. 복잡한 제어문을 줄여 코드의 가독성과 유지보수성이 향상된다.

## 20. [자료구조 · 알고리즘] 스택과 큐는 각각 어떤 상황에서 선택해야 하는가?

<!-- id: df71f7ad-ff91-4396-add5-4ebc09ba6352 -->

스택은 가장 최근 데이터를 먼저 처리해야 할 때 쓰고, 큐는 들어온 순서대로 데이터를 처리해야 할 때 선택한다.

| 기준 | 스택 (Stack) | 큐 (Queue) |
| --- | --- | --- |
| 입출력 방식 | LIFO (후입선출) | FIFO (선입선출) |
| 주요 용도 | 되돌리기, 재귀 처리 | 작업 대기열, 버퍼 |
| 알고리즘 | 깊이 우선 탐색 (DFS) | 너비 우선 탐색 (BFS) |

위 표는 두 자료구조의 핵심 동작 방식과 쓰임새 차이를 보여준다. 스택은 입력된 역순으로 돌아가는 이력 관리에 유용하며, 큐는 유입된 요청을 순서대로 소화하는 완충 지대에 알맞다.

스택은 함수 호출(Call Stack)이나 실행 취소(Undo)처럼 직전의 상태를 기억해야 하는 곳에 필수적이다. 반면 큐는 이메일 발송 대기열이나 프린터 인쇄 작업처럼 순차적인 처리가 보장되어야 하는 비동기 시스템의 기초가 된다.

면접에서는 실무적인 한계도 자주 묻는다. 스택은 메모리 한계로 인한 오버플로우를 주의해야 하고, 큐는 데이터를 꺼낼 때 발생하는 배열 내 요소 이동 비용을 줄이기 위해 원형 큐나 연결 리스트 구조를 고민해야 한다.

## 21. [자료구조 · 알고리즘] 정렬의 안정성이 실무에서 문제가 되는 때는?

<!-- id: b3ca72d9-b8c3-4d45-9a56-feefe91eb6a7 -->

정렬을 두 번 겹쳐 다중 기준을 만들 때다. 안정성이 없으면 앞서 맞춰둔 순서가 뒤 정렬에서 흐트러진다.

안정 정렬은 키가 같은 원소들의 원래 순서를 그대로 둔다. 이름순으로 정렬한 목록을 부서순으로 다시 정렬하면, 안정 정렬에서는 부서 안이 이름순으로 남는다. 불안정 정렬에서는 그 안이 뒤섞인다.

:::flow
원본 -> 1차 정렬: 이름순으로 세운다
1차 정렬 -> 2차 정렬: 부서순으로 다시 세운다
2차 정렬 -> 결과: 안정이면 부서 안이 이름순으로 남고, 불안정이면 뒤섞인다
:::

언어마다 기본값이 다르다. 자바는 객체 배열에 TimSort를 써서 안정적이지만 원시 타입에는 퀵정렬 계열을 써서 그렇지 않다. 값이 같은 int 둘은 구별할 방법이 없으니 순서가 바뀌어도 관측되지 않기 때문이다.

그래서 판단 기준은 간단하다. 같은 키를 가진 두 원소를 사용자가 구별할 수 있으면 안정성이 필요하다. 화면에 이름이 보이는 목록이 그렇고, 숫자 배열은 아니다.

면접에서는 비교자를 하나로 합치는 쪽과 두 번 정렬하는 쪽 중 무엇이 나은지로 들어온다. 합치면 안정성에 기대지 않아 안전하지만, 기준이 런타임에 정해지는 화면에서는 겹쳐 정렬하는 편이 단순하다.

## 22. [프레임워크] JVM GC의 효율을 높이는 튜닝 포인트는 무엇인가?

<!-- id: 503859af-cf26-4668-83d6-93711d6f96eb -->

힙 메모리 영역의 크기와 GC 알고리즘 선택이다. 세밀한 튜닝을 통해 Stop-the-world 시간을 줄이는 것이 핵심이다.

:::stack
Young Generation | Eden, Survivor. 짧은 생존 객체 관리
Old Generation | 장기 생존 객체 관리. Major GC 발생
:::

객체 생존 기간에 따라 영역을 나누어 관리한다. Young 영역에서 살아남은 객체가 Old 영역으로 이동하며, Old 영역이 꽉 차면 전체 힙을 검사하는 Full GC가 발생한다.

Stop-the-world는 모든 애플리케이션 스레드가 멈추는 현상이다. GC 알고리즘에 따라 멈춤 시간이 달라지므로, 서비스 특성에 맞춰 G1 GC나 ZGC를 선택한다.

힙 크기를 너무 크게 잡으면 Full GC의 처리 시간이 길어진다. 반대로 너무 작으면 GC가 빈번하게 발생하여 CPU 사용률이 올라간다.

---

## 23. [프레임워크] 수정 메서드 없이 UPDATE가 나가는 이유는?

<!-- id: ac066d0e-33e2-4e3e-ac1c-0bd053e68b64 -->

영속성 컨텍스트가 관리 엔티티의 최초 상태와 현재 상태를 flush 때 비교하기 때문이다. 달라진 속성이 있으면 UPDATE SQL을 만든다.

:::flow
조회 -> 컨텍스트: 엔티티와 최초 상태를 둔다
코드 -> 엔티티: 필드를 바꾼다
커밋 -> flush: 최초 상태와 비교한다
flush -> DB: 차이가 있으면 UPDATE한다
:::

flush는 커밋 직전이나 쿼리 실행 전에 일어날 수 있다. SQL이 보였다는 사실과 커밋됐다는 사실은 다르며 롤백하면 변경은 사라진다.

관리 상태인 엔티티만 대상이다. detach나 clear 뒤의 객체는 바꿔도 감지되지 않는다. merge는 전달 객체가 아니라 반환된 관리 객체를 갱신한다.

벌크 UPDATE는 영속성 컨텍스트를 건너뛴다. 이미 관리 중인 객체가 낡을 수 있어 flush 후 clear하거나 다시 조회하는 전략이 필요하다.

## 24. [프레임워크] 인터페이스와 추상 클래스는 무엇으로 구분하는가?

<!-- id: bbd92984-377a-4412-8c70-4d7a73812fe2 -->

설계 목적의 차이로 구분한다. 인터페이스는 '무엇을 하는지' 정의하는 행위의 규격이고, 추상 클래스는 '무엇인지' 정의하는 클래스의 정체성이다.

| 기준 | 인터페이스 | 추상 클래스 |
| --- | --- | --- |
| 목적 | 행위의 규격화 | 정체성 상속 |
| 관계 | can-do 관계 | is-a 관계 |
| 다중 상속 | 가능 | 불가능 |

인터페이스는 클래스가 어떤 기능을으로 구현해야 함을 강제하는 계약서다. 서로 다른 계층의 클래스들이 공통된 행위로 소통//

추상 클래스는 공통된 상태와 기본 구현을 공유하여 중복 코드를 줄이는 상속 구조다. 자식 클래스가 반드시적으로 owneclatenty implementing method를 통해 정체성을 구체화한다.

## 25. [프론트엔드] useEffect 의존성 배열을 잘못 넣으면 어떤 문제가 생기는가?

<!-- id: f369d7e3-bdcc-4ff7-a0f9-9896e5f6e903 -->

너무 적게 넣으면 오래된 값을 붙잡고, 너무 많이 넣으면 불필요하게 다시 실행된다. 방향이 반대인 두 문제다.

| 넣는 양 | 증상 | 알아채기 |
| --- | --- | --- |
| 너무 적다 | 클로저가 첫 렌더의 값을 계속 본다 | 오류가 안 나서 늦게 발견된다 |
| 너무 많다 | 매 렌더마다 실행되고 무한 루프로 간다 | 바로 티가 난다 |

의존성을 빠뜨리면 클로저가 첫 렌더의 값을 계속 참조한다. 이펙트 안에서 최신 상태를 읽는 줄 알았는데 초기값이 나오는 상황이 여기서 생긴다. 콘솔에는 아무 오류도 없어 발견이 늦다.

반대로 매 렌더마다 새로 만들어지는 객체나 함수를 의존성에 넣으면 참조가 계속 바뀐다. 이펙트가 매번 실행되고, 그 안에서 상태를 갱신하면 무한 루프가 된다.

정리 함수를 빠뜨리는 것도 같은 범주다. 구독이나 타이머를 걸어두고 정리하지 않으면 언마운트된 컴포넌트가 계속 살아 있다. 이펙트가 자주 실행될수록 누수가 빨리 쌓인다.

판단 기준은 단순하다. 이펙트 안에서 쓰는 모든 외부 값을 넣고, 그래서 너무 자주 실행되면 값 자체를 안정화한다. 의존성을 빼서 해결하는 것은 증상만 가리는 것이다.

## 26. [프론트엔드] 번들은 어떤 경계로 나눠 불러오는가?

<!-- id: 8b7774d5-834c-4620-acc9-43ab17bf2d5f -->

초기 경로에 필요한 코드만 먼저 보낸다. 나머지는 경로, 기능, 무거운 라이브러리 경계로 나눠 필요할 때 불러온다.

:::flow
초기 진입 -> 핵심 청크: 즉시 내려받는다
경로 이동 -> 경로 청크: 동적으로 불러온다
기능 실행 -> 기능 청크: 처음 사용할 때 불러온다
:::

동적 import는 별도 청크를 만드는 경계가 된다. React에서는 lazy와 Suspense를 조합해 로딩 상태를 보여주며 컴포넌트를 늦게 읽는다.

너무 잘게 나누면 요청 수와 로딩 화면이 늘고 공통 모듈이 중복될 수 있다. 사용 빈도, 청크 크기, 캐시 적중률을 측정해 경계를 조정한다.

## 27. [프론트엔드] 체감 성능은 어떤 세 지표로 판단하는가?

<!-- id: c87653b7-3510-4fea-9cb4-7c63b6726086 -->

LCP로 주요 콘텐츠 표시 속도를 판단한다. INP로 상호작용 반응성을 본다. CLS로 시각적 안정성을 확인한다. 세 지표는 서로 다른 불편을 드러낸다.

| 기준 | 지표 | 판단 대상 |
| --- | --- | --- |
| 표시 | LCP | 주요 콘텐츠 속도 |
| 반응 | INP | 상호작용 지연 |
| 안정 | CLS | 레이아웃 이동 |

좋음 기준은 LCP 2.5초 이하, INP 200밀리초 이하, CLS 0.1 이하다. 페이지 방문의 75번째 백분위에서 모바일과 데스크톱을 나눠 본다.

현장 데이터는 실제 기기와 네트워크의 경험을 보여준다. 실험실 데이터는 재현과 원인 분석에 유리하다. 개선 전후에는 둘을 함께 본다.
