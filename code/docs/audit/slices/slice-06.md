## 1. [네트워크] HTTP 상태 코드는 어떤 기준으로 분류하는가?

<!-- id: a9f6be16-909e-4878-a933-203dd568dbd1 -->

첫 번째 자리 숫자가 응답의 성격으로 분류된다. 1xx는 정보, 2xx는 성공, 3xx는 리다이렉션, 4xx는 클라이언트 오류, 5xx는 서버 오류다.

:::stack
상태 코드 | 분류
--- | ---
1xx | 정보 제공
2xx는 성공적인 처리
3xx는 리다이렉션
4xx는 클라이언트 요청 오류
5xx는 서버 내부 오류
:::

위 표는 숫자의 첫 자리만으로도 로그 분석이나 모니터링 도구에서 빠르게 판단하는 기준이 된다.

4xx와 5xx의 차이는 책임 소재가 어디에 있느냐다. 4xx는 요청자가 잘못 보냈으니 수정해서 다시 보내야 하고, 5xx는 서버가 처리로직으로 인해 장애가 발생했음을 의미한다.

## 2. [네트워크] 브라우저에 URL을 입력하면 어떤 과정을 거치는가?

<!-- id: b1e8f5ab-4e72-4d9c-8bf8-e239b728463d -->

DNS로 IP 주소를 찾고, TCP 연결을 맺고, HTTP 요청을 보내어 응답을 받는 과정이다.

:::flow
브라우저 -> DNS: 도메인으로 IP 조회
DNS -> 브라우저: IP 주소 반환
브라우저 -> 서버: TCP 3-Way Handshake
브라우저 -> 서버: HTTP 요청
서버 -> 브라우저: HTTP 응답
:::

먼저 브라우저와 OS로 부터 캐시된 IP를 확인한다. 없으면 DNS 서버에 재귀적으로 요청하여 서버의 IP 주소를 알아낸다.

그 후 TCP 3-Way Handshake를 통해 신뢰성 있는 연결을 맺는다. HTTPS의 경우 TLS Handshake 과정이 추가되어 데이터 암호화 세션을 구축한다.

마지막으로 HTTP 요청 메시지를 생성해 전송하고, 서버는 이를 처리해 HTML 문서와 같은 리소스를 반환한다. 브라우저는 이를 렌더링하여 화면에 표시한다.

## 3. [네트워크] 전송 계층에서 멀티플렉싱과 디멀티플렉싱은 무엇으로 구분하는가?

<!-- id: ce9dc1e2-688b-4a88-8f28-efb66f892224 -->

포트 번호를 통해 구분한다. 하나의 IP 주소로 들어오는 데이터 패킷을 어떤 프로세스나 소켓에 전달할지 결정하는 기준이다.

:::stack
전송 계층 | 포트 번호로 프로세스 구분
네트워크 계층 | IP 주소로 호스트 구분
:::

멀티플렉싱은 전송 계층에서 여러 소켓의 데이터를 모아 하나의 네트워크 인터페이스로 보내는 과정이다. 반대로 디멀티플렉싱은 수신 측에서 포트 번호를를 확인하여 적절한 소켓으로 데이터를 배분하는 과정이다.

UDP는 목적지 포트와 출발지 포트, 프로토콜로만 구분한다. TCP는 4가지 요소(출발지 IP, 목적지 IP, 출발지 포트, 목적지 포트)를 모두 확인해 연결 지향적 소켓을 구분한다.

## 4. [데이터베이스] Redis를 활용한 분산 락 구현 시 스핀 락 방식과 Pub/Sub 방식의 성능 및 구조적 차이는 무엇인가?

<!-- id: f995b280-0d7f-405f-846d-2b7cda082021 -->

스핀 락은 계속해서 락 락 획득을 시도하는 방식이고, Pub/Sub은 락으로 락 해제 신호를 기다리는 방식이다.

:::flow
클라이언트 -> Redis: 락 획득 시도
Redis -> 클라이언트: 실패 (Retry loop)
클라이언트 -> Redis: 락 획득 시도
:::

위 도식은 스핀 락의 반복적인 요청으로 인한 Redis 부하를 보여준다.

스핀 락은 구현이 단순하지만, 락을 획득하지 못했을 때 계속해서 Redis에 요청을 보내므로 CPU와 네트워크 부하가 발생한다.

반면 Pub/Sub 방식은 락이 해제될 때 Redis가 알림을 보내주어 불필요한 요청을 최소화한다. 네트워크 트래픽이 최소화되어 전체적인 시스템 성능이 성능이 향상된다.

## 5. [데이터베이스] 데이터베이스 옵티마이저에서 서브쿼리 언네스팅과 뷰 포스팅(View Merging)의 차이점은 무엇인가?

<!-- id: 18fcb0bd-12e5-4a18-8b63-2c4330a53af4 -->

서브쿼리 언네스팅은 WHERE절 등의 서브쿼리를 메인 쿼리와의 조인 형태로 변환하는 기법이고, 뷰 포스팅(View Merging)은 FROM절의 뷰 블록을 메인 쿼리와 하나로 병합하는 기법이라는 차이가 있다.

| 기준 | 서브쿼리 언네스팅 | 뷰 포스팅 (View Merging) |
| --- | --- | --- |
| 변환 대상 | WHERE/HAVING절 서브쿼리 | FROM절 인라인 뷰 및 뷰 |
| 변환 방식 | 서브쿼리를 메인 조인문으로 변환 | 뷰의 쿼리 블록을 메인 쿼리에 병합 |
| 주요 목적 | 서브쿼리의 반복 수행 방지 | 불필요한 중간 집합 생성 방지 |

이 도식은 두 최적화 기법이 다루는 SQL 위치와 변환 방식을 보여준다. 언네스팅은 서브쿼리가 필터 조건처럼 매번 반복 실행되는 것을 막아 해시 조인 등을 활용할 수 있게 돕는다.

반면 뷰 포스팅은 FROM절 인라인 뷰의 쿼리 블록을 메인 쿼리로 흡수한다. 이를 통해 불필요한 임시 테이블 생성이나 메인 쿼리와의 중복 검색을 줄인다.

두 기법 모두 옵티마이저가 쿼리 블록을 단순화하여 최적화 공간을 넓히는 기법이다. 하지만 작동하는 대상절과 조인 구조 생성 방식에서 명확히 구분된다.

## 6. [데이터베이스] 인덱스 생성 시 조회 성능과 쓰기 성능의 트레이드오프는 무엇인가?

<!-- id: 53f134dc-5a68-4e06-9ee0-775b21cd0fc7 -->

조회 속도는 빨라지나 데이터 변경 시 인덱스 갱신 비용이 발생해 쓰기 성능이 떨어진다.

| 기준 | 조회 성능 | 쓰기 성능 |
| --- | --- | --- |
| 인덱스 없음 | 느림 (전체 스캔) | 빠름 (단순 삽입) |
| 인덱스 있음 | 빠름 (탐색으로 찾음) | 느림 (정렬 유지) |

인덱스는 데이터의 물리적 순서와 별개로 정렬된 별도의 저장 공간을 갖는다. 데이터를 넣을 때마다 이 정렬 순서를 유지해야 하므로 삽입, 수정, 수정 삭제 시 부하가 증가한다.

반면 조회 시에는 정렬된 상태를 이용해 전체 데이터를 다 훑지 않고 빠르게 찾을 수 있다. 특히 범위 검색이나 정렬된 결과가 필요할 때 효과가 극히 크다.

무분별한 인덱스 생성은 오히려 디스크 I/O를 늘려 시스템 전체 성능을 저하시킨다. 데이터의 분포도와 쿼리 패턴을 분석해 필요한 컬럼에만 최소한으로 설정하는 것이 중요하다.

## 7. [모바일] 백그라운드 제약을 피하는 방법은 무엇인가?

<!-- id: c6f28d19-8a07-4f36-9659-ca576ec2685d -->

포그라운드 서비스와 WorkManager를 사용한다. 앱이 보이지 않아도 시스템이 강제 종료시키지 않도록 알림을 띄우거나 예약 작업을 등록하는 방식이다.

:::stack
포그라운드 서비스 | 알림창에 상주하며 즉시 실행
WorkManager | 조건 충족 시 시스템이 최적 시점에 실행
:::

포그라운드 서비스는 사용자에게 앱이 동작 중임을 알린다. 시스템은 알림이 떠 있는 서비스를 중요도로 높게 평가해 메모리 부족 상황에서도 종료 우선순위를 늦춘다.

WorkManager는 지연 가능한 작업을 처리한다. 배터리 최적화 모드나 Doze 모드에서도 OS가 적절한 시점을 골라 작업을 묶어 처리하므로 전력 소모를 줄인다.

최신 OS 버전에서는 포그라운드 서비스 타입 선언이 필수다. 타입을 명시하지 않거나 부적절한 타입을 쓰면 앱이 비정상 종료된다.

## 8. [모바일] 앱이 백그라운드로 가면 무엇을 중단해야 하는가?

<!-- id: e273a512-da9e-4b93-96b6-e8ff1b1f1654 -->

화면 갱신과 사용자 상호작용에 묶인 작업을 중단해야 한다. 카메라와 타이머 같은 자원을 놓고 복구에 필요한 상태는 즉시 저장한다.

:::flow
시스템 -> Scene: active에서 inactive로 바꾼다
Scene -> 앱: 상호작용과 갱신을 멈춘다
시스템 -> Scene: background로 바꾼다
Scene -> 저장소: 복구할 상태를 기록한다
:::

여러 창을 지원하면 앱 전체 상태와 Scene 상태를 나눠야 한다. UIKit은 SceneDelegate를 쓰고 SwiftUI는 scenePhase 변화를 관찰한다.

백그라운드에 간 뒤 프로세스가 예고 없이 종료될 수 있다. 종료 콜백에만 저장을 맡기지 말고 중요한 변경 시점마다 내구성 있게 기록한다.

계속 실행할 정당한 작업은 목적에 맞는 백그라운드 API로 요청한다. 허용 시간은 시스템이 제한한다. 예약 작업은 실행 시점과 호출 여부도 보장되지 않는다.

## 9. [모바일] 푸시 알림의 전달 보장을 위해 무엇을 설계하는가?

<!-- id: deb6d06b-318a-4bc7-97be-05872d66f4d3 -->

푸시 서버와 FCM/APNs 같은 외부 플랫폼의 전송 상태를 추적하고 재시도 메커니즘을 구현한다.

:::flow
푸시 서버 -> 플랫폼: 메시지 전송 요청
플랫폼 -> 푸시 서버: 수신 확인(ACK) 응답
푸시 서버 -> 플랫폼: 실패 시 지수 백오프 재시도
:::

전송 요청 후 플랫폼에서 주는 응답만으로는 실제 단말기 도달 여부를 알 수 없다. 플랫폼이 메시지를 큐에 넣었을 때 성공으로 응답하기 때문이다.

따라서 단말기가 알림을 수신했을 때 서버로 수신 확인 신호를 보내는 피드백 루프를 설계한다. 이를 통해 누락된 알림을 다시 보낼 수 있다.

메시지 ID를 통해 중복 수신을 방지하는 멱등성 처리도 함께 고려해야 한다. 네트워크 불안정으로 인한 재시도 시 동일 알림이 여러 번 뜰 수 있다.

## 10. [아키텍처 · 분산시스템] 메시지 큐를 두면 무엇을 얻고 무엇을 잃는가?

<!-- id: 76123298-3456-4517-a4a6-5455a6626ded -->

보내는 쪽과 받는 쪽의 시간을 떼어내는 대신 순서와 즉시성을 잃는다. 트래픽이 몰려도 받는 쪽이 자기 속도로 처리할 수 있게 되는 것이 가장 큰 이득이다.

직접 호출은 받는 쪽이 죽으면 보내는 쪽도 같이 실패한다. 큐를 끼우면 메시지가 쌓여 있다가 받는 쪽이 살아난 뒤에 처리된다. 배포 중에도 요청이 유실되지 않는다.

| 기준 | 직접 호출 | 큐를 통해 |
| --- | --- | --- |
| 받는 쪽이 죽으면 | 보내는 쪽도 실패 | 쌓였다가 나중에 처리 |
| 결과를 아는 시점 | 즉시 | 나중에. 따로 알려야 한다 |
| 순서 | 호출한 순서 | 파티션 안에서만 보장 |

대가가 분명하다. 결과를 즉시 못 준다. 주문이 접수됐다는 응답과 실제로 처리됐다는 사실 사이에 틈이 생기고, 그 틈을 화면이 설명해야 한다. 실패도 그 자리에서 안 보여서 따로 관측해야 한다.

면접에서는 중복과 순서로 한 단계 더 들어온다. 대부분의 큐는 최소 한 번 전달을 보장하므로 같은 메시지가 두 번 올 수 있다. 받는 쪽이 멱등해야 하고, 순서가 필요하면 같은 키를 같은 파티션으로 보내야 한다.

## 11. [아키텍처 · 분산시스템] 캐시를 지우는 일이 어려운 이유는?

<!-- id: 9106cc19-bdbc-4862-a28c-83d6573741a3 -->

언제 지워야 하는지를 캐시가 모르기 때문이다. 원본이 바뀐 사실은 쓰기 쪽에서만 아는데, 캐시는 읽기 쪽에 있어서 그 소식이 저절로 오지 않는다.

| 방식 | 언제 지우나 | 약한 곳 |
| --- | --- | --- |
| TTL | 시간이 지나면 | 그 사이에는 옛 값이 나간다 |
| 쓰기 때 삭제 | 원본을 바꿀 때 같이 | 삭제가 실패하면 계속 옛 값 |
| 쓰기 때 갱신 | 원본과 함께 새 값으로 | 두 곳이 어긋날 틈이 생긴다 |

어느 쪽이든 원본과 캐시라는 두 저장소를 하나의 트랜잭션으로 못 묶는다. 그래서 완전한 일관성이 아니라 어긋나는 시간을 얼마나 짧게 두느냐의 문제가 된다.

더 성가신 것은 무엇을 지워야 하는지다. 상품 하나가 바뀌면 그 상품 캐시만이 아니라 그것이 들어간 목록·검색 결과·집계까지 낡는다. 의존 관계가 코드에 흩어져 있으면 빠뜨린다.

실무에서는 TTL을 기본으로 깔고 중요한 것만 쓰기 시점에 지운다. 지우기를 빠뜨려도 시간이 지나면 스스로 낫는 구조를 바닥에 두는 것이다.

## 12. [언어 · 런타임] volatile 키워드는 가시성 문제를 어떻게 해결하는가?

<!-- id: 64aa7712-1181-48f7-9dec-84df722e1d63 -->

메인 메모리에서 직접 읽고 쓰게 하여 모든 스레드가 최신 값을 보게 한다. CPU 캐시를 거치지 않고 메모리에 즉시 반영하기 때문이다.

:::stack
스레드 A | L1/L2 캐시. 지역적으로 값을 복사해 사용한다
메인 메모리 | 공유 영역. volatile 변수가 저장되는 곳
스레드 B | L1/L2 캐시. 메모리에서 직접 읽어 최신값을 얻는다
:::

CPU는 성능을 위해 값을 캐시에 복사해 쓴다. 여러 스레드가 같은 변수를 수정할 때 각자 캐시만 보면 다른 값을 가지게 된다.

volatile은 읽기/쓰기 시점에 메모리 장벽을 세운다. 이를 통해 CPU 캐시에 저장된 값을 무효화하고 메모리의 값을 강제로 읽게 한다.

다만 원자성은 보장하지 않는다. `count++` 같은 연산은 읽기, 수정, 쓰기 세 단계로 나뉘어 여전히 데이터 경쟁이 발생한다.

## 13. [언어 · 런타임] 메모리 관점에서 값 타입과 참조 타입의 선택 기준은 무엇인가?

<!-- id: 718653d4-4ede-4faf-a3c7-33f5a3639ebc -->

값 타입과 참조 타입을 선택하는 핵심 기준은 데이터의 생명주기와 크기, 그리고 불변성 여부다. 값 타입은 스택(Stack) 영역에 값이 직접 저장되어 할당과 해제가 빠르지만 데이터 복사 비용이 발생한다. 반면 참조 타입은 힙(Heap) 영역에 실제 데이터를 두고 스택에는 주소만 저장하므로, 데이터가 크거나 여러 곳에서 공유해야 할 때 유리하다.

아래 구조는 두 타입이 메모리에 저장되는 물리적 위치의 차이를 나타낸다.

:::stack
힙 영역 | 참조 타입의 실제 데이터 (예: 인스턴스, 배열)
스택 영역 | 값 타입의 데이터 직접 저장 / 참조 타입의 주소값(포인터) 저장
:::

작고 수명이 짧으며 변경할 필요가 없는 데이터는 값 타입으로 선언하여 가비지 컬렉션(GC)의 부담을 줄이는 것이 좋다. 반면, 데이터의 크기가 크거나 시스템 전체에서 동일한 인스턴스를 공유하며 상태를 변경해야 한다면 참조 타입을 선택해야 한다. 이때 참조 타입은 주소만 복사하므로 전달 비용은 저렴하지만, 힙 메모리 관리와 GC 오버헤드가 발생한다는 트레이드오프가 존재한다.

---

## 14. [언어 · 런타임] 중간 연산을 바로 실행하지 않는 이유는?

<!-- id: 338f9ca9-2ee5-4bc2-b6ba-dd0894f6ae34 -->

종료 연산이 요구할 때까지 미루면 여러 중간 연산을 한 번의 순회로 결합할 수 있다. 단락 종료로 필요한 원소만 처리할 수도 있다.

:::flow
스트림 소스 -> 중간 연산: 실행하지 않고 단계를 기록한다
종료 연산 -> 스트림 소스: 원소 처리를 요구한다
스트림 소스 -> 결과: 필터와 변환을 한 순회로 적용한다
:::

filter와 map 같은 상태 없는 연산은 원소 하나씩 이어서 처리한다. sorted와 distinct 같은 상태 있는 연산은 지연 실행이어도 버퍼를 쓸 수 있다.

findFirst와 anyMatch는 답이 정해지면 순회를 멈춘다. 무한 스트림도 그 전에 전체 입력을 요구하는 연산이 없다면 유한 시간에 끝날 수 있다.

스트림은 한 번만 소비할 수 있다. 공유 상태를 바꾸는 부수 효과는 지연 실행과 병렬 처리에서 순서와 안전성을 흐리므로 피해야 한다.

## 15. [운영체제] 가상 메모리 관리 시 페이징과 세그멘테이션은 무엇으로 구분하는가?

<!-- id: fc40f6e8-ff5e-4fdd-b195-93eef3e58e06 -->

메모리를 나누는 물리적 단위로 나누느냐, 논리적 단위로 나누느냐의 차이다.

| 기준 | 페이징 | 세그멘테이션 |
| --- | --- | --- |
| 분할 단위 | 고정 크기 | 가변 크기 |
| 분할 근거 | 물리적 주소 | 논리적 구조 (코드, 데이터, 스택) |
| 단편화 | 내부 단편화 | 외부 단편화 |

페이징은 메모리를 동일한 크기의 페이지로 쪼갠다. 프로세스를 물리적으로 분할하여 빈 공간에 배치하므로 외부 단편화가 없다. 하지만 마지막으로 할당된 페이지에 공간이 남으면 내부 단편화가 발생한다.

세그멘테이션은 코드, 데이터, 스택처럼 의미론적 단위로 메모리를 분할한다. 사용자가 정의한 논리적 구조를 반영하므로 보호와 공유가 쉽다. 하지만 크기가 제로로 서로 달라 메모리 사이에 빈틈이 생기는 외부 단편화가 발생한다.

## 16. [운영체제] 사용자 모드에서 커널 모드로 진입하는 이유는 무엇인가?

<!-- id: dd899ffd-3cf6-4877-9508-eb6e7238bae4 -->

사용자 프로그램이 하드웨어에 직접 접근하여 시스템을 파괴하는 것을 막기 위해서다.

:::stack
사용자 모드 | 프로세스. 제한된 권한으로 실행
커널 모드 | 운영체제. 모든 하드웨어 권한 보유
:::

위 구조처럼 권한을 분리하여 하드웨어 제어권을 독점한다. 프로그램이 메모리나 디스크에 직접 쓰기를 시도하면 CPU가 이를 감지해 커널 모드로 전환한다.

시스템 콜은 이 전환을 수행하는 유일한 통로다. 운영체제가 미리 정해놓은 인터페이스를 통해 요청을 보내고, 커널이 요청의 정당성을 검사한 후 대신 수행한다.

이 과정에서 컨텍스트 스위칭 비용이 발생한다. 빈번한 시스템 콜 호출은 전체 시스템 성능에 영향을 주므로 효율적으로 설계해야 한다.

## 17. [운영체제] 프로세스 주소공간을 나누어 사용하는 이유는 무엇인가?

<!-- id: 93a1ba7f-a849-441e-8656-ba9035bc362e -->

프로세스 간의 간섭을 막고 메모리 관리를 효율적으로 하기 위해서다.

:::stack
코드 | 프로그램 실행 파일의 기계어
데이터 | 전역 변수, 정적 변수
힙 | 런타임에 할당되는 동적 메모리
스택 | 지역 변수, 함수 호출 정보
:::

위 구조는 메모리 활용 목적에 따라 영역을 구분한 것이다. 각 영역은 데이터의 성격과 생명주기가 다르기에 분리하여 관리한다.

스택은 위에서 아래로, 힙은 아래에서 위로 자란다. 두 영역이 서로 마주 보고 자라게 하여 가용 공간을 유동적으로 공유한다.

가상 메모리 기법을 통해 각 프로세스는 독립된 주소공간을 가진다. 이를 통해 한 프로세스의 오류가 다른 프로세스의 메모리를 오염시키는 것을 방지한다.

## 18. [인프라 · 보안] 경쟁 상태를 막으려면 무엇을 고려해야 하는가?

<!-- id: 2d3e822c-6061-4831-aa0f-640315da6da5 -->

공유 자원에 접근하는 순서가 결과에 영향을 주는 상황을 제어해야 한다. 원자적 연산으로 처리하거나 상호 배제 기법을 사용한다.

:::flow
스레드 A -> 자원: 접근 요청
자원 -> 스레드 A: **락 획득**. 단독 접근 권한 부여
스레드 A -> 자원: 데이터 수정
스레드 A -> 자원: **락 해제**. 다른 스레드 접근 허용
:::

위 흐름처럼 임계 구역에 진입하기 전 락을 걸어 다른 스레드의 진입을 막는다. 이는 데이터 정합성을 보장하는 가장 확실한 방법이다.

다만 락의 범위가 넓으면 성능이 떨어진다. 꼭 필요한 구간만 묶거나, 원자적 변수처럼 하드웨어 수준의 명령어를 활용해 오버헤드를 줄여야 한다.

## 19. [인프라 · 보안] 컨테이너는 가상 머신과 무엇이 다른가?

<!-- id: 1728103c-348b-49d7-a413-01febbae2993 -->

커널을 공유한다. 가상 머신은 게스트 운영체제를 통째로 올리지만 컨테이너는 호스트 커널 위에서 프로세스로 돈다.

:::stack
컨테이너 | 앱과 라이브러리만. 커널은 호스트 것을 쓴다
컨테이너 런타임 | 격리와 자원 제한을 건다
호스트 커널 | 하나를 모두가 나눠 쓴다
:::

격리의 뼈대는 커널 기능 둘이다. 네임스페이스가 보이는 것을 가르고 cgroup이 쓸 수 있는 양을 정한다. seccomp이나 SELinux 같은 것이 그 위에 더 얹힌다.

그래서 뜨는 것이 빠르고 이미지가 작다. 대신 커널을 나눠 쓰므로 탈출로 이어지는 커널 취약점이 나오면 격리가 뚫린다. 다른 커널이 필요한 워크로드도 못 올린다.

가상 머신과 고르는 문제가 아니다. 실무에서는 가상 머신 위에 컨테이너를 올린다.

## 20. [자료구조 · 알고리즘] 메모리보다 큰 데이터를 정렬할 때 무엇을 쓰는가?

<!-- id: cdfbedf8-315c-4276-beb1-89e1d2516937 -->

외부 정렬을 사용한다. 데이터를 작은 조각으로 나누어 정렬한 뒤, 이를 다시 합치는 방식을 취한다.

:::flow
데이터 분할 -> 정렬된 런 생성 -> 병합 과정 진행
:::

가장 흔한 방식은 외부 병합 정렬이다. 메모리에 올릴 수 있는 만큼 데이터를 읽어 정렬하고 임시 파일로 저장한다. 이를 '런(Run)'이라고 부른다.

이후 여러 런을 동시에 읽으며 가장 작은 값을 선택해 결과 파일에 쓴다. 이때 최소 힙(Min Heap)을 사용해 병합 속도를 높인다.

디스크 I/O 횟수를 줄이는 것이 핵심이다. 메모리 버퍼 크기를 키우거나 병합 단계를 줄여 읽고 쓰는 횟수를 최소화해야 한다.

## 21. [자료구조 · 알고리즘] 일반 이진트리 대신 이진탐색트리를 사용하는 이유는 무엇인가?

<!-- id: 0e2fdc1c-8df4-4c4b-86c7-86979b559ba7 -->

정렬된 구조를 유지하여 특정 값을 빠르게 찾기 위해서다. 부모 노드를 기준으로 작은 값은 왼쪽, 큰 값은 오른쪽에 배치하여 탐색 범위를 지속해서 줄인다.

| 구분 | 이진트리 | 이진탐색트리 |
| --- | --- | --- |
| 노드 배치 | 규칙 없음 | 왼쪽 < 부모 < 오른쪽 |
| 평균 탐색 | O(N) | O(log N) |

표에서 보듯 이진탐색트리는 탐색 시 매 단계마다 비교 대상을 절반으로 줄여 평균 O(log N) 시간에 데이터에 접근한다. 단순 이진트리는 모든 노드를 확인해야 해 O(N)이 걸린다.

다만 정렬된 데이터가 순서대로 들어오면 한쪽으로 치우친 편향 트리가 된다. 이 경우 선형 탐색과 다를 바 없어 최악의 경우 O(N)으로 성능이 저하된다.

이러한 한계를 극복하기 위해 실무에서는 높이 균형을 자동으로 맞추는 Red-Black 트리나 AVL 트리 같은 자발적 균형 트리를 활용한다.

## 22. [자료구조 · 알고리즘] 해시 테이블의 평균 O(1)이 무너지는 경우는?

<!-- id: 2b02b81f-fd8d-4c73-bea0-074def8764e6 -->

키가 한 버킷으로 몰릴 때다. 평균 O(1)은 해시가 고르게 흩어진다는 전제 위의 값이라, 그 전제가 깨지면 최악 O(n)으로 간다. 완화는 충돌한 것을 어떻게 담느냐와 언제 늘리느냐 두 갈래다.

| 갈래 | 하는 일 | 최악을 어디까지 |
| --- | --- | --- |
| 담는 방식 | 한 버킷이 길어지면 연결 리스트를 트리로 | `O(n)` → `O(log n)` |
| 늘리는 시점 | load factor를 넘으면 버킷을 두 배로 | 애초에 안 몰리게 |

자바 HashMap은 둘을 함께 쓴다. 앞쪽은 이미 몰린 뒤의 방어고, 뒤쪽은 몰리기 전의 예방이다.

몰리는 이유는 둘이다. 해시 함수가 나빠서 자연히 겹치거나, 누군가 일부러 겹치게 만들거나. 뒤쪽이 해시 충돌 공격인데, 사용자 입력이 그대로 키가 되는 자리에서는 실제 공격 벡터가 된다.

늘리는 것 자체에도 값이 있다. 리사이즈는 모든 키를 다시 배치하므로 그 한 번이 무겁다. 분할 상환하면 평균은 O(1)이지만 평균이 지연을 보장하지는 않는다 — 응답 시간이 중요한 경로에서는 이 한 번이 튀는 지점으로 나타난다.

면접에서는 왜 버킷 수를 2의 거듭제곱으로 잡는지로 한 단계 더 들어온다. 나머지 연산 대신 비트 마스크를 쓸 수 있어서다. 대신 하위 비트만 보게 되므로 해시를 한 번 더 섞어야 한다.

## 23. [프레임워크] 빈 초기화 로직은 어느 시점에 실행해야 하는가?

<!-- id: 412ece4d-926e-4e50-a424-d6938987089b -->

의존성 주입이 끝난 뒤 초기화 콜백에서 실행해야 한다. 생성자에서는 모든 주입과 컨테이너 후처리가 끝났다고 보장할 수 없다.

:::flow
컨테이너 -> 빈: 인스턴스를 만들고 의존성을 주입한다
빈 후처리기 -> 빈: 초기화 전 처리를 한다
컨테이너 -> 빈: @PostConstruct 등 콜백을 호출한다
빈 후처리기 -> 빈: 프록시 등 초기화 후 처리를 한다
:::

초기화 콜백은 @PostConstruct, InitializingBean, initMethod 순서로 호출된다. 애플리케이션 로직은 스프링 인터페이스보다 애너테이션이나 설정 콜백에 두는 편이 덜 결합된다.

종료 때는 @PreDestroy 같은 소멸 콜백이 실행된다. 다만 prototype 빈은 생성 뒤 컨테이너가 추적하지 않으므로 호출자가 정리해야 한다.

## 24. [프레임워크] 외부 롤백과 무관한 기록은 어떻게 남기는가?

<!-- id: ac244c68-6b8c-4c76-a760-b128dad66f52 -->

감사 기록을 별도 빈의 REQUIRES_NEW 메서드로 호출한다. 기존 트랜잭션을 보류하고 새 트랜잭션에서 커밋해야 외부 롤백과 분리된다.

:::flow
외부 작업 -> 기존 트랜잭션: 변경 수행
기존 트랜잭션 -> 프록시 빈: 감사 기록 호출
프록시 빈 -> 새 트랜잭션: 기존 작업 보류
새 트랜잭션 -> DB: 기록 독립 커밋
:::

REQUIRED는 기존 트랜잭션에 합류한다. 내부 예외를 잡아도 이미 rollback-only가 됐다면 마지막 커밋에서 예상치 못한 롤백이 발생한다.

REQUIRES_NEW는 외부 연결을 잡아 둔 채 새 연결을 요구할 수 있다. 동시 요청 수에 비해 풀이 작으면 연결 고갈이나 교착 위험이 커진다.

NESTED는 같은 물리 트랜잭션의 savepoint로 부분 롤백한다. 외부 트랜잭션이 롤백하면 내부 변경도 사라지므로 독립 커밋과 다르다.

같은 객체 안의 self-invocation은 보통 프록시를 지나지 않는다. 전파 설정이 적용되도록 별도 빈 경계를 만들거나 호출 구조를 바꿔야 한다.

## 25. [프론트엔드] React Hook을 사용하는 이유는 무엇인가?

<!-- id: d2c66d5d-e803-4db2-a174-9a966c16328f -->

함수형 컴포넌트에서도 상태 관리와 생명주기 기능을 사용할 수 있기 때문이다.

:::stack
클래스 컴포넌트 | this.state, lifecycle methods
함수형 컴포넌트 | useState, useEffect
:::

기존 클래스 컴포넌트는 로직 재사용이 어렵고 코드가 비대해지는 경향이 있었다. 훅을 통해 상태 관련 로직을 함수로 분리하여 여러 컴포넌트에서 공유할 수 있다.

또한, useEffect를 통해 마운트, 업데이트, 언마운트 시점을 하나의 훅으로 통합 관리한다. 이는 코드의 응집도를 높이고 가독성을 개선한다.

## 26. [프론트엔드] 리렌더링이 필요 이상으로 도는 이유는?

<!-- id: c40eac52-7aa5-4447-ad08-2595e5f80928 -->

렌더마다 새 값이 만들어지기 때문이다. 객체와 함수는 내용이 같아도 참조가 달라서, 비교하는 쪽은 매번 바뀐 것으로 본다.

| 무엇을 넘기나 | 렌더마다 | 결과 |
| --- | --- | --- |
| 문자열·숫자 | 같은 값 | 다시 안 그린다 |
| 인라인 객체·배열 | 새 참조 | 매번 다시 그린다 |
| 인라인 함수 | 새 참조 | 매번 다시 그린다 |

부모가 다시 그려지면 자식도 따라 그려지는 것이 기본이다. 대부분은 그래도 싸서 문제가 안 된다. 목록이 길거나 자식이 무거울 때만 비용이 눈에 띈다.

그때 쓰는 것이 메모다. 자식을 `memo`로 감싸고 넘기는 값을 고정한다. 다만 감싸기만 하고 인라인 객체를 계속 넘기면 비교만 늘고 효과는 없다.

메모를 먼저 뿌리는 것은 대개 손해다. 비교에도 값이 들고 코드가 읽기 어려워진다. 프로파일러로 실제 느린 곳을 찾은 뒤에 붙인다.

## 27. [프론트엔드] 웹 서버와 WAS의 역할 분담은 왜 하는가?

<!-- id: bf82e0fb-89e4-44fe-b91f-a096579ddb48 -->

정적 리소스 처리 효율을 높이고 서버 부하를 분산하기 위해서다.

:::stack
웹 서버 | HTML, CSS, 이미지 등 정적 파일 처리
WAS | DB 조회, 비즈니스 로직 등 동적 콘텐츠 생성
:::

웹 서버가 앞단에서 정적 파일을 먼저 처리하면 WAS는 무거운 로직 수행에만 집중할 수 있다. 요청의 성격에 따라 처리 주체를 나누어 전체 응답 속도를 높인다.

또한 WAS에 장애가 발생해도 웹 서버가 에러 페이지를 대신 보여줄 수 있다. 여러 대의 WAS를 웹 서버 뒤에 배치하여 부하를 나누는 로드밸런싱 구조를 구축하기 쉽다.

## 28. [프론트엔드] 화면이 바뀐 뒤 포커스는 어디로 보내는가?

<!-- id: 6f9ce9df-774f-495d-bbe9-c14986056df8 -->

사용자가 다음 행동을 이해할 수 있는 지점으로 보낸다. 모달은 제목이나 첫 입력에 둔다. 닫을 때는 모달을 연 요소로 돌려보낸다.

:::flow
사용자 -> 열기 버튼: 모달을 연다
열기 버튼 -> 모달 제목: 포커스를 옮긴다
모달 -> 열기 버튼: 닫을 때 되돌린다
:::

모달이 열린 동안 Tab 이동은 모달 안에 머물러야 한다. 배경은 키보드와 보조 기술에서 비활성화한다. Esc로 닫는 경로도 제공한다.

DOM 순서를 시각적 순서와 맞춘다. 포커스 표시를 없애지 않는다. 자동 이동은 화면 변화로 현재 맥락이 끊길 때만 사용한다.
