## 1. [네트워크] DNS 조회는 어떤 순서로 도는가?

<!-- id: e701e42e-a3dc-44b7-baa1-332f197e90b1 -->

가까운 캐시부터 확인하고 없으면 위로 올라간다. 브라우저·운영체제·리졸버 순으로 묻고, 아무도 모를 때만 루트에서 시작해 단계마다 다음 서버를 안내받는다.

:::flow
브라우저 -> 리졸버: 캐시에 없다. 대신 물어봐 달라
리졸버 -> 루트: .com은 누가 아는가
루트 -> 리졸버: com 네임서버 주소다
com -> 리졸버: example.com 네임서버 주소다
리졸버 -> 브라우저: 최종 IP다. TTL만큼 캐시해라
:::

한 번에 답을 주는 것이 아니라 다음에 물을 곳을 알려준다. 루트가 모든 도메인을 알 필요가 없어서 이 구조가 버틴다.

TTL이 실무의 급소다. 값을 바꿔도 캐시가 만료되기 전까지는 옛 주소로 간다. 그래서 이전을 앞두고는 TTL을 미리 낮춰두고, 옮긴 뒤에 되돌린다.

면접에서는 왜 UDP를 쓰는지로 들어온다. 질의 하나에 응답 하나라 연결을 맺는 값이 아깝고, 응답이 커지면 TCP로 다시 묻는 경로가 따로 있다.

## 2. [네트워크] TCP 연결을 끊을 때 TIME_WAIT 상태가 필요한 이유는?

<!-- id: 6928bfd0-7ad2-4316-8122-c9b62c8edce3 -->

마지막 ACK가 유실될 수 있기 때문이다. 먼저 닫는 쪽이 잠시 남아 있어야 상대의 재전송을 받아줄 수 있다.

:::flow
능동 종료 -> 수동 종료: FIN. 보낼 것은 다 보냈다
수동 종료 -> 능동 종료: ACK. 알겠다
수동 종료 -> 능동 종료: FIN. 나도 다 보냈다
능동 종료 -> 수동 종료: 마지막 ACK. **이게 유실되면 상대는 FIN을 다시 보낸다**
:::

4-way handshake의 마지막에서 능동 종료 측은 상대의 FIN에 ACK를 보낸다. 이 ACK가 유실되면 상대는 FIN을 재전송한다. 이때 소켓이 이미 사라졌다면 응답할 주체가 없어 상대는 연결을 정상 종료하지 못한다.

두 번째 이유는 이전 연결의 지연 패킷이다. 같은 포트 조합으로 새 연결이 곧바로 열리면 뒤늦게 도착한 옛 패킷이 새 연결의 데이터로 섞일 수 있다. TIME_WAIT은 그 시간을 벌어준다.

대기 시간은 통상 2MSL이다. 문제는 트래픽이 많은 서버에서 TIME_WAIT 소켓이 쌓여 포트가 고갈되는 것이다. 다만 이는 대개 능동 종료를 서버가 하고 있다는 신호다.

면접에서는 해결책을 물어온다. `SO_REUSEADDR`나 커널 파라미터를 만지기 전에 keep-alive로 연결을 재사용하는 쪽이 먼저다. 원인이 연결을 너무 자주 맺고 끊는 데 있기 때문이다.

## 3. [네트워크] 연결 설정 왕복을 언제 줄일 수 있는가?

<!-- id: af9fd00b-4fa7-4b8c-8f3f-ea6b0470bdbe -->

새 TCP 연결의 상태 동기화는 생략할 수 없다. 대신 연결을 재사용하거나 재접속 정보를 활용해 애플리케이션 데이터 전송을 앞당길 수 있다.

:::flow
클라이언트 -> 서버: SYN. 시작 순번을 알린다
서버 -> 클라이언트: SYN + ACK. 수락하고 순번을 알린다
클라이언트 -> 서버: ACK. 양쪽 상태가 맞았음을 확인한다
:::

세 단계는 양쪽의 송수신 가능 여부와 초기 순번을 확인한다. 한 단계를 없애면 지연 패킷을 새 연결로 오인하거나 반쪽 연결이 늘 수 있다.

Keep-Alive와 연결 풀은 이미 맺은 연결을 다시 쓴다. 새 핸드셰이크 자체를 줄이므로 가장 일반적인 지연 절감 수단이다.

TCP Fast Open은 쿠키가 있는 재접속에서 SYN에 데이터를 실을 수 있다. 핸드셰이크는 계속 진행되며 중간 장비 호환성과 재전송 안전성을 고려해야 한다.

## 4. [데이터베이스] DB 커넥션을 매번 새로 맺는 비용이 큰 이유는?

<!-- id: 5d9cb401-d07f-46db-885b-c2a94c063919 -->

커넥션 생성은 객체 하나를 만드는 일이 아니다. 네트워크 연결부터 세션 준비까지 여러 단계를 매번 다시 밟는다.

한 번 맺을 때 실제로 오가는 것은 이렇다. 단계마다 왕복이 끼어 있어 밀리초가 쌓인다.

:::flow
앱 -> DB: TCP 연결 요청. 3-way handshake가 먼저 돈다
앱 -> DB: 인증 정보 전달. 계정과 권한을 확인한다
DB -> 앱: 세션 준비 완료. 내부 자원을 할당한 뒤 응답한다
:::

요청마다 맺고 닫으면 이 비용이 응답 시간에 그대로 실린다. 동시 요청이 몰리면 문제가 커진다. DB가 질의 처리 대신 커넥션 생성과 해제에 CPU와 메모리를 쓰기 때문이다.

connection pool은 두 가지를 한다. 미리 만들어 둔 커넥션을 재사용해 생성 비용을 없앤다. 동시에 DB로 나가는 커넥션 수에 상한을 둬 DB를 보호한다. 뒤쪽이 더 중요하다.

면접에서는 pool 크기를 어떻게 정하느냐로 한 단계 더 들어온다. 크게 잡으면 DB 자원을 과점유하고 작게 잡으면 애플리케이션 쪽 대기가 늘어난다는 양면을 함께 말할 수 있어야 한다.

## 5. [데이터베이스] 낙관적 락을 사용할 때 데이터 충돌이 발생하면 애플리케이션 수준에서 재시도 로직을 어떻게 구현하는가?

<!-- id: ce219de9-f5fb-45ac-bcff-55edd4b4b8ec -->

낙관적 락 충돌 발생 시 애플리케이션은 예외를 감지하고 일정 횟수 재시도하는 로직을 수행해야 한다. JPA 환경에서는 ObjectOptimisticLockingFailureException을 포착하여 트랜잭션을 다시 시작한다. Spring 기반 애플리케이션에서는 @Retryable 어노테이션이나 Loop 기반의 재시도 컴포넌트를 주로 활용한다. 재시도 구현 시 단순 반복보다는 대기 시간을 두는 백오프 전략을 적용하는 것이 핵심이다. 즉시 재시도하면 동일한 충돌이 연속으로 발생하여 시스템 부담을 늘린다. 지수 백오프나 무작위 지터를 추가하면 동시 요청이 분산되어 재시도 성공률이 대폭 상승한다. 면접에서 강조되는 지점은 트랜잭션 경계와 영속성 컨텍스트의 분리다. 이미 예외가 발생한 트랜잭션 내부에서 루프를 돌면 영속성 컨텍스트가 롤백 전용으로 표시되어 정상적으로 재시도되지 않는다. 따라서 재시도 로직은 반드시 트랜잭션 외부에서 작동하여 매 시도마다 새로운 트랜잭션을 시작해야 한다. 지정한 최대 재시도 횟수를 초과하면 최종 실패로 처리하고 적절한 후속 조치를 취해야 한다. 사용자에게 예외 메시지를 전달하거나 비동기 큐로 이관하여 보상 트랜잭션을 수행한다. 무한 재시도는 데이터베이스 연결을 고갈시키므로 반드시 엄격한 상한선을 두어야 한다.

## 6. [데이터베이스] 데이터베이스에서 EXISTS 서브쿼리와 IN 서브쿼리를 조인으로 변환할 때 발생하는 차이점은 무엇인가?

<!-- id: 9e5a2ea6-ae8f-4cb4-b3fc-0c16b9e0d465 -->

서브쿼리에 중복 데이터가 있을 때 일반 조인으로 변환하면 결과 행이 늘어나는 문제와 NULL 값 평가 메커니즘의 차이다.

| 기준 | IN / EXISTS 서브쿼리 | 일반 INNER JOIN 변환 |
| --- | --- | --- |
| 결과 건수 | 메인 테이블 행 수 유지 | 서브쿼리 중복 시 행 수 증가 |
| NULL 처리 | IN은 UNKNOWN 처리, EXISTS는 무시 | ON 조건 절칙에 따라 평가 |

IN과 EXISTS는 조건을 만족하는 행이 있는지 확인하는 세미 조인(Semi-Join)으로 동작한다. 따라서 서브쿼리에 중복 데이터가 있어도 메인 테이블의 결과 행이 늘어나지 않는다. 반면 일반 INNER JOIN으로 변환하면 1:N 관계에 의해 결과 수가 부풀어 오른다.

중복 뻥튀기를 막으려면 조인 변환 시 DISTINCT나 GROUP BY를 명시해야 한다. 그러나 최신 RDBMS 옵티마이저는 IN과 EXISTS를 내부적으로 세미 조인 알고리즘으로 자동 최적화하므로 무조건 조인으로 바꿀 필요는 없다.

부정 조건인 NOT IN을 변환할 때는 NULL 처리를 조심해야 한다. NOT IN 서브쿼리에 NULL이 섞여 있으면 결과가 전부 비어버리지만, NOT EXISTS나 LEFT OUTER JOIN 변환은 NULL을 무시하고 정상 평가한다.

## 7. [데이터베이스] 트랜잭션 격리 수준을 결정하는 기준은 무엇인가?

<!-- id: c41f45e9-a7c0-4357-8947-e82a6baf3b50 -->

데이터 정합성 보장 수준과 시스템 성능 사이의 트레이드오프를 기준으로 결정한다.

| 기준 | 격리 수준 낮음 | 격리 수준 높음 |
| --- | --- | --- |
| 정합성 | 낮음 (이상 현상 발생) | 높음 (데이터 일관성) |
| 성능/처리량 | 높음 (잠금 최소화) | 낮음 (잠금/대기 증가) |

격리 수준이 낮으면 여러 트랜잭션이 같은 데이터를 동시에 읽고 쓸 수 있어 처리량이 늘어난다. 하지만 더티 리드나 팬텀 리드 같은 현상이 발생해 데이터가 꼬일 수 있다.

반대로 격리 수준을 높이면 엄격한 잠금을 사용해 정합성을 완벽하게 보장한다. 다만, 트랜잭션 간 대기 시간이 길어져 전체적인 시스템 응답 속도가 떨어진다.

실무에서는 보통 Read Committed를 기본으로 쓰며, 정밀한 계산이 필요한 금융권이나 결제 로직에서는 Repeatable Read 이상을 선택한다.

## 8. [모바일] 상태 소유자를 잘못 두면 어떤 버그가 생기는가?

<!-- id: 3f06eab6-e006-438c-88ec-97153237b346 -->

뷰 재생성 때 상태가 초기화되거나 모델이 중복 생성된다. 소유권이 여러 곳에 생기면 화면마다 값이 어긋나고 불필요한 갱신도 늘어난다.

:::stack
상위 뷰 | 상태의 단일 소유자다
하위 뷰 | Binding으로 변경 통로를 받는다
렌더링 | 읽은 상태가 바뀌면 다시 계산된다
:::

작은 값은 가장 가까운 뷰가 State로 소유한다. 하위 뷰가 같은 값을 편집해야 하면 복사하지 않고 Binding을 전달한다.

ObservableObject 모델을 뷰가 만들고 유지하면 StateObject를 쓴다. 외부에서 받은 모델은 ObservedObject로 관찰해 소유와 관찰을 분리한다.

넓게 공유하는 의존성은 Environment로 주입할 수 있다. 편리하더라도 범위를 넓히면 데이터 흐름과 테스트 의존성이 숨는다.

## 9. [모바일] 자동 참조 계산인데 왜 메모리가 남는가?

<!-- id: 053bb484-67b1-4627-b5f8-1313b4d7edaf -->

강한 참조 고리가 생기면 각 객체의 참조 수가 0이 되지 않기 때문이다. 외부 소유자가 놓아도 고리 안의 객체는 해제되지 않는다.

:::flow
객체 A -> 객체 B: 강한 참조로 수를 올린다
객체 B -> 객체 A: 강한 참조로 수를 올린다
소유자 -> 객체 A: 참조를 놓아도 두 객체가 남는다
:::

소유 관계가 아닌 역참조는 weak로 끊는다. 대상이 먼저 사라지지 않는다는 수명 보장이 있을 때만 unowned를 쓴다.

클로저가 self를 강하게 캡처하고 self가 그 클로저를 보관해도 고리가 된다. 캡처 목록은 수명과 비동기 실행 시점을 따져 정한다.

deinit 로그와 메모리 그래프로 해제 여부를 확인한다. weak를 무조건 붙이면 작업 중 객체가 사라지는 다른 버그를 만들 수 있다.

## 10. [모바일] 회전 뒤에도 남겨야 할 상태는 어디에 두는가?

<!-- id: 0948a5a7-ba14-40a8-8f67-064d86dcf801 -->

다시 계산할 화면 데이터는 ViewModel에 둔다. 선택값과 입력처럼 복원에 필요한 작은 UI 상태는 저장 상태에 둔다. 영구 데이터는 저장소에 둔다.

| 기준 | ViewModel | 저장 상태 |
| --- | --- | --- |
| 구성 변경 | 같은 인스턴스를 잇는다 | 값으로 복원한다 |
| 프로세스 종료 | 사라진다 | 조건부로 복원한다 |

회전과 창 크기 변경은 Activity를 재생성할 수 있다. ViewModel은 이 재생성 동안 메모리 데이터를 유지한다.

시스템이 프로세스를 죽이면 ViewModel도 사라진다. 이때 화면을 다시 만드는 최소 키만 Bundle 기반 저장 상태에서 복원한다.

큰 목록이나 비즈니스 데이터는 저장 상태에 넣지 않는다. ID나 검색어만 남기고 데이터 계층에서 다시 읽는다.

## 11. [아키텍처 · 분산시스템] 스트레티지 패턴을 사용하는 판단 기준은 무엇인가?

<!-- id: 97035d84-ac30-45eb-8af1-758190d3769d -->

실행 중에 알고리즘을 선택해야 하거나, 조건문이 계속 늘어나는 구조를 제거하고 싶을 때다.

| 기준 | 조건문(if/switch) | 스트레티지 패턴 |
| --- | --- | --- |
| 변경 빈도 | 로직 추가 시 코드 수정 | 클래스 추가로 확장 |
| 결합도 | 로직이 강하게 결합 | 인터페이스로 분리 |
| 런타임 변경 | 불가능 또는 어려움 | 동적으로 교체 가능 |

상위 클래스나 클라이언트가 구체적인 구현체에 의존하지 않게 한다. 이를 통해 새로운 전략을 추가해도 기존 코드를 수정하지 않는 개방-폐쇄 원칙을 지킬 수 있다.

객체 내부의 상태에 따라 동작을 바꿔야 할 때 유용하다. 예를 들어 결제 수단이 카드, 페이, 계좌이체로 늘어날 때 각각의 전략 클래스로 분리하면 유지보수가 쉽다.

다만 전략의 개수가 너무 적거나 거의 바뀌지 않는다면 오히려 클래스 수가 늘어나 구조가 복잡해지는 오버헤드가 발생한다.

## 12. [언어 · 런타임] JVM 메모리 영역은 어떻게 구분하는가?

<!-- id: edc30f9f-9306-4469-9138-9b49efd609b8 -->

런타임 데이터 영역으로 구분하며, 스레드 간 공유 여부에 따라 공유 영역과 개별 영역으로 나눈다.

:::stack
공유 영역 | Heap, Method Area
개별 영역 | Stack, PC Register, Native Method Stack
:::

공유 영역은 모든 스레드가 접근 가능하다. 가비지 컬렉션의 대상이 되어 메모리 관리가 자동화된다.

개별 영역은 스레드 생성 시 함께 생성되고 종료 시 사라진다. 스레드만 접근하므로 동기화 문제가 발생하지 않는다.

## 13. [언어 · 런타임] 객체와 호출 프레임은 왜 따로 저장하는가?

<!-- id: 311895c6-7c6c-4d1d-8961-691de7f6f96d -->

객체는 여러 스레드가 공유할 수 있어 힙에 둔다. 호출 프레임은 스레드마다 독립된 실행 상태라 각 JVM 스택에 둔다.

| 기준 | 공유 영역 | 스레드별 영역 |
| --- | --- | --- |
| 대표 공간 | 힙, 메서드 영역 | JVM 스택, PC 레지스터 |
| 수명 | JVM과 함께 | 스레드와 함께 |

프레임에는 지역 변수, 피연산자 스택, 반환 정보가 있다. 메서드가 끝나면 프레임이 사라져 별도 GC가 필요 없다.

힙의 객체는 참조가 끊겨도 바로 사라지지 않는다. GC가 도달 불가능하다고 판단한 뒤 회수한다.

메서드 영역은 명세상의 공유 영역이다. HotSpot은 클래스 메타데이터를 네이티브 메모리의 Metaspace에 둔다.

## 14. [언어 · 런타임] 순환 참조 객체도 회수할 수 있는 이유는?

<!-- id: 25d4b8af-8c78-490a-ad1e-471800e6255d -->

HotSpot의 추적식 수집기는 참조 횟수가 아니라 GC 루트에서 도달 가능한지를 본다. 서로 가리켜도 루트에서 닿지 않으면 둘 다 회수 대상이다.

:::flow
GC 루트 -> 객체 그래프: 참조를 따라 생존 객체를 표시한다
수집기 -> 미도달 객체: 메모리를 회수한다
수집기 -> 생존 객체: 필요하면 이동하고 압축한다
:::

GC 루트에는 실행 중인 스레드의 스택 참조와 정적 참조 등이 포함된다. 루트가 살아 있으면 그 경로의 객체도 살아 있다.

세대별 수집은 대다수 객체가 빨리 죽는다는 관찰을 이용한다. 새 객체를 자주 수집하고 오래 산 객체는 승격한다.

표시와 이동 과정에는 일시 정지가 생길 수 있다. 동시 수집기는 일부 단계를 애플리케이션과 겹쳐 정지 시간을 줄인다.

---

## 15. [언어 · 런타임] 파이썬의 가비지 컬렉션은 무엇으로 동작하는가?

<!-- id: 195d1e9d-b104-40d8-9948-406614f30576 -->

참조 횟수 계산과 세대별 가비지 컬렉션의 조합으로 동작한다. 기본적으로 참조 횟수가 0이 되면 즉시 메모리에서 제거한다.

:::stack
참조 횟수 | 기본 메커니즘. 0이 되면 즉시 해제
세대별 GC | 보조 메커니즘. 순환 참조 해결
:::

참조 횟수 계산은 빠르고 즉각적이다. 하지만 두 객체가 서로를 가리키는 순환 참조가 발생하면 횟수가 0이 되지 않아 메모리 누수가 생긴다.

이를 해결하기 위해 세대별 GC가 주기적으로 동작한다. 객체를 0, 1, 2세대로 나누어 오래 살아남은 객체는 덜 자주 검사하여 성능 효율을 높인다.

## 16. [운영체제] 데몬 프로세스는 왜 세션 리더로 지정되지 않는가?

<!-- id: e2a3399c-208b-4918-a710-97027c0f9bc7 -->

백그라운드에서 계속 실행되어야 하므로 제어 터미널로 인한 종료 신호를 받지 않기 위해서다.

:::stack
터미널 세션 | 사용자 로그인, 쉘로 제어
데몬 프로세스 | 세션 리더가 아니며, 제어 터미널 없음
:::

사용자가 로그아웃하면 세션 리더가 받은 SIGHUP 신호를 모든 프로세스에만 보낸다. 데몬은 의도적으로 세션 리더가 mãos a own sessiony는 잊고 새 세션을 만들어 리더가 아닌 자식으로 남는다.

setsid() 시스템 호출을 setsid() 시스템 호출을 통해 세션과 프로세스 그룹으로적으로지정되지 않은 상태로 분리//분리된다. 이를 통해 터미널과의 연결 고리를 게 끊어내어 시스템 리더가 종료 신호를를 보낸다고 해도 영향을 받지지 않고 계속 실행된다.

## 17. [운영체제] 인터럽트와 폴링의 결정적인 차이는 무엇인가?

<!-- id: 3d43d6fb-daf3-422c-ac82-56c0e74b4e55 -->

이벤트 발생 시 CPU가 직접 확인하는지 아니면 장치가 CPU를 깨우는지의 차이다.

:::flow
장치 -> CPU: 인터럽트 요청(IRQ). 신호를 보낸다
CPU -> 장치: 인터럽트 서비스 루틴(ISR) 실행. 요청을 처리한다
::: 

폴링은 CPU가 루프를 돌며 상태를 계속 확인하는 방식이다. 장치가 준비될 때까지 CPU가 대기하므로 자원 낭비가 심하다.

반면 인터럽트는 하드웨어 신호로 CPU의 실행 흐름을 제어한다. CPU는 다른 작업을 수행하다가 신호가 오면 처리 루틴으로 점프한다.

이 흐름은 현대 운영체제의 멀티태스킹을 가능하게 하는 핵심 기제다. 하드웨어 인터럽트와 소프트웨어 인터럽트(트랩)를 구분하여 처리하는 지점이 면접의 핵심이다.

## 18. [인프라 · 보안] JWT를 세션 대신 쓸 때 무엇을 잃는가?

<!-- id: 45d1365b-23d9-48e2-8e92-6c1e964f5709 -->

즉시 무효화 능력을 잃는다. 서버가 상태를 갖지 않는다는 장점이 그대로 단점이 된다.

세션은 서버가 저장소를 들고 있으므로 지우면 그 순간 끝난다. JWT는 서명만 유효하면 통과하므로 발급된 토큰을 회수할 방법이 없다. 로그아웃, 권한 변경, 탈취 대응이 전부 만료 시각까지 지연된다.

| 기준 | 세션 | JWT |
| --- | --- | --- |
| 상태 보관 | 서버가 들고 있다 | 토큰 안에 들어 있다 |
| 즉시 무효화 | 지우면 끝 | **만료까지 못 막는다** |
| 서버 확장 | 저장소 공유가 필요하다 | 서버끼리 공유할 것이 없다 |

통상적인 대응은 수명을 짧게 가져가고 리프레시 토큰을 붙이는 것이다. 다만 리프레시 토큰은 결국 서버가 상태를 들고 관리해야 하므로, 무상태라는 원래 이점이 상당 부분 사라진다.

저장 위치도 문제다. 로컬 스토리지는 XSS에 그대로 노출되고, 쿠키는 CSRF를 따로 막아야 한다. 어디에 둬도 공짜가 아니다.

판단 기준은 규모다. 서버가 여러 대이고 세션 공유 비용이 실제 부담일 때 JWT가 값을 한다. 단일 서비스에서 관성으로 고르면 잃는 쪽이 크다.

## 19. [인프라 · 보안] 리팩토링과 기능 추가를 동시에 하는 이유는 무엇인가?

<!-- id: 0e488dff-b273-44ab-8a74-76b9f33989a9 -->

코드의 수정 범위와 영향도를 명확히 구분하여 버그 발생 가능성을 낮추기 때문이다.

| 기준 | 리팩토링 | 기능 추가 |
| --- | --- | --- |
| 목적 | 내부 구조 개선 | 새로운 동작 구현 |
| 외부 동작 | 동일함 | 변경됨 |
| 테스트 | 기존 테스트 통과 | 새로운 테스트 추가 |

리팩토링 단계에서는 기존 테스트 코드가 계속 통과해야 한다. 구조만 바꾸고 동작은 유지해야 하므로, 기능 변경이 섞이면 어디서 버그가 발생했는지 찾기 힘들다.

기능 추가 단계에서는 리팩토링으로 정돈된 구조 위에 새 기능을 얹는다. 깨끗한 토대가으로 인해 구현 속도가 빨라지고 예상치 못한 사이드 이펙트를 줄일 수 있다.

두 작업을 분리하여 커밋 단위로 관리하면 코드 리뷰어의 인지 부하를 줄인다. 변경 사항이 '구조 개선'인지 '동작 변경'인지 명확히 알 수 있어 검증 효율이 높아진다.

## 20. [자료구조 · 알고리즘] 공유 자료구조를 Thread-Safe하게 만드는 방법은 무엇인가?

<!-- id: b702a8a3-b7b2-460d-9dd1-df95688272d5 -->

상호 배제(Mutual Exclusion)를 통해 한 번에 하나의 스레드만 데이터에 접근하도록 제어하는 것이다.

| 기준 | 동기화 블록 | CAS (Compare-And-Swap) | 
| --- | --- | --- | 
| 방식 | 락으로 접근 제어 | 값 비교 후 교체 | 
| 성능 | 컨텍스트 스위칭 비용 발생 | 논블로킹으로 성능 높음 | 
| 특징 | 구현이 쉽고 안전함 | 스핀락으로 CPU 점유율 상승 | 

동기화 블록이나 `synchronized` 키워드를 사용하면 임계 영역을 최소화하여 동시성 제어를 가능하게 한다. 하지만 락을 획득하지 못한 스레드는 대기 상태로 전환되어 컨텍스트 스위칭 비용이 발생한다.

CAS 연산은 락을 사용하지 않은 논블로킹 알고리즘으로 구현된다. 현재 값과 예상 값이 일치할 때만 새로운 값으로 교체하는 원자적(Atomic) 원리를 이용한다.

최근에는 읽기-쓰기 락(Read-Write Lock)을 것처럼 읽기 작업이 많을 때 읽기 권한을 대해로 분리하여 효율을 높이는 방식을 주로 사용한다.

---

## 21. [자료구조 · 알고리즘] 스택과 큐의 가장 큰 차이는 무엇인가?

<!-- id: 48921120-138d-4047-ade4-70261a9610f9 -->

데이터가 나가는 순서의 차이다. 스택은 마지막에 들어온 것이 먼저 나가고, 큐는 먼저 들어온 것이 먼저 나간다.

| 기준 | 스택 | 큐 |
| --- | --- | --- |
| 처리 순서 | LIFO (후입선출) | FIFO (선입선출) |
| 입출력 지점 | 한쪽 끝에서만 가능 | 입구와 출구가 다름 |

스택은 되돌리기(Undo)나 함수 호출 스택처럼 가장 최근의 상태를 기억해야 할 때 쓴다. 반면 큐는 프로세스 스케줄링이나 프린터 대기열처럼 순서대로 처리해야 할 때 적합하다.

두 구조 모두 삽입과 삭제의 시간 복잡도가 O(1)이다. 하지만 큐를 배열로 구현할 때 앞쪽 데이터를 지우면 나머지 데이터를 당겨야 하는 비용이 발생한다. 이를 위해 원형 큐를 주로 사용한다.

## 22. [자료구조 · 알고리즘] 최소 신장 트리(MST)를 구성하는 알고리즘으로 무엇을 선택하는가?

<!-- id: 929059df-0698-4f86-ac43-2a540fb31a54 -->

가중치 합이 최소가 되는 신장 트리를 찾기 위해 크루스칼이나 프림 알고리즘을 선택한다. 데이터의 밀집도에 따라 선택 기준이 달라진다.

| 기준 | 크루스칼 | 프림 |
| --- | --- | --- |
| 데이터 밀집도 | 희소 그래프 | 밀집 그래프 |
| 구현체 | Union-Find | 우선순위 큐 |

크루스칼 알고리즘은 간선 위주로 선택한다. 가중치가 낮은 간선을 우선적으로 연결하며, 사이클이 발생하지 않는지 Union-Find로 검사한다.

프림 알고리즘은 정점 위주로 선택한다. 현재 트리로 연결된 정점들 중 가장 가중치가 낮은 정점을 추가하며 확장한다.

간선 수가 적은 희소 그래프에서는 크루스칼이 효율적이다. 반면 정점 수가 많고 간선이 빽빽한 밀집 그래프에서는 프림이 유리하다.

## 23. [프레임워크] ORM을 사용하는 이유는 무엇인가?

<!-- id: 6876f3f6-e938-491f-980c-739b5d094da5 -->

객체지향적 설계와 관계형 데이터베이스 간의 패러다임 불일치를 해결하기 때문이다. 이를 통해 개발자는 SQL로 인한 반복적인 CRUD 작업을 줄이고 비즈니스 로직에 집중할 수 있다.

| 기준 | SQL 매퍼 | ORM | 
| --- | --- | --- | 
| 중심 관점 | 테이블/SQL | 객체/엔티티 | 
| 생산성 | 쿼리 직접 작성 | 메서드 호출로 처리 | 
| 유지보수 | 스키마 변경 시 수정 많음 | 엔티티 수정으로 반영 | 

위 표는 SQL 매퍼와 ORM의 결정적인 차이를 보여준다. ORM은 데이터베이스의 행을 객체로 매핑하여 자바 객체로서의 상속이나 참조로 데이터를 처리한다.

하지만 ORM은 학습 곡선이 높고, 복잡한 쿼리 작성 시 성능 최적화가 어려울 수 있다. 특히 N+1 문제는 발생 빈도가가 높으며, 이를 해결하기 위해 페치 조인이나 @EntityGraph 등을 적절히 사용해야 한다.

## 24. [프레임워크] 스프링 AOP의 프록시 자기 호출 시 무엇이 문제인가?

<!-- id: 77772f02-fcc0-4bd7-b51d-9abd0e553506 -->

프록시 객체를 거치지 않고 대상 객체 스스로 own method를 호출할 때 AOP 적용으로 인한 부가 기능이 동작하지 않는 문제다.

:::flow
외부 호출 -> 프록시 -> 대상 객체: AOP 기능 수행 후 실제 로직으로 전달
외부 호출 -> 대상 객체: **자기 호출** 발생. 프록시를 거치지 않고 직접 호출하여 AOP 누락
:::

스프링은 기본적으로 CGLIB이나 JDK Dynamic Proxy를 사용해 대상 객체를 감싸는 프록시를 만든다. 외부에서 호출할 때만 이 프록시를 통해 진입하며, 클래스 내부에서 다른 메서드 호출 시에는 `this`를 통해 직접 호출한다.

이로 인해 `@Transactional`이나 `@Cacheable` 같은 설정이 붙은 내부 메서드를 호출해도 프록시의 가로채기(intercept)가 불가능해져 트랜잭션으로 묶이지 않거나 캐시가 모두 무동작으로 작동한다.

이를 해결하기 위해 `ApplicationContext`에서 자기 자신을 다시 주입받거나, 별도의 서비스로 로직을 분리하여 외부 호출 구조로 바꾼다.

## 25. [프레임워크] 정적 클래스 내부에 정적 메서드를 정의하는 이유는 무엇인가?

<!-- id: 0211b774-3323-4b37-b52c-4c2db13bf42e -->

객체 생성 없이 기능을 제공하기 위해서다. 상태를 가지지 않는 유틸리티 성격의 기능을 묶어두는 용도로 사용한다.

:::stack
정적 클래스 | 유틸리티 클래스. 인스턴스화로 인한 메모리 성능으로 인한 손실을 없앤다
정적 메서드 | 상태 없는 로직. 입력값으로만 결과가만 나오는 same-result same-input 구조다
:::

정적 클래스로 선언하면 외부에서 `new` 키워드로 인스턴스를 생성하는 것을 막을 수 있다. 이는 클래스가 단순한 도구 모음임을 명확히 알리는 설계적 의도이다.

정적 메서드는 인스턴스 변수(필드)에 접근할 수 없다. 오직 정적 변수나 매개변수로 전달받은 데이터로만 동작한다. 따라서 테스트 코드 작성 시 모킹(Mocking)가 어렵다는 단점이 있다.

## 26. [프론트엔드] 계산 단계와 반영 단계를 왜 나누는가?

<!-- id: 39479b2f-fa91-4fa6-a268-0cce74ae001f -->

계산을 중단하거나 다시 시작해도 화면이 중간 상태에 놓이지 않게 하려고 나눈다. DOM과 ref는 커밋에서 일관되게 반영한다.

:::flow
상태 변경 -> 렌더 단계: 새 트리와 변경점을 계산한다
렌더 단계 -> 커밋 단계: DOM과 ref를 반영한다
커밋 단계 -> 브라우저: 변경된 화면을 그린다
:::

렌더 단계는 컴포넌트를 호출해 결과를 계산한다. 우선순위에 따라 중단되거나 폐기될 수 있으므로 외부 부작용을 두면 안 된다.

커밋은 DOM 변경과 ref를 적용하며 중간에 쪼개지 않는다. useLayoutEffect는 페인트 전, useEffect는 대체로 페인트 뒤에 실행된다.

## 27. [프론트엔드] 브라우저가 화면을 그리기까지 무슨 일이 일어나는가?

<!-- id: 1f9fed87-b3c9-492a-95f2-33709bcd174c -->

HTML과 CSS를 각각 트리로 만들고 둘을 합쳐 위치를 계산한 뒤 픽셀로 칠한다. 어느 단계를 건드리느냐에 따라 비용이 크게 갈린다.

:::flow
파서 -> DOM: HTML을 읽어 요소 트리를 만든다
파서 -> CSSOM: 스타일 규칙을 트리로 만든다
DOM+CSSOM -> 렌더 트리: 화면에 나올 것만 남긴다
렌더 트리 -> 레이아웃: 각 요소의 위치와 크기를 잰다
레이아웃 -> 페인트: 색과 그림자를 칠한다
:::

스타일을 바꾸면 어디까지 되돌아가는지가 성능을 가른다. 너비나 위치를 건드리면 레이아웃부터 다시 한다. 색만 바꾸면 페인트만 다시 한다. `transform`과 `opacity`는 합성 단계에서만 처리돼 앞의 둘을 건너뛴다.

자바스크립트가 이 흐름을 막을 수 있다. CSSOM이 완성되기 전에는 스크립트를 실행할 수 없고, 스크립트가 도는 동안에는 파싱이 멈춘다. 스타일시트를 위에, 스크립트를 아래에 두라는 오래된 조언이 여기서 나왔다.

면접에서는 레이아웃을 강제로 일으키는 코드를 짚어온다. 스타일을 바꾼 직후에 `offsetHeight` 같은 값을 읽으면 브라우저가 그 자리에서 레이아웃을 다시 계산한다. 반복문 안에서 쓰기와 읽기를 번갈아 하면 매 회전마다 그 비용이 든다.

## 28. [프론트엔드] 클라이언트 데이터는 어디에 보관해야 하는가?

<!-- id: 7abdb31d-9eb8-484c-8c2d-39a34c013c7d -->

수명, 용량, 접근 범위, 서버 전송 필요성으로 고른다. 작은 서버 연동 값은 쿠키에 둔다. 큰 구조화 데이터는 IndexedDB에 둔다.

| 기준 | 쿠키 | IndexedDB |
| --- | --- | --- |
| 서버 전송 | 자동 | 없음 |
| 용량 | 작음 | 큼 |
| API | 동기 | 비동기 |

sessionStorage는 탭이 살아 있는 동안만 필요한 값에 맞다. localStorage는 단순한 장기 설정에 편하지만 동기 API라 큰 데이터를 다루면 메인 스레드를 막는다.

민감한 값을 자바스크립트로 읽을 수 있는 저장소에 두면 XSS에 노출된다. 세션 식별자는 Secure와 HttpOnly를 적용한 쿠키를 우선 검토한다.
