## 1. [네트워크] HTTP 메서드 선택 기준은 무엇인가?

<!-- id: e1382ce5-221d-40e3-b024-a440a3134b1b -->

리소스의 상태를 변경하는지, 요청이 멱등한지를 기준으로 선택한다.

| 기준 | GET | POST | PUT | PATCH | DELETE |
| --- | --- | --- | --- | --- | --- |
| 상태 변경 | 없음 | 있음 | 있음 | 있음 | 있음 |
| 멱등성 | 멱등 | 비멱등 | 멱등 | 비멱등 | 멱등 |

GET은 조회 목적이며 서버 상태를 바꾸지 않는다. 캐싱이 가능해 응답 속도를 높일 수 있다.

POST는 새로운 리소스를 생성하거나 서버의 상태를 변경할 때 쓴다. 요청할 때마다 결과가 달라질 수 있어 비멱등하다.

PUT은 리소스를 전체 교체한다. 동일한 요청을 여러 번 보내도 결과가 같으므로 멱등하다.

PATCH는 리소스의 일부만 수정한다. 구현 방식에 따라 멱등할 수도, 비멱등할 수도 있어 주의가 필요하다.

## 2. [네트워크] 내부 API에 바이너리 RPC가 유리한 때는?

<!-- id: ff906a57-aafa-47f7-8526-ef90423e5d62 -->

호출 양이 많고 엄격한 계약과 낮은 지연, 스트리밍이 필요할 때 유리하다. 클라이언트와 서버를 함께 통제할 수 있을수록 도입 비용이 낮다.

| 기준 | gRPC | REST JSON |
| --- | --- | --- |
| 계약 | Protobuf 스키마 | 문서 또는 별도 스키마 |
| 전송 | HTTP/2 바이너리 | 주로 텍스트 |
| 스트리밍 | 기본 지원 | 별도 방식 필요 |

Protobuf로 서버와 여러 언어의 클라이언트 코드를 생성한다. 정적 타입 언어에서는 타입 불일치를 컴파일 단계에서 줄일 수 있지만 스키마 호환 규칙을 지켜야 한다.

멀티플렉싱과 작은 메시지는 서비스 간 통신에 효과적이다. 그러나 공개 API에서는 브라우저 지원과 사람이 읽기 어려운 페이로드가 장벽이 된다.

프록시와 관측 도구가 HTTP/2와 gRPC를 제대로 지원하는지도 확인한다. 단순 CRUD나 외부 연동은 REST가 운영과 디버깅에 더 쉬울 수 있다.

## 3. [네트워크] 자물쇠 표시는 무엇을 검증한 결과인가?

<!-- id: 1490ff42-5028-42e8-abb7-d33c132ca451 -->

브라우저가 신뢰 사슬과 도메인, 유효 기간을 확인하고 서버가 개인 키를 가졌음을 검증한 결과다. 사이트의 신뢰성이나 안전한 운영까지 보장하지는 않는다.

:::flow
서버 -> 브라우저: 서버 인증서와 중간 인증서를 보낸다
브라우저 -> 신뢰 저장소: 루트까지 서명 사슬을 확인한다
브라우저 -> 서버: 도메인과 키 소유 증명을 확인한다
:::

루트를 제외한 각 인증서의 서명은 상위 인증서 공개 키로 확인한다. 루트 인증서는 운영체제나 브라우저의 신뢰 저장소에 미리 들어 있다.

브라우저는 접속 호스트가 SAN의 이름과 맞는지 확인한다. 발급 대상이 다른 유효한 인증서를 가져와도 이 단계에서 막힌다.

폐기 상태 확인은 OCSP나 CRL, OCSP Stapling을 활용한다. 구현과 정책에 따라 조회 실패를 엄격히 막지 않을 수 있어 자물쇠를 절대적 보증으로 보면 안 된다.

## 4. [데이터베이스] JOIN 연산의 성능을 결정하는 핵심 요소는 무엇인가?

<!-- id: 50e027c9-dd85-4d2a-b84f-0642577086d2 -->

인덱스 활용 여부와 조인 방식의 선택이다. 인덱스가 없으면 전체 테이블을 훑어야 하므로 비용이 급격히 증가한다.

| 기준 | Nested Loop | Hash Join |
| --- | --- | --- |
| 적합한 데이터 | 소량/인덱스 있음 | 대량/인덱스 없음 |
| 처리 방식 | 중첩 반복 수행 | 해시 테이블 생성 |

Nested Loop 조인은 바깥쪽 테이블의 행마다 안쪽 테이블을 탐색한다. 안쪽 테이블의 조인 컬럼에 인덱스가 있으면 매우 빠르게 동작한다.

Hash Join은 두 테이블 중 작은 쪽으로 해시 맵을 먼저 만든다. 이후 큰 테이블을 읽으며 해시 맵에서 일치하는 값을 찾는다. 대량 데이터 처리에 유리하다.

정렬 상태에 따라 Merge Join이 선택되기도 한다. 옵티마이저는 통계 정보를 바탕으로 데이터 양과 인덱스 상태를 보고 가장 싼 비용의 방식을 결정한다.

## 5. [데이터베이스] 데이터베이스 뷰는 언제 사용하는가?

<!-- id: 577db5ee-a456-43d1-8b9f-14178363b74d -->

복잡한 쿼리를 단순화하거나 보안을 위해 특정 컬럼만 노출할 때 사용한다. 가상 테이블로서 실제 데이터를 저장하지 않고 쿼리문만 저장한다.

| 기준 | 뷰(View) | 일반 테이블 |
| --- | --- | --- |
| 데이터 저장 | 저장 안 함 | 실제 데이터 저장 |
| 물리적 공간 | 정의만 저장 | 데이터만큼 점유 |
| 용도 | 가독성, 보안 | 데이터 관리 |

뷰를 쓰면 복잡한 조인 문을 매번 쓸 필요가 없다. 사용자는 정의된 뷰를 조회함으로써 내부 구조를 몰라도 데이터를 가져올 수 있다.

보안 측면에서는 민감한 정보를 제외한 컬럼만 뷰로 제공한다. 이를 통해 원본 테이블에 직접 접근하지 않고 필요한 데이터만 안전하게 노출한다.

다만 뷰는 조회 시마다 정의된 쿼리가 실행된다. 원본 테이블의 인덱스를 타지 못하는 복잡한 뷰는 성능 저하를 일으킬 수 있다.

## 6. [데이터베이스] 인덱스 범위 스캔과 전체 스캔 중 무엇을 선택하는가?

<!-- id: 552308dc-7dc6-4fb3-b64c-fcd4621f6859 -->

데이터의 선택도와 비용 옵티마이저의 판단에 따라 결정한다. 읽어야 할 데이터가 전체의 일정 비율을 넘으면 인덱스보다 전체 스캔이 빠르다.

| 기준 | 인덱스 범위 스캔 | 전체 스캔 |
| --- | --- | --- |
| 접근 방식 | B-Tree 탐색 후 리프 노드 순회 | 데이터 페이지 순차 읽기 |
| 효율성 | 소량 데이터 추출 시 유리 | 대량 데이터 추출 시 유리 |
| I/O 방식 | 랜덤 I/O 발생 | 순차 I/O 발생 |

인덱스 범위 스캔은 인덱스 페이지를 거쳐 데이터 페이지로 이동하는 랜덤 I/O가 발생한다. 읽을 양이 많아지면 이 오버헤드가 순차적으로 읽는 전체 스캔보다 커진다.

옵티마이저는 통계 정보를 바탕으로 비용을 계산한다. 인덱스를 통해 읽어야 할 페이지 수가 전체 페이지 수의 상당 부분을 차지하면 전체 스캔을 선택한다.

실무에서는 통계 정보가 오래되었을 때 엉뚱한 스캔 방식이 선택되어 성능이 급락한다. 이때는 힌트를 사용해 강제로 실행 계획을 변경해야 한다.

## 7. [모바일] 모바일 요청은 실패할 때마다 다시 보내도 되는가?

<!-- id: 8788eb07-49fa-40ec-bdc5-e7639981f653 -->

실패할 때마다 보내면 안 된다. 일시 오류만 제한적으로 재시도하고 쓰기 요청은 멱등성을 보장해야 한다. 영구 오류와 사용자 취소는 즉시 끝낸다.

:::flow
클라이언트 -> 서버: 요청과 멱등 키를 보낸다
서버 -> 클라이언트: 일시 오류와 대기 정보를 돌려준다
클라이언트 -> 클라이언트: 백오프와 지터로 기다린다
클라이언트 -> 서버: 조건이 맞을 때만 재시도한다
:::

타임아웃과 일부 5xx와 429는 후보가 된다. 상태 코드만 보지 말고 API 계약과 Retry-After를 따른다. 대부분의 4xx는 재시도해도 성공하지 않는다.

지수 백오프는 반복할수록 간격을 늘린다. 지터는 여러 기기가 동시에 깨어 서버를 다시 압박하는 재시도 폭주를 줄인다.

앱이 백그라운드로 가거나 연결이 바뀌면 예약을 다시 판단한다. 꼭 전달할 작업은 메모리가 아닌 영속 큐에 넣고 최대 횟수와 만료 시점을 둔다.

## 8. [모바일] 안드로이드 메인 스레드에서 무거운 작업을 하면 왜 ANR이 발생하는가?

<!-- id: 3ccdd4cf-917c-4b03-83e2-72432d2bc735 -->

메인 스레드가 일정 시간 동안 이벤트 루프를 돌지 못해 사용자 입력에 응답하지 않기 때문이다.

:::flow
사용자 입력 -> 메인 스레드: 이벤트 전달
메인 스레드 -> OS: 응답 처리 및 UI 갱신
블로킹 작업 -> 메인 스레드: 처리 지연 및 응답 불가
:::

안드로이드는 UI 갱신과 사용자 입력 처리를 메인 스레드 하나에서 전담한다. 여기서 네트워크 요청이나 DB 조회 같은 무거운 작업이 수행되면 큐에 쌓인 다음 이벤트들을 처리하지 못한다.

시스템은 메인 스레드가 5초 이상 응답하지 않을 때 이를 ANR로 판단하고 사용자에게 알림창을 띄운다. 이때 메인 스레드는 여전히 작업 중이지만, 더 이상 사용자 인터랙션이 불가능한 상태가 된다.

결국 ANR을 막으려면 메인 스레드에서는 UI 갱신만 수행하고, 시간이 오래 걸리는 작업은 Worker 스레드나 Coroutine으로 분리해야 한다.

## 9. [모바일] 첫 화면을 빠르게 띄우려면 무엇을 미뤄야 하는가?

<!-- id: 63ec5b1d-ab0a-4062-870e-188b3fe4133c -->

첫 화면에 필요 없는 초기화를 미뤄야 한다. Application과 시작 화면의 동기 작업을 줄이고 분석 도구나 캐시 예열은 지연하거나 백그라운드로 보낸다.

:::flow
프로세스 -> Application: 필수 초기화만 한다
Application -> 첫 화면: 렌더링을 시작한다
첫 화면 -> 백그라운드: 나머지를 지연 실행한다
:::

콜드 시작은 시작 요청부터 첫 프레임까지 재며 프로세스 초기화도 포함한다. 웜 시작과 핫 시작은 재사용 자원이 달라서 같은 수치로 섞으면 병목을 잘못 판단한다.

시작 추적에서 메인 스레드의 디스크 접근과 클래스 로딩을 찾는다. Baseline Profile은 자주 쓰는 코드의 해석과 컴파일 비용을 줄인다.

지연 초기화도 사용 직전에 몰리면 끊김이 생긴다. 기능 우선순위와 의존성을 정하고 실제 기기에서 첫 표시와 완전 표시를 함께 측정한다.

## 10. [아키텍처 · 분산시스템] 노드를 늘릴 때 일관된 해싱이 필요한 이유는?

<!-- id: eec3255b-7173-4982-881a-0097afcf2bc5 -->

나머지 연산으로 나누면 노드가 하나 늘 때 거의 모든 키가 옮겨 가기 때문이다. 캐시라면 그 순간 적중률이 0에 가까워진다.

| 기준 | 나머지 연산 | 일관된 해싱 |
| --- | --- | --- |
| 노드 추가 시 이동 | 거의 전부 | `1/n`만 |
| 구현 | 간단하다 | 링과 가상 노드가 필요 |
| 분포 | 고르다 | 가상 노드로 보정한다 |

원리는 키와 노드를 같은 링 위에 올리는 것이다. 키는 시계 방향으로 처음 만나는 노드가 맡는다. 노드가 빠지면 그 구간만 다음 노드로 넘어간다.

노드 수가 적으면 구간 크기가 들쭉날쭉해진다. 그래서 노드 하나를 링 위 여러 지점에 올리는 가상 노드를 쓴다.

면접에서는 어디에 쓰는지를 묻는다. 분산 캐시와 샤딩이 대표적이고, 로드 밸런서의 세션 고정에도 같은 원리가 들어간다.

## 11. [아키텍처 · 분산시스템] 읽기와 쓰기 모델을 나누면 무엇을 얻고 잃는가?

<!-- id: 1a9edae2-63e5-4f36-b29d-c13d0ae22394 -->

읽기를 화면 모양대로 미리 만들어 두는 것을 얻고, 두 모델이 어긋나는 시간을 잃는다.

| 기준 | 한 모델 | 읽기 분리 |
| --- | --- | --- |
| 조회 | 매번 조인한다 | 미리 만든 것을 읽는다 |
| 일관성 | 즉시 | 잠깐 어긋난다 |
| 복잡도 | 낮다 | 동기화가 늘어난다 |

쓰기는 정규화된 모델로 받고, 읽기는 화면이 필요한 모양으로 따로 저장한다. 조회가 조인 없이 끝나므로 읽기가 많은 서비스에서 효과가 크다.

대가는 그 사이의 틈이다. 글을 쓰고 목록으로 돌아왔는데 아직 안 보이는 순간이 생긴다. 그 틈을 화면이 설명하거나 감춰야 한다.

면접에서는 언제 쓰지 말아야 하는지를 묻는다. 읽기와 쓰기 비율이 비슷하거나 즉시 일관성이 필요한 자리에서는 복잡도만 늘어난다.

## 12. [언어 · 런타임] let도 끌어올려지는데 왜 바로 읽지 못하는가?

<!-- id: 222e3328-335e-4cce-a997-78a039ea35c7 -->

let과 const의 바인딩은 스코프 시작 때 만들어지지만 선언문을 평가하기 전에는 초기화되지 않는다. 이 시간적 사각지대에서 읽으면 ReferenceError가 난다.

| 기준 | var | let·const |
| --- | --- | --- |
| 실행 전 상태 | undefined로 초기화 | 미초기화 |
| 선언 전 읽기 | undefined | ReferenceError |
| 블록 경계 | 무시 | 적용 |

호이스팅은 소스 코드를 실제로 위로 옮기는 동작이 아니다. 실행 컨텍스트를 만들 때 선언을 등록하고 각 종류의 초기화 시점을 달리하는 설명 모델이다.

함수 선언은 본문까지 일찍 바인딩되어 선언 앞에서 호출할 수 있다. 함수 표현식은 담긴 변수의 초기화 규칙을 따르므로 var와 let의 차이가 그대로 드러난다.

시간적 사각지대의 let을 typeof로 확인해도 ReferenceError가 난다. 아예 선언되지 않은 이름에 typeof를 썼을 때 undefined가 나오는 것과 다르다.

## 13. [언어 · 런타임] 동등한 객체의 해시값도 같아야 하는 이유는?

<!-- id: ab3d9d1b-7e1f-4db1-a601-16c886ab301e -->

해시 컬렉션은 hashCode로 버킷을 고른 뒤 equals를 확인한다. 동등한 객체의 해시값이 다르면 다른 버킷을 찾아 같은 키를 놓친다.

:::flow
조회 키 -> hashCode: 검색할 버킷을 고른다
버킷 -> equals: 후보와 논리적 동등성을 비교한다
equals -> 결과: 같은 키인지 결정한다
:::

equals는 반사성, 대칭성, 추이성, 일관성을 지켜야 하며 null에는 거짓이어야 한다. hashCode는 동등하면 같아야 하지만 충돌은 허용된다.

두 메서드에 쓰는 필드가 달라지면 규약이 깨진다. 특히 키를 Map에 넣은 뒤 해시에 쓰인 필드를 바꾸면 다시 찾지 못할 수 있다.

상속 계층에서 값 동등성을 추가하면 대칭성이 쉽게 깨진다. 값 객체는 불변으로 만들고 두 메서드를 같은 필드에서 함께 생성하는 편이 안전하다.

## 14. [언어 · 런타임] 이름이 같은 클래스가 다른 타입이 되는 조건은?

<!-- id: a9d85699-91db-42d7-8cf2-0a2dc163566c -->

바이너리 이름이 같아도 정의한 클래스 로더가 다르면 JVM은 다른 타입으로 본다. 런타임 타입은 이름과 정의 로더의 조합이다.

| 기준 | 같은 타입 | 다른 타입 |
| --- | --- | --- |
| 바이너리 이름 | 같다 | 같을 수 있다 |
| 정의 로더 | 같다 | 다르다 |

로딩 뒤 검증과 준비를 한다. 심벌 참조의 해결은 필요할 때 늦출 수 있다. 처음 적극 사용하면 정적 초기화가 실행된다.

부모 우선 위임은 이미 로드된 핵심 클래스의 중복 정의를 막는다. 플러그인과 서버는 격리를 위해 이 순서를 일부러 뒤집기도 한다.

서로 다른 로더가 만든 객체는 이름이 같아도 캐스팅할 수 없다. 로더가 실행 중인 스레드나 외부 정적 참조에 붙잡히면 클래스도 언로드되지 않는다.

## 15. [운영체제] CPU 스케줄러의 단계별 역할은 무엇인가?

<!-- id: 5276a513-ff3e-48aa-b584-0cb7fb62e121 -->

프로세스의 상태 변화와 실행 우선순위에 따라 실행 주기와 대상자를 정하는 역할이다.

:::stack
장기 | 작업 큐에서 메모리로 올릴 프로세스 결정
중기 | 메모리 부족 시 일부를 디스크로 내보냄
단기 | 준비 큐에서 CPU를 할당할 프로세스 선택
:::

위 도식은 각 스케줄러가 결정하는 범위와 시간적 단위를 보여준다. 장기 스케줄러는 시스템의 다중 프로그래밍 정도를 조절하며, 단기 스케줄러는 밀리초 단위로 빠르게 동작한다.

중기 스케줄러는 스와핑을 통해 메모리 효율을 높인다. 메모리가 부족하면 프로세스를 일시적으로 디스크로 옮겨 가상 메모리를 확보한다.

단기 스케줄러는 실제 CPU 점유를 결정하므로 응답 시간과 처리량에 가장 큰 영향을 미친다. 문맥 교환 비용을 최소화하는 것이 핵심이다.

## 16. [운영체제] 멀티스레드 환경에서 스레드 세이프한 코드를 작성하는 방법은 무엇인가?

<!-- id: b79af82f-ae3a-4733-a2bb-0ba239328604 -->

임계 영역으로의 동시 접근을 막아 데이터 일관성을 보장하는 것이다. 한 번에 하나의 스레드만 자원에 접근하도록 제어하는 것이 핵심이다.

:::stack
제어 방법 | 설명
--|--
동기화 | synchronized, Lock API를 이용한 상호 배제
불변성 | final, Read-only 객체로 상태 변경 차단
원자성 | Atomic 클래스로 단일 연산 수행
:::

위의 방법들로 공유 자원에 대한 경쟁 상태를 방지한다. 특히 데이터 읽기/쓰기 과정에서 문맥 전환이 발생하면 데이터가 오기집단될 수 있다.

동기화 락을 과하게 사용하면 성능이 떨어진다. 락으로 인해 스레드가 대기 상태로 대기하며 컨텍스트 스위칭 비용이 증가하기 때문이다.

상황에 따라 락-프리 알고리즘을 Senatorial Atomic 연산을 이용해 구현한다. 이를 통해 락 없이도 데이터 일관성을 성능상 이점만 챙기며 보장할 수 있다.

## 17. [운영체제] 프로세스 스케줄링 방식은 무엇으로 결정하는가?

<!-- id: 5994ff96-42af-4dd1-8735-0d260a1fe027 -->

CPU 효율과 응답 시간 사이의 트레이드오프를 고려해 결정한다. 처리량은 높이되 지연 시간은 줄이는 것이 핵심이다.

| 기준 | 비선점형 | 선점형 |
| --- | --- | --- |
| CPU 점유 | 프로세스가 반납할 때까지 대기 | OS가 강제로 회수 가능 |
| 응답성 | 낮음. 긴 작업으로 밀림 | 높음. 시분할 처리 |

비선점형인 FCFS는 먼저 온 순서대로 처리한다. 구현이 간단하지만, 짧은 작업이 긴 작업 뒤에서 무작정 대기하는 호위 효과가 발생한다.

선점형인 라운드 로빈은 정해진 시간 단위로 CPU를 전환한다. 모든 프로세스에 공평한 기회를 주어 응답성을 높이지만, 시간이 너무 짧으면 문맥 교환 비용이 커진다.

우선순위 스케줄링은 중요도에 따라 순서를 정한다. 낮은 우선순위의 작업이 영원히 실행되지 않는 기아 현상이 발생하며, 이를 해결하기 위해 대기 시간이 길어지면 순위를 높이는 에이징 기법을 사용한다.

## 18. [인프라 · 보안] 가상 메모리 관리에서 페이징과 세그먼테이션은 무엇으로 구분하는가?

<!-- id: f872a4d2-b77b-424a-b900-2a72ed50075e -->

메모리를 나누는 단위의 고정성 여부로 구분한다. 페이징은 시스템이 정한 고정 크기로 나누고, 세그먼테이션은 논리적 의미에 따라 가변 크기로 나눈다.

| 기준 | 페이징 | 세그먼테이션 |
| --- | --- | --- |
| 분할 단위 | 고정 크기(페이지) | 가변 크기(세그먼트) |
| 분할 기준 | 물리적 주소 | 논리적 의미(함수, 스택) |
| 파편화 | 내부 파편화 발생 | 외부 파편화 발생 |

페이징은 물리적 메모리를 효율적으로 관리하기 위해 도입했다. 프로세스 전체를 메모리에 올리지 않고 필요한 부분만 올리는 수요 페이징으로 메모리 활용도를 높인다.

세그먼테이션은 사용자가 정의한 논리적 단위로 메모리를를 나누는 방식이다. 코드, 데이터, 스택 영역을 구분하여 보호 및 공유가 쉽다.

현대 OS는 두 방식을 섞어 쓴다. 세그먼트로 논리적 영역을 나누고, 그 영역을 다시 페이징으로 관리하여 외부 파편화 문제를 해결한다.

## 19. [인프라 · 보안] 블로킹과 논블로킹 I/O의 결정적 차이는 무엇인가?

<!-- id: 0c72906c-013c-4126-acbe-a8805e04c930 -->

제어권의 반환 시점이다. 블로킹은 작업 완료까지 기다리며, 논블로킹은 호출 즉시 제어권을 돌려준다.

:::flow
호출자 -> 커널: I/O 요청
커널 -> 호출자: **블로킹**: 완료까지 대기 / **논블로킹**: 즉시 반환 (EAGAIN)
::: 

블로킹 방식은 코드가 직관적이다. 하지만 I/O가 끝날 때까지 쓰레드가 멈춰 자원을 낭비한다.

논블로킹은 대기 시간 동안 다른 일을 할 수 있다. 대신 작업 완료 여부를 계속 확인하거나 알림을 받아야 하므로 로직이 복잡해진다.

이 구분은 동기/비동기 개념과 섞이기 쉽다. 핵심은 '제어권'이 누구에게 있는지에 주목해 구분해야 한다.

## 20. [자료구조 · 알고리즘] 그리디 알고리즘과 동적 계획법은 무엇으로 구분하는가?

<!-- id: 95ba245f-289f-4640-b244-f70a914fafe1 -->

최적 부분 구조를 가졌으나, 현재의 최적해를 선택하는지 아니면 모든 경우의 수를 고려하여 결정하는지로 구분한다.

| 기준 | 그리디 알고리즘 | 동적 계획법 |
| --- | --- | --- |
| 선택 방식 | 현재의 최적해를 선택 | 모든 부분 문제의 해를 조합 |
| 효율성 | 연산량이 적고 빠름 | 연산량이 많고 정확함 |
| 최적성 보장 | 특정 조건에서만 가능 | 항상 최적해를 보장함 |

그리디 알고리즘은 매 순간 가장 이득이 되는 선택을 하며, 뒤를 돌아보지 않는다. 이 방식은 선택지가로 인해 전체적인 최적해를 구할 수 없는 경우에 대해 취약하다.

반면, 동적 계획법은 작은 문제의 답을 메모이제이션을 통해 저장하여 중복으로 계산하지 않는다. 모든 가능성을 탐색하며 과거의 것을 활용해 최종적인 최적해를 구성한다.

두 방식의 차이점을 이해하는 것은 문제의 최적 부분 구조와 중복되는 부분 문제로 구성되어 있는지 판단하는 정확한 정확한 기준을 세우는 데 중요하다.

## 21. [자료구조 · 알고리즘] 이진 탐색 트리가 한쪽으로 치우치면 무엇이 문제인가?

<!-- id: f4143480-1029-4cdb-b5b5-aea957aad362 -->

연결 리스트가 된다. 탐색이 절반씩 줄어든다는 전제가 깨져서 O(log n)이 O(n)으로 내려앉는다. 정렬된 데이터를 순서대로 넣으면 실제로 이 모양이 나온다.

| 상태 | 높이 | 탐색 |
| --- | --- | --- |
| 균형 잡힌 트리 | `log n` | `O(log n)` |
| 한쪽으로 치우친 트리 | `n` | `O(n)` |

그래서 스스로 균형을 잡는 트리를 쓴다. 넣거나 지울 때 높이 차이를 확인하고 회전으로 맞춘다. 회전 비용이 붙지만 최악을 O(log n)으로 묶는 값이다.

해시 테이블과 갈리는 지점은 순서다. 해시는 단건 조회가 더 빠르지만 범위 질의와 정렬 순회를 못 한다. "20에서 30 사이"를 물어야 하면 트리 쪽이다.

데이터베이스 인덱스가 이진 트리 대신 B-트리를 쓰는 이유도 여기 있다. 디스크는 블록 단위로 읽으므로 한 노드에 키를 많이 담아 높이를 낮추는 편이 유리하다.

## 22. [자료구조 · 알고리즘] 해시 충돌을 해결하는 두 방식의 차이는 무엇인가?

<!-- id: 466eaf7e-6cae-4f48-a32f-5d1f58832ec2 -->

체이닝은 연결 리스트로 충돌 데이터를 쌓고, 개방 주소법은 빈 공간을 찾아 저장한다.

| 기준 | 체이닝 | 개방 주소법 |
| --- | --- | --- |
| 저장 위치 | 버킷 외부 | 버킷 내부 |
| 메모리 활용 | 추가 할당 필요 | 정해진 크기 내 활용 |
| 성능 저하 | 리스트 탐색 시간 증가 | 클러스터링 발생 |

체이닝은 데이터가 계속 늘어나도 저장 가능하며 구현이 간단하다. 하지만 데이터가 한 버킷에 쏠리면 탐색 시간이 선형적으로 증가한다.

개방 주소법은 메모리 효율이 좋으나 데이터가 찰수록 빈 칸을 찾는 비용이 크다. 특히 특정 영역에 데이터가 뭉치는 클러스터링 현상이 발생하면 성능이 급격히 떨어진다.

따라서 데이터의 양을 예측할 수 없다면 체이닝을, 메모리 공간이 한정적이라면 개방 주소법을 선택한다.

## 23. [프레임워크] 단위 시험과 통합 시험은 무엇으로 가르는가?

<!-- id: 2a1ae829-21b3-42da-8593-599384cd6ec3 -->

무엇을 함께 확인하는지로 가른다. 단위 시험은 작은 동작 하나를 따로 보고 통합 시험은 여러 조각이 맞물리는 자리를 본다.

| 기준 | 단위 | 통합 |
| --- | --- | --- |
| 보는 범위 | 동작 하나 | 조각들이 만나는 곳 |
| 둘레 | 자주 가짜로 바꾼다 | 대개 실제 것을 쓴다 |
| 대개의 속도 | 빠르다 | 느리다 |

가짜로 바꾸는 것은 경향이지 정의가 아니다. 단위 시험이 실제 협력 객체를 써도 되고, 통합 시험이 바깥 시스템만 가짜로 둬도 된다.

비율보다 중요한 것은 **되돌렸을 때 빨간불이 뜨는가**다. 고친 자리를 원래대로 돌려도 통과하면 그 시험은 적어도 이 회귀를 못 잡는다.

## 24. [프레임워크] 예외를 어디서 HTTP 응답으로 바꾸는가?

<!-- id: 29eaf779-ed8f-43f9-8bd8-f2640fb211bf -->

컨트롤러 경계의 전역 예외 처리기에서 바꾼다. 도메인 예외를 안정된 오류 코드와 HTTP 상태로 매핑하고 예상 밖 예외는 500으로 감춘다.

:::flow
서비스 -> 처리기: 의미 있는 예외를 전달한다
처리기 -> 오류 계약: 상태와 코드를 매핑한다
오류 계약 -> 클라이언트: 일관된 응답을 반환한다
:::

예상 가능한 실패는 의미가 드러나는 예외로 표현한다. 저장소 예외나 구현 메시지를 그대로 노출하면 API가 내부 기술에 묶인다.

처리기는 구체적인 예외부터 매핑한다. 필터에서 발생한 예외는 컨트롤러 처리기에 도달하지 않으므로 별도 경계가 필요하다.

로그는 한 경계에서 한 번 남긴다. 응답에는 추적 ID와 안정된 코드를 싣고 스택 트레이스와 민감한 메시지는 숨긴다.

## 25. [프레임워크] 톰캣은 WAS와 웹 서버의 차이점으로 무엇을 수행하는가?

<!-- id: e63a3f49-6807-43ff-ac54-ac899b30f0ac -->

서블릿 컨테이너로서 자바 코드를 실행해 동적인 응답을 생성한다. 정적인 파일은 웹 서버에 맡기고, 비즈니스 로직이 필요한 요청을 처리한다.

:::stack
웹 서버 | Apache, Nginx. 정적 리소스 응답
WAS | Tomcat, Jetty. 서블릿 실행 및 DB 연동
:::

톰캣은 HTTP 요청을 받아 서블릿으로 전달하고 그 결과를 다시 응답한다. 이 과정에서 서블릿의 생명주기를 관리하고 멀티스레딩을 처리한다.

최근에는 톰캣 자체의 정적 파일 처리 성능이 좋아져 단독으로 쓰기도 한다. 하지만 보안과 로드밸런싱을 위해 앞단에 웹 서버를 두는 구조가 여전히 일반적이다.

## 26. [프론트엔드] 렌더링 방식은 어떤 요구로 결정하는가?

<!-- id: 56fa1f6f-eb91-4b02-a5e8-e605d731a066 -->

콘텐츠 갱신 주기, 개인화, 검색 노출, 서버 비용으로 결정한다. 정적 콘텐츠는 SSG, 요청별 데이터는 SSR, 앱형 상호작용은 CSR이 유리하다.

| 상황 | 방식 | 이유 |
| --- | --- | --- |
| 정적 콘텐츠 | SSG | 미리 생성 |
| 요청별 데이터 | SSR | 요청 시 생성 |
| 앱형 상호작용 | CSR | 브라우저 렌더 |

SSG는 응답이 빠르고 서버 부하가 작지만 갱신이 늦을 수 있다. SSR은 최신 데이터를 주지만 요청마다 렌더링 비용과 장애 지점이 생긴다.

CSR은 초기 자바스크립트 비용과 검색 노출을 관리해야 한다. 실제 서비스는 경로와 컴포넌트마다 방식을 섞고 캐시나 재생성으로 약점을 보완한다.

## 27. [프론트엔드] 선언한 너비와 실제 크기가 왜 달라지는가?

<!-- id: d680678d-e67b-42d5-8352-54f4b471be1a -->

기본 content-box에서는 선언한 너비 밖에 패딩과 테두리가 더해지기 때문이다. border-box를 쓰면 선언한 너비 안에 둘이 포함된다.

| 기준 | content-box | border-box |
| --- | --- | --- |
| width 범위 | 콘텐츠만 | 콘텐츠+패딩+테두리 |
| 바깥 크기 | 값보다 커질 수 있음 | 선언값으로 고정 |

렌더된 박스 너비는 콘텐츠와 좌우 패딩, 좌우 테두리를 합한 값이다. 마진은 박스 크기에 포함되지 않고 주변 간격을 만든다.

전체에 box-sizing: border-box를 적용하면 레이아웃 계산이 직관적이다. 다만 콘텐츠 영역은 패딩과 테두리가 늘수록 줄어든다.

## 28. [프론트엔드] 한 축 배치와 두 축 배치는 어떻게 구분하는가?

<!-- id: b827236c-a773-47a2-9b7c-7709be8244cd -->

행이나 열 한 축의 흐름이 핵심이면 Flexbox를 쓴다. 행과 열을 함께 맞추거나 영역 전체를 설계하면 Grid를 쓴다.

| 기준 | Flexbox | Grid |
| --- | --- | --- |
| 주축 | 한 축 중심 | 두 축 동시 |
| 크기 결정 | 콘텐츠 흐름 중심 | 트랙 구조 중심 |

Flexbox는 콘텐츠 크기와 남은 공간을 따라 항목을 배치한다. 줄바꿈해도 각 줄은 독립적으로 정렬되므로 열 맞춤에는 약하다.

Grid는 행과 열 트랙을 먼저 정의해 항목을 배치한다. 두 방식을 함께 써도 된다. 페이지는 Grid, 내부 도구 모음은 Flexbox가 자연스럽다.
