## 1. [네트워크] Git 협업 시 충돌 해결을 위해 무엇을 우선하는가?

<!-- id: 9dfe7042-36f0-4054-ac7c-b9310f7b926b -->

팀원 간 합의된 브랜치 전략과 코드 컨벤션을 우선한다. 기술적인 머지 방식보다 소통을 통한 충돌 방지가 먼저다.

| 기준 | Git Flow | GitHub Flow |
| --- | --- | --- |
| 복잡도 | 높음. 브랜치가 많다 | 낮음. 메인 중심이다 |
| 배포 주기 | 정기 배포에 적합 | 지속적 배포에 적합 |

전략이 없으면 각자 다른 시점에 같은 파일을 수정해 충돌이 잦아진다. 명확한 브랜치 명명 규칙과 작업 단위 분리가 해결책이다.

코드 컨벤션을 맞추면 단순 포맷팅 차이로 발생하는 불필요한 충돌을 줄인다. Prettier 같은 도구로 자동화하는 것이 일반적이다.

최종 충돌 해결은 항상 변경 사항의 맥락을 파악하는 것에서 시작한다. 단순 툴 사용보다 작성자와의 소통이 가장 빠르고 정확하다.

## 2. [네트워크] XSS 공격으로 훔칠 수 있는 데이터는 무엇인가?

<!-- id: 01c1e4d2-0628-4e29-91fe-3efa911fe82b -->

사용자의 세션 쿠키와 로컬 스토리지 데이터다. 브라우저가 실행하는 스크립트를 통해 저장된 정보를 가로채 외부 서버로 전송한다.

:::stack
저장소 | 데이터
쿠키 | 세션 ID, 사용자 인증 정보
로컬 스토리지 | 토큰, 설정값
:::

위 표는 XSS가 노리는 주요 타겟이다. 공격자는 ‖javascript:alert('XSS')‖ 같은 코드를 삽입하여 브라우저의 ‖document.cookie‖ 속성에 접근한다.

단순히 정보 유출을 넘어 페이지 내용을 변조하는 경우도 많다. 가짜 로그인 폼을 띄워 사용자의 비밀번호를 직접 입력하게 만드는 피싱 공격으로 이어진다.

최근에는 단일 페이지 애플리케이션(SPA)에서 토큰 기반 인증을 사용하며 로컬 스토리지 사용량이 늘었다. 이에 따라 스토리지 기반 XSS 공격의 위험성이 더 커졌다.

## 3. [네트워크] 웹소켓과 일반 소켓 통신은 무엇으로 구분하는가?

<!-- id: e1bbcc1c-686f-4845-bc0d-485d37ee8898 -->

웹소켓은 HTTP 기반의 전이중 통신 프로토콜이며, 일반 소켓은 전송 계층의 TCP/UDP 연결 자체를 의미한다.

| 기준 | 웹소켓 | 일반 소켓 |
| --- | --- | --- |
| 계층 | 애플리케이션(L7) | 전송(L4) |
| 연결 방식 | HTTP 핸드셰이크 필요 | 직접 연결 |
| 특징 | 상태 유지(Stateful) | 로우 레벨 데이터 전송 |

웹소켓은 웹 브라우저 환경에서 실시간 통신을 하기 위해 설계되었다. HTTP의 요청-응답 모델을 유지하면서도 연결을 계속 열어두어 서버가 클라이언트로 데이터를 보낼 수 있게 한다.

일반 소켓은 운영체제가 제공하는 네트워크 인터페이스다. IP와 포트를 통해 바이트 스트림을 주고받는 가장 기초적인 도구이며, 웹소켓은 내부적으로 이 소켓을 활용해 구현된다.

따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 통신을 위한 하드웨어/소프트웨어적 통로 그 자체라고 볼 수 있다.

## 4. [데이터베이스] Hash Anti Join은 데이터베이스 내부에서 구체적으로 어떻게 동작하는가?

<!-- id: 3696debd-7e93-44aa-9b0c-a106be574bf8 -->

Hash Anti Join은 우측 집합으로 메모리에 해시 테이블을 만든 뒤, 좌측 집합을 읽으며 해시 테이블에 존재하지 않는 행만 선별해 반환하는 방식으로 동작한다.

:::flow
Build 단계: 우측(서브쿼리) 집합을 읽어 메모리에 해시 테이블 구축
Probe 단계: 좌측(메인) 집합 행을 하나씩 읽으며 해시 키 탐색
결과 반환: 해시 테이블에 매칭되는 키가 없는 행만 최종 출력
:::

Build 단계에서는 조건절 오른쪽 집합을 스캔하여 조인 키 기준의 해시 테이블을 만든다. 이때 해시 함수를 거쳐 버킷에 데이터를 할당하며 메모리 공간을 확보한다.

Probe 단계에서는 왼쪽 집합의 행을 순차적으로 읽으며 동일한 해시 함수로 해시 테이블을 탐색한다. 일치하는 키를 찾는 즉시 검색을 중단하고 해당 행을 버린다.

이러한 조기 종료(Short-circuit) 특성 덕분에 대용량 데이터의 NOT EXISTS나 NOT IN 절을 빠르게 처리할 수 있다.

## 5. [데이터베이스] 데이터베이스 복제와 클러스터링의 선택 기준은 무엇인가?

<!-- id: 7fcff009-e402-48a8-865d-80bcf4743616 -->

가용성과 읽기 성능 향상과 읽기-쓰기 분리라는 목적에 따라 고른다.

| 기준 | 복제(Replication) | 클러스터링(Clustering) | 
| --- | --- | --- | 
| 핵심 목적 | 데이터 백업 및 읽기 분산 | 고가용성 및 시스템 확장 | 
| 데이터 일관성 | 비동기적, 지연 발생 | 동기적, 높은 일관성 | 
| 구조 | Master-Slave 구조 | 공유 저장소 또는 분산 저장 | 

복제는 기본적으로 데이터를 다른 서버로 복사하는 방식이다. 주로 읽기 전용 복제본(Slave)을 늘려 읽기 트래픽을 분산시킨다. 데이터가 복사되는 시점차로 인해 복제 지연(Replication Lag) 방향으로 파고들 수 있다.

클러스터링은 여러 대의 서버를 하나의 시스템처럼 동작하게 한다. 노드 하나가 죽어도 서비스가 중단되지 않는 고가용성(HA)이 핵심이다. 공유 저장소를 사용하거나 데이터 샤딩으로 처리량을 높인다.

실무에서는 읽기 요청이 압도적으로 많다면 복제를 선택하고, 쓰기 작업이 빈번하고 중단 없는 서비스가 필수적이라면 클러스터링을 구성한다.

## 6. [데이터베이스] 서브쿼리를 언제 조인으로 재작성해야 성능이 향상되는가?

<!-- id: 67fb7a7c-ecfe-4846-bb47-87c1f8c06079 -->

RDBMS 옵티마이저는 조인 연산의 최적화 경로를 서브쿼리보다 더 다양하게 탐색할 수 있다. 서브쿼리를 사용하면 서브쿼리 블록 단위로 최적화가 수행되어 전체 쿼리 수준에서의 최적화 기회를 잃기 쉽다. 특히 외부 쿼리의 값을 참조하는 상관 서브쿼리는 매 행마다 반복 실행되어 성능 저하의 주 원인이 된다.

서브쿼리를 조인으로 변환할 때는 일대다 관계에서 데이터가 증폭되는 문제를 주의해야 한다. 서브쿼리는 단순히 존재 여부만 확인하여 원본 행 수를 유지하지만, 이를 단순 조인으로 바꾸면 중복 데이터가 생성되어 DISTINCT나 GROUP BY를 추가해야 하므로 오히려 성능이 떨어질 수 있다.

| 기준 | 서브쿼리 | 조인 (Join) |
| --- | --- | --- |
| 실행 방식 | 독립된 블록 또는 반복 실행 | 다양한 조인 알고리즘 선택 |
| 결과 행 수 | 원본 테이블 행 수 유지 | 관계에 따라 중복 발생 가능 |
| 최적화 범위 | 쿼리 블록 내로 제한됨 | 전역적인 실행 계획 수립 |

최신 옵티마이저는 서브쿼리 언네스팅 기법을 통해 내부적으로 서브쿼리를 조인으로 자동 변환하여 실행한다. 따라서 개발자가 성능 개선을 위해 수동으로 변환하기 전에, 옵티마이저의 실행 계획을 먼저 확인하고 자동 최적화가 작동하지 않는 경우에만 수동으로 변환해야 한다.

## 7. [모바일] 메모리 부족 시 어떤 프로세스부터 종료되는가?

<!-- id: 9128bf1e-095a-45b0-bc3e-56d2281574ef -->

사용 중인 컴포넌트가 없는 캐시 프로세스부터 종료된다. 가시성과 사용자 영향이 클수록 우선순위가 높아지고 포그라운드 프로세스는 마지막에 보호된다.

:::stack
포그라운드 | 사용자가 현재 상호작용한다
가시 | 화면에 보이거나 인지되는 작업이다
서비스 | 시작된 서비스를 수행한다
캐시 | 활성 컴포넌트가 없다
:::

프로세스 등급은 가장 중요한 활성 컴포넌트에 맞춰진다. 중요한 클라이언트가 바인드한 서비스의 프로세스도 우선순위가 올라간다.

백그라운드 프로세스의 수명을 전제로 설계하면 안 된다. 메모리의 싱글턴 값은 사라질 수 있으므로 화면과 작업을 복원 가능하게 만든다.

## 8. [모바일] 실행 시점과 사용자 인지 여부로 어떤 수단을 고르는가?

<!-- id: 38371c67-d6a4-4aa9-b6a6-c9ac7de034b2 -->

지연 가능하고 끝내야 하는 일은 WorkManager를 쓴다. 즉시 진행하며 사용자가 알아야 하는 일은 포그라운드 서비스를 쓴다. 정시 알림은 알람을 검토한다.

| 기준 | WorkManager | 포그라운드 서비스 |
| --- | --- | --- |
| 목적 | 지연 가능한 지속 작업 | 즉시 체감 작업 |
| 특성 | 시각이 정확하지 않다 | 알림과 시작 제한이 있다 |

Doze와 앱 대기는 네트워크와 알람을 미루고 백그라운드 서비스 실행도 제한한다. 스레드나 일반 서비스만 띄워 계속 실행되리라 기대할 수 없다.

정확한 시각이 핵심인 사용자 기능은 AlarmManager를 검토한다. 정확한 알람은 권한과 용도 제한이 있어 일반 동기화에 쓰지 않는다.

## 9. [모바일] 전송 성공은 단말 수신까지 뜻하는가?

<!-- id: 37fe91c6-7947-45c4-b84c-4bbe5ca331d2 -->

아니다. 서버가 받은 메시지 ID는 FCM이 전달 요청을 접수했다는 뜻이다. 단말 도착이나 앱 처리를 보장하지 않는다.

:::flow
앱 서버 -> FCM: 메시지를 접수한다
FCM -> 단말: 연결 상태에 따라 전달을 시도한다
단말 -> 앱 서버: 처리 결과를 별도로 확인한다
:::

오프라인과 Doze와 토큰 만료 때문에 지연되거나 유실될 수 있다. TTL이 지나거나 같은 collapse key의 새 메시지가 오면 대기 메시지가 버려질 수 있다.

백그라운드 알림 메시지는 시스템 트레이가 처리한다. 데이터 메시지의 앱 처리는 짧아야 하며 긴 후속 작업은 지속 작업으로 넘긴다.

업무상 전달 확인이 필요하면 앱이 처리 ACK를 서버에 보낸다. 서버는 이벤트 ID로 중복을 제거하고 누락 시 원본 데이터를 다시 동기화한다.

## 10. [아키텍처 · 분산시스템] 게이트웨이를 두면 무엇을 얻고 무엇을 걱정해야 하는가?

<!-- id: f4719fe6-91a3-4923-b23c-ccf4bfd5bb10 -->

모든 서비스가 각자 하던 일을 한곳으로 모으는 것을 얻고, 그 한곳이 죽으면 전부 죽는 것을 걱정해야 한다.

:::stack
인증·인가 | 서비스마다 구현하지 않아도 된다
요청 제한 | 한곳에서 세야 정확하다
라우팅·집계 | 클라이언트가 서비스 수를 몰라도 된다
:::

특히 값진 것은 클라이언트가 내부 구조를 모르게 되는 것이다. 서비스를 쪼개거나 합쳐도 바깥 주소는 그대로 둘 수 있다.

대가는 단일 장애점과 배포 병목이다. 모든 팀의 라우팅 규칙이 한 저장소에 모이면 그것을 고치는 순서가 곧 줄서기가 된다.

면접에서는 로드 밸런서와의 차이를 묻는다. 로드 밸런서는 어느 서버로 보낼지만 정하고, 게이트웨이는 요청 내용을 보고 판단한다.

## 11. [아키텍처 · 분산시스템] 이벤트 소싱을 도입할 때의 트레이드오프는 무엇인가?

<!-- id: e20bf8cd-8e00-40aa-9c8a-8b798a574286 -->

이벤트 소싱을 도입하면 데이터의 완전한 이력 관리가 가능해지지만, 시스템 복잡도가 상승하고 데이터 조회 성능이 떨어진다.

데이터를 최종 상태로 저장하지 않고 발생한 모든 이벤트를 저장하기 때문이다. 상태를 알기 위해 이벤트를 순차적으로 재생해야 한다. 이 과정에서 읽기 성능 저하가 발생한다. 이를 해결하기 위해 읽기 전용 모델을 따로 만드는 CQRS 패턴을 함께 도입하는 경우가 많다.

이벤트 저장소(Event Store)의 데이터가 계속 쌓이면 재생 시간이 길어진다. 이를 최적화하기 위해 현재 상태를 특정 시점의 스냅샷으로 저장하는 기법을 사용한다. 아래 도식은 이벤트 소싱의 기본 처리 흐름을 보여준다.

:::flow
이벤트 발생 -> 이벤트 저장소: 상태 변경 이벤트 저장
이벤트 저장소 -> 프로젝션: 이벤트를 읽어 읽기 모델 갱신
프로젝션 -> 읽기 모델: 최종 상태 저장
:::

이후 데이터 구조 변경이 필요할 때 문제가 된다. 과거의 이벤트를 수정할 수 없으며, 새로운 버전의 이벤트 스키마를 통해 하위 호환성을 유지하는 업캐스팅(Upcasting) 작업이 필요하다. 이는 개발 및 유지보수 비용을 중심으로 한 트레이드오프다.

## 12. [언어 · 런타임] equals를 재정의할 때 hashCode도 함께 재정의해야 하는 이유는?

<!-- id: 2e8d9a00-0d82-4044-bbf9-66e543fb9a1e -->

해시 기반 컬렉션이 두 메서드를 함께 쓰기 때문이다. 하나만 바꾸면 컬렉션이 같은 객체를 다른 객체로 취급한다.

HashMap은 먼저 hashCode로 버킷을 찾고 그 안에서 equals로 비교한다. equals만 재정의하면 논리적으로 같은 두 객체가 서로 다른 버킷으로 흩어진다. equals 비교까지 가지도 못하므로 조회가 실패한다.

:::flow
get(key) -> hashCode: 어느 버킷인지 먼저 정한다
hashCode -> 버킷: 그 버킷 안의 후보들만 꺼낸다
버킷 -> equals: 후보와 하나씩 견준다. **여기까지 와야 비교가 일어난다**
:::

규약은 단방향이다. equals가 true면 hashCode는 반드시 같아야 한다. 반대는 성립하지 않는다. hashCode가 같아도 equals는 false일 수 있고 이게 해시 충돌이다.

실무에서 자주 터지는 자리는 JPA 엔티티다. 식별자가 영속화 시점에 채워지므로 id 기반 hashCode는 저장 전후로 값이 바뀐다. Set에 넣어둔 엔티티를 저장하면 다시 찾지 못하게 된다.

가변 필드를 hashCode에 쓰는 것도 같은 함정이다. 컬렉션에 넣은 뒤 필드를 바꾸면 그 객체는 사실상 사라진다.

## 13. [언어 · 런타임] 대입 뒤 한쪽을 바꿀 때 결과가 갈리는 이유는?

<!-- id: 41f73f6c-d815-4ca8-9a8d-071e5b6bb635 -->

값 타입 대입은 값 자체를 복사한다. 참조 타입 대입은 같은 객체를 가리키는 참조를 복사한다. 값 안의 참조 필드는 여전히 같은 객체를 가리킬 수 있다.

| 기준 | 값 의미론 | 참조 의미론 |
| --- | --- | --- |
| 대입 결과 | 값 자체 복사 | 같은 객체의 참조 복사 |
| 변경 영향 | 값 필드는 분리 | 별칭을 통해 공유 |
| 동등성 | 값 비교가 자연스러움 | 값·정체성 구분 |

이 구분은 스택과 힙의 저장 위치와 같지 않다. 값도 최적화나 캡처에 따라 힙에 놓일 수 있고 참조 값 자체는 스택 프레임에 놓일 수 있다.

Java처럼 인자를 항상 값으로 전달하는 언어도 객체 참조 값을 복사해 넘긴다. 호출자는 같은 객체의 변경을 보지만 자신의 변수 재대입은 영향받지 않는다.

가변 참조 객체는 별칭과 동시성 위험을 키운다. 불변 객체와 방어적 복사는 공유 위험을 줄이지만 새 객체 생성과 복사 비용을 낸다.

## 14. [언어 · 런타임] 왜 모든 바이트코드를 바로 최적화하지 않는가?

<!-- id: bc007580-c5a3-4146-8970-f36138830ab4 -->

모두 최적화하면 시작이 느려지고 실행되지 않을 코드에도 비용을 쓴다. JVM은 실행 정보를 모아 자주 쓰이는 코드만 기계어로 최적화한다.

:::flow
인터프리터 -> 프로파일: 실행 횟수와 타입을 수집한다
프로파일 -> JIT: 뜨거운 메서드와 루프를 고른다
JIT -> 기계어: 인라이닝과 특수화를 적용한다
:::

HotSpot의 계층형 컴파일은 C1으로 빠르게 컴파일한 뒤 충분히 뜨거운 코드를 C2로 더 최적화한다. 시작 속도와 최고 성능을 절충한다.

JIT는 관찰된 타입을 바탕으로 가상 호출을 인라이닝할 수 있다. 가정이 깨지면 최적화 코드를 폐기하고 디옵티마이즈한다.

그래서 짧은 벤치마크는 워밍업과 컴파일 시간을 섞어 잘못 읽기 쉽다. JMH처럼 워밍업과 측정을 분리해야 한다.

## 15. [언어 · 런타임] 호이스팅으로 인한 부작용을 어떻게 막는가?

<!-- id: 6b76ee3c-f879-4719-b1aa-e8fac2c9228d -->

let과 const를 사용하고 선언부를 최상단으로 올린다. var로 선언한 변수는 선언과 동시에 undefined로 초기화되어 논리적 오류를 유발하기 때문이다.

| 기준 | var | let/const |
| --- | --- | --- |
| 초기화 시점 | 선언과 동시에 | 할당 전 접근 불가 |
| 스코프 | 함수 단위 | 블록 단위 |

var는 선언문이 스코프 최상단으로 끌어올려져 변수 이름만 예약된다. 하지만 값은 할당문 단계에서 결정된다. 이 틈에 접근하면 undefined가 나온다.

반면 let과 const는 선언 전 접근 시 TDZ(Temporal Dead Zone)에 빠진다. 런타임 에러를 발생시켜 개발자가 잘못된 접근을 즉시 알게 한다.

함수 선언문은 호이스팅되어 선언 전 호출이 가능하다. 하지만 의도치 않은 함수 덮어쓰기가 발생할 수 있어 함수 표현식을 권장한다.

## 16. [운영체제] 동기화 문제를 하드웨어적으로 어떻게 해결하는가?

<!-- id: 3ddad76b-7308-4416-8d74-bbb8947b8e43 -->

원자적 명령어로 처리한다. CPU가 명령어를 실행하는 동안 다른 프로세스가 개입하지 못하게 막아 메모리 접근을 보장하는 방식이다.

:::stack
하드웨어 수준 | **Test-and-Set**, **Compare-and-Swap (CAS)**
명령어 수준 | 인터럽트 비활성화. 단일 코어에서만 유효하다
:::

Test-and-Set은 메모리 값의 현재 상태를 읽고 새로운 값을 쓰는 작업을 한 번에 처리한다. 중간에 컨텍스트 스위칭이 발생하지 않아 데이터 정합성을 지킨다.

CAS는 기대하는 값과 현재 메모리 값의 일치 여부를를 확인하고 다를 경우에만 값을 바꾼다. 락-프리(Lock-free) 알고리즘의 핵심 기반이 된다.

인터럽트 비활성화는 간단하지만 멀티코어 환경에서는 모든 CPU의 인터럽트를 동시에 끄는 비용이 너무 커서 실무적으로 쓰이지 않는다.

## 17. [운영체제] 컨텍스트 스위칭 시 CPU는 무엇을 저장하고 복원하는가?

<!-- id: 2ecb28ba-31f6-43b5-9473-afb9c0a3ccb5 -->

현재 실행 중인 프로세스의 상태 정보인 PCB로 상태를 저장하고, 다음으로 실행할 프로세스의 PCB에서 상태를 복원한다.

:::stack
PCB | 프로세스 제어 블록. 상태, PC, 레지스터 값 저장
CPU 레지스터 | 현재 연산으로 사용 중인 실제 물리적 값
:::

상태 저장 시 CPU의 프로그램 카운터(PC)과 레지스터 값들이 PCB에 옮겨진다. 그래야 나중에 다시 돌아왔을 때 중단된 지점부터 정확히 연산으로 돌아갈 수 있다.

이후 스케줄러가 선택한 다음 프로세스의 PCB를 읽어 CPU 레지스터에 값을 덮어쓴다. 이 과정에서 CPU는 어떤 실제 연산을 수행하지 않는 것을 오버헤드로 본다.

캐시 메모리나 TLB 같은 메모리 캐시가 무효화되는 비용이 발생하는 점이 중요하다. 단순한 레지스터 복원보다 이 캐시 초기화 비용이 더 크다.

## 18. [인프라 · 보안] TLS 핸드셰이크의 핵심 목적은 무엇인가?

<!-- id: a4ec9e80-ba7e-409b-91c8-68118a65141f -->

클라이언트와 서버가 서로의 신원을 확인하고, 데이터를 암호화할 수 있는 대칭키를 안전하게 공유하는 것이다.

:::flow
클라이언트 -> 서버: Client Hello. 지원 버전과 암호화 방식 제안
서버 -> 클라이언트: Server Hello. 암호화 방식 선택 및 인증서 전달
클라이언트 -> 서버: Key Exchange. 서버 신원 확인 후 프리마스터 시크릿 전달
서버 -> 클라이언트: Finished. 모든 설정 완료 및 대칭키 생성
:::

위 흐름을 통해 신뢰할 수 있는 기관(CA)이 서명한 인증서를 확인하여 중간자 공격을 방지한다. 공개키 기반의 비대칭 암호화로 초기 연결을 횃불처럼 보호한다.

최종적으로 생성된 세션 키는 대칭키 암호화 방식을 사용한다. 비대칭 암호화는 연산량이 많아 실제 데이터 전송 시에는 효율적인 대칭키를 쓰는 것이 핵심이다.

TLS 1.3 버전에서는 이 과정을 1-RTT로 줄여 연결 속도를 성능상 이득을 얻었다. 이전 버전보다 불필요한 왕복 횟수를 처음부터 줄여 지연 시간을 단축했다.

## 19. [인프라 · 보안] 배열보다 연결 리스트를 사용하는 기준은 무엇인가?

<!-- id: 9ec7cfb5-a4ef-47e4-b2db-9d3de3f5194e -->

데이터의 추가와 삭제가 빈번하게 일어날 때다. 인덱스로 접근하지 않고 순차적으로 탐색해도 무방한 환경에서 유리하다.

| 기준 | 배열 | 연결 리스트 |
| --- | --- | --- |
| 요소 접근 | $O(1)$. 인덱스로 즉시 찾음 | $O(n)$. 처음부터 훑어야 함 |
| 중간 삽입/삭제 | $O(n)$. 데이터를 밀고 당김 | $O(1)$. 포인터만 변경 |

배열은 연속된 메모리 공간을 사용한다. 삽입이나 삭제 시 나머지 요소를 모두 이동시켜야 하므로 비용이 크다.

반면 연결 리스트는 노드가 흩어져 있다. 앞뒤 노드의 주소값만 바꿔주면 되므로 데이터 이동 없이 빠르게 처리한다.

최근 CPU 캐시 지역성 때문에 단순 탐색 성능은 배열이 압도적이다. 따라서 무작정 리스트를 쓰기보다 데이터 변경 빈도를 먼저 따져야 한다.

## 20. [자료구조 · 알고리즘] 그래프를 인접 행렬과 인접 리스트 중 어떤 방식으로 구현해야 하는가?

<!-- id: 9790ab29-7f64-4732-9a0f-f187c14796ce -->

간선의 밀도와 탐색 연산의 주된 목적에 따라 결정한다. 간선이 많은 밀집 그래프는 인접 행렬을, 간선이 적은 희소 그래프는 인접 리스트를 선택하는 것이 유리하다.

| 기준 | 인접 행렬 | 인접 리스트 |
| --- | --- | --- |
| 공간 복잡도 | **O(V²)** | **O(V + E)** |
| 간선 존재 확인 | **O(1)** | **O(degree(V))** |
| 인접 정점 탐색 | **O(V)** | **O(degree(V))** |

인접 행렬은 2차원 배열을 써서 두 정점 간의 연결 여부를 상수 시간에 확인한다. 정점 수가 많고 간선이 적다면 메모리 낭비가 크다.

인접 리스트는 각 정점에 연결된 정점만 가변 배열이나 연결 리스트로 저장한다. 메모리를 절약하지만 특정 두 정점이 연결되었는지 확인하려면 리스트를 순회해야 한다.

실무나 일반적인 문제 해결에서는 정점 수에 비해 간선 수가 적은 희소 그래프가 많아 인접 리스트를 주로 사용한다.

## 21. [자료구조 · 알고리즘] 우선순위 큐를 힙으로 구현하는 이유는 무엇인가?

<!-- id: 9ac88a5c-11c3-4a52-b642-09a97936fdfa -->

배열로 구현한 우선순위 큐는 삽입이나 삭제 시 데이터를 밀어내야 해서 시간이 많이 걸리기 때문이다.

:::stack
최대 힙 | 부모가 자식보다 항상 크거나 같다
최소 힙 | 부모가 자식보다 항상 작거나 같다
:::

힙은 완전 이진 트리 구조를 사용한다. 이를 통해 삽입과 삭제 모두 O(log N)의 시간 복잡도로 처리할 수 있다.

반면 정렬된 배열은 삭제는 빠르지만 삽입 시 데이터 이동이 O(N)만큼 필요하다. 정렬되지 않은 배열은 삽입은 빠르지만 최댓값/최솟값을 찾는데 O(N)이 걸린다.

실무에서는 다익스트라 알고리즘이나 OS의 스케줄러처럼 우선순위가 계속 바뀌는 환경에서 힙을 선택한다.

## 22. [자료구조 · 알고리즘] 해시 충돌 발생 시 해결적으로 어떤 방법을 사용하는가?

<!-- id: 206e4412-af51-4d71-8d71-9210387ee437 -->

체이닝과 오픈 어드레싱으로 해결한다. 충돌이 발생한 데이터를 연결 리스트나 빈 공간으로 밀어내는 방식이다.

| 기준 | 체이닝 | 오픈 어드레싱 |
| --- | --- | --- |
| 저장 방식 | 리스트로 연결 | 빈 슬롯으로 이동 |
| 공간 효율 | 추가 메모리 필요 | 기존 배열로 해결 |
| 삭제 연산 | 리스트에서 제거 | 삭제 마커 필요 |

체이닝은 버킷으로 리스트를 구현하여 데이터가 계속 늘어나도 수용 가능하다. 다만 리스트가 길어지면 탐색 시간이 O(1)에서 O(n)으로 늘어난다.

오픈 어드레싱은 빈 칸을 찾을 때까지 계속 탐색한다. 데이터가 꽉 찰수록 충돌이 잦아져 성능이 급격히 떨어진다. 이를 막기 위해 로드 팩터를 관리하고 리사이징을 수행한다.

## 23. [프레임워크] 내부 메서드 호출에 부가기능이 빠지는 이유는?

<!-- id: c896600d-ad6d-426d-b790-22cc223e1543 -->

같은 객체 안에서 this로 호출하면 프록시를 거치지 않기 때문이다. 프록시가 가로채야 트랜잭션이나 로깅 같은 어드바이스가 실행된다.

:::flow
클라이언트 -> 프록시: 공개 메서드를 호출한다
프록시 -> 어드바이스: 트랜잭션 등을 적용한다
어드바이스 -> 대상 객체: 실제 메서드를 호출한다
대상 객체 -> 대상 객체: 내부 호출은 프록시를 우회한다
:::

JDK 동적 프록시는 인터페이스를 기반으로 한다. 클래스 기반 프록시는 상속을 쓰므로 final 클래스와 final 메서드를 가로챌 수 없다.

적용 경계를 별도 빈으로 분리해 외부 호출로 만드는 방법이 명확하다. 프록시 노출이나 자기 자신 주입은 결합도를 높이므로 우선 선택이 아니다.

## 24. [프레임워크] 엔티티를 API 응답에 바로 쓰면 무엇이 새는가?

<!-- id: 40cade8a-b67a-4d4d-a480-604d64b188f3 -->

영속성 구조와 내부 필드가 외부 계약으로 샌다. 연관관계 직렬화가 지연 쿼리와 순환 참조를 만들고 엔티티 변경이 API 변경으로 번진다.

:::stack
API DTO | 외부 계약과 검증
응용 서비스 | 유스케이스 조정
도메인 엔티티 | 상태와 핵심 규칙
영속성 | 테이블과 연관관계
:::

요청 DTO는 입력 형식과 검증을 맡는다. 응답 DTO는 공개할 필드와 표현을 고정한다. 엔티티는 자신의 불변식과 생명주기에 집중한다.

조회 전용 응답은 필요한 필드만 투영하면 엔티티 그래프를 만들지 않아도 된다. 이는 직렬화 중 추가 쿼리와 과도한 데이터 노출을 줄인다.

분리에는 매핑 코드와 중복 비용이 따른다. 계약이 자주 변하거나 외부에 공개될수록 가치가 크며 작은 내부 기능은 복잡도와 함께 판단한다.

## 25. [프레임워크] 체크 예외와 언체크 예외의 선택 기준은 무엇인가?

<!-- id: 080aa4a6-9daf-4a63-9a2c-09a8d243bd85 -->

복구 가능 여부에 따라 결정한다. 호출자가 예외 상황을 인지하고 대처할 수 있다면 체크 예외를, 개발자의 실수나 시스템 장애라면 언체크 예외를 쓴다.

| 기준 | 체크 예외 | 언체크 예외 |
| --- | --- | --- |
| 복구 가능성 | 높음 | 낮음 |
| 처리 강제 | 컴파일 타임 | 런타임 |
| 상속 클래스 | Exception | RuntimeException |

체크 예외는 시그니처에 명시해야 하므로 호출자에게 처리 의무를 강제한다. 이를 통해 런타임에 발생할 수 있는 예외 상황을 미리 방지할 수 있다.

반면 언체크 예외는 강제성이 없다. 널 포인터 참조나 배열 인덱스 초과 같은 논리적 오류는 코드를 수정해야 풀리는 문제지, try-catch로 잡는다고 해결되지 않기 때문이다.

최근에는 체크 예외의 과도한 사용이 코드 가독성을 해치고 의존성을 높인다는 비판이 많다. 그래서 많은 프레임워크가 언체크 예외로 래핑하여 던지는 추세다.

## 26. [프론트엔드] 레이아웃 계산과 픽셀 갱신은 언제 생기는가?

<!-- id: 9f87d916-34b6-4ff7-ace2-c74e0dd591f9 -->

요소의 크기나 위치가 바뀌면 레이아웃 계산이 생긴다. 색상처럼 기하에 영향 없는 속성이 바뀌면 픽셀만 다시 그린다.

:::flow
기하 속성 변경 -> 레이아웃: 크기와 위치를 계산한다
레이아웃 -> 페인트: 픽셀을 그린다
페인트 -> 합성: 레이어를 배치한다
:::

DOM 쓰기 뒤 곧바로 크기를 읽으면 브라우저가 미뤄 둔 계산을 즉시 끝내야 한다. 읽기와 쓰기를 섞어 반복하면 레이아웃 스래싱이 된다.

애니메이션은 가능하면 transform과 opacity를 쓴다. 별도 레이어에서 합성할 수 있어 레이아웃과 페인트를 피하지만 레이어 메모리는 늘 수 있다.

## 27. [프론트엔드] 서버 HTML과 첫 렌더가 다르면 왜 문제인가?

<!-- id: ca19498f-84e7-46e6-a79f-1e1461fe3dea -->

하이드레이션이 기존 DOM을 안전하게 재사용하지 못한다. 프레임워크가 경고하거나 일부 트리를 다시 그린다. 깜빡임, 상태 손실, 이벤트 연결 오류가 생길 수 있다.

:::flow
서버 -> 브라우저: HTML을 보낸다
브라우저 -> 렌더 함수: 같은 입력으로 첫 트리를 만든다
렌더 함수 -> 기존 DOM: 같으면 이벤트만 연결한다
렌더 함수 -> 재렌더: 다르면 복구 비용이 생긴다
:::

현재 시각, 난수, 시간대, 잘못된 HTML 중첩이 흔한 원인이다. 렌더 중 window나 저장소를 읽어 서버에 없던 값을 만드는 경우도 해당한다.

서버와 클라이언트에 같은 초기 데이터를 전달한다. 브라우저 전용 값은 마운트 뒤 읽는다. 비결정적 출력은 첫 렌더 경로에서 제거한다.

## 28. [프론트엔드] 프론트엔드 성능 최적화 시 번들 크기를 무엇으로 판단하는가?

<!-- id: acc5be7a-f9e9-419c-88aa-3d0bf7192558 -->

최초 로딩 시 사용자가 체감하는 LCP(Largest Contentful Paint)와 TBT(Total Blocking Time)를 기준으로 판단한다. 단순히 파일 용량만 줄이는 것이 아니라 런타임 실행 시간과 파싱 시간을 함께 고려해야 한다.

:::stack
런타임 성능 | JS 실행 및 DOM 조작 속도
네트워크 성능 | 번들 다운로드 및 압축 해제 속도
::: 

위 도식은 번들이 실제 성능에 영향을 주는 두 가지 경로를 보여준다. 파일이 작아도 복잡한 로직이 많으면 TBT가 늘어난다.

코드 분할(Code Splitting)을 통해 초기 진입점에 필요한 최소한의 JS만 로드하게 만든다. 이를 통해 메인 스레드 점유 시간을 줄이고 빠른 상호작용을 유도한다.

트리 쉐이킹(Tree Shaking)으로 사용하지 않는 코드를 제거해 전송량을 줄인다. 라이브러리 선택 시 ESM(ES Modules) 지원 여부를 확인하는 것이 핵심이다.
