# 묶음 10 — 27편

## 1. [네트워크] TCP 연결 종료 시 TIME_WAIT 상태가 누적되어 포트가 고갈되는 현상을 진단하는 방법은 무엇인가?

<!-- id: 2f9ed05f-6771-4752-a46f-9c198e8a812f -->

netstat이나 ss 명령어로 TIME_WAIT 상태의 소켓 개수를 세고 local_port_range 한도와 비교하는 것이다.

:::stack
소켓 수 계측 | ss -s 또는 netstat -antp | grep TIME_WAIT
포트 한도 확인 | sysctl net.ipv4.ip_local_port_range
에러 로그 진단 | Cannot assign requested address 발생 여부
:::

시스템에서 사용할 수 있는 에페머럴 포트 범위는 한정되어 있다. TIME_WAIT 소켓 수가 이 포트 범위를 꽉 채우면 새 연결을 맺을 때 EADDRNOTAVAIL 에러가 발생한다.

주로 요청을 보낸 클라이언트나 백엔드 API를 호출하는 서비스에서 능동적 닫기(Active Close)를 연속으로 수행할 때 이 현상이 나타난다. 따라서 소켓 수뿐만 아니라 어떤 프로세스가 능동적 닫기를 주도하는지 확인해야 한다.

실무에서는 진단 이후 해결책으로 `net.ipv4.tcp_tw_reuse` 커널 설정 적용이나 커넥션 풀ing, HTTP Keep-Alive 도입을 검토하게 된다.

## 2. [네트워크] 실패 응답 코드는 무엇을 기준으로 고르는가?

<!-- id: 58aa7465-a1c0-4167-bb9a-720b8b1800fe -->

요청이나 인증·권한·사용량 제한 같은 클라이언트 측 조건 때문에 처리할 수 없으면 4xx를 쓴다. 서버가 정상 요청을 처리하지 못하면 5xx를 쓴다. 원인과 재시도 가능성을 코드에 담아야 한다.

| 기준 | 4xx | 5xx |
| --- | --- | --- |
| 책임 | 요청 또는 권한 | 서버 처리 |
| 예 | 400, 404, 409 | 500, 503, 504 |

400은 요청 형식이 잘못된 경우다. 401은 인증이 필요하고 403은 신원을 알아도 권한이 없다. 존재를 숨기려면 404를 택할 수도 있다.

409는 현재 자원 상태와 충돌할 때 적합하다. 문법은 맞지만 필드 검증에 실패한 요청은 API 규약에 따라 400 또는 422로 일관되게 처리한다.

503은 일시적 과부하나 점검을 알린다. `Retry-After`를 주면 재시도 시점을 안내할 수 있다. 내부 오류를 모두 200으로 감싸면 중간 장비가 실패를 오해한다.

## 3. [네트워크] 쿠키와 세션의 상태 유지 방식은 무엇으로 구분하는가?

<!-- id: 7b38d98d-9bd4-4db6-86b8-539718229686 -->

저장 위치의 차이다. 쿠키는 클라이언트의 브라우저에, 세션은 서버의 메모리나 DB에 데이터를 저장한다.

| 기준 | 쿠키 | 세션 |
| --- | --- | --- |
| 저장 위치 | 브라우저 | 서버 |
| 데이터 크기 | 제한적 | 사실상 무제한 |
| 보안성 | 낮음 | 높음 |

쿠키는 네트워크 요청마다 자동으로 포함되어 전송된다. 서버는 이를 통해 사용자를 식별하며, 별도의 저장소 없이 상태를 유지한다.

세션은 서버에 데이터를 저장하고 클라이언트에 세션 ID만 전달한다. 실제 데이터는 서버가 관리하므로 쿠키보다 보안성이 높다.

분산 서버 환경에서는 세션 불일치 문제가 발생한다. 이를 해결하기 위해 세션 클러스터링이나 Redis 같은 외부 저장소를 사용한다.

## 4. [데이터베이스] 낙관적 락과 비관적 락은 무엇으로 고르는가?

<!-- id: eb4d321c-88a1-491d-b344-3980915332a5 -->

데이터 충돌로 인한 갱신 손실을 막기 위해 충돌 빈도와 시스템 부하를 기준으로 고른다.

| 기준 | 낙관적 락 | 비관적 락 |
| --- | --- | --- |
| 충돌 빈도 | 드물 때 | 잦을 때 |
| 락킹 비용 | 낮음 (버전 체크) | 높음 (물리적 잠금) |
| 대기 시간 | 없음 (실패 시 재시도) | 발생 (락 획득 대기) |

낙관적 락은 데이터 수정 시점에 버전 번호를 확인해 충돌을 감지한다. 충돌이 없으면 반영하고, 버전이 다르면 예외를 던져 사용자가 다시 시도하게 만든다.

비관적 락은 데이터를 읽을 때부터 잠금을 걸어 다른 트랜잭션이 접근하지 못하게 막는다. 데이터 무결성을 강하게 보장하지만, 대기 시간이 늘어나 성능 저하가 발생할 수 있다.

실무에서는 읽기 비중이 높고 충돌이 적은 서비스에 낙관적 락을 쓴다. 반면, 결제나 재고 관리처럼 충돌이 잦고 데이터 정확성이 절대적인 곳에 비관적 락을 쓴다.

## 5. [데이터베이스] 데이터베이스에서 ANTI JOIN과 SEMI JOIN의 차이점은 무엇인가?

<!-- id: f9a0b251-a94b-4b97-ad0f-957c49073c66 -->

SEMI JOIN은 서브쿼리 조건에 일치하는 메인 테이블 행만 반환하고, ANTI JOIN은 일치하지 않는 행만 반환하는 차이점이 있다.

| 기준 | SEMI JOIN | ANTI JOIN |
| --- | --- | --- |
| 추출 조건 | 우측에 존재함 (`EXISTS`) | 우측에 존재하지 않음 (`NOT EXISTS`) |
| 결과 행 | 매칭되는 메인 테이블 행 | 매칭 없는 메인 테이블 행 |
| 주요 용도 | `IN`, `EXISTS` 최적화 | `NOT IN`, `NOT EXISTS` 최적화 |

두 조인 모두 우측 테이블 데이터를 메인 결과 집합에 결합하지 않고 일치 여부만 검장한다.

두 방식 모두 조건이 만족되는 순간 우측 테이블 탐색을 멈춘다. 일반 INNER JOIN처럼 중복 행이 늘어나지 않아서 별도의 `DISTINCT` 연산 없이도 메인 테이블의 원본 고유성을 유지한다.

면접에서는 ANTI JOIN 사용 시 `NULL` 처리에 관한 주의점을 자주 묻는다. 우측 테이블 컬럼에 `NULL`이 존재하면 `NOT IN` 서브쿼리가 ANTI JOIN으로 변환될 때 전체 결과가 빈 집합으로 변할 수 있다.

## 6. [데이터베이스] 테이블 설계 시 기본키를 설정하는 기준은 무엇인가?

<!-- id: e4014f65-c4a8-4335-9a5d-fe7424175880 -->

데이터의 유일성과 불변성을 보장하는 값을 선택한다. 중복되지 않아야 하며 값이 바뀌지 않는 속성이 가장 적합하다.

| 기준 | 적절한 키 | 부적절한 키 |
| --- | --- | --- |
| **유일성** | 주민등록번호 | 이름, 나이 |
| **불변성** | UUID, 일련번호 | 이메일, 전화번호 |
| **변경 가능성** | 시스템 생성 ID | 사용자 수정 가능 값 |

후보키 중에서 가장 효율적으로 식별자 역할을 수행할 수 있는 키를 기본키로 정한다. 비즈니스 로직에 의존적인 값은 변경 가능성이 있어 피하는 것이다.

대리 키를 사용하는 이유는 데이터 모델의 안정성을 때문이다. 실제 데이터(이메일 등)가 변경되어도 외래 키 참조 무결성을 유지하기 쉽기 때문이다.

기본키가 너무 크거나 복잡하면 인덱스 성능이 왜곡된다. 인덱스 B-Tree 구조에서 키의 크기가 것이 효율적인 검색과 정렬으로 이어진다.

## 7. [모바일] 상태 변경은 어디까지 다시 실행되는가?

<!-- id: 01ecbaee-6d30-4c09-988b-6bfb96364bfd -->

변경된 State를 읽은 재시작 범위가 다시 실행된다. 그 아래에서도 입력이 바뀌지 않은 스킵 가능 컴포저블은 건너뛸 수 있다.

:::flow
상태 -> 컴포저블: 읽은 재시작 범위를 무효화한다
Compose -> 컴포저블: 필요한 범위만 다시 실행한다
Compose -> UI 트리: 달라진 노드만 반영한다
:::

일반 mutable 객체의 필드만 바꾸면 Compose가 변화를 알지 못한다. MutableState로 바꾸거나 Flow를 collectAsState 계열로 수집해야 갱신이 예약된다.

remember는 같은 Composition에서 값만 보존한다. 부수 효과를 본문에 직접 두면 재실행이나 취소 순서가 깨지므로 LaunchedEffect와 DisposableEffect에 둔다.

Compose는 입력 동일성으로 스킵을 판단한다. 안정성 계약과 key를 잘못 선언하면 오래된 UI 상태가 다른 항목에 붙을 수 있다.

## 8. [모바일] 외부 링크를 곧바로 화면에 열어도 되는가?

<!-- id: 9a3084e6-fb3c-4e86-b3fe-3740701dc144 -->

곧바로 열면 안 된다. 스킴과 호스트와 경로를 허용 목록으로 검증하고 로그인 상태와 객체 접근 권한을 확인한 뒤 안전한 인자만 화면에 넘긴다.

:::flow
외부 앱 -> 링크 라우터: URI를 전달한다
링크 라우터 -> 검증기: 스킴과 호스트를 확인한다
검증기 -> 인증 계층: 세션과 권한을 확인한다
인증 계층 -> 화면: 검증된 인자만 넘긴다
:::

커스텀 스킴은 다른 앱이 선점할 수 있다. Android App Links와 iOS Universal Links는 도메인 소유를 검증해 탈취 위험을 줄인다.

로그인이 필요하면 원래 목적지를 보관했다가 인증 후 복원한다. 이미 열린 화면과 중복되지 않도록 백 스택 규칙도 정해야 한다.

인코딩과 중복 파라미터를 정규화한 뒤 검증한다. 웹 주소로 다시 보내는 값은 오픈 리다이렉트가 되지 않도록 대상 도메인을 제한한다.

## 9. [모바일] 화면이 닫혔는데 객체가 남는 이유는?

<!-- id: 21f3e89a-acb2-43f7-b879-67a7b0a88d26 -->

정적 필드와 싱글턴과 실행 중 스레드 같은 긴 수명의 객체가 Activity나 View를 계속 참조하기 때문이다. GC Root에서 도달 가능하면 수집되지 않는다.

:::stack
GC Root | 정적 필드나 실행 중 스레드다
싱글턴·콜백 | 화면 객체를 참조한다
Activity·View | 종료돼도 도달 가능하다
:::

리스너를 등록한 수명에서 해제하고 코루틴과 콜백도 함께 취소한다. UI가 필요 없는 객체에는 Application Context를 사용한다.

ViewModel에는 Activity나 View 참조를 두지 않는다. Fragment의 뷰 바인딩은 onDestroyView에서 비워 뷰 수명과 맞춘다.

힙 덤프에서 누수 객체의 GC Root 경로를 따라간다. 지배 참조를 끊은 뒤 같은 화면을 반복 열고 보유 개수가 줄어드는지 확인한다.

## 10. [아키텍처 · 분산시스템] 서킷 브레이커는 무엇을 막아주는가?

<!-- id: 97fb467a-7f0b-4375-9bb4-416678702c4b -->

죽은 서비스를 계속 두드리다 내 쪽까지 무너지는 것을 막는다. 응답 없는 곳에 요청을 보내면 스레드와 커넥션이 그만큼 묶인다.

:::flow
닫힘 -> 열림: 실패율이 기준을 넘는다. 이제 즉시 거절한다
열림 -> 반열림: 일정 시간 뒤 몇 건만 흘려본다
반열림 -> 닫힘: 성공하면 원래대로
반열림 -> 열림: 또 실패하면 다시 막는다
:::

핵심은 빠른 실패다. 30초를 기다렸다 실패하는 것보다 즉시 실패하는 편이 낫다. 그동안 자원이 안 묶이고 대체 응답을 줄 수 있다.

기준을 잡는 것이 어렵다. 너무 민감하면 잠깐 흔들린 것에도 끊기고, 둔하면 이미 무너진 뒤에 열린다.

면접에서는 재시도와 함께 물어본다. 서킷이 열린 상태에서 재시도를 걸면 서로 상쇄되므로 두 장치의 설정을 함께 봐야 한다.

## 11. [언어 · 런타임] GC 알고리즘 선택 기준은 무엇인가?

<!-- id: e2d1f494-78aa-45b5-88df-a9b300d31862 -->

애플리케이션의 서비스 특성과 지연 시간 허용 범위에 따라 결정한다. 처리량 중심인지, 응답 속도 중심인지가 핵심이다.

| 기준 | Parallel GC | G1 GC | ZGC |
| --- | --- | --- |
| 목표 | 처리량 최대화 | 균형 잡힌 지연 | 초저지연 |
| 특징 | STW 길다 | 리전 분할 관리 | 색상 포인터 사용 |

Parallel GC는 전체 처리량을 높이는 데 유리하다. 하지만 모든 GC 발생 시 전체 시스템이 멈추는 Stop-The-World 시간이 길어 서비스 응답이 끊긴다.

G1 GC는 힙을 리전으로 나누어 효율적으로 수집한다. 설정한 목표 지연 시간을 맞추기 위해 수집 효율이 높은 영역부터 먼저 처리한다.

ZGC는 힙 크기에 상관없이 지연 시간을 10ms 이하로 유지한다. 컬러 포인터와 로드 배리어를 통해 애플리케이션과 동시에 GC를 수행한다.

## 12. [언어 · 런타임] 같은 함수를 불렀는데 this가 달라지는 이유는?

<!-- id: 9d4bf821-5e6d-4985-a3dc-f71c5b778a6e -->

일반 함수의 this는 함수 정의가 아니라 호출 형태로 정해지기 때문이다. 메서드 호출과 일반 호출은 수신자가 다르며 화살표 함수는 바깥 this를 캡처한다.

| 호출 | 표현 | this |
| --- | --- | --- |
| 생성 | new f() | 새 객체 |
| 명시 | f.call(x) | 엄격 함수면 x |
| 메서드 | x.f() | x |
| 일반 | f() | 엄격 함수면 undefined |

객체에서 메서드를 떼어 콜백으로 넘기면 수신자 정보가 사라진다. bind로 고정하거나 수신자를 보존하는 래퍼를 써야 한다.

화살표 함수에는 자체 this와 arguments가 없다. call이나 apply로 this를 바꿀 수도 없고 new로 생성할 수도 없다. 동적 수신자가 필요한 메서드에는 일반 함수가 맞다.

## 13. [언어 · 런타임] 수집기는 처리량과 지연 중 무엇으로 고르는가?

<!-- id: 15d2f624-5763-4105-8dfe-58dd08145d18 -->

배치 작업은 처리량을, 응답형 서비스는 최악 지연 시간을 우선한다. 힙 크기, CPU 여유, 할당률과 실제 JDK 지원 범위도 함께 본다.

| 기준 | Parallel GC | ZGC |
| --- | --- | --- |
| 우선 목표 | 높은 처리량 | 짧은 정지 |
| 대가 | 긴 정지 가능 | CPU·메모리 여유 필요 |

Parallel GC는 수집 중 애플리케이션을 멈추고 여러 GC 스레드를 쓴다. 작업 완료량은 높지만 살아 있는 집합이 크면 정지가 길어진다.

ZGC는 표시와 재배치 대부분을 동시에 수행한다. 짧은 정지를 목표로 하지만 장벽 비용과 충분한 힙 여유가 필요하다.

G1은 리전 단위로 수집해 처리량과 정지 목표를 절충한다. 선택 전 운영과 같은 부하에서 p99 지연, 처리량, GC CPU를 측정한다.

## 14. [언어 · 런타임] 타입스크립트의 구조적 타이핑은 무엇을 기준으로 판별하는가?

<!-- id: db936a6a-fcce-47f1-a5af-2368b6024604 -->

객체의 실제 구조와 필요한 속성이 일치하는지로 판별한다. 이름이 달라도 가지고 있는 멤버의 타입과 형태가 같다면 동일한 타입으로 간주한다.

| 기준 | 명목적 타이핑 | 구조적 타이핑 |
| --- | --- | --- |
| 판별 근거 | 선언된 이름(명칭) | 객체의 형태(구조) |
| 유연성 | 엄격함 | 높음 |

이러한 특성으로 인해 인터페이스를 명시적으로 상속받지 않아도 요구하는 속성만 갖추고 있다면 타입 체크를 통과한다. 덕분에 외부 라이브러리와의 타입 호환성을 확보하기 쉽다.

다만 예상치 못한 타입 일치로 인해 런타임 오류가 발생할 위험이 있다. 이를 방지하기 위해 브랜드 태그나 고유한 식별자를 추가해 타입을 구분하기도 한다.

## 15. [운영체제] 데드락을 해결하기 위한 회피 전략은 무엇인가?

<!-- id: 65a36957-f003-4389-9f1d-92bdba32cb78 -->

은행원 알고리즘을 사용하여 자원 할당 시 안전 상태를 유지하는 것이다. 자원을 할당한 후에도 모든 프로세스가 완료될 수 있는 경로가 있는지 확인한다.

:::flow
자원 요청 -> 안전 상태 확인: 할당 가능한 자원이 있는지 검사
안전 상태 확인 -> 자원 할당: 모든 프로세스가 완료될 수 있는 경로가 있다면 할당
자원 할당 -> 자원 반납: 프로세스 완료 후 자원을 시스템에 반납
:::

회피는 교착 상태가 발생할 수 있는 상황을 아예 만들지 않는 것이다. 요청한 자원을 즉시 줄 수 없다면, 다른 프로세스가 자원 반납을 통해 안전하게 완료될 수 있을 때까지 대기시킨다.

반면 예방은 교착 상태의 발생 조건 네 가지 중 하나라도 깨뜨리는 것. 회피는 시스템의 자원 상태를 계속 추적하며 동적으로적으로 결정한다.

은행원 알고리즘은 모든 프로세스가 필요로 하는 최대 자원량을 미리로 알고 있어야 한다. 실무적으로는 프로세스의 최대 자원을 예측하기 어려워 적용으로 범위가 좁다.

## 16. [운영체제] 쓰레싱이 발생하는 원인과 해결책은 무엇인가?

<!-- id: 5c9cee42-893b-43b8-a767-a4baeff36913 -->

페이지 부재가 빈번하게 발생하여 CPU로의 입출력으로 인해 CPU로의 입출력으로 인해 CPU 이용률이 급격히 떨어지는 현상이다.

:::stack
메모리 부족 | 페이지 부재 빈번
CPU 이용률 | 급격히 하락
::: 

운영체제는 CPU 이용률이 낮아지면 더 많은 프로세스를 메모리에 올려 CPU 이용률을 높이려 한다. 이 과정에서 각 프로세스에 할당된 메모리 공간이 줄어들어 페이지 부재가 더 심해진다.

이런 악순환의 고리가 형성되어 시스템 전체적으로는 CPU가 일을로 하는 것보다 페이지 교체 작업에 더 많은 시간을 쓰게 된다.

해결을 위해서는 워킹셋(Working Set) 모델이나 페이지 부재 빈도(PFF)를 조절하여 프로세스가 필요로 하는 최소한의 프레임을로 할당해 주어야 한다.

## 17. [인프라 · 보안] HTTPS는 무엇을 보장하고 무엇을 못 하는가?

<!-- id: 7ff301ef-5a43-4119-a1f6-6e36a31c4542 -->

오가는 내용의 비밀과 위변조 여부, 그리고 상대가 그 도메인의 주인인지까지 보장한다. 그 너머는 보장하지 않는다.

| 보장하는 것 | 어떻게 | 보장하지 않는 것 |
| --- | --- | --- |
| 내용의 비밀 | 대칭키로 암호화 | 접속한 도메인 자체는 드러난다 |
| 위변조 탐지 | 메시지 인증 코드 | 서버가 안전한지는 모른다 |
| 상대의 신원 | 인증서와 CA 검증 | 그 사이트가 정직한지는 모른다 |

흔한 오해가 둘이다. 자물쇠가 붙었다고 안전한 사이트는 아니다. 인증서는 그 도메인의 주인이 맞다는 것만 말하고, 피싱 사이트도 자기 도메인의 인증서를 받을 수 있다. 그리고 어디에 접속했는지는 숨겨지지 않는다 — DNS 조회와 인증서 교환 과정에서 도메인이 노출된다.

서버에 저장된 뒤의 안전도 별개다. HTTPS는 이동 중만 지킨다. 비밀번호를 평문으로 저장하는 서버는 HTTPS를 써도 털린다.

면접에서는 대칭키와 비대칭키를 왜 섞어 쓰는지로 들어온다. 비대칭키는 느려서 데이터 전체에 쓰기 어렵고, 대칭키는 빠르지만 키를 안전하게 건네줄 방법이 없다. 그래서 비대칭키로 대칭키만 주고받고 이후는 대칭키로 간다.

## 18. [인프라 · 보안] 데이터 오류로 인한 손실을 어떻게 방지하는가?

<!-- id: f8062f83-5259-4475-873e-5bc64057ca97 -->

패리티 비트와 해밍 코드로 검출과 복구로 나누어 처리한다. 단순 검출은 패리티 비트로, 위치를 찾아 복구하는 것은 해밍 코드로 한다.

:::stack
검출 전용 | 패리티 비트. 짝수/홀수 합을 맞춰 오류로 판단
복구 가능 | 해밍 코드. 여러 체크 비트로 위치를 추적
:::

패리티 비트는 데이터 끝에 1비트를 추가해 합을 맞춘다. 1비트만 틀렸을 때 알 수 있지만, 어디가 틀렸을 때인지 모르고 데이터는 버려야 한다.

해밍 코드는 데이터 비트 사이에 체크 비트를 적절히 배치한다. 각 체크 비트는 서로 다른 비트 그룹을 보급한다. 이를 통해 오류가 발생한 정확한 위치를 계산할 수 있다.

단순히로 검출만 하면 재전송 요청을 통해 데이터를 살릴 수 있다. 하지만 지연 시간이 길거나 재전송이 불가능한 메모리 영역에서는 해밍 코드를 직접 복구하는 방식이 쓴다.

## 19. [자료구조 · 알고리즘] B-tree는 왜 디스크에 유리한가?

<!-- id: 212ffacb-9cca-4c8f-9cb5-906568c356b3 -->

한 번 읽을 때 많이 가져오기 때문이다. 디스크는 블록 단위로 읽으므로 노드 하나를 블록만큼 크게 잡으면 읽기 횟수가 준다.

:::tree
[30 60] | 루트 하나에 열쇠가 여럿이다
  [10 20] | 30보다 작은 것
  [40 50] | 30과 60 사이
  [70 80] | 60보다 큰 것
:::

균형 잡힌 이진 트리도 백만 건이면 깊이가 스물이다. 갈래를 백으로 늘리면 셋이면 닿는다. 캐시가 비어 있다면 깊이만큼 디스크를 읽는다.

모든 잎이 같은 깊이에 있다. 넣고 지울 때 노드를 쪼개거나 합쳐서 균형을 지키므로 최악도 `O(log n)`을 지킨다.

위쪽 노드는 대개 버퍼 캐시에 남아 있어 실제 읽기는 깊이보다 적다. 메모리만 쓰는 색인에서는 이 이점이 줄어든다.

## 20. [자료구조 · 알고리즘] 스택과 큐는 어떤 상황에서 구분해 쓰는가?

<!-- id: 123ded34-49d4-439c-b50f-6b3267bca2d3 -->

데이터의 처리 순서가 최신순인지 선입선출순인지에 따라 결정한다. 가장 나중에 들어온 데이터를 먼저 처리해야 하면 스택을, 먼저 들어온 순서대로 처리해야 하면 큐를 쓴다.

| 기준 | 스택 (Stack) | 큐 (Queue) |
| --- | --- | --- |
| 처리 순서 | LIFO (후입선출) | FIFO (선입선출) |
| 주요 연산 | push / pop | enqueue / dequeue |
| 활용 사례 | 되돌리기, 재귀 호출 | 대기열, 프로세스 스케줄링 |

스택은 데이터의 '맥락'을 유지하는 데 유리하다. 함수 호출 스택처럼 현재 작업을 멈추고 새로운 작업을 수행한 뒤, 다시 이전 상태로 돌아와야 할 때 적합하다.

큐는 데이터의 '흐름'을 제어하는 데 유리하다. 요청이 몰릴 때 이를 순차적으로 처리하여 시스템의 부하를 조절하는 버퍼 역할로 주로 쓰인다.

두 구조 모두 삽입과 삭제가 $O(1)$의 시간 복잡도를 가진다. 하지만 큐를 배열로 구현할 때 삭제 연산 시 데이터 시프팅이 발생하므로, 원형 큐나 연결 리스트로 구현하는 것이 효율적이다.

## 21. [자료구조 · 알고리즘] 최단 경로 알고리즘의 선택 기준은 무엇인가?

<!-- id: 8296435a-7e7f-4cf3-8f42-343e167d7983 -->

가중치 유무와 음수 가중치 존재 여부에 따라 결정한다. 가중치가 없다면 BFS, 양수 가중치만 있다면 다익스트라, 음수 가중치가 있다면 벨만-포드 알고리즘을 쓴다.

| 기준 | BFS | 다익스트라 | 벨만-포드 |
| --- | --- | --- | --- |
| 가중치 | 없음 | 양수 | 음수 포함 |

BFS는 모든 노드를 동일한 거리로 계산하므로 가중치가 없을 때 가장 빠르다. 다익스트라는 우선순위 큐를 이용해 최단 거리를 확정하며 탐색 범위를 좁힌다.

벨만-포드는 모든 간선을 반복적으로 확인하여 음수 사이클이 있는지 판단한다. 다익스트라와 달리 음수 가중치가 있어도 정확한 거리값을 찾을 수 있다.

알고리즘마다 시간 복잡도와 정확성의 트레이드오프가 발생한다. 상황에 맞는 알고리즘을 선택해 불필요한 계산량을 줄이는 것이 핵심이다.

## 22. [프레임워크] JVM의 핵심 역할은 무엇인가?

<!-- id: a1497084-ec66-4667-a481-be82e6438792 -->

JVM은 자바 바이트코드를 실행하는 가상 머신이다. OS로 부터 독립적인 실행 환경을 제공하여 'Write Once, Run Anywhere'를 실현한다.

:::stack
JVM 내부 | Java Runtime Environment (JRE)
실행 대상 | Java Bytecode (.class)
::: 

컴파일러가 소스코드를 바이트코드로 변환하면, JVM은 이를 읽어 각 OS에 맞는 기계어로 바이트코드를 해석한다. 이 과정에서 메모리 관리와 최적화가 핵심이다.

가장 큰 특징은 가비지 컬렉션을 통해 메모리를 자동으로 관리한다는 점이다. 개발자가 직접 메모리를 해제하는 수고를 록고, 메모리 누수 가능성을 획기적으로 낮춘다.

JIT 컴파일러는 반복적으로 실행되는 코드를 기계어로 미리 변환해 캐싱한다. 이를 통해 인터프리터 방식의 실행 속도를 획기적으로 개선한다.

## 23. [프레임워크] 스트림의 지연 연산은 왜 필요한가?

<!-- id: 808ae487-ceed-42e8-8eb2-7de7dc8b7497 -->

불필요한 계산을 최소화하여 성능을 최적화하기 때문이다. 모든 데이터를 처리하지 않고 필요한 시점에만 연산을 수행한다.

:::flow
데이터 소스 -> 중간 연산 -> 터미널 연산: 최종 결과가 필요할 때 모든 과정이 시작된다
::: 

중간 연산은 결과값을 즉시 계산하지 않고, 파이프라인을 구성하는 일종의 설계도만 만든다. 필터링이나 매핑 같은 작업이 누적된다.

터미널 연산이 호출되어야만 데이터가 흐르기 시작한다. 이때 스트림은 최적화 엔진을 통해 루프를 한 번만 돌며 모든 연산을 처리한다.

만약 즉시 연산했다면 중간 단계마다 임시 컬렉션을 생성해야 한다. 이는 메모리 낭비와 CPU 오버헤드로 이어진다.

## 24. [프레임워크] 자동 구성은 어떤 조건에서 물러나는가?

<!-- id: 4ff87e8e-5945-4e05-b622-26ca9a5d0dda -->

필요한 클래스가 없거나 프로퍼티 조건이 맞지 않으면 적용되지 않는다. 사용자가 같은 역할의 빈을 선언해도 기본 구성이 물러난다.

:::flow
앱 -> 후보: 클래스와 설정값을 검사한다
후보 -> 조건 평가: 사용자 빈 유무도 확인한다
조건 평가 -> 빈 팩토리: 통과한 기본 빈만 등록한다
:::

SpringBootApplication이 EnableAutoConfiguration을 켠다. 부트는 AutoConfiguration.imports 같은 메타데이터에서 후보를 찾는다.

ConditionalOnMissingBean은 사용자 정의를 존중하는 핵심 장치다. 너무 넓은 타입의 빈을 선언하면 예상치 못한 기본 구성까지 꺼질 수 있다.

구성이 빠졌다면 조건 평가 보고서에서 일치와 불일치 이유를 확인한다. 제외 설정은 의도와 영향 범위를 알 때만 사용한다.

## 25. [프론트엔드] 계산 결과와 함수 참조는 언제 기억해야 하는가?

<!-- id: 24e259d2-5196-4784-aa40-3ffeee416f6e -->

재계산 비용이 크거나 참조 안정성이 하위 최적화에 필요할 때만 기억한다. 값은 useMemo로, 함수 참조는 useCallback으로 유지한다.

| 기준 | useMemo | useCallback |
| --- | --- | --- |
| 반환 | 계산한 값 | 함수 자체 |
| 주된 목적 | 비싼 계산 재사용 | 함수 참조 유지 |

의존성이 Object.is 비교로 같을 때 이전 결과나 참조를 재사용한다. 의존성을 빠뜨리면 함수가 오래된 상태를 잡는 문제가 생긴다.

둘 다 의미 보장이 아닌 성능 최적화다. 값 계산이 싸거나 소비자가 참조를 비교하지 않으면 메모리와 의존성 관리 비용만 늘어난다.

## 26. [프론트엔드] 변경점을 비교하면 언제 비용이 줄어드는가?

<!-- id: 5c284b0c-1288-4a01-92bf-46fd2599c71b -->

메모리의 트리에서 변경점을 모아 실제 노드 갱신 횟수를 줄일 때 이득이다. 비교와 재조정 비용보다 직접 DOM 조작 비용이 클 때 효과가 난다.

| 기준 | 가상 트리 비교 | 직접 DOM 갱신 |
| --- | --- | --- |
| 강점 | 선언적 일괄 반영 | 작은 변경에 단순함 |

렌더링마다 화면 전체를 다시 그리는 것은 아니다. 프레임워크는 이전 트리와 새 트리를 비교해 필요한 DOM 변경만 커밋한다.

업데이트가 작고 구조가 단순하면 직접 조작이 더 싸다. 가상 트리는 무조건 빠른 기술이 아니라 상태 기반 UI를 예측 가능하게 만드는 절충이다.

## 27. [프론트엔드] 클라이언트 경계는 어디에 두는가?

<!-- id: eced940e-fa73-4120-961f-c2b265e04e8e -->

데이터 접근과 무거운 의존성은 서버에 둔다. 상호작용과 브라우저 API가 필요한 최소 영역만 클라이언트로 둔다.

| 기준 | 서버 | 클라이언트 |
| --- | --- | --- |
| 적합한 일 | 데이터 조회 | 상태와 이벤트 |
| 번들 영향 | 코드 미전송 | 코드 전송 |

서버 컴포넌트 코드는 브라우저 번들에 포함되지 않아 자바스크립트를 줄인다. 서버 자원에 직접 접근할 수 있지만 요청 지연은 남는다.

서버에서 클라이언트로 넘기는 props는 직렬화할 수 있어야 한다. 클라이언트 컴포넌트가 서버 자식을 받는 조합으로 상호작용 범위를 좁힌다.
