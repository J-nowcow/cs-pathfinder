# 묶음 08 — 27편

## 1. [네트워크] HTTPS는 HTTP와 무엇이 다른가?

<!-- id: 10f835f1-f9b4-4bff-90ab-d398907b5bea -->

HTTP에 SSL/TLS 프로토콜을 추가해 데이터를 암호화한 것이다. 이를 통해 도청, 변조, 위조를 막는다.

:::stack
HTTPS | HTTP + SSL/TLS
HTTP | 평문 전송
:::

전송 계층 위에 SSL/TLS라는 보안 계층을 얹은 구조다. 클라이언트와 서버가 서로의 신원을 확인하고 암호화 키를 교환하는 과정이 핵심이다.

대칭키로 데이터를 빠르게 암호화하고, 비대칭키로 그 대칭키를 안전하게 전달한다. 성능 저하를 최소화하면서 보안성을 챙긴 방식이다.

인증서 기관(CA)의 서명을 통해 서버가 가짜가 아님을 보증한다. 인증서가 없으면 암호화는 가능해도 상대가 누구인지 알 수 없어 피싱에 취약하다.

## 2. [네트워크] 신뢰성보다 지연을 우선할 기준은?

<!-- id: d8359e86-e42c-491b-b0f7-c7e426833cd2 -->

일부 손실을 허용하고 최신 데이터가 더 중요할 때 UDP가 맞다. 순서와 재전송을 애플리케이션이 직접 설계할 수 있어야 한다.

| 기준 | TCP | UDP |
| --- | --- | --- |
| 전달 | 순서와 재전송 보장 | 보장 없음 |
| 지연 | 손실 시 대기 | 손실을 건너뛸 수 있음 |
| 상태 | 연결 유지 | 연결 상태 없음 |

음성 통화와 게임은 늦게 도착한 과거 패킷의 가치가 낮다. 재전송을 기다리기보다 손실을 보간하고 다음 데이터를 처리하는 편이 낫다.

DNS처럼 요청과 응답이 작고 짧은 경우도 연결 비용을 피할 수 있다. 다만 크기가 커지면 분할과 재시도 전략이 필요하다.

UDP가 곧 빠름을 뜻하지는 않는다. 혼잡 제어와 인증, 순서 보장이 필요하면 직접 구현하거나 QUIC 같은 검증된 프로토콜을 써야 한다.

## 3. [네트워크] 첫 보안 연결에는 왜 왕복이 필요한가?

<!-- id: b97817a2-f658-4ac6-98ea-c320020aeef9 -->

암호 규칙을 합의하고 서버를 인증하며 공유 비밀에서 통신 키를 만들어야 하기 때문이다. 이 준비가 끝나야 애플리케이션 데이터를 안전하게 보낼 수 있다.

:::flow
클라이언트 -> 서버: 버전, 암호군, 키 공유를 제안한다
서버 -> 클라이언트: 선택값, 인증서, 키 공유, 서명, Finished를 보낸다
클라이언트 -> 서버: 인증과 Finished를 검증하고 Finished를 보낸다
:::

TLS 1.3은 키 교환에 필요한 값을 첫 메시지부터 보내 일반적인 새 연결을 1-RTT로 줄였다. 이후 트래픽은 파생된 대칭 키로 암호화한다.

서버는 인증서의 공개 키에 대응하는 개인 키 소유를 증명한다. 브라우저는 인증서 사슬과 호스트 이름을 확인해 중간자 공격을 막는다.

세션 재개는 이전 비밀을 활용해 지연을 줄인다. 0-RTT 데이터는 재전송 공격에 노출될 수 있으므로 멱등한 요청에만 제한하는 편이 안전하다.

## 4. [데이터베이스] SQL에서 뷰나 인라인 뷰를 사용하여 쿼리를 작성할 때 성능 최적화를 위해 주의해야 할 점은 무엇인가?

<!-- id: 659355a6-1670-497f-ae52-55059ff9d6de -->

뷰나 인라인 뷰 작성 시 가장 주의할 점은 옵티마이저의 뷰 병합 실패로 인한 성능 저하다.

| 구분 | 뷰 병합 (Merging) | 뷰 미병합 (Materialization) |
| --- | --- | --- |
| 처리 방식 | 메인 쿼리와 통합 실행 | 결과를 임시 테이블로 구체화 |
| 인덱스 활용 | 메인 쿼리 인덱스 사용 | 구체화 집합에 인덱스 없음 |

옵티마이저가 뷰를 병합하지 못하면 메인 쿼리의 조건이 뷰 내부로 전달되지 않는다.

GROUP BY나 DISTINCT가 들어간 뷰는 병합이 어렵다. 뷰 결과를 임시 집합으로 먼저 만든다. 메모리와 I/O 부담이 늘어난다.

뷰 외부 조건이 내부로 전달되는지 확인한다. 조건 절 푸시다운에 실패하면 뷰 전체를 가져온 뒤 필터링한다.

필요 이상으로 많은 테이블을 조인한 뷰를 피한다. 일부 컬럼만 필요해도 뷰 내부의 모든 조인을 처리한다.

## 5. [데이터베이스] 데이터베이스 정규화를 수행하는 이유는 무엇인가?

<!-- id: de461af2-e76f-4420-85f5-c0c86b9d951d -->

데이터 중복을 최소화하여 데이터 무결성을 유지하고 이상 현상을 방지하기 때문이다.

| 기준 | 정규화 전 | 정규화 후 |
| --- | --- | --- |
| 데이터 중복 | 많음 | 적음 |
| 삽입/삭제/수정 이상 | 발생 가능 | 방지 가능 |
| 조회 성능 | 단순 조인 없음 | 조인 필요 |

정규화를 하지 않으면 동일한 정보가 여러 곳에 저장된다. 이로 인해 데이터를 수정할 때 일부만 수정되어 데이터 간 불일치가 발생하는 수정 이상이 생긴다.

또한, 관련된 정보가 함께 저장되어 필요 없는 정보까지 함께 삽입하거나 삭제해야 하는 삽입 및 삭제 이상이 발생한다.

과도한 정규화는 조회 시 많은 조인(Join) 연산을 유도하여 성능 저하를 일으킨다. 따라서 실무에서는 성능 향상을 위해 일부러 정규화를 푸는 역정규화 과정을 거치기도 한다.

## 6. [데이터베이스] 조인으로 인해 성능 저하가 발생하는 원인은 무엇인가?

<!-- id: 1df69e64-8fcc-48b4-88a5-57d9b3fa0e5e -->

조인이 많아지면 데이터셋의 크기가 기하급수적으로 늘어나고 메모리 내 정렬과 병합 작업이 증가하기 때문이다.

| 기준 | Nested Loop Join | Hash Join | Merge Join |
| --- | --- | --- | --- |
| 처리 방식 | 이중 루프 순회 | 해시 테이블 생성 | 정렬 후 병합 |
| 적합한 데이터 | 소량 데이터 | 대량 데이터 | 정렬된 데이터 |
| 시간 복잡도 | O(N*M) | O(N+M) | O(N log N + M log M) |

Nested Loop Join은 외부 테이블의 모든 행을 하나씩 읽어 내부 테이블에서 조건에 맞는 행을을 찾는다. 인덱스가 없으면 전체 테이블 스캔이 발생해 성능이 급격히 떨어진다.

Hash Join은 작은 테이블을 메모리에 해시 테이블로 올린 뒤 큰 테이블을 스캔하며 매칭되는 값을 찾는다. 메모리 부족 시 디스크 I/O가 발생해 느려진다.

Merge Join은 양쪽 테이블을 조인 키로 정렬한 뒤 순차적으로 읽으며 병합한다. 이미 정렬되어 있거나 범위 조인을 수행할 때 효율적이다.

## 7. [모바일] 뷰 바인딩은 왜 onDestroyView에서 비우는가?

<!-- id: f9cf5fce-d378-43f4-9fd6-bda108fa4dd8 -->

Fragment 인스턴스가 백 스택에 남아도 뷰는 먼저 파괴될 수 있기 때문이다. 바인딩을 계속 잡으면 폐기된 뷰가 수집되지 않고 잘못 접근할 수도 있다.

:::stack
Fragment 수명 | onCreate부터 onDestroy까지다
View 수명 | onCreateView부터 onDestroyView까지다
:::

뷰를 갱신하는 관찰은 viewLifecycleOwner에 묶는다. 그러면 뷰가 파괴될 때 관찰도 멈춘다.

onDestroyView에서 어댑터와 리스너도 필요에 따라 끊는다. Fragment 필드에는 새 뷰가 생기기 전까지 뷰 참조를 남기지 않는다.

## 8. [모바일] 예약한 작업은 정말 한 번만 실행되는가?

<!-- id: 8da4aa3c-b99b-4c3d-a0f7-937489a7a2a1 -->

아니다. 조건이 맞은 뒤 실행되도록 영속적으로 예약하지만 재시도와 중단 때문에 Worker가 여러 번 시작될 수 있다. 외부 부수 효과는 멱등하게 만든다.

:::flow
앱 -> WorkManager: 작업과 제약 조건을 저장한다
WorkManager -> Worker: 조건이 맞으면 실행한다
Worker -> WorkManager: 재시도를 반환하면 다시 예약한다
:::

WorkManager는 프로세스 종료와 기기 재부팅 뒤에도 작업을 다시 예약한다. 다만 정확한 시작 시각은 보장하지 않는다.

성공은 완료로 끝난다. 실패는 영구 실패로 끝난다. 재시도는 백오프 뒤 다시 돈다. 실행 중 제약이 깨지면 작업이 중지되고 다시 시도될 수 있다.

고유 작업은 중복 예약을 줄인다. 서버 요청에는 멱등성 키를 넣고 로컬 갱신은 트랜잭션으로 묶어 실행 중단에도 결과를 일관되게 만든다.

## 9. [모바일] 화면 상태를 둘 때 두 수단을 어떻게 나누는가?

<!-- id: eedcf90a-a00a-4cc9-97d4-56138e002a51 -->

화면 로직과 계산된 UI 상태는 ViewModel에 둔다. 프로세스 재생성 뒤 화면을 복구할 최소 키만 SavedStateHandle에 둔다.

| 기준 | ViewModel | SavedStateHandle |
| --- | --- | --- |
| 구성 변경 | 메모리에 유지한다 | 값도 유지된다 |
| 프로세스 종료 | 인스턴스가 사라진다 | 저장된 값을 복원한다 |

SavedStateHandle도 Bundle 기반이다. 큰 객체 대신 항목 ID와 필터처럼 다시 데이터를 만들 단서만 저장한다.

강제 종료나 최근 앱에서 태스크를 지우면 복원이 보장되지 않는다. 반드시 남아야 하는 데이터는 데이터베이스 같은 영구 저장소에 둔다.

## 10. [아키텍처 · 분산시스템] 분산 시스템에서 CAP 중 무엇을 포기하게 되는가?

<!-- id: c477cda6-0fed-4650-86da-ba77f94f9eeb -->

가용성이나 일관성 중 하나다. 네트워크가 끊기는 일은 고를 수 있는 것이 아니라 일어나는 것이라, 분단 내성은 사실상 전제다.

:::stack
분단 내성 (P) | 네트워크는 끊긴다. 고르는 것이 아니다
일관성 (C) | 끊긴 동안 응답을 막는다
가용성 (A) | 끊긴 동안 옛 값이라도 답한다
:::

그래서 실제 선택은 CP냐 AP냐다. 결제 잔액은 틀린 값을 주느니 막는 편이 낫고, 상품 조회수는 조금 틀려도 답하는 편이 낫다.

오해가 잦은 지점이 있다. 셋 중 둘을 항상 고른다는 뜻이 아니다. 분단이 없는 평상시에는 일관성과 가용성을 함께 지킬 수 있다.

면접에서는 PACELC로 한 단계 더 들어온다. 분단이 없을 때도 지연과 일관성 사이에서 골라야 한다는 확장이다.

## 11. [아키텍처 · 분산시스템] 팩토리 메소드 패턴을 언제 사용하는가?

<!-- id: c455ab5e-f217-4cee-bb5c-bd9486e9ed5b -->

객체 생성 로직을 자식 클래스에서 결정해야 할 때 사용한다. 생성자의 구체적인 클래스 타입을 숨기고 인터페이스로 반환하기 위해서다.

| 기준 | 생성자 호출 | 팩토리 메소드 |
| --- | --- | --- |
| 결합도 | 구체 클래스에 강하게 결합 | 인터페이스에 결합 |
| 확장성 | 새 타입 추가 시 코드 수정 필요 | 자식 클래스에서 확장 가능 |

클라이언트는 팩토리 인터페이스만 알면 된다. 어떤 구체 클래스가 생성되는지 몰라도 기능을 수행할 수 있어 변경에 유연하다.

새로운 제품군이 추가되어도 기존 클라이언트 코드를 수정하지 않아도 된다. 추상 팩토리와 달리 단일 제품의 생성 책임을 분리하는 데 집중한다.

## 12. [언어 · 런타임] 가비지 컬렉션이 멈춤을 만드는 이유는?

<!-- id: acd8d116-38e7-4e74-82ae-3075e2ff9956 -->

살아 있는 객체를 세는 동안 그 관계가 바뀌면 안 되기 때문이다. 세는 중에 애플리케이션이 참조를 바꾸면 이미 확인한 것이 틀려져서, 그 구간만은 실행을 세운다.

:::stack
Eden | 새 객체가 여기 태어난다. 대부분 금방 죽는다
Survivor | 한두 번 살아남은 것이 잠시 머문다
Old | 오래 산 것이 승격된다. 여기 청소가 비싸다
:::

대부분의 객체는 태어나자마자 죽는다. 그래서 젊은 영역만 자주 짧게 치우고 늙은 영역은 가끔 손댄다. 젊은 쪽 청소는 보통 밀리초 단위라 눈에 안 띈다.

문제는 늙은 영역이다. 대상이 많고 흩어져 있어 오래 걸리고, 그동안 응답이 멈춘다. 힙을 키우면 빈도는 줄지만 한 번의 멈춤은 길어진다 — 총량과 최악값의 맞바꿈이다.

요즘 수집기는 세는 일 대부분을 실행과 겹쳐서 한다. 멈추는 구간을 시작과 끝의 짧은 두 번으로 줄이는 방식이다. 완전히 없애지는 못한다.

## 13. [언어 · 런타임] 서로 다른 List 타입 인자는 런타임에 남는가?

<!-- id: 0beab0b2-a792-41a1-9163-b90f9c773534 -->

객체 자체에는 보통 남지 않는다. 컴파일러가 타입 안전성을 검사한 뒤 타입 인자를 소거한다. 문자열 List와 정수 List는 런타임에 같은 클래스다.

| 기준 | 컴파일 시점 | 런타임 |
| --- | --- | --- |
| 타입 인자 | 검사한다 | 객체에는 없다 |
| 형변환 | 필요한 곳에 삽입한다 | 실행 중 검사한다 |

소거 뒤 오버라이딩 시그니처가 달라질 수 있다. 컴파일러는 다형성을 유지하려고 합성 브리지 메서드를 만든다.

타입 변수의 직접 인스턴스화와 배열 생성은 제한된다. 구체 타입 인자를 붙인 타입을 instanceof로 검사하거나 소거형이 같은 메서드를 오버로드할 수도 없다.

다만 필드와 메서드 선언의 제네릭 시그니처는 클래스 파일에 남을 수 있다. 리플렉션은 그 선언 정보를 읽지만 객체의 실제 타입 인자를 복원하지는 못한다.

## 14. [언어 · 런타임] 체크 예외는 언제 API 계약에 넣는가?

<!-- id: 763cc8c4-af6d-4a14-9976-ed90e0ead99f -->

호출자가 복구 전략을 세울 수 있고 반드시 처리 여부를 결정해야 할 때 체크 예외를 계약에 넣는다. 프로그래밍 오류에는 런타임 예외가 맞다.

| 기준 | 체크 예외 | 런타임 예외 |
| --- | --- | --- |
| 컴파일러 | 처리·선언을 강제한다 | 강제하지 않는다 |
| 적합한 상황 | 예측 가능한 복구 | 계약 위반·버그 |

Exception의 하위 타입 중 RuntimeException이 아닌 예외는 체크 대상이다. Error와 런타임 예외는 컴파일러가 처리나 선언을 강제하지 않는다.

체크 예외를 너무 넓게 쓰면 호출 계층마다 의미 없는 catch와 throws가 퍼진다. 복구할 수 없으면 도메인 런타임 예외로 번역하되 원인을 보존한다.

예외를 경계에서 번역하면 저장소나 네트워크 구현을 API 밖으로 숨길 수 있다. 메시지와 원인, 복구 가능 여부를 계약에 명확히 둔다.

## 15. [운영체제] 가상 메모리를 사용하는 이유는 무엇인가?

<!-- id: ea98d35f-0f7b-4508-b7d8-743175283515 -->

물리 메모리보다 큰 프로세스를 실행하고 메모리 효율을 높이기 때문이다.

:::stack
가상 주소 | 프로세스가 보는 주소
페이지 테이블 | 가상 주소를 물리 주소로 매핑
물리 주소 | 실제 RAM의 위치
:::

프로세스는 가상 주소만 보고 동작한다. 운영체제는 필요한 부분만 물리 메모리에 올리고 나머지는 디스크의 스왑 영역에 둔다.

이 방식은 프로세스 간 메모리 격리를 가능케 한다. 각 프로세스는 독립된 주소 공간을 가져 서로의 영역을 침범하지 못한다.

물리 메모리가 부족하면 페이지 폴트가 발생한다. 이때 운영체제는 덜 쓰이는 페이지를 디스크로 내보내고 새 페이지를 가져온다.

## 16. [운영체제] 소스 코드가 실행 파일로 변하는 과정은 무엇인가?

<!-- id: 4df60c8d-051a-4eca-9bec-2c43c5162841 -->

전처리기, 컴파일러, 어셈블러, 링커가 순차적으로 처리한다.

:::flow
소스 코드 -> 전처리기: 매크로 확장 및 헤더 포함
전처리기 -> 컴파일러: 어셈블리 코드로 변환
컴파일러 -> 어셈블러: 기계어로 변환
어셈블러 -> 링커: 실행 파일 생성
:::

전처리기는 `#include`와 같은 지시문을 처리한다. 불필요한 주석을 제거하고 매크로를 실제 값으로 치환한다.

컴파일러는 전처리된 코드를 어셈블리 언어로 바꾼다. 구문 분석을 통해 논리적 오류를 잡고 최적화를 수행한다.

어셈블러는 이를 CPU가 읽는 이진 기계어로 바꾼다. 하지만 이 단계의 파일은 다른 모듈과의 연결 정보가 없다.

링커는 여러 오브젝트 파일을 하나로 합친다. 외부 함수 호출부의 실제 메모리 주소를 연결해 최종 실행 파일을 만든다.

## 17. [인프라 · 보안] CORS는 무엇을 막는가?

<!-- id: 4ce26567-b0b6-4d5e-a6cd-962d3923f5c2 -->

다른 출처에서 온 스크립트가 응답을 읽는 것을 막는다. 요청 자체를 막는 것이 아니다 — 서버에는 도착하고, 브라우저가 결과를 스크립트에 안 넘긴다.

:::flow
스크립트 -> 브라우저: 다른 출처로 DELETE를 보내겠다
브라우저 -> 서버: 먼저 OPTIONS로 물어본다
서버 -> 브라우저: 이 출처와 이 메서드는 허용한다
브라우저 -> 서버: 그제서야 진짜 요청을 보낸다
:::

단순한 요청은 이 예비 확인을 건너뛰고 바로 나간다. 그래서 폼 전송으로 하는 공격은 CORS로 못 막는다 — 그쪽은 CSRF 토큰의 몫이다.

오해가 잦은 지점이 여기다. CORS는 내 서버를 지키는 장치가 아니라 사용자의 브라우저에 있는 자격 증명을 남의 페이지가 쓰지 못하게 하는 장치다. 서버 인증은 따로 있어야 한다.

쿠키를 함께 보내려면 양쪽이 더 엄격해진다. 출처를 `*`로 열어둘 수 없고 정확한 주소를 적어야 한다. 개발 중에 `*`로 열어놓고 배포에서 막히는 일이 여기서 나온다.

## 18. [인프라 · 보안] 공개키와 비밀키는 무엇으로 구분하는가?

<!-- id: 417f12a2-6daa-40e2-8a1c-8cc17a30b82a -->

키의 공개 여부와 암호화/복호화의 주체가 누구인지로 구분한다. 공개키는 누구나 가질 수 있고, 비밀키는 소유자만 엄격히 관리한다.

| 기준 | 공개키 | 비밀키 |
| --- | --- | --- |
| 공개 여부 | 모두에게 공개 | 소유자만 보유 |
| 사용 용도 | 암호화, 검증 | 복호화, 서명 |

공개키 암호화 방식은 서로 다른 키로 암호화와 복호화를 수행한다. A의 공개키로 암호화한 데이터는 오직 A의 비밀키로만 풀 수 있다.

비밀키 방식은 하나의 키를 공유하여 양방향으로 사용한다. 속도가 빠르지만, 키를 안전하게 전달하는 과정에서 탈취될 위험이 크다.

실무에서는 두 방식을 섞어 쓴다. 대칭키를 생성해 공개키로 암호화해 전달하고, 실제 데이터 통신은 전달받은 대칭키로 빠르게 처리한다.

## 19. [인프라 · 보안] 트라이를 사용하는 이유는 무엇인가?

<!-- id: 0e62b699-6555-439e-9eea-cfc08b57b240 -->

문자열 검색 속도를 문자열 길이만큼으로 줄이기 때문이다. 키 전체를 비교하지 않고 문자 경로를 따라가며 빠르게 찾는다.

:::flow
루트 -> 'a' 노드 -> 'b' 노드 -> 'c' 노드: 'abc' 검색 완료
:::

위 도식은 단어의 각 문자를 노드로 연결해 경로로 인식하는 구조를 보여준다.

해시 맵은 평균적으로 O(1)이지만 최악의 경우 충돌로 인해 성능이 떨어진다. 반면 트라이는 최악의 경우에도 문자열 길이인 O(L)을 보장한다.

공통 접두사를 공유하는 구조 덕분에 자동 완성이나 사전 검색 기능 구현에 최적화되어 있다.

## 20. [자료구조 · 알고리즘] 문자열 검색 효율을 높이는 최적의 자료구조는 무엇인가?

<!-- id: a800d17a-9f99-4247-a5a5-e44f199a00b5 -->

트라이(Trie)다. 문자열을 트리 구조로 저장해 접두사 공유를 통해 탐색 시간을 문자열 길이에 비례하게 줄인다.

:::stack
트라이 | 문자열의 각 문자를 노드로 저장
해시 맵 | 전체 문자열을 키로 저장
:::

트라이는 문자열의 공통 접두사를 노드로 공유한다. 따라서 동일한 시작 문자를 가진 단어들은 같은 경로를 따라가므로 중복 탐색을 피한다.

KMP나 라빈-카프 알고리즘은 특정 텍스트 내에서 패턴을 찾을 때 쓴다. 트라이는 사전(Dictionary)처럼 여러 단어를 빠르게 검색하거나 자동완성에 적합하다.

시간 복잡도는 O(L)이다. 여기서 L은 검색하려는 문자열의 길이이며, 데이터셋의 크기와 상관없이 일정하게 유지된다.

## 21. [자료구조 · 알고리즘] 재귀 호출 대신 반복문을 써야 하는 순간은 언제인가?

<!-- id: 436fc399-d963-4956-b653-e5c7c949e473 -->

호출 깊이가 깊어져 스택 오버플로우가 발생할 위험이 있거나 극단의 성능과 메모리 효율이 필요할 때다.

:::stack
재귀 호출 | 매 호출마다 스택 프레임 생성 (메모리 오버헤드)
반복문 | 동일 스택 프레임 안에서 변수 업데이트 (메모리 고정)
:::

위 구조처럼 재귀는 함수를 부를 때마다 매개변수, 지역 변수, 복귀 주소를 스택 메모리에 쌓는다. 따라서 가독성은 높지만 오버헤드가 발생한다.

호출 횟수가 입력 크기에 비례해 커지면 스택 영역 한도를 넘겨 프로그램이 종료될 수 있다. 언어가 꼬리 재귀 최적화를 지원하지 않는다면 가독성을 포기하더라도 반복문으로 전환해야 한다.

## 22. [프레임워크] JPA에서 N+1 쿼리는 왜 생기고 무엇으로 막는가?

<!-- id: 2ac697dd-fb59-4aff-b357-5f9d90a01b56 -->

연관을 지연 로딩으로 두고 목록을 순회할 때 생긴다. 목록을 가져오는 질의 하나에 더해, 원소마다 연관을 채우는 질의가 한 번씩 더 나간다.

:::flow
앱 -> DB: 주문 목록 조회. 질의 1번
앱 -> DB: 1번 주문의 회원 조회
앱 -> DB: 2번 주문의 회원 조회. **원소 수만큼 반복된다**
:::

즉시 로딩으로 바꾸는 것은 답이 아니다. 그러면 연관이 필요 없는 조회에서도 매번 조인이 붙는다. N+1이 사라지는 대신 모든 질의가 무거워진다. 문제를 옮긴 것이지 푼 것이 아니다.

해결은 필요한 자리에서만 한 번에 가져오는 것이다. fetch join이나 @EntityGraph로 그 조회에 한해 함께 읽는다. 어디를 함께 읽을지는 화면이 결정하므로, 매핑이 아니라 질의 쪽에 두는 것이 맞다.

fetch join에도 함정이 있다. 컬렉션을 조인하면 행이 곱해져 부모가 중복되고, 그 상태로는 페이징을 데이터베이스에 맡길 수 없다. 하이버네이트는 이때 전부 읽어 메모리에서 자르며 경고를 남긴다. 목록이 크면 그대로 사고다.

그래서 페이징이 함께 필요한 화면에서는 batch size를 쓴다. 연관을 원소마다 한 번씩이 아니라 IN 절로 묶어 몇 번에 나눠 읽는다. 질의 수가 N에서 N/배치로 줄고 페이징은 데이터베이스가 그대로 맡는다.

## 23. [프레임워크] 서비스 계층이 모든 일을 맡으면 무엇이 무너지는가?

<!-- id: 57680d0a-3338-4a07-b711-1516a830ff1d -->

유스케이스 조정과 비즈니스 규칙, DB 세부 구현이 한곳에 섞여 응집도가 무너진다. 변경 이유가 늘고 단위 테스트와 재사용이 어려워진다.

:::stack
표현 | HTTP 입출력 변환
응용 | 유스케이스와 트랜잭션
도메인 | 상태 전이와 핵심 규칙
인프라 | DB와 외부 연동
:::

표현 계층은 프로토콜을 변환한다. 응용 계층은 유스케이스와 트랜잭션을 조정한다. 도메인 계층은 상태 전이와 핵심 규칙을 지킨다.

인프라 계층은 저장소와 외부 연동을 구현한다. 상위 정책이 구현 기술을 직접 알지 않게 인터페이스 경계를 두면 교체와 테스트가 쉬워진다.

경계는 호출 수를 줄이는 장식이 아니다. 각 변경 이유와 의존 방향을 고정하는 규칙이며 예외를 허용할 때도 근거와 범위를 명시해야 한다.

## 24. [프레임워크] 인증 정보는 어떻게 보안 문맥에 들어가는가?

<!-- id: 46cd1316-9f2a-4c04-861f-d1df114147e6 -->

인증 필터가 요청에서 자격 증명을 꺼내 미인증 토큰을 만든다. AuthenticationManager가 검증을 위임하고 성공 결과를 SecurityContext에 넣는다.

:::flow
필터 -> Manager: 미인증 토큰
Manager -> Provider: 검증 위임
Provider -> Manager: 인증된 주체·권한
Manager -> 필터: 인증 결과
필터 -> 보안 문맥: 결과 저장
:::

AuthenticationProvider는 토큰 종류를 지원하는지 판단한다. 사용자 조회와 비밀번호 해시 비교를 거쳐 주체와 권한을 담은 결과를 만든다.

이후 인가 필터가 보안 문맥의 권한으로 접근을 판정한다. 인증이 없으면 401이다. 인증은 됐지만 권한이 부족하면 403이다.

세션 방식은 보안 문맥을 요청 사이에 복원한다. 무상태 토큰 방식은 매 요청 토큰을 검증한다. 저장 정책과 필터 위치가 흐름을 바꾼다.

## 25. [프론트엔드] useEffect 의존성 배열을 비워두면 언제 실행되는가?

<!-- id: 406b4418-da89-4d72-865c-d8377f1d435a -->

컴포넌트가 마운트될 때 딱 한 번만 실행된다. 배열에 넣은 값이 변하지 않으면 리액트가 이펙트 함수를 다시 호출하지 않기 때문이다.

:::stack
빈 배열 | 마운트 시 1회 실행
값 포함 | 해당 값이 변경될 때 실행
배열 생략 | 매 렌더링마다 실행
:::

위 도식은 의존성 배열의 상태에 따라 실행 시점이 달라짐을 보여준다. 배열을 비워두면 렌더링과 상관없이 생명주기상 마운트 시점에만 작동한다.

함수나 객체를 의존성 배열에 넣을 때는 주의해야 한다. 렌더링 시마다 주소값이 바뀌면 의존성 배열이 비어있지 않음에도 무한 루프에 빠질 수 있다.

## 26. [프론트엔드] 번들 최적화는 어디서 시작하는가?

<!-- id: 5bc8a097-71de-4105-8f40-492b3ad03029 -->

분석 도구로 큰 모듈과 중복 의존성을 찾는 데서 시작한다. 사용하지 않는 코드를 제거하고 진입점별로 나눈 뒤 전송량과 실행 시간을 함께 측정한다.

:::flow
번들 분석 -> 제거: 큰 모듈과 중복 의존성을 찾는다
제거 -> 분할: 트리 셰이킹 뒤 경로별로 나눈다
분할 -> 검증: 전송량과 실행 시간을 비교한다
:::

압축은 전송량만 줄인다. 파싱과 실행 비용을 낮추려면 실제 코드 자체를 덜 보내야 한다. 소스 맵과 분석기로 변경 전후를 확인한다.

청크를 지나치게 잘게 나누면 요청과 로딩 조율 비용이 늘어난다. 화면 진입 빈도와 공통 의존성을 기준으로 경계를 잡아야 한다.

## 27. [프론트엔드] 첫 화면을 막는 리소스는 어떻게 줄이는가?

<!-- id: 509b342c-e196-4739-b5e5-a98cb4179c68 -->

필수 CSS만 먼저 제공하고 나머지는 늦게 불러온다. 스크립트는 의존 순서에 맞춰 defer나 async를 써서 HTML 파싱 정지를 줄인다.

| 기준 | CSS | 스크립트 |
| --- | --- | --- |
| 차단 지점 | 렌더 트리 구성 | HTML 파싱 |
| 완화 | 핵심 CSS 우선 | defer, async |

외부 스타일시트는 CSSOM이 준비될 때까지 첫 페인트를 늦춘다. 사용하지 않는 CSS를 제거하고 미디어 조건을 나누면 차단 범위가 줄어든다.

defer는 파싱 뒤 문서 순서대로 실행한다. async는 다운로드 즉시 실행해 순서를 보장하지 않는다. 독립적인 코드에 알맞다.
