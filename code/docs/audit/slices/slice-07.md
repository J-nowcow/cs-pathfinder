# 묶음 07 — 27편

## 1. [네트워크] HTTP/2는 HTTP/1.1의 무엇을 고쳤는가?

<!-- id: d29e123e-1e44-4e8b-8c97-98b8ee7f7604 -->

한 연결에서 요청 하나가 끝나야 다음이 나가던 제약을 없앴다. 앞의 응답이 늦으면 뒤가 통째로 밀리던 문제가 여기서 온다. HTTP/2는 요청과 응답을 프레임으로 쪼개고 스트림 번호를 붙여 한 연결에 섞어 보낸다.

| 기준 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 한 연결의 요청 | 순서대로 하나씩 | 여러 개가 섞여서 |
| 헤더 | 매번 통째로 | 표로 눌러서(HPACK) |
| 브라우저 우회책 | 도메인 쪼개기, 스프라이트 | 필요 없어진다 |

도착한 순서대로 다시 조립되므로 순서 제약이 사라진다. 연결 하나로 충분해진다.

HTTP/1.1도 연결을 재사용하기는 했다. 다만 응답이 보낸 순서대로 와야 해서 앞의 것이 느리면 뒤에 줄 선 요청이 전부 기다렸다. 그래서 브라우저는 도메인당 연결을 예닐곱 개씩 열었고, 이미지를 하나로 합치는 기법이 유행했다.

다만 TCP 계층의 줄서기는 남는다. 패킷 하나가 유실되면 그 연결의 모든 스트림이 재전송을 기다린다. HTTP/3가 전송을 QUIC으로 바꾼 이유가 이것이다.

면접에서는 우회책이 왜 역효과가 되는지로 들어온다. 도메인을 쪼개면 연결이 늘어 HTTP/2의 이점이 사라진다. 스프라이트는 한 조각만 바뀌어도 전체를 다시 받게 만든다.

## 2. [네트워크] 수신자는 여유 있는데 전송이 느린 이유는?

<!-- id: 944b54e3-4faf-4a40-82e7-80286f3e9109 -->

수신 창이 넉넉해도 네트워크가 혼잡하면 송신자는 혼잡 창을 줄인다. 실제 전송량은 두 창 중 작은 값으로 제한된다.

| 기준 | 흐름 제어 | 혼잡 제어 |
| --- | --- | --- |
| 보호 대상 | 수신자 버퍼 | 네트워크 |
| 제한 값 | `rwnd` | `cwnd` |

수신자는 ACK의 `rwnd`로 남은 버퍼를 알린다. 송신자는 이를 넘겨 보내지 않아 느린 수신자의 버퍼가 넘치는 일을 막는다.

송신자는 알고리즘에 따라 손실, ECN, 지연·전달률 같은 신호로 `cwnd`를 조절한다. 손실 뒤 속도가 크게 떨어지고 서서히 회복되는 이유다.

처리량 문제를 볼 때는 두 창과 왕복 시간, 패킷 손실을 함께 본다. 수신 버퍼만 늘려서는 혼잡 구간이 빨라지지 않는다.

## 3. [네트워크] 중계 서버의 주체는 어떻게 구분하는가?

<!-- id: 4a15b794-4740-4439-9817-a69876de0f47 -->

클라이언트를 대신하면 포워드 프록시다. 서버를 대신하면 리버스 프록시다. 누구의 위치와 신원을 감추고 정책을 적용하는지가 구분 기준이다.

| 기준 | 포워드 프록시 | 리버스 프록시 |
| --- | --- | --- |
| 대리 대상 | 클라이언트 | 서버 |
| 설정 주체 | 사용자 또는 조직 | 서비스 운영자 |
| 주요 역할 | 접근 통제, 익명화 | 분산, TLS 종료 |

포워드 프록시는 외부 서버가 원래 클라이언트 대신 프록시를 보게 한다. 사내 인터넷 통제와 캐시, 우회 접속에 활용한다.

리버스 프록시는 공개 진입점을 하나로 만들고 내부 서버를 숨긴다. 요청 라우팅과 로드 밸런싱, 압축, 인증 같은 공통 기능을 맡는다.

둘 다 중계하므로 배치 관점이 없으면 헷갈린다. 요청을 시작한 쪽을 대리하는지 요청을 받는 쪽을 대리하는지부터 본다.

## 4. [데이터베이스] SQL과 NoSQL은 어떤 기준으로 선택하는가?

<!-- id: 17beb041-8cb3-4c6a-820e-3ff9d60d93fb -->

데이터의 구조와 일관성 필요 수준에 따라 선택한다. 정형 데이터와 엄격한 스키마가 필요하면 SQL, 유연한 데이터 구조와 대규모 확장성이 필요하면 NoSQL을 쓴다.

| 기준 | SQL | NoSQL |
| --- | --- | --- |
| 데이터 구조 | 고정 스키마 | 동적 스키마 |
| 확장 방식 | 수직 확장 (Scale-up) | 수평 확장 (Scale-up) |
| 일관성 | 강한 일관성 (ACID) | 최종 일관성 (BASE) |

위 표는 두 방식의 데이터 관리 전략의 차이점을 보여준다.

SQL은 외래키를 통한 관계형 모델을 사용하여 데이터 무결성을 보장한다. 복잡한 조인 연산이 필요하고 트랜잭션의 원칙을 엄격히 지켜야 하는 금융 서비스 등에 적합하다.

NoSQL은 정해진 틀 없이 데이터를 저장한다. 읽기와 쓰기 속도가 매우 빠르며, 대량의 로그 데이터나 실시간 채팅 데이터처럼 구조가 자주 바뀌는 비정형 데이터 처리에 유리하다.

## 5. [데이터베이스] 데이터베이스 옵티마이저에서 서브쿼리 언네스팅의 정의와 발생 조건은 무엇인가?

<!-- id: 731d1828-bec1-4118-8fad-6f211e38f3ad -->

서브쿼리 언네스팅은 중첩된 서브쿼리를 평탄화하여 조인 문으로 변환하는 최적화 기술이며, 옵티마이저가 조인 방식의 집합 처리가 필터링보다 비용이 낮다고 판단할 때 발생한다.

| 구분 | 서브쿼리 유지 (필터링) | 서브쿼리 언네스팅 (조인) |
| --- | --- | --- |
| 수행 방식 | 메인 쿼리 행마다 반복 실행 | 조인 기법(Hash/NL)으로 일괄 처리 |
| 최적화 | 드라이빙 집합 변경 불가 | 조인 순서 및 기법 자유롭게 선택 |

위 표처럼 언네스팅을 거치면 서브쿼리가 메인쿼리와 동등한 조인 대상이 된다. 이에 따라 옵티마이저는 조인 순서 변경이나 해시 조인 등 다양한 최적화 선택지를 얻는다.

주로 `IN`이나 `EXISTS` 절로 작성된 서브쿼리가 세미 조인이나 안티 조인으로 변환될 수 있을 때 적용된다. 상관 서브쿼리이더라도 서브쿼리의 조인 조건이 메인 쿼리의 키와 동등하게 연결될 수 있으면 언네스팅 대상이 된다.

다만 서브쿼리의 결과가 1:N 관계일 때 단순 조인으로 변환하면 메인 쿼리의 결과 집합이 부풀어 오를 수 있다. 따라서 옵티마이저는 유일성 검증이나 집계 작업을 거쳐 데이터 중복을 방지한다.

## 6. [데이터베이스] 인덱스를 만들었는데 실행 계획에서 타지 않는 이유는?

<!-- id: 89d388cf-89c4-4956-aaf6-1694bfb4e576 -->

인덱스가 있어도 옵티마이저가 쓸 수 없거나 쓰지 않는 편이 낫다고 판단한 것이다. 두 경우는 원인이 다르다.

| 갈래 | 실행 계획에서 | 대표 원인 |
| --- | --- | --- |
| 쓸 수 없다 | 후보에도 안 오른다 | 컬럼에 함수 적용, 암묵 타입 변환, 선행 컬럼 누락 |
| 쓰지 않는다 | 후보엔 있는데 안 고른다 | 조회 비율이 높다, 통계가 낡았다 |

쓸 수 없는 경우가 먼저다. 인덱스 컬럼에 함수나 연산을 적용하면 인덱스는 무력해진다. 저장된 값과 비교 대상이 달라지기 때문이다. 타입이 암묵적으로 변환되는 경우도 같다. 복합 인덱스에서 선행 컬럼을 조건에 넣지 않은 경우도 여기 속한다.

쓰지 않기로 한 경우는 통계 문제다. 조회 대상이 전체의 상당 비율이면 인덱스로 한 건씩 찾아가는 것보다 풀 스캔이 빠르다. 옵티마이저는 카디널리티 추정으로 이를 판단하는데, 통계가 오래되면 추정이 틀린다.

진단 순서가 있다. 실행 계획을 먼저 보고 인덱스가 후보에 올랐는지 확인한다. 후보에도 없으면 쓸 수 없는 경우이고, 후보에 있는데 선택되지 않았으면 통계나 비용 추정 문제다.

면접에서는 함수 적용 사례를 자주 묻는다. 날짜 컬럼에 포맷 함수를 씌운 조건이 대표적이다. 조건을 범위 비교로 바꾸면 인덱스가 다시 살아난다.

## 7. [모바일] 부모 작업이 취소되면 자식은 어떻게 되는가?

<!-- id: a51f25d6-19ac-47e0-9ac4-8a82b740ce3e -->

부모 작업이 취소되면 모든 자식 작업에도 취소가 전파된다. 자식은 같은 수명 경계 안에서 정리되고 부모보다 오래 남지 않는다.

:::flow
부모 -> 자식: 취소를 아래로 전파한다
자식 -> 부모: 실패를 위로 전파한다
부모 -> 형제 자식: 일반 Job이면 함께 취소한다
:::

부모는 모든 자식이 끝나야 완료된다. 이 규칙 덕분에 호출 범위를 벗어난 작업이 남는 것을 막고 예외와 자원을 한곳에서 관리할 수 있다.

자식 하나의 실패를 격리해야 한다면 SupervisorJob이나 supervisorScope를 쓴다. 이때도 부모 취소는 모든 자식에게 전파된다.

## 8. [모바일] 앱이 백그라운드에서 죽는 이유는?

<!-- id: 911ca3df-2237-4cb4-97ef-ca788cb85fee -->

시스템이 메모리를 회수하기 때문이다. 앞에 보이는 앱을 살리는 것이 우선이라, 안 보이는 프로세스부터 순서대로 거둬간다.

:::stack
포그라운드 | 화면에 보인다. 거의 안 죽인다
보이는 상태 | 가려졌지만 살아 있다
서비스 | 백그라운드 작업 중. 상황에 따라 거둔다
캐시된 상태 | 안 보인다. 여기부터 먼저 죽는다
:::

죽는 것은 사고가 아니라 설계다. 그래서 앱은 언제 죽어도 되도록, 그리고 돌아왔을 때 이어지도록 만들어야 한다.

문제는 죽을 때 알림이 없다는 것이다. 화면을 떠날 때 저장하지 않으면 그대로 사라진다. 사용자에게는 "쓰던 게 날아갔다"로만 보인다.

오래 걸리는 일은 앱 프로세스에 매달지 않는다. 업로드나 동기화는 작업 관리자에 맡겨서, 프로세스가 죽어도 시스템이 나중에 다시 실행하게 한다.

## 9. [모바일] 푸시 알림이 안 오는 이유는 대개 무엇인가?

<!-- id: ad1c8aaa-dd18-43ec-96c6-1bc2ffae28b6 -->

기기가 절전 상태로 들어가 네트워크와 작업을 묶어 처리하고 있기 때문이다. 서버가 보냈다고 즉시 도착하는 것이 아니다.

안드로이드는 화면이 꺼진 채로 시간이 지나면 도즈 모드로 들어간다. 이때 네트워크 접근과 예약 작업이 일정 간격으로 몰아서 처리된다. 배터리를 아끼려는 설계이고, 그 대가로 알림이 몇 분씩 늦을 수 있다.

:::flow
서버 -> 푸시 서비스: 메시지 전달
푸시 서비스 -> 기기: 연결이 열려 있을 때 내려보낸다
기기 -> 앱: 절전 중이면 다음 창이 열릴 때까지 미룬다
:::

급한 알림에는 높은 우선순위를 지정할 수 있다. 그러면 절전을 뚫고 즉시 전달되지만 무제한은 아니다 — 남용하면 할당량이 깎여 오히려 더 늦어진다. 진짜 사용자를 깨워야 하는 메시지에만 쓴다.

면접에서는 전달 보장을 묻는다. 푸시는 최선 노력이라 유실될 수 있다. 놓치면 안 되는 것은 알림에만 기대지 말고, 앱이 열릴 때 서버에서 다시 확인하는 경로를 함께 둔다.

## 10. [아키텍처 · 분산시스템] 배포 방식은 무엇을 기준으로 고르는가?

<!-- id: f612b074-b3f1-43ad-b45e-d2c6d3d17c2e -->

문제가 생겼을 때 몇 명이 겪느냐다. 되돌리는 속도와 자원 비용이 그다음이다.

| 기준 | 블루그린 | 카나리 |
| --- | --- | --- |
| 노출 범위 | 전환 즉시 전부 | 일부부터 |
| 되돌리기 | 트래픽만 되돌린다 | 비율을 줄인다 |
| 자원 | 두 벌이 필요 | 한 벌에 조금 더 |

블루그린은 새 버전을 통째로 띄워 두고 트래픽만 옮긴다. 되돌리기가 가장 빠르지만 그 순간 모든 사용자가 새 버전을 만난다.

카나리는 5%부터 늘린다. 문제가 있어도 그만큼만 겪지만, 두 버전이 동시에 도는 동안 DB 스키마가 양쪽과 맞아야 한다.

면접에서는 스키마 변경을 어떻게 다루는지로 들어온다. 컬럼을 지우는 배포는 한 번에 못 한다. 읽기를 끊고, 쓰기를 끊고, 그다음에 지운다.

## 11. [아키텍처 · 분산시스템] 컴포지트 패턴을 어떤 상황에서 사용하는가?

<!-- id: 6c67c76c-45ce-4c5e-9bec-b86322a0d2cb -->

전체와 부분의 관계를 가진 객체들을 동일한 인터페이스로 다루기 위해 사용한다. 단일 객체와 복합 객체를 구분하지 않고 하나의 타입으로 처리하고 싶을 때다.

| 기준 | 리프(Leaf) | 컴포지트(Composite) |
| --- | --- | --- |
| 구성 요소 | 단일 객체 | 리프와 컴포지트의 집합 |
| 인터페이스 | 기본 동작으로 구현 | 자식 요소들의 동작을 위임 |

클라이언트는 구체적인 타입으로 형변환을 하지든가 구분 로직을 없다. 그냥 호출하면 리프는 자기 일을 하고, 컴포지트 컴포지트는 내부의 자식들을 순회하며 동작을 수행한다.

이 방식은 트리 구조의 데이터를 모델링할 때 가장 효율적이다. 폴더와 파일로 구성된 파일 시스템이나 UI 컴포넌트 계층 구조가 대표적인 사례다.

다만, 자식 요소의 제약을 추가하기로 어렵다. 특정 컴포지트에만 특정 리프를 넣고 싶을 때, 인터페이스에 모든 메서드를 지원해야 하므로 런타임으로 체크해야 하는 단점이 있다.

## 12. [언어 · 런타임] volatile은 무엇을 보장하고 놓치는가?

<!-- id: b1a3b244-6da2-4a91-a161-29177c46bf91 -->

volatile 쓰기는 뒤따르는 같은 변수의 읽기보다 먼저 일어난다. 해당 접근을 경계로 가시성과 재정렬 제약을 제공하지만 복합 연산은 원자화하지 않는다.

| 기준 | volatile | synchronized |
| --- | --- | --- |
| 가시성·순서 | 보장한다 | 보장한다 |
| 복합 연산 원자성 | 보장하지 않는다 | 같은 모니터로 보호할 때 보장한다 |

한 스레드가 volatile 변수에 쓰기 전에 수행한 일반 쓰기도 그 값을 읽은 스레드에 보인다. 이 happens-before 관계가 다른 상태의 전달까지 만든다.

단순 상태 플래그와 완전히 생성된 객체 참조의 게시에는 적합하다. 이중 확인 잠금의 인스턴스 참조에도 필요하다.

count++는 읽기, 계산, 쓰기의 세 단계라 volatile이어도 갱신을 잃을 수 있다. 경쟁 갱신에는 AtomicInteger나 잠금이 필요하다.

## 13. [언어 · 런타임] 상태 변경을 막으면 동시성에서 무엇을 얻는가?

<!-- id: 6b1a37d0-9b64-4af8-af52-d96041ef3f8b -->

생성 뒤 상태가 변하지 않으면 여러 스레드가 잠금 없이 공유하기 쉽다. 해시 키도 안정된다. 대신 변경마다 새 객체가 필요하다.

| 기준 | 불변 객체 | 가변 객체 |
| --- | --- | --- |
| 공유 | 동기화 부담이 작다 | 경쟁을 제어해야 한다 |
| 변경 | 새 객체를 만든다 | 제자리에서 바꾼다 |

필드를 private final로 두는 것만으로는 부족하다. 생성자에서 가변 인자를 복사하고 내부 배열과 컬렉션도 방어적 복사로 반환해야 한다.

final 필드는 생성자 종료 뒤 초기화 안전성을 제공한다. 단, 생성 중 this가 외부로 노출되면 이 보장이 깨질 수 있다.

작은 값 객체에는 잘 맞는다. 큰 그래프를 자주 갱신하면 할당과 복사 비용이 커져 빌더나 구조 공유 컬렉션이 필요할 수 있다.

## 14. [언어 · 런타임] 참조 횟수가 0이 아닌 객체도 왜 수거되는가?

<!-- id: 7e2716c9-fed0-41b1-9382-787ba6b17fa9 -->

CPython의 참조 카운팅만으로는 서로를 가리키는 순환 객체를 해제할 수 없다. 외부에서 닿지 않는 순환은 별도 순환 수집기가 찾아 수거한다.

| 기준 | 참조 카운팅 | 순환 수집 |
| --- | --- | --- |
| 해제 조건 | 참조 수 0 | 외부에서 도달 불가 |
| 시점 | 대체로 즉시 | 수집 주기 |
| 강점 | 예측 가능 | 순환 처리 |

참조 횟수가 0이 되면 대부분 즉시 해제된다. 순환 수집기는 추적 대상 컨테이너를 세대별 정책으로 검사한다. 오래 살아남은 객체는 덜 자주 본다.

gc.disable()은 자동 순환 수집만 끈다. 참조 카운팅은 계속 동작한다. 수집 빈도를 낮추면 정지는 줄지만 순환 객체의 메모리 회수는 늦어진다.

## 15. [운영체제] 가상 메모리는 무엇을 해결하는가?

<!-- id: 4b85da13-1505-4313-b640-1dd708d1fbb5 -->

프로세스마다 자기만의 연속된 주소 공간을 준다. 실제 물리 메모리가 조각나 있어도, 남의 메모리와 섞여 있어도 프로그램은 그것을 몰라도 된다.

:::flow
CPU -> MMU: 가상 주소로 읽어라
MMU -> 페이지 테이블: 이 주소는 어느 프레임인가
페이지 테이블 -> MMU: 없다. 디스크에 밀려 있다
MMU -> 커널: 페이지 폴트. 가져와라
커널 -> CPU: 프레임에 올렸다. 다시 실행해라
:::

얻는 것이 셋이다. 프로세스끼리 격리되고, 물리 메모리보다 큰 프로그램이 돌고, 같은 코드를 여러 프로세스가 한 벌만 올려 쓴다.

값은 변환 비용이다. 주소마다 테이블을 뒤지면 느려서 TLB라는 캐시를 둔다. 컨텍스트 스위칭에서 이 캐시가 비워지는 것이 전환 비용의 큰 몫이다.

디스크로 밀리기 시작하면 성능이 무너진다. 페이지 폴트가 연쇄로 나면서 실행보다 옮기는 데 시간을 더 쓰는 상태를 스래싱이라 한다.

## 16. [운영체제] 사용자 모드와 커널 모드 전환의 이유는 무엇인가?

<!-- id: 04ed8550-4c49-4cfc-8a8b-151aae35920e -->

시스템 콜을 통해 커널의 특권 권한으로 진입하여 하드웨어와 시스템 자원을 안전하게 보호하기 때문이다.

:::stack
사용자 모드 | 제한된 권한. 애플리케이션이 동작하는 영역
커널 모드 | 무제한 권한 | 하드웨어 제어 및 메모리 보호
:::

사용자 모드에서 하드웨어에 직접 접근하면 악성 코드가 메모리를 조작하거나 시스템을 파괴할 수 있다. 따라서 CPU의 모드 비트를 통해 접근 권한을 시스템 콜로 격리한다.

시스템 콜이 호출되면 인터럽트가 발생하고, CPU는 현재 상태를 저장한 뒤 커널 모드로 전환한다. 커널은 요청한 작업을 수행한 뒤 다시 사용자 모드로 돌아온다.

이 과정에서 컨텍스트 스위칭 비용이 발생한다. 잦은 시스템 콜 호출은 성능 저하의 원인이며, 이를 줄이기 위해 vmsplice나 io_uring 같은 기술이 사용된다.

## 17. [운영체제] 프로세스와 스레드의 핵심 차이는 무엇인가?

<!-- id: 8add93e5-3894-4b90-95bb-b7fb8058e071 -->

자원 할당과 공유 범위의 차이다. 프로세스는 운영체제로부터 독립적인 메모리 공간을 할당받지만, 스레드는 프로세스 내의 메모리를 공유한다.

| 기준 | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 독립적 할당 | 스택 제외 공유 |
| 컨텍스트 스위칭 | 무겁다 | 가볍다 |
| 영향도 | 독립적 실행 | 장애 전파 가능 |

프로세스는 코드, 데이터, 힙 영역을 각자 가진다. 그래서 한 프로세스가 죽어도 다른 프로세스에 직접적인 영향을 주지 않는다.

스레드는 힙과 정적 데이터를 공유하고 개별 스택만 가진다. 데이터 공유가 빠르지만, 한 스레드의 메모리 오염이 전체 프로세스를 종료시킬 수 있다.

컨텍스트 스위칭 비용도 다르다. 프로세스는 캐시 메모리를 완전히 비워야 하지만, 스레드는 공유 영역이 많아 전환 속도가 빠르다.

## 18. [인프라 · 보안] 고정 소수점과 부동 소수점은 무엇으로 구분하는가?

<!-- id: 0d67cdac-b12a-4508-a843-bf5fc3240f73 -->

소수점의 위치를 고정하느냐, 혹은 데이터의 값에 따라 유동적으로 옮기느냐의 차이다.

| 기준 | 고정 소수점 | 부동 소수점 |
| --- | --- | --- |
| 소수점 위치 | 정해진 위치 | 값에 따라 변함 |
| 표현 범위 | 좁음 | 매우 넓음 |
| 연산 속도 | 빠름 | 느림 |

고정 소수점은 정수부와 소수부의 비트 수를 미리 정해둔다. 계산이 정수 연산과 비슷해 속도가 매우 빠르지만, 표현할 수 있는 숫자의 범위가 매우 제한적이다.

부동 소수점은 가수부와 지수부를 나누어 소수점의 위치를 조정한다. 아주 작은 수나 아주 큰 수를 효율적으로 표현할 수 있어 범용적인 계산에 쓰인다.

다만 부동 소수점은 2진수로 변환하는 과정에서 무한 소수가 발생한다. 이로 인해 정밀한 계산이 필요한 금융권 서비스에서는 오차가로 인해 고정 소수점이나 별도의 정밀도 높은 타입을 사용한다.

## 19. [인프라 · 보안] 컨텍스트 스위칭은 왜 비용이 발생하는가?

<!-- id: 0671d985-6096-44de-8d32-24f8669d880d -->

현재 실행 중인 프로세스의 상태를 저장하고 다음 프로세스의 상태를 복원하는 과정에서 CPU 시간이 소모되기 때문이다.

:::flow
실행 프로세스 -> PCB 저장: CPU 레지스터 값을 기록한다
PCB 로드 -> 다음 프로세스: 저장된 값을 레지스터에 복구한다
::: 

위 과정에서 CPU는 실제 연산을 수행하지 않고 상태 관리만 한다. 특히 메모리 관리 유닛(MMU)의 페이지 테이블 베이스 레지스터를 교체하면 TLB 캐시가 모두 무효화된다.

캐시 미스가 급증하며 메모리 접근 속도가 느려진다. 이를 '캐시 오염'이라 하며, 프로세스가 다시 안정적인 속도로 복구되기까지 시간이 걸린다.

이런 오버헤드가 누적되면 CPU가 실제 작업보다 문맥 교환에 더 많은 시간을 쓰는 쓰레싱 상태에 빠질 수 있다.

## 20. [자료구조 · 알고리즘] 문자열 검색 최적화 시 어떤 기준으로 알고리즘을 고르는가?

<!-- id: 588dc1c9-8c1b-417f-bbeb-c3932c61de1b -->

검색 대상의 크기, 패턴의 반복성, 그리고 검색 빈도에 따라 고른다. 정적인 사전에서 빠른 조회가 필요하면 트라이를, 긴 텍스트 내 단일 패턴 검색은 KMP나 라빈-카프를 쓴다.

| 기준 | 트라이 | KMP / 라빈-카프 |
| --- | --- | --- |
| 주 용도 | 사전식 탐색 | 패턴 매칭 |
| 시간 복잡도 | 문자열 길이 $O(m)$ | 텍스트 길이 $O(n)$ |
| 메모리 사용 | 매우 높음 | 낮음 |

트라이는 문자열을 트리 형태로 저장해 접두사 공유를 극대화한다. 한 번 구축하면 검색 속도가 매우 빠르지만, 각 노드에 포인터 배열을 두어 메모리 낭비가 심하다.

KMP는 패턴 내부의 반복 구조를 미리 계산해 불필요한 비교를 건너뛴다. 텍스트를 되돌아가지 않고 한 번만 훑으므로 효율적이다.

라빈-카프는 해시 값을 이용해 문자열을 비교한다. 해시가 일치할 때만 실제 문자열을 대조하므로, 여러 패턴을 동시에 찾거나 대용량 데이터를 처리할 때 유리하다.

## 21. [자료구조 · 알고리즘] 재귀 함수 사용 시 스택 오버플로가 발생하는 이유는 무엇인가?

<!-- id: b7d2bf6d-44dc-4f87-b4b6-0a5badabbb01 -->

함수 호출 시마다 스택 프레임이 생성되어 메모리의 스택 영역을 가득 채우기 때문이다.

:::stack
스택 프레임 | 지역 변수, 매개변수, 복귀 주소
스택 메모리 | 프레임이 쌓이는 한정된 공간
:::

재귀는 자기 자신을 다시 호출하며 멈추지 않고 쌓인다. 각 호출은 이전 상태를 기억해야 하므로 메모리 공간을 계속 점유한다.

탈출 조건이 없거나 깊이가 너무 깊으면 할당된 스택 크기를 초과한다. 이때 런타임 에러인 스택 오버플로가 발생한다.

반복문으로 대체하면 추가적인 스택 프레임 생성이 없어 메모리 효율이 높다. 하지만 트리나 그래프 같은 계층 구조 탐색 시에는 재귀가 가독성이 좋다.

---

## 22. [프레임워크] @Transactional이 걸리지 않는 경우는?

<!-- id: 7c4fc33e-3e7f-4204-b0ef-5376568ea8d6 -->

프록시를 거치지 않고 메서드에 들어갔을 때다. 스프링의 트랜잭션은 코드가 아니라 프록시가 여는 것이라, 프록시를 통과하지 않으면 애초에 열릴 기회가 없다.

가장 흔한 자리가 자기 호출이다. 같은 클래스 안에서 `this.method()`로 부르면 그 호출은 프록시를 지나지 않고 실제 객체로 곧장 들어간다. 애너테이션은 붙어 있는데 아무 일도 일어나지 않는다. 로그도 예외도 없어서 원인을 찾기 어렵다.

:::flow
다른 빈 -> 프록시: 빈 참조로 부른다. **여기서 트랜잭션이 열린다**
프록시 -> 실제 객체: 메서드 실행
실제 객체 -> 실제 객체: this.method(). 프록시를 건너뛴다 — 안 걸린다
:::

private 메서드도 같은 이유로 안 걸린다. CGLIB 프록시는 상속으로 만들어지는데 private은 재정의할 수 없다. final 메서드와 final 클래스도 마찬가지다.

걸렸는데 안 되돌아가는 경우도 있다. 기본 롤백 대상은 unchecked 예외라, 체크 예외를 던지면 트랜잭션은 그대로 커밋된다. 되돌리려면 rollbackFor를 명시해야 한다.

면접에서는 왜 자기 호출이 안 되는지를 프록시 구조로 설명할 수 있는지를 본다. 우회책을 아는 것보다 구조를 아는 쪽이 중요하다. 우회책은 대개 그 메서드를 다른 빈으로 꺼내는 것이고, 꺼내야 한다는 판단 자체가 구조 이해에서 나온다.

## 23. [프레임워크] 생성자 주입이 기본 선택인 이유는?

<!-- id: 153ee4b0-df68-400e-9a05-d10b23cf4fbe -->

필수 의존성을 객체 생성 시점에 보장하고 불변으로 만들 수 있기 때문이다. 테스트에서 직접 주입하기 쉽다. 순환 참조도 시작 단계에서 드러난다.

| 기준 | 생성자 주입 | 필드 주입 |
| --- | --- | --- |
| 필수성 | 생성 시 확인 | 실행 뒤 발견 |
| 불변성 | final 가능 | final 불가 |
| 테스트 | 직접 전달 | 컨테이너 필요 |

선택 의존성은 세터나 ObjectProvider로 표현할 수 있다. 필수 값과 선택 값을 주입 방식에서 구분하면 객체의 계약이 선명해진다.

생성자가 하나면 @Autowired를 생략할 수 있다. 매개변수가 지나치게 많다면 주입 문법보다 클래스가 너무 많은 책임을 가진 것은 아닌지 먼저 본다.

## 24. [프레임워크] 요청 공통 처리는 어느 지점에 두는가?

<!-- id: 73bef8e4-d8f4-4fa4-9814-a6a1f5ee6284 -->

원시 요청과 응답 전체에 적용할 일은 필터에 둔다. 선택된 컨트롤러 정보가 필요한 일은 인터셉터에 둔다. 비즈니스 규칙은 서비스에 둔다.

| 기준 | 필터 | 인터셉터 |
| --- | --- | --- |
| 경계 | 서블릿 체인 | MVC 내부 |
| 문맥 | 요청·응답 | 핸들러·모델 |
| 용도 | 보안·인코딩 | 로깅·검사 |

필터는 DispatcherServlet 전후를 감싸 정적 자원과 오류 디스패치에도 관여할 수 있다. 인터셉터는 preHandle부터 afterCompletion까지 실행된다.

필터에서 난 예외는 보통 ControllerAdvice 범위 밖이다. 필터 체인에서 응답으로 바꾸거나 서블릿 오류 처리로 넘겨야 한다.

실행 횟수와 순서도 설계 대상이다. 비동기·오류 디스패치에서는 필터가 다시 불릴 수 있어 OncePerRequestFilter 정책을 확인해야 한다.

## 25. [프론트엔드] div만 쓰면 어떤 비용이 드는가?

<!-- id: 6e93f902-1ad0-4373-939a-e3b0658f0120 -->

브라우저와 보조 기술이 구조와 역할을 알기 어렵다. 개발자는 ARIA와 키보드 동작을 직접 구현해야 한다. 코드의 의도도 흐려진다.

| 기준 | 시맨틱 요소 | div 흉내 |
| --- | --- | --- |
| 구조 인식 | 기본 제공 | ARIA 직접 지정 |
| 키보드 동작 | 기본 제공 | 직접 구현 |

네이티브 요소는 기본 역할과 키보드 동작을 함께 제공한다. button을 div로 흉내 내면 Enter와 Space 처리, 비활성 상태도 직접 구현해야 한다.

화면 모양만 보고 요소를 고르면 안 된다. 콘텐츠의 의미와 동작을 먼저 정하고 CSS로 표현을 바꿔야 접근성과 유지보수가 함께 좋아진다.

## 26. [프론트엔드] 목록 항목의 정체성을 어떻게 보존하는가?

<!-- id: ec7b6bcd-d9e9-46ee-907d-94e3620548a2 -->

렌더 사이에 같은 항목을 가리키는 안정적이고 고유한 키를 준다. 프레임워크는 키로 기존 인스턴스와 상태를 새 항목에 대응시킨다.

| 기준 | 안정적 ID | 배열 인덱스 |
| --- | --- | --- |
| 재정렬 | 상태를 항목에 유지 | 상태가 위치에 붙을 수 있음 |

같은 부모 아래에서 키와 타입이 같으면 기존 컴포넌트와 DOM을 재사용한다. 키가 바뀌면 새로 마운트해 내부 상태도 초기화한다.

인덱스 키는 추가·삭제·정렬이 없는 고정 목록에서만 안전하다. 매번 생성한 난수 키는 전부 다시 마운트해 성능과 입력 상태를 해친다.

## 27. [프론트엔드] 응답 특성에 따라 캐시 방식을 어떻게 고르는가?

<!-- id: 138c022d-4017-48c1-addb-24a5908596a7 -->

변경 빈도와 오프라인 요구로 고른다. 정적 자산은 Cache First가 맞다. 최신성이 중요한 API는 Network First나 Network Only를 쓴다.

| 기준 | Cache First | Network First |
| --- | --- | --- |
| 응답 속도 | 빠름 | 네트워크 의존 |
| 최신성 | 낮을 수 있음 | 높음 |
| 오프라인 | 강함 | 폴백 필요 |

Stale While Revalidate는 캐시를 즉시 보여주고 뒤에서 갱신한다. 빠른 표시와 적당한 최신성이 모두 필요한 이미지나 목록에 알맞다.

캐시 이름에 버전을 두고 activate 단계에서 이전 항목을 정리한다. 실패 응답을 저장하지 않는다. 요청 종류별 만료와 최대 개수도 제한한다.
