## #163 문자열 검색 효율을 높이는 최적의 자료구조는 무엇인가?
`자료구조 · 알고리즘`

```
트라이(Trie)다. 문자열을 트리 구조로 저장해 접두사 공유를 통해 탐색 시간을 문자열 길이에 비례하게 줄인다.

| 자료구조 | 저장 방식 |
| --- | --- |
| 트라이 | 문자열의 각 문자를 노드로 저장 |
| 해시 맵 | 전체 문자열을 키로 저장 |

트라이는 문자열의 공통 접두사를 노드로 공유한다. 따라서 동일한 시작 문자를 가진 단어들은 같은 경로를 따라가므로 중복 탐색을 피한다.

KMP나 라빈-카프 알고리즘은 특정 텍스트 내에서 패턴을 찾을 때 쓴다. 트라이는 사전(Dictionary)처럼 여러 단어를 빠르게 검색하거나 자동완성에 적합하다.

시간 복잡도는 O(L)이다. 여기서 L은 검색하려는 문자열의 길이이며, 데이터셋의 크기와 상관없이 일정하게 유지된다.
```

## #164 그리디 알고리즘과 동적 계획법은 무엇으로 구분하는가?
`자료구조 · 알고리즘`

```
최적 부분 구조를 가졌으나, 현재의 최적해를 선택하는지 아니면 모든 경우의 수를 고려하여 결정하는지로 구분한다.

| 기준 | 그리디 알고리즘 | 동적 계획법 |
| --- | --- | --- |
| 선택 방식 | 현재의 최적해를 선택 | 모든 부분 문제의 해를 조합 |
| 효율성 | 연산량이 적고 빠름 | 연산량이 많고 정확함 |
| 최적성 보장 | 특정 조건에서만 가능 | 항상 최적해를 보장함 |

그리디 알고리즘은 매 순간 가장 이득이 되는 선택을 하며, 뒤를 돌아보지 않는다. 이 방식은 선택지가로 인해 전체적인 최적해를 구할 수 없는 경우에 대해 취약하다.

반면, 동적 계획법은 작은 문제의 답을 메모이제이션을 통해 저장하여 중복으로 계산하지 않는다. 모든 가능성을 탐색하며 과거의 것을 활용해 최종적인 최적해를 구성한다.

두 방식의 차이점을 이해하는 것은 문제의 최적 부분 구조와 중복되는 부분 문제로 구성되어 있는지 판단하는 정확한 정확한 기준을 세우는 데 중요하다.
```

## #168 HTTP 메서드 선택의 기준은 무엇인가?
`네트워크`

```
리소스의 상태를 변경하는 성격과 멱등성 여부로 결정한다. 조회를 위해 GET을, 생성은 POST, 수정은 PUT이나 PATCH를, 삭제는 DELETE를 사용한다.

| 기준 | GET | POST | PUT | PATCH | DELETE |
| --- | --- | --- | --- | --- | --- |
| 목적 | 조회 | 생성 | 전체 수정 | 부분 수정 | 삭제 |
| 멱등성 | O | X | O | X | O |
| 안전성 | O | X | X | X | X |

안전한 메서드는 리소스를 변경하지 않는다. GET은 데이터를 읽기만 하므로 안전하다. 반면 POST는 서버 상태를 바꾼다.

멱등성이란 여러 번 호출해도 결과가 같은지 여부다. PUT은 동일한 데이터로 요청을 보내면 몇 번을 보내도 결과가 항상 같다.

PATCH는 리소스의 일부만 바꾸기 때문에 호출 순서나 현재 상태에 따라 결과가 달라질 수 있다. 그래서 멱등성이 보장되지 않는 경우가 많다.
```

## #170 데이터베이스 정규화를 수행하는 이유는 무엇인가?
`데이터베이스`

```
데이터 중복을 최소화하여 데이터 무결성을 유지하고 이상 현상을 방지하기 때문이다.

| 기준 | 정규화 전 | 정규화 후 |
| --- | --- | --- |
| 데이터 중복 | 많음 | 적음 |
| 삽입/삭제/수정 이상 | 발생 가능 | 방지 가능 |
| 조회 성능 | 단순 조인 없음 | 조인 필요 |

정규화를 하지 않으면 동일한 정보가 여러 곳에 저장된다. 이로 인해 데이터를 수정할 때 일부만 수정되어 데이터 간 불일치가 발생하는 수정 이상이 생긴다.

또한, 관련된 정보가 함께 저장되어 필요 없는 정보까지 함께 삽입하거나 삭제해야 하는 삽입 및 삭제 이상이 발생한다.

과도한 정규화는 조회 시 많은 조인(Join) 연산을 유도하여 성능 저하를 일으킨다. 따라서 실무에서는 성능 향상을 위해 일부러 정규화를 푸는 역정규화 과정을 거치기도 한다.
```

## #173 고정 소수점과 부동 소수점은 무엇으로 구분하는가?
`인프라 · 보안`

```
소수점의 위치를 고정하느냐, 혹은 데이터의 값에 따라 유동적으로 옮기느냐의 차이다.

| 기준 | 고정 소수점 | 부동 소수점 |
| --- | --- | --- |
| 소수점 위치 | 정해진 위치 | 값에 따라 변함 |
| 표현 범위 | 좁음 | 매우 넓음 |
| 연산 속도 | 빠름 | 느림 |

고정 소수점은 정수부와 소수부의 비트 수를 미리 정해둔다. 계산이 정수 연산과 비슷해 속도가 매우 빠르지만, 표현할 수 있는 숫자의 범위가 매우 제한적이다.

부동 소수점은 가수부와 지수부를 나누어 소수점의 위치를 조정한다. 아주 작은 수나 아주 큰 수를 효율적으로 표현할 수 있어 범용적인 계산에 쓰인다.

다만 부동 소수점은 2진수로 변환하는 과정에서 무한 소수가 발생한다. 이로 인해 정밀한 계산이 필요한 금융권 서비스에서는 오차가로 인해 고정 소수점이나 별도의 정밀도 높은 타입을 사용한다.
```

## #174 배열보다 연결 리스트를 사용하는 기준은 무엇인가?
`인프라 · 보안`

```
데이터의 추가와 삭제가 빈번하게 일어날 때다. 인덱스로 접근하지 않고 순차적으로 탐색해도 무방한 환경에서 유리하다.

| 기준 | 배열 | 연결 리스트 |
| --- | --- | --- |
| 요소 접근 | $O(1)$. 인덱스로 즉시 찾음 | $O(n)$. 처음부터 훑어야 함 |
| 중간 삽입/삭제 | $O(n)$. 데이터를 밀고 당김 | $O(1)$. 포인터만 변경 |

배열은 연속된 메모리 공간을 사용한다. 삽입이나 삭제 시 나머지 요소를 모두 이동시켜야 하므로 비용이 크다.

반면 연결 리스트는 노드가 흩어져 있다. 앞뒤 노드의 주소값만 바꿔주면 되므로 데이터 이동 없이 빠르게 처리한다.

최근 CPU 캐시 지역성 때문에 단순 탐색 성능은 배열이 압도적이다. 따라서 무작정 리스트를 쓰기보다 데이터 변경 빈도를 먼저 따져야 한다.
```

## #175 공개키와 비밀키는 무엇으로 구분하는가?
`인프라 · 보안`

```
키의 공개 여부와 암호화/복호화의 주체가 누구인지로 구분한다. 공개키는 누구나 가질 수 있고, 비밀키는 소유자만 엄격히 관리한다.

| 기준 | 공개키 | 비밀키 |
| --- | --- | --- |
| 공개 여부 | 모두에게 공개 | 소유자만 보유 |
| 사용 용도 | 암호화, 검증 | 복호화, 서명 |

공개키 암호화 방식은 서로 다른 키로 암호화와 복호화를 수행한다. A의 공개키로 암호화한 데이터는 오직 A의 비밀키로만 풀 수 있다.

비밀키 방식은 하나의 키를 공유하여 양방향으로 사용한다. 속도가 빠르지만, 키를 안전하게 전달하는 과정에서 탈취될 위험이 크다.

실무에서는 두 방식을 섞어 쓴다. 대칭키를 생성해 공개키로 암호화해 전달하고, 실제 데이터 통신은 전달받은 대칭키로 빠르게 처리한다.
```

## #179 HTTP 상태 코드는 어떤 기준으로 분류하는가?
`네트워크`

```
첫 번째 자리 숫자가 응답의 성격으로 분류된다. 1xx는 정보, 2xx는 성공, 3xx는 리다이렉션, 4xx는 클라이언트 오류, 5xx는 서버 오류다.

| 상태 코드 | 분류 |
| --- | --- |
| 1xx | 정보 제공 |
| 2xx | 성공적인 처리 |
| 3xx | 리다이렉션 |
| 4xx | 클라이언트 요청 오류 |
| 5xx | 서버 내부 오류 |

위 표는 숫자의 첫 자리만으로도 로그 분석이나 모니터링 도구에서 빠르게 판단하는 기준이 된다.

4xx와 5xx의 차이는 책임 소재가 어디에 있느냐다. 4xx는 요청자가 잘못 보냈으니 수정해서 다시 보내야 하고, 5xx는 서버가 처리로직으로 인해 장애가 발생했음을 의미한다.
```

## #180 로그 레벨을 구분하여 설정하는 이유는 무엇인가?
`프론트엔드`

```
운영 환경의 불필요한 로그를 줄여 성능 저하를 막고 문제 분석 효율을 높이기 때문이다.

| 기준 | DEBUG | INFO | ERROR |
| --- | --- | --- | --- |
| 대상 | 개발자 | 운영자 | 시스템 관리자 |
| 목적 | 변수 추적 | 흐름 파악 | 장애 복구 |
| 출력 빈도 | 매우 높음 | 보통 | 낮음 |

로그 레벨은 보통 계층 구조를 가진다. 예를 들어 INFO 레벨로 설정하면 DEBUG 로그는 무시되고 INFO 이상의 레벨만 출력된다.

잘못된 레벨 설정은 치명적이다. 운영 서버에 DEBUG 레벨을 켜두면 디스크 I/O가 폭증하여 애플리케이션 성능이 급격히 떨어질 수 있다.

반면, ERROR 레벨만 남기면 장애 발생 시 원인을 찾기 위한 맥락 정보가 부족해 복구 시간이 길어진다.
```

## #181 CSRF와 XSS의 결정적인 차이는 무엇인가?
`프론트엔드`

```
사용자 브라우저의 권한을 도용하는 방식의 차이다. XSS는 악성 스크립트를 웹 페이지에 삽입해 실행시키고, CSRF는 사용자의 인증된 세션을 이용해 원치 않는 요청을 보내는 것이다.

| 기준 | XSS | CSRF |
| --- | --- | --- |
| 공격 대상 | 사용자 브라우저 | 서버의 상태 변경 |
| 실행 주체 | 삽입된 스크립트 | 위조된 요청 |
| 핵심 원인 | 검증되지 않은 입력값 | 자동 전송되는 쿠키 |

XSS는 스크립트가 실행되면 쿠키, 세션 ID로 같은 톤으로 함께만 사용하여 세션 하이재킹을 수행한다. 반면 CSRF는 세션 ID를 가로채지 않고, 사용자가 로그인한 상태라는 점을 즉시 이용한다.

CSRF는 주로 데이터 변경, 비밀번호 변경과 같은 상태 변경 요청에 치명적이다. XSS는 데이터 탈취취 및 페이지 변조로 범위가 더 넓다.
```

## #182 프론트엔드 성능 최적화 시 번들 크기를 무엇으로 판단하는가?
`프론트엔드`

```
최초 로딩 시 사용자가 체감하는 LCP(Largest Contentful Paint)와 TBT(Total Blocking Time)를 기준으로 판단한다. 단순히 파일 용량만 줄이는 것이 아니라 런타임 실행 시간과 파싱 시간을 함께 고려해야 한다.

| 성능 요소 | 영향 |
| --- | --- |
| 런타임 성능 | JS 실행 및 DOM 조작 속도 |
| 네트워크 성능 | 번들 다운로드 및 압축 해제 속도 |

위 도식은 번들이 실제 성능에 영향을 주는 두 가지 경로를 보여준다. 파일이 작아도 복잡한 로직이 많으면 TBT가 늘어난다.

코드 분할(Code Splitting)을 통해 초기 진입점에 필요한 최소한의 JS만 로드하게 만든다. 이를 통해 메인 스레드 점유 시간을 줄이고 빠른 상호작용을 유도한다.

트리 쉐이킹(Tree Shaking)으로 사용하지 않는 코드를 제거해 전송량을 줄인다. 라이브러리 선택 시 ESM(ES Modules) 지원 여부를 확인하는 것이 핵심이다.
```

## #183 Git 협업 시 충돌 해결을 위해 무엇을 우선하는가?
`네트워크`

```
팀원 간 합의된 브랜치 전략과 코드 컨벤션을 우선한다. 기술적인 머지 방식보다 소통을 통한 충돌 방지가 먼저다.

| 기준 | Git Flow | GitHub Flow |
| --- | --- | --- |
| 복잡도 | 높음. 브랜치가 많다 | 낮음. 메인 중심이다 |
| 배포 주기 | 정기 배포에 적합 | 지속적 배포에 적합 |

전략이 없으면 각자 다른 시점에 같은 파일을 수정해 충돌이 잦아진다. 명확한 브랜치 명명 규칙과 작업 단위 분리가 해결책이다.

코드 컨벤션을 맞추면 단순 포맷팅 차이로 발생하는 불필요한 충돌을 줄인다. Prettier 같은 도구로 자동화하는 것이 일반적이다.

최종 충돌 해결은 항상 변경 사항의 맥락을 파악하는 것에서 시작한다. 단순 툴 사용보다 작성자와의 소통이 가장 빠르고 정확하다.
```

## #185 클로저를 사용해 상태를 은닉하는 이유는 무엇인가?
`언어 · 런타임`

```
외부 함수의 지역 변수를 외부에서 직접 수정하지 못하게 막아 데이터 무결성을 지키기 때문이다.

| 기준 | 전역 변수 | 클로저 은닉 |

```

```
인접 리스트는 연결된 정점만 저장한다. 정점 수 대비 간선 수가 적은 희소 그래프에서 메모리를 획기적으로 아낀다.

실무에서는 대부분의 그래프가 희소 그래프이므로 인접 리스트를 주로 쓴다. 다만, 모든 정점이 서로 연결된 완전 그래프라면 행렬이 유리하다.
```

## #191 공유 자료구조를 Thread-Safe하게 만드는 방법은 무엇인가?
`자료구조 · 알고리즘`

```
상호 배제(Mutual Exclusion)를 통해 한 번에 하나의 스레드만 데이터에 접근하도록 제어하는 것이다.

| 기준 | 동기화 블록 | CAS (Compare-And-Swap) | 
| --- | --- | --- | 
| 방식 | 락으로 접근 제어 | 값 비교 후 교체 | 
| 성능 | 컨텍스트 스위칭 비용 발생 | 논블로킹으로 성능 높음 | 
| 특징 | 구현이 쉽고 안전함 | 스핀락으로 CPU 점유율 상승 | 

동기화 블록이나 `synchronized` 키워드를 사용하면 임계 영역을 최소화하여 동시성 제어를 가능하게 한다. 하지만 락을 획득하지 못한 스레드는 대기 상태로 전환되어 컨텍스트 스위칭 비용이 발생한다.

CAS 연산은 락을 사용하지 않은 논블로킹 알고리즘으로 구현된다. 현재 값과 예상 값이 일치할 때만 새로운 값으로 교체하는 원자적(Atomic) 원리를 이용한다.

최근에는 읽기-쓰기 락(Read-Write Lock)을 것처럼 읽기 작업이 많을 때 읽기 권한을 대해로 분리하여 효율을 높이는 방식을 주로 사용한다.
```

```

| 스케줄러 | 역할 |
| --- | --- |
| 장기 | 작업 큐에서 메모리로 올릴 프로세스 결정 |

단기 스케줄러는 실제 CPU 점유를 결정하므로 응답 시간과 처리량에 가장 큰 영향을 미친다. 문맥 교환 비용을 최소화하는 것이 핵심이다.
```

`운영체제`

```
동기와 비동기는 호출한 함수의 완료 여부를 누가 확인하느냐의 차이이고, 블로킹과 논블로킹은 호출된 함수가 제어권을 언제 돌려주느냐의 차이다.

비동기 논블로킹 모델은 호출 즉시 제어권을 돌려받고, 콜백(Callback)이나 이벤트 루프를 통해 작업 완료를 알림받아 효율을 극대화한다.
```

## #197 웹소켓과 일반 소켓 통신은 무엇으로 구분하는가?
`네트워크`

```
웹소켓은 HTTP 기반의 전이중 통신 프로토콜이며, 일반 소켓은 전송 계층의 TCP/UDP 연결 자체를 의미한다.

따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 통신을 위한 하드웨어/소프트웨어적 통로 그 자체라고 볼 수 있다.
```

## #200 트랜잭션 격리 수준을 결정하는 기준은 무엇인가?
`데이터베이스`

```

| 기준 | 격리 수준 낮음 | 격리 수준 높음 |
```

## #203 JVM의 핵심 역할은 무엇인가?
`프레임워크`

```
| 구분 | 내용 |
| --- | --- |
| JVM 내부 | Java Runtime Environment (JRE) |
| 실행 대상 | Java Bytecode (.class) |

가장 큰 특징은 가비지 컬렉션을 통해 메모리를 자동으로 관리한다는 점이다. 개발자가 직접 메모리를 해제하는 수고를 록고, 메모리 누수 가능성을 획기적으로 낮춘다.

JIT 컴파일러는 반복적으로 실행되는 코드를 기계어로 미리 변환해 캐싱한다. 이를 통해 인터프리터 방식의 실행 속도를 획기적으로 개선한다.
```

## #204 체크 예외와 언체크 예외의 선택 기준은 무엇인가?
`프레임워크`

```

| 기준 | 체크 예외 | 언체크 예외 |
| --- | --- | --- |
| 복구 가능성 | 높음 | 낮음 |

반면 언체크 예외는 강제성이 없다. 널 포인터 참조나 배열 인덱스 초과 같은 논리적 오류는 코드를 수정해야 풀리는 문제지, try-catch로 잡는다고 해결되지 않기 때문이다.

최근에는 체크 예외의 과도한 사용이 코드 가독성을 해치고 의존성을 높인다는 비판이 많다. 그래서 많은 프레임워크가 언체크 예외로 래핑하여 던지는 추세다.
```

```
| --- | --- |
```


## #207 JOIN 연산의 성능을 결정하는 핵심 요소는 무엇인가?
`데이터베이스`

```
인덱스 활용 여부와 조인 방식의 선택이다. 인덱스가 없으면 전체 테이블을 훑어야 하므로 비용이 급격히 증가한다.

| 기준 | Nested Loop | Hash Join |
| --- | --- | --- |
| 적합한 데이터 | 소량/인덱스 있음 | 대량/인덱스 없음 |

정렬 상태에 따라 Merge Join이 선택되기도 한다. 옵티마이저는 통계 정보를 바탕으로 데이터 양과 인덱스 상태를 보고 가장 싼 비용의 방식을 결정한다.
```

## #215 DBSCAN은 K-means보다 어떤 상황에서 더 유리한가?
`데이터베이스`

```
데이터의 분포가 원형이 아니거나 노이즈가 섞인 데이터셋에서 유리하다. K-means는 구형의 클러스터만 찾을 수 있지만, DBSCAN은 밀도 기반으로 임의의 모양을 찾아내기 때문이다.

| 기준 | K-means | DBSCAN |
| --- | --- | --- |
| 클러스터 모양 | 구형 (Centroid 기반) | 임의의 모양 (Density 기반) |
| 노이즈 처리 | 모든 점을 할당 | 밀도 미달 점을 노이즈로 분류 |
| 파라미터 | K (클러스터 개수) | eps, minPts (밀도 기준) |

DBSCAN은 설정한 거리(eps) 내에 최소 점 개수(minPts)가 있으면 이를 핵심적으로 연결한다. 이 과정을 반복해 밀도가 높은 영역을 하나의 덩어리로 묶는다.

반면 K-means는 모든 데이터를 강제로 클러스터에 포함시킨다. 밀도가 낮은 외곽의 점들이 중심점과 묶여 클러스터의 모양을 왜곡시킨다.

따라서 데이터의 실제 모양을 모르거나 이상치(Outlier)를 제거해야 하는 전처리 단계에서 DBSCAN이 효과적이다.
```

## #217 해시 충돌이 발생했을 때의 해결책은 무엇인가?

## #219 문자열 검색 최적화 시 어떤 기준으로 알고리즘을 고르는가?
`자료구조 · 알고리즘`

```
검색 대상의 크기, 패턴의 반복성, 그리고 검색 빈도에 따라 고른다. 정적인 사전에서 빠른 조회가 필요하면 트라이를, 긴 텍스트 내 단일 패턴 검색은 KMP나 라빈-카프를 쓴다.

| 기준 | 트라이 | KMP / 라빈-카프 |
| --- | --- | --- |
| 주 용도 | 사전식 탐색 | 패턴 매칭 |
| 시간 복잡도 | 문자열 길이 $O(m)$ | 텍스트 길이 $O(n)$ |
| 메모리 사용 | 매우 높음 | 낮음 |

트라이는 문자열을 트리 형태로 저장해 접두사 공유를 극대화한다. 한 번 구축하면 검색 속도가 매우 빠르지만, 각 노드에 포인터 배열을 두어 메모리 낭비가 심하다.

KMP는 패턴 내부의 반복 구조를 미리 계산해 불필요한 비교를 건너뛴다. 텍스트를 되돌아가지 않고 한 번만 훑으므로 효율적이다.

라빈-카프는 해시 값을 이용해 문자열을 비교한다. 해시가 일치할 때만 실제 문자열을 대조하므로, 여러 패턴을 동시에 찾거나 대용량 데이터를 처리할 때 유리하다.
```

## #222 메모리 연속할당 방식 중 무엇을 선택하는가?
`운영체제`

```
프로세스의 크기와 가용 메모리 조각의 분포를 고려해 결정한다. 충돌이 적고 빠른 할당이 필요하면 First-fit, 메모리 낭비를 최소화하려면 Best-fit를 쓴다.

| 기준 | First-fit | Best-fit | Worst-fit |
| --- | --- | --- |
| 선택 방식 | 가장 먼저 발견한 조각 | 크기가 가장 딱 맞는 조각 | 가장 큰 조각 |
| 장점 | 할당 속도가 매우 빠름 | 메모리 낭비가 적음 | 남은 조각이 큼 |
| 단점 | 앞부분에 작은 조각 누적 | 탐색 시간이 길고 파편화 심함 | 메모리 낭비가 가장 큼 |

First-fit는 리스트의 처음부터 탐색하므로 오버헤드가 적다. 실무적으로 가장 효율적인 선택지로 꼽힌다.

Best-fit는 모든 조각을 확인해야 하므로 느리다. 아주 작은 크기의 조각들이 많이 생겨 오히려 사용할 수 없는 외부 단편화가 심해진다.

Worst-fit는 가장 큰 조각을 할당해 남은 공간을 유의미하게 활용하려 한다. 하지만 큰 프로세스가 들어올 자리를 미리 없애는 치명적인 단점이 있다.
```

## #228 조인으로 인해 성능 저하가 발생하는 원인은 무엇인가?
`데이터베이스`

```
조인이 많아지면 데이터셋의 크기가 기하급수적으로 늘어나고 메모리 내 정렬과 병합 작업이 증가하기 때문이다.

| 기준 | Nested Loop Join | Hash Join | Merge Join |
| --- | --- | --- | --- |
| 처리 방식 | 이중 루프 순회 | 해시 테이블 생성 | 정렬 후 병합 |
| 적합한 데이터 | 소량 데이터 | 대량 데이터 | 정렬된 데이터 |
| 시간 복잡도 | O(N*M) | O(N+M) | O(N log N + M log M) |

Nested Loop Join은 외부 테이블의 모든 행을 하나씩 읽어 내부 테이블에서 조건에 맞는 행을을 찾는다. 인덱스가 없으면 전체 테이블 스캔이 발생해 성능이 급격히 떨어진다.

Hash Join은 작은 테이블을 메모리에 해시 테이블로 올린 뒤 큰 테이블을 스캔하며 매칭되는 값을 찾는다. 메모리 부족 시 디스크 I/O가 발생해 느려진다.

Merge Join은 양쪽 테이블을 조인 키로 정렬한 뒤 순차적으로 읽으며 병합한다. 이미 정렬되어 있거나 범위 조인을 수행할 때 효율적이다.
```

## #231 스택과 큐는 어떤 상황에서 구분해 쓰는가?
`자료구조 · 알고리즘`

```
데이터의 처리 순서가 최신순인지 선입선출순인지에 따라 결정한다. 가장 나중에 들어온 데이터를 먼저 처리해야 하면 스택을, 먼저 들어온 순서대로 처리해야 하면 큐를 쓴다.

| 기준 | 스택 (Stack) | 큐 (Queue) |
| --- | --- | --- |
| 처리 순서 | LIFO (후입선출) | FIFO (선입선출) |
| 주요 연산 | push / pop | enqueue / dequeue |
| 활용 사례 | 되돌리기, 재귀 호출 | 대기열, 프로세스 스케줄링 |

스택은 데이터의 '맥락'을 유지하는 데 유리하다. 함수 호출 스택처럼 현재 작업을 멈추고 새로운 작업을 수행한 뒤, 다시 이전 상태로 돌아와야 할 때 적합하다.

큐는 데이터의 '흐름'을 제어하는 데 유리하다. 요청이 몰릴 때 이를 순차적으로 처리하여 시스템의 부하를 조절하는 버퍼 역할로 주로 쓰인다.

두 구조 모두 삽입과 삭제가 $O(1)$의 시간 복잡도를 가진다. 하지만 큐를 배열로 구현할 때 삭제 연산 시 데이터 시프팅이 발생하므로, 원형 큐나 연결 리스트로 구현하는 것이 효율적이다.
```

## #233 HTTPS는 HTTP와 무엇이 다른가?
`네트워크`

```
HTTP에 SSL/TLS 프로토콜을 추가해 데이터를 암호화한 것이다. 이를 통해 도청, 변조, 위조를 막는다.
```

## #248 멀티스레드 환경에서 스레드 세이프한 코드를 작성하는 방법은 무엇인가?
`운영체제`

```
임계 영역으로의 동시 접근을 막아 데이터 일관성을 보장하는 것이다. 한 번에 하나의 스레드만 자원에 접근하도록 제어하는 것이 핵심이다.

:::stack
제어 방법 | 설명
--|--
동기화 | synchronized, Lock API를 이용한 상호 배제
불변성 | final, Read-only 객체로 상태 변경 차단
원자성 | Atomic 클래스로 단일 연산 수행
:::

위의 방법들로 공유 자원에 대한 경쟁 상태를 방지한다. 특히 데이터 읽기/쓰기 과정에서 문맥 전환이 발생하면 데이터가 오기집단될 수 있다.

동기화 락을 과하게 사용하면 성능이 떨어진다. 락으로 인해 스레드가 대기 상태로 대기하며 컨텍스트 스위칭 비용이 증가하기 때문이다.

상황에 따라 락-프리 알고리즘을 Senatorial Atomic 연산을 이용해 구현한다. 이를 통해 락 없이도 데이터 일관성을 성능상 이점만 챙기며 보장할 수 있다.
```

## #250 동기화 문제를 하드웨어적으로 어떻게 해결하는가?
`운영체제`

```
원자적 명령어로 처리한다. CPU가 명령어를 실행하는 동안 다른 프로세스가 개입하지 못하게 막아 메모리 접근을 보장하는 방식이다.

| 구분 | 방식 |
| --- | --- |
| 하드웨어 수준 | **Test-and-Set**, **Compare-and-Swap (CAS)** |
| 명령어 수준 | 인터럽트 비활성화. 단일 코어에서만 유효하다 |

Test-and-Set은 메모리 값의 현재 상태를 읽고 새로운 값을 쓰는 작업을 한 번에 처리한다. 중간에 컨텍스트 스위칭이 발생하지 않아 데이터 정합성을 지킨다.

CAS는 기대하는 값과 현재 메모리 값의 일치 여부를를 확인하고 다를 경우에만 값을 바꾼다. 락-프리(Lock-free) 알고리즘의 핵심 기반이 된다.

인터럽트 비활성화는 간단하지만 멀티코어 환경에서는 모든 CPU의 인터럽트를 동시에 끄는 비용이 너무 커서 실무적으로 쓰이지 않는다.
```

## #251 RDB와 NoSQL 중 무엇을 기준으로 선택하는가?
`데이터베이스`

```
데이터의 정형성도와 쓰기/읽기 부하량에 따라 결정한다. 엄격한 스키마가 필요하면 RDB를, 유연한 구조와 대용량 처리가 우선이면 NoSQL을 쓴다.

| 기준 | RDB | NoSQL |
| --- | --- | --- |
| 스키마 | 고정적 | 유연함 |
| 확장성 | 수직 확장(Scale-up) | 수평 확장(Scale-out) |
| 트랜잭션 | ACID 준수 | BASE (최종 일관성) |

정형 데이터는 RDB가 유리하다. 조인(Join)을 통해 중복을 제거하고 무결성을 보장한다. 반면 NoSQL은 중복을 허용하며 데이터 접근 속도를 높인다.

트랜잭션 보장 수준이 중요하다면 RDB를 쓴다. 금융 거래처럼 정확한 데이터 일관성이 필수적인 곳에 적합하다.

분산 환경에서 빠르게 확장해야 한다면 NoSQL이 낫다. 샤딩(Sharding)이나 복제(Replication)를 통해 수평적 확장이 용이해 데이터 양이 늘어나도 대응이 가능하다.
```

```
| 기준 | 복제(Replication) | 클러스터링(Clustering) | 
| --- | --- | --- | 
| 핵심 목적 | 데이터 백업 및 읽기 분산 | 고가용성 및 시스템 확장 |

실무에서는 읽기 요청이 압도적으로 많다면 복제를 선택하고, 쓰기 작업이 빈번하고 중단 없는 서비스가 필수적이라면 클러스터링을 구성한다.
```

```
| 기준 | 낙관적 락 | 비관적 락 |
| --- | --- | --- |

비관적 락은 데이터를 읽을 때부터 잠금을 걸어 다른 트랜잭션이 접근하지 못하게 막는다. 데이터 무결성을 강하게 보장하지만, 대기 시간이 늘어나 성능 저하가 발생할 수 있다.

실무에서는 읽기 비중이 높고 충돌이 적은 서비스에 낙관적 락을 쓴다. 반면, 결제나 재고 관리처럼 충돌이 잦고 데이터 정확성이 절대적인 곳에 비관적 락을 쓴다.
```

## #260 SQL과 NoSQL은 어떤 기준으로 선택하는가?
`데이터베이스`

```

| 기준 | SQL | NoSQL |

위 표는 두 방식의 데이터 관리 전략의 차이점을 보여준다.

NoSQL은 정해진 틀 없이 데이터를 저장한다. 읽기와 쓰기 속도가 매우 빠르며, 대량의 로그 데이터나 실시간 채팅 데이터처럼 구조가 자주 바뀌는 비정형 데이터 처리에 유리하다.
```

```
순수 함수는 외부 상태를 바꾸지 않고 오직 입력값으로만 결과를 만든다. 따라서 사이드 이펙트가 없어 테스트와 디버깅이 매우 쉽다.

선언적 스타일로 코드를 작성하면 비즈니스 로직이 명확해진다. 복잡한 제어문을 줄여 코드의 가독성과 유지보수성이 향상된다.
```

```

| --- | --- | --- | --- | --- | --- |
| 상태 변경 | 없음 | 있음 | 있음 | 있음 | 있음 |

PATCH는 리소스의 일부만 수정한다. 구현 방식에 따라 멱등할 수도, 비멱등할 수도 있어 주의가 필요하다.
```

## #268 GC 알고리즘 선택 기준은 무엇인가?
`언어 · 런타임`

```
애플리케이션의 서비스 특성과 지연 시간 허용 범위에 따라 결정한다. 처리량 중심인지, 응답 속도 중심인지가 핵심이다.

| 기준 | Parallel GC | G1 GC | ZGC |
| --- | --- | --- |
| 목표 | 처리량 최대화 | 균형 잡힌 지연 | 초저지연 |
| 특징 | STW 길다 | 리전 분할 관리 | 색상 포인터 사용 |

Parallel GC는 전체 처리량을 높이는 데 유리하다. 하지만 모든 GC 발생 시 전체 시스템이 멈추는 Stop-The-World 시간이 길어 서비스 응답이 끊긴다.

G1 GC는 힙을 리전으로 나누어 효율적으로 수집한다. 설정한 목표 지연 시간을 맞추기 위해 수집 효율이 높은 영역부터 먼저 처리한다.

ZGC는 힙 크기에 상관없이 지연 시간을 10ms 이하로 유지한다. 컬러 포인터와 로드 배리어를 통해 애플리케이션과 동시에 GC를 수행한다.
```

## #277 자바의 원시 타입과 래퍼 클래스는 메모리 구조상 어떤 차이가 있는가?
`언어 · 런타임`

```
원시 타입은 변수 공간에 실제 값을 직접 저장하고, 래퍼 클래스는 힙 영역에 있는 객체의 참조 주소를 저장한다. 메모리 점유량과 접근 방식에서 큰 차이가 난다.

| 기준 | 원시 타입 (예: int) | 래퍼 클래스 (예: Integer) |
| --- | --- | --- |
| 저장 위치 | 스택 프레임 또는 객체 필드 | 힙 영역 |
| 저장 내용 | 실제 데이터 값 | 객체 헤더 + 데이터 값 |
| 메모리 크기 | 4바이트 고정 | 최소 16바이트 이상 |

원시 타입 `int`는 4바이트 메모리만 차지한다. 반면 래퍼 클래스 `Integer`는 8~12바이트의 객체 헤더와 내부 `int` 필드를 합쳐 최소 16바이트 이상을 소비한다. 64비트 JVM 환경에서는 메모리 사용량이 훨씬 커진다.

래퍼 클래스는 힙 영역에 할당되므로 가비지 컬렉션의 관리 대상이다. 변수를 읽을 때도 참조를 거치는 간접 접근이 일어나 CPU 캐시 효율이 떨어진다. 반복문에서 오토박싱이 자주 일어나면 짧은 시간에 수많은 객체가 만들어져 GC 부담을 늘린다.
```

## #19836 TCP 연결에서 RST 패킷은 어떤 상황에 전송되는가?
`네트워크`

```
비정상적인 연결 요청을 받거나 연결을 즉시 끊어야 할 때다. 정상적인 FIN 교환 과정과 달리 대기 시간 없이 연결을 즉시 파기한다.

| 상황 | 발생 조건 | 상대방의 동작 |
| --- | --- | --- |
| 포트 미개방 | 닫힌 포트로 SYN 패킷 수신 | 연결 거절을 확인하고 중단한다 |
| 세션 불일치 | 이미 닫힌 연결로 데이터 수신 | 세션 오류를 인지하고 소켓을 닫는다 |
| 강제 종료 | `SO_LINGER`를 0으로 설정 후 닫기 | 수신 버퍼를 비우고 즉시 종료한다 |

대표적으로 포트가 열려 있지 않은 서버에 SYN 요청이 들어오면 서버는 RST를 보낸다. 해당 포트를 사용할 수 없음을 상대에게 즉시 알리기 위해서다.

이미 끊어진 연결로 데이터나 ACK 패킷이 들어올 때도 RST를 전송한다. 양쪽의 세션 상태가 맞지 않아 연결을 더 유지할 수 없기 때문이다.

애플리케이션이 강제 종료되거나 소켓을 즉시 닫도록 설정했을 때도 나간다. 이 때 상대방은 버퍼의 미처리 데이터를 버리고 연결을 해제한다.
```

## #25425 고차원 데이터에서 거리 계산 시 발생하는 문제는 무엇인가?
`데이터베이스`

```
고차원 데이터에서는 모든 점 사이의 거리가 비슷해져 데이터 간 유사도를 구분하기 어려워지는 문제다. 차원이 증가할수록 데이터 공간이 급격히 넓어진다.

| 상황 | 데이터 밀도 | 최단·최장 거리 차이 | 거리 기반 분석 |
| --- | --- | --- | --- |
| 저차원 | 높음 | 크다 | 명확한 구분 가능 |
| 고차원 | 극도로 낮음 | 거의 없다 | 모든 점의 거리가 비슷함 |

위 표는 차원이 증가함에 따라 공간 특성과 거리 구별력이 어떻게 변화하는지 보여준다.

차원이 늘어나면 공간 부피가 기하급수적으로 늘어난다. 고차원 공간에서는 데이터가 존재하는 영역보다 비어 있는 공간이 훨씬 많아진다.

유클리드 거리를 쓰면 최단 거리와 최장 거리의 비율이 1에 수렴한다. 이 때문에 이웃을 정의하거나 밀도를 측정하는 기존 방식이 무력화된다.

이 문제는 DBSCAN이나 K-means 같은 거리 기반 알고리즘의 성능을 크게 떨어뜨린다. PCA로 차원을 줄이거나 코사인 유사도를 쓰는 이유다.
```
