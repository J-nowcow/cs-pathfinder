## 가장 심각한 것 셋

### 1. `동적 계획법은 항상 최적해를 보장함` — 틀렸다

표에 그렇게 적혀 있다. 상태와 점화식이 문제를 정확히 모델링한 **최적화 문제에서만** 보장한다. 동적 계획법은 개수 세기나 가능성 판정에도 쓴다.

같은 편에 더 있다.

- `모든 경우의 수를 고려하여 결정` — 아니다. 모든 경우를 열거하는 것은 완전 탐색이다. DP는 **필요한 부분 문제만** 계산하고 재사용한다
- `메모이제이션을 통해 저장` — DP에는 하향식 메모이제이션과 **상향식 테이블 채우기**가 둘 다 있다
- `연산량이 많고 정확함` — 연산량은 상태와 전이 수에 달렸다. 정확성은 알고리즘 분류로 보장되지 않는다

면접에서 이대로 말하면 감점된다.

### 2. `오브젝트 파일은 다른 모듈과의 연결 정보가 없다` — 틀렸다

오브젝트 파일에는 **심볼 테이블과 재배치 정보가 있다.** 없는 것은 연결 정보가 아니라 **아직 해소되지 않은 외부 심볼**이다.

같은 편에 더 있다.

- `구문 분석을 통해 논리적 오류를 잡고` — 구문 분석은 **구문 오류**를 찾는다. 타입 오류 같은 일부 정적 의미 오류는 잡지만 일반적인 논리 오류는 못 잡는다
- `링커가 실제 메모리 주소를 연결한다` — 링커는 심볼 참조를 해소하고 재배치한다. 동적 심볼과 실제 런타임 주소는 **로더**가 나중에 정한다
- 전체가 C/C++ 네이티브 빌드 전제인데 그렇게 안 적혀 있다. 모든 언어가 이 과정을 거치지 않는다

### 3. 본문에 깨진 글이 남아 있다

같은 그리디/DP 편이다.

- `정확한 정확한 기준을 세우는 데` — 낱말 반복
- `선택지가로 인해 전체적인 최적해를 구할 수 없는` — **조사가 깨졌다.** 뜻이 안 통한다

낱말 반복은 오늘 검사기에 넣어 새로 만드는 것은 막힌다. **조사 깨짐은 못 잡는다** — 규칙으로 만들면 기준선이 걸릴 위험이 크다.

## 나머지

**DBSCAN과 K-means** — `K-means는 구형의 클러스터만 찾을 수 있다`는 과한 단정이다. 유클리드 거리 기반 K-means는 **크기와 밀도가 비슷한 볼록한 군집**에 적합하다고 해야 한다. `데이터의 실제 모양을 모르면 DBSCAN이 효과적`도 그렇다 — 밀도가 크게 다르거나 고차원이면 DBSCAN이 오히려 나쁘다.

**메시지 순서** — `버전으로 판단하면 순서 요구 자체가 사라진다`는 조건이 빠졌다. **최신 상태 이벤트가 이전 상태를 완전히 담을 때만** 안전하다. 증분 이벤트나 반드시 적용해야 하는 상태 전이를 버리면 데이터가 사라진다.

**즉시 로딩** — 표의 `지연 | 접근할 때`가 단정이다. JPA의 `FetchType.LAZY`는 **공급자에 대한 힌트**다. `지연 프록시를 컨텍스트 밖에서 건드리면 초기화에 실패한다`도 **아직 초기화되지 않은** 것에만 해당한다.

## 판정이 갈린 것

**경쟁 상태** — Codex는 문제 없다고 했고 나는 `이는 데이터 정합성을 보장하는 가장 확실한 방법이다`를 과장으로 봤다. 원자적 연산이나 락 프리 방식도 정합성을 보장하고, 락은 교착 위험을 새로 만든다. 강한 지적은 아니라 남겨만 둔다.

**교차 검증이 값을 했다.** 나는 2·3번(오브젝트 파일·구문 분석)을 놓쳤고 Codex는 깨진 글 두 곳을 안 짚었다. 한쪽만 봤으면 절반을 놓쳤다.

## 분야가 틀린 것

- **DBSCAN이 `데이터베이스`에 있다.** 군집 알고리즘이라 `자료구조 · 알고리즘`이 맞다
- **경쟁 상태가 `인프라 · 보안`에 있다.** 운영체제 기초다

둘 다 rs-data가 찾은 패턴 그대로다 — `인프라 · 보안` 19개 중 9개가 다른 분야 CS 기초의 재등재다. 미분류 수용소가 됐다.

## 그래서 무엇을 해야 하나

1. **표본을 늘려 비율을 확정한다.** 10편은 규모를 말하기엔 작다. 50% 오류율이 전체에 그대로 적용된다면 251편 중 125편이다. 지금은 "표본 10편에서 5편"까지만 말할 수 있다
2. **기계로 못 잡는 것이 이 결함의 본질이다.** 규칙 검사기는 `정확한 정확한` 하나만 잡았다. 사실 오류는 사람이나 다른 모델이 읽어야 한다. **검수를 정기 작업으로 돌리는 편이 맞다**
3. **고치는 것은 운영 DB 쓰기라 승인이 필요하다.** 여기 적어만 둔다. `db:enrich`가 제자리에서 다시 쓰는 명령인데, 다시 쓰면 같은 모델이 같은 오류를 낼 수도 있다
4. **분야 재배치**도 같이 본다. 위 둘은 확실하다
