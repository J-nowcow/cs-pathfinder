## 0211b774-3323-4b37-b52c-4c2db13bf42e

질문: 정적 클래스 내부에 정적 메서드를 정의하는 이유는 무엇인가?
판정: 고침
지적: (1) "정적 클래스"가 어느 언어 이야기인지 안 밝혔다 (2) 인스턴스화가 메모리·성능 손실을 만든다고 했다 (3) static을 순수 함수와 같은 것으로 썼다

원래: | 정적 클래스 | 유틸리티 클래스. 인스턴스화로 인한 메모리 성능으로 인한 손실을 없앤다 |
고침: | 유틸리티 클래스(Java) | 인스턴스 상태가 필요 없다는 설계 의도를 나타낸다 |

원래: | 정적 메서드 | 상태 없는 로직. 입력값으로만 결과가만 나오는 same-result same-input 구조다 |
고침: | 정적 메서드 | 인스턴스 없이 호출한다. 외부 상태를 안 읽을 때만 같은 입력에 같은 결과가 나온다 |

원래: 정적 클래스로 선언하면 외부에서 `new` 키워드로 인스턴스를 생성하는 것을 막을 수 있다. 이는 클래스가 단순한 도구 모음임을 명확히 알리는 설계적 의도이다.
고침: Java에는 최상위 static 클래스가 없다. private 생성자를 두어 `new`를 막는다. C#은 static 클래스 키워드로 같은 의도를 언어가 강제한다.

> 세 번째 문장은 지적이 직접 짚지 않았다. 다만 표를 Java로 명시하면 "정적 클래스로 선언하면"이 Java에서 거짓이 되어 함께 고쳤다.

## 080aa4a6-9daf-4a63-9a2c-09a8d243bd85

질문: 체크 예외와 언체크 예외의 선택 기준은 무엇인가?
판정: 고침
지적: (1) 표의 "처리 강제 | 컴파일 타임 | 런타임"이 언체크도 런타임에 강제되는 것처럼 읽힌다 (2) 체크 예외가 예외 상황을 미리 방지한다고 했다

원래: | 처리 강제 | 컴파일 타임 | 런타임 |
고침: | 처리 강제 | 컴파일 타임에 catch 또는 throws | 강제 없음 |

원래: 체크 예외는 시그니처에 명시해야 하므로 호출자에게 처리 의무를 강제한다. 이를 통해 런타임에 발생할 수 있는 예외 상황을 미리 방지할 수 있다.
고침: 체크 예외는 시그니처에 명시해야 하므로 호출자에게 처리 의무를 강제한다. 다만 강제되는 것은 catch나 선언까지다. 예외가 나는 것 자체를 막아주지는 않는다.

## 153ee4b0-df68-400e-9a05-d10b23cf4fbe

질문: 생성자 주입이 기본 선택인 이유는?
판정: 고침
지적: 표의 "필수성 | 생성 시 확인 | 실행 뒤 발견". 필드 주입도 컨테이너가 빈을 만드는 기동 단계에서 누락을 잡는다

원래: | 필수성 | 생성 시 확인 | 실행 뒤 발견 |
고침: | 필수성 | 생성자 시그니처에 드러남 | 컨테이너 밖에서는 안 드러남 |

> `@Autowired`는 required 기본값이 true다. 빈이 없으면 기동 단계에서 실패한다.
> 필드 주입의 실제 약점은 컨테이너 없이 `new`로 만들 때 필수 의존성이 비어도 조용히 넘어가는 것이라 그쪽으로 옮겼다.

## 2ac697dd-fb59-4aff-b357-5f9d90a01b56

질문: JPA에서 N+1 쿼리는 왜 생기고 무엇으로 막는가?
판정: 고침
지적: `EAGER`가 조인을 붙인다고 전제했다. `EAGER`는 조인을 보장하지 않아 N+1이 그대로 날 수 있다

원래: 즉시 로딩으로 바꾸는 것은 답이 아니다. 그러면 연관이 필요 없는 조회에서도 매번 조인이 붙는다. N+1이 사라지는 대신 모든 질의가 무거워진다. 문제를 옮긴 것이지 푼 것이 아니다.
고침: 즉시 로딩으로 바꾸는 것은 답이 아니다. `EAGER`는 언제 읽을지만 정하고 조인으로 읽으라는 뜻이 아니다. JPQL로 목록을 조회하면 연관마다 추가 select가 나가 N+1이 그대로 난다. 필요 없는 조회에서도 연관을 끌고 오는 것은 덤이다.

## 46cd1316-9f2a-4c04-861f-d1df114147e6

질문: 인증 정보는 어떻게 보안 문맥에 들어가는가?
판정: 고침
지적: `AuthenticationManager`가 결과를 `SecurityContext`에 넣는다고 했다. Manager는 반환만 하고 저장은 필터가 한다

원래: 인증 필터가 요청에서 자격 증명을 꺼내 미인증 토큰을 만든다. AuthenticationManager가 검증을 위임하고 성공 결과를 SecurityContext에 넣는다.
고침: 인증 필터가 요청에서 자격 증명을 꺼내 미인증 토큰을 만든다. AuthenticationManager는 검증을 위임하고 인증된 Authentication을 돌려준다. 그것을 SecurityContext에 넣는 일은 필터가 한다.

원래: AuthenticationProvider는 토큰 종류를 지원하는지 판단한다. 사용자 조회와 비밀번호 해시 비교를 거쳐 주체와 권한을 담은 결과를 만든다.
고침: AuthenticationProvider는 토큰 종류를 지원하는지 판단한다. 아이디·비밀번호 방식이면 `DaoAuthenticationProvider`가 사용자 조회와 해시 비교를 거쳐 주체와 권한을 담은 결과를 만든다.

> 두 번째 문장은 지적이 직접 짚지 않았다. 사용자 조회·해시 비교는 인터페이스 일반의 동작이 아니라 특정 구현체의 동작이라 이름을 한 번 댔다.
> 도식(191~195행)은 이미 "Manager → 필터 → 보안 문맥" 순서로 맞게 그려져 있다. 첫 문단만 도식과 어긋났다. 도식은 손대지 않았다.

## bbd92984-377a-4412-8c70-4d7a73812fe2

질문: 인터페이스와 추상 클래스는 무엇으로 구분하는가?
판정: 반려
지적: can-do와 is-a는 설계 휴리스틱일 뿐 정의가 아니다. 인터페이스도 타입 정체성과 기본 구현을 표현할 수 있다
반려 사유: 원문이 이미 "설계 목적의 차이로 구분한다"고 한정하고 들어간다. 정의라고 주장한 적이 없으니 지적의 전제가 원문과 어긋난다. can-do / is-a 대비는 면접 대비 자료에서 통용되는 표준 설명이고, 면접관이 되물어도 그 자리에서 드러날 사실 오류가 아니다. 원문이 "인터페이스는 구현을 가질 수 없다"까지 말했다면 default method 때문에 틀렸겠지만 그런 서술은 없다.

## a1497084-ec66-4667-a481-be82e6438792

질문: JVM의 핵심 역할은 무엇인가?
판정: 고침
지적: (1) "JVM 내부 | JRE"로 포함 관계를 뒤집었다 (2) 바이트코드를 "기계어로 해석한다"며 해석과 컴파일을 뒤섞었다

원래: | JVM 내부 | Java Runtime Environment (JRE) |
고침: | JRE 구성 | JVM과 Java 실행 라이브러리 |

원래: 컴파일러가 소스코드를 바이트코드로 변환하면, JVM은 이를 읽어 각 OS에 맞는 기계어로 바이트코드를 해석한다. 이 과정에서 메모리 관리와 최적화가 핵심이다.
고침: 컴파일러가 소스코드를 바이트코드로 변환하면, JVM은 이를 읽어 인터프리터로 실행한다. 기계어 컴파일은 뒤의 JIT가 맡는다. 이 과정에서 메모리 관리와 최적화가 핵심이다.

> JIT 설명은 같은 편 431행에 이미 있다. 여기서 다시 풀지 않고 넘겨 중복을 피했다.
