## 62e02f6b-29f6-4147-97a3-651d066b5e3f

질문: DNS 질의 시 재귀적 질의와 반복적 질의의 차이는 무엇인가?
판정: 고침
지적: (1) 도식에 권한 서버 질의 단계가 빠져 TLD 응답만으로 IP가 나온다 (2) 반복적 질의에서 서버가 답을 절대 직접 주지 않는 것처럼 썼다

원래: `로컬 DNS -> TLD 서버: 권한 있는 서버의 주소`
      `TLD 서버 -> 로컬 DNS: 권한 있는 서버 주소`
      `로컬 DNS -> 클라이언트: IP 주소 응답`
고침: `로컬 DNS -> TLD 서버: 권한 있는 서버의 주소`
      `TLD 서버 -> 로컬 DNS: 권한 있는 서버 주소`
      `로컬 DNS -> 권한 있는 서버: 대상 레코드를 알려달라`
      `권한 있는 서버 -> 로컬 DNS: A 레코드`
      `로컬 DNS -> 클라이언트: IP 주소 응답`

> 주의: 이 건만 `:::flow` 안을 건드린다. 울타리와 `A -> B: 설명` 형식은 그대로 두고 줄 2개를 끼워 넣었다.
> 도식 밖에서는 고칠 방법이 없는 오류다. 본문만 손대라는 지침과 충돌하니 팀 리드가 판단해 주기 바란다.

원래: 반복적 질의는 각 단계의 서버가 답을 직접 주지 않고 다음으로 가야 할 서버의 주소를로 알려준다.
고침: 반복적 질의는 각 단계의 서버가 아는 만큼만 답한다. 최종 답을 가졌으면 그것을 주고, 모르면 더 가까운 권한 서버의 주소를 알려준다.

## 4052fe26-b550-4c15-bcfe-0dfd9d709234

질문: TCP의 4-way handshake 과정을 3단계로 단축할 수 없는 이유는 무엇인가?
판정: 고침
지적: (1) ACK와 FIN은 합칠 수 있다. 3단계 종료가 실제로 일어난다 (2) `shutdown()`이 송신만 닫는다고 단정했다

원래: 만약 2단계인 ACK와 3단계인 FIN을 합쳐 3단계로 줄인다면 문제가 생긴다. B가 아직 A에게 보낼 데이터가 남았는데도 강제로 연결을 종료해야 하므로 데이터 유실이 발생한다. B의 전송이 끝날 때까지 기다려주는 반이중(Half-Close) 상태가 존재해야만 안전한 종료가 보장된다.
고침: 네 단계가 되는 것은 B에게 보낼 데이터가 남았을 때다. 그때는 ACK를 먼저 보내고 FIN은 전송을 마친 뒤 보낸다. B가 곧바로 닫으면 ACK와 FIN이 한 세그먼트로 합쳐져 3단계로 끝난다. 반이중(Half-Close) 상태가 남은 데이터를 지킨다.

원래: close()는 소켓을 완전히 닫아 전송과 수신을 모두 차단하지만, shutdown()은 송신만 차단하고 수신은 열어두는 Half-Close 상태를 명시적으로 구현할 때 사용한다.
고침: close()는 디스크립터를 반납해 송수신을 함께 끝내지만, shutdown()은 인자로 방향을 고른다. Half-Close는 송신만 닫는 shutdown(SHUT_WR)로 만든다.

## e1bbcc1c-686f-4845-bc0d-485d37ee8898

질문: 웹소켓과 일반 소켓 통신은 무엇으로 구분하는가?
판정: 고침
지적: (1) 소켓을 "TCP/UDP 연결 자체"·"하드웨어적 통로"라 했다 (2) 웹소켓이 HTTP 요청-응답 모델을 유지한다고 했다

원래: 웹소켓은 HTTP 기반의 전이중 통신 프로토콜이며, 일반 소켓은 전송 계층의 TCP/UDP 연결 자체를 의미한다.
고침: 웹소켓은 HTTP 핸드셰이크로 시작하는 전이중 통신 프로토콜이며, 일반 소켓은 TCP·UDP 통신의 종단점을 다루는 운영체제 API다.

원래: HTTP의 요청-응답 모델을 유지하면서도 연결을 계속 열어두어 서버가 클라이언트로 데이터를 보낼 수 있게 한다.
고침: HTTP로 핸드셰이크만 하고 그 뒤로는 요청-응답 모델을 벗어난다. 양쪽이 언제든 프레임을 보내는 전이중 통신으로 전환한다.

원래: 따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 통신을 위한 하드웨어/소프트웨어적 통로 그 자체라고 볼 수 있다.
고침: 따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 그 규약을 실어 나르는 통신 종단점의 추상화다.

## a9f6be16-909e-4878-a933-203dd568dbd1

질문: HTTP 상태 코드는 어떤 기준으로 분류하는가?
판정: 고침
지적: "5xx는 서버 내부 오류". `Internal Server Error`는 500의 이름이고 5xx 전체의 분류명은 `Server Error`다

원래: | 5xx는 서버 내부 오류 |  |
고침: | 5xx는 서버 오류 |  |

원래: 4xx는 요청자가 잘못 보냈으니 수정해서 다시 보내야 하고, 5xx는 서버가 처리로직으로 인해 장애가 발생했음을 의미한다.
고침: 4xx는 요청자가 잘못 보냈으니 수정해서 다시 보내야 하고, 5xx는 요청이 올바른데도 서버가 수행에 실패했음을 의미한다.

> 두 번째 문장은 지적이 직접 짚지 않았다. 다만 502·503처럼 "내부 로직" 탓이 아닌 5xx가 많아 같은 오류다.
> 첫 문단은 이미 "5xx는 서버 오류다"로 맞게 써 있어 표·본문만 맞추면 정합이 선다.

## ce9dc1e2-688b-4a88-8f28-efb66f892224

질문: 전송 계층에서 멀티플렉싱과 디멀티플렉싱은 무엇으로 구분하는가?
판정: 고침
지적: "UDP는 목적지 포트와 출발지 포트, 프로토콜로만 구분한다". UDP 디멀티플렉싱에 출발지 포트는 쓰이지 않는다

원래: UDP는 목적지 포트와 출발지 포트, 프로토콜로만 구분한다. TCP는 4가지 요소(출발지 IP, 목적지 IP, 출발지 포트, 목적지 포트)를 모두 확인해 연결 지향적 소켓을 구분한다.
고침: UDP는 목적지 IP와 목적지 포트 두 가지로 구분한다. 출발지가 달라도 같은 소켓으로 올라간다. connect()로 상대를 고정하면 출발지까지 본다. TCP는 출발지 IP·포트와 목적지 IP·포트 네 가지를 모두 확인해 연결마다 소켓을 나눈다.

## a6cc9679-ec7b-4f81-88d2-cfa10da977a5

질문: IP 주소의 핵심 역할은 무엇인가?

원래: 네트워크 상의 기기별로 고유한 식별자와 위치 정보를 제공하는 것이다. 이를 통해 데이터 패킷이 목적지까지 정확하게 전달될 수 있다.
고침: 네트워크 인터페이스를 식별하고 라우팅 토폴로지상의 위치를 알려주는 것이다. 이를 통해 데이터 패킷이 목적지까지 정확하게 전달될 수 있다.

판정: 고침
지적: (1) 쿠키(전송 수단)와 세션(상태 개념)은 층위가 달라 저장 위치로만 대비할 수 없다 (2) 세션 크기가 "제한 없음"이라 했다

원래: | 데이터 크기 | 작음 | 제한 없음 |
고침: | 데이터 크기 | 작음(4KB 안팎) | 저장소 용량까지 |

## 10f835f1-f9b4-4bff-90ab-d398907b5bea

질문: HTTPS는 HTTP와 무엇이 다른가? (`네트워크.md` 501행)
판정: 고침안만 제시 — 배정 8편에 없음

하드 오류 목록에는 없다. 다만 팀 리드가 "확실히 고쳐야 한다"고 지목한 TLS 오류 두 개가 이 편에 그대로 있다.
지적 자체는 감사 코퍼스에 실려 있다 — `2026-08-07-fact-check-full.md` 77~79행, `2026-08-07-fact-check-20.md` 52~66행.

원래: 클라이언트와 서버가 서로의 신원을 확인하고 암호화 키를 교환하는 과정이 핵심이다.
고침: 클라이언트가 서버의 신원을 확인하고 양쪽이 공유 비밀을 합의하는 과정이 핵심이다. 서버가 클라이언트까지 확인하는 것은 mTLS라는 별도 선택이다.

원래: 대칭키로 데이터를 빠르게 암호화하고, 비대칭키로 그 대칭키를 안전하게 전달한다. 성능 저하를 최소화하면서 보안성을 챙긴 방식이다.
고침: 데이터는 빠른 대칭키로 암호화한다. 그 대칭키는 실어 보내지 않고 (EC)DHE로 양쪽이 각자 만든다. 공개키는 서버가 진짜임을 서명으로 증명하는 데 쓴다.

> 근거: TLS 1.3은 RSA 키 전송을 아예 제거했다. 1.2도 현실에서는 대부분 (EC)DHE로 공유 비밀을 합의한다.
