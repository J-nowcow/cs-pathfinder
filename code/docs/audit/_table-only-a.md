## #4 컨텍스트 스위칭 비용은 구체적으로 어디서 발생하는가?
`운영체제`

```
레지스터 교체 자체보다 캐시가 무너지는 비용이 크다. 눈에 보이는 저장·복원은 일부일 뿐이다.

| 구분 | 무엇이 일어나나 | 크기 |
| --- | --- | --- |
| 직접 비용 | 레지스터·PC를 PCB에 저장하고 복원, 커널 모드 전환 | 수 마이크로초 |
| 간접 비용 | 캐시와 TLB가 무효화되어 다시 채워야 한다 | **이쪽이 본체** |

직접 비용은 명확하다. 실행 중이던 스레드의 레지스터와 프로그램 카운터를 PCB에 저장하고 다음 스레드의 것을 복원한다. 커널 모드 전환도 함께 일어난다. 이건 수 마이크로초 수준이다.

간접 비용이 본체다. CPU 캐시와 TLB에 쌓아둔 내용이 새 스레드에게는 쓸모없다. 다시 실행될 때 캐시 미스가 연달아 나고 메모리에서 다시 읽어와야 한다. 프로세스 간 전환이면 주소 공간까지 바뀌어 TLB를 통째로 비운다.

그래서 스레드를 늘린다고 처리량이 비례해 늘지 않는다. 코어 수를 넘어서면 실행이 아니라 전환에 시간을 쓰기 시작한다. 커넥션 풀 크기를 코어 수 기준으로 잡는 근거가 여기 있다.

CPU 바운드 작업은 코어 수에 맞추고 I/O 바운드는 더 늘려도 되는 이유도 같다. 대기 중인 스레드는 CPU를 점유하지 않기 때문이다.
```

## #5 인덱스를 만들었는데 실행 계획에서 타지 않는 이유는?
`데이터베이스`

```
인덱스가 있어도 옵티마이저가 쓸 수 없거나 쓰지 않는 편이 낫다고 판단한 것이다. 두 경우는 원인이 다르다.

| 갈래 | 실행 계획에서 | 대표 원인 |
| --- | --- | --- |
| 쓸 수 없다 | 후보에도 안 오른다 | 컬럼에 함수 적용, 암묵 타입 변환, 선행 컬럼 누락 |
| 쓰지 않는다 | 후보엔 있는데 안 고른다 | 조회 비율이 높다, 통계가 낡았다 |

쓸 수 없는 경우가 먼저다. 인덱스 컬럼에 함수나 연산을 적용하면 인덱스는 무력해진다. 저장된 값과 비교 대상이 달라지기 때문이다. 타입이 암묵적으로 변환되는 경우도 같다. 복합 인덱스에서 선행 컬럼을 조건에 넣지 않은 경우도 여기 속한다.

쓰지 않기로 한 경우는 통계 문제다. 조회 대상이 전체의 상당 비율이면 인덱스로 한 건씩 찾아가는 것보다 풀 스캔이 빠르다. 옵티마이저는 카디널리티 추정으로 이를 판단하는데, 통계가 오래되면 추정이 틀린다.

진단 순서가 있다. 실행 계획을 먼저 보고 인덱스가 후보에 올랐는지 확인한다. 후보에도 없으면 쓸 수 없는 경우이고, 후보에 있는데 선택되지 않았으면 통계나 비용 추정 문제다.

면접에서는 함수 적용 사례를 자주 묻는다. 날짜 컬럼에 포맷 함수를 씌운 조건이 대표적이다. 조건을 범위 비교로 바꾸면 인덱스가 다시 살아난다.
```

## #6 useEffect 의존성 배열을 잘못 넣으면 어떤 문제가 생기는가?
`프론트엔드`

```
너무 적게 넣으면 오래된 값을 붙잡고, 너무 많이 넣으면 불필요하게 다시 실행된다. 방향이 반대인 두 문제다.

| 넣는 양 | 증상 | 알아채기 |
| --- | --- | --- |
| 너무 적다 | 클로저가 첫 렌더의 값을 계속 본다 | 오류가 안 나서 늦게 발견된다 |
| 너무 많다 | 매 렌더마다 실행되고 무한 루프로 간다 | 바로 티가 난다 |

의존성을 빠뜨리면 클로저가 첫 렌더의 값을 계속 참조한다. 이펙트 안에서 최신 상태를 읽는 줄 알았는데 초기값이 나오는 상황이 여기서 생긴다. 콘솔에는 아무 오류도 없어 발견이 늦다.

반대로 매 렌더마다 새로 만들어지는 객체나 함수를 의존성에 넣으면 참조가 계속 바뀐다. 이펙트가 매번 실행되고, 그 안에서 상태를 갱신하면 무한 루프가 된다.

정리 함수를 빠뜨리는 것도 같은 범주다. 구독이나 타이머를 걸어두고 정리하지 않으면 언마운트된 컴포넌트가 계속 살아 있다. 이펙트가 자주 실행될수록 누수가 빨리 쌓인다.

판단 기준은 단순하다. 이펙트 안에서 쓰는 모든 외부 값을 넣고, 그래서 너무 자주 실행되면 값 자체를 안정화한다. 의존성을 빼서 해결하는 것은 증상만 가리는 것이다.
```

## #7 JWT를 세션 대신 쓸 때 무엇을 잃는가?
`인프라 · 보안`

```
즉시 무효화 능력을 잃는다. 서버가 상태를 갖지 않는다는 장점이 그대로 단점이 된다.

세션은 서버가 저장소를 들고 있으므로 지우면 그 순간 끝난다. JWT는 서명만 유효하면 통과하므로 발급된 토큰을 회수할 방법이 없다. 로그아웃, 권한 변경, 탈취 대응이 전부 만료 시각까지 지연된다.

| 기준 | 세션 | JWT |
| --- | --- | --- |
| 상태 보관 | 서버가 들고 있다 | 토큰 안에 들어 있다 |
| 즉시 무효화 | 지우면 끝 | **만료까지 못 막는다** |
| 서버 확장 | 저장소 공유가 필요하다 | 서버끼리 공유할 것이 없다 |

통상적인 대응은 수명을 짧게 가져가고 리프레시 토큰을 붙이는 것이다. 다만 리프레시 토큰은 결국 서버가 상태를 들고 관리해야 하므로, 무상태라는 원래 이점이 상당 부분 사라진다.

저장 위치도 문제다. 로컬 스토리지는 XSS에 그대로 노출되고, 쿠키는 CSRF를 따로 막아야 한다. 어디에 둬도 공짜가 아니다.

판단 기준은 규모다. 서버가 여러 대이고 세션 공유 비용이 실제 부담일 때 JWT가 값을 한다. 단일 서비스에서 관성으로 고르면 잃는 쪽이 크다.
```

## #9 데이터베이스 커넥션 풀의 적정 크기를 설정할 때 왜 CPU 코어 수를 기준으로 설정하는지 그 이유가 궁금합니다.
`데이터베이스`

```
코어 수가 동시에 돌릴 수 있는 CPU 작업 수를 정해 병목을 추정하는 기준이 되기 때문이다. I/O로 대기하는 요청까지 코어 수로 묶이지는 않는다. 코어 수가 적은데 풀 크기만 늘리면 컨텍스트 스위칭 비용만 증가한다.

| 항목 | 내용 |
| --- | --- |
| 풀 크기 시작값 | 코어 수 × 목표 CPU 사용률 × (1 + 대기 시간 / 계산 시간) |
| 병목 지점 | CPU 코어 수. 연산 처리의 실제 한계 |

DB 서버의 CPU는 쿼리 실행 계획을 짜고 데이터를 연산한다. 풀 크기가 너무 크면 수많은 스레드가 CPU 점유를 위해 경쟁하며 오버헤드가 발생한다.

반면 너무 작으면 CPU가 놀고 있어도 요청이 큐에서 대기한다. 따라서 코어 수와 디스크 I/O 성능을 고려한 적정 지점을 찾아야 한다.

면접에서는 CPU 코어 수뿐만 아니라 디스크 타입(SSD/HDD)에 따른 I/O 대기 시간을 함께 언급하는 것이 좋다.
```

## #14 해시 테이블의 평균 O(1)이 무너지는 경우는?
`자료구조 · 알고리즘`

```
키가 한 버킷으로 몰릴 때다. 평균 O(1)은 해시가 고르게 흩어진다는 전제 위의 값이라, 그 전제가 깨지면 최악 O(n)으로 간다. 완화는 충돌한 것을 어떻게 담느냐와 언제 늘리느냐 두 갈래다.

| 갈래 | 하는 일 | 최악을 어디까지 |
| --- | --- | --- |
| 담는 방식 | 한 버킷이 길어지면 연결 리스트를 트리로 | `O(n)` → `O(log n)` |
| 늘리는 시점 | load factor를 넘으면 버킷을 두 배로 | 애초에 안 몰리게 |

자바 HashMap은 둘을 함께 쓴다. 앞쪽은 이미 몰린 뒤의 방어고, 뒤쪽은 몰리기 전의 예방이다.

몰리는 이유는 둘이다. 해시 함수가 나빠서 자연히 겹치거나, 누군가 일부러 겹치게 만들거나. 뒤쪽이 해시 충돌 공격인데, 사용자 입력이 그대로 키가 되는 자리에서는 실제 공격 벡터가 된다.

늘리는 것 자체에도 값이 있다. 리사이즈는 모든 키를 다시 배치하므로 그 한 번이 무겁다. 분할 상환하면 평균은 O(1)이지만 평균이 지연을 보장하지는 않는다 — 응답 시간이 중요한 경로에서는 이 한 번이 튀는 지점으로 나타난다.

면접에서는 왜 버킷 수를 2의 거듭제곱으로 잡는지로 한 단계 더 들어온다. 나머지 연산 대신 비트 마스크를 쓸 수 있어서다. 대신 하위 비트만 보게 되므로 해시를 한 번 더 섞어야 한다.
```

## #18 화면을 돌리면 데이터가 사라지는 이유는?
`모바일`

```
구성이 바뀌면 액티비티가 파괴되고 새로 만들어지기 때문이다. 기존 인스턴스가 들고 있던 값은 그 인스턴스와 함께 사라진다. 남기려면 무엇까지 견뎌야 하는지에 따라 세 층 중 하나를 고른다.

| 수단 | 어디까지 견디나 | 담기 좋은 것 |
| --- | --- | --- |
| ViewModel | 구성 변경까지. **프로세스 종료엔 사라진다** | 목록, 진행 중인 작업 |
| onSaveInstanceState | 프로세스 종료까지 | 작고 직렬화 가능한 값 |
| 파일·DB | 앱을 지울 때까지 | 오래 남겨야 하는 것 |

일부러 그렇게 설계했다. 가로와 세로는 레이아웃도, 이미지도, 때로는 문자열도 다른 리소스를 쓴다. 리소스를 다시 고르는 가장 확실한 방법이 처음부터 다시 만드는 것이다 — 언어 변경이나 다크 모드 전환도 같은 경로를 탄다.

셋을 가르는 축은 무엇을 견뎌야 하느냐다. 구성 변경만 견디면 되는 값은 ViewModel로 충분하다. 다만 시스템이 메모리를 회수하며 프로세스를 죽이면 ViewModel도 함께 사라진다. 그때까지 살아야 하는 값은 번들이나 저장소로 내려야 한다.

면접에서는 이 둘을 구별하는지를 본다. "ViewModel을 쓰면 된다"까지는 대부분 말한다. 프로세스 종료는 못 견딘다는 것과 그 자리를 SavedStateHandle이 메운다는 데까지 가면 한 단계 위다.
```

## #22 서브쿼리를 언제 조인으로 재작성해야 성능이 향상되는가?
`데이터베이스`

```
RDBMS 옵티마이저는 조인 연산의 최적화 경로를 서브쿼리보다 더 다양하게 탐색할 수 있다. 서브쿼리를 사용하면 서브쿼리 블록 단위로 최적화가 수행되어 전체 쿼리 수준에서의 최적화 기회를 잃기 쉽다. 특히 외부 쿼리의 값을 참조하는 상관 서브쿼리는 매 행마다 반복 실행되어 성능 저하의 주 원인이 된다.

서브쿼리를 조인으로 변환할 때는 일대다 관계에서 데이터가 증폭되는 문제를 주의해야 한다. 서브쿼리는 단순히 존재 여부만 확인하여 원본 행 수를 유지하지만, 이를 단순 조인으로 바꾸면 중복 데이터가 생성되어 DISTINCT나 GROUP BY를 추가해야 하므로 오히려 성능이 떨어질 수 있다.

| 기준 | 서브쿼리 | 조인 (Join) |
| --- | --- | --- |
| 실행 방식 | 독립된 블록 또는 반복 실행 | 다양한 조인 알고리즘 선택 |
| 결과 행 수 | 원본 테이블 행 수 유지 | 관계에 따라 중복 발생 가능 |
| 최적화 범위 | 쿼리 블록 내로 제한됨 | 전역적인 실행 계획 수립 |

최신 옵티마이저는 서브쿼리 언네스팅 기법을 통해 내부적으로 서브쿼리를 조인으로 자동 변환하여 실행한다. 따라서 개발자가 성능 개선을 위해 수동으로 변환하기 전에, 옵티마이저의 실행 계획을 먼저 확인하고 자동 최적화가 작동하지 않는 경우에만 수동으로 변환해야 한다.
```

## #23 HTTP/2는 HTTP/1.1의 무엇을 고쳤는가?
`네트워크`

```
한 연결에서 요청 하나가 끝나야 다음이 나가던 제약을 없앴다. 앞의 응답이 늦으면 뒤가 통째로 밀리던 문제가 여기서 온다. HTTP/2는 요청과 응답을 프레임으로 쪼개고 스트림 번호를 붙여 한 연결에 섞어 보낸다.

| 기준 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 한 연결의 요청 | 순서대로 하나씩 | 여러 개가 섞여서 |
| 헤더 | 매번 통째로 | 표로 눌러서(HPACK) |
| 브라우저 우회책 | 도메인 쪼개기, 스프라이트 | 필요 없어진다 |

도착한 순서대로 다시 조립되므로 순서 제약이 사라진다. 연결 하나로 충분해진다.

HTTP/1.1도 연결을 재사용하기는 했다. 다만 응답이 보낸 순서대로 와야 해서 앞의 것이 느리면 뒤에 줄 선 요청이 전부 기다렸다. 그래서 브라우저는 도메인당 연결을 예닐곱 개씩 열었고, 이미지를 하나로 합치는 기법이 유행했다.

다만 TCP 계층의 줄서기는 남는다. 패킷 하나가 유실되면 그 연결의 모든 스트림이 재전송을 기다린다. HTTP/3가 전송을 QUIC으로 바꾼 이유가 이것이다.

면접에서는 우회책이 왜 역효과가 되는지로 들어온다. 도메인을 쪼개면 연결이 늘어 HTTP/2의 이점이 사라진다. 스프라이트는 한 조각만 바뀌어도 전체를 다시 받게 만든다.
```

## #24 데드락은 어떤 조건이 모두 모여야 생기는가?
`운영체제`

```
네 조건이 동시에 성립할 때다. 하나만 깨도 데드락은 생기지 않는다.

| 조건 | 뜻 |
| --- | --- |
| 상호 배제 | 자원을 한 번에 하나만 쓸 수 있다 |
| 점유하며 대기 | 하나를 쥔 채로 다른 것을 기다린다 |
| 비선점 | 쥔 것을 강제로 뺏을 수 없다 |
| 순환 대기 | 기다림이 고리를 이룬다 |

실무에서 가장 자주 깨는 것은 마지막이다. 자원에 순서를 매기고 항상 그 순서로만 잡게 하면 고리가 생길 수 없다. 계좌 두 개를 잠글 때 언제나 번호가 작은 쪽부터 잡는 식이다.

점유하며 대기를 깨는 방법도 있다. 필요한 자원을 한 번에 전부 잡거나, 못 잡으면 쥔 것을 놓고 처음부터 다시 한다. 다만 이쪽은 굶주림이 생길 수 있다 — 계속 실패하는 쪽이 영영 못 잡는다.

면접에서는 예방과 회피와 탐지를 구별하는지를 본다. 예방은 조건을 아예 못 만들게 한다. 회피는 요청마다 안전한지 따져본다. 탐지는 생기게 두되 발견하면 푼다. 데이터베이스는 대개 마지막을 고른다 — 앞의 둘이 처리량을 너무 깎기 때문이다.
```

## #25 메시지 큐를 두면 무엇을 얻고 무엇을 잃는가?
`아키텍처 · 분산시스템`

```
보내는 쪽과 받는 쪽의 시간을 떼어내는 대신 순서와 즉시성을 잃는다. 트래픽이 몰려도 받는 쪽이 자기 속도로 처리할 수 있게 되는 것이 가장 큰 이득이다.

직접 호출은 받는 쪽이 죽으면 보내는 쪽도 같이 실패한다. 큐를 끼우면 메시지가 쌓여 있다가 받는 쪽이 살아난 뒤에 처리된다. 배포 중에도 요청이 유실되지 않는다.

| 기준 | 직접 호출 | 큐를 통해 |
| --- | --- | --- |
| 받는 쪽이 죽으면 | 보내는 쪽도 실패 | 쌓였다가 나중에 처리 |
| 결과를 아는 시점 | 즉시 | 나중에. 따로 알려야 한다 |
| 순서 | 호출한 순서 | 파티션 안에서만 보장 |

대가가 분명하다. 결과를 즉시 못 준다. 주문이 접수됐다는 응답과 실제로 처리됐다는 사실 사이에 틈이 생기고, 그 틈을 화면이 설명해야 한다. 실패도 그 자리에서 안 보여서 따로 관측해야 한다.

면접에서는 중복과 순서로 한 단계 더 들어온다. 대부분의 큐는 최소 한 번 전달을 보장하므로 같은 메시지가 두 번 올 수 있다. 받는 쪽이 멱등해야 하고, 순서가 필요하면 같은 키를 같은 파티션으로 보내야 한다.
```

## #27 HTTPS는 무엇을 보장하고 무엇을 못 하는가?
`인프라 · 보안`

```
오가는 내용의 비밀과 위변조 여부, 그리고 상대가 그 도메인의 주인인지까지 보장한다. 그 너머는 보장하지 않는다.

| 보장하는 것 | 어떻게 | 보장하지 않는 것 |
| --- | --- | --- |
| 내용의 비밀 | 대칭키로 암호화 | 접속한 도메인 자체는 드러난다 |
| 위변조 탐지 | 메시지 인증 코드 | 서버가 안전한지는 모른다 |
| 상대의 신원 | 인증서와 CA 검증 | 그 사이트가 정직한지는 모른다 |

흔한 오해가 둘이다. 자물쇠가 붙었다고 안전한 사이트는 아니다. 인증서는 그 도메인의 주인이 맞다는 것만 말하고, 피싱 사이트도 자기 도메인의 인증서를 받을 수 있다. 그리고 어디에 접속했는지는 숨겨지지 않는다 — DNS 조회와 인증서 교환 과정에서 도메인이 노출된다.

서버에 저장된 뒤의 안전도 별개다. HTTPS는 이동 중만 지킨다. 비밀번호를 평문으로 저장하는 서버는 HTTPS를 써도 털린다.

면접에서는 대칭키와 비대칭키를 왜 섞어 쓰는지로 들어온다. 비대칭키는 느려서 데이터 전체에 쓰기 어렵고, 대칭키는 빠르지만 키를 안전하게 건네줄 방법이 없다. 그래서 비대칭키로 대칭키만 주고받고 이후는 대칭키로 간다.
```

## #30 격리 수준을 올리면 무엇을 잃는가?
`데이터베이스`

```
동시성을 잃는다. 위로 올라갈수록 막아주는 현상이 늘지만 그만큼 잠금을 오래 넓게 쥔다. 무엇을 막고 싶은지가 아니라 무엇을 견딜 수 있는지로 고른다.

| 수준 | 막아주는 것 | 대가 |
| --- | --- | --- |
| Read Committed | 커밋 안 된 값 읽기 | 같은 질의가 두 번 다를 수 있다 |
| Repeatable Read | 읽은 행이 중간에 바뀌는 것 | 없던 행이 끼어드는 것은 못 막는다 |
| Serializable | 전부 | 충돌 시 트랜잭션이 취소된다 |

기본값은 대개 Read Committed다. 대부분의 화면은 조금 어긋난 값을 견딘다. 잔액을 읽어 검사하고 쓰는 자리처럼 읽은 값을 근거로 판단할 때만 위로 올린다.

올리는 것 말고 다른 길도 있다. `select ... for update`로 그 한 줄만 잠그거나, 버전을 두고 커밋 때 확인하는 방식이다. 범위를 좁게 잡으면 수준을 올리지 않고도 같은 것을 지킬 수 있다.

면접에서는 Serializable이 어떻게 구현되는지로 들어온다. 전부 줄 세우는 것이 아니라 충돌을 감지해 한쪽을 취소하는 방식이다. 그래서 애플리케이션에 재시도 코드가 있어야 한다.
```

## #34 이진 탐색 트리가 한쪽으로 치우치면 무엇이 문제인가?
`자료구조 · 알고리즘`

```
연결 리스트가 된다. 탐색이 절반씩 줄어든다는 전제가 깨져서 O(log n)이 O(n)으로 내려앉는다. 정렬된 데이터를 순서대로 넣으면 실제로 이 모양이 나온다.

| 상태 | 높이 | 탐색 |
| --- | --- | --- |
| 균형 잡힌 트리 | `log n` | `O(log n)` |
| 한쪽으로 치우친 트리 | `n` | `O(n)` |

그래서 스스로 균형을 잡는 트리를 쓴다. 넣거나 지울 때 높이 차이를 확인하고 회전으로 맞춘다. 회전 비용이 붙지만 최악을 O(log n)으로 묶는 값이다.

해시 테이블과 갈리는 지점은 순서다. 해시는 단건 조회가 더 빠르지만 범위 질의와 정렬 순회를 못 한다. "20에서 30 사이"를 물어야 하면 트리 쪽이다.

데이터베이스 인덱스가 이진 트리 대신 B-트리를 쓰는 이유도 여기 있다. 디스크는 블록 단위로 읽으므로 한 노드에 키를 많이 담아 높이를 낮추는 편이 유리하다.
```

## #35 스프링 빈이 싱글톤인 것이 언제 문제가 되는가?
`프레임워크`

```
빈이 상태를 들고 있을 때다. 인스턴스가 하나뿐이라 모든 요청이 같은 필드를 공유한다. 한 요청이 써 넣은 값을 다른 요청이 읽는다.

| 두는 자리 | 공유 범위 | 안전한가 |
| --- | --- | --- |
| 빈의 필드 | 애플리케이션 전체 | 아니다. 요청끼리 섞인다 |
| 메서드 지역 변수 | 호출 하나 | 안전하다 |
| ThreadLocal | 스레드 하나 | 반납을 빠뜨리면 샌다 |

가장 흔한 사고는 빈에 사용자 정보를 담아두는 것이다. 테스트에서는 요청이 하나씩 들어와 안 드러나고, 동시 접속이 생기는 순간 남의 데이터가 보인다.

해법은 상태를 빈 밖으로 빼는 것이다. 필요한 값은 인자로 넘기고, 빈은 동작만 들고 있게 한다. 스코프를 요청 단위로 바꾸는 방법도 있지만 대개 마지막 수단이다.

면접에서는 왜 기본이 싱글톤인지로 들어온다. 대부분의 빈이 상태 없는 서비스라 하나면 충분하다. 요청마다 만들면 생성 비용과 GC 부담이 그대로 늘어난다.
```

## #36 캐시를 지우는 일이 어려운 이유는?
`아키텍처 · 분산시스템`

```
언제 지워야 하는지를 캐시가 모르기 때문이다. 원본이 바뀐 사실은 쓰기 쪽에서만 아는데, 캐시는 읽기 쪽에 있어서 그 소식이 저절로 오지 않는다.

| 방식 | 언제 지우나 | 약한 곳 |
| --- | --- | --- |
| TTL | 시간이 지나면 | 그 사이에는 옛 값이 나간다 |
| 쓰기 때 삭제 | 원본을 바꿀 때 같이 | 삭제가 실패하면 계속 옛 값 |
| 쓰기 때 갱신 | 원본과 함께 새 값으로 | 두 곳이 어긋날 틈이 생긴다 |

어느 쪽이든 원본과 캐시라는 두 저장소를 하나의 트랜잭션으로 못 묶는다. 그래서 완전한 일관성이 아니라 어긋나는 시간을 얼마나 짧게 두느냐의 문제가 된다.

더 성가신 것은 무엇을 지워야 하는지다. 상품 하나가 바뀌면 그 상품 캐시만이 아니라 그것이 들어간 목록·검색 결과·집계까지 낡는다. 의존 관계가 코드에 흩어져 있으면 빠뜨린다.

실무에서는 TTL을 기본으로 깔고 중요한 것만 쓰기 시점에 지운다. 지우기를 빠뜨려도 시간이 지나면 스스로 낫는 구조를 바닥에 두는 것이다.
```

## #37 리렌더링이 필요 이상으로 도는 이유는?
`프론트엔드`

```
렌더마다 새 값이 만들어지기 때문이다. 객체와 함수는 내용이 같아도 참조가 달라서, 비교하는 쪽은 매번 바뀐 것으로 본다.

| 무엇을 넘기나 | 렌더마다 | 결과 |
| --- | --- | --- |
| 문자열·숫자 | 같은 값 | 다시 안 그린다 |
| 인라인 객체·배열 | 새 참조 | 매번 다시 그린다 |
| 인라인 함수 | 새 참조 | 매번 다시 그린다 |

부모가 다시 그려지면 자식도 따라 그려지는 것이 기본이다. 대부분은 그래도 싸서 문제가 안 된다. 목록이 길거나 자식이 무거울 때만 비용이 눈에 띈다.

그때 쓰는 것이 메모다. 자식을 `memo`로 감싸고 넘기는 값을 고정한다. 다만 감싸기만 하고 인라인 객체를 계속 넘기면 비교만 늘고 효과는 없다.

메모를 먼저 뿌리는 것은 대개 손해다. 비교에도 값이 들고 코드가 읽기 어려워진다. 프로파일러로 실제 느린 곳을 찾은 뒤에 붙인다.
```

## #42 데몬 프로세스는 왜 세션 리더로 지정되지 않는가?
`운영체제`

```
세션 리더만 제어 터미널을 획득할 수 있어서다. 리더가 아니면 터미널을 다시 붙잡을 일이 없어 터미널이 끊겨도 신호를 받지 않는다.

| 실행 형태 | 터미널 관계 |
| --- | --- |
| 터미널 세션 | 사용자 로그인, 쉘로 제어 |
| 데몬 프로세스 | 세션 리더가 아니며, 제어 터미널 없음 |

터미널이 끊기면 SIGHUP은 세션 리더에게 간다. 로그아웃할 때 셸이 자기 작업들에 SIGHUP을 보내기도 한다. 데몬은 새 세션을 만든 뒤 다시 fork해 리더가 아닌 자식으로 남는다.

첫 자식이 `setsid()`를 부르면 새 세션의 리더이자 새 프로세스 그룹의 리더가 되면서 제어 터미널이 떨어진다. 여기서 한 번 더 fork하면 최종 데몬은 리더가 아니라 터미널을 다시 획득할 수 없다.
```

## #43 데이터베이스 옵티마이저에서 서브쿼리 언네스팅의 정의와 발생 조건은 무엇인가?
`데이터베이스`

```
서브쿼리 언네스팅은 중첩된 서브쿼리를 평탄화하여 조인 문으로 변환하는 최적화 기술이며, 옵티마이저가 조인 방식의 집합 처리가 필터링보다 비용이 낮다고 판단할 때 발생한다.

| 구분 | 서브쿼리 유지 (필터링) | 서브쿼리 언네스팅 (조인) |
| --- | --- | --- |
| 수행 방식 | 메인 쿼리 행마다 반복 실행 | 조인 기법(Hash/NL)으로 일괄 처리 |
| 최적화 | 드라이빙 집합 변경 불가 | 조인 순서 및 기법 자유롭게 선택 |

위 표처럼 언네스팅을 거치면 서브쿼리가 메인쿼리와 동등한 조인 대상이 된다. 이에 따라 옵티마이저는 조인 순서 변경이나 해시 조인 등 다양한 최적화 선택지를 얻는다.

주로 `IN`·`EXISTS`가 세미 조인으로, `NOT IN`·`NOT EXISTS`가 안티 조인으로 변환될 수 있을 때 적용된다. 상관 서브쿼리이더라도 서브쿼리의 조인 조건이 메인 쿼리의 키와 동등하게 연결될 수 있으면 언네스팅 대상이 된다.

다만 서브쿼리의 결과가 1:N 관계일 때 단순 조인으로 변환하면 메인 쿼리의 결과 집합이 부풀어 오를 수 있다. 따라서 옵티마이저는 유일성 검증이나 집계 작업을 거쳐 데이터 중복을 방지한다.
```

## #44 데이터베이스 옵티마이저에서 서브쿼리 언네스팅과 뷰 포스팅(View Merging)의 차이점은 무엇인가?
`데이터베이스`

```
서브쿼리 언네스팅은 WHERE절 등의 서브쿼리를 메인 쿼리와의 조인 형태로 변환하는 기법이고, 뷰 병합(View Merging)은 FROM절의 뷰 블록을 메인 쿼리와 하나로 병합하는 기법이라는 차이가 있다.

| 기준 | 서브쿼리 언네스팅 | 뷰 병합 (View Merging) |
| --- | --- | --- |
| 변환 대상 | WHERE/HAVING절 서브쿼리 | FROM절 인라인 뷰 및 뷰 |
| 변환 방식 | 서브쿼리를 메인 조인문으로 변환 | 뷰의 쿼리 블록을 메인 쿼리에 병합 |
| 주요 목적 | 서브쿼리의 반복 수행 방지 | 불필요한 중간 집합 생성 방지 |

이 도식은 두 최적화 기법이 다루는 SQL 위치와 변환 방식을 보여준다. 언네스팅은 서브쿼리가 필터 조건처럼 매번 반복 실행되는 것을 막아 해시 조인 등을 활용할 수 있게 돕는다.

반면 뷰 병합은 FROM절 인라인 뷰의 쿼리 블록을 메인 쿼리로 흡수한다. 이를 통해 불필요한 임시 테이블 생성이나 메인 쿼리와의 중복 검색을 줄인다.

두 기법 모두 옵티마이저가 쿼리 블록을 단순화하여 최적화 공간을 넓히는 기법이다. 하지만 작동하는 대상절과 조인 구조 생성 방식에서 명확히 구분된다.
```

## #49 데이터베이스에서 EXISTS 서브쿼리와 IN 서브쿼리를 조인으로 변환할 때 발생하는 차이점은 무엇인가?
`데이터베이스`

```
서브쿼리에 중복 데이터가 있을 때 일반 조인으로 변환하면 결과 행이 늘어나는 문제와 NULL 값 평가 메커니즘의 차이다.

| 기준 | IN / EXISTS 서브쿼리 | 일반 INNER JOIN 변환 |
| --- | --- | --- |
| 결과 건수 | 메인 테이블 행 수 유지 | 서브쿼리 중복 시 행 수 증가 |
| NULL 처리 | IN은 비교 대상에 NULL이 있으면 UNKNOWN, EXISTS는 행 존재만 검사 | ON 조건 절칙에 따라 평가 |

IN과 EXISTS는 조건을 만족하는 행이 있는지 확인하는 세미 조인(Semi-Join)으로 동작한다. 따라서 서브쿼리에 중복 데이터가 있어도 메인 테이블의 결과 행이 늘어나지 않는다. 반면 일반 INNER JOIN으로 변환하면 1:N 관계에 의해 결과 수가 부풀어 오른다.

중복 뻥튀기를 막으려면 조인 변환 시 DISTINCT나 GROUP BY를 명시해야 한다. 그러나 최신 RDBMS 옵티마이저는 IN과 EXISTS를 내부적으로 세미 조인 알고리즘으로 자동 최적화하므로 무조건 조인으로 바꿀 필요는 없다.

부정 조건인 NOT IN을 변환할 때는 NULL 처리를 조심해야 한다. NOT IN 서브쿼리에 NULL이 섞여 있으면 결과가 전부 비어버리지만, NOT EXISTS나 LEFT OUTER JOIN 변환은 NULL을 무시하고 정상 평가한다.
```

## #50 데이터베이스에서 ANTI JOIN과 SEMI JOIN의 차이점은 무엇인가?
`데이터베이스`

```
SEMI JOIN은 서브쿼리 조건에 일치하는 메인 테이블 행만 반환하고, ANTI JOIN은 일치하지 않는 행만 반환하는 차이점이 있다.

| 기준 | SEMI JOIN | ANTI JOIN |
| --- | --- | --- |
| 추출 조건 | 우측에 존재함 (`EXISTS`) | 우측에 존재하지 않음 (`NOT EXISTS`) |
| 결과 행 | 매칭되는 메인 테이블 행 | 매칭 없는 메인 테이블 행 |
| 주요 용도 | `IN`, `EXISTS` 최적화 | `NOT IN`, `NOT EXISTS` 최적화 |

두 조인 모두 우측 테이블 데이터를 메인 결과 집합에 결합하지 않고 일치 여부만 검장한다.

두 방식 모두 조건이 만족되는 순간 우측 테이블 탐색을 멈춘다. 일반 INNER JOIN처럼 중복 행이 늘어나지 않아서 별도의 `DISTINCT` 연산 없이도 메인 테이블의 원본 고유성을 유지한다.

면접에서는 ANTI JOIN 사용 시 `NULL` 처리에 관한 주의점을 자주 묻는다. 우측 테이블 컬럼에 `NULL`이 존재하면 `NOT IN` 서브쿼리가 ANTI JOIN으로 변환될 때 전체 결과가 빈 집합으로 변할 수 있다.
```

## #52 분산 시스템에서 CAP 중 무엇을 포기하게 되는가?
`아키텍처 · 분산시스템`

```
가용성이나 일관성 중 하나다. 네트워크가 끊기는 일은 고를 수 있는 것이 아니라 일어나는 것이라, 분단 내성은 사실상 전제다.

| 속성 | 분단 시 의미 |
| --- | --- |
| 분단 내성 (P) | 네트워크는 끊긴다. 고르는 것이 아니다 |
| 일관성 (C) | 끊긴 동안 응답을 막는다 |
| 가용성 (A) | 끊긴 동안 옛 값이라도 답한다 |

그래서 실제 선택은 CP냐 AP냐다. 결제 잔액은 틀린 값을 주느니 막는 편이 낫고, 상품 조회수는 조금 틀려도 답하는 편이 낫다.

오해가 잦은 지점이 있다. 셋 중 둘을 항상 고른다는 뜻이 아니다. 분단이 없는 평상시에는 일관성과 가용성을 함께 지킬 수 있다.

면접에서는 PACELC로 한 단계 더 들어온다. 분단이 없을 때도 지연과 일관성 사이에서 골라야 한다는 확장이다.
```

```
객체는 여러 스레드가 공유할 수 있어 힙에 둔다. 호출 프레임은 스레드마다 독립된 실행 상태라 각 JVM 스택에 둔다.

| 기준 | 공유 영역 | 스레드별 영역 |
| --- | --- | --- |

프레임에는 지역 변수, 피연산자 스택, 반환 정보가 있다. 메서드가 끝나면 프레임이 사라져 별도 GC가 필요 없다.

힙의 객체는 참조가 끊겨도 바로 사라지지 않는다. GC가 도달 불가능하다고 판단한 뒤 회수한다.

메서드 영역은 명세상의 공유 영역이다. HotSpot은 클래스 메타데이터를 네이티브 메모리의 Metaspace에 둔다.
```

## #64 수집기는 처리량과 지연 중 무엇으로 고르는가?
`언어 · 런타임`

```

| 기준 | Parallel GC | ZGC |
| --- | --- | --- |

ZGC는 표시와 재배치 대부분을 동시에 수행한다. 짧은 정지를 목표로 하지만 장벽 비용과 충분한 힙 여유가 필요하다.

G1은 리전 단위로 수집해 처리량과 정지 목표를 절충한다. 선택 전 운영과 같은 부하에서 p99 지연, 처리량, GC CPU를 측정한다.
```

## #73 volatile은 무엇을 보장하고 놓치는가?
`언어 · 런타임`

```
volatile 쓰기는 뒤따르는 같은 변수의 읽기보다 먼저 일어난다. 해당 접근을 경계로 가시성과 재정렬 제약을 제공하지만 복합 연산은 원자화하지 않는다.

| 기준 | volatile | synchronized |
| --- | --- | --- |
| 가시성·순서 | 보장한다 | 보장한다 |
| 복합 연산 원자성 | 보장하지 않는다 | 같은 모니터로 보호할 때 보장한다 |

한 스레드가 volatile 변수에 쓰기 전에 수행한 일반 쓰기도 그 값을 읽은 스레드에 보인다. 이 happens-before 관계가 다른 상태의 전달까지 만든다.

단순 상태 플래그와 완전히 생성된 객체 참조의 게시에는 적합하다. 이중 확인 잠금의 인스턴스 참조에도 필요하다.

count++는 읽기, 계산, 쓰기의 세 단계라 volatile이어도 갱신을 잃을 수 있다. 경쟁 갱신에는 AtomicInteger나 잠금이 필요하다.
```

## #79 let도 끌어올려지는데 왜 바로 읽지 못하는가?
`언어 · 런타임`

```
let과 const의 바인딩은 스코프 시작 때 만들어지지만 선언문을 평가하기 전에는 초기화되지 않는다. 이 시간적 사각지대에서 읽으면 ReferenceError가 난다.

| 기준 | var | let·const |
| --- | --- | --- |
| 실행 전 상태 | undefined로 초기화 | 미초기화 |
| 선언 전 읽기 | undefined | ReferenceError |
| 블록 경계 | 무시 | 적용 |

호이스팅은 소스 코드를 실제로 위로 옮기는 동작이 아니다. 실행 컨텍스트를 만들 때 선언을 등록하고 각 종류의 초기화 시점을 달리하는 설명 모델이다.

함수 선언은 본문까지 일찍 바인딩되어 선언 앞에서 호출할 수 있다. 함수 표현식은 담긴 변수의 초기화 규칙을 따르므로 var와 let의 차이가 그대로 드러난다.

시간적 사각지대의 let을 typeof로 확인해도 ReferenceError가 난다. 아예 선언되지 않은 이름에 typeof를 썼을 때 undefined가 나오는 것과 다르다.
```

## #80 같은 함수를 불렀는데 this가 달라지는 이유는?
`언어 · 런타임`


## #82 널 검사를 했는데도 안전 호출이 필요한 때는?
`언어 · 런타임`

```

| 기준 | 스마트 캐스트 가능 | 안전 호출 필요 |

Java에서 온 플랫폼 타입은 널 가능성이 타입에 확정되지 않는다. 경계에서 어노테이션과 검증으로 불확실성을 좁혀야 내부의 널 안전성이 유지된다.

안전 호출을 길게 잇는 방식은 실패 원인을 숨길 수 있다. 반드시 있어야 하는 값은 초기에 검사하고 의미 있는 오류로 바꾸는 편이 낫다.
```

```
| 대입 결과 | 값 자체 복사 | 같은 객체의 참조 복사 |
| 변경 영향 | 값 필드는 분리 | 별칭을 통해 공유 |
| 동등성 | 값 비교가 자연스러움 | 값·정체성 구분 |

이 구분은 스택과 힙의 저장 위치와 같지 않다. 값도 최적화나 캡처에 따라 힙에 놓일 수 있고 참조 값 자체는 스택 프레임에 놓일 수 있다.

Java처럼 인자를 항상 값으로 전달하는 언어도 객체 참조 값을 복사해 넘긴다. 호출자는 같은 객체의 변경을 보지만 자신의 변수 재대입은 영향받지 않는다.

가변 참조 객체는 별칭과 동시성 위험을 키운다. 불변 객체와 방어적 복사는 공유 위험을 줄이지만 새 객체 생성과 복사 비용을 낸다.
```

## #86 회전 뒤에도 남겨야 할 상태는 어디에 두는가?
`모바일`

```
다시 계산할 화면 데이터는 ViewModel에 둔다. 선택값과 입력처럼 복원에 필요한 작은 UI 상태는 저장 상태에 둔다. 영구 데이터는 저장소에 둔다.

| 기준 | ViewModel | 저장 상태 |
| --- | --- | --- |
| 구성 변경 | 같은 인스턴스를 잇는다 | 값으로 복원한다 |
| 프로세스 종료 | 사라진다 | 조건부로 복원한다 |

회전과 창 크기 변경은 Activity를 재생성할 수 있다. ViewModel은 이 재생성 동안 메모리 데이터를 유지한다.

시스템이 프로세스를 죽이면 ViewModel도 사라진다. 이때 화면을 다시 만드는 최소 키만 Bundle 기반 저장 상태에서 복원한다.

큰 목록이나 비즈니스 데이터는 저장 상태에 넣지 않는다. ID나 검색어만 남기고 데이터 계층에서 다시 읽는다.
```

## #87 화면 상태를 둘 때 두 수단을 어떻게 나누는가?
`모바일`

```
화면 로직과 계산된 UI 상태는 ViewModel에 둔다. 프로세스 재생성 뒤 화면을 복구할 최소 키만 SavedStateHandle에 둔다.

| 기준 | ViewModel | SavedStateHandle |
| --- | --- | --- |
| 구성 변경 | 메모리에 유지한다 | 값도 유지된다 |
| 프로세스 종료 | 인스턴스가 사라진다 | 저장된 값을 복원한다 |

SavedStateHandle도 Bundle 기반이다. 큰 객체 대신 항목 ID와 필터처럼 다시 데이터를 만들 단서만 저장한다.

강제 종료나 최근 앱에서 태스크를 지우면 복원이 보장되지 않는다. 반드시 남아야 하는 데이터는 데이터베이스 같은 영구 저장소에 둔다.
```

## #115 선언한 너비와 실제 크기가 왜 달라지는가?
`프론트엔드`

```

전체에 box-sizing: border-box를 적용하면 레이아웃 계산이 직관적이다. 다만 콘텐츠 영역은 패딩과 테두리가 늘수록 줄어든다.
```

## #116 한 축 배치와 두 축 배치는 어떻게 구분하는가?

```
| 기준 | 시맨틱 요소 | div 흉내 |
| --- | --- | --- |
```

## #125 응답 특성에 따라 캐시 방식을 어떻게 고르는가?
`프론트엔드`

```

| 기준 | Cache First | Network First |
```

## #126 렌더링 방식은 어떤 요구로 결정하는가?
`프론트엔드`

```

| --- | --- | --- |
| 정적 콘텐츠 | SSG | 미리 생성 |
```

## #137 외래 키 변경은 어느 쪽에서 반영해야 하는가?
`프레임워크`

```
연관관계의 주인 쪽을 바꿔야 한다. 주인은 외래 키나 조인 테이블 값을 쓰는 매핑이며 반대편만 바꾸면 SQL에 반영되지 않는다.

| 기준 | 주인 쪽 | mappedBy 쪽 |
| --- | --- | --- |
| 외래 키 SQL | 반영한다 | 반영하지 않는다 |
| 매핑 표시 | mappedBy 없음 | mappedBy 지정 |
| 객체 탐색 | 가능하다 | 가능하다 |

다대일과 일대다 양방향 관계에서는 외래 키를 가진 다대일 쪽이 보통 주인이다. 주인이라는 말은 도메인상 중요도가 아니라 쓰기 권한을 뜻한다.

객체 그래프의 일관성을 위해 양쪽 참조를 함께 맞춘다. 편의 메서드가 컬렉션과 참조를 한 번에 갱신하면 같은 트랜잭션 안의 오해를 줄인다.

cascade와 orphanRemoval은 주인 여부와 별도 규칙이다. 하나는 연산 전파를 정하고 다른 하나는 고아 삭제를 정한다.
```

## #138 즉시 로딩을 기본값처럼 쓰면 왜 위험한가?
`프레임워크`

```
사용하지 않는 연관관계까지 읽어 과조회가 생긴다. 조인이 보장되는 것도 아니어서 보조 쿼리가 반복되면 N+1과 메모리 낭비로 이어진다.

| 기준 | 지연 | 즉시 |
| --- | --- | --- |
| 시점 | 접근할 때 | 주 객체 조회 때 |
| 통제 | 용도별 선택 | 항상 적용 |
| 위험 | 세션 밖 접근 | 과조회·N+1 |

기본 매핑은 지연 로딩으로 두고 유스케이스마다 fetch join, EntityGraph, 배치 조회를 선택하면 SQL 모양을 의도적으로 통제할 수 있다.

지연 프록시를 영속성 컨텍스트 밖에서 건드리면 초기화에 실패한다. 응답 직렬화가 연관관계를 순회하면 예기치 않은 쿼리도 발생한다.

컬렉션 fetch join은 중복 행을 만들고 페이징을 깨뜨릴 수 있다. 먼저 루트 식별자를 페이지로 구한 뒤 별도 조회하는 방식도 검토한다.
```

## #139 동적 조건이 많을 때 문자열 쿼리는 왜 약한가?

```
| 기준 | 문자열 | QueryDSL |
| --- | --- | --- |
| 조건 | 문자열 결합 | 식 조합 |

선택 조건을 작은 BooleanExpression으로 나누면 필요한 식만 조합할 수 있다. 공통 조건도 재사용해 조회 의도를 읽기 쉽게 만든다.

타입 안전성이 SQL의 정확성과 성능까지 보장하지는 않는다. 조인 수, 인덱스, fetch join, 실행 계획은 생성된 쿼리로 따로 검증해야 한다.

```

## #143 수신자는 여유 있는데 전송이 느린 이유는?
`네트워크`

```
수신 창이 넉넉해도 네트워크가 혼잡하면 송신자는 혼잡 창을 줄인다. 실제 전송량은 두 창 중 작은 값으로 제한된다.

| 기준 | 흐름 제어 | 혼잡 제어 |
| --- | --- | --- |
| 보호 대상 | 수신자 버퍼 | 네트워크 |

송신자는 알고리즘에 따라 손실, ECN, 지연·전달률 같은 신호로 `cwnd`를 조절한다. 손실 뒤 속도가 크게 떨어지고 서서히 회복되는 이유다.
```

## #145 신뢰성보다 지연을 우선할 기준은?
`네트워크`

```
일부 손실을 허용하고 최신 데이터가 더 중요할 때 UDP가 맞다. 순서와 재전송을 애플리케이션이 직접 설계할 수 있어야 한다.

| 기준 | TCP | UDP |
| --- | --- | --- |
| 전달 | 순서와 재전송 보장 | 보장 없음 |
| 지연 | 손실 시 대기 | 손실을 건너뛸 수 있음 |
| 상태 | 연결 유지 | 연결 상태 없음 |

음성 통화와 게임은 늦게 도착한 과거 패킷의 가치가 낮다. 재전송을 기다리기보다 손실을 보간하고 다음 데이터를 처리하는 편이 낫다.

DNS처럼 요청과 응답이 작고 짧은 경우도 연결 비용을 피할 수 있다. 다만 크기가 커지면 분할과 재시도 전략이 필요하다.

UDP가 곧 빠름을 뜻하지는 않는다. 혼잡 제어와 인증, 순서 보장이 필요하면 직접 구현하거나 QUIC 같은 검증된 프로토콜을 써야 한다.
```

## #146 재검증 없이 응답을 써도 되는 기준은?
`네트워크`

```
저장된 응답이 `max-age` 안에 있으면 재검증 없이 쓸 수 있다. 기간이 지났다면 검증자로 서버에 변경 여부를 물어야 한다.

| 지시자 | 저장 | 재사용 조건 |
| --- | --- | --- |
| `max-age` | 가능 | 신선한 동안 즉시 사용 |
| `no-cache` | 가능 | 매번 재검증 |
| `no-store` | 금지 | 재사용 불가 |

`no-cache`는 저장 금지가 아니다. 캐시에 보관해도 되지만 사용할 때마다 `ETag`나 `Last-Modified`로 확인하라는 뜻이다.

변경이 없으면 서버는 본문 없이 `304 Not Modified`를 보낸다. 전송량은 줄지만 네트워크 왕복은 남는다.

해시가 포함된 정적 파일명에는 긴 `max-age`와 `immutable`이 잘 맞는다. 개인화 응답은 `private`과 `Vary`를 함께 검토해야 한다.
```

## #147 실패 응답 코드는 무엇을 기준으로 고르는가?
`네트워크`

```
요청이나 인증·권한·사용량 제한 같은 클라이언트 측 조건 때문에 처리할 수 없으면 4xx를 쓴다. 서버가 정상 요청을 처리하지 못하면 5xx를 쓴다. 원인과 재시도 가능성을 코드에 담아야 한다.

| 기준 | 4xx | 5xx |
| --- | --- | --- |
| 책임 | 요청 또는 권한 | 서버 처리 |
| 예 | 400, 404, 409 | 500, 503, 504 |

400은 요청 형식이 잘못된 경우다. 401은 인증이 필요하고 403은 신원을 알아도 권한이 없다. 존재를 숨기려면 404를 택할 수도 있다.

409는 현재 자원 상태와 충돌할 때 적합하다. 문법은 맞지만 필드 검증에 실패한 요청은 API 규약에 따라 400 또는 422로 일관되게 처리한다.

503은 일시적 과부하나 점검을 알린다. `Retry-After`를 주면 재시도 시점을 안내할 수 있다. 내부 오류를 모두 200으로 감싸면 중간 장비가 실패를 오해한다.
```

## #150 중계 서버의 주체는 어떻게 구분하는가?
`네트워크`

```
클라이언트를 대신하면 포워드 프록시다. 서버를 대신하면 리버스 프록시다. 누구의 위치와 신원을 감추고 정책을 적용하는지가 구분 기준이다.

| 주요 역할 | 접근 통제, 익명화 | 분산, TLS 종료 |

포워드 프록시는 외부 서버가 원래 클라이언트 대신 프록시를 보게 한다. 사내 인터넷 통제와 캐시, 우회 접속에 활용한다.

리버스 프록시는 공개 진입점을 하나로 만들고 내부 서버를 숨긴다. 요청 라우팅과 로드 밸런싱, 압축, 인증 같은 공통 기능을 맡는다.
```

## #155 연결 리스트가 배열보다 항상 삽입이 빠른가?
`자료구조 · 알고리즘`

```
항상 빠르지는 않으며, 삽입하려는 위치를 찾는 탐색 비용에 따라 더 느려질 수 있다. 맨 앞이나 맨 뒤에 삽입할 때만 연결 리스트가 더 빠르다.

배열과 연결 리스트의 연산별 시간 복잡도를 비교하면 다음과 같다.

| 연산 | 배열 (Array) | 연결 리스트 (Linked List) |
| --- | --- | --- |
| 특정 인덱스 탐색 | O(1) | O(N) |
| 특정 위치에 삽입/삭제 | O(N) | O(1) (노드 포인터 확인 시) |

연결 리스트는 임의의 위치에 삽입할 때 먼저 그 위치까지 노드를 타고 이동해야 한다. 탐색에 O(N)의 시간이 걸리므로, 삽입 자체는 O(1)이라도 총 시간 복잡도는 O(N)이 된다.

반면 배열은 탐색은 O(1)로 빠르지만 삽입 시 뒤의 원소들을 한 칸씩 밀어내는 쉬프트 비용 때문에 O(N)이 걸린다. 결국 데이터가 무작위로 위치할 때는 두 자료구조 모두 한계가 있다.

데이터의 삽입과 삭제가 양 끝에서만 빈번하게 일어난다면 연결 리스트가 배열보다 압도적으로 유리하다. 대표적으로 큐(Queue)를 구현할 때 연결 리스트가 쓰인다.
```

## #156 스택과 큐는 각각 어떤 상황에서 선택해야 하는가?
`자료구조 · 알고리즘`

```
스택은 가장 최근 데이터를 먼저 처리해야 할 때 쓰고, 큐는 들어온 순서대로 데이터를 처리해야 할 때 선택한다.

| 기준 | 스택 (Stack) | 큐 (Queue) |
| --- | --- | --- |
| 입출력 방식 | LIFO (후입선출) | FIFO (선입선출) |
| 주요 용도 | 되돌리기, 재귀 처리 | 작업 대기열, 버퍼 |
| 알고리즘 | 깊이 우선 탐색 (DFS) | 너비 우선 탐색 (BFS) |

위 표는 두 자료구조의 핵심 동작 방식과 쓰임새 차이를 보여준다. 스택은 입력된 역순으로 돌아가는 이력 관리에 유용하며, 큐는 유입된 요청을 순서대로 소화하는 완충 지대에 알맞다.

스택은 함수 호출(Call Stack)이나 실행 취소(Undo)처럼 직전의 상태를 기억해야 하는 곳에 필수적이다. 반면 큐는 이메일 발송 대기열이나 프린터 인쇄 작업처럼 순차적인 처리가 보장되어야 하는 비동기 시스템의 기초가 된다.

면접에서는 실무적인 한계도 자주 묻는다. 스택은 메모리 한계로 인한 오버플로우를 주의해야 하고, 큐는 데이터를 꺼낼 때 발생하는 배열 내 요소 이동 비용을 줄이기 위해 원형 큐나 연결 리스트 구조를 고민해야 한다.
```

## #157 해시 충돌 발생 시 해결 방법은 무엇인가?
`자료구조 · 알고리즘`

```
체이닝과 개방 주소법을 사용한다. 체이닝은 연결 리스트로 데이터를 엮고, 개방 주소법은 빈 공간을 찾아 저장한다.

| 기준 | 체이닝 | 개방 주소법 |
| --- | --- | --- |
| 저장 방식 | 외부 리스트 연결 | 내부 빈 슬롯 탐색 |
| 성능 저하 | 리스트 길어질 때 | 클러스터링 발생 시 |
| 메모리 사용 | 추가 메모리 필요 | 미리 할당된 공간 사용 |

체이닝은 삭제가 쉽고 테이블이 꽉 차지 않는다. 하지만 리스트가 길어지면 탐색 시간이 O(n)으로 늘어난다. 최근 Java의 HashMap은 일정 길이 이상이면 트리로 변환해 이를 해결한다.

개방 주소법은 추가 메모리가 없지만, 데이터가 뭉치는 클러스터링 현상이 발생한다. 선형 탐색은 인접한 빈칸을 찾으므로 뭉침이 심해 효율이 떨어진다.

해시 함수가 균등하게 분산시키지 못하면 충돌이 잦아진다. 이 경우 시간 복잡도가 최악의 경우 O(n)까지 떨어진다.
```

## #158 일반 이진트리 대신 이진탐색트리를 사용하는 이유는 무엇인가?
`자료구조 · 알고리즘`

```
정렬된 구조를 유지하여 특정 값을 빠르게 찾기 위해서다. 부모 노드를 기준으로 작은 값은 왼쪽, 큰 값은 오른쪽에 배치하여 탐색 범위를 지속해서 줄인다.

| 구분 | 이진트리 | 이진탐색트리 |
| --- | --- | --- |
| 노드 배치 | 규칙 없음 | 왼쪽 < 부모 < 오른쪽 |
| 평균 탐색 | O(N) | O(log N) |

표에서 보듯 이진탐색트리는 탐색 시 매 단계마다 비교 대상을 절반으로 줄여 평균 O(log N) 시간에 데이터에 접근한다. 단순 이진트리는 모든 노드를 확인해야 해 O(N)이 걸린다.

다만 정렬된 데이터가 순서대로 들어오면 한쪽으로 치우친 편향 트리가 된다. 이 경우 선형 탐색과 다를 바 없어 최악의 경우 O(N)으로 성능이 저하된다.

이러한 한계를 극복하기 위해 실무에서는 높이 균형을 자동으로 맞추는 Red-Black 트리나 AVL 트리 같은 자발적 균형 트리를 활용한다.
```

## #159 그래프를 인접 행렬과 인접 리스트 중 어떤 방식으로 구현해야 하는가?
`자료구조 · 알고리즘`

```
간선의 밀도와 탐색 연산의 주된 목적에 따라 결정한다. 간선이 많은 밀집 그래프는 인접 행렬을, 간선이 적은 희소 그래프는 인접 리스트를 선택하는 것이 유리하다.

| 기준 | 인접 행렬 | 인접 리스트 |
| --- | --- | --- |
| 공간 복잡도 | **O(V²)** | **O(V + E)** |
| 간선 존재 확인 | **O(1)** | **O(degree(V))** |
| 인접 정점 탐색 | **O(V)** | **O(degree(V))** |

인접 행렬은 2차원 배열을 써서 두 정점 간의 연결 여부를 상수 시간에 확인한다. 정점 수가 많고 간선이 적다면 메모리 낭비가 크다.

인접 리스트는 각 정점에 연결된 정점만 가변 배열이나 연결 리스트로 저장한다. 메모리를 절약하지만 특정 두 정점이 연결되었는지 확인하려면 리스트를 순회해야 한다.

실무나 일반적인 문제 해결에서는 정점 수에 비해 간선 수가 적은 희소 그래프가 많아 인접 리스트를 주로 사용한다.
```

## #160 다익스트라와 벨만-포드 알고리즘은 언제 구분하여 쓰는가?
`자료구조 · 알고리즘`

```
간선의 음수 가중치 존재 여부와 음수 사이클의 유무에 따라 구분하여 쓴다. 음수 가중치가 없다면 다익스트라를 쓰고, 있다면 벨만-포드를 써야 한다.

| --- | --- | --- |
| 음수 가중치 | 허용 안 함 | 허용 |
| 시간 복잡도 | O((V+E) log V) | O(VE) |
| 사이클 감지 | 불가능 | 가능 |

다익스트라는 매번 최단 거리가 가장 짧은 노드를 선택하며 탐색한다. 이미 방문한 노드의 거리는 변하지 않는다고 가정하므로 음수 가중치가 있으면 오동작한다. 대신 우선순위 큐를 사용해 속도가 매우 빠르다.

벨만-포드는 매 단계 모든 간선을 전부 확인하며 거리를 갱신한다. 이 과정을 노드 수만큼 반복하므로 느리지만 음수 가중치를 처리할 수 있다. 마지막 반복에서 값이 또 바뀌면 음수 사이클이 있다고 판단한다.
```

## #162 최소 신장 트리(MST)를 구성하는 알고리즘으로 무엇을 선택하는가?

