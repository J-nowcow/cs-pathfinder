## #9 데이터베이스 커넥션 풀의 적정 크기를 설정할 때 왜 CPU 코어 수를 기준으로 설정하는지 그 이유가 궁금합니다.
`데이터베이스`

앞: 코어 수가 동시에 돌릴 수 있는 CPU 작업 수를 정해 병목을 추정하는 기준이 되기 때문이다. I/O로 대기하는 요청까지 코어 수로 묶이지는 않는다. 코어 수가 적은데 풀 크기만 늘리면 컨텍스트 스위칭 비용만 증가한다.

```
:::stack
풀 크기 시작값 | 코어 수 × 목표 CPU 사용률 × (1 + 대기 시간 / 계산 시간)
병목 지점 | CPU 코어 수. 연산 처리의 실제 한계
:::
```

뒤: DB 서버의 CPU는 쿼리 실행 계획을 짜고 데이터를 연산한다. 풀 크기가 너무 크면 수많은 스레드가 CPU 점유를 위해 경쟁하며 오버헤드가 발생한다.

## #19 setTimeout(0)이 즉시 실행되지 않는 이유는?
`언어 · 런타임`

앞: 콜백이 큐에 들어갈 뿐이고, 지금 돌고 있는 코드가 끝나야 이벤트 루프가 그것을 꺼내기 때문이다. 0은 "지금"이 아니라 "가능한 가장 이른 다음 차례"라는 뜻이다. 게다가 꺼내 가는 큐가 하나도 아니다.

```
:::stack
지금 도는 동기 코드 | 이게 끝나야 아래로 내려간다
마이크로태스크 큐 | Promise.then. 비워질 때까지 전부
매크로태스크 큐 | setTimeout, 이벤트 콜백. 한 번에 하나
:::
```

뒤: 자바스크립트는 한 번에 하나의 콜스택만 돌린다. 루프는 스택이 빌 때까지 아무것도 꺼내지 않는다. 앞선 동기 코드가 100밀리초를 쓰면 setTimeout(0)도 그만큼 밀린다.

## #20 데이터베이스 격리 수준을 높이면 전체 처리량은 어떻게 변화하는가?
`데이터베이스`

앞: 전체 처리량은 감소한다.

```
:::stack
격리 수준 높음 | Serializable
격리 수준 낮음 | Read Uncommitted
:::
```

뒤: 위 도식은 격리 수준의 단계적 구조를 보여준다. 수준이 높아질수록 정밀한 데이터 일관성을 보장하지만, 잠금 범위와 유지 시간이 늘어난다.

## #21 메모리 관점에서 값 타입과 참조 타입의 선택 기준은 무엇인가?
`언어 · 런타임`

앞: 아래 구조는 두 타입이 메모리에 저장되는 물리적 위치의 차이를 나타낸다.

```
:::stack
힙 영역 | 참조 타입의 실제 데이터 (예: 인스턴스, 배열)
스택 영역 | 값 타입의 데이터 직접 저장 / 참조 타입의 주소값(포인터) 저장
:::
```

뒤: 작고 수명이 짧으며 변경할 필요가 없는 데이터는 값 타입으로 선언하여 가비지 컬렉션(GC)의 부담을 줄이는 것이 좋다. 반면, 데이터의 크기가 크거나 시스템 전체에서 동일한 인스턴스를 공유하며 상태를 변경해야 한다면 참조 타입을 선택해야 한다. 이때 참조 타입은 주소만 복사하므로 전달 비용은 저렴하지만, 힙 메모리 관리와 GC 오버헤드가 발생한다는 트레이드오프가 존재한다.

## #24 데드락은 어떤 조건이 모두 모여야 생기는가?
`운영체제`

앞: 네 조건이 동시에 성립할 때다. 하나만 깨도 데드락은 생기지 않는다.

```
:::stack
상호 배제 | 자원을 한 번에 하나만 쓸 수 있다
점유하며 대기 | 하나를 쥔 채로 다른 것을 기다린다
비선점 | 쥔 것을 강제로 뺏을 수 없다
순환 대기 | 기다림이 고리를 이룬다
:::
```

뒤: 실무에서 가장 자주 깨는 것은 마지막이다. 자원에 순서를 매기고 항상 그 순서로만 잡게 하면 고리가 생길 수 없다. 계좌 두 개를 잠글 때 언제나 번호가 작은 쪽부터 잡는 식이다.

## #32 가비지 컬렉션이 멈춤을 만드는 이유는?
`언어 · 런타임`

앞: 살아 있는 객체를 세는 동안 그 관계가 바뀌면 안 되기 때문이다. 세는 중에 애플리케이션이 참조를 바꾸면 이미 확인한 것이 틀려져서, 그 구간만은 실행을 세운다.

```
:::stack
Eden | 새 객체가 여기 태어난다. 대부분 금방 죽는다
Survivor | 한두 번 살아남은 것이 잠시 머문다
Old | 오래 산 것이 승격된다. 여기 청소가 비싸다
:::
```

뒤: 대부분의 객체는 태어나자마자 죽는다. 그래서 젊은 영역만 자주 짧게 치우고 늙은 영역은 가끔 손댄다. 젊은 쪽 청소는 보통 밀리초 단위라 눈에 안 띈다.

## #39 앱이 백그라운드에서 죽는 이유는?
`모바일`

앞: 시스템이 메모리를 회수하기 때문이다. 앞에 보이는 앱을 살리는 것이 우선이라, 안 보이는 프로세스부터 순서대로 거둬간다.

```
:::stack
포그라운드 | 화면에 보인다. 거의 안 죽인다
보이는 상태 | 가려졌지만 살아 있다
서비스 | 백그라운드 작업 중. 상황에 따라 거둔다
캐시된 상태 | 안 보인다. 여기부터 먼저 죽는다
:::
```

뒤: 죽는 것은 사고가 아니라 설계다. 그래서 앱은 언제 죽어도 되도록, 그리고 돌아왔을 때 이어지도록 만들어야 한다.

## #41 TCP 연결 종료 시 TIME_WAIT 상태가 누적되어 포트가 고갈되는 현상을 진단하는 방법은 무엇인가?
`네트워크`

앞: netstat이나 ss 명령어로 TIME_WAIT 상태의 소켓 개수를 세고 local_port_range 한도와 비교하는 것이다.

```
:::stack
소켓 수 계측 | ss -s 또는 netstat -antp | grep TIME_WAIT
포트 한도 확인 | sysctl net.ipv4.ip_local_port_range
에러 로그 진단 | Cannot assign requested address 발생 여부
:::
```

뒤: 시스템에서 사용할 수 있는 에페머럴 포트 범위는 한정되어 있다. TIME_WAIT 소켓 수가 이 포트 범위를 꽉 채우면 새 연결을 맺을 때 EADDRNOTAVAIL 에러가 발생한다.

## #42 데몬 프로세스는 왜 세션 리더로 지정되지 않는가?
`운영체제`

앞: 세션 리더만 제어 터미널을 획득할 수 있어서다. 리더가 아니면 터미널을 다시 붙잡을 일이 없어 터미널이 끊겨도 신호를 받지 않는다.

```
:::stack
터미널 세션 | 사용자 로그인, 쉘로 제어
데몬 프로세스 | 세션 리더가 아니며, 제어 터미널 없음
:::
```

뒤: 터미널이 끊기면 SIGHUP은 세션 리더에게 간다. 로그아웃할 때 셸이 자기 작업들에 SIGHUP을 보내기도 한다. 데몬은 새 세션을 만든 뒤 다시 fork해 리더가 아닌 자식으로 남는다.

## #47 컨테이너 이미지를 최소화해야 하는 이유는 무엇인가?

앞: 공격 표면을 줄여 보안성을 높이고 이미지 크기를 줄여 배포 속도를 높이기 때문이다.

```
:::stack
보안 | 불필요한 셸, 패키지 관리자 제거로 침투 경로 차단
배포 | 레이어 크기 감소로 네트워크 전송 및 풀링 속도 향상
운영 | 취약점 스캔 결과의 노이즈를 줄여 관리 효율 증대
:::
```

뒤: 이미지 내에 셸이나 curl 같은 도구가 많을수록 해커가 침투 후 내부망을 탐색하거나 추가 악성 코드를를 설치하기 쉽다. Distroless 이미지는 실행 파일과 런타임만 포함해 이런 도구를 원본적으로 차단한다.

## #48 useEffect 의존성 배열을 비워두면 언제 실행되는가?
`프론트엔드`

앞: 컴포넌트가 마운트될 때 딱 한 번만 실행된다. 배열에 넣은 값이 변하지 않으면 리액트가 이펙트 함수를 다시 호출하지 않기 때문이다.

```
:::stack
빈 배열 | 마운트 시 1회 실행
값 포함 | 해당 값이 변경될 때 실행
배열 생략 | 매 렌더링마다 실행
:::
```

뒤: 위 도식은 의존성 배열의 상태에 따라 실행 시점이 달라짐을 보여준다. 배열을 비워두면 렌더링과 상관없이 생명주기상 마운트 시점에만 작동한다.

## #52 분산 시스템에서 CAP 중 무엇을 포기하게 되는가?
`아키텍처 · 분산시스템`

앞: 가용성이나 일관성 중 하나다. 네트워크가 끊기는 일은 고를 수 있는 것이 아니라 일어나는 것이라, 분단 내성은 사실상 전제다.

```
:::stack
분단 내성 (P) | 네트워크는 끊긴다. 고르는 것이 아니다
일관성 (C) | 끊긴 동안 응답을 막는다
가용성 (A) | 끊긴 동안 옛 값이라도 답한다
:::
```

뒤: 그래서 실제 선택은 CP냐 AP냐다. 결제 잔액은 틀린 값을 주느니 막는 편이 낫고, 상품 조회수는 조금 틀려도 답하는 편이 낫다.

## #56 메시지 순서는 어디까지 보장되는가?
`아키텍처 · 분산시스템`

앞: 대개 파티션 안에서만이다. 여러 파티션에 흩어진 메시지 사이에는 전역 순서가 없고, 만들려면 병렬 처리를 포기해야 한다.

```
:::stack
같은 파티션 | 넣은 순서대로 읽힌다
다른 파티션 | 순서가 없다. 병렬로 흐른다
전역 순서 | 파티션 하나로 몰아야 한다. 처리량을 잃는다
:::
```

뒤: 그래서 순서가 중요한 것끼리 같은 파티션으로 보낸다. 주문 이벤트를 주문 번호로 나누면 한 주문의 사건들은 순서가 지켜진다.

## #60 호출 시간 제한은 무엇을 기준으로 정하는가?
`아키텍처 · 분산시스템`

앞: 바깥에서 안으로 좁혀 간다. 사용자가 기다릴 수 있는 시간에서 시작해 그 안에 들어가도록 각 단계를 나눈다.

```
:::stack
사용자 응답 3초 | 여기서 시작한다
게이트웨이 2.5초 | 남는 시간에 여유를 뺀다
주문 서비스 2초 | 다시 그 안에서
결제 호출 1초 | 재시도까지 넣어도 들어가야 한다
:::
```

뒤: 안쪽이 바깥쪽보다 길면 안 된다. 그러면 바깥이 이미 포기한 요청을 안쪽이 계속 붙들고 자원을 쓴다.

## #61 게이트웨이를 두면 무엇을 얻고 무엇을 걱정해야 하는가?
`아키텍처 · 분산시스템`

앞: 모든 서비스가 각자 하던 일을 한곳으로 모으는 것을 얻고, 그 한곳이 죽으면 전부 죽는 것을 걱정해야 한다.

```
:::stack
인증·인가 | 서비스마다 구현하지 않아도 된다
요청 제한 | 한곳에서 세야 정확하다
라우팅·집계 | 클라이언트가 서비스 수를 몰라도 된다
:::
```

뒤: 특히 값진 것은 클라이언트가 내부 구조를 모르게 되는 것이다. 서비스를 쪼개거나 합쳐도 바깥 주소는 그대로 둘 수 있다.

## #72 락보다 높은 수준의 도구를 먼저 고르는 이유는?
`언어 · 런타임`

앞: 검증된 원자 연산과 대기 정책을 재사용해 경쟁 조건과 교착 위험을 줄이기 때문이다. 작업 성격에 맞는 가장 높은 수준의 도구를 고른다.

```
:::stack
CompletableFuture | 비동기 결과 조합
ExecutorService | 실행 정책과 작업 분리
BlockingQueue | 생산자·소비자 조절
동시 컬렉션·원자 변수 | 공유 상태 갱신
Lock·동기화 도구 | 임계 구역 제어
:::
```

뒤: 공유 맵의 get 뒤 put은 두 번의 연산이라 경쟁할 수 있다. ConcurrentHashMap의 computeIfAbsent처럼 의도를 한 원자 연산으로 표현해야 한다.

## #77 함수가 끝난 뒤 지역 변수가 남는 이유는?
`언어 · 런타임`

앞: 내부 함수가 지역 변수의 렉시컬 환경을 계속 참조하기 때문이다. 바깥 함수 호출이 끝나도 내부 함수가 살아 있으면 캡처한 바인딩도 유지된다.

```
:::stack
내부 함수 | 실행 코드와 환경 참조를 가진다
렉시컬 환경 | 캡처한 변수 바인딩을 보관한다
참조된 객체 | 도달 가능한 동안 메모리에 남는다
:::
```

뒤: 클로저는 값을 만든 시점의 복사본이 아니라 바인딩을 잡는다. 같은 바인딩을 공유한 함수들은 변경을 함께 본다. let의 블록별 바인딩은 루프 문제를 피한다.

## #85 뷰 바인딩은 왜 onDestroyView에서 비우는가?
`모바일`

앞: Fragment 인스턴스가 백 스택에 남아도 뷰는 먼저 파괴될 수 있기 때문이다. 바인딩을 계속 잡으면 폐기된 뷰가 수집되지 않고 잘못 접근할 수도 있다.

```
:::stack
Fragment 수명 | onCreate부터 onDestroy까지다
View 수명 | onCreateView부터 onDestroyView까지다
:::
```

뒤: 뷰를 갱신하는 관찰은 viewLifecycleOwner에 묶는다. 그러면 뷰가 파괴될 때 관찰도 멈춘다.

## #88 메모리 부족 시 어떤 프로세스부터 종료되는가?
`모바일`

앞: 사용 중인 컴포넌트가 없는 캐시 프로세스부터 종료된다. 가시성과 사용자 영향이 클수록 우선순위가 높아지고 포그라운드 프로세스는 마지막에 보호된다.

```
:::stack
포그라운드 | 사용자가 현재 상호작용한다
가시 | 화면에 보이거나 인지되는 작업이다
서비스 | 시작된 서비스를 수행한다
캐시 | 활성 컴포넌트가 없다
:::
```

뒤: 프로세스 등급은 가장 중요한 활성 컴포넌트에 맞춰진다. 중요한 클라이언트가 바인드한 서비스의 프로세스도 우선순위가 올라간다.

## #92 화면이 닫혔는데 객체가 남는 이유는?

GC Root | 정적 필드나 실행 중 스레드다
싱글턴·콜백 | 화면 객체를 참조한다

:::
```

뒤: 리스너를 등록한 수명에서 해제하고 코루틴과 콜백도 함께 취소한다. UI가 필요 없는 객체에는 Application Context를 사용한다.

## #101 상태 소유자를 잘못 두면 어떤 버그가 생기는가?

## #154 리소스 API의 성숙도를 무엇으로 판단하는가?
`네트워크`

앞: 리소스를 URI로 나누고 HTTP 메서드와 상태 코드를 의미에 맞게 쓰며 응답이 다음 행동 링크를 제공하는지로 판단한다. 단계가 높을수록 HTTP 의미를 더 활용한다.

```
:::stack
Level 3 | 하이퍼미디어가 다음 행동을 안내한다
Level 2 | HTTP 메서드와 상태 코드를 활용한다
Level 1 | 리소스별 URI를 분리한다
Level 0 | 하나의 URI로 원격 호출한다
:::
```

뒤: Richardson 모델은 API가 HTTP를 얼마나 충실히 활용하는지 설명한다. Level 2만 되어도 자원과 행위, 오류 의미가 명확해져 일반적인 API에 실용적이다.

## #163 문자열 검색 효율을 높이는 최적의 자료구조는 무엇인가?

트라이 | 문자열의 각 문자를 노드로 저장
해시 맵 | 전체 문자열을 키로 저장
:::
```

뒤: 트라이는 문자열의 공통 접두사를 노드로 공유한다. 따라서 동일한 시작 문자를 가진 단어들은 같은 경로를 따라가므로 중복 탐색을 피한다.

## #167 스레드 풀을 사용하는 주된 이유는 무엇인가?

## #169 전송 계층에서 멀티플렉싱과 디멀티플렉싱은 무엇으로 구분하는가?

```

## #171 정적 클래스 내부에 정적 메서드를 정의하는 이유는 무엇인가?

정적 메서드 | 상태 없는 로직. 입력값으로만 결과가만 나오는 same-result same-input 구조다

뒤: 정적 클래스로 선언하면 외부에서 `new` 키워드로 인스턴스를 생성하는 것을 막을 수 있다. 이는 클래스가 단순한 도구 모음임을 명확히 알리는 설계적 의도이다.

## #172 JVM GC의 효율을 높이는 튜닝 포인트는 무엇인가?
`프레임워크`

앞: 힙 메모리 영역의 크기와 GC 알고리즘 선택이다. 세밀한 튜닝을 통해 Stop-the-world 시간을 줄이는 것이 핵심이다.

```
:::stack
Young Generation | Eden, Survivor. 짧은 생존 객체 관리
Old Generation | 장기 생존 객체 관리. Major GC 발생
:::
```

뒤: 객체 생존 기간에 따라 영역을 나누어 관리한다. Young 영역에서 살아남은 객체가 Old 영역으로 이동하며, Old 영역이 꽉 차면 전체 힙을 검사하는 Full GC가 발생한다.

## #178 가상 메모리를 사용하는 이유는 무엇인가?
`운영체제`

```
:::stack
가상 주소 | 프로세스가 보는 주소
페이지 테이블 | 가상 주소를 물리 주소로 매핑
물리 주소 | 실제 RAM의 위치
:::
```

뒤: 프로세스는 가상 주소만 보고 동작한다. 운영체제는 필요한 부분만 물리 메모리에 올리고 나머지는 디스크의 스왑 영역에 둔다.

## #182 프론트엔드 성능 최적화 시 번들 크기를 무엇으로 판단하는가?
`프론트엔드`

앞: 최초 로딩 시 사용자가 체감하는 LCP(Largest Contentful Paint)와 TBT(Total Blocking Time)를 기준으로 판단한다. 단순히 파일 용량만 줄이는 것이 아니라 런타임 실행 시간과 파싱 시간을 함께 고려해야 한다.

```
:::stack
런타임 성능 | JS 실행 및 DOM 조작 속도
네트워크 성능 | 번들 다운로드 및 압축 해제 속도
::: 
```

뒤: 위 도식은 번들이 실제 성능에 영향을 주는 두 가지 경로를 보여준다. 파일이 작아도 복잡한 로직이 많으면 TBT가 늘어난다.

## #184 volatile 키워드는 가시성 문제를 어떻게 해결하는가?
`언어 · 런타임`

앞: 메인 메모리에서 직접 읽고 쓰게 하여 모든 스레드가 최신 값을 보게 한다. CPU 캐시를 거치지 않고 메모리에 즉시 반영하기 때문이다.

```
:::stack
스레드 A | L1/L2 캐시. 지역적으로 값을 복사해 사용한다
메인 메모리 | 공유 영역. volatile 변수가 저장되는 곳
스레드 B | L1/L2 캐시. 메모리에서 직접 읽어 최신값을 얻는다
:::
```

뒤: CPU는 성능을 위해 값을 캐시에 복사해 쓴다. 여러 스레드가 같은 변수를 수정할 때 각자 캐시만 보면 다른 값을 가지게 된다.

## #187 백그라운드 제약을 피하는 방법은 무엇인가?
`모바일`

```
:::stack
포그라운드 서비스 | 알림창에 상주하며 즉시 실행
WorkManager | 조건 충족 시 시스템이 최적 시점에 실행
:::
```

뒤: 포그라운드 서비스는 사용자에게 앱이 동작 중임을 알린다. 시스템은 알림이 떠 있는 서비스를 중요도로 높게 평가해 메모리 부족 상황에서도 종료 우선순위를 늦춘다.

## #192 사용자 모드와 커널 모드 전환의 이유는 무엇인가?

뒤: 사용자 모드에서 하드웨어에 직접 접근하면 악성 코드가 메모리를 조작하거나 시스템을 파괴할 수 있다. 따라서 CPU의 모드 비트를 통해 접근 권한을 시스템 콜로 격리한다.

## #193 CPU 스케줄러의 단계별 역할은 무엇인가?
`운영체제`

앞: 프로세스의 상태 변화와 실행 우선순위에 따라 실행 주기와 대상자를 정하는 역할이다.

```
:::stack
장기 | 작업 큐에서 메모리로 올릴 프로세스 결정
중기 | 메모리 부족 시 일부를 디스크로 내보냄
단기 | 준비 큐에서 CPU를 할당할 프로세스 선택
:::
```

뒤: 위 도식은 각 스케줄러가 결정하는 범위와 시간적 단위를 보여준다. 장기 스케줄러는 시스템의 다중 프로그래밍 정도를 조절하며, 단기 스케줄러는 밀리초 단위로 빠르게 동작한다.

## #198 IP 주소의 핵심 역할은 무엇인가?
`네트워크`

앞: 네트워크 상의 기기별로 고유한 식별자와 위치 정보를 제공하는 것이다. 이를 통해 데이터 패킷이 목적지까지 정확하게 전달될 수 있다.

:::
```

뒤: IP 주소는 계층적 구조를 통해 네트워크 영역과 호스트 영역으로 나뉜다. 이 구조 덕분에 라우터는 모든 경로를 알 필요 없이 목적지 네트워크로 패킷을 보내는 라우팅으로 작동한다.

## #199 XSS 공격으로 훔칠 수 있는 데이터는 무엇인가?

저장소 | 데이터
쿠키 | 세션 ID, 사용자 인증 정보

:::
```

뒤: 위 표는 XSS가 노리는 주요 타겟이다. 공격자는 ‖javascript:alert('XSS')‖ 같은 코드를 삽입하여 브라우저의 ‖document.cookie‖ 속성에 접근한다.

## #203 JVM의 핵심 역할은 무엇인가?
`프레임워크`

앞: JVM은 자바 바이트코드를 실행하는 가상 머신이다. OS로 부터 독립적인 실행 환경을 제공하여 'Write Once, Run Anywhere'를 실현한다.

```
:::stack
JVM 내부 | Java Runtime Environment (JRE)
실행 대상 | Java Bytecode (.class)
::: 
```

뒤: 컴파일러가 소스코드를 바이트코드로 변환하면, JVM은 이를 읽어 각 OS에 맞는 기계어로 바이트코드를 해석한다. 이 과정에서 메모리 관리와 최적화가 핵심이다.

## #205 데이터 오류로 인한 손실을 어떻게 방지하는가?
`인프라 · 보안`

앞: 패리티 비트와 해밍 코드로 검출과 복구로 나누어 처리한다. 단순 검출은 패리티 비트로, 위치를 찾아 복구하는 것은 해밍 코드로 한다.

```
:::stack
검출 전용 | 패리티 비트. 짝수/홀수 합을 맞춰 오류로 판단
복구 가능 | 해밍 코드. 여러 체크 비트로 위치를 추적
:::
```

뒤: 패리티 비트는 데이터 끝에 1비트를 추가해 합을 맞춘다. 1비트만 틀렸을 때 알 수 있지만, 어디가 틀렸을 때인지 모르고 데이터는 버려야 한다.

## #216 JVM 메모리 영역은 어떻게 구분하는가?

공유 영역 | Heap, Method Area
개별 영역 | Stack, PC Register, Native Method Stack
:::
```

뒤: 공유 영역은 모든 스레드가 접근 가능하다. 가비지 컬렉션의 대상이 되어 메모리 관리가 자동화된다.

## #221 컨텍스트 스위칭 시 CPU는 무엇을 저장하고 복원하는가?

:::
```

뒤: 상태 저장 시 CPU의 프로그램 카운터(PC)과 레지스터 값들이 PCB에 옮겨진다. 그래야 나중에 다시 돌아왔을 때 중단된 지점부터 정확히 연산으로 돌아갈 수 있다.

## #230 톰캣은 WAS와 웹 서버의 차이점으로 무엇을 수행하는가?

:::
```

뒤: 톰캣은 HTTP 요청을 받아 서블릿으로 전달하고 그 결과를 다시 응답한다. 이 과정에서 서블릿의 생명주기를 관리하고 멀티스레딩을 처리한다.

## #233 HTTPS는 HTTP와 무엇이 다른가?
`네트워크`

앞: HTTP에 SSL/TLS 프로토콜을 추가해 데이터를 암호화한 것이다. 이를 통해 도청, 변조, 위조를 막는다.

```
:::stack
HTTPS | HTTP + SSL/TLS
HTTP | 평문 전송
:::
```

뒤: 전송 계층 위에 SSL/TLS라는 보안 계층을 얹은 구조다. 클라이언트와 서버가 서로의 신원을 확인하고 암호화 키를 교환하는 과정이 핵심이다.

## #239 웹 서버와 WAS의 역할 분담은 왜 하는가?
`프론트엔드`

:::stack
웹 서버 | HTML, CSS, 이미지 등 정적 파일 처리
WAS | DB 조회, 비즈니스 로직 등 동적 콘텐츠 생성
:::
```

뒤: 웹 서버가 앞단에서 정적 파일을 먼저 처리하면 WAS는 무거운 로직 수행에만 집중할 수 있다. 요청의 성격에 따라 처리 주체를 나누어 전체 응답 속도를 높인다.

## #240 React Hook을 사용하는 이유는 무엇인가?

## #241 파이썬의 가비지 컬렉션은 무엇으로 동작하는가?
`언어 · 런타임`

```
:::stack
참조 횟수 | 기본 메커니즘. 0이 되면 즉시 해제
세대별 GC | 보조 메커니즘. 순환 참조 해결
:::
```

뒤: 참조 횟수 계산은 빠르고 즉각적이다. 하지만 두 객체가 서로를 가리키는 순환 참조가 발생하면 횟수가 0이 되지 않아 메모리 누수가 생긴다.

## #243 값 타입과 참조 타입은 무엇으로 구분하는가?
`언어 · 런타임`

앞: 데이터가 메모리에 저장되는 방식과 전달되는 방식의 차이로 구분한다. 값 타입은 실제 값을 직접 저장하고, 참조 타입은 값이 저장된 메모리 주소를 저장한다.

```
:::stack
값 타입 | 스택 메모리. 실제 데이터가 저장됨
참조 타입 | 힙 메모리. 주소값이 저장되며 데이터는 힙에 위치함
:::
```

뒤: 값 타입은 변수 간 복사 시 값이 그대로 복사되어 서로 영향을 주지 않는다. 독립적인 상태를 유지하므로 부수 효과가 적어 안전하다.

## #246 재귀 함수 사용 시 스택 오버플로가 발생하는 이유는 무엇인가?
`자료구조 · 알고리즘`

앞: 함수 호출 시마다 스택 프레임이 생성되어 메모리의 스택 영역을 가득 채우기 때문이다.

```
:::stack
스택 프레임 | 지역 변수, 매개변수, 복귀 주소
스택 메모리 | 프레임이 쌓이는 한정된 공간
:::
```

뒤: 재귀는 자기 자신을 다시 호출하며 멈추지 않고 쌓인다. 각 호출은 이전 상태를 기억해야 하므로 메모리 공간을 계속 점유한다.

## #248 멀티스레드 환경에서 스레드 세이프한 코드를 작성하는 방법은 무엇인가?
`운영체제`

앞: 임계 영역으로의 동시 접근을 막아 데이터 일관성을 보장하는 것이다. 한 번에 하나의 스레드만 자원에 접근하도록 제어하는 것이 핵심이다.

```
:::stack
제어 방법 | 설명
--|--
동기화 | synchronized, Lock API를 이용한 상호 배제
불변성 | final, Read-only 객체로 상태 변경 차단
원자성 | Atomic 클래스로 단일 연산 수행
:::
```

뒤: 위의 방법들로 공유 자원에 대한 경쟁 상태를 방지한다. 특히 데이터 읽기/쓰기 과정에서 문맥 전환이 발생하면 데이터가 오기집단될 수 있다.

## #249 쓰레싱이 발생하는 원인과 해결책은 무엇인가?
`운영체제`

앞: 페이지 부재가 빈번하게 발생하여 CPU로의 입출력으로 인해 CPU로의 입출력으로 인해 CPU 이용률이 급격히 떨어지는 현상이다.

```
:::stack
메모리 부족 | 페이지 부재 빈번
CPU 이용률 | 급격히 하락
::: 
```

뒤: 운영체제는 CPU 이용률이 낮아지면 더 많은 프로세스를 메모리에 올려 CPU 이용률을 높이려 한다. 이 과정에서 각 프로세스에 할당된 메모리 공간이 줄어들어 페이지 부재가 더 심해진다.

## #250 동기화 문제를 하드웨어적으로 어떻게 해결하는가?
`운영체제`

앞: 원자적 명령어로 처리한다. CPU가 명령어를 실행하는 동안 다른 프로세스가 개입하지 못하게 막아 메모리 접근을 보장하는 방식이다.

```
:::stack
하드웨어 수준 | **Test-and-Set**, **Compare-and-Swap (CAS)**
명령어 수준 | 인터럽트 비활성화. 단일 코어에서만 유효하다
:::
```

뒤: Test-and-Set은 메모리 값의 현재 상태를 읽고 새로운 값을 쓰는 작업을 한 번에 처리한다. 중간에 컨텍스트 스위칭이 발생하지 않아 데이터 정합성을 지킨다.

## #258 CPU와 메모리 중 무엇이 데이터 처리 속도를 결정하는가?
`인프라 · 보안`

```
:::stack
CPU 코어 | 연산 속도. 직접 처리하는 힘
메모리 | 데이터 공급 속도. 대기 시간 발생
:::
```

뒤: CPU는 매우 빠르지만 메모리에서 데이터를 가져오는 속도는 상대적으로 느리다. 이를 메모리 벽(Memory Wall)리라 부른다.

## #259 우선순위 큐를 힙으로 구현하는 이유는 무엇인가?
`자료구조 · 알고리즘`

최대 힙 | 부모가 자식보다 항상 크거나 같다

:::
```

뒤: 힙은 완전 이진 트리 구조를 사용한다. 이를 통해 삽입과 삭제 모두 O(log N)의 시간 복잡도로 처리할 수 있다.

## #267 브라우저에서 FTP 지원을 중단하는 이유는 무엇인가?
`프론트엔드`

앞: 보안 취약점과 현대적인 웹 표준의 부재 때문이다. FTP는 평문으로 데이터를 주고받아 스니핑으로 계정 정보와 파일로 내용이 유발출된다. 

```
:::stack
보안 수준 | FTP. 평문 전송. 매우 위험
HTTPS | TLS 암호화. 표준으로 정착
:::
```

뒤: 또한 FTP는 방화벽과 프록시 서버 환경에서 포트 제어와 포트 범위 지정이 까다롭다. 이는 사용자 경험을 해방하고 개발 효율을 떨어뜨린다.

## #269 안드로이드에서 메모리 누수가 발생하는 주원인은 무엇인가?
`모바일`

앞: 활동(Activity)이 파괴되었음에도 외부 객체에 의해 참조가 유지되어 가비지 컬렉터가 회수하지 못할 때 발생한다.

```
:::stack
참조 체인 | Activity $\rightarrow$ 익명 클래스 $\rightarrow$ 외부 객체
루트 객체 | GC Root. 메모리 해제제한의 시작점
:::
```

뒤: 가장 흔한 사례는 Activity 내부에서 익명 클래스나 내부 클래스를 사용하는 경우다. 이들은 외부 클래스에 대한 숨은 참조를 가지므로, 내부 클래스가 살아있으면 Activity도 메모리에 남는다.

## #270 코루틴의 구조적 동시성은 무엇을 해결하는가?
`모바일`

앞: 비정상적으로 종료된 자식 코루틴이 부모 코루틴에 의해 관리되지 않아 메모리 누수나 불필요한 작업이 계속되는 현상을 해결한다.

```
:::stack
부모 코루틴 | 자식 코루틴의 생명주기를 관리하고 완료를 기다림
자식 코루틴 | 부모의 컨텍스트와 Job로 묶여 제어됨
:::
```

뒤: 구조적 동시성은 코루틴 간의 계층 구조를 형성한다. 부모 코루틴은 모든 자식 코루틴이 끝날 때까지 대기한다. 자식에서 예외가 발생하면 부모와 형제 코루틴 모두 취소된다.

## #272 컨테이너는 가상 머신과 무엇이 다른가?
`인프라 · 보안`

앞: 커널을 공유한다. 가상 머신은 게스트 운영체제를 통째로 올리지만 컨테이너는 호스트 커널 위에서 프로세스로 돈다.

```
:::stack
컨테이너 | 앱과 라이브러리만. 커널은 호스트 것을 쓴다
컨테이너 런타임 | 격리와 자원 제한을 건다
호스트 커널 | 하나를 모두가 나눠 쓴다
:::
```

뒤: 격리의 뼈대는 커널 기능 둘이다. 네임스페이스가 보이는 것을 가르고 cgroup이 쓸 수 있는 양을 정한다. seccomp이나 SELinux 같은 것이 그 위에 더 얹힌다.
