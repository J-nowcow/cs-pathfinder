# 매일 알림 채널 — 대안 비교와 순서 (F3)

카톡이 목표 9였는데 F1 조사가 두 벽을 확인했다 — "나에게 보내기"는
로그인 뒤에나 성립하고, 채널 개설은 사업자등록이 앞에 있다. 그러면
그동안 무엇으로 알리는가. 넷을 견준다.

## 비교

| | RSS | 웹푸시 | 이메일 | 카톡 |
|---|---|---|---|---|
| 상태 | **이미 산다** (`/rss.xml`) | 미구현 | 미구현 | 막힘 |
| 돈 | 0 | 0 | Resend 무료 3천 통/월 | 나에게 보내기 0 · 알림톡 8원/건 |
| 개인정보 | **없음** | 구독 endpoint 저장(기기 토큰) | **이메일 주소 수집** — `/privacy` 개정 | 카카오 계정 연결 |
| 선행 조건 | 없음 | 구독 저장 테이블 + VAPID 키 | 로그인(주소를 받을 명분) | 로그인 + refresh 만료 실측(F1-b) |
| iOS | 리더 앱 | **16.4+ 홈 화면 추가 필수** — 문턱 크다 | 됨 | 됨 |
| 도달 확인 | 불가(구독자 수도 모른다) | 가능 | 가능(오픈률) | 가능 |

## 판정 — 순서가 답이다

1. **지금: RSS로 충분하다.** 이미 살아 있고 약속할 게 없다. README·홈에서
   더 보이게 하는 것 외에 할 일이 없다
2. **다음(홍보 후 수요 확인되면): 웹푸시.** 돈 0, 로그인 불필요, PWA
   manifest가 이미 있다. 대신 iOS 문턱(홈 화면 추가)이 커서 **수요를 보고
   만든다** — 알림 신청 버튼을 먼저 놓고 누르는 사람 수를 세는 것이 구현보다
   먼저다. 그 숫자가 없으면 구독 테이블·VAPID·발송 훅이 전부 추측 위에 선다
3. **로그인 후: 이메일.** 주소를 받을 명분(계정)이 생긴 뒤에. Resend 무료
   한도로 시작, `/privacy` 개정 동반
4. **마지막: 카톡.** F1-b(refresh 만료 실측)가 풀려야 하고, 그 전까지는
   "매일 보내다 조용히 멈추는" 위험을 안는다

## 하지 않기로 한 것

- **웹푸시를 지금 만드는 것** — 수요 숫자 없이 만드는 인프라는 M2-b(승격
  파이프라인)와 같은 이유로 보류: 대상이 생기면 만든다
- **이메일을 로그인보다 먼저** — 알림 목적만으로 주소를 수집하면 수집
  최소화 원칙과 충돌한다. 계정의 부속으로 받는 것이 맞다
