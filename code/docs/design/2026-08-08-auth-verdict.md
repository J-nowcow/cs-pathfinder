# 회원가입 결정 — 개정

2026-08-08. `docs/plan/2026-08-07-auth-design.md`의 결정을 Codex(외부 모델, read-only)에 반박시켰고 **넷이 뒤집혔다.** 근거는 내가 원문·npm으로 대조했다.

## 내가 틀린 방식

한 시간 전에 나는 "설계안의 근거가 오늘도 참"이라고 적었다. 실제로 잰 것은 이것뿐이다.

```
next-auth@beta = 5.0.0-beta.32
peerDeps: next ^14||^15||^16 · react ^18.2||^19
```

**사실은 맞았고 논증은 틀렸다.** v5의 peer만 재고 v4의 peer를 안 쟀다. 그런데 설계안이 v5를 고른 첫째 이유가 "Next 16·React 19가 선언돼 있다"였다. 그 성질이 v5만의 것인지 확인하지 않으면 아무것도 증명한 게 아니다.

실제로 재 보니 이렇다.

| | next | react | 배포일 |
|---|---|---|---|
| `next-auth@4.24.15` (stable) | `^12.2.5 \|\| ^13 \|\| ^14 \|\| ^15 \|\| ^16` | `^17.0.2 \|\| ^18 \|\| ^19` | 2026-07-20 |
| `next-auth@5.0.0-beta.32` | `^14.0.0-0 \|\| ^15.0.0 \|\| ^16.0.0` | `^18.2.0 \|\| ^19.0.0` | 2026-07-20 |

**stable도 Next 16과 React 19를 지원한다.** 같은 날 나왔다. 호환성은 v5를 고를 이유가 못 된다.

그리고 `5.0.0-beta.0`은 **2023-10-24**에 나왔다. 오늘로 **1,019일째 beta**다. "곧 정식"이라고 볼 근거가 없다.

## 뒤집힌 것 넷

### 1. Auth.js v5 beta → 보류

위 표가 이유다. 고를 이유였던 것이 v5만의 성질이 아니었다. 남는 것은 beta 위험뿐이다.

**다만 v4로 바로 갈아탈 수는 없다.** `@auth/pg-adapter@1.11.3`은 `@auth/core@0.41.3`에 맞춰져 있고 v4는 `@auth/core: 0.34.3`을 고정한다. 섞으면 안 된다 — v4용 어댑터가 따로 있는지 확인해야 한다.

**결정을 미룬다.** C3에 들어가기 전에 셋을 짧게 시험(spike)한다.

1. `next-auth@4.24.15` + v4용 pg 어댑터
2. `next-auth@5.0.0-beta.32` + `@auth/pg-adapter@1.11.3` (버전 고정, lockfile 박제)
3. `better-auth@1.6.26`

재는 것: 구글 로그인이 되는가 · 카카오를 커스텀으로 붙일 수 있는가 · raw `pg`와 붙는가 · 계정 연결을 명시적으로 막을 수 있는가.

### 2. JWT 세션 → DB 세션

설계안이 스스로 모순됐다. **"즉시 하드 삭제"**를 요구하면서(§5) 세션은 JWT로 둔다(§1).

JWT는 DB를 안 본다. 사용자 행을 지워도 **다른 기기의 쿠키는 만료까지 계속 인증된다.** 탈퇴 표에 `sessions` 삭제가 적혀 있지만 JWT 전략에서 그 테이블은 비어 있다.

"짧은 만료"는 답이 아니다. 그건 "즉시"가 아니다. 그리고 JWT를 유지하면서 매 요청 사용자 존재를 확인하면 비용이 DB 세션과 같아지고 폐기 로직만 더 는다.

**DB 세션으로 간다.** Neon 비용 걱정은 실측으로 다시 본다 — 지금 트래픽에서 세션 조회가 얼마나 되는지 재지도 않고 JWT를 고른 것이었다.

### 3. 익명 localStorage 공유 → 계정별로 가른다

**이것이 가장 위험하다. 계정 간 데이터 유출이다.**

지금 저장 키는 모든 사용자 공통 `csqt.journey.v1`이다(`journey/storage.ts:3`). 설계안은 로그아웃해도 로컬을 남긴다(§2). 그러면 이렇게 된다.

1. Alice 로그인 → 서버 여정이 공통 로컬에 저장된다
2. Alice 로그아웃 (로컬은 남는다)
3. Bob 로그인 → **공통 로컬 여정이 Bob 계정으로 병합된다**

한 브라우저를 나눠 쓰는 흔한 상황이다. 손실이 아니라 유출이다.

**키를 가른다.** 익명은 `journey.anon.v1`, 로그인은 `journey.user.<uid>.v1`. 익명 기록의 귀속은 **최초 1회만** 묻고 표시를 남겨 다른 계정에 다시 붙지 않게 한다. 로그아웃할 때 계정 데이터를 익명 키로 복사하지 않는다.

### 4. FK를 안 두는 것 → 둔다

설계안은 "과거 테이블이 나중에 생긴 `users`를 참조할 수 없다"를 이유로 들었는데 **성립하지 않는다.** `users`를 만든 뒤 `ALTER TABLE`로 걸면 된다.

FK를 빼면 탈퇴 트랜잭션이 일부 실패했을 때 고아 ID가 남는다. 원하는 삭제 의미가 FK로 정확히 표현된다 — `tree.author_id`는 `ON DELETE SET NULL`, `journey_occurrence`는 `CASCADE`.

## 유지되는 것 둘

- **개인정보처리방침 선배포.** 이미 했다(`/privacy`)
- **익명 지원 유지.** 다만 "공통 로컬을 모든 계정에 자동 병합"은 틀렸다. 지원과 병합은 다른 이야기다

## 새로 드러난 것

**`path_key`가 깊은 여정에서 터진다.** 전체 UUID를 `>`로 이으면 한 마디가 36자다. 깊이 73쯤에서 PostgreSQL B-tree 인덱스 행 한계를 넘어 `index row size exceeds maximum`으로 삽입이 실패한다. → `path_hash bytea`(SHA-256)에 유니크를 걸고, 해시는 **서버가 검증된 부모 관계로** 계산한다. 클라이언트가 보낸 것을 믿지 않는다.

**어댑터가 방침보다 많이 저장한다.** `@auth/pg-adapter`는 `image`와 `access_token`·`refresh_token`·`id_token`·`scope`를 저장한다. 설계안 §5는 "프로필 이미지를 저장하지 않는다"고 했다. **로그인을 붙이는 순간 `/privacy`가 거짓이 된다.** 어댑터를 감싸 지우거나, 저장한다면 방침에 적고 탈퇴 시 폐기까지 정한다.

**마이그레이션 번호가 낡았다.** 설계안은 `0010`부터라고 했는데 `0010_qnode_number.sql`이 이미 있다. `0011`부터다.

**어댑터가 `pg.Pool`을 요구한다.** 이 저장소의 Pool은 `createPostgres` 안의 지역 변수이고(`db/client.ts:91`) `getDb()`는 자체 인터페이스를 돌려준다. 그대로는 못 넘긴다. 별도 Pool을 만들면 인스턴스마다 연결이 두 배가 된다. **공용 Pool을 노출하는 것이 먼저다.**

**시험 정리 함수가 새 테이블을 모른다**(`db/client.ts:210`). 인증 시험을 추가하면 사용자 데이터가 시험 사이에 남는다.

**익명 투표가 이중 집계된다.** 지금 투표는 정확한 `voter_key`만 토글한다(`db/votes.ts:29`). 로그인 전 한 표, 로그인 후 `user:<uid>`로 또 한 표가 된다.

**CSRF·계정 연결 정책이 통째로 없다.** 특히 카카오는 이메일을 안 받으므로 구글 계정과 같은 사람인지 판별할 방법이 없다. `allowDangerousEmailAccountLinking`을 켜면 안 되고, 연결은 **로그인된 상태의 설정 화면에서 명시적으로만** 한다.

## 사람이 해야 하는 것

**Google Cloud Console에서 OAuth 클라이언트를 만들어야 한다.** 내가 못 한다.

- `AUTH_GOOGLE_ID`·`AUTH_GOOGLE_SECRET`
- **동의 화면을 "테스트 중"으로 두면 refresh token이 7일에 만료된다.** Production으로 전환해야 한다
- `email`·`profile`·`openid`는 non-sensitive라 **검수 없이** Production이 된다
