스레드를 늘려도 CPU 병렬성이 없는 이유는?

언어 · 런타임 · python 기초 동시성

CPython 기본 빌드에서는 같은 인터프리터에 속한 스레드 하나만 한 시점에 파이썬 바이트코드를 실행한다. CPU 연산 스레드를 늘리면 GIL 경합과 전환 비용만 커질 수 있다.

셋을 띄워도 한 칸에 하나만 돈다. 코어가 넉넉해도 마찬가지다. 늘린 만큼 기다리는 줄만 길어진다.

대기하는 많은 I/O 호출과 일부 네이티브 확장은 GIL을 놓는다. 그래서 네트워크 작업이나 GIL을 해제하는 수치 연산은 스레드로도 겹쳐 실행할 수 있다.

멀티프로세스는 CPU 병렬성을 얻지만 메모리와 직렬화 비용을 낸다. GIL도 복합 연산의 논리적 경쟁까지 막지 않으므로 공유 상태는 따로 동기화해야 한다.

미리보기 — 새 문법 도입 시

CPU 연산을 늘리려면 스레드가 아니라 프로세스를 늘려야 한다. multiprocessing은 인터프리터를 따로 띄우므로 GIL 경합이 없다.

핵심 정리

I/O 대기는 스레드로 겹치고, CPU 연산은 프로세스로 나눈다.

주의

GIL은 list.append 같은 단일 연산만 지켜 준다. 읽고 고쳐 쓰는 복합 연산은 따로 잠가야 한다.

각주 — 현행에서 바꾼 값

  • ① 답 블록 16px → 18px, 행간 1.8 → 1.7, 왼쪽 3px solid --accent + 바탕 --accent-soft, 아래 여백 28px. 대비: ink #191c20 on #e9f4f2 = 15.2:1 (AA 통과, 여유 큼).
  • ② 인라인 코드 글자색 --ink → --accent #0f7a6c. 바탕은 --accent-soft 그대로. 대비 4.65:1 — 0.88em(≈14px) 본문 글씨라 AA 4.5:1 기준을 넘지만 여유가 0.15뿐이다. accent 토큰을 조금이라도 밝히면 곧바로 미달하므로, 적용 시 이 조합을 회귀 검사에 넣어야 한다.
  • ③ 도식 머리띠 linear-gradient(180deg, --accent-soft, #f6fbfa). th 글자는 --muted #565d66 유지 — accent-soft 위 5.93:1. 표 카드 머리띠는 linear-gradient(90deg, --accent-soft, transparent 90%)이고 글자는 --ink라 대비 문제 없음.
  • ③ 반지름 도식·표 8px → 10px. 테두리 색은 --line 그대로 — 띠가 이미 경계를 말하므로 테두리를 진하게 할 이유가 없다.
  • ④ 리듬 문단 아래 여백 1.15em → 1.3em. 도식 여백 24px/24px → 28px/18px(앞은 벌리고 뒤는 붙임). 첫 문장 굵게는 하지 않았다 — 저장된 본문에 **가 없고 데이터는 무변경이 전제다.
  • 미리보기 ==하이라이트==는 글자 뒤 60% 아래만 칠하는 형광펜 밑줄. 통칠보다 줄이 가볍다. :::note·:::warn은 답 블록과 같은 문법(왼쪽 3px + soft 바탕)이라 새 규칙이 늘지 않는다. 라벨 대비: accent on accent-soft 4.65:1, warn #a8452f on warn-soft #f8ebe7 5.07:1 — 둘 다 12px라 AA 통과.
  • 안 바꾼 것 헤더·제목 24px·메타줄·꼬리질문·자유 입력·본문 16px·행간 1.8·--line·표 접힘 규칙.
