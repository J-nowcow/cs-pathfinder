# 진단 퀴즈 설계

해설을 읽기 전에 객관식 세 문제를 먼저 낸다. 맞히면 건너뛰고, 틀리면 그 오답이 겨냥한 꼬리질문이 맨 위로 올라온다.

## 왜 만드나

지금 `AnswerPractice`는 사용자가 답을 쓰고, 모범답안을 열어, **스스로** 비교한다. 결과는 localStorage에 텍스트로만 남는다. 시스템은 그 사람이 맞았는지 모른다.

그래서 꼬리질문 5개가 항상 같다. 이 질문의 이웃 개념이지, **이 사람이 틀린 지점**이 아니다. 진단 신호가 없으니 처방을 겨눌 수 없다.

객관식을 하나 붙이면 신호가 생긴다. 그리고 이 저장소에서는 그 신호가 갈 곳이 이미 있다 — 꼬리질문 5개와 그래프다. 커리큘럼이 고정된 서비스는 약점을 알아도 다음 화면이 안 바뀌지만, 여기서는 **약점이 곧 다음 경로**가 된다.

## 무엇을 안 하나

**커리큘럼 레이어를 얹지 않는다.** 도메인 > 과목 > 레슨 순서를 부여하는 것은 "경로는 개인의 것"이라는 설계 축(`engineering.md`)과 정면으로 어긋난다. 그렇게 하면 그래프가 장식이 된다.

**런타임에 문제를 만들지 않는다.** 해설이 이미 고정된 정적 자산인데 매번 LLM을 부를 이유가 없다. 문제는 `data/quiz.ts`에 손으로 써서 커밋한다 — `authored-nodes.ts`(90편)와 같은 방식이다. 비용이 0이고, git에서 리뷰되고, 시험으로 형식을 검사할 수 있다.

**주관식을 없애지 않는다.** 객관식은 진단이고 주관식은 면접 대비다. 역할이 다르다. 객관식이 앞, 주관식은 해설 안에 지금 자리 그대로 둔다.

## 흐름

```
질문 열기
  ↓
[진단 3문제]  ← 새 질문일 때만. 한 번 푼 질문은 건너뛴다
  ↓         "건너뛰고 바로 읽기"는 항상 열려 있다
  ├─ 3/3 정답 → "이미 아네요" + 해설은 접힌 채로. 꼬리질문 바로 노출
  └─ 오답 있음 → 해설 펼침 + 틀린 문제가 겨냥한 꼬리질문이 맨 위로
  ↓
해설 (기존 그대로) + 주관식 답변 연습 (기존 그대로)
  ↓
꼬리질문 5개 ← 순서가 오답에 따라 바뀐다
```

건너뛰기를 항상 열어두는 이유는 첫인상이다. 링크를 타고 들어온 사람에게 시험을 강제하면 그대로 나간다. 유입 대부분이 카톡 링크라는 것은 `roots.ts`에 이미 적혀 있다.

## 문제 세 개의 역할

한 노드에 세 문제를 붙이고 각각 다른 것을 잰다. 셋 다 같은 것을 물으면 진단이 아니라 반복이다.

| 종류 | 무엇을 재나 | 틀렸을 때의 뜻 |
|---|---|---|
| `concept` | 핵심 결론을 아는가 | 이 주제를 처음 본다 |
| `misconception` | 흔한 오해에 빠지지 않는가 | 얕게 안다. 면접에서 되묻히는 자리 |
| `boundary` | 조건·예외를 아는가 | 안다고 생각하지만 단정한다 |

`boundary`가 중요하다. `README.md`의 정확도 측정에서 나온 오류 대부분이 "조건을 뺀 단정"이었다 — 실제로는 조건부인데 "항상", "반드시"로 쓴 문장들. 사람의 이해도 같은 자리에서 무너진다.

## 오답이 꼬리질문을 겨냥한다

여기가 핵심이다. 각 오답 보기는 **그 오해를 다루는 꼬리질문의 인덱스**를 들고 있다.

```ts
{
  kind: 'misconception',
  stem: 'TIME_WAIT이 쌓인 서버에서 가장 먼저 할 일은?',
  choices: [
    { text: 'SO_REUSEADDR을 켠다',        leadsTo: 3 },  // → keep-alive 질문으로
    { text: '커널 대기 시간을 줄인다',       leadsTo: 3 },
    { text: '누가 먼저 닫는지 확인한다',     correct: true },
    { text: 'CLOSE_WAIT 수를 센다',        leadsTo: 4 },  // → CLOSE_WAIT 질문으로
  ],
}
```

`leadsTo`는 그 노드 `suggestions[]`의 인덱스다(0~4). 문제를 쓸 때 오답마다 "이 사람은 어디로 가야 하나"를 같이 정한다. 새 질문을 만들지 않고 **이미 있는 꼬리질문의 순서만 바꾼다** — 콘텐츠가 늘지 않고 정밀도만 오른다.

정답에는 `leadsTo`가 없다. 맞힌 사람을 어디로 보낼 이유가 없다.

## 데이터

### `data/quiz.ts`

노드를 자연키로 참조한다. `(identityScope, question)` 쌍은 `bootstrap.ts`의 `rootNodeId()`가 uuid를 파생하는 바로 그 키다. 퀴즈가 uuid를 직접 들고 있으면 질문 문장을 고칠 때 조용히 끊긴다.

```ts
export type QuizChoice = {
  text: string
  /** 정답 하나에만 true. 나머지는 생략한다 */
  correct?: boolean
  /** 이 오답을 고른 사람에게 올려줄 suggestions 인덱스 (0~4) */
  leadsTo?: number
}

export type QuizItem = {
  kind: 'concept' | 'misconception' | 'boundary'
  stem: string
  choices: QuizChoice[]
  /** 정답 공개 시 보여줄 한 문장. 해설 본문에 근거가 있어야 한다 */
  rationale: string
}

export type NodeQuiz = {
  identityScope: string
  question: string
  items: QuizItem[]
}
```

### `supabase/migrations/0020_quiz.sql`

문제 자체는 DB에 넣지 않는다. `data/quiz.ts`가 원본이고 앱이 그대로 읽는다 — 정적 자산을 DB로 복사하면 두 벌이 되고 어느 쪽이 진짜인지 흐려진다.

DB에 남기는 것은 **답한 기록**뿐이다. 그것도 로그인 사용자만 — 익명은 localStorage에 남는다. `streak_read`와 같은 원칙이다.

```sql
create table if not exists quiz_answer (
  user_id     text not null references "user" ("id") on delete cascade,
  qnode_id    uuid not null references qnode (id) on delete cascade,
  item_index  smallint not null,        -- items[] 안의 자리 (0~2)
  chosen      smallint not null,        -- 고른 보기 인덱스
  correct     boolean  not null,
  answered_at timestamptz not null default now(),
  primary key (user_id, qnode_id, item_index)
);
```

복합 PK가 "한 문제는 한 번만"을 DB가 보증한다. 다시 풀면 덮어쓴다(`on conflict do update`) — 두 번째 시도가 진짜 이해일 수 있고, 첫 오답을 영구 낙인으로 남길 이유가 없다.

`item_index`를 쓰는 이유는 문제에 별도 id를 두지 않기 위해서다. 문제는 노드에 종속된 배열이고 그 순서가 정체성이다. 나중에 순서를 바꾸면 기록이 어긋나므로, **문제를 지우지 말고 뒤에 붙인다**는 규칙을 검증 스크립트가 강제한다.

### localStorage

`csqt.quiz.v1`. 익명 사용자의 전부이고 로그인 사용자에게도 1차 저장소다. `answer-practice/storage.ts`와 같은 모양을 쓴다.

```ts
type QuizState = {
  /** nodeId -> 문제별 고른 답 */
  answers: Record<string, { chosen: number[]; at: string }>
  /** 건너뛴 노드. 다시 안 묻는다 */
  skipped: string[]
}
```

## 검증

`npm run verify:quiz`가 형식을 검사한다. 시험으로 걸어 CI에서도 돈다.

| 검사 | 왜 |
|---|---|
| 참조하는 `(scope, question)` 노드가 실재하는가 | 질문 문장을 고치면 퀴즈가 조용히 끊긴다 |
| 정답이 정확히 하나인가 | 둘이면 채점이 무너진다 |
| 오답의 `leadsTo`가 `suggestions` 범위(0~4) 안인가 | 넘으면 빈 추천이 뜬다 |
| 정답에 `leadsTo`가 없는가 | 맞힌 사람을 보낼 이유가 없다 |
| `kind` 세 종류가 다 있는가 | 셋 다 `concept`이면 진단이 아니다 |
| `rationale`의 근거가 본문에 있는가 | 본문에 없는 사실을 새로 만들면 안 된다 |

마지막 항목은 자동으로 완전히 판정할 수 없다. 지금은 `rationale`의 핵심 명사가 본문에 등장하는지만 본다 — 통과했다고 맞는 것은 아니고, 걸리면 확실히 틀렸다는 뜻의 검사다.

## 알려진 한계

- **오답률이 낮은 문제가 좋은 문제인지 알 수 없다.** 너무 쉬워서일 수도, 정답이 티나서일 수도 있다. 답한 기록이 쌓이면 문항별 정답률을 보고 고를 수 있지만 지금은 데이터가 없다
- **내가 쓴 문제에도 오류가 있을 수 있다.** 해설 328편은 이미 4회 훑어 59건을 고친 상태라 그것을 근거로 쓰면 새 사실을 지어낼 여지는 작다. 그래도 `README.md`가 해설에 적용한 것과 같은 잣대로 표본을 떠 재야 한다
- **`leadsTo` 매핑은 저자의 판단이다.** 그 오답을 고른 사람이 정말 그 꼬리질문을 필요로 하는지는 측정된 적이 없다. 클릭률로 뒤에 잴 수 있다
- **문제 없는 노드가 대부분이다.** 328편 중 5편으로 시작한다. 문제가 없으면 지금과 똑같이 동작한다 — 퀴즈는 있으면 뜨고 없으면 안 뜬다
