# 만든 방법

서비스를 쓰는 데는 필요 없는 내용이다. 왜 이렇게 만들었고 무엇을 재서 그렇게 정했는지를 적는다.

사용 설명은 [레포 루트의 README](../../README.md)에 있다.

---

## 직접 돌려보기

```bash
cd code
npm install
npm run dev     # http://localhost:3000
npm test
npm run typecheck
```

**Docker도 API 키도 필요 없다.** `DATABASE_URL`이 없으면 인메모리 Postgres(PGlite)로 돌고, AI 키가 없으면 결정론적 스텁이 대신 답한다. 부팅할 때 질문 335개와 그 사이 관계 397개가 자동으로 들어간다. 노드 ID는 질문 텍스트에서 파생하므로 서버를 다시 띄워도 같은 URL이 살아 있다.

질문 335개의 출처는 넷이고 파일이 따로다. 손으로 쓴 것이 90개(기준선 30 + 분야 구멍을 메운 보충 60), 모델이 쓴 것이 245개(배치 219 + 사용자가 물어보다 만들어진 26)다. 기준선을 보충분과 섞지 않는 이유는 검사기 시험이 기준선을 상대로 걸려 있어서다 — 섞으면 기준이 흔들린다.

## 폴더

```
cs/       질문 전문. 코드를 안 열어도 무엇이 담겼는지 보인다
code/     앱 전부 — src·data·scripts·tests·설정
```

`cs/questions.md`는 발행 워크플로가 매일 다시 쓴다. 손으로 고치지 않는다. **사용자가 자유 입력으로 판 질문은 담지 않는다** — `ready`는 생성이 끝났다는 뜻이지 공개해도 된다는 뜻이 아니고, 레포에 박히면 되돌릴 수 없다.

## 설계에서 중요한 것

**노드는 개념이고 경로는 개인의 것이다.** `qnode`의 유일키는 (의미 범위 + 질문 문장) 해시이고 부모와 무관하다. "TCP 3-way handshake란?"은 하나만 존재하고 DB 경로와 네트워크 경로 양쪽에서 도달한다. 부모-자식 관계는 `qedge`에 따로 있다.

**전역 그래프는 DAG가 아니다.** 순환을 허용한다. 지식 관계에서는 `TCP → 3-way handshake`와 그 역이 둘 다 성립한다. 조상 중복은 경로를 만들 때만 막는다.

**경로는 노드 참조가 아니라 발자국(occurrence)으로 저장한다.** 전역 간선이 `A→C`와 `B→C`일 때 방문 집합 `{A,B,C}`에서 부분그래프를 유도하면 가본 적 없는 `B→C`가 화면에 그려진다. 부모를 명시적으로 들고 있어야 그때 그 경로가 유일하게 복원된다.

**여정은 나무가 아니라 숲이다.** 저장된 여정에 없는 질문으로 들어오면 새 뿌리로 붙는다. 전에는 그 자리에서 판 것을 통째로 버렸다 — 새 탭으로 열거나 공유 링크를 타고 들어오면 지도가 사라졌다. 서로 안 이어진 갈래로 남는 것이 맞다. 억지로 이으면 가지 않은 길을 그린 것이 된다.

**같은 질문을 다시 물으면 새로 만들지 않는다.** 여기가 비용의 급소다.

처음에는 LLM이 자유 입력을 표준 문장으로 다듬고 그 해시를 캐시 키로 쓰려 했다. **실호출에서 반증됐다.** 같은 뜻의 세 표현이 세 개의 문장이 됐고, 바이트 단위 재현이 전제였던 비용 모델이 무너졌다. 원인은 프롬프트가 아니라 방식이었다 — LLM의 자유 생성은 결정론이 아니다.

지금은 **생성이 아니라 선택**이다. 후보를 주고 "같은 것을 묻는 게 있으면 골라라"고 시킨다. 출력이 문장이 아니라 id라 재현성이 훨씬 높고, 모델을 바꿔도 계약이 안 깨진다.

후보는 세 층에서 모은다 — 그래프 이웃(형제·조부모), 의미 관계(semantic_relation), 임베딩 코사인 이웃. 구조만 보던 시절에는 노드 321개 중 309개(96.3%)가 후보 0개였다. 게이트가 정확해도 보여줄 것이 없으면 매칭이 일어나지 않는다. 세 층을 합친 뒤 후보 0개는 19%까지 내려왔고, 남은 것은 주제가 실제로 외딴 질문들이다.

**잘못 나눈 노드는 나중에 합칠 수 있지만 잘못 합친 노드는 복구되지 않는다.** 그래서 게이트는 애매하면 고르지 않는다. 정확도 기준도 비대칭으로 잡았다 — precision은 100%, recall은 90%면 된다.

## 정확도 측정

게이트가 제대로 고르는지는 짐작이 아니라 실측으로 본다. 실제 `runGate`를 부르고, 함정(고르면 안 되는 것)을 세트의 4분의 1 넣는다. 매칭 케이스만 넣으면 "전부 고르는" 게이트가 만점을 받는데, 그게 최악의 게이트다.

```bash
npm run measure:match -- --runs 4                 # 튜닝 세트
npm run measure:match -- --set heldout --runs 3   # 홀드아웃
```

| 지표 | 뜻 | 목표 |
|---|---|---|
| precision | 고른 것 중 맞은 비율 | 100% — 잘못 합치면 되돌릴 수 없다 |
| recall | 골랐어야 할 것 중 고른 비율 | 90% — 놓치면 노드가 하나 더 생길 뿐이다 |
| 잘못 거절 | 멀쩡한 질문을 문전에서 막은 수 | 0 — 사용자가 겪는 실패 중 가장 나쁘다 |
| 어투 위반 | 새로 만든 문장이 경어체로 끝난 수 | 0 — 한 트리 안에서 말투가 갈리면 안 된다 |

뒤의 두 줄은 나중에 붙였다. precision은 매칭한 것만, recall은 매칭했어야 할 것만 본다. 멀쩡한 CS 질문을 거절하는 실패도, 판정은 맞았는데 문장이 "~인가요?"로 나오는 실패도 두 분모 어디에도 없다. 지표가 없는 동안 둘 다 실제로 일어나고 있었다.

**세트가 둘인 이유.** 프롬프트를 이 세트를 보면서 세 번 고쳤다(v2 → v3 → v4). 그 뒤의 만점은 일반화가 아니라 그 세트에 맞춰진 결과일 수 있다. 그래서 튜닝에 한 번도 쓰지 않은 세트를 따로 뒀다. 도메인도 겹치지 않게 골랐다.

| 세트 | 케이스 | 반복 | precision | recall | 잘못 거절 | 회차 간 흔들림 |
|---|---|---|---|---|---|---|
| 튜닝 | 46 | 4 | 124/124 | 124/124 | 0/172 | 0/46 |
| 홀드아웃 | 30 | 3 | 60/60 | 60/60 | 0/84 | 0/30 |

**"완벽하다"고 읽으면 안 된다.** 게이트 호출 274건에서 오류가 0건이라는 뜻이고, 표본이 그만큼이면 실제 오류율의 신뢰상한은 1% 안팎이다. 두 세트 모두 같은 사람이 같은 방식으로 만들었다는 한계도 그대로 있다. 프롬프트를 고칠 일이 생기면 튜닝 세트에서 고치고 홀드아웃은 결과만 읽는다 — 홀드아웃을 보고 고치는 순간 홀드아웃이 아니게 된다.

## 규칙을 검사한다

**검사하지 않는 규칙은 규칙이 아니라 바람이다.**

규칙은 오래 프롬프트에만 있었다. 강제하는 코드는 배치 스크립트 하나뿐이었고 그건 코퍼스를 만들 때 한 번 돈 오프라인 작업이다. **매일 올라오는 오늘의 질문과 사용자가 파는 모든 질문은 "비었나"만 통과하면 그대로 DB에 들어갔다.**

지금은 `src/lib/llm/content-rules.ts` 한 곳이 규칙을 갖고, 배치와 운영이 같이 부른다.

| | 무엇 | 어긋나면 |
|---|---|---|
| **막는다** | 문단 150자·꼬리질문 35자·꼬리질문 5개·꼬리질문 형식·도식 위치·도식 삼킴·낱말 반복 | 지적을 붙여 한 번 다시 부른다 |
| **적어둔다** | 도식 없음·문체(번역투·과장·접속부사·긴 문장) | 그대로 내보내고 로그에 센다 |

**던지지 않는다.** 문단이 170자인 해설은 읽기 불편할 뿐이지만 거기서 예외를 던지면 사용자는 아무것도 못 받는다. 두 번째도 어긋나면 **덜 어긋난 쪽**을 쓰고, 다시 부르는 것 자체가 실패하면(한도·과부하) 첫 번째를 쓴다. 검사를 붙였다고 전에 되던 것이 안 되면 안 된다.

```bash
npx tsx scripts/measure-rules.ts
```

| 대상 | 막힐 것 | 적어둘 것 | 깨끗 |
|---|---|---|---|
| 손으로 쓴 30개 (기준선) | 0 | 0 | 30 |
| 생성된 219개 | 0 | 52 (23.7%) | 167 |

기준선이 0인 것이 이 표의 요점이다. **기준선을 거는 검사기는 검사기가 틀린 것이다** — 사람이 좋다고 판단한 글을 버리게 만든다. 음절 단위로 낱말 반복을 잡으려던 시도가 그렇게 반증됐다(`사이사이`·`스스로`·`질의의`가 걸려 33% 오탐).

생성분의 막힐 것이 0인 이유는 이것들이 이미 배치 게이트를 통과한 것들이라서다(생존 편향). 그래서 이 숫자로 운영 재시도율을 짐작하면 안 된다.

그 과정에서 죽은 검사를 하나 찾았다. 배치 게이트가 파싱한 **문단**에서 `:::`를 찾고 있었는데, 파서는 알아본 울타리도 못 알아본 울타리도 전부 털어내고 문단을 내놓는다. 참이 될 수 없는 조건이라 한 번도 발동한 적이 없다. 진짜 신호는 반대쪽이었다 — **원문에 울타리가 있는데 도식 블록이 안 나오면 그리려던 그림이 통째로 사라진 것**이고, 독자에게는 안 그린 것과 똑같아 보여서 검사하지 않으면 영영 안 보인다.

## 도식이 실제로 붙는지

프롬프트만 고치고 넘어가면 모델이 따르는지 알 수 없다. 실호출로 잰다.

```bash
npm run measure:diagrams 2
```

| 지표 | 결과 |
|---|---|
| 도식이 붙은 해설 | 9/12 |
| 기호가 샌 해설 | 0/12 |
| 첫 도식이 답 바로 뒤 | 9/9 |
| 150자 넘는 문단 | 0/45 |
| 35자 넘는 꼬리질문 | 4/54 |

도식이 없는 건은 정상이다. 넣을 것이 없으면 넣지 말라고 프롬프트에 적었고, 억지로 만든 도식은 없는 것보다 나쁘다.

프롬프트에 도식 조각만 있고 완성된 해설 한 편이 없어서, 모델이 전체 모양을 본 적이 없었다. 한 편을 넣은 뒤 도식 채택률이 4/6에서 9/12로 올랐다. 넣은 예시는 측정에 쓰는 여섯 주제와 겹치지 않는 것으로 골랐다 — 측정 주제를 예시로 넣으면 그 측정이 무의미해진다.

**손으로 쓴 예시는 프롬프트에 안 들어간다.** `../data/example-nodes.ts`는 DB 시드 전용이다. 그래서 위 숫자는 규칙만으로 나온 결과다.

Mermaid를 쓰지 않았다. SVG 문자열을 `innerHTML`로 넣어야 하는데 자유 입력이 전역 자산이 되는 구조라 그 경로를 아예 두지 않는 편이 낫고, 2.8MB짜리 의존성이 붙고, 생김새가 이 디자인과 겉돈다. 전부 React 요소로 그린다.

파서의 첫째 성질은 **본문을 절대 먹지 않는 것**이다. 모델이 문법을 조금 틀렸다고 해설이 빈 화면이 되면 도식으로 얻은 것보다 잃는 것이 크다. 못 알아본 것은 문단으로 떨어지고, 어떤 이유로든 남은 울타리 기호는 화면에 닿기 전에 털어낸다.

## 본문을 읽는 문법

도식 말고도 본문에 쓸 수 있는 것이 셋 더 있다. **강조는 세게 하지 않는다** — 해설 한 편에서 눈에 띄는 자리가 여럿이면 어느 것도 안 띈다.

**답 블록.** 처음 나오는 문단에 `prose-lead`가 붙어 글씨가 한 단 커지고(1.125em) 왼쪽에 선이 선다. `blocks[0]`이 아니라 **처음 나오는 문단**을 찾는다 — 도식이 먼저 오는 글에서 도식에 이 스타일이 붙으면 안 된다.

**`==하이라이트==`.** `<mark>`로 그리되 글자 뒤를 통째로 칠하지 않고 `linear-gradient`로 **아래 40%만** 칠한다. 형광펜으로 밑줄 친 모양이다. 브라우저 기본 `<mark>`는 노란 바탕에 검은 글씨라 다크 모드에서 글자가 사라지므로 색을 직접 되돌린다.

인라인 갈래의 **순서가 곧 우선순위**다. 코드가 하이라이트보다 앞에 있어야 `` `a == b` `` 같은 비교 연산이 강조로 새지 않는다. 줄바꿈도 막았다(`[^=\n]`) — 안 막으면 서로 다른 문단의 `==`가 짝을 이뤄 그 사이를 통째로 칠한다.

**`:::note` · `:::warn`.** 각각 `핵심 정리`와 `주의`로 그린다. 라벨은 파서가 아니라 렌더러가 정한다. 답 블록과 **같은 시각 문법**(왼쪽 3px 선 + 옅은 바탕)을 쓰고 색으로만 갈린다. 안쪽은 문단과 같은 경로를 타므로 콜아웃 안에서도 코드·하이라이트·용어 링크가 살아 있다. 콜아웃만 빈 줄을 살려 받는데, 도식과 달리 여기서는 빈 줄이 문단 구분이라는 뜻이라서다.

간격도 위계다. 답 블록 뒤 28.8px > 문단 사이 20.8px > 도식 뒤 18px. 도식이 앞 문단에서 떨어져 나와 홀로 뜨지 않게 붙여 둔 것이다.

인라인 코드의 대비는 재서 골랐다 — 라이트 4.65:1, 다크 6.27:1로 둘 다 AA(4.5:1)를 넘긴다. 여유가 0.15밖에 없으므로 이 조합은 눈대중으로 바꾸면 안 된다.

## 이거 봤으면 이것도

해설 끝에 관련 질문 다섯 개를 붙인다. 꼬리질문과 **다른 것**이다. 꼬리질문은 새 글을 만들고 할당량을 깎는 단추이고, 이쪽은 이미 있는 글로 옆으로 옮기는 링크다. 그래서 하나는 버튼이고 하나는 `<a>`다.

후보는 두 층이고 **순서가 있다.**

1. **관계** — `semantic_relation`에서 표를 2개 이상 받은 것. 여기서 자리가 다 차면 벡터는 아예 묻지 않는다
2. **벡터** — 코사인 0.76 이상. 남은 자리만 채운다

여기서 votes는 사용자 추천이 아니다. **판정을 여러 회차 돌렸을 때 그 관계를 본 회차 수**다(기본 3회, 과반이 문턱). 사용자가 누르는 추천은 트리에 붙는 `upvotes`이고 이쪽과 아무 관계가 없다. 이름이 같아 헷갈리기 쉬운 자리다.

문턱을 매칭(0.85)보다 낮춘 것은 의도다. 0.85 위는 사실상 같은 질문이라 그것을 권하면 **방금 읽은 글을 다시 권하는 셈**이 된다. 0.76은 실측 분포의 90분위 자리다.

관계로 온 줄에는 왜 이어졌는지가 한 문장 붙고 벡터로 온 줄에는 안 붙는다. 판정이 이유를 남기고 코사인은 안 남기기 때문이고, 없는 이유를 지어내지 않는다.

두 층 모두 밑이 빠져도 안 죽는다. 관계 표를 통째로 지워도 벡터로, 임베딩 차원이 어긋나도 관계로 목록이 나온다. 둘 다 없으면 빈 목록이고 그때는 제목까지 통째로 안 그린다 — 빈 상자만 남는 것이 가장 나쁘다.

## 동시성 검증

테스트는 PGlite로 돈다. Postgres를 WASM으로 컴파일한 것이라 의미론은 같지만 **연결이 하나뿐이라 진짜 경합이 재현되지 않는다.** 행 잠금과 `on conflict` 경합은 순차 정합성만 증명된다.

그래서 실제 Postgres에 동시 요청을 던지는 검사를 따로 둔다.

```bash
npm run verify:concurrency
```

| 검사 | 무엇이 어긋나면 문제인가 | 결과 |
|---|---|---|
| 할당량 예약 | 한도 5에 20건이 몰릴 때 5건만 통과해야 한다 | 5/20 승인 |
| 추천 카운터 | 20명이 동시에 눌러도 카운터가 20이어야 한다 | 카운터 20 · 표 행 20 |
| 같은 사람 연타 | 카운터와 표 행이 어긋나면 사용자가 자기 표를 잃는다 | 일치 |
| 생성 리스 | 하나만 생성해야 한다. 여럿이면 그만큼 LLM을 태운다 | acquired 1 / busy 11 |
| 하루 하나 보장 | 같은 날짜에 트리가 둘 생기면 홈이 주인공을 못 고른다 | 트리 1개 |
| 시드 소비 | 밀린 시도가 시드를 되돌려야 400개가 안 녹는다 | 1개 소비 |

프로덕션 DB에 쓰기 때문에 흔적은 만든 자리에서 전부 지운다. 발행 검사는 2099년 날짜를 써서 실제 발행일과 겹칠 수 없게 했다.

**다른 작업과 겹쳐 돌리면 안 된다.** 시드 소비 검사는 전체 미소비 시드 수의 변화를 본다. 옆에서 발행이 돌다가 실패해 시드를 되돌리면 그 +1이 검사의 -1을 상쇄해서 멀쩡한 코드가 실패로 나온다. 실제로 한 번 겪었고, 옆 작업을 끄니 6/6이 됐다.

## 로그인은 이메일만 받는다

better-auth로 구글 로그인만 붙였다. **서버에 남는 것은 이메일과 세션뿐이다.** 이름도 프로필 사진도 받지 않는다.

better-auth에는 "이건 수집하지 마라"는 설정이 없다. 그래서 코드로 두 겹을 건다.

1. `mapProfileToUser` — 구글이 준 프로필에서 이름과 사진을 비워 넘긴다
2. `databaseHooks` — DB에 닿기 직전에 다시 지운다. 사용자의 이름·사진, 계정의 토큰 5종, 세션의 IP·UA

두 겹인 이유는 **한 겹이면 라이브러리가 경로를 바꿨을 때 조용히 새기 시작해서**다. 훅은 `create`와 `update` **양쪽**에 건다 — 생성만 막으면 재로그인 때 토큰이 다시 들어온다.

**DB 스키마는 그 컬럼들을 그대로 갖고 있다.** 막는 것은 코드 쪽이고 스키마는 저항하지 않는다. 배선이 끊기면 조용히 새는 구조라서, 시험이 소스를 문자열로 읽어 훅이 세 쌍 다 걸려 있는지를 센다. 실제 동작이 아니라 배선을 고정하는 방식이고 그 한계도 그대로다 — 테스트 DB인 PGlite에는 `pg.Pool`이 없어 인스턴스를 만들 수 없다.

`name`을 `null`이 아니라 빈 문자열로 두는 것은 스키마가 `not null`이라서다.

**탈퇴는 화면에서 두 번 묻는다.** 첫 클릭은 아무것도 지우지 않고 확인 문구를 펼칠 뿐이다. 브라우저 기본 `confirm`을 안 쓰는 이유가 있다 — 문구를 고를 수 없고, 사용자가 "이 페이지에서 대화상자를 다시 표시 안 함"을 켜면 **첫 클릭이 곧 삭제**가 된다.

지워지는 범위는 코드가 아니라 **DB의 `on delete cascade`가 정한다.** 세션·계정·여정 발자국·여정 커서·잔디가 사용자 행 하나에 걸려 있다. 순차 삭제 코드를 두지 않은 것은 표가 늘 때마다 빠뜨릴 자리가 생기기 때문이다. 브라우저에 남은 기록은 지워지지 않고, 화면이 그렇다고 먼저 말한다.

세션 `freshAge`를 0으로 껐다. 구글 전용이라 비밀번호 재확인 경로가 없는데, better-auth는 비밀번호 없는 탈퇴 요청에 세션 나이를 보고 `SESSION_EXPIRED`를 낸다. 껐으므로 재검토가 필요한 자리이고 주석에 그렇게 적어 뒀다.

**로그인은 선택이다.** 미들웨어가 없고, 세션을 읽는 라우트는 동기화용 셋뿐이다. 로그인하지 않아도 전부 그대로 돌아간다. 로그인이 주는 것은 하나 — 기기 간 동기화다. 그 이상으로 적으면 로그인한 사람이 "그래서 뭐가 달라졌지"를 겪는다.

## 기기 간 동기화

여정과 잔디를 계정에 올려 다른 기기에서 이어본다. `SyncAgent`가 `(site)` 레이아웃에 하나 살면서 **세션에서 읽은 userId가 채워질 때 한 번** 돈다. 주기 실행도 이탈 훅도 없고, `sessionStorage` 마커가 탭당 1회로 더 줄인다.

**더하기만 한다.** 치환 엔드포인트(PUT)를 아예 만들지 않았고 서버 코드에 `delete from`이 없다. 엔드포인트 이름으로 실수를 막는 쪽을 골랐다. 서버 행이 사라지는 유일한 경로는 탈퇴 cascade다.

합칠 수 있는 이유는 발자국의 정체성을 **경로**로 잡았기 때문이다. `pathKey`는 뿌리부터 그 발자국까지의 nodeId를 `>`로 이은 문자열이다. occurrence id는 브라우저가 만들어 기기마다 다르므로 id로는 같은 자리를 못 알아본다. 같은 노드라도 부모가 다르면 다른 키이고, 그것이 맞다 — 다른 경로로 도달한 것은 다른 발자국이다.

**서버가 pathKey를 다시 계산한다.** 클라이언트가 보낸 키를 그대로 믿으면 조작한 키 하나로 남의 경로 자리를 차지할 수 있다. `unique (user_id, path_key)`가 중복을 DB에서 막고 재전송은 `on conflict do nothing`이 받는다.

로컬이 이기는 자리는 **커서 하나**다. 로컬은 방금 보던 자리이고 서버는 다른 기기에서 예전에 보던 자리다. 발자국 자체는 겹치면 서버 id를 남긴다 — 다음 동기화 때 같은 행으로 접히게 하려는 것이다.

잔디는 날짜별로 **id 집합의 합집합**이다. 편수를 더하지 않는다. 저장하는 것이 숫자가 아니라 그날 연 질문의 id라서 같은 날 같은 글을 몇 번 읽어도 하나로 센다. 날짜는 클라이언트의 KST 판정을 그대로 받는다 — 서버 시각으로 다시 정하면 자정 근처에 올린 기록이 다른 날에 적힌다.

**실전에서 400을 두 번 맞았고 원인이 서로 달랐다.**

첫째, 옛 버전이 저장한 여정에 미아 부모·중복 id가 남아 있었다. 보내기 전에 정화한다 — 규칙은 하나, **앞서 나온 발자국만 부모로 인정한다.** 이 한 줄로 미아·순서 위반·순환이 같이 정리된다. 손상된 것을 지우지 않고 뿌리로 올리는데, 숲이어도 되기 때문이다.

둘째, 서비스 초기에 팠다가 재시드로 사라진 노드가 브라우저에 남아 있었다. 처음에는 전체를 거부했고, 그러면 **그 사용자만 동기화가 영영 실패한다.** 지금은 죽은 노드와 그 자손 가지만 버리고 나머지를 받는다. 자손까지 버리는 것은 자손의 pathKey에 죽은 nodeId가 박혀 있어서다 — 오염된 키를 저장하면 그 경로는 영영 안 접힌다.

두 방어 모두 규모를 로그에 센다. 응답 본문은 로그에 안 남으므로 400의 사유를 서버가 직접 적어야 한다.

실패하면 마커를 남기지 않는다. 그래서 다음 기회에 저절로 다시 시도하고, 그동안 로컬 기록은 손대지 않는다.

## 학습 기록을 그림으로

잔디를 PNG로 구워 공유 시트에 넘긴다. **서버에서 굽지 않는다** — 잔디의 재료가 localStorage에 있어서 서버는 그 사람의 기록을 모른다. 캔버스 2D API로 직접 그리고 의존성은 하나도 안 늘렸다.

그리는 함수는 캔버스를 만들지 않고 **붓(`ctx`)을 받는다.** 시험 환경(happy-dom)에 2D 컨텍스트가 없어서 실물로는 검사할 수 없기 때문이다. 가짜 붓을 넣어 좌표·색·문구를 숫자로 잰다.

색은 다크 테마 값을 미리 섞어 상수로 박았다. 화면 잔디는 `color-mix(in oklab, …)`를 쓰지만 **캔버스는 CSS를 모른다.** 주소도 상수다 — 사이트 주소를 환경변수에서 읽으면 그것이 비었을 때 공유한 그림에 `localhost`가 박힌다.

공유는 `navigator.canShare({ files })`에 **파일을 실제로 넣어 물어본 뒤** 갈린다. `navigator.share`의 존재만 보면 파일을 못 받는 브라우저에서 실패한다. 사용자가 공유 시트를 닫으면 조용히 돌아간다 — 거기서 다운로드로 넘어가면 취소가 취소가 아니게 된다.

## 카카오톡 스킬 서버

`POST /api/kakao/skill`이 오픈빌더의 스킬 서버다. 채널 친구가 봇에게 말을 걸면 카카오가 여기를 부르고 2.0 규격 JSON으로 답한다. 먼저 보내는 푸시(알림톡)는 사업자 영역이라 없다.

**언제나 200으로 답한다.** 오픈빌더는 200이 아니면 "스킬 실패" 오류 블록을 사용자에게 보여준다. 임베딩이 죽어도 발화가 비어도 실패를 말로 전한다.

발화는 네 갈래로 나뉜다 — 도움말, 질문 목록, `오늘`이 들어간 말, 그 외 전부. 마지막이 검색이다. 발화를 그대로 임베딩해 코사인 0.55 이상인 질문 셋을 준다. 매칭 문턱(0.85)이 "같은 질문"의 기준인 데 비해 여기는 "관련 있으면" 충분하다.

모든 응답 아래에 바로가기 두 개(`오늘의 질문`·`질문 목록 보기`)가 붙는다. 링크가 아니라 **그 문구를 발화로 되쏘는** 버튼이라, 폴백 블록이 이 스킬로 돌려보내면 오픈빌더에 발화 블록을 따로 만들 필요가 없다.

인증이 없다. 오픈빌더 스킬 호출에는 서명이 없고, 돌려주는 것이 전부 공개 데이터(발행된 질문과 해설)라 위험이 낮다. 비용이 드는 곳은 임베딩 하나뿐이라 발화를 200자에서 자른다.

## 무료 티어로 돈다

Gemini 무료 티어 안에서 굴러가게 짰다.

**모델을 일마다 다르게 쓴다.** 매칭 게이트는 매 요청마다 도니 가장 싼 것을, 해설 생성은 사용자가 실제로 읽는 글이라 한 단계 위를, 오늘의 질문은 하루 한 번이고 서비스의 얼굴이라 품질을 앞에 둔다.

**키와 모델 양쪽으로 폴백한다.** 한도·인증·일시 오류·치명 오류를 갈라서, 한도면 다음 모델로 내려가고 일시 오류면 같은 조합을 한 번 더 친다. 사슬의 끝은 Gemma다.

비용 모델은 **캐시가 하나도 안 맞는다고 치고** 짰다. 캐시는 하되 적중률을 비용 계산의 전제로 삼지 않는다. 적중률을 모르는 채로 안전한 쪽이다.

## 알려진 한계

- **해설 스트리밍이 없다.** `POST /api/expand`가 JSON 통짜 응답이라 대기가 그대로 대기다. 재보니 꼬리질문을 누르고 새 화면까지 35초였다. 지금은 시간대별로 말이 바뀌는 안내로 대체한다
- **꼬리질문 35자 규칙이 모바일에서 성립하지 않는다.** 390px에서 라벨 칸이 274px, 한글 한 자가 12.98px이라 **한 줄에 21자**가 한계다. 33자짜리도 두 줄로 접힌다. 지금 규칙은 데스크톱 기준이다
- ~~인증이 없다~~ **로그인이 생겼지만 따라오는 것은 여정과 잔디뿐이다.** 트리 추천은 여전히 `anon:` 키로만 세고 세션과 안 잇는다. 기기를 옮기면 내가 누른 추천은 안 따라온다
- **로그인해도 할당량은 익명과 같다.** `QUOTA_LOGIN_DAILY`가 환경변수에 있지만 코드가 아직 읽지 않는다. 할당량 키도 여전히 IP 기반이라, 같은 IP를 쓰는 사람들이 한 통을 나눠 쓴다
- **`/map`에서는 동기화가 돌지 않는다.** `SyncAgent`가 `(site)` 레이아웃에 있는데 지도는 그 밖의 전체 화면이다. 지도만 열고 있으면 그 세션에서는 안 돈다
- **익명 하루 한도를 임시로 9999회까지 열어 뒀다.** 기본값은 5회이고 `QUOTA_ANON_DAILY`로 바꾼다. 5회로 되돌리면 그래프가 작을수록 새 생성이 많아, 서비스가 가장 비어 있을 때 사용자가 가장 빨리 막힌다
- **문의 주소가 HTML에 그대로 실린다.** 헤더의 메일 주소가 수집 봇에 긁힌다. GitHub 이슈만 두는 것보다 문턱이 낮은 쪽을 골랐고, 스팸이 실제로 오면 폼으로 바꾼다
- ~~거의 같은 질문이 따로 떠 있다~~ **접었다.** 임베딩 0.90+ 쌍을 판정해 중복 20쌍을 등가로 기록하고(qnode_equivalence), 목록·지도에서 잉여를 접는다. 옛 주소는 산다. 새 중복이 생기면 같은 절차로 늘린다
- **무료 한도가 마르면 오늘의 질문 발행이 사실상 멈춘다.** 사슬을 계측해서 원인을 갈랐다.

  | 구간 | 처음 잰 값 | 지금 (2026-08-06) |
  |---|---|---|
  | 3.5-flash → quota 실패 | 9.0초 | **0.7초** |
  | 3.6-flash → quota 실패 | 15.9초 (누적) | **1.0초 (누적)** |
  | Gemma가 답하는 자리 | 10초일 때도, 120초를 넘길 때도 있다 | 그대로 |

  사슬 통과 시간이 16초에서 1초로 줄었다. AI SDK가 안에서 3번 재시도하고 있었고, 우리 폴백 사슬이 이미 같은 일을 더 잘하는데 그 앞에서 backoff를 두 번 기다리고 있었다(`maxRetries: 0`). 답하는 모델에게 44초밖에 못 주던 것이 59초가 됐다.

  무료 하루 한도도 정확한 값을 오류 본문에서 읽었다. `gemini-3.6-flash`는 `generate_content_free_tier_requests limit: 20` — **하루 20건**이다. 대량 배치에 쓸 수 없다. Gemma는 자릿수가 다르다.

  프롬프트 크기 탓이 아니다. 같은 프롬프트·같은 시드 주제어로 `generateDailyRoot`를 다섯 번 부르니 전부 24.8~26.6초에 성공했다. 실패는 Gemma 응답 시간이 길게 튀는 회차에서만 난다.

  그 과정에서 버그를 하나 잡았다. `This model is currently experiencing high demand.`가 `fatal`로 분류돼 폴백 사슬을 통째로 건너뛰고 있었다. 낱말 목록에 걸리는 것이 하나도 없어서였다. 과부하는 저쪽 사정이라 다른 모델에서는 되는데 시도조차 안 했다. `transient`로 고쳤다.

  대응은 두 겹이다. 워크플로가 30초 간격으로 **세 번까지 다시 던진다** — 응답 시간이 회차마다 갈리니 한 번 실패했다고 그날 질문이 없어질 이유가 없다. 하루 하나는 DB가 보장하므로 재시도가 중복 발행을 만들지 않는다. 그리고 한도가 살아 있는 시간대에 며칠치를 미리 뽑아둘 수 있다 — 미래 발행분은 목록에도 직접 URL에도 안 나오므로 하루 하나라는 약속은 지켜진다.

  근본 해결은 Gemma에 기대지 않는 것이다. 사슬 끝을 응답 시간이 안정적인 모델로 바꾸는 쪽이다. 프롬프트를 줄이는 것은 답이 아니다 — 위 실측이 프롬프트 크기를 이미 배제했다
