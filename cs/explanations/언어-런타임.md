## 8. equals를 재정의할 때 hashCode도 함께 재정의해야 하는 이유는?

해시 기반 컬렉션이 두 메서드를 함께 쓰기 때문이다. 하나만 바꾸면 컬렉션이 같은 객체를 다른 객체로 취급한다.

HashMap은 먼저 hashCode로 버킷을 찾고 그 안에서 equals로 비교한다. equals만 재정의하면 논리적으로 같은 두 객체가 서로 다른 버킷으로 흩어진다. equals 비교까지 가지도 못하므로 조회가 실패한다.

1. **get(key) → hashCode** — 어느 버킷인지 먼저 정한다
2. **hashCode → 버킷** — 그 버킷 안의 후보들만 꺼낸다
3. **버킷 → equals** — 후보와 하나씩 견준다. **여기까지 와야 비교가 일어난다**

규약은 단방향이다. equals가 true면 hashCode는 반드시 같아야 한다. 반대는 성립하지 않는다. hashCode가 같아도 equals는 false일 수 있고 이게 해시 충돌이다.

실무에서 자주 터지는 자리는 JPA 엔티티다. 식별자가 영속화 시점에 채워지므로 id 기반 hashCode는 저장 전후로 값이 바뀐다. Set에 넣어둔 엔티티를 저장하면 다시 찾지 못하게 된다.

가변 필드를 hashCode에 쓰는 것도 같은 함정이다. 컬렉션에 넣은 뒤 필드를 바꾸면 그 객체는 사실상 사라진다.

## 19. setTimeout(0)이 즉시 실행되지 않는 이유는?

콜백이 큐에 들어갈 뿐이고, 지금 돌고 있는 코드가 끝나야 이벤트 루프가 그것을 꺼내기 때문이다. 0은 "지금"이 아니라 "가능한 가장 이른 다음 차례"라는 뜻이다. 게다가 꺼내 가는 큐가 하나도 아니다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 지금 도는 동기 코드 | 이게 끝나야 아래로 내려간다 |
| 마이크로태스크 큐 | Promise.then. 비워질 때까지 전부 |
| 매크로태스크 큐 | setTimeout, 이벤트 콜백. 한 번에 하나 |

자바스크립트는 한 번에 하나의 콜스택만 돌린다. 루프는 스택이 빌 때까지 아무것도 꺼내지 않는다. 앞선 동기 코드가 100밀리초를 쓰면 setTimeout(0)도 그만큼 밀린다.

마이크로태스크 큐는 매크로태스크보다 먼저, 그리고 스택이 빌 때마다 전부 비워진다. 그래서 나중에 등록한 Promise.then이 먼저 등록한 setTimeout(0)보다 앞선다.

브라우저는 여기에 하한을 하나 더 얹는다. 중첩이 일정 단계를 넘으면 0을 요청해도 최소 지연이 걸린다. 재귀적으로 setTimeout(0)을 걸어 바쁘게 도는 코드를 막기 위한 장치다.

실무에서 이 구조가 드러나는 자리는 화면이 멈출 때다. 무거운 계산이 한 덩어리로 돌면 그동안 렌더링도 입력도 처리되지 않는다. 작업을 잘라 큐에 나눠 넣으면 사이사이에 화면이 숨을 쉰다 — setTimeout(0)의 쓸모가 대부분 여기에 있다.

## 21. 메모리 관점에서 값 타입과 참조 타입의 선택 기준은 무엇인가?

값 타입과 참조 타입을 선택하는 핵심 기준은 데이터의 생명주기와 크기, 그리고 불변성 여부다. 값 타입은 스택(Stack) 영역에 값이 직접 저장되어 할당과 해제가 빠르지만 데이터 복사 비용이 발생한다. 반면 참조 타입은 힙(Heap) 영역에 실제 데이터를 두고 스택에는 주소만 저장하므로, 데이터가 크거나 여러 곳에서 공유해야 할 때 유리하다.

아래 구조는 두 타입이 메모리에 저장되는 물리적 위치의 차이를 나타낸다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 힙 영역 | 참조 타입의 실제 데이터 (예: 인스턴스, 배열) |
| 스택 영역 | 값 타입의 데이터 직접 저장 / 참조 타입의 주소값(포인터) 저장 |

작고 수명이 짧으며 변경할 필요가 없는 데이터는 값 타입으로 선언하여 가비지 컬렉션(GC)의 부담을 줄이는 것이 좋다. 반면, 데이터의 크기가 크거나 시스템 전체에서 동일한 인스턴스를 공유하며 상태를 변경해야 한다면 참조 타입을 선택해야 한다. 이때 참조 타입은 주소만 복사하므로 전달 비용은 저렴하지만, 힙 메모리 관리와 GC 오버헤드가 발생한다는 트레이드오프가 존재한다.

## 32. 가비지 컬렉션이 멈춤을 만드는 이유는?

살아 있는 객체를 세는 동안 그 관계가 바뀌면 안 되기 때문이다. 세는 중에 애플리케이션이 참조를 바꾸면 이미 확인한 것이 틀려져서, 그 구간만은 실행을 세운다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| Eden | 새 객체가 여기 태어난다. 대부분 금방 죽는다 |
| Survivor | 한두 번 살아남은 것이 잠시 머문다 |
| Old | 오래 산 것이 승격된다. 여기 청소가 비싸다 |

대부분의 객체는 태어나자마자 죽는다. 그래서 젊은 영역만 자주 짧게 치우고 늙은 영역은 가끔 손댄다. 젊은 쪽 청소는 보통 밀리초 단위라 눈에 안 띈다.

문제는 늙은 영역이다. 대상이 많고 흩어져 있어 오래 걸리고, 그동안 응답이 멈춘다. 힙을 키우면 빈도는 줄지만 한 번의 멈춤은 길어진다 — 총량과 최악값의 맞바꿈이다.

요즘 수집기는 세는 일 대부분을 실행과 겹쳐서 한다. 멈추는 구간을 시작과 끝의 짧은 두 번으로 줄이는 방식이다. 완전히 없애지는 못한다.

## 62. 객체와 호출 프레임은 왜 따로 저장하는가?

객체는 여러 스레드가 공유할 수 있어 힙에 둔다. 호출 프레임은 스레드마다 독립된 실행 상태라 각 JVM 스택에 둔다.

| 기준 | 공유 영역 | 스레드별 영역 |
| --- | --- | --- |
| 대표 공간 | 힙, 메서드 영역 | JVM 스택, PC 레지스터 |
| 수명 | JVM과 함께 | 스레드와 함께 |

프레임에는 지역 변수, 피연산자 스택, 반환 정보가 있다. 메서드가 끝나면 프레임이 사라져 별도 GC가 필요 없다.

힙의 객체는 참조가 끊겨도 바로 사라지지 않는다. GC가 도달 불가능하다고 판단한 뒤 회수한다.

메서드 영역은 명세상의 공유 영역이다. HotSpot은 클래스 메타데이터를 네이티브 메모리의 Metaspace에 둔다.

## 63. 순환 참조 객체도 회수할 수 있는 이유는?

HotSpot의 추적식 수집기는 참조 횟수가 아니라 GC 루트에서 도달 가능한지를 본다. 서로 가리켜도 루트에서 닿지 않으면 둘 다 회수 대상이다.

1. **GC 루트 → 객체 그래프** — 참조를 따라 생존 객체를 표시한다
2. **수집기 → 미도달 객체** — 메모리를 회수한다
3. **수집기 → 생존 객체** — 필요하면 이동하고 압축한다

GC 루트에는 실행 중인 스레드의 스택 참조와 정적 참조 등이 포함된다. 루트가 살아 있으면 그 경로의 객체도 살아 있다.

세대별 수집은 대다수 객체가 빨리 죽는다는 관찰을 이용한다. 새 객체를 자주 수집하고 오래 산 객체는 승격한다.

표시와 이동 과정에는 일시 정지가 생길 수 있다. 동시 수집기는 일부 단계를 애플리케이션과 겹쳐 정지 시간을 줄인다.

## 64. 수집기는 처리량과 지연 중 무엇으로 고르는가?

배치 작업은 처리량을, 응답형 서비스는 최악 지연 시간을 우선한다. 힙 크기, CPU 여유, 할당률과 실제 JDK 지원 범위도 함께 본다.

| 기준 | Parallel GC | ZGC |
| --- | --- | --- |
| 우선 목표 | 높은 처리량 | 짧은 정지 |
| 대가 | 긴 정지 가능 | CPU·메모리 여유 필요 |

Parallel GC는 수집 중 애플리케이션을 멈추고 여러 GC 스레드를 쓴다. 작업 완료량은 높지만 살아 있는 집합이 크면 정지가 길어진다.

ZGC는 표시와 재배치 대부분을 동시에 수행한다. 짧은 정지를 목표로 하지만 장벽 비용과 충분한 힙 여유가 필요하다.

G1은 리전 단위로 수집해 처리량과 정지 목표를 절충한다. 선택 전 운영과 같은 부하에서 p99 지연, 처리량, GC CPU를 측정한다.

## 65. 왜 모든 바이트코드를 바로 최적화하지 않는가?

모두 최적화하면 시작이 느려지고 실행되지 않을 코드에도 비용을 쓴다. JVM은 실행 정보를 모아 자주 쓰이는 코드만 기계어로 최적화한다.

1. **인터프리터 → 프로파일** — 실행 횟수와 타입을 수집한다
2. **프로파일 → JIT** — 뜨거운 메서드와 루프를 고른다
3. **JIT → 기계어** — 인라이닝과 특수화를 적용한다

HotSpot의 계층형 컴파일은 C1으로 빠르게 컴파일한 뒤 충분히 뜨거운 코드를 C2로 더 최적화한다. 시작 속도와 최고 성능을 절충한다.

JIT는 관찰된 타입을 바탕으로 가상 호출을 인라이닝할 수 있다. 가정이 깨지면 최적화 코드를 폐기하고 디옵티마이즈한다.

그래서 짧은 벤치마크는 워밍업과 컴파일 시간을 섞어 잘못 읽기 쉽다. JMH처럼 워밍업과 측정을 분리해야 한다.

## 66. 이름이 같은 클래스가 다른 타입이 되는 조건은?

바이너리 이름이 같아도 정의한 클래스 로더가 다르면 JVM은 다른 타입으로 본다. 런타임 타입은 이름과 정의 로더의 조합이다.

| 기준 | 같은 타입 | 다른 타입 |
| --- | --- | --- |
| 바이너리 이름 | 같다 | 같을 수 있다 |
| 정의 로더 | 같다 | 다르다 |

로딩 뒤 검증과 준비를 한다. 심벌 참조의 해결은 필요할 때 늦출 수 있다. 처음 적극 사용하면 정적 초기화가 실행된다.

부모 우선 위임은 이미 로드된 핵심 클래스의 중복 정의를 막는다. 플러그인과 서버는 격리를 위해 이 순서를 일부러 뒤집기도 한다.

서로 다른 로더가 만든 객체는 이름이 같아도 캐스팅할 수 없다. 로더가 실행 중인 스레드나 외부 정적 참조에 붙잡히면 클래스도 언로드되지 않는다.

## 67. 서로 다른 List 타입 인자는 런타임에 남는가?

객체 자체에는 보통 남지 않는다. 컴파일러가 타입 안전성을 검사한 뒤 타입 인자를 소거한다. 문자열 List와 정수 List는 런타임에 같은 클래스다.

| 기준 | 컴파일 시점 | 런타임 |
| --- | --- | --- |
| 타입 인자 | 검사한다 | 객체에는 없다 |
| 형변환 | 필요한 곳에 삽입한다 | 실행 중 검사한다 |

소거 뒤 오버라이딩 시그니처가 달라질 수 있다. 컴파일러는 다형성을 유지하려고 합성 브리지 메서드를 만든다.

타입 변수의 직접 인스턴스화와 배열 생성은 제한된다. 구체 타입 인자를 붙인 타입을 instanceof로 검사하거나 소거형이 같은 메서드를 오버로드할 수도 없다.

다만 필드와 메서드 선언의 제네릭 시그니처는 클래스 파일에 남을 수 있다. 리플렉션은 그 선언 정보를 읽지만 객체의 실제 타입 인자를 복원하지는 못한다.

## 68. 상태 변경을 막으면 동시성에서 무엇을 얻는가?

생성 뒤 상태가 변하지 않으면 여러 스레드가 잠금 없이 공유하기 쉽다. 해시 키도 안정된다. 대신 변경마다 새 객체가 필요하다.

| 기준 | 불변 객체 | 가변 객체 |
| --- | --- | --- |
| 공유 | 동기화 부담이 작다 | 경쟁을 제어해야 한다 |
| 변경 | 새 객체를 만든다 | 제자리에서 바꾼다 |

필드를 private final로 두는 것만으로는 부족하다. 생성자에서 가변 인자를 복사하고 내부 배열과 컬렉션도 방어적 복사로 반환해야 한다.

final 필드는 생성자 종료 뒤 초기화 안전성을 제공한다. 단, 생성 중 this가 외부로 노출되면 이 보장이 깨질 수 있다.

작은 값 객체에는 잘 맞는다. 큰 그래프를 자주 갱신하면 할당과 복사 비용이 커져 빌더나 구조 공유 컬렉션이 필요할 수 있다.

## 69. 동등한 객체의 해시값도 같아야 하는 이유는?

해시 컬렉션은 hashCode로 버킷을 고른 뒤 equals를 확인한다. 동등한 객체의 해시값이 다르면 다른 버킷을 찾아 같은 키를 놓친다.

1. **조회 키 → hashCode** — 검색할 버킷을 고른다
2. **버킷 → equals** — 후보와 논리적 동등성을 비교한다
3. **equals → 결과** — 같은 키인지 결정한다

equals는 반사성, 대칭성, 추이성, 일관성을 지켜야 하며 null에는 거짓이어야 한다. hashCode는 동등하면 같아야 하지만 충돌은 허용된다.

두 메서드에 쓰는 필드가 달라지면 규약이 깨진다. 특히 키를 Map에 넣은 뒤 해시에 쓰인 필드를 바꾸면 다시 찾지 못할 수 있다.

상속 계층에서 값 동등성을 추가하면 대칭성이 쉽게 깨진다. 값 객체는 불변으로 만들고 두 메서드를 같은 필드에서 함께 생성하는 편이 안전하다.

## 70. 체크 예외는 언제 API 계약에 넣는가?

호출자가 복구 전략을 세울 수 있고 반드시 처리 여부를 결정해야 할 때 체크 예외를 계약에 넣는다. 프로그래밍 오류에는 런타임 예외가 맞다.

| 기준 | 체크 예외 | 런타임 예외 |
| --- | --- | --- |
| 컴파일러 | 처리·선언을 강제한다 | 강제하지 않는다 |
| 적합한 상황 | 예측 가능한 복구 | 계약 위반·버그 |

Exception의 하위 타입 중 RuntimeException이 아닌 예외는 체크 대상이다. Error와 런타임 예외는 컴파일러가 처리나 선언을 강제하지 않는다.

체크 예외를 너무 넓게 쓰면 호출 계층마다 의미 없는 catch와 throws가 퍼진다. 복구할 수 없으면 도메인 런타임 예외로 번역하되 원인을 보존한다.

예외를 경계에서 번역하면 저장소나 네트워크 구현을 API 밖으로 숨길 수 있다. 메시지와 원인, 복구 가능 여부를 계약에 명확히 둔다.

## 71. 중간 연산을 바로 실행하지 않는 이유는?

종료 연산이 요구할 때까지 미루면 여러 중간 연산을 한 번의 순회로 결합할 수 있다. 단락 종료로 필요한 원소만 처리할 수도 있다.

1. **스트림 소스 → 중간 연산** — 실행하지 않고 단계를 기록한다
2. **종료 연산 → 스트림 소스** — 원소 처리를 요구한다
3. **스트림 소스 → 결과** — 필터와 변환을 한 순회로 적용한다

filter와 map 같은 상태 없는 연산은 원소 하나씩 이어서 처리한다. sorted와 distinct 같은 상태 있는 연산은 지연 실행이어도 버퍼를 쓸 수 있다.

findFirst와 anyMatch는 답이 정해지면 순회를 멈춘다. 무한 스트림도 그 전에 전체 입력을 요구하는 연산이 없다면 유한 시간에 끝날 수 있다.

스트림은 한 번만 소비할 수 있다. 공유 상태를 바꾸는 부수 효과는 지연 실행과 병렬 처리에서 순서와 안전성을 흐리므로 피해야 한다.

## 72. 락보다 높은 수준의 도구를 먼저 고르는 이유는?

검증된 원자 연산과 대기 정책을 재사용해 경쟁 조건과 교착 위험을 줄이기 때문이다. 작업 성격에 맞는 가장 높은 수준의 도구를 고른다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| CompletableFuture | 비동기 결과 조합 |
| ExecutorService | 실행 정책과 작업 분리 |
| BlockingQueue | 생산자·소비자 조절 |
| 동시 컬렉션·원자 변수 | 공유 상태 갱신 |
| Lock·동기화 도구 | 임계 구역 제어 |

공유 맵의 get 뒤 put은 두 번의 연산이라 경쟁할 수 있다. ConcurrentHashMap의 computeIfAbsent처럼 의도를 한 원자 연산으로 표현해야 한다.

AtomicInteger는 한 값의 갱신에는 맞지만 여러 필드 불변식까지 묶지 못한다. 그런 경우 Lock이나 synchronized로 임계 구역을 만든다.

ExecutorService는 작업 제출과 스레드 생명 주기를 분리한다. 큐 용량과 거부 정책을 정하지 않으면 과부하가 메모리 증가로 바뀔 수 있다.

## 73. volatile은 무엇을 보장하고 놓치는가?

volatile 쓰기는 뒤따르는 같은 변수의 읽기보다 먼저 일어난다. 해당 접근을 경계로 가시성과 재정렬 제약을 제공하지만 복합 연산은 원자화하지 않는다.

| 기준 | volatile | synchronized |
| --- | --- | --- |
| 가시성·순서 | 보장한다 | 보장한다 |
| 복합 연산 원자성 | 보장하지 않는다 | 같은 모니터로 보호할 때 보장한다 |

한 스레드가 volatile 변수에 쓰기 전에 수행한 일반 쓰기도 그 값을 읽은 스레드에 보인다. 이 happens-before 관계가 다른 상태의 전달까지 만든다.

단순 상태 플래그와 완전히 생성된 객체 참조의 게시에는 적합하다. 이중 확인 잠금의 인스턴스 참조에도 필요하다.

count++는 읽기, 계산, 쓰기의 세 단계라 volatile이어도 갱신을 잃을 수 있다. 경쟁 갱신에는 AtomicInteger나 잠금이 필요하다.

## 74. 스레드를 늘려도 CPU 병렬성이 없는 이유는?

CPython 기본 빌드에서는 한 프로세스의 스레드 하나만 한 시점에 파이썬 바이트코드를 실행한다. CPU 연산 스레드를 늘리면 GIL 경합과 전환 비용만 커질 수 있다.

| --- | --- | --- |

## 75. 참조 횟수가 0이 아닌 객체도 왜 수거되는가?

CPython의 참조 카운팅만으로는 서로를 가리키는 순환 객체를 해제할 수 없다. 외부에서 닿지 않는 순환은 별도 순환 수집기가 찾아 수거한다.

| 기준 | 참조 카운팅 | 순환 수집 |
| --- | --- | --- |
| 해제 조건 | 참조 수 0 | 외부에서 도달 불가 |
| 시점 | 대체로 즉시 | 수집 주기 |
| 강점 | 예측 가능 | 순환 처리 |

참조 횟수가 0이 되면 대부분 즉시 해제된다. 순환 수집기는 추적 대상 컨테이너를 세대별 정책으로 검사한다. 오래 살아남은 객체는 덜 자주 본다.

gc.disable()은 자동 순환 수집만 끈다. 참조 카운팅은 계속 동작한다. 수집 빈도를 낮추면 정지는 줄지만 순환 객체의 메모리 회수는 늦어진다.

## 76. Promise와 타이머 중 무엇이 먼저 실행되는가?

같은 턴에 예약됐다면 Promise 콜백이 보통 타이머보다 먼저 실행된다. 현재 태스크가 끝난 뒤 마이크로태스크 큐를 비우고 다음 타이머 태스크를 꺼내기 때문이다.

1. **현재 태스크 → 마이크로태스크** — Promise 콜백을 모두 처리한다
2. **마이크로태스크 → 렌더링 기회** — 브라우저가 갱신할 수 있다
3. **렌더링 기회 → 다음 태스크** — 타이머나 이벤트 하나를 처리한다

Promise.then과 queueMicrotask는 마이크로태스크다. setTimeout 콜백은 태스크다. await 뒤의 연속 실행도 마이크로태스크로 재개된다.

마이크로태스크가 계속 새 작업을 넣으면 렌더링과 타이머가 굶는다. 긴 동기 코드도 루프를 막는다. Node.js는 단계별 세부 순서가 브라우저와 다르다.

## 77. 함수가 끝난 뒤 지역 변수가 남는 이유는?

내부 함수가 지역 변수의 렉시컬 환경을 계속 참조하기 때문이다. 바깥 함수 호출이 끝나도 내부 함수가 살아 있으면 캡처한 바인딩도 유지된다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 내부 함수 | 실행 코드와 환경 참조를 가진다 |
| 렉시컬 환경 | 캡처한 변수 바인딩을 보관한다 |
| 참조된 객체 | 도달 가능한 동안 메모리에 남는다 |

클로저는 값을 만든 시점의 복사본이 아니라 바인딩을 잡는다. 같은 바인딩을 공유한 함수들은 변경을 함께 본다. let의 블록별 바인딩은 루프 문제를 피한다.

은닉 상태와 콜백에 유용하지만 큰 객체를 캡처하면 수명이 늘어난다. 이벤트 리스너와 타이머를 해제해 불필요한 참조를 끊어야 한다.

## 78. 속성이 없을 때 엔진은 어디까지 찾는가?

객체의 자체 속성을 먼저 보고, 없으면 내부 프로토타입을 따라 같은 키를 찾는다. 일치할 때까지 반복하며 체인의 끝인 null에 닿으면 undefined가 된다.

1. **객체 → 자체 속성** — 키가 있는지 확인한다
2. **키 없음 → 프로토타입** — 같은 키를 찾는다
3. **키 계속 없음 → 상위 프로토타입** — null까지 반복한다

하위 객체에 같은 키가 있으면 상속 속성을 가린다. 대입은 보통 자체 속성을 만들지만 상속된 setter나 쓰기 금지 속성이 있으면 결과가 달라진다.

class의 인스턴스 메서드는 prototype에 둔다. static 메서드는 클래스 생성자 자체에 두며 각 위치에서 같은 속성 탐색 규칙을 따른다.

## 79. let도 끌어올려지는데 왜 바로 읽지 못하는가?

let과 const의 바인딩은 스코프 시작 때 만들어지지만 선언문을 평가하기 전에는 초기화되지 않는다. 이 시간적 사각지대에서 읽으면 ReferenceError가 난다.

| 기준 | var | let·const |
| --- | --- | --- |
| 실행 전 상태 | undefined로 초기화 | 미초기화 |
| 선언 전 읽기 | undefined | ReferenceError |
| 블록 경계 | 무시 | 적용 |

호이스팅은 소스 코드를 실제로 위로 옮기는 동작이 아니다. 실행 컨텍스트를 만들 때 선언을 등록하고 각 종류의 초기화 시점을 달리하는 설명 모델이다.

함수 선언은 본문까지 일찍 바인딩되어 선언 앞에서 호출할 수 있다. 함수 표현식은 담긴 변수의 초기화 규칙을 따르므로 var와 let의 차이가 그대로 드러난다.

시간적 사각지대의 let을 typeof로 확인해도 ReferenceError가 난다. 아예 선언되지 않은 이름에 typeof를 썼을 때 undefined가 나오는 것과 다르다.

## 80. 같은 함수를 불렀는데 this가 달라지는 이유는?

일반 함수의 this는 함수 정의가 아니라 호출 형태로 정해지기 때문이다. 메서드 호출과 일반 호출은 수신자가 다르며 화살표 함수는 바깥 this를 캡처한다.

| 호출 | 표현 | this |
| --- | --- | --- |
| 생성 | new f() | 새 객체 |
| 명시 | f.call(x) | 엄격 함수면 x |
| 메서드 | x.f() | x |
| 일반 | f() | 엄격 함수면 undefined |

객체에서 메서드를 떼어 콜백으로 넘기면 수신자 정보가 사라진다. bind로 고정하거나 수신자를 보존하는 래퍼를 써야 한다.

화살표 함수에는 자체 this와 arguments가 없다. call이나 apply로 this를 바꿀 수도 없고 new로 생성할 수도 없다. 동적 수신자가 필요한 메서드에는 일반 함수가 맞다.

## 82. 널 검사를 했는데도 안전 호출이 필요한 때는?

검사와 사용 사이에 값이 바뀔 수 있거나 getter 결과가 달라질 수 있으면 컴파일러가 스마트 캐스트를 보장하지 않는다. 지역 val로 고정하거나 ?.로 접근해야 한다.

| 기준 | 스마트 캐스트 가능 | 안전 호출 필요 |
| --- | --- | --- |
| 값 안정성 | 지역 val·안정된 var | 변경 가능 프로퍼티 |
| 재조회 결과 | 같다고 증명 | 달라질 수 있음 |

Kotlin은 String과 String?를 다른 타입으로 취급한다. 안전 호출과 Elvis 연산자는 null 경로를 명시한다. !!는 null이면 런타임 예외를 던져 컴파일 시 안전성을 포기한다.

Java에서 온 플랫폼 타입은 널 가능성이 타입에 확정되지 않는다. 경계에서 어노테이션과 검증으로 불확실성을 좁혀야 내부의 널 안전성이 유지된다.

안전 호출을 길게 잇는 방식은 실패 원인을 숨길 수 있다. 반드시 있어야 하는 값은 초기에 검사하고 의미 있는 오류로 바꾸는 편이 낫다.

## 83. 대입 뒤 한쪽을 바꿀 때 결과가 갈리는 이유는?

값 타입 대입은 값 자체를 복사한다. 참조 타입 대입은 같은 객체를 가리키는 참조를 복사한다. 값 안의 참조 필드는 여전히 같은 객체를 가리킬 수 있다.

| 기준 | 값 의미론 | 참조 의미론 |
| --- | --- | --- |
| 대입 결과 | 값 자체 복사 | 같은 객체의 참조 복사 |
| 변경 영향 | 값 필드는 분리 | 별칭을 통해 공유 |
| 동등성 | 값 비교가 자연스러움 | 값·정체성 구분 |

이 구분은 스택과 힙의 저장 위치와 같지 않다. 값도 최적화나 캡처에 따라 힙에 놓일 수 있고 참조 값 자체는 스택 프레임에 놓일 수 있다.

Java처럼 인자를 항상 값으로 전달하는 언어도 객체 참조 값을 복사해 넘긴다. 호출자는 같은 객체의 변경을 보지만 자신의 변수 재대입은 영향받지 않는다.

가변 참조 객체는 별칭과 동시성 위험을 키운다. 불변 객체와 방어적 복사는 공유 위험을 줄이지만 새 객체 생성과 복사 비용을 낸다.

## 184. volatile 키워드는 가시성 문제를 어떻게 해결하는가?

메인 메모리에서 직접 읽고 쓰게 하여 모든 스레드가 최신 값을 보게 한다. CPU 캐시를 거치지 않고 메모리에 즉시 반영하기 때문이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 스레드 A | L1/L2 캐시. 지역적으로 값을 복사해 사용한다 |
| 메인 메모리 | 공유 영역. volatile 변수가 저장되는 곳 |
| 스레드 B | L1/L2 캐시. 메모리에서 직접 읽어 최신값을 얻는다 |

CPU는 성능을 위해 값을 캐시에 복사해 쓴다. 여러 스레드가 같은 변수를 수정할 때 각자 캐시만 보면 다른 값을 가지게 된다.

volatile은 읽기/쓰기 시점에 메모리 장벽을 세운다. 이를 통해 CPU 캐시에 저장된 값을 무효화하고 메모리의 값을 강제로 읽게 한다.

다만 원자성은 보장하지 않는다. `count++` 같은 연산은 읽기, 수정, 쓰기 세 단계로 나뉘어 여전히 데이터 경쟁이 발생한다.

## 185. 클로저를 사용해 상태를 은닉하는 이유는 무엇인가?

외부 함수의 지역 변수를 외부에서 직접 수정하지 못하게 막아 데이터 무결성을 지키기 때문이다.

| 기준 | 전역 변수 | 클로저 은닉 |
| --- | --- | --- |
| 접근성 | 누구나 가능 | 정의된 함수만 가능 |
| 상태 보호 | 불가능 | 캡슐화 가능 |

함수가 생성될 때 자신의 렉시컬 환경을 기억한다. 따라서 내부 함수를 통해 변수에 접근하는 통로만 열어두면 외부에서는 변수 값을 바꿀 수 없다.

이는 객체 지향의 캡슐화와 유사한 효과를 낸다. 불필요한 전역 변수 사용을 줄여 이름 충돌을 방지하고 상태 변화를 예측 가능하게 만든다.

다만 클로저는 참조하는 변수를 계속 메모리에 유지한다. 과하게 사용하면 가비지 컬렉션 대상에서 제외되어 메모리 누수가 발생할 수 있다.

## 186. 타입스크립트의 구조적 타이핑은 무엇을 기준으로 판별하는가?

객체의 실제 구조와 필요한 속성이 일치하는지로 판별한다. 이름이 달라도 가지고 있는 멤버의 타입과 형태가 같다면 동일한 타입으로 간주한다.

| 기준 | 명목적 타이핑 | 구조적 타이핑 |
| --- | --- | --- |
| 판별 근거 | 선언된 이름(명칭) | 객체의 형태(구조) |
| 유연성 | 엄격함 | 높음 |

이러한 특성으로 인해 인터페이스를 명시적으로 상속받지 않아도 요구하는 속성만 갖추고 있다면 타입 체크를 통과한다. 덕분에 외부 라이브러리와의 타입 호환성을 확보하기 쉽다.

다만 예상치 못한 타입 일치로 인해 런타임 오류가 발생할 위험이 있다. 이를 방지하기 위해 브랜드 태그나 고유한 식별자를 추가해 타입을 구분하기도 한다.

## 216. JVM 메모리 영역은 어떻게 구분하는가?

런타임 데이터 영역으로 구분하며, 스레드 간 공유 여부에 따라 공유 영역과 개별 영역으로 나눈다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 공유 영역 | Heap, Method Area |
| 개별 영역 | Stack, PC Register, Native Method Stack |

공유 영역은 모든 스레드가 접근 가능하다. 가비지 컬렉션의 대상이 되어 메모리 관리가 자동화된다.

개별 영역은 스레드 생성 시 함께 생성되고 종료 시 사라진다. 스레드만 접근하므로 동기화 문제가 발생하지 않는다.

## 241. 파이썬의 가비지 컬렉션은 무엇으로 동작하는가?

> 이 해설은 교차 대조에서 지적이 나왔으나 **검토 후 그대로 두기로 했다.** 판단 근거는 [교정 기록](../../code/docs/audit/fixes/)에 있다.

참조 횟수 계산과 세대별 가비지 컬렉션의 조합으로 동작한다. 기본적으로 참조 횟수가 0이 되면 즉시 메모리에서 제거한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 참조 횟수 | 기본 메커니즘. 0이 되면 즉시 해제 |
| 세대별 GC | 보조 메커니즘. 순환 참조 해결 |

참조 횟수 계산은 빠르고 즉각적이다. 하지만 두 객체가 서로를 가리키는 순환 참조가 발생하면 횟수가 0이 되지 않아 메모리 누수가 생긴다.

이를 해결하기 위해 세대별 GC가 주기적으로 동작한다. 객체를 0, 1, 2세대로 나누어 오래 살아남은 객체는 덜 자주 검사하여 성능 효율을 높인다.

## 242. 호이스팅으로 인한 부작용을 어떻게 막는가?

let과 const를 사용하고 선언부를 최상단으로 올린다. var로 선언한 변수는 선언과 동시에 undefined로 초기화되어 논리적 오류를 유발하기 때문이다.

| 기준 | var | let/const |
| --- | --- | --- |
| 초기화 시점 | 선언과 동시에 | 할당 전 접근 불가 |
| 스코프 | 함수 단위 | 블록 단위 |

var는 선언문이 스코프 최상단으로 끌어올려져 변수 이름만 예약된다. 하지만 값은 할당문 단계에서 결정된다. 이 틈에 접근하면 undefined가 나온다.

반면 let과 const는 선언 전 접근 시 TDZ(Temporal Dead Zone)에 빠진다. 런타임 에러를 발생시켜 개발자가 잘못된 접근을 즉시 알게 한다.

함수 선언문은 호이스팅되어 선언 전 호출이 가능하다. 하지만 의도치 않은 함수 덮어쓰기가 발생할 수 있어 함수 표현식을 권장한다.

## 243. 값 타입과 참조 타입은 무엇으로 구분하는가?

데이터가 메모리에 저장되는 방식과 전달되는 방식의 차이로 구분한다. 값 타입은 실제 값을 직접 저장하고, 참조 타입은 값이 저장된 메모리 주소를 저장한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 값 타입 | 스택 메모리. 실제 데이터가 저장됨 |
| 참조 타입 | 힙 메모리. 주소값이 저장되며 데이터는 힙에 위치함 |

값 타입은 변수 간 복사 시 값이 그대로 복사되어 서로 영향을 주지 않는다. 독립적인 상태를 유지하므로 부수 효과가 적어 안전하다.

참조 타입은 주소값을 복사한다. 여러 변수가 동일한 객체를 가리키므로 한 곳에서 수정하면 다른 변수에도 반영된다. 이는 메모리 효율을 높이지만 상태 변경 추적이 어렵다.

## 268. GC 알고리즘 선택 기준은 무엇인가?

애플리케이션의 서비스 특성과 지연 시간 허용 범위에 따라 결정한다. 처리량 중심인지, 응답 속도 중심인지가 핵심이다.

| 기준 | Parallel GC | G1 GC | ZGC |
| --- | --- | --- | --- |
| 목표 | 처리량 최대화 | 균형 잡힌 지연 | 초저지연 |
| 특징 | STW 길다 | 리전 분할 관리 | 색상 포인터 사용 |

Parallel GC는 전체 처리량을 높이는 데 유리하다. 하지만 모든 GC 발생 시 전체 시스템이 멈추는 Stop-The-World 시간이 길어 서비스 응답이 끊긴다.

G1 GC는 힙을 리전으로 나누어 효율적으로 수집한다. 설정한 목표 지연 시간을 맞추기 위해 수집 효율이 높은 영역부터 먼저 처리한다.

ZGC는 힙 크기에 상관없이 지연 시간을 10ms 이하로 유지한다. 컬러 포인터와 로드 배리어를 통해 애플리케이션과 동시에 GC를 수행한다.
