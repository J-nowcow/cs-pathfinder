## JWT를 세션 대신 쓸 때 무엇을 잃는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

즉시 무효화 능력을 잃는다. 서버가 상태를 갖지 않는다는 장점이 그대로 단점이 된다.

세션은 서버가 저장소를 들고 있으므로 지우면 그 순간 끝난다. JWT는 서명만 유효하면 통과하므로 발급된 토큰을 회수할 방법이 없다. 로그아웃, 권한 변경, 탈취 대응이 전부 만료 시각까지 지연된다.

| 기준 | 세션 | JWT |
| --- | --- | --- |
| 상태 보관 | 서버가 들고 있다 | 토큰 안에 들어 있다 |
| 즉시 무효화 | 지우면 끝 | **만료까지 못 막는다** |
| 서버 확장 | 저장소 공유가 필요하다 | 서버끼리 공유할 것이 없다 |

통상적인 대응은 수명을 짧게 가져가고 리프레시 토큰을 붙이는 것이다. 다만 리프레시 토큰은 결국 서버가 상태를 들고 관리해야 하므로, 무상태라는 원래 이점이 상당 부분 사라진다.

저장 위치도 문제다. 로컬 스토리지는 XSS에 그대로 노출되고, 쿠키는 CSRF를 따로 막아야 한다. 어디에 둬도 공짜가 아니다.

판단 기준은 규모다. 서버가 여러 대이고 세션 공유 비용이 실제 부담일 때 JWT가 값을 한다. 단일 서비스에서 관성으로 고르면 잃는 쪽이 크다.

## HTTPS는 무엇을 보장하고 무엇을 못 하는가?

오가는 내용의 비밀과 위변조 여부, 그리고 상대가 그 도메인의 주인인지까지 보장한다. 그 너머는 보장하지 않는다.

| 보장하는 것 | 어떻게 | 보장하지 않는 것 |
| --- | --- | --- |
| 내용의 비밀 | 대칭키로 암호화 | 접속한 도메인 자체는 드러난다 |
| 위변조 탐지 | 메시지 인증 코드 | 서버가 안전한지는 모른다 |
| 상대의 신원 | 인증서와 CA 검증 | 그 사이트가 정직한지는 모른다 |

흔한 오해가 둘이다. 자물쇠가 붙었다고 안전한 사이트는 아니다. 인증서는 그 도메인의 주인이 맞다는 것만 말하고, 피싱 사이트도 자기 도메인의 인증서를 받을 수 있다. 그리고 어디에 접속했는지는 숨겨지지 않는다 — DNS 조회와 인증서 교환 과정에서 도메인이 노출된다.

서버에 저장된 뒤의 안전도 별개다. HTTPS는 이동 중만 지킨다. 비밀번호를 평문으로 저장하는 서버는 HTTPS를 써도 털린다.

면접에서는 대칭키와 비대칭키를 왜 섞어 쓰는지로 들어온다. 비대칭키는 느려서 데이터 전체에 쓰기 어렵고, 대칭키는 빠르지만 키를 안전하게 건네줄 방법이 없다. 그래서 비대칭키로 대칭키만 주고받고 이후는 대칭키로 간다.

## CORS는 무엇을 막는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

다른 출처에서 온 스크립트가 응답을 읽는 것을 막는다. 요청 자체를 막는 것이 아니다 — 서버에는 도착하고, 브라우저가 결과를 스크립트에 안 넘긴다.

1. **스크립트 → 브라우저** — 다른 출처로 DELETE를 보내겠다
2. **브라우저 → 서버** — 먼저 OPTIONS로 물어본다
3. **서버 → 브라우저** — 이 출처와 이 메서드는 허용한다
4. **브라우저 → 서버** — 그제서야 진짜 요청을 보낸다

단순한 요청은 이 예비 확인을 건너뛰고 바로 나간다. 그래서 폼 전송으로 하는 공격은 CORS로 못 막는다 — 그쪽은 CSRF 토큰의 몫이다.

오해가 잦은 지점이 여기다. CORS는 내 서버를 지키는 장치가 아니라 사용자의 브라우저에 있는 자격 증명을 남의 페이지가 쓰지 못하게 하는 장치다. 서버 인증은 따로 있어야 한다.

쿠키를 함께 보내려면 양쪽이 더 엄격해진다. 출처를 `*`로 열어둘 수 없고 정확한 주소를 적어야 한다. 개발 중에 `*`로 열어놓고 배포에서 막히는 일이 여기서 나온다.

## 고정 소수점과 부동 소수점은 무엇으로 구분하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

소수점의 위치를 고정하느냐, 혹은 데이터의 값에 따라 유동적으로 옮기느냐의 차이다.

| 기준 | 고정 소수점 | 부동 소수점 |
| --- | --- | --- |
| 소수점 위치 | 정해진 위치 | 값에 따라 변함 |
| 표현 범위 | 좁음 | 매우 넓음 |
| 연산 속도 | 빠름 | 느림 |

고정 소수점은 정수부와 소수부의 비트 수를 미리 정해둔다. 계산이 정수 연산과 비슷해 속도가 매우 빠르지만, 표현할 수 있는 숫자의 범위가 매우 제한적이다.

부동 소수점은 가수부와 지수부를 나누어 소수점의 위치를 조정한다. 아주 작은 수나 아주 큰 수를 효율적으로 표현할 수 있어 범용적인 계산에 쓰인다.

다만 부동 소수점은 2진수로 변환하는 과정에서 무한 소수가 발생한다. 이로 인해 정밀한 계산이 필요한 금융권 서비스에서는 오차가로 인해 고정 소수점이나 별도의 정밀도 높은 타입을 사용한다.

## 배열보다 연결 리스트를 사용하는 기준은 무엇인가?

데이터의 추가와 삭제가 빈번하게 일어날 때다. 인덱스로 접근하지 않고 순차적으로 탐색해도 무방한 환경에서 유리하다.

| 기준 | 배열 | 연결 리스트 |
| --- | --- | --- |
| 요소 접근 | $O(1)$. 인덱스로 즉시 찾음 | $O(n)$. 처음부터 훑어야 함 |
| 중간 삽입/삭제 | $O(n)$. 데이터를 밀고 당김 | $O(1)$. 포인터만 변경 |

배열은 연속된 메모리 공간을 사용한다. 삽입이나 삭제 시 나머지 요소를 모두 이동시켜야 하므로 비용이 크다.

반면 연결 리스트는 노드가 흩어져 있다. 앞뒤 노드의 주소값만 바꿔주면 되므로 데이터 이동 없이 빠르게 처리한다.

최근 CPU 캐시 지역성 때문에 단순 탐색 성능은 배열이 압도적이다. 따라서 무작정 리스트를 쓰기보다 데이터 변경 빈도를 먼저 따져야 한다.

## 공개키와 비밀키는 무엇으로 구분하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

키의 공개 여부와 암호화/복호화의 주체가 누구인지로 구분한다. 공개키는 누구나 가질 수 있고, 비밀키는 소유자만 엄격히 관리한다.

| 기준 | 공개키 | 비밀키 |
| --- | --- | --- |
| 공개 여부 | 모두에게 공개 | 소유자만 보유 |
| 사용 용도 | 암호화, 검증 | 복호화, 서명 |

공개키 암호화 방식은 서로 다른 키로 암호화와 복호화를 수행한다. A의 공개키로 암호화한 데이터는 오직 A의 비밀키로만 풀 수 있다.

비밀키 방식은 하나의 키를 공유하여 양방향으로 사용한다. 속도가 빠르지만, 키를 안전하게 전달하는 과정에서 탈취될 위험이 크다.

실무에서는 두 방식을 섞어 쓴다. 대칭키를 생성해 공개키로 암호화해 전달하고, 실제 데이터 통신은 전달받은 대칭키로 빠르게 처리한다.

## 데이터 오류로 인한 손실을 어떻게 방지하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

패리티 비트와 해밍 코드로 검출과 복구로 나누어 처리한다. 단순 검출은 패리티 비트로, 위치를 찾아 복구하는 것은 해밍 코드로 한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 검출 전용 | 패리티 비트. 짝수/홀수 합을 맞춰 오류로 판단 |
| 복구 가능 | 해밍 코드. 여러 체크 비트로 위치를 추적 |

패리티 비트는 데이터 끝에 1비트를 추가해 합을 맞춘다. 1비트만 틀렸을 때 알 수 있지만, 어디가 틀렸을 때인지 모르고 데이터는 버려야 한다.

해밍 코드는 데이터 비트 사이에 체크 비트를 적절히 배치한다. 각 체크 비트는 서로 다른 비트 그룹을 보급한다. 이를 통해 오류가 발생한 정확한 위치를 계산할 수 있다.

단순히로 검출만 하면 재전송 요청을 통해 데이터를 살릴 수 있다. 하지만 지연 시간이 길거나 재전송이 불가능한 메모리 영역에서는 해밍 코드를 직접 복구하는 방식이 쓴다.

## 대칭키와 공개키 중 무엇을 선택하는가?

데이터의 양과 보안 요구 수준에 따라 선택한다. 대량 데이터 전송에는 대칭키를, 초기 키 교환이나 인증에는 공개키를 쓴다.

| 기준 | 대칭키 | 공개키 |
| --- | --- | --- |
| 속도 | 빠름 | 매우 느림 |
| 키 관리 | 공유 키 보안 위험 | 공개키 배포 가능 |
| 용도 | 본문 암호화 | 키 교환, 서명 |

공개키 방식은 복잡한 수학 연산을 수행하므로 대칭키보다 훨씬 느리다. 따라서 전체 데이터를 공개키로 암호화하면 성능 저하가 심하다.

실무에서는 하이브리드 방식을 쓴다. 공개키로 대칭키를 안전하게 전달한 뒤, 실제 데이터는 그 대칭키로 빠르게 암호화하는 구조다.

TLS 핸드셰이크가 대표적인 사례다. 비대칭키로 세션 키를 합의하고, 이후 통신은 대칭키로 수행하여 보안과 효율을 모두 잡는다.

## 블로킹과 논블로킹 I/O의 결정적 차이는 무엇인가?

제어권의 반환 시점이다. 블로킹은 작업 완료까지 기다리며, 논블로킹은 호출 즉시 제어권을 돌려준다.

1. **호출자 → 커널** — I/O 요청
2. **커널 → 호출자** — **블로킹**: 완료까지 대기 / **논블로킹**: 즉시 반환 (EAGAIN)

블로킹 방식은 코드가 직관적이다. 하지만 I/O가 끝날 때까지 쓰레드가 멈춰 자원을 낭비한다.

논블로킹은 대기 시간 동안 다른 일을 할 수 있다. 대신 작업 완료 여부를 계속 확인하거나 알림을 받아야 하므로 로직이 복잡해진다.

이 구분은 동기/비동기 개념과 섞이기 쉽다. 핵심은 '제어권'이 누구에게 있는지에 주목해 구분해야 한다.

## 경쟁 상태를 막으려면 무엇을 고려해야 하는가?

공유 자원에 접근하는 순서가 결과에 영향을 주는 상황을 제어해야 한다. 원자적 연산으로 처리하거나 상호 배제 기법을 사용한다.

1. **스레드 A → 자원** — 접근 요청
2. **자원 → 스레드 A** — **락 획득**. 단독 접근 권한 부여
3. **스레드 A → 자원** — 데이터 수정
4. **스레드 A → 자원** — **락 해제**. 다른 스레드 접근 허용

## 트라이를 사용하는 이유는 무엇인가?

문자열 검색 속도를 문자열 길이만큼으로 줄이기 때문이다. 키 전체를 비교하지 않고 문자 경로를 따라가며 빠르게 찾는다.

1. **루트 → 'a' 노드**
2. **'a' 노드 → 'b' 노드**
3. **'b' 노드 → 'c' 노드** — 'abc' 검색 완료

## 컨텍스트 스위칭은 왜 비용이 발생하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

현재 실행 중인 프로세스의 상태를 저장하고 다음 프로세스의 상태를 복원하는 과정에서 CPU 시간이 소모되기 때문이다.

1. **실행 프로세스 → PCB 저장** — CPU 레지스터 값을 기록한다
2. **PCB 로드 → 다음 프로세스** — 저장된 값을 레지스터에 복구한다

위 과정에서 CPU는 실제 연산을 수행하지 않고 상태 관리만 한다. 특히 메모리 관리 유닛(MMU)의 페이지 테이블 베이스 레지스터를 교체하면 TLB 캐시가 모두 무효화된다.

캐시 미스가 급증하며 메모리 접근 속도가 느려진다. 이를 '캐시 오염'이라 하며, 프로세스가 다시 안정적인 속도로 복구되기까지 시간이 걸린다.

이런 오버헤드가 누적되면 CPU가 실제 작업보다 문맥 교환에 더 많은 시간을 쓰는 쓰레싱 상태에 빠질 수 있다.

## 뮤텍스와 세마포어는 무엇으로 구분하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

소유권의 유무와 허용 가능한 프로세스 수로 구분한다. 뮤텍스는 한 번에 하나만 자원을 점유하고, 세마포어는 정해진 개수만큼 접근을 허용한다.

| 기준 | 뮤텍스 | 세마포어 |
| --- | --- | --- |
| 소유권 | 소유자만 해제 가능 | 누구나 신호 가능 |
| 접근 수 | 무조건 1개 | 설정한 N개 |
| 용도 | 상호 배제 | 자원 관리 및 순서 제어 |

뮤텍스는 락(Lock)의 개념이다. 자원을 점유한 프로세스가 반드시 락을 해제해야 다른 프로세스가 들어올 수 있다.

세마포어는 신호(Signal)의 개념이다. 카운트 값을 관리하며, 자원이 남았을 때만 진입을 허용한다. 소유권이 없으므로 다른 프로세스가 신호를 보내 깨울 수 있다.

상호 배제만을 목적으로 한다면 뮤텍스가 더 가볍고 안전하다. 반면 여러 개의 동일 자원을 효율적으로 나누어 써야 한다면 세마포어를 선택한다.

## TLS 핸드셰이크의 핵심 목적은 무엇인가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

클라이언트와 서버가 서로의 신원을 확인하고, 데이터를 암호화할 수 있는 대칭키를 안전하게 공유하는 것이다.

1. **클라이언트 → 서버** — Client Hello. 지원 버전과 암호화 방식 제안
2. **서버 → 클라이언트** — Server Hello. 암호화 방식 선택 및 인증서 전달

4. **서버 → 클라이언트** — Finished. 모든 설정 완료 및 대칭키 생성

위 흐름을 통해 신뢰할 수 있는 기관(CA)이 서명한 인증서를 확인하여 중간자 공격을 방지한다. 공개키 기반의 비대칭 암호화로 초기 연결을 횃불처럼 보호한다.

최종적으로 생성된 세션 키는 대칭키 암호화 방식을 사용한다. 비대칭 암호화는 연산량이 많아 실제 데이터 전송 시에는 효율적인 대칭키를 쓰는 것이 핵심이다.

TLS 1.3 버전에서는 이 과정을 1-RTT로 줄여 연결 속도를 성능상 이득을 얻었다. 이전 버전보다 불필요한 왕복 횟수를 처음부터 줄여 지연 시간을 단축했다.

## 컨테이너는 가상 머신과 무엇이 다른가?

커널을 공유한다. 가상 머신은 게스트 운영체제를 통째로 올리지만 컨테이너는 호스트 커널 위에서 프로세스로 돈다.

| --- | --- |

## SQL 인젝션은 무엇으로 막는가?

질의문과 값을 갈라 두면 막힌다. 값을 문자열로 이어 붙이는 순간 값이 문법이 될 수 있다.

| 기준 | 이어 붙이기 | 값 바인딩 |
| --- | --- | --- |
| 값의 신분 | 질의문의 일부가 된다 | 끝까지 값이다 |
| 막는 방법 | 위험한 글자를 지운다 | 문법 자리에 못 들어간다 |
