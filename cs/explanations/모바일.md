## 18. 화면을 돌리면 데이터가 사라지는 이유는?

구성이 바뀌면 액티비티가 파괴되고 새로 만들어지기 때문이다. 기존 인스턴스가 들고 있던 값은 그 인스턴스와 함께 사라진다. 남기려면 무엇까지 견뎌야 하는지에 따라 세 층 중 하나를 고른다.

| 수단 | 어디까지 견디나 | 담기 좋은 것 |
| --- | --- | --- |
| ViewModel | 구성 변경까지. **프로세스 종료엔 사라진다** | 목록, 진행 중인 작업 |
| onSaveInstanceState | 프로세스 종료까지 | 작고 직렬화 가능한 값 |
| 파일·DB | 앱을 지울 때까지 | 오래 남겨야 하는 것 |

일부러 그렇게 설계했다. 가로와 세로는 레이아웃도, 이미지도, 때로는 문자열도 다른 리소스를 쓴다. 리소스를 다시 고르는 가장 확실한 방법이 처음부터 다시 만드는 것이다 — 언어 변경이나 다크 모드 전환도 같은 경로를 탄다.

셋을 가르는 축은 무엇을 견뎌야 하느냐다. 구성 변경만 견디면 되는 값은 ViewModel로 충분하다. 다만 시스템이 메모리를 회수하며 프로세스를 죽이면 ViewModel도 함께 사라진다. 그때까지 살아야 하는 값은 번들이나 저장소로 내려야 한다.

면접에서는 이 둘을 구별하는지를 본다. "ViewModel을 쓰면 된다"까지는 대부분 말한다. 프로세스 종료는 못 견딘다는 것과 그 자리를 SavedStateHandle이 메운다는 데까지 가면 한 단계 위다.

## 28. 푸시 알림이 안 오는 이유는 대개 무엇인가?

기기가 절전 상태로 들어가 네트워크와 작업을 묶어 처리하고 있기 때문이다. 서버가 보냈다고 즉시 도착하는 것이 아니다.

안드로이드는 화면이 꺼진 채로 시간이 지나면 도즈 모드로 들어간다. 이때 네트워크 접근과 예약 작업이 일정 간격으로 몰아서 처리된다. 배터리를 아끼려는 설계이고, 그 대가로 알림이 몇 분씩 늦을 수 있다.

1. **서버 → 푸시 서비스** — 메시지 전달
2. **푸시 서비스 → 기기** — 연결이 열려 있을 때 내려보낸다
3. **기기 → 앱** — 절전 중이면 다음 창이 열릴 때까지 미룬다

급한 알림에는 높은 우선순위를 지정할 수 있다. 그러면 절전을 뚫고 즉시 전달되지만 무제한은 아니다 — 남용하면 할당량이 깎여 오히려 더 늦어진다. 진짜 사용자를 깨워야 하는 메시지에만 쓴다.

면접에서는 전달 보장을 묻는다. 푸시는 최선 노력이라 유실될 수 있다. 놓치면 안 되는 것은 알림에만 기대지 말고, 앱이 열릴 때 서버에서 다시 확인하는 경로를 함께 둔다.

## 39. 앱이 백그라운드에서 죽는 이유는?

시스템이 메모리를 회수하기 때문이다. 앞에 보이는 앱을 살리는 것이 우선이라, 안 보이는 프로세스부터 순서대로 거둬간다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 포그라운드 | 화면에 보인다. 거의 안 죽인다 |
| 보이는 상태 | 가려졌지만 살아 있다 |
| 서비스 | 백그라운드 작업 중. 상황에 따라 거둔다 |
| 캐시된 상태 | 안 보인다. 여기부터 먼저 죽는다 |

죽는 것은 사고가 아니라 설계다. 그래서 앱은 언제 죽어도 되도록, 그리고 돌아왔을 때 이어지도록 만들어야 한다.

문제는 죽을 때 알림이 없다는 것이다. 화면을 떠날 때 저장하지 않으면 그대로 사라진다. 사용자에게는 "쓰던 게 날아갔다"로만 보인다.

오래 걸리는 일은 앱 프로세스에 매달지 않는다. 업로드나 동기화는 작업 관리자에 맡겨서, 프로세스가 죽어도 시스템이 나중에 다시 실행하게 한다.

## 84. 백그라운드 전환 때 어디서 자원을 해제하는가?

화면이 완전히 보이지 않으면 onStop에서 화면 전용 자원을 멈추거나 줄인다. onPause에는 포커스를 잃을 때 꼭 필요한 짧은 처리만 둔다.

1. **시스템 → Activity** — onCreate. 화면을 만든다
2. **Activity → Activity** — onStart와 onResume. 보이고 입력받는다
3. **시스템 → Activity** — onPause와 onStop. 포커스와 가시성을 잃는다

onPause 상태에서도 멀티 윈도우나 반투명 화면 뒤로 보일 수 있다. 그래서 무거운 종료 작업을 넣으면 전환이 느려진다.

onStop 뒤에는 프로세스가 종료될 수 있다. onDestroy 호출에 저장을 의존하지 말고 작은 UI 상태는 저장 상태 API로 남긴다.

## 85. 뷰 바인딩은 왜 onDestroyView에서 비우는가?

Fragment 인스턴스가 백 스택에 남아도 뷰는 먼저 파괴될 수 있기 때문이다. 바인딩을 계속 잡으면 폐기된 뷰가 수집되지 않고 잘못 접근할 수도 있다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| Fragment 수명 | onCreate부터 onDestroy까지다 |
| View 수명 | onCreateView부터 onDestroyView까지다 |

뷰를 갱신하는 관찰은 viewLifecycleOwner에 묶는다. 그러면 뷰가 파괴될 때 관찰도 멈춘다.

onDestroyView에서 어댑터와 리스너도 필요에 따라 끊는다. Fragment 필드에는 새 뷰가 생기기 전까지 뷰 참조를 남기지 않는다.

## 86. 회전 뒤에도 남겨야 할 상태는 어디에 두는가?

다시 계산할 화면 데이터는 ViewModel에 둔다. 선택값과 입력처럼 복원에 필요한 작은 UI 상태는 저장 상태에 둔다. 영구 데이터는 저장소에 둔다.

| 기준 | ViewModel | 저장 상태 |
| --- | --- | --- |
| 구성 변경 | 같은 인스턴스를 잇는다 | 값으로 복원한다 |
| 프로세스 종료 | 사라진다 | 조건부로 복원한다 |

회전과 창 크기 변경은 Activity를 재생성할 수 있다. ViewModel은 이 재생성 동안 메모리 데이터를 유지한다.

시스템이 프로세스를 죽이면 ViewModel도 사라진다. 이때 화면을 다시 만드는 최소 키만 Bundle 기반 저장 상태에서 복원한다.

큰 목록이나 비즈니스 데이터는 저장 상태에 넣지 않는다. ID나 검색어만 남기고 데이터 계층에서 다시 읽는다.

## 87. 화면 상태를 둘 때 두 수단을 어떻게 나누는가?

화면 로직과 계산된 UI 상태는 ViewModel에 둔다. 프로세스 재생성 뒤 화면을 복구할 최소 키만 SavedStateHandle에 둔다.

| 기준 | ViewModel | SavedStateHandle |
| --- | --- | --- |
| 구성 변경 | 메모리에 유지한다 | 값도 유지된다 |
| 프로세스 종료 | 인스턴스가 사라진다 | 저장된 값을 복원한다 |

SavedStateHandle도 Bundle 기반이다. 큰 객체 대신 항목 ID와 필터처럼 다시 데이터를 만들 단서만 저장한다.

강제 종료나 최근 앱에서 태스크를 지우면 복원이 보장되지 않는다. 반드시 남아야 하는 데이터는 데이터베이스 같은 영구 저장소에 둔다.

## 88. 메모리 부족 시 어떤 프로세스부터 종료되는가?

사용 중인 컴포넌트가 없는 캐시 프로세스부터 종료된다. 가시성과 사용자 영향이 클수록 우선순위가 높아지고 포그라운드 프로세스는 마지막에 보호된다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 포그라운드 | 사용자가 현재 상호작용한다 |
| 가시 | 화면에 보이거나 인지되는 작업이다 |
| 서비스 | 시작된 서비스를 수행한다 |
| 캐시 | 활성 컴포넌트가 없다 |

프로세스 등급은 가장 중요한 활성 컴포넌트에 맞춰진다. 중요한 클라이언트가 바인드한 서비스의 프로세스도 우선순위가 올라간다.

백그라운드 프로세스의 수명을 전제로 설계하면 안 된다. 메모리의 싱글턴 값은 사라질 수 있으므로 화면과 작업을 복원 가능하게 만든다.

## 89. 실행 시점과 사용자 인지 여부로 어떤 수단을 고르는가?

지연 가능하고 끝내야 하는 일은 WorkManager를 쓴다. 즉시 진행하며 사용자가 알아야 하는 일은 포그라운드 서비스를 쓴다. 정시 알림은 알람을 검토한다.

| 기준 | WorkManager | 포그라운드 서비스 |
| --- | --- | --- |
| 목적 | 지연 가능한 지속 작업 | 즉시 체감 작업 |
| 특성 | 시각이 정확하지 않다 | 알림과 시작 제한이 있다 |

Doze와 앱 대기는 네트워크와 알람을 미루고 백그라운드 서비스 실행도 제한한다. 스레드나 일반 서비스만 띄워 계속 실행되리라 기대할 수 없다.

정확한 시각이 핵심인 사용자 기능은 AlarmManager를 검토한다. 정확한 알람은 권한과 용도 제한이 있어 일반 동기화에 쓰지 않는다.

## 90. 예약한 작업은 정말 한 번만 실행되는가?

아니다. 조건이 맞은 뒤 실행되도록 영속적으로 예약하지만 재시도와 중단 때문에 Worker가 여러 번 시작될 수 있다. 외부 부수 효과는 멱등하게 만든다.

1. **앱 → WorkManager** — 작업과 제약 조건을 저장한다
2. **WorkManager → Worker** — 조건이 맞으면 실행한다
3. **Worker → WorkManager** — 재시도를 반환하면 다시 예약한다

WorkManager는 프로세스 종료와 기기 재부팅 뒤에도 작업을 다시 예약한다. 다만 정확한 시작 시각은 보장하지 않는다.

성공은 완료로 끝난다. 실패는 영구 실패로 끝난다. 재시도는 백오프 뒤 다시 돈다. 실행 중 제약이 깨지면 작업이 중지되고 다시 시도될 수 있다.

고유 작업은 중복 예약을 줄인다. 서버 요청에는 멱등성 키를 넣고 로컬 갱신은 트랜잭션으로 묶어 실행 중단에도 결과를 일관되게 만든다.

## 91. 비동기로 옮겼는데도 왜 응답 없음이 생기는가?

작업을 다른 스레드로 보냈어도 메인 스레드가 결과나 잠금을 기다리면 막히기 때문이다. 느린 Binder 호출과 과도한 그리기도 입력 처리를 지연시킨다.

1. **사용자 → 메인 Looper** — 입력 이벤트를 보낸다
2. **메인 Looper → 작업** — 결과나 잠금을 기다린다
3. **시스템 → 앱** — 기한 내 응답이 없어 ANR을 기록한다

메인 스레드는 입력과 생명주기 콜백과 화면 갱신을 직렬로 처리한다. 입력 이벤트에 약 5초간 응답하지 못하면 입력 디스패치 ANR이 날 수 있다.

스택 덤프에서 main의 대기 지점을 찾고 잠금 보유 스레드도 따라간다. StrictMode와 Perfetto로 I/O와 느린 Binder 호출을 확인한다.

## 92. 화면이 닫혔는데 객체가 남는 이유는?

정적 필드와 싱글턴과 실행 중 스레드 같은 긴 수명의 객체가 Activity나 View를 계속 참조하기 때문이다. GC Root에서 도달 가능하면 수집되지 않는다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| GC Root | 정적 필드나 실행 중 스레드다 |
| 싱글턴·콜백 | 화면 객체를 참조한다 |
| Activity·View | 종료돼도 도달 가능하다 |

리스너를 등록한 수명에서 해제하고 코루틴과 콜백도 함께 취소한다. UI가 필요 없는 객체에는 Application Context를 사용한다.

ViewModel에는 Activity나 View 참조를 두지 않는다. Fragment의 뷰 바인딩은 onDestroyView에서 비워 뷰 수명과 맞춘다.

힙 덤프에서 누수 객체의 GC Root 경로를 따라간다. 지배 참조를 끊은 뒤 같은 화면을 반복 열고 보유 개수가 줄어드는지 확인한다.

## 93. 전송 성공은 단말 수신까지 뜻하는가?

아니다. 서버가 받은 메시지 ID는 FCM이 전달 요청을 접수했다는 뜻이다. 단말 도착이나 앱 처리를 보장하지 않는다.

1. **앱 서버 → FCM** — 메시지를 접수한다
2. **FCM → 단말** — 연결 상태에 따라 전달을 시도한다
3. **단말 → 앱 서버** — 처리 결과를 별도로 확인한다

오프라인과 Doze와 토큰 만료 때문에 지연되거나 유실될 수 있다. TTL이 지나거나 같은 collapse key의 새 메시지가 오면 대기 메시지가 버려질 수 있다.

백그라운드 알림 메시지는 시스템 트레이가 처리한다. 데이터 메시지의 앱 처리는 짧아야 하며 긴 후속 작업은 지속 작업으로 넘긴다.

## 94. 재사용 셀에 이전 데이터가 비치는 이유는?

onBindViewHolder가 새 항목의 모든 가변 속성을 덮어쓰지 않았기 때문이다. 이전 항목의 가시성이나 체크 상태와 이미지가 ViewHolder에 남는다.

1. **RecyclerView → ViewHolder** — 화면 밖 셀을 회수한다
2. **RecyclerView → Adapter** — 새 위치의 데이터를 요청한다
3. **Adapter → ViewHolder** — 모든 가변 상태를 덮어쓴다

전체 바인딩에서는 텍스트와 이미지와 선택 상태와 리스너를 현재 모델 기준으로 모두 설정한다. 비동기 이미지 요청은 재사용 전에 취소하거나 새 요청으로 교체한다.

클릭 시 바인딩 때 받은 position을 저장하지 않는다. 실행 시점의 bindingAdapterPosition을 확인하거나 항목 자체를 콜백에 넘긴다.

DiffUtil과 stable ID는 변경 계산과 애니메이션을 돕는다. 올바른 바인딩을 대신하지 않으며 잘못된 ID는 화면 상태를 엉뚱한 항목에 붙인다.

## 95. 상태 변경은 어디까지 다시 실행되는가?

변경된 State를 읽은 재시작 범위가 다시 실행된다. 그 아래에서도 입력이 바뀌지 않은 스킵 가능 컴포저블은 건너뛸 수 있다.

1. **상태 → 컴포저블** — 읽은 재시작 범위를 무효화한다
2. **Compose → 컴포저블** — 필요한 범위만 다시 실행한다
3. **Compose → UI 트리** — 달라진 노드만 반영한다

일반 mutable 객체의 필드만 바꾸면 Compose가 변화를 알지 못한다. MutableState로 바꾸거나 Flow를 collectAsState 계열로 수집해야 갱신이 예약된다.

remember는 같은 Composition에서 값만 보존한다. 부수 효과를 본문에 직접 두면 재실행이나 취소 순서가 깨지므로 LaunchedEffect와 DisposableEffect에 둔다.

Compose는 입력 동일성으로 스킵을 판단한다. 안정성 계약과 key를 잘못 선언하면 오래된 UI 상태가 다른 항목에 붙을 수 있다.

## 96. 부모 작업이 취소되면 자식은 어떻게 되는가?

부모는 모든 자식이 끝나야 완료된다. 이 규칙 덕분에 호출 범위를 벗어난 작업이 남는 것을 막고 예외와 자원을 한곳에서 관리할 수 있다.

자식 하나의 실패를 격리해야 한다면 SupervisorJob이나 supervisorScope를 쓴다. 이때도 부모 취소는 모든 자식에게 전파된다.

## 97. 권한을 한 번 받으면 계속 쓸 수 있는가?

거부 뒤 다시 요청할 수 있는지는 시스템 상태에 달렸다. 설명 화면과 설정 이동을 구분하고 거부되어도 핵심 기능이 무너지지 않게 설계한다.

## 100. 자동 참조 계산인데 왜 메모리가 남는가?

강한 참조 고리가 생기면 각 객체의 참조 수가 0이 되지 않기 때문이다. 외부 소유자가 놓아도 고리 안의 객체는 해제되지 않는다.

1. **객체 A → 객체 B** — 강한 참조로 수를 올린다
2. **객체 B → 객체 A** — 강한 참조로 수를 올린다
3. **소유자 → 객체 A** — 참조를 놓아도 두 객체가 남는다

소유 관계가 아닌 역참조는 weak로 끊는다. 대상이 먼저 사라지지 않는다는 수명 보장이 있을 때만 unowned를 쓴다.

클로저가 self를 강하게 캡처하고 self가 그 클로저를 보관해도 고리가 된다. 캡처 목록은 수명과 비동기 실행 시점을 따져 정한다.

deinit 로그와 메모리 그래프로 해제 여부를 확인한다. weak를 무조건 붙이면 작업 중 객체가 사라지는 다른 버그를 만들 수 있다.

## 101. 상태 소유자를 잘못 두면 어떤 버그가 생기는가?

뷰 재생성 때 상태가 초기화되거나 모델이 중복 생성된다. 소유권이 여러 곳에 생기면 화면마다 값이 어긋나고 불필요한 갱신도 늘어난다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 상위 뷰 | 상태의 단일 소유자다 |
| 하위 뷰 | Binding으로 변경 통로를 받는다 |
| 렌더링 | 읽은 상태가 바뀌면 다시 계산된다 |

작은 값은 가장 가까운 뷰가 State로 소유한다. 하위 뷰가 같은 값을 편집해야 하면 복사하지 않고 Binding을 전달한다.

ObservableObject 모델을 뷰가 만들고 유지하면 StateObject를 쓴다. 외부에서 받은 모델은 ObservedObject로 관찰해 소유와 관찰을 분리한다.

넓게 공유하는 의존성은 Environment로 주입할 수 있다. 편리하더라도 범위를 넓히면 데이터 흐름과 테스트 의존성이 숨는다.

## 105. 모바일 요청은 실패할 때마다 다시 보내도 되는가?

실패할 때마다 보내면 안 된다. 일시 오류만 제한적으로 재시도하고 쓰기 요청은 멱등성을 보장해야 한다. 영구 오류와 사용자 취소는 즉시 끝낸다.

1. **클라이언트 → 서버** — 요청과 멱등 키를 보낸다
2. **서버 → 클라이언트** — 일시 오류와 대기 정보를 돌려준다
3. **클라이언트 → 클라이언트** — 백오프와 지터로 기다린다
4. **클라이언트 → 서버** — 조건이 맞을 때만 재시도한다

타임아웃과 일부 5xx와 429는 후보가 된다. 상태 코드만 보지 말고 API 계약과 Retry-After를 따른다. 대부분의 4xx는 재시도해도 성공하지 않는다.

지수 백오프는 반복할수록 간격을 늘린다. 지터는 여러 기기가 동시에 깨어 서버를 다시 압박하는 재시도 폭주를 줄인다.

앱이 백그라운드로 가거나 연결이 바뀌면 예약을 다시 판단한다. 꼭 전달할 작업은 메모리가 아닌 영속 큐에 넣고 최대 횟수와 만료 시점을 둔다.

## 187. 백그라운드 제약을 피하는 방법은 무엇인가?

포그라운드 서비스와 WorkManager를 사용한다. 앱이 보이지 않아도 시스템이 강제 종료시키지 않도록 알림을 띄우거나 예약 작업을 등록하는 방식이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 포그라운드 서비스 | 알림창에 상주하며 즉시 실행 |
| WorkManager | 조건 충족 시 시스템이 최적 시점에 실행 |

포그라운드 서비스는 사용자에게 앱이 동작 중임을 알린다. 시스템은 알림이 떠 있는 서비스를 중요도로 높게 평가해 메모리 부족 상황에서도 종료 우선순위를 늦춘다.

WorkManager는 지연 가능한 작업을 처리한다. 배터리 최적화 모드나 Doze 모드에서도 OS가 적절한 시점을 골라 작업을 묶어 처리하므로 전력 소모를 줄인다.

최신 OS 버전에서는 포그라운드 서비스 타입 선언이 필수다. 타입을 명시하지 않거나 부적절한 타입을 쓰면 앱이 비정상 종료된다.

## 188. 푸시 알림의 전달 보장을 위해 무엇을 설계하는가?

푸시 서버와 FCM/APNs 같은 외부 플랫폼의 전송 상태를 추적하고 재시도 메커니즘을 구현한다.

1. **푸시 서버 → 플랫폼** — 메시지 전송 요청
2. **플랫폼 → 푸시 서버** — 수신 확인(ACK) 응답
3. **푸시 서버 → 플랫폼** — 실패 시 지수 백오프 재시도

전송 요청 후 플랫폼에서 주는 응답만으로는 실제 단말기 도달 여부를 알 수 없다. 플랫폼이 메시지를 큐에 넣었을 때 성공으로 응답하기 때문이다.

따라서 단말기가 알림을 수신했을 때 서버로 수신 확인 신호를 보내는 피드백 루프를 설계한다. 이를 통해 누락된 알림을 다시 보낼 수 있다.

메시지 ID를 통해 중복 수신을 방지하는 멱등성 처리도 함께 고려해야 한다. 네트워크 불안정으로 인한 재시도 시 동일 알림이 여러 번 뜰 수 있다.

## 244. 안드로이드 메인 스레드에서 무거운 작업을 하면 왜 ANR이 발생하는가?

메인 스레드가 일정 시간 동안 이벤트 루프를 돌지 못해 사용자 입력에 응답하지 않기 때문이다.

1. **사용자 입력 → 메인 스레드** — 이벤트 전달
2. **메인 스레드 → OS** — 응답 처리 및 UI 갱신
3. **블로킹 작업 → 메인 스레드** — 처리 지연 및 응답 불가

안드로이드는 UI 갱신과 사용자 입력 처리를 메인 스레드 하나에서 전담한다. 여기서 네트워크 요청이나 DB 조회 같은 무거운 작업이 수행되면 큐에 쌓인 다음 이벤트들을 처리하지 못한다.

시스템은 메인 스레드가 5초 이상 응답하지 않을 때 이를 ANR로 판단하고 사용자에게 알림창을 띄운다. 이때 메인 스레드는 여전히 작업 중이지만, 더 이상 사용자 인터랙션이 불가능한 상태가 된다.

결국 ANR을 막으려면 메인 스레드에서는 UI 갱신만 수행하고, 시간이 오래 걸리는 작업은 Worker 스레드나 Coroutine으로 분리해야 한다.

## 269. 안드로이드에서 메모리 누수가 발생하는 주원인은 무엇인가?

활동(Activity)이 파괴되었음에도 외부 객체에 의해 참조가 유지되어 가비지 컬렉터가 회수하지 못할 때 발생한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 참조 체인 | Activity $\rightarrow$ 익명 클래스 $\rightarrow$ 외부 객체 |
| 루트 객체 | GC Root. 메모리 해제제한의 시작점 |

가장 흔한 사례는 Activity 내부에서 익명 클래스나 내부 클래스를 사용하는 경우다. 이들은 외부 클래스에 대한 숨은 참조를 가지므로, 내부 클래스가 살아있으면 Activity도 메모리에 남는다.

특히 핸들러(Handler)나 비동기 작업이 Activity보다 오래 실행될 때 위험하다. 작업이 끝나기 전까지 Activity 참조를 붙잡고 있어 누수가 발생한다.

이를 방지하려면 Static 클래스로 선언하고 약한 참조(WeakReference)를 사용해야 한다. 또한 Activity 생명주기에 맞춰 등록한 리스너를 명시적으로 해제해야 한다.

## 270. 코루틴의 구조적 동시성은 무엇을 해결하는가?

비정상적으로 종료된 자식 코루틴이 부모 코루틴에 의해 관리되지 않아 메모리 누수나 불필요한 작업이 계속되는 현상을 해결한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 부모 코루틴 | 자식 코루틴의 생명주기를 관리하고 완료를 기다림 |
| 자식 코루틴 | 부모의 컨텍스트와 Job로 묶여 제어됨 |

구조적 동시성은 코루틴 간의 계층 구조를 형성한다. 부모 코루틴은 모든 자식 코루틴이 끝날 때까지 대기한다. 자식에서 예외가 발생하면 부모와 형제 코루틴 모두 취소된다.

이러한 구조 덕분에 Scope를 통해 코루틴을 한 번에 취소할 수 있다. 예를 들어 안드로이드의 ViewModelScope를 쓰면 화면이 닫힐 때 실행 중인 모든 작업이 자동으로 중단된다.
