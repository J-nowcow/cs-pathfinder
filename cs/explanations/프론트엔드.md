## useEffect 의존성 배열을 잘못 넣으면 어떤 문제가 생기는가?

너무 적게 넣으면 오래된 값을 붙잡고, 너무 많이 넣으면 불필요하게 다시 실행된다. 방향이 반대인 두 문제다.

| 넣는 양 | 증상 | 알아채기 |
| --- | --- | --- |
| 너무 적다 | 클로저가 첫 렌더의 값을 계속 본다 | 오류가 안 나서 늦게 발견된다 |
| 너무 많다 | 매 렌더마다 실행되고 무한 루프로 간다 | 바로 티가 난다 |

의존성을 빠뜨리면 클로저가 첫 렌더의 값을 계속 참조한다. 이펙트 안에서 최신 상태를 읽는 줄 알았는데 초기값이 나오는 상황이 여기서 생긴다. 콘솔에는 아무 오류도 없어 발견이 늦다.

반대로 매 렌더마다 새로 만들어지는 객체나 함수를 의존성에 넣으면 참조가 계속 바뀐다. 이펙트가 매번 실행되고, 그 안에서 상태를 갱신하면 무한 루프가 된다.

정리 함수를 빠뜨리는 것도 같은 범주다. 구독이나 타이머를 걸어두고 정리하지 않으면 언마운트된 컴포넌트가 계속 살아 있다. 이펙트가 자주 실행될수록 누수가 빨리 쌓인다.

판단 기준은 단순하다. 이펙트 안에서 쓰는 모든 외부 값을 넣고, 그래서 너무 자주 실행되면 값 자체를 안정화한다. 의존성을 빼서 해결하는 것은 증상만 가리는 것이다.

## 브라우저가 화면을 그리기까지 무슨 일이 일어나는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

HTML과 CSS를 각각 트리로 만들고 둘을 합쳐 위치를 계산한 뒤 픽셀로 칠한다. 어느 단계를 건드리느냐에 따라 비용이 크게 갈린다.

1. **파서 → DOM** — HTML을 읽어 요소 트리를 만든다
2. **파서 → CSSOM** — 스타일 규칙을 트리로 만든다
3. **DOM+CSSOM → 렌더 트리** — 화면에 나올 것만 남긴다
4. **렌더 트리 → 레이아웃** — 각 요소의 위치와 크기를 잰다
5. **레이아웃 → 페인트** — 색과 그림자를 칠한다

스타일을 바꾸면 어디까지 되돌아가는지가 성능을 가른다. 너비나 위치를 건드리면 레이아웃부터 다시 한다. 색만 바꾸면 페인트만 다시 한다. `transform`과 `opacity`는 합성 단계에서만 처리돼 앞의 둘을 건너뛴다.

자바스크립트가 이 흐름을 막을 수 있다. CSSOM이 완성되기 전에는 스크립트를 실행할 수 없고, 스크립트가 도는 동안에는 파싱이 멈춘다. 스타일시트를 위에, 스크립트를 아래에 두라는 오래된 조언이 여기서 나왔다.

면접에서는 레이아웃을 강제로 일으키는 코드를 짚어온다. 스타일을 바꾼 직후에 `offsetHeight` 같은 값을 읽으면 브라우저가 그 자리에서 레이아웃을 다시 계산한다. 반복문 안에서 쓰기와 읽기를 번갈아 하면 매 회전마다 그 비용이 든다.

## 리렌더링이 필요 이상으로 도는 이유는?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

렌더마다 새 값이 만들어지기 때문이다. 객체와 함수는 내용이 같아도 참조가 달라서, 비교하는 쪽은 매번 바뀐 것으로 본다.

| 무엇을 넘기나 | 렌더마다 | 결과 |
| --- | --- | --- |
| 문자열·숫자 | 같은 값 | 다시 안 그린다 |
| 인라인 객체·배열 | 새 참조 | 매번 다시 그린다 |
| 인라인 함수 | 새 참조 | 매번 다시 그린다 |

부모가 다시 그려지면 자식도 따라 그려지는 것이 기본이다. 대부분은 그래도 싸서 문제가 안 된다. 목록이 길거나 자식이 무거울 때만 비용이 눈에 띈다.

그때 쓰는 것이 메모다. 자식을 `memo`로 감싸고 넘기는 값을 고정한다. 다만 감싸기만 하고 인라인 객체를 계속 넘기면 비교만 늘고 효과는 없다.

메모를 먼저 뿌리는 것은 대개 손해다. 비교에도 값이 들고 코드가 읽기 어려워진다. 프로파일러로 실제 느린 곳을 찾은 뒤에 붙인다.

## 변경점을 비교하면 언제 비용이 줄어드는가?

메모리의 트리에서 변경점을 모아 실제 노드 갱신 횟수를 줄일 때 이득이다. 비교와 재조정 비용보다 직접 DOM 조작 비용이 클 때 효과가 난다.

| 기준 | 가상 트리 비교 | 직접 DOM 갱신 |
| --- | --- | --- |
| 강점 | 선언적 일괄 반영 | 작은 변경에 단순함 |

렌더링마다 화면 전체를 다시 그리는 것은 아니다. 프레임워크는 이전 트리와 새 트리를 비교해 필요한 DOM 변경만 커밋한다.

업데이트가 작고 구조가 단순하면 직접 조작이 더 싸다. 가상 트리는 무조건 빠른 기술이 아니라 상태 기반 UI를 예측 가능하게 만드는 절충이다.

## 계산 단계와 반영 단계를 왜 나누는가?

계산을 중단하거나 다시 시작해도 화면이 중간 상태에 놓이지 않게 하려고 나눈다. DOM과 ref는 커밋에서 일관되게 반영한다.

1. **상태 변경 → 렌더 단계** — 새 트리와 변경점을 계산한다
2. **렌더 단계 → 커밋 단계** — DOM과 ref를 반영한다
3. **커밋 단계 → 브라우저** — 변경된 화면을 그린다

렌더 단계는 컴포넌트를 호출해 결과를 계산한다. 우선순위에 따라 중단되거나 폐기될 수 있으므로 외부 부작용을 두면 안 된다.

커밋은 DOM 변경과 ref를 적용하며 중간에 쪼개지 않는다. useLayoutEffect는 페인트 전, useEffect는 대체로 페인트 뒤에 실행된다.

## 공유 상태는 어느 컴포넌트에 두는가?

그 상태를 읽거나 바꾸는 컴포넌트들의 가장 가까운 공통 조상에 둔다. 한 출처에서 값을 내려주고 변경 의도를 올려보낸다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 공통 조상 | 상태와 변경 함수를 소유한다 |
| 자식 A | 값을 props로 받는다 |
| 자식 B | 변경 함수를 호출한다 |

각 자식이 같은 값을 따로 보관하면 동기화 코드가 생긴다. 한쪽 갱신이 빠지면 화면마다 다른 값을 보여주는 상태 불일치가 난다.

너무 높이 올리면 관련 없는 자식까지 의존하고 전달 경로가 길어진다. 상태가 넓게 공유되면 Context나 외부 저장소가 더 적합할 수 있다.

## 목록 항목의 정체성을 어떻게 보존하는가?

렌더 사이에 같은 항목을 가리키는 안정적이고 고유한 키를 준다. 프레임워크는 키로 기존 인스턴스와 상태를 새 항목에 대응시킨다.

| 기준 | 안정적 ID | 배열 인덱스 |
| --- | --- | --- |
| 재정렬 | 상태를 항목에 유지 | 상태가 위치에 붙을 수 있음 |

같은 부모 아래에서 키와 타입이 같으면 기존 컴포넌트와 DOM을 재사용한다. 키가 바뀌면 새로 마운트해 내부 상태도 초기화한다.

인덱스 키는 추가·삭제·정렬이 없는 고정 목록에서만 안전하다. 매번 생성한 난수 키는 전부 다시 마운트해 성능과 입력 상태를 해친다.

## 계산 결과와 함수 참조는 언제 기억해야 하는가?

재계산 비용이 크거나 참조 안정성이 하위 최적화에 필요할 때만 기억한다. 값은 useMemo로, 함수 참조는 useCallback으로 유지한다.

| 기준 | useMemo | useCallback |
| --- | --- | --- |
| 반환 | 계산한 값 | 함수 자체 |
| 주된 목적 | 비싼 계산 재사용 | 함수 참조 유지 |

의존성이 Object.is 비교로 같을 때 이전 결과나 참조를 재사용한다. 의존성을 빠뜨리면 함수가 오래된 상태를 잡는 문제가 생긴다.

둘 다 의미 보장이 아닌 성능 최적화다. 값 계산이 싸거나 소비자가 참조를 비교하지 않으면 메모리와 의존성 관리 비용만 늘어난다.

## 클라이언트 경계는 어디에 두는가?

데이터 접근과 무거운 의존성은 서버에 둔다. 상호작용과 브라우저 API가 필요한 최소 영역만 클라이언트로 둔다.

| 기준 | 서버 | 클라이언트 |
| --- | --- | --- |
| 적합한 일 | 데이터 조회 | 상태와 이벤트 |
| 번들 영향 | 코드 미전송 | 코드 전송 |

서버에서 클라이언트로 넘기는 props는 직렬화할 수 있어야 한다. 클라이언트 컴포넌트가 서버 자식을 받는 조합으로 상호작용 범위를 좁힌다.

## 첫 화면을 막는 리소스는 어떻게 줄이는가?

필수 CSS만 먼저 제공하고 나머지는 늦게 불러온다. 스크립트는 의존 순서에 맞춰 defer나 async를 써서 HTML 파싱 정지를 줄인다.

| 기준 | CSS | 스크립트 |
| --- | --- | --- |
| 차단 지점 | 렌더 트리 구성 | HTML 파싱 |
| 완화 | 핵심 CSS 우선 | defer, async |

외부 스타일시트는 CSSOM이 준비될 때까지 첫 페인트를 늦춘다. 사용하지 않는 CSS를 제거하고 미디어 조건을 나누면 차단 범위가 줄어든다.

defer는 파싱 뒤 문서 순서대로 실행한다. async는 다운로드 즉시 실행해 순서를 보장하지 않는다. 독립적인 코드에 알맞다.

## 레이아웃 계산과 픽셀 갱신은 언제 생기는가?

요소의 크기나 위치가 바뀌면 레이아웃 계산이 생긴다. 색상처럼 기하에 영향 없는 속성이 바뀌면 픽셀만 다시 그린다.

1. **기하 속성 변경 → 레이아웃** — 크기와 위치를 계산한다
2. **레이아웃 → 페인트** — 픽셀을 그린다
3. **페인트 → 합성** — 레이어를 배치한다

DOM 쓰기 뒤 곧바로 크기를 읽으면 브라우저가 미뤄 둔 계산을 즉시 끝내야 한다. 읽기와 쓰기를 섞어 반복하면 레이아웃 스래싱이 된다.

애니메이션은 가능하면 transform과 opacity를 쓴다. 별도 레이어에서 합성할 수 있어 레이아웃과 페인트를 피하지만 레이어 메모리는 늘 수 있다.

## 선택자 최적화는 실제로 언제 필요한가?

스타일 재계산이 병목으로 측정되고 DOM이 클 때 필요하다. 보통은 선택자보다 DOM 규모와 잦은 클래스 변경을 먼저 줄이는 편이 효과가 크다.

| 기준 | 단순 클래스 | 깊은 후손 선택자 |
| --- | --- | --- |
| 매칭 범위 | 좁히기 쉽다 | 후보 탐색이 늘 수 있다 |

브라우저는 보통 오른쪽 선택자에서 후보를 찾고 조상을 거슬러 조건을 확인한다. 오른쪽 항이 넓고 조합이 깊으면 검사량이 늘 수 있다.

## 렌더링 방식은 어떤 요구로 결정하는가?

콘텐츠 갱신 주기, 개인화, 검색 노출, 서버 비용으로 결정한다. 정적 콘텐츠는 SSG, 요청별 데이터는 SSR, 앱형 상호작용은 CSR이 유리하다.

| 상황 | 방식 | 이유 |
| --- | --- | --- |
| 정적 콘텐츠 | SSG | 미리 생성 |
| 요청별 데이터 | SSR | 요청 시 생성 |

SSG는 응답이 빠르고 서버 부하가 작지만 갱신이 늦을 수 있다. SSR은 최신 데이터를 주지만 요청마다 렌더링 비용과 장애 지점이 생긴다.

CSR은 초기 자바스크립트 비용과 검색 노출을 관리해야 한다. 실제 서비스는 경로와 컴포넌트마다 방식을 섞고 캐시나 재생성으로 약점을 보완한다.

## 로그 레벨을 구분하여 설정하는 이유는 무엇인가?

| 기준 | DEBUG | INFO | ERROR |
| --- | --- | --- | --- |

## CSRF와 XSS의 결정적인 차이는 무엇인가?

사용자 브라우저의 권한을 도용하는 방식의 차이다. XSS는 악성 스크립트를 웹 페이지에 삽입해 실행시키고, CSRF는 사용자의 인증된 세션을 이용해 원치 않는 요청을 보내는 것이다.

| 기준 | XSS | CSRF |
| --- | --- | --- |
| 공격 대상 | 사용자 브라우저 | 서버의 상태 변경 |
| 실행 주체 | 삽입된 스크립트 | 위조된 요청 |
| 핵심 원인 | 검증되지 않은 입력값 | 자동 전송되는 쿠키 |

XSS는 스크립트가 실행되면 쿠키, 세션 ID로 같은 톤으로 함께만 사용하여 세션 하이재킹을 수행한다. 반면 CSRF는 세션 ID를 가로채지 않고, 사용자가 로그인한 상태라는 점을 즉시 이용한다.

CSRF는 주로 데이터 변경, 비밀번호 변경과 같은 상태 변경 요청에 치명적이다. XSS는 데이터 탈취취 및 페이지 변조로 범위가 더 넓다.

## 프론트엔드 성능 최적화 시 번들 크기를 무엇으로 판단하는가?

최초 로딩 시 사용자가 체감하는 LCP(Largest Contentful Paint)와 TBT(Total Blocking Time)를 기준으로 판단한다. 단순히 파일 용량만 줄이는 것이 아니라 런타임 실행 시간과 파싱 시간을 함께 고려해야 한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 런타임 성능 | JS 실행 및 DOM 조작 속도 |
| 네트워크 성능 | 번들 다운로드 및 압축 해제 속도 |

위 도식은 번들이 실제 성능에 영향을 주는 두 가지 경로를 보여준다. 파일이 작아도 복잡한 로직이 많으면 TBT가 늘어난다.

코드 분할(Code Splitting)을 통해 초기 진입점에 필요한 최소한의 JS만 로드하게 만든다. 이를 통해 메인 스레드 점유 시간을 줄이고 빠른 상호작용을 유도한다.

트리 쉐이킹(Tree Shaking)으로 사용하지 않는 코드를 제거해 전송량을 줄인다. 라이브러리 선택 시 ESM(ES Modules) 지원 여부를 확인하는 것이 핵심이다.

## 웹 서버와 WAS의 역할 분담은 왜 하는가?

정적 리소스 처리 효율을 높이고 서버 부하를 분산하기 위해서다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 웹 서버 | HTML, CSS, 이미지 등 정적 파일 처리 |
| WAS | DB 조회, 비즈니스 로직 등 동적 콘텐츠 생성 |

웹 서버가 앞단에서 정적 파일을 먼저 처리하면 WAS는 무거운 로직 수행에만 집중할 수 있다. 요청의 성격에 따라 처리 주체를 나누어 전체 응답 속도를 높인다.

또한 WAS에 장애가 발생해도 웹 서버가 에러 페이지를 대신 보여줄 수 있다. 여러 대의 WAS를 웹 서버 뒤에 배치하여 부하를 나누는 로드밸런싱 구조를 구축하기 쉽다.

## React Hook을 사용하는 이유는 무엇인가?

함수형 컴포넌트에서도 상태 관리와 생명주기 기능을 사용할 수 있기 때문이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 클래스 컴포넌트 | this.state, lifecycle methods |
| 함수형 컴포넌트 | useState, useEffect |

기존 클래스 컴포넌트는 로직 재사용이 어렵고 코드가 비대해지는 경향이 있었다. 훅을 통해 상태 관련 로직을 함수로 분리하여 여러 컴포넌트에서 공유할 수 있다.

## 브라우저에서 FTP 지원을 중단하는 이유는 무엇인가?

보안 취약점과 현대적인 웹 표준의 부재 때문이다. FTP는 평문으로 데이터를 주고받아 스니핑으로 계정 정보와 파일로 내용이 유발출된다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 보안 수준 | FTP. 평문 전송. 매우 위험 |
| HTTPS | TLS 암호화. 표준으로 정착 |

또한 FTP는 방화벽과 프록시 서버 환경에서 포트 제어와 포트 범위 지정이 까다롭다. 이는 사용자 경험을 해방하고 개발 효율을 떨어뜨린다.

현재는 HTTP/S 기반의 파일 업로드와 다운로드 API를 사용하는 것이 표준이다. 브라우저가 직접 FTP 프로토콜을 동작시키는 기능은 더 이상 필요하지 않다.
