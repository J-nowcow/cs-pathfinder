## DB 커넥션을 매번 새로 맺는 비용이 큰 이유는?

커넥션 생성은 객체 하나를 만드는 일이 아니다. 네트워크 연결부터 세션 준비까지 여러 단계를 매번 다시 밟는다.

한 번 맺을 때 실제로 오가는 것은 이렇다. 단계마다 왕복이 끼어 있어 밀리초가 쌓인다.

1. **앱 → DB** — TCP 연결 요청. 3-way handshake가 먼저 돈다
2. **앱 → DB** — 인증 정보 전달. 계정과 권한을 확인한다
3. **DB → 앱** — 세션 준비 완료. 내부 자원을 할당한 뒤 응답한다

요청마다 맺고 닫으면 이 비용이 응답 시간에 그대로 실린다. 동시 요청이 몰리면 문제가 커진다. DB가 질의 처리 대신 커넥션 생성과 해제에 CPU와 메모리를 쓰기 때문이다.

connection pool은 두 가지를 한다. 미리 만들어 둔 커넥션을 재사용해 생성 비용을 없앤다. 동시에 DB로 나가는 커넥션 수에 상한을 둬 DB를 보호한다. 뒤쪽이 더 중요하다.

면접에서는 pool 크기를 어떻게 정하느냐로 한 단계 더 들어온다. 크게 잡으면 DB 자원을 과점유하고 작게 잡으면 애플리케이션 쪽 대기가 늘어난다는 양면을 함께 말할 수 있어야 한다.

## 인덱스를 만들었는데 실행 계획에서 타지 않는 이유는?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

인덱스가 있어도 옵티마이저가 쓸 수 없거나 쓰지 않는 편이 낫다고 판단한 것이다. 두 경우는 원인이 다르다.

| 갈래 | 실행 계획에서 | 대표 원인 |
| --- | --- | --- |
| 쓸 수 없다 | 후보에도 안 오른다 | 컬럼에 함수 적용, 암묵 타입 변환, 선행 컬럼 누락 |
| 쓰지 않는다 | 후보엔 있는데 안 고른다 | 조회 비율이 높다, 통계가 낡았다 |

쓸 수 없는 경우가 먼저다. 인덱스 컬럼에 함수나 연산을 적용하면 인덱스는 무력해진다. 저장된 값과 비교 대상이 달라지기 때문이다. 타입이 암묵적으로 변환되는 경우도 같다. 복합 인덱스에서 선행 컬럼을 조건에 넣지 않은 경우도 여기 속한다.

쓰지 않기로 한 경우는 통계 문제다. 조회 대상이 전체의 상당 비율이면 인덱스로 한 건씩 찾아가는 것보다 풀 스캔이 빠르다. 옵티마이저는 카디널리티 추정으로 이를 판단하는데, 통계가 오래되면 추정이 틀린다.

진단 순서가 있다. 실행 계획을 먼저 보고 인덱스가 후보에 올랐는지 확인한다. 후보에도 없으면 쓸 수 없는 경우이고, 후보에 있는데 선택되지 않았으면 통계나 비용 추정 문제다.

면접에서는 함수 적용 사례를 자주 묻는다. 날짜 컬럼에 포맷 함수를 씌운 조건이 대표적이다. 조건을 범위 비교로 바꾸면 인덱스가 다시 살아난다.

## 서브쿼리를 언제 조인으로 재작성해야 성능이 향상되는가?

RDBMS 옵티마이저는 조인 연산의 최적화 경로를 서브쿼리보다 더 다양하게 탐색할 수 있다. 서브쿼리를 사용하면 서브쿼리 블록 단위로 최적화가 수행되어 전체 쿼리 수준에서의 최적화 기회를 잃기 쉽다. 특히 외부 쿼리의 값을 참조하는 상관 서브쿼리는 매 행마다 반복 실행되어 성능 저하의 주 원인이 된다.

서브쿼리를 조인으로 변환할 때는 일대다 관계에서 데이터가 증폭되는 문제를 주의해야 한다. 서브쿼리는 단순히 존재 여부만 확인하여 원본 행 수를 유지하지만, 이를 단순 조인으로 바꾸면 중복 데이터가 생성되어 DISTINCT나 GROUP BY를 추가해야 하므로 오히려 성능이 떨어질 수 있다.

| 기준 | 서브쿼리 | 조인 (Join) |
| --- | --- | --- |
| 실행 방식 | 독립된 블록 또는 반복 실행 | 다양한 조인 알고리즘 선택 |
| 결과 행 수 | 원본 테이블 행 수 유지 | 관계에 따라 중복 발생 가능 |
| 최적화 범위 | 쿼리 블록 내로 제한됨 | 전역적인 실행 계획 수립 |

최신 옵티마이저는 서브쿼리 언네스팅 기법을 통해 내부적으로 서브쿼리를 조인으로 자동 변환하여 실행한다. 따라서 개발자가 성능 개선을 위해 수동으로 변환하기 전에, 옵티마이저의 실행 계획을 먼저 확인하고 자동 최적화가 작동하지 않는 경우에만 수동으로 변환해야 한다.

## 격리 수준을 올리면 무엇을 잃는가?

동시성을 잃는다. 위로 올라갈수록 막아주는 현상이 늘지만 그만큼 잠금을 오래 넓게 쥔다. 무엇을 막고 싶은지가 아니라 무엇을 견딜 수 있는지로 고른다.

| 수준 | 막아주는 것 | 대가 |
| --- | --- | --- |
| Read Committed | 커밋 안 된 값 읽기 | 같은 질의가 두 번 다를 수 있다 |
| Repeatable Read | 읽은 행이 중간에 바뀌는 것 | 없던 행이 끼어드는 것은 못 막는다 |
| Serializable | 전부 | 충돌 시 트랜잭션이 취소된다 |

기본값은 대개 Read Committed다. 대부분의 화면은 조금 어긋난 값을 견딘다. 잔액을 읽어 검사하고 쓰는 자리처럼 읽은 값을 근거로 판단할 때만 위로 올린다.

올리는 것 말고 다른 길도 있다. `select ... for update`로 그 한 줄만 잠그거나, 버전을 두고 커밋 때 확인하는 방식이다. 범위를 좁게 잡으면 수준을 올리지 않고도 같은 것을 지킬 수 있다.

면접에서는 Serializable이 어떻게 구현되는지로 들어온다. 전부 줄 세우는 것이 아니라 충돌을 감지해 한쪽을 취소하는 방식이다. 그래서 애플리케이션에 재시도 코드가 있어야 한다.

## 데이터베이스 정규화를 수행하는 이유는 무엇인가?

데이터 중복을 최소화하여 데이터 무결성을 유지하고 이상 현상을 방지하기 때문이다.

| 기준 | 정규화 전 | 정규화 후 |
| --- | --- | --- |
| 데이터 중복 | 많음 | 적음 |
| 삽입/삭제/수정 이상 | 발생 가능 | 방지 가능 |
| 조회 성능 | 단순 조인 없음 | 조인 필요 |

정규화를 하지 않으면 동일한 정보가 여러 곳에 저장된다. 이로 인해 데이터를 수정할 때 일부만 수정되어 데이터 간 불일치가 발생하는 수정 이상이 생긴다.

또한, 관련된 정보가 함께 저장되어 필요 없는 정보까지 함께 삽입하거나 삭제해야 하는 삽입 및 삭제 이상이 발생한다.

과도한 정규화는 조회 시 많은 조인(Join) 연산을 유도하여 성능 저하를 일으킨다. 따라서 실무에서는 성능 향상을 위해 일부러 정규화를 푸는 역정규화 과정을 거치기도 한다.

## 트랜잭션 격리 수준을 결정하는 기준은 무엇인가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

데이터 정합성 보장 수준과 시스템 성능 사이의 트레이드오프를 기준으로 결정한다.

| 기준 | 격리 수준 낮음 | 격리 수준 높음 |
| --- | --- | --- |
| 정합성 | 낮음 (이상 현상 발생) | 높음 (데이터 일관성) |
| 성능/처리량 | 높음 (잠금 최소화) | 낮음 (잠금/대기 증가) |

격리 수준이 낮으면 여러 트랜잭션이 같은 데이터를 동시에 읽고 쓸 수 있어 처리량이 늘어난다. 하지만 더티 리드나 팬텀 리드 같은 현상이 발생해 데이터가 꼬일 수 있다.

반대로 격리 수준을 높이면 엄격한 잠금을 사용해 정합성을 완벽하게 보장한다. 다만, 트랜잭션 간 대기 시간이 길어져 전체적인 시스템 응답 속도가 떨어진다.

실무에서는 보통 Read Committed를 기본으로 쓰며, 정밀한 계산이 필요한 금융권이나 결제 로직에서는 Repeatable Read 이상을 선택한다.

## 데이터베이스 뷰는 언제 사용하는가?

복잡한 쿼리를 단순화하거나 보안을 위해 특정 컬럼만 노출할 때 사용한다. 가상 테이블로서 실제 데이터를 저장하지 않고 쿼리문만 저장한다.

| 기준 | 뷰(View) | 일반 테이블 |
| --- | --- | --- |
| 데이터 저장 | 저장 안 함 | 실제 데이터 저장 |
| 물리적 공간 | 정의만 저장 | 데이터만큼 점유 |
| 용도 | 가독성, 보안 | 데이터 관리 |

뷰를 쓰면 복잡한 조인 문을 매번 쓸 필요가 없다. 사용자는 정의된 뷰를 조회함으로써 내부 구조를 몰라도 데이터를 가져올 수 있다.

보안 측면에서는 민감한 정보를 제외한 컬럼만 뷰로 제공한다. 이를 통해 원본 테이블에 직접 접근하지 않고 필요한 데이터만 안전하게 노출한다.

다만 뷰는 조회 시마다 정의된 쿼리가 실행된다. 원본 테이블의 인덱스를 타지 못하는 복잡한 뷰는 성능 저하를 일으킬 수 있다.

## 데이터베이스 스키마를 설계할 때 고려할 점은 무엇인가?

데이터의 무결성을 유지하면서 중복을 최소화하는 정규화와 확장성을 고려한 비정규화를 조절하는 것이다.

| 기준 | 정규화 | 비정규화 |
| --- | --- | --- |
| 목적 | 중복 제거 및 무결성 | 조회 성능 향상 |
| 영향 | 쓰기 속도 증가 | 읽기 속도 증가 |

정규화는 데이터 중복을 없애 테이블을 쪼개는 과정이다. 삽입, 수정, 삭제 시 발생하는 이상 현상을 방지해 데이터 신뢰도를 높인다.

반면 비정규화는 성능을 위해 의도적으로 중복을 허용하는 것이다. 조인 횟수가 너무 많아 읽기 성능이 급격히 떨어질 때 선택한다.

결국 서비스의 읽기-쓰기 비율과 트래픽 규모를 판단해 두 전략의 균형점을 찾는 것이 핵심이다.

## JOIN 연산의 성능을 결정하는 핵심 요소는 무엇인가?

인덱스 활용 여부와 조인 방식의 선택이다. 인덱스가 없으면 전체 테이블을 훑어야 하므로 비용이 급격히 증가한다.

| 기준 | Nested Loop | Hash Join |
| --- | --- | --- |
| 적합한 데이터 | 소량/인덱스 있음 | 대량/인덱스 없음 |
| 처리 방식 | 중첩 반복 수행 | 해시 테이블 생성 |

Nested Loop 조인은 바깥쪽 테이블의 행마다 안쪽 테이블을 탐색한다. 안쪽 테이블의 조인 컬럼에 인덱스가 있으면 매우 빠르게 동작한다.

Hash Join은 두 테이블 중 작은 쪽으로 해시 맵을 먼저 만든다. 이후 큰 테이블을 읽으며 해시 맵에서 일치하는 값을 찾는다. 대량 데이터 처리에 유리하다.

정렬 상태에 따라 Merge Join이 선택되기도 한다. 옵티마이저는 통계 정보를 바탕으로 데이터 양과 인덱스 상태를 보고 가장 싼 비용의 방식을 결정한다.

## 인덱스 생성 시 읽기 성능과 쓰기 성능의 트레이드오프는 무엇인가?

인덱스가 많아지면 읽기 속도는 빨라지지만, 데이터 변경 시 인덱스 구조를 함께 수정해야 하므로 쓰기 성능이 떨어진다.

| 기준 | 읽기 성능 | 쓰기 성능 |
| --- | --- | --- |
| 인덱스 수 | 많을수록 유리 | 많을수록 불리 |
| 작업 내용 | 인덱스 탐색으로 범위 좁힘 | B-Tree 구조 재구성 및 정렬 |

인덱스는 데이터의 위치를 저장한 별도의 저장소다. 데이터를 삽입하거나 수정할 때 실제 데이터 페이지와 인덱스 페이지를 모두 갱신해야 한다.

특히 삽입 시 B-Tree의 노드 분할이 발생하면 여러 페이지를 수정해야 하므로 오버헤드가 크다. 따라서 쓰기 작업이 빈번한 테이블에서는 인덱스 수를 최소화해야 한다.

## DBSCAN은 K-means보다 어떤 상황에서 더 유리한가?

데이터의 분포가 원형이 아니거나 노이즈가 섞인 데이터셋에서 유리하다. K-means는 구형의 클러스터만 찾을 수 있지만, DBSCAN은 밀도 기반으로 임의의 모양을 찾아내기 때문이다.

| 기준 | K-means | DBSCAN |
| --- | --- | --- |
| 클러스터 모양 | 구형 (Centroid 기반) | 임의의 모양 (Density 기반) |
| 노이즈 처리 | 모든 점을 할당 | 밀도 미달 점을 노이즈로 분류 |
| 파라미터 | K (클러스터 개수) | eps, minPts (밀도 기준) |

DBSCAN은 설정한 거리(eps) 내에 최소 점 개수(minPts)가 있으면 이를 핵심적으로 연결한다. 이 과정을 반복해 밀도가 높은 영역을 하나의 덩어리로 묶는다.

반면 K-means는 모든 데이터를 강제로 클러스터에 포함시킨다. 밀도가 낮은 외곽의 점들이 중심점과 묶여 클러스터의 모양을 왜곡시킨다.

따라서 데이터의 실제 모양을 모르거나 이상치(Outlier)를 제거해야 하는 전처리 단계에서 DBSCAN이 효과적이다.

## 테이블 설계 시 기본키를 설정하는 기준은 무엇인가?

데이터의 유일성과 불변성을 보장하는 값을 선택한다. 중복되지 않아야 하며 값이 바뀌지 않는 속성이 가장 적합하다.

| 기준 | 적절한 키 | 부적절한 키 |
| --- | --- | --- |
| **유일성** | 주민등록번호 | 이름, 나이 |
| **불변성** | UUID, 일련번호 | 이메일, 전화번호 |
| **변경 가능성** | 시스템 생성 ID | 사용자 수정 가능 값 |

후보키 중에서 가장 효율적으로 식별자 역할을 수행할 수 있는 키를 기본키로 정한다. 비즈니스 로직에 의존적인 값은 변경 가능성이 있어 피하는 것이다.

대리 키를 사용하는 이유는 데이터 모델의 안정성을 때문이다. 실제 데이터(이메일 등)가 변경되어도 외래 키 참조 무결성을 유지하기 쉽기 때문이다.

기본키가 너무 크거나 복잡하면 인덱스 성능이 왜곡된다. 인덱스 B-Tree 구조에서 키의 크기가 것이 효율적인 검색과 정렬으로 이어진다.

## 인덱스 생성 시 조회 성능과 쓰기 성능의 트레이드오프는 무엇인가?

조회 속도는 빨라지나 데이터 변경 시 인덱스 갱신 비용이 발생해 쓰기 성능이 떨어진다.

| 기준 | 조회 성능 | 쓰기 성능 |
| --- | --- | --- |
| 인덱스 없음 | 느림 (전체 스캔) | 빠름 (단순 삽입) |
| 인덱스 있음 | 빠름 (탐색으로 찾음) | 느림 (정렬 유지) |

인덱스는 데이터의 물리적 순서와 별개로 정렬된 별도의 저장 공간을 갖는다. 데이터를 넣을 때마다 이 정렬 순서를 유지해야 하므로 삽입, 수정, 수정 삭제 시 부하가 증가한다.

반면 조회 시에는 정렬된 상태를 이용해 전체 데이터를 다 훑지 않고 빠르게 찾을 수 있다. 특히 범위 검색이나 정렬된 결과가 필요할 때 효과가 극히 크다.

무분별한 인덱스 생성은 오히려 디스크 I/O를 늘려 시스템 전체 성능을 저하시킨다. 데이터의 분포도와 쿼리 패턴을 분석해 필요한 컬럼에만 최소한으로 설정하는 것이 중요하다.

## 조인으로 인해 성능 저하가 발생하는 원인은 무엇인가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

조인이 많아지면 데이터셋의 크기가 기하급수적으로 늘어나고 메모리 내 정렬과 병합 작업이 증가하기 때문이다.

| 기준 | Nested Loop Join | Hash Join | Merge Join |
| --- | --- | --- | --- |
| 처리 방식 | 이중 루프 순회 | 해시 테이블 생성 | 정렬 후 병합 |
| 적합한 데이터 | 소량 데이터 | 대량 데이터 | 정렬된 데이터 |
| 시간 복잡도 | O(N*M) | O(N+M) | O(N log N + M log M) |

Nested Loop Join은 외부 테이블의 모든 행을 하나씩 읽어 내부 테이블에서 조건에 맞는 행을을 찾는다. 인덱스가 없으면 전체 테이블 스캔이 발생해 성능이 급격히 떨어진다.

Hash Join은 작은 테이블을 메모리에 해시 테이블로 올린 뒤 큰 테이블을 스캔하며 매칭되는 값을 찾는다. 메모리 부족 시 디스크 I/O가 발생해 느려진다.

Merge Join은 양쪽 테이블을 조인 키로 정렬한 뒤 순차적으로 읽으며 병합한다. 이미 정렬되어 있거나 범위 조인을 수행할 때 효율적이다.

## 커넥션 풀을 사용하는 이유는 무엇인가?

데이터베이스 연결 생성 비용이 매우 크기 때문이다. 매번 연결을 맺고 끊는 과정에서 TCP 핸드셰이크와 인증 과정이 반복되어 응답 시간이 늘어난다.

1. **클라이언트 → 커넥션 풀** — 연결 요청
2. **커넥션 풀 → 클라이언트** — 유효한 커넥션 대여
3. **클라이언트 → 커넥션 풀** — 사용 후 반납

풀에 미리 연결을 생성해 두고 대여하는 방식으로 동작한다. 이를 통해 연결 생성 시간을 제거하여 시스템 전체의 처리량(Throughput)을 높일 수 있다.

풀의 크기를 너무 크게 잡으면 DB 서버의 메모리와 CPU 자원을 과하게 사용한다. 반대로 너무 작게 잡으면 요청이 밀려 대기 시간이 길어진다.

적절한 크기를 설정하는 것이 핵심이다. 서비스의 트래픽 패턴과 DB 서버의 사양을 고려하여 벤치마크 테스트를 통해 최적값을 찾아야 한다.

## RDB와 NoSQL 중 무엇을 기준으로 선택하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

데이터의 정형성도와 쓰기/읽기 부하량에 따라 결정한다. 엄격한 스키마가 필요하면 RDB를, 유연한 구조와 대용량 처리가 우선이면 NoSQL을 쓴다.

| 기준 | RDB | NoSQL |
| --- | --- | --- |
| 스키마 | 고정적 | 유연함 |
| 확장성 | 수직 확장(Scale-up) | 수평 확장(Scale-out) |
| 트랜잭션 | ACID 준수 | BASE (최종 일관성) |

정형 데이터는 RDB가 유리하다. 조인(Join)을 통해 중복을 제거하고 무결성을 보장한다. 반면 NoSQL은 중복을 허용하며 데이터 접근 속도를 높인다.

트랜잭션 보장 수준이 중요하다면 RDB를 쓴다. 금융 거래처럼 정확한 데이터 일관성이 필수적인 곳에 적합하다.

분산 환경에서 빠르게 확장해야 한다면 NoSQL이 낫다. 샤딩(Sharding)이나 복제(Replication)를 통해 수평적 확장이 용이해 데이터 양이 늘어나도 대응이 가능하다.

## 데이터베이스 복제와 클러스터링의 선택 기준은 무엇인가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

가용성과 읽기 성능 향상과 읽기-쓰기 분리라는 목적에 따라 고른다.

| 기준 | 복제(Replication) | 클러스터링(Clustering) |
| --- | --- | --- |
| 핵심 목적 | 데이터 백업 및 읽기 분산 | 고가용성 및 시스템 확장 |
| 데이터 일관성 | 비동기적, 지연 발생 | 동기적, 높은 일관성 |
| 구조 | Master-Slave 구조 | 공유 저장소 또는 분산 저장 |

복제는 기본적으로 데이터를 다른 서버로 복사하는 방식이다. 주로 읽기 전용 복제본(Slave)을 늘려 읽기 트래픽을 분산시킨다. 데이터가 복사되는 시점차로 인해 복제 지연(Replication Lag) 방향으로 파고들 수 있다.

클러스터링은 여러 대의 서버를 하나의 시스템처럼 동작하게 한다. 노드 하나가 죽어도 서비스가 중단되지 않는 고가용성(HA)이 핵심이다. 공유 저장소를 사용하거나 데이터 샤딩으로 처리량을 높인다.

실무에서는 읽기 요청이 압도적으로 많다면 복제를 선택하고, 쓰기 작업이 빈번하고 중단 없는 서비스가 필수적이라면 클러스터링을 구성한다.

## 낙관적 락과 비관적 락은 무엇으로 고르는가?

데이터 충돌로 인한 갱신 손실을 막기 위해 충돌 빈도와 시스템 부하를 기준으로 고른다.

| 기준 | 낙관적 락 | 비관적 락 |
| --- | --- | --- |
| 충돌 빈도 | 드물 때 | 잦을 때 |
| 락킹 비용 | 낮음 (버전 체크) | 높음 (물리적 잠금) |
| 대기 시간 | 없음 (실패 시 재시도) | 발생 (락 획득 대기) |

낙관적 락은 데이터 수정 시점에 버전 번호를 확인해 충돌을 감지한다. 충돌이 없으면 반영하고, 버전이 다르면 예외를 던져 사용자가 다시 시도하게 만든다.

비관적 락은 데이터를 읽을 때부터 잠금을 걸어 다른 트랜잭션이 접근하지 못하게 막는다. 데이터 무결성을 강하게 보장하지만, 대기 시간이 늘어나 성능 저하가 발생할 수 있다.

실무에서는 읽기 비중이 높고 충돌이 적은 서비스에 낙관적 락을 쓴다. 반면, 결제나 재고 관리처럼 충돌이 잦고 데이터 정확성이 절대적인 곳에 비관적 락을 쓴다.

## 인덱스 범위 스캔과 전체 스캔 중 무엇을 선택하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

데이터의 선택도와 비용 옵티마이저의 판단에 따라 결정한다. 읽어야 할 데이터가 전체의 일정 비율을 넘으면 인덱스보다 전체 스캔이 빠르다.

| 기준 | 인덱스 범위 스캔 | 전체 스캔 |
| --- | --- | --- |
| 접근 방식 | B-Tree 탐색 후 리프 노드 순회 | 데이터 페이지 순차 읽기 |
| 효율성 | 소량 데이터 추출 시 유리 | 대량 데이터 추출 시 유리 |
| I/O 방식 | 랜덤 I/O 발생 | 순차 I/O 발생 |

인덱스 범위 스캔은 인덱스 페이지를 거쳐 데이터 페이지로 이동하는 랜덤 I/O가 발생한다. 읽을 양이 많아지면 이 오버헤드가 순차적으로 읽는 전체 스캔보다 커진다.

옵티마이저는 통계 정보를 바탕으로 비용을 계산한다. 인덱스를 통해 읽어야 할 페이지 수가 전체 페이지 수의 상당 부분을 차지하면 전체 스캔을 선택한다.

실무에서는 통계 정보가 오래되었을 때 엉뚱한 스캔 방식이 선택되어 성능이 급락한다. 이때는 힌트를 사용해 강제로 실행 계획을 변경해야 한다.

## SQL과 NoSQL은 어떤 기준으로 선택하는가?

> ⚠️ 이 해설은 교차 대조에서 **사실 지적이 나왔다**(사람 검토 전). 지적 내용은 [하드 오류 목록](../../code/docs/audit/2026-08-07-hard-errors.md)에 있다.

데이터의 구조와 일관성 필요 수준에 따라 선택한다. 정형 데이터와 엄격한 스키마가 필요하면 SQL, 유연한 데이터 구조와 대규모 확장성이 필요하면 NoSQL을 쓴다.

| 기준 | SQL | NoSQL |

위 표는 두 방식의 데이터 관리 전략의 차이점을 보여준다.

SQL은 외래키를 통한 관계형 모델을 사용하여 데이터 무결성을 보장한다. 복잡한 조인 연산이 필요하고 트랜잭션의 원칙을 엄격히 지켜야 하는 금융 서비스 등에 적합하다.

NoSQL은 정해진 틀 없이 데이터를 저장한다. 읽기와 쓰기 속도가 매우 빠르며, 대량의 로그 데이터나 실시간 채팅 데이터처럼 구조가 자주 바뀌는 비정형 데이터 처리에 유리하다.
