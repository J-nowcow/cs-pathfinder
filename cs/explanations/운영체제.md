## 컨텍스트 스위칭 비용은 구체적으로 어디서 발생하는가?

레지스터 교체 자체보다 캐시가 무너지는 비용이 크다. 눈에 보이는 저장·복원은 일부일 뿐이다.

| 구분 | 무엇이 일어나나 | 크기 |
| --- | --- | --- |
| 직접 비용 | 레지스터·PC를 PCB에 저장하고 복원, 커널 모드 전환 | 수 마이크로초 |
| 간접 비용 | 캐시와 TLB가 무효화되어 다시 채워야 한다 | **이쪽이 본체** |

직접 비용은 명확하다. 실행 중이던 스레드의 레지스터와 프로그램 카운터를 PCB에 저장하고 다음 스레드의 것을 복원한다. 커널 모드 전환도 함께 일어난다. 이건 수 마이크로초 수준이다.

간접 비용이 본체다. CPU 캐시와 TLB에 쌓아둔 내용이 새 스레드에게는 쓸모없다. 다시 실행될 때 캐시 미스가 연달아 나고 메모리에서 다시 읽어와야 한다. 프로세스 간 전환이면 주소 공간까지 바뀌어 TLB를 통째로 비운다.

그래서 스레드를 늘린다고 처리량이 비례해 늘지 않는다. 코어 수를 넘어서면 실행이 아니라 전환에 시간을 쓰기 시작한다. 커넥션 풀 크기를 코어 수 기준으로 잡는 근거가 여기 있다.

CPU 바운드 작업은 코어 수에 맞추고 I/O 바운드는 더 늘려도 되는 이유도 같다. 대기 중인 스레드는 CPU를 점유하지 않기 때문이다.

## 데드락은 어떤 조건이 모두 모여야 생기는가?

네 조건이 동시에 성립할 때다. 하나만 깨도 데드락은 생기지 않는다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 상호 배제 | 자원을 한 번에 하나만 쓸 수 있다 |
| 점유하며 대기 | 하나를 쥔 채로 다른 것을 기다린다 |
| 비선점 | 쥔 것을 강제로 뺏을 수 없다 |
| 순환 대기 | 기다림이 고리를 이룬다 |

실무에서 가장 자주 깨는 것은 마지막이다. 자원에 순서를 매기고 항상 그 순서로만 잡게 하면 고리가 생길 수 없다. 계좌 두 개를 잠글 때 언제나 번호가 작은 쪽부터 잡는 식이다.

점유하며 대기를 깨는 방법도 있다. 필요한 자원을 한 번에 전부 잡거나, 못 잡으면 쥔 것을 놓고 처음부터 다시 한다. 다만 이쪽은 굶주림이 생길 수 있다 — 계속 실패하는 쪽이 영영 못 잡는다.

면접에서는 예방과 회피와 탐지를 구별하는지를 본다. 예방은 조건을 아예 못 만들게 한다. 회피는 요청마다 안전한지 따져본다. 탐지는 생기게 두되 발견하면 푼다. 데이터베이스는 대개 마지막을 고른다 — 앞의 둘이 처리량을 너무 깎기 때문이다.

## 가상 메모리는 무엇을 해결하는가?

프로세스마다 자기만의 연속된 주소 공간을 준다. 실제 물리 메모리가 조각나 있어도, 남의 메모리와 섞여 있어도 프로그램은 그것을 몰라도 된다.

1. **CPU → MMU** — 가상 주소로 읽어라
2. **MMU → 페이지 테이블** — 이 주소는 어느 프레임인가
3. **페이지 테이블 → MMU** — 없다. 디스크에 밀려 있다
4. **MMU → 커널** — 페이지 폴트. 가져와라
5. **커널 → CPU** — 프레임에 올렸다. 다시 실행해라

얻는 것이 셋이다. 프로세스끼리 격리되고, 물리 메모리보다 큰 프로그램이 돌고, 같은 코드를 여러 프로세스가 한 벌만 올려 쓴다.

값은 변환 비용이다. 주소마다 테이블을 뒤지면 느려서 TLB라는 캐시를 둔다. 컨텍스트 스위칭에서 이 캐시가 비워지는 것이 전환 비용의 큰 몫이다.

디스크로 밀리기 시작하면 성능이 무너진다. 페이지 폴트가 연쇄로 나면서 실행보다 옮기는 데 시간을 더 쓰는 상태를 스래싱이라 한다.

## 사용자 모드에서 커널 모드로 진입하는 이유는 무엇인가?

사용자 프로그램이 하드웨어에 직접 접근하여 시스템을 파괴하는 것을 막기 위해서다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 사용자 모드 | 프로세스. 제한된 권한으로 실행 |
| 커널 모드 | 운영체제. 모든 하드웨어 권한 보유 |

위 구조처럼 권한을 분리하여 하드웨어 제어권을 독점한다. 프로그램이 메모리나 디스크에 직접 쓰기를 시도하면 CPU가 이를 감지해 커널 모드로 전환한다.

시스템 콜은 이 전환을 수행하는 유일한 통로다. 운영체제가 미리 정해놓은 인터페이스를 통해 요청을 보내고, 커널이 요청의 정당성을 검사한 후 대신 수행한다.

이 과정에서 컨텍스트 스위칭 비용이 발생한다. 빈번한 시스템 콜 호출은 전체 시스템 성능에 영향을 주므로 효율적으로 설계해야 한다.

## 스레드 풀을 사용하는 주된 이유는 무엇인가?

스레드 생성과 제거에 드는 오버헤드를 줄이기 위해서다. 요청마다 스레드를 새로 만들면 커널 모드 전환과 메모리 할당 비용이 반복적으로 발생한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 풀링 영역 | 미리 생성해 둔 스레드들의 집합 |
| 작업 큐 | 대기 중인 요청들이 쌓이는 곳 |

작업 큐에 요청이 들어오면 풀에 있는 유휴 스레드가 이를 가져가 처리한다. 처리가 끝나면 스레드는 소멸하지 않고 다시 풀로 돌아가 다음 작업을 기다린다.

적절한 풀 크기를 설정하지 않으면 문제가 생긴다. 너무 작으면 요청이 큐에 쌓여 응답 시간이 느려지고, 너무 크면 컨텍스트 스위칭 비용이 커져 전체 처리량이 떨어진다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |

## 데드락을 해결하기 위한 회피 전략은 무엇인가?

은행원 알고리즘을 사용하여 자원 할당 시 안전 상태를 유지하는 것이다. 자원을 할당한 후에도 모든 프로세스가 완료될 수 있는 경로가 있는지 확인한다.

1. **자원 요청 → 안전 상태 확인** — 할당 가능한 자원이 있는지 검사
2. **안전 상태 확인 → 자원 할당** — 모든 프로세스가 완료될 수 있는 경로가 있다면 할당
3. **자원 할당 → 자원 반납** — 프로세스 완료 후 자원을 시스템에 반납

회피는 교착 상태가 발생할 수 있는 상황을 아예 만들지 않는 것이다. 요청한 자원을 즉시 줄 수 없다면, 다른 프로세스가 자원 반납을 통해 안전하게 완료될 수 있을 때까지 대기시킨다.

반면 예방은 교착 상태의 발생 조건 네 가지 중 하나라도 깨뜨리는 것. 회피는 시스템의 자원 상태를 계속 추적하며 동적으로적으로 결정한다.

은행원 알고리즘은 모든 프로세스가 필요로 하는 최대 자원량을 미리로 알고 있어야 한다. 실무적으로는 프로세스의 최대 자원을 예측하기 어려워 적용으로 범위가 좁다.

## 가상 메모리를 사용하는 이유는 무엇인가?

물리 메모리보다 큰 프로세스를 실행하고 메모리 효율을 높이기 때문이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 가상 주소 | 프로세스가 보는 주소 |
| 페이지 테이블 | 가상 주소를 물리 주소로 매핑 |
| 물리 주소 | 실제 RAM의 위치 |

프로세스는 가상 주소만 보고 동작한다. 운영체제는 필요한 부분만 물리 메모리에 올리고 나머지는 디스크의 스왑 영역에 둔다.

이 방식은 프로세스 간 메모리 격리를 가능케 한다. 각 프로세스는 독립된 주소 공간을 가져 서로의 영역을 침범하지 못한다.

물리 메모리가 부족하면 페이지 폴트가 발생한다. 이때 운영체제는 덜 쓰이는 페이지를 디스크로 내보내고 새 페이지를 가져온다.

## 사용자 모드와 커널 모드 전환의 이유는 무엇인가?

시스템 콜을 통해 커널의 특권 권한으로 진입하여 하드웨어와 시스템 자원을 안전하게 보호하기 때문이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 사용자 모드 | 제한된 권한. 애플리케이션이 동작하는 영역 |
| 커널 모드 | 무제한 권한 \| 하드웨어 제어 및 메모리 보호 |

사용자 모드에서 하드웨어에 직접 접근하면 악성 코드가 메모리를 조작하거나 시스템을 파괴할 수 있다. 따라서 CPU의 모드 비트를 통해 접근 권한을 시스템 콜로 격리한다.

시스템 콜이 호출되면 인터럽트가 발생하고, CPU는 현재 상태를 저장한 뒤 커널 모드로 전환한다. 커널은 요청한 작업을 수행한 뒤 다시 사용자 모드로 돌아온다.

이 과정에서 컨텍스트 스위칭 비용이 발생한다. 잦은 시스템 콜 호출은 성능 저하의 원인이며, 이를 줄이기 위해 vmsplice나 io_uring 같은 기술이 사용된다.

## CPU 스케줄러의 단계별 역할은 무엇인가?

프로세스의 상태 변화와 실행 우선순위에 따라 실행 주기와 대상자를 정하는 역할이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 장기 | 작업 큐에서 메모리로 올릴 프로세스 결정 |
| 중기 | 메모리 부족 시 일부를 디스크로 내보냄 |
| 단기 | 준비 큐에서 CPU를 할당할 프로세스 선택 |

## 소스 코드가 실행 파일로 변하는 과정은 무엇인가?

## 동기/비동기 및 블로킹/논블로킹의 차이는 무엇인가?

동기와 비동기는 호출한 함수의 완료 여부를 누가 확인하느냐의 차이이고, 블로킹과 논블로킹은 호출된 함수가 제어권을 언제 돌려주느냐의 차이다.

| 기준 | 동기/비동기 | 블로킹/논블로킹 |
| --- | --- | --- |
| 핵심 관점 | 작업 완료 여부 및 순서 | 제어권의 반환 시점 |
| 주체 | 호출한 쪽에서 확인 | 호출된 쪽에서 반환 |

제어권을 바로로 돌려받는 논블로킹 방식은 호출한 쪽에서 계속해서 작업 완료 여부를 확인해야 한다. 이를 폴링(Polling)이라고 하며, 비동기 방식의 구현체로 많이 쓰인다.

## 인터럽트와 폴링의 결정적인 차이는 무엇인가?

이벤트 발생 시 CPU가 직접 확인하는지 아니면 장치가 CPU를 깨우는지의 차이다.

1. **장치 → CPU** — 인터럽트 요청(IRQ). 신호를 보낸다
2. **CPU → 장치** — 인터럽트 서비스 루틴(ISR) 실행. 요청을 처리한다

폴링은 CPU가 루프를 돌며 상태를 계속 확인하는 방식이다. 장치가 준비될 때까지 CPU가 대기하므로 자원 낭비가 심하다.

반면 인터럽트는 하드웨어 신호로 CPU의 실행 흐름을 제어한다. CPU는 다른 작업을 수행하다가 신호가 오면 처리 루틴으로 점프한다.

이 흐름은 현대 운영체제의 멀티태스킹을 가능하게 하는 핵심 기제다. 하드웨어 인터럽트와 소프트웨어 인터럽트(트랩)를 구분하여 처리하는 지점이 면접의 핵심이다.

## 컨텍스트 스위칭 시 CPU는 무엇을 저장하고 복원하는가?

## 메모리 연속할당 방식 중 무엇을 선택하는가?

프로세스의 크기와 가용 메모리 조각의 분포를 고려해 결정한다. 충돌이 적고 빠른 할당이 필요하면 First-fit, 메모리 낭비를 최소화하려면 Best-fit를 쓴다.

| 기준 | First-fit | Best-fit | Worst-fit |
| --- | --- | --- | --- |
| 선택 방식 | 가장 먼저 발견한 조각 | 크기가 가장 딱 맞는 조각 | 가장 큰 조각 |

| 단점 | 앞부분에 작은 조각 누적 | 탐색 시간이 길고 파편화 심함 | 메모리 낭비가 가장 큼 |

First-fit는 리스트의 처음부터 탐색하므로 오버헤드가 적다. 실무적으로 가장 효율적인 선택지로 꼽힌다.

Best-fit는 모든 조각을 확인해야 하므로 느리다. 아주 작은 크기의 조각들이 많이 생겨 오히려 사용할 수 없는 외부 단편화가 심해진다.

Worst-fit는 가장 큰 조각을 할당해 남은 공간을 유의미하게 활용하려 한다. 하지만 큰 프로세스가 들어올 자리를 미리 없애는 치명적인 단점이 있다.

## TLB 미스가 발생했을 때 처리 과정은 무엇인가?

가상 주소를 물리 주소로 변환하는 과정에서 TLB에 정보가 없으면 페이지 테이블로 이동한다. 이후 메모리에서 페이지 테이블 엔트리를 찾아 주소 변환을 완료한다.

1. **가상 주소 → TLB** — 주소 변환 요청
2. **TLB → 메모리** — TLB 미스 발생, 페이지 테이블 참조
3. **메모리 → CPU** — 물리 주소 반환

TLB는 주소 변환 속도를 높이기 위한 캐시이다. 페이지 테이블은 메인 메모리에 저장되어 있어 접근 속도가가 느리다. 따라서 TLB에 정보가 없으면 메모리에 두 번 접근해야 하므로 성능이 저하된다.

컨텍스트 스위칭이 발생하면 이전 프로세스의 TLB 정보는 더 이상 유효하지 않는다. 이때 TLB를 모두 비우는 플러시로 성능을 저하 시킨다. ASID를 사용하여 프로세스별로 정보를 구분하여 플러시를 줄이는 방식이 대안이다.

## 프로세스 스케줄링 방식은 무엇으로 결정하는가?

CPU 효율과 응답 시간 사이의 트레이드오프를 고려해 결정한다. 처리량은 높이되 지연 시간은 줄이는 것이 핵심이다.

| 기준 | 비선점형 | 선점형 |
| --- | --- | --- |

선점형인 라운드 로빈은 정해진 시간 단위로 CPU를 전환한다. 모든 프로세스에 공평한 기회를 주어 응답성을 높이지만, 시간이 너무 짧으면 문맥 교환 비용이 커진다.

## 멀티스레드 환경에서 스레드 세이프한 코드를 작성하는 방법은 무엇인가?

임계 영역으로의 동시 접근을 막아 데이터 일관성을 보장하는 것이다. 한 번에 하나의 스레드만 자원에 접근하도록 제어하는 것이 핵심이다.

| 제어 방법 | 설명 |
| --- | --- |
| 동기화 | synchronized, Lock API를 이용한 상호 배제 |

위의 방법들로 공유 자원에 대한 경쟁 상태를 방지한다. 특히 데이터 읽기/쓰기 과정에서 문맥 전환이 발생하면 데이터가 오기집단될 수 있다.

## 동기화 문제를 하드웨어적으로 어떻게 해결하는가?

원자적 명령어로 처리한다. CPU가 명령어를 실행하는 동안 다른 프로세스가 개입하지 못하게 막아 메모리 접근을 보장하는 방식이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 하드웨어 수준 | **Test-and-Set**, **Compare-and-Swap (CAS)** |
| 명령어 수준 | 인터럽트 비활성화. 단일 코어에서만 유효하다 |

Test-and-Set은 메모리 값의 현재 상태를 읽고 새로운 값을 쓰는 작업을 한 번에 처리한다. 중간에 컨텍스트 스위칭이 발생하지 않아 데이터 정합성을 지킨다.

CAS는 기대하는 값과 현재 메모리 값의 일치 여부를를 확인하고 다를 경우에만 값을 바꾼다. 락-프리(Lock-free) 알고리즘의 핵심 기반이 된다.

인터럽트 비활성화는 간단하지만 멀티코어 환경에서는 모든 CPU의 인터럽트를 동시에 끄는 비용이 너무 커서 실무적으로 쓰이지 않는다.

## 프로세스와 스레드의 핵심 차이는 무엇인가?

자원 할당과 공유 범위의 차이다. 프로세스는 운영체제로부터 독립적인 메모리 공간을 할당받지만, 스레드는 프로세스 내의 메모리를 공유한다.

| 기준 | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 독립적 할당 | 스택 제외 공유 |
| 컨텍스트 스위칭 | 무겁다 | 가볍다 |
| 영향도 | 독립적 실행 | 장애 전파 가능 |

프로세스는 코드, 데이터, 힙 영역을 각자 가진다. 그래서 한 프로세스가 죽어도 다른 프로세스에 직접적인 영향을 주지 않는다.

스레드는 힙과 정적 데이터를 공유하고 개별 스택만 가진다. 데이터 공유가 빠르지만, 한 스레드의 메모리 오염이 전체 프로세스를 종료시킬 수 있다.

컨텍스트 스위칭 비용도 다르다. 프로세스는 캐시 메모리를 완전히 비워야 하지만, 스레드는 공유 영역이 많아 전환 속도가 빠르다.
