## @Transactional이 걸리지 않는 경우는?

프록시를 거치지 않고 메서드에 들어갔을 때다. 스프링의 트랜잭션은 코드가 아니라 프록시가 여는 것이라, 프록시를 통과하지 않으면 애초에 열릴 기회가 없다.

가장 흔한 자리가 자기 호출이다. 같은 클래스 안에서 `this.method()`로 부르면 그 호출은 프록시를 지나지 않고 실제 객체로 곧장 들어간다. 애너테이션은 붙어 있는데 아무 일도 일어나지 않는다. 로그도 예외도 없어서 원인을 찾기 어렵다.

1. **다른 빈 → 프록시** — 빈 참조로 부른다. **여기서 트랜잭션이 열린다**
2. **프록시 → 실제 객체** — 메서드 실행
3. **실제 객체 → 실제 객체** — this.method(). 프록시를 건너뛴다 — 안 걸린다

private 메서드도 같은 이유로 안 걸린다. CGLIB 프록시는 상속으로 만들어지는데 private은 재정의할 수 없다. final 메서드와 final 클래스도 마찬가지다.

걸렸는데 안 되돌아가는 경우도 있다. 기본 롤백 대상은 unchecked 예외라, 체크 예외를 던지면 트랜잭션은 그대로 커밋된다. 되돌리려면 rollbackFor를 명시해야 한다.

면접에서는 왜 자기 호출이 안 되는지를 프록시 구조로 설명할 수 있는지를 본다. 우회책을 아는 것보다 구조를 아는 쪽이 중요하다. 우회책은 대개 그 메서드를 다른 빈으로 꺼내는 것이고, 꺼내야 한다는 판단 자체가 구조 이해에서 나온다.

## JPA에서 N+1 쿼리는 왜 생기고 무엇으로 막는가?

연관을 지연 로딩으로 두고 목록을 순회할 때 생긴다. 목록을 가져오는 질의 하나에 더해, 원소마다 연관을 채우는 질의가 한 번씩 더 나간다.

1. **앱 → DB** — 주문 목록 조회. 질의 1번
2. **앱 → DB** — 1번 주문의 회원 조회
3. **앱 → DB** — 2번 주문의 회원 조회. **원소 수만큼 반복된다**

즉시 로딩으로 바꾸는 것은 답이 아니다. 그러면 연관이 필요 없는 조회에서도 매번 조인이 붙는다. N+1이 사라지는 대신 모든 질의가 무거워진다. 문제를 옮긴 것이지 푼 것이 아니다.

해결은 필요한 자리에서만 한 번에 가져오는 것이다. fetch join이나 @EntityGraph로 그 조회에 한해 함께 읽는다. 어디를 함께 읽을지는 화면이 결정하므로, 매핑이 아니라 질의 쪽에 두는 것이 맞다.

fetch join에도 함정이 있다. 컬렉션을 조인하면 행이 곱해져 부모가 중복되고, 그 상태로는 페이징을 데이터베이스에 맡길 수 없다. 하이버네이트는 이때 전부 읽어 메모리에서 자르며 경고를 남긴다. 목록이 크면 그대로 사고다.

그래서 페이징이 함께 필요한 화면에서는 batch size를 쓴다. 연관을 원소마다 한 번씩이 아니라 IN 절로 묶어 몇 번에 나눠 읽는다. 질의 수가 N에서 N/배치로 줄고 페이징은 데이터베이스가 그대로 맡는다.

## 스프링 빈이 싱글톤인 것이 언제 문제가 되는가?

빈이 상태를 들고 있을 때다. 인스턴스가 하나뿐이라 모든 요청이 같은 필드를 공유한다. 한 요청이 써 넣은 값을 다른 요청이 읽는다.

| 두는 자리 | 공유 범위 | 안전한가 |
| --- | --- | --- |
| 빈의 필드 | 애플리케이션 전체 | 아니다. 요청끼리 섞인다 |
| 메서드 지역 변수 | 호출 하나 | 안전하다 |
| ThreadLocal | 스레드 하나 | 반납을 빠뜨리면 샌다 |

가장 흔한 사고는 빈에 사용자 정보를 담아두는 것이다. 테스트에서는 요청이 하나씩 들어와 안 드러나고, 동시 접속이 생기는 순간 남의 데이터가 보인다.

해법은 상태를 빈 밖으로 빼는 것이다. 필요한 값은 인자로 넘기고, 빈은 동작만 들고 있게 한다. 스코프를 요청 단위로 바꾸는 방법도 있지만 대개 마지막 수단이다.

면접에서는 왜 기본이 싱글톤인지로 들어온다. 대부분의 빈이 상태 없는 서비스라 하나면 충분하다. 요청마다 만들면 생성 비용과 GC 부담이 그대로 늘어난다.

## 생성자 주입이 기본 선택인 이유는?

필수 의존성을 객체 생성 시점에 보장하고 불변으로 만들 수 있기 때문이다. 테스트에서 직접 주입하기 쉽다. 순환 참조도 시작 단계에서 드러난다.

| 기준 | 생성자 주입 | 필드 주입 |
| --- | --- | --- |
| 필수성 | 생성 시 확인 | 실행 뒤 발견 |
| 불변성 | final 가능 | final 불가 |
| 테스트 | 직접 전달 | 컨테이너 필요 |

선택 의존성은 세터나 ObjectProvider로 표현할 수 있다. 필수 값과 선택 값을 주입 방식에서 구분하면 객체의 계약이 선명해진다.

생성자가 하나면 @Autowired를 생략할 수 있다. 매개변수가 지나치게 많다면 주입 문법보다 클래스가 너무 많은 책임을 가진 것은 아닌지 먼저 본다.

## 빈 초기화 로직은 어느 시점에 실행해야 하는가?

의존성 주입이 끝난 뒤 초기화 콜백에서 실행해야 한다. 생성자에서는 모든 주입과 컨테이너 후처리가 끝났다고 보장할 수 없다.

1. **컨테이너 → 빈** — 인스턴스를 만들고 의존성을 주입한다
2. **빈 후처리기 → 빈** — 초기화 전 처리를 한다
3. **컨테이너 → 빈** — @PostConstruct 등 콜백을 호출한다
4. **빈 후처리기 → 빈** — 프록시 등 초기화 후 처리를 한다

초기화 콜백은 @PostConstruct, InitializingBean, initMethod 순서로 호출된다. 애플리케이션 로직은 스프링 인터페이스보다 애너테이션이나 설정 콜백에 두는 편이 덜 결합된다.

종료 때는 @PreDestroy 같은 소멸 콜백이 실행된다. 다만 prototype 빈은 생성 뒤 컨테이너가 추적하지 않으므로 호출자가 정리해야 한다.

## 내부 메서드 호출에 부가기능이 빠지는 이유는?

같은 객체 안에서 this로 호출하면 프록시를 거치지 않기 때문이다. 프록시가 가로채야 트랜잭션이나 로깅 같은 어드바이스가 실행된다.

1. **클라이언트 → 프록시** — 공개 메서드를 호출한다
2. **프록시 → 어드바이스** — 트랜잭션 등을 적용한다
3. **어드바이스 → 대상 객체** — 실제 메서드를 호출한다
4. **대상 객체 → 대상 객체** — 내부 호출은 프록시를 우회한다

JDK 동적 프록시는 인터페이스를 기반으로 한다. 클래스 기반 프록시는 상속을 쓰므로 final 클래스와 final 메서드를 가로챌 수 없다.

적용 경계를 별도 빈으로 분리해 외부 호출로 만드는 방법이 명확하다. 프록시 노출이나 자기 자신 주입은 결합도를 높이므로 우선 선택이 아니다.

## 자동 구성은 어떤 조건에서 물러나는가?

필요한 클래스가 없거나 프로퍼티 조건이 맞지 않으면 적용되지 않는다. 사용자가 같은 역할의 빈을 선언해도 기본 구성이 물러난다.

1. **앱 → 후보** — 클래스와 설정값을 검사한다
2. **후보 → 조건 평가** — 사용자 빈 유무도 확인한다
3. **조건 평가 → 빈 팩토리** — 통과한 기본 빈만 등록한다

SpringBootApplication이 EnableAutoConfiguration을 켠다. 부트는 AutoConfiguration.imports 같은 메타데이터에서 후보를 찾는다.

ConditionalOnMissingBean은 사용자 정의를 존중하는 핵심 장치다. 너무 넓은 타입의 빈을 선언하면 예상치 못한 기본 구성까지 꺼질 수 있다.

구성이 빠졌다면 조건 평가 보고서에서 일치와 불일치 이유를 확인한다. 제외 설정은 의도와 영향 범위를 알 때만 사용한다.

## 요청 공통 처리는 어느 지점에 두는가?

원시 요청과 응답 전체에 적용할 일은 필터에 둔다. 선택된 컨트롤러 정보가 필요한 일은 인터셉터에 둔다. 비즈니스 규칙은 서비스에 둔다.

| 기준 | 필터 | 인터셉터 |
| --- | --- | --- |
| 경계 | 서블릿 체인 | MVC 내부 |
| 문맥 | 요청·응답 | 핸들러·모델 |
| 용도 | 보안·인코딩 | 로깅·검사 |

필터는 DispatcherServlet 전후를 감싸 정적 자원과 오류 디스패치에도 관여할 수 있다. 인터셉터는 preHandle부터 afterCompletion까지 실행된다.

필터에서 난 예외는 보통 ControllerAdvice 범위 밖이다. 필터 체인에서 응답으로 바꾸거나 서블릿 오류 처리로 넘겨야 한다.

실행 횟수와 순서도 설계 대상이다. 비동기·오류 디스패치에서는 필터가 다시 불릴 수 있어 OncePerRequestFilter 정책을 확인해야 한다.

## 예외를 어디서 HTTP 응답으로 바꾸는가?

컨트롤러 경계의 전역 예외 처리기에서 바꾼다. 도메인 예외를 안정된 오류 코드와 HTTP 상태로 매핑하고 예상 밖 예외는 500으로 감춘다.

1. **서비스 → 처리기** — 의미 있는 예외를 전달한다
2. **처리기 → 오류 계약** — 상태와 코드를 매핑한다
3. **오류 계약 → 클라이언트** — 일관된 응답을 반환한다

예상 가능한 실패는 의미가 드러나는 예외로 표현한다. 저장소 예외나 구현 메시지를 그대로 노출하면 API가 내부 기술에 묶인다.

처리기는 구체적인 예외부터 매핑한다. 필터에서 발생한 예외는 컨트롤러 처리기에 도달하지 않으므로 별도 경계가 필요하다.

로그는 한 경계에서 한 번 남긴다. 응답에는 추적 ID와 안정된 코드를 싣고 스택 트레이스와 민감한 메시지는 숨긴다.

## 인증 정보는 어떻게 보안 문맥에 들어가는가?

인증 필터가 요청에서 자격 증명을 꺼내 미인증 토큰을 만든다. AuthenticationManager가 검증을 위임하고 성공 결과를 SecurityContext에 넣는다.

1. **필터 → Manager** — 미인증 토큰
2. **Manager → Provider** — 검증 위임
3. **Provider → Manager** — 인증된 주체·권한
4. **Manager → 필터** — 인증 결과
5. **필터 → 보안 문맥** — 결과 저장

AuthenticationProvider는 토큰 종류를 지원하는지 판단한다. 사용자 조회와 비밀번호 해시 비교를 거쳐 주체와 권한을 담은 결과를 만든다.

이후 인가 필터가 보안 문맥의 권한으로 접근을 판정한다. 인증이 없으면 401이다. 인증은 됐지만 권한이 부족하면 403이다.

세션 방식은 보안 문맥을 요청 사이에 복원한다. 무상태 토큰 방식은 매 요청 토큰을 검증한다. 저장 정책과 필터 위치가 흐름을 바꾼다.

## 같은 엔티티를 두 번 조회하면 왜 같은 객체인가?

한 영속성 컨텍스트는 엔티티 타입과 식별자별로 인스턴스를 하나만 관리한다. 이미 관리 중이면 1차 캐시에서 같은 객체를 반환한다.

1. **코드 → 컨텍스트** — 타입과 ID로 찾는다
2. **컨텍스트 → 1차 캐시** — 관리 객체를 확인한다
3. **1차 캐시 → 코드** — 있으면 같은 객체를 준다
4. **컨텍스트 → DB** — 없으면 조회해 관리한다

JPQL은 조회 쿼리를 실행할 수 있다. 그래도 같은 식별자가 이미 관리 중이면 결과를 기존 인스턴스에 맞춰 객체 동일성을 지킨다.

이 캐시는 EntityManager 범위 안에서만 유효하다. 여러 요청이 공유하는 2차 캐시가 아니며 트랜잭션 격리도 대신하지 않는다.

clear나 detach 뒤에는 관리가 끊긴다. 긴 범위에 많은 엔티티를 쌓으면 메모리와 낡은 상태 문제가 커지므로 필요한 작업에서는 주기적으로 비워야 한다.

## 수정 메서드 없이 UPDATE가 나가는 이유는?

영속성 컨텍스트가 관리 엔티티의 최초 상태와 현재 상태를 flush 때 비교하기 때문이다. 달라진 속성이 있으면 UPDATE SQL을 만든다.

1. **조회 → 컨텍스트** — 엔티티와 최초 상태를 둔다
2. **코드 → 엔티티** — 필드를 바꾼다
3. **커밋 → flush** — 최초 상태와 비교한다
4. **flush → DB** — 차이가 있으면 UPDATE한다

flush는 커밋 직전이나 쿼리 실행 전에 일어날 수 있다. SQL이 보였다는 사실과 커밋됐다는 사실은 다르며 롤백하면 변경은 사라진다.

관리 상태인 엔티티만 대상이다. detach나 clear 뒤의 객체는 바꿔도 감지되지 않는다. merge는 전달 객체가 아니라 반환된 관리 객체를 갱신한다.

벌크 UPDATE는 영속성 컨텍스트를 건너뛴다. 이미 관리 중인 객체가 낡을 수 있어 flush 후 clear하거나 다시 조회하는 전략이 필요하다.

## 외부 롤백과 무관한 기록은 어떻게 남기는가?

감사 기록을 별도 빈의 REQUIRES_NEW 메서드로 호출한다. 기존 트랜잭션을 보류하고 새 트랜잭션에서 커밋해야 외부 롤백과 분리된다.

1. **외부 작업 → 기존 트랜잭션** — 변경 수행
2. **기존 트랜잭션 → 프록시 빈** — 감사 기록 호출
3. **프록시 빈 → 새 트랜잭션** — 기존 작업 보류
4. **새 트랜잭션 → DB** — 기록 독립 커밋

REQUIRED는 기존 트랜잭션에 합류한다. 내부 예외를 잡아도 이미 rollback-only가 됐다면 마지막 커밋에서 예상치 못한 롤백이 발생한다.

REQUIRES_NEW는 외부 연결을 잡아 둔 채 새 연결을 요구할 수 있다. 동시 요청 수에 비해 풀이 작으면 연결 고갈이나 교착 위험이 커진다.

NESTED는 같은 물리 트랜잭션의 savepoint로 부분 롤백한다. 외부 트랜잭션이 롤백하면 내부 변경도 사라지므로 독립 커밋과 다르다.

같은 객체 안의 self-invocation은 보통 프록시를 지나지 않는다. 전파 설정이 적용되도록 별도 빈 경계를 만들거나 호출 구조를 바꿔야 한다.

## JVM GC의 효율을 높이는 튜닝 포인트는 무엇인가?

힙 메모리 영역의 크기와 GC 알고리즘 선택이다. 세밀한 튜닝을 통해 Stop-the-world 시간을 줄이는 것이 핵심이다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| Young Generation | Eden, Survivor. 짧은 생존 객체 관리 |
| Old Generation | 장기 생존 객체 관리. Major GC 발생 |

객체 생존 기간에 따라 영역을 나누어 관리한다. Young 영역에서 살아남은 객체가 Old 영역으로 이동하며, Old 영역이 꽉 차면 전체 힙을 검사하는 Full GC가 발생한다.

Stop-the-world는 모든 애플리케이션 스레드가 멈추는 현상이다. GC 알고리즘에 따라 멈춤 시간이 달라지므로, 서비스 특성에 맞춰 G1 GC나 ZGC를 선택한다.

힙 크기를 너무 크게 잡으면 Full GC의 처리 시간이 길어진다. 반대로 너무 작으면 GC가 빈번하게 발생하여 CPU 사용률이 올라간다.

## 체크 예외와 언체크 예외의 선택 기준은 무엇인가?

서블릿 컨테이너로서 자바 코드를 실행해 동적인 응답을 생성한다. 정적인 파일은 웹 서버에 맡기고, 비즈니스 로직이 필요한 요청을 처리한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| 웹 서버 | Apache, Nginx. 정적 리소스 응답 |
| WAS | Tomcat, Jetty. 서블릿 실행 및 DB 연동 |

톰캣은 HTTP 요청을 받아 서블릿으로 전달하고 그 결과를 다시 응답한다. 이 과정에서 서블릿의 생명주기를 관리하고 멀티스레딩을 처리한다.

최근에는 톰캣 자체의 정적 파일 처리 성능이 좋아져 단독으로 쓰기도 한다. 하지만 보안과 로드밸런싱을 위해 앞단에 웹 서버를 두는 구조가 여전히 일반적이다.

## 스트림의 지연 연산은 왜 필요한가?

불필요한 계산을 최소화하여 성능을 최적화하기 때문이다. 모든 데이터를 처리하지 않고 필요한 시점에만 연산을 수행한다.

1. **데이터 소스 → 중간 연산**
2. **중간 연산 → 터미널 연산** — 최종 결과가 필요할 때 모든 과정이 시작된다

중간 연산은 결과값을 즉시 계산하지 않고, 파이프라인을 구성하는 일종의 설계도만 만든다. 필터링이나 매핑 같은 작업이 누적된다.

터미널 연산이 호출되어야만 데이터가 흐르기 시작한다. 이때 스트림은 최적화 엔진을 통해 루프를 한 번만 돌며 모든 연산을 처리한다.

만약 즉시 연산했다면 중간 단계마다 임시 컬렉션을 생성해야 한다. 이는 메모리 낭비와 CPU 오버헤드로 이어진다.

## ORM을 사용하는 이유는 무엇인가?

객체지향적 설계와 관계형 데이터베이스 간의 패러다임 불일치를 해결하기 때문이다. 이를 통해 개발자는 SQL로 인한 반복적인 CRUD 작업을 줄이고 비즈니스 로직에 집중할 수 있다.

| 기준 | SQL 매퍼 | ORM |
| --- | --- | --- |
| 중심 관점 | 테이블/SQL | 객체/엔티티 |
| 생산성 | 쿼리 직접 작성 | 메서드 호출로 처리 |
| 유지보수 | 스키마 변경 시 수정 많음 | 엔티티 수정으로 반영 |

위 표는 SQL 매퍼와 ORM의 결정적인 차이를 보여준다. ORM은 데이터베이스의 행을 객체로 매핑하여 자바 객체로서의 상속이나 참조로 데이터를 처리한다.

하지만 ORM은 학습 곡선이 높고, 복잡한 쿼리 작성 시 성능 최적화가 어려울 수 있다. 특히 N+1 문제는 발생 빈도가가 높으며, 이를 해결하기 위해 페치 조인이나 @EntityGraph 등을 적절히 사용해야 한다.

## 단위 시험과 통합 시험은 무엇으로 가르는가?

무엇을 함께 확인하는지로 가른다. 단위 시험은 작은 동작 하나를 따로 보고 통합 시험은 여러 조각이 맞물리는 자리를 본다.

| 기준 | 단위 | 통합 |
| --- | --- | --- |
| 보는 범위 | 동작 하나 | 조각들이 만나는 곳 |
| 둘레 | 자주 가짜로 바꾼다 | 대개 실제 것을 쓴다 |
| 대개의 속도 | 빠르다 | 느리다 |

가짜로 바꾸는 것은 경향이지 정의가 아니다. 단위 시험이 실제 협력 객체를 써도 되고, 통합 시험이 바깥 시스템만 가짜로 둬도 된다.

비율보다 중요한 것은 **되돌렸을 때 빨간불이 뜨는가**다. 고친 자리를 원래대로 돌려도 통과하면 그 시험은 적어도 이 회귀를 못 잡는다.
