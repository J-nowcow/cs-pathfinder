## TCP 연결을 끊을 때 TIME_WAIT 상태가 필요한 이유는?

마지막 ACK가 유실될 수 있기 때문이다. 먼저 닫는 쪽이 잠시 남아 있어야 상대의 재전송을 받아줄 수 있다.

1. **능동 종료 → 수동 종료** — FIN. 보낼 것은 다 보냈다
2. **수동 종료 → 능동 종료** — ACK. 알겠다
3. **수동 종료 → 능동 종료** — FIN. 나도 다 보냈다
4. **능동 종료 → 수동 종료** — 마지막 ACK. **이게 유실되면 상대는 FIN을 다시 보낸다**

4-way handshake의 마지막에서 능동 종료 측은 상대의 FIN에 ACK를 보낸다. 이 ACK가 유실되면 상대는 FIN을 재전송한다. 이때 소켓이 이미 사라졌다면 응답할 주체가 없어 상대는 연결을 정상 종료하지 못한다.

두 번째 이유는 이전 연결의 지연 패킷이다. 같은 포트 조합으로 새 연결이 곧바로 열리면 뒤늦게 도착한 옛 패킷이 새 연결의 데이터로 섞일 수 있다. TIME_WAIT은 그 시간을 벌어준다.

대기 시간은 통상 2MSL이다. 문제는 트래픽이 많은 서버에서 TIME_WAIT 소켓이 쌓여 포트가 고갈되는 것이다. 다만 이는 대개 능동 종료를 서버가 하고 있다는 신호다.

면접에서는 해결책을 물어온다. `SO_REUSEADDR`나 커널 파라미터를 만지기 전에 keep-alive로 연결을 재사용하는 쪽이 먼저다. 원인이 연결을 너무 자주 맺고 끊는 데 있기 때문이다.

## HTTP/2는 HTTP/1.1의 무엇을 고쳤는가?

한 연결에서 요청 하나가 끝나야 다음이 나가던 제약을 없앴다. 앞의 응답이 늦으면 뒤가 통째로 밀리던 문제가 여기서 온다. HTTP/2는 요청과 응답을 프레임으로 쪼개고 스트림 번호를 붙여 한 연결에 섞어 보낸다.

| 기준 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 한 연결의 요청 | 순서대로 하나씩 | 여러 개가 섞여서 |
| 헤더 | 매번 통째로 | 표로 눌러서(HPACK) |
| 브라우저 우회책 | 도메인 쪼개기, 스프라이트 | 필요 없어진다 |

도착한 순서대로 다시 조립되므로 순서 제약이 사라진다. 연결 하나로 충분해진다.

HTTP/1.1도 연결을 재사용하기는 했다. 다만 응답이 보낸 순서대로 와야 해서 앞의 것이 느리면 뒤에 줄 선 요청이 전부 기다렸다. 그래서 브라우저는 도메인당 연결을 예닐곱 개씩 열었고, 이미지를 하나로 합치는 기법이 유행했다.

다만 TCP 계층의 줄서기는 남는다. 패킷 하나가 유실되면 그 연결의 모든 스트림이 재전송을 기다린다. HTTP/3가 전송을 QUIC으로 바꾼 이유가 이것이다.

면접에서는 우회책이 왜 역효과가 되는지로 들어온다. 도메인을 쪼개면 연결이 늘어 HTTP/2의 이점이 사라진다. 스프라이트는 한 조각만 바뀌어도 전체를 다시 받게 만든다.

## DNS 조회는 어떤 순서로 도는가?

가까운 캐시부터 확인하고 없으면 위로 올라간다. 브라우저·운영체제·리졸버 순으로 묻고, 아무도 모를 때만 루트에서 시작해 단계마다 다음 서버를 안내받는다.

1. **브라우저 → 리졸버** — 캐시에 없다. 대신 물어봐 달라
2. **리졸버 → 루트** — .com은 누가 아는가
3. **루트 → 리졸버** — com 네임서버 주소다
4. **com → 리졸버** — example.com 네임서버 주소다
5. **리졸버 → 브라우저** — 최종 IP다. TTL만큼 캐시해라

한 번에 답을 주는 것이 아니라 다음에 물을 곳을 알려준다. 루트가 모든 도메인을 알 필요가 없어서 이 구조가 버틴다.

TTL이 실무의 급소다. 값을 바꿔도 캐시가 만료되기 전까지는 옛 주소로 간다. 그래서 이전을 앞두고는 TTL을 미리 낮춰두고, 옮긴 뒤에 되돌린다.

면접에서는 왜 UDP를 쓰는지로 들어온다. 질의 하나에 응답 하나라 연결을 맺는 값이 아깝고, 응답이 커지면 TCP로 다시 묻는 경로가 따로 있다.

## 수신자는 여유 있는데 전송이 느린 이유는?

수신 창이 넉넉해도 네트워크가 혼잡하면 송신자는 혼잡 창을 줄인다. 실제 전송량은 두 창 중 작은 값으로 제한된다.

| 기준 | 흐름 제어 | 혼잡 제어 |
| --- | --- | --- |
| 보호 대상 | 수신자 버퍼 | 네트워크 |
| 제한 값 | `rwnd` | `cwnd` |

수신자는 ACK의 `rwnd`로 남은 버퍼를 알린다. 송신자는 이를 넘겨 보내지 않아 느린 수신자의 버퍼가 넘치는 일을 막는다.

송신자는 알고리즘에 따라 손실, ECN, 지연·전달률 같은 신호로 `cwnd`를 조절한다. 손실 뒤 속도가 크게 떨어지고 서서히 회복되는 이유다.

처리량 문제를 볼 때는 두 창과 왕복 시간, 패킷 손실을 함께 본다. 수신 버퍼만 늘려서는 혼잡 구간이 빨라지지 않는다.

## 연결 설정 왕복을 언제 줄일 수 있는가?

새 TCP 연결의 상태 동기화는 생략할 수 없다. 대신 연결을 재사용하거나 재접속 정보를 활용해 애플리케이션 데이터 전송을 앞당길 수 있다.

1. **클라이언트 → 서버** — SYN. 시작 순번을 알린다
2. **서버 → 클라이언트** — SYN + ACK. 수락하고 순번을 알린다
3. **클라이언트 → 서버** — ACK. 양쪽 상태가 맞았음을 확인한다

세 단계는 양쪽의 송수신 가능 여부와 초기 순번을 확인한다. 한 단계를 없애면 지연 패킷을 새 연결로 오인하거나 반쪽 연결이 늘 수 있다.

Keep-Alive와 연결 풀은 이미 맺은 연결을 다시 쓴다. 새 핸드셰이크 자체를 줄이므로 가장 일반적인 지연 절감 수단이다.

TCP Fast Open은 쿠키가 있는 재접속에서 SYN에 데이터를 실을 수 있다. 핸드셰이크는 계속 진행되며 중간 장비 호환성과 재전송 안전성을 고려해야 한다.

## 신뢰성보다 지연을 우선할 기준은?

일부 손실을 허용하고 최신 데이터가 더 중요할 때 UDP가 맞다. 순서와 재전송을 애플리케이션이 직접 설계할 수 있어야 한다.

| 기준 | TCP | UDP |
| --- | --- | --- |
| 전달 | 순서와 재전송 보장 | 보장 없음 |
| 지연 | 손실 시 대기 | 손실을 건너뛸 수 있음 |
| 상태 | 연결 유지 | 연결 상태 없음 |

음성 통화와 게임은 늦게 도착한 과거 패킷의 가치가 낮다. 재전송을 기다리기보다 손실을 보간하고 다음 데이터를 처리하는 편이 낫다.

DNS처럼 요청과 응답이 작고 짧은 경우도 연결 비용을 피할 수 있다. 다만 크기가 커지면 분할과 재시도 전략이 필요하다.

UDP가 곧 빠름을 뜻하지는 않는다. 혼잡 제어와 인증, 순서 보장이 필요하면 직접 구현하거나 QUIC 같은 검증된 프로토콜을 써야 한다.

## 재검증 없이 응답을 써도 되는 기준은?

저장된 응답이 `max-age` 안에 있으면 재검증 없이 쓸 수 있다. 기간이 지났다면 검증자로 서버에 변경 여부를 물어야 한다.

| 지시자 | 저장 | 재사용 조건 |
| --- | --- | --- |
| `max-age` | 가능 | 신선한 동안 즉시 사용 |
| `no-cache` | 가능 | 매번 재검증 |
| `no-store` | 금지 | 재사용 불가 |

`no-cache`는 저장 금지가 아니다. 캐시에 보관해도 되지만 사용할 때마다 `ETag`나 `Last-Modified`로 확인하라는 뜻이다.

변경이 없으면 서버는 본문 없이 `304 Not Modified`를 보낸다. 전송량은 줄지만 네트워크 왕복은 남는다.

해시가 포함된 정적 파일명에는 긴 `max-age`와 `immutable`이 잘 맞는다. 개인화 응답은 `private`과 `Vary`를 함께 검토해야 한다.

## 실패 응답 코드는 무엇을 기준으로 고르는가?

요청이나 인증·권한·사용량 제한 같은 클라이언트 측 조건 때문에 처리할 수 없으면 4xx를 쓴다. 서버가 정상 요청을 처리하지 못하면 5xx를 쓴다. 원인과 재시도 가능성을 코드에 담아야 한다.

| 기준 | 4xx | 5xx |
| --- | --- | --- |
| 책임 | 요청 또는 권한 | 서버 처리 |
| 예 | 400, 404, 409 | 500, 503, 504 |

400은 요청 형식이 잘못된 경우다. 401은 인증이 필요하고 403은 신원을 알아도 권한이 없다. 존재를 숨기려면 404를 택할 수도 있다.

409는 현재 자원 상태와 충돌할 때 적합하다. 문법은 맞지만 필드 검증에 실패한 요청은 API 규약에 따라 400 또는 422로 일관되게 처리한다.

503은 일시적 과부하나 점검을 알린다. `Retry-After`를 주면 재시도 시점을 안내할 수 있다. 내부 오류를 모두 200으로 감싸면 중간 장비가 실패를 오해한다.

## 자물쇠 표시는 무엇을 검증한 결과인가?

브라우저가 신뢰 사슬과 도메인, 유효 기간을 확인하고 서버가 개인 키를 가졌음을 검증한 결과다. 사이트의 신뢰성이나 안전한 운영까지 보장하지는 않는다.

1. **서버 → 브라우저** — 서버 인증서와 중간 인증서를 보낸다
2. **브라우저 → 신뢰 저장소** — 루트까지 서명 사슬을 확인한다
3. **브라우저 → 서버** — 도메인과 키 소유 증명을 확인한다

루트를 제외한 각 인증서의 서명은 상위 인증서 공개 키로 확인한다. 루트 인증서는 운영체제나 브라우저의 신뢰 저장소에 미리 들어 있다.

브라우저는 접속 호스트가 SAN의 이름과 맞는지 확인한다. 발급 대상이 다른 유효한 인증서를 가져와도 이 단계에서 막힌다.

폐기 상태 확인은 OCSP나 CRL, OCSP Stapling을 활용한다. 구현과 정책에 따라 조회 실패를 엄격히 막지 않을 수 있어 자물쇠를 절대적 보증으로 보면 안 된다.

## 첫 보안 연결에는 왜 왕복이 필요한가?

암호 규칙을 합의하고 서버를 인증하며 공유 비밀에서 통신 키를 만들어야 하기 때문이다. 이 준비가 끝나야 애플리케이션 데이터를 안전하게 보낼 수 있다.

1. **클라이언트 → 서버** — 버전, 암호군, 키 공유를 제안한다
2. **서버 → 클라이언트** — 선택값, 인증서, 키 공유, 서명, Finished를 보낸다
3. **클라이언트 → 서버** — 인증과 Finished를 검증하고 Finished를 보낸다

TLS 1.3은 키 교환에 필요한 값을 첫 메시지부터 보내 일반적인 새 연결을 1-RTT로 줄였다. 이후 트래픽은 파생된 대칭 키로 암호화한다.

서버는 인증서의 공개 키에 대응하는 개인 키 소유를 증명한다. 브라우저는 인증서 사슬과 호스트 이름을 확인해 중간자 공격을 막는다.

세션 재개는 이전 비밀을 활용해 지연을 줄인다. 0-RTT 데이터는 재전송 공격에 노출될 수 있으므로 멱등한 요청에만 제한하는 편이 안전하다.

## 중계 서버의 주체는 어떻게 구분하는가?

클라이언트를 대신하면 포워드 프록시다. 서버를 대신하면 리버스 프록시다. 누구의 위치와 신원을 감추고 정책을 적용하는지가 구분 기준이다.

| 기준 | 포워드 프록시 | 리버스 프록시 |
| --- | --- | --- |
| 대리 대상 | 클라이언트 | 서버 |
| 설정 주체 | 사용자 또는 조직 | 서비스 운영자 |

## 리소스 API의 성숙도를 무엇으로 판단하는가?

리소스를 URI로 나누고 HTTP 메서드와 상태 코드를 의미에 맞게 쓰며 응답이 다음 행동 링크를 제공하는지로 판단한다. 단계가 높을수록 HTTP 의미를 더 활용한다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| Level 3 | 하이퍼미디어가 다음 행동을 안내한다 |
| Level 2 | HTTP 메서드와 상태 코드를 활용한다 |
| Level 1 | 리소스별 URI를 분리한다 |
| Level 0 | 하나의 URI로 원격 호출한다 |

Richardson 모델은 API가 HTTP를 얼마나 충실히 활용하는지 설명한다. Level 2만 되어도 자원과 행위, 오류 의미가 명확해져 일반적인 API에 실용적이다.

## HTTP 메서드 선택의 기준은 무엇인가?

리소스의 상태를 변경하는 성격과 멱등성 여부로 결정한다. 조회를 위해 GET을, 생성은 POST, 수정은 PUT이나 PATCH를, 삭제는 DELETE를 사용한다.

| 기준 | GET | POST | PUT | PATCH | DELETE |
| --- | --- | --- | --- | --- | --- |
| 목적 | 조회 | 생성 | 전체 수정 | 부분 수정 | 삭제 |
| 멱등성 | O | X | O | X | O |
| 안전성 | O | X | X | X | X |

안전한 메서드는 리소스를 변경하지 않는다. GET은 데이터를 읽기만 하므로 안전하다. 반면 POST는 서버 상태를 바꾼다.

멱등성이란 여러 번 호출해도 결과가 같은지 여부다. PUT은 동일한 데이터로 요청을 보내면 몇 번을 보내도 결과가 항상 같다.

PATCH는 리소스의 일부만 바꾸기 때문에 호출 순서나 현재 상태에 따라 결과가 달라질 수 있다. 그래서 멱등성이 보장되지 않는 경우가 많다.

## 웹소켓과 일반 소켓 통신은 무엇으로 구분하는가?

웹소켓은 HTTP 기반의 전이중 통신 프로토콜이며, 일반 소켓은 전송 계층의 TCP/UDP 연결 자체를 의미한다.

| 기준 | 웹소켓 | 일반 소켓 |
| --- | --- | --- |
| 계층 | 애플리케이션(L7) | 전송(L4) |
| 연결 방식 | HTTP 핸드셰이크 필요 | 직접 연결 |
| 특징 | 상태 유지(Stateful) | 로우 레벨 데이터 전송 |

웹소켓은 웹 브라우저 환경에서 실시간 통신을 하기 위해 설계되었다. HTTP의 요청-응답 모델을 유지하면서도 연결을 계속 열어두어 서버가 클라이언트로 데이터를 보낼 수 있게 한다.

일반 소켓은 운영체제가 제공하는 네트워크 인터페이스다. IP와 포트를 통해 바이트 스트림을 주고받는 가장 기초적인 도구이며, 웹소켓은 내부적으로 이 소켓을 활용해 구현된다.

따라서 웹소켓은 특정 규약(프로토콜)을 정의한 것이고, 소켓은 통신을 위한 하드웨어/소프트웨어적 통로 그 자체라고 볼 수 있다.

| 기준 | 쿠키 | 세션 |
| --- | --- | --- |
| 저장 위치 | 브라우저 | 서버 |
| 데이터 크기 | 작음 | 제한 없음 |
| 보안성 | 낮음 | 높음 |

쿠키는 네트워크 요청마다 서버로 자동 전송된다. 서버는 이를 읽어 사용자를 식별한다. 클라이언트가 데이터를 직접 수정할 수 있어 보안에 취약하다.

세션은 서버에 데이터를 저장하고 클라이언트에는 세션 ID만 전달한다. 실제 데이터는 서버가 관리하므로 조작이 어렵다. 하지만 서버 메모리를 사용하므로 사용자 수가 늘면 부하가 증가한다.

## 브라우저에 URL을 입력하면 어떤 과정을 거치는가?

DNS로 IP 주소를 찾고, TCP 연결을 맺고, HTTP 요청을 보내어 응답을 받는 과정이다.

1. **브라우저 → DNS** — 도메인으로 IP 조회
2. **DNS → 브라우저** — IP 주소 반환
3. **브라우저 → 서버** — TCP 3-Way Handshake
4. **브라우저 → 서버** — HTTP 요청
5. **서버 → 브라우저** — HTTP 응답

먼저 브라우저와 OS로 부터 캐시된 IP를 확인한다. 없으면 DNS 서버에 재귀적으로 요청하여 서버의 IP 주소를 알아낸다.

그 후 TCP 3-Way Handshake를 통해 신뢰성 있는 연결을 맺는다. HTTPS의 경우 TLS Handshake 과정이 추가되어 데이터 암호화 세션을 구축한다.

마지막으로 HTTP 요청 메시지를 생성해 전송하고, 서버는 이를 처리해 HTML 문서와 같은 리소스를 반환한다. 브라우저는 이를 렌더링하여 화면에 표시한다.

## HTTPS는 HTTP와 무엇이 다른가?

HTTP에 SSL/TLS 프로토콜을 추가해 데이터를 암호화한 것이다. 이를 통해 도청, 변조, 위조를 막는다.

위가 위층이다.

| 층 | 설명 |
| --- | --- |
| HTTPS | HTTP + SSL/TLS |
| HTTP | 평문 전송 |

전송 계층 위에 SSL/TLS라는 보안 계층을 얹은 구조다. 클라이언트와 서버가 서로의 신원을 확인하고 암호화 키를 교환하는 과정이 핵심이다.

대칭키로 데이터를 빠르게 암호화하고, 비대칭키로 그 대칭키를 안전하게 전달한다. 성능 저하를 최소화하면서 보안성을 챙긴 방식이다.

인증서 기관(CA)의 서명을 통해 서버가 가짜가 아님을 보증한다. 인증서가 없으면 암호화는 가능해도 상대가 누구인지 알 수 없어 피싱에 취약하다.

## 쿠키와 세션의 상태 유지 방식은 무엇으로 구분하는가?

저장 위치의 차이다. 쿠키는 클라이언트의 브라우저에, 세션은 서버의 메모리나 DB에 데이터를 저장한다.

| 기준 | 쿠키 | 세션 |
| --- | --- | --- |
| 저장 위치 | 브라우저 | 서버 |
| 데이터 크기 | 제한적 | 사실상 무제한 |
| 보안성 | 낮음 | 높음 |

쿠키는 네트워크 요청마다 자동으로 포함되어 전송된다. 서버는 이를 통해 사용자를 식별하며, 별도의 저장소 없이 상태를 유지한다.

세션은 서버에 데이터를 저장하고 클라이언트에 세션 ID만 전달한다. 실제 데이터는 서버가 관리하므로 쿠키보다 보안성이 높다.

분산 서버 환경에서는 세션 불일치 문제가 발생한다. 이를 해결하기 위해 세션 클러스터링이나 Redis 같은 외부 저장소를 사용한다.

## HTTP 메서드 선택 기준은 무엇인가?

리소스의 상태를 변경하는지, 요청이 멱등한지를 기준으로 선택한다.

| 기준 | GET | POST | PUT | PATCH | DELETE |
| --- | --- | --- | --- | --- | --- |
| 상태 변경 | 없음 | 있음 | 있음 | 있음 | 있음 |
| 멱등성 | 멱등 | 비멱등 | 멱등 | 비멱등 | 멱등 |

GET은 조회 목적이며 서버 상태를 바꾸지 않는다. 캐싱이 가능해 응답 속도를 높일 수 있다.

POST는 새로운 리소스를 생성하거나 서버의 상태를 변경할 때 쓴다. 요청할 때마다 결과가 달라질 수 있어 비멱등하다.

PUT은 리소스를 전체 교체한다. 동일한 요청을 여러 번 보내도 결과가 같으므로 멱등하다.

PATCH는 리소스의 일부만 수정한다. 구현 방식에 따라 멱등할 수도, 비멱등할 수도 있어 주의가 필요하다.
